# Agent Note: 管理 agent 调度 Claude Code 与独立验收

Status: proposed

## Problem

项目需要把需求、代码和验收责任分开，并将当前工作交给其他管理 agent。若继续依赖聊天历史、旧 M0 状态文字或由代码执行器自报通过，接手方会重复询问或错误推进。用户希望日常低风险工作自动进行，只在高风险和预算边界介入。

BATCH-001 的独立审查已发现遗漏原始 Claude 成功记录、重复执行、时间统计及状态不一致等问题。用户还明确会把项目复制到其他 Windows 设备继续工作。交接必须保留未提交成果和全部相关运行记录，同时排除本机凭据，并让接手方分清“历史通过”与“新机已验证”。

## Proposal

沿用现有 docs/tasks 作为事实源，由具备终端与文件能力的管理 agent 负责任务、风险、Note、验证和审查，通过 Claude Code CLI 交付代码。管理 agent 先固定范围与验收计划，再调度单一代码执行器，独立核对差异和执行验证。

用户已指定每任务最多 3 轮修复、90 分钟，每批最多 3 个任务，不设置费用上限。合并与发布沿用此前人工确认；不把未回答的自动合并偏好当作授权。

操作规范见 [HANDOFF](../../../../docs/HANDOFF.md)，换设备步骤见 [DEVICE-HANDOFF](../../../../docs/DEVICE-HANDOFF.md)，恢复入口见 [MANAGER-RESUME](../../../../docs/prompts/MANAGER-RESUME.md)，数值权限见 [EXECUTION-POLICY](../../../../tasks/EXECUTION-POLICY.json)，调用约定见 [CLAUDE-WORKER](../../../../docs/CLAUDE-WORKER.md)。

真实委派和独立验证已有运行证据，但管理记录仍有待修问题，详见 [独立审查](../../../../docs/runs/BATCH-001-independent-review-20260913.md)。此 Note 尚未随代码提交落地，继续保持 proposed；不宣称控制器、跨机锁或自动迁移程序已经实现。

跨设备交接继续使用本项目的任务和权限文件，不建立第二套状态权威。先停止旧机派发并形成稳定快照，保存任务身份、所有尝试、原始截止时间、剩余额度和下一动作；新机校验快照与环境后接续。转移等待仍计入既定墙钟预算，超时必须由用户追加，不能在新设备重置。

## Alternatives considered

### 复用单一 agent 同时编码和验收

最强理由是上下文共享充分，少一个调用边界，设置和故障排查简单。现有基线已经通过同一会话产生，复用成本低。

本次未采用为默认分工，因为用户明确要求管理与编码分离，并希望 Claude 负责代码。保留现有工具验收与报告方式，但由管理 agent 独立判断结果。

### 用户逐任务直接指挥 Claude

最强理由是无需调度层，所有产品判断直接由用户掌握，过程容易观察。

本次未采用，因为用户希望减少重复沟通、执行与验收工作。用户保留高风险、预算追加、合并与发布控制，日常事务交给管理 agent。

### 立即实现完整 SDK/后台控制器

最强理由是能把锁、超时、权限回调、断点和报告校验做成可测试的程序，可靠性优于纯文字约束。

目前不作为交接前置条件，因为管理 agent 的终端工具已可调用 CLI，而现有记录问题应先收敛。若宿主不能可靠控制进程，或需要退出会话后继续工作，再另立控制器实现任务。

### 保持现状，直接复制整个目录与聊天记录

最强理由是操作最少，未提交文件和缓存都能一起带走。但当前项目缓存内已有认证令牌副本，运行中的文件也可能在复制时继续变化；聊天记录不能可靠恢复所有尝试和预算。因此使用明确清单制作稳定的交接副本，保留必要证据，排除凭据、真实数据和可重新生成的依赖。

### 用通用 workflow-kit 重新初始化当前项目

最强理由是通用工具包已有较严格的状态校验和恢复模板。但它的 POLICY、DECISIONS 等字段与 FluxReader 现有 EXECUTION-POLICY 和 PRODUCT 决定表不同，直接初始化不能作为迁移方案。先复用其恢复原则；若要接入辅助脚本，另立适配任务，保留现有任务身份和授权。

### 只用一个干净 Git 提交移交

最强理由是源码、文档和回滚基准容易绑定，长期应优先采用获准工作分支提交。但当前重要文档和代码仍未提交，单独 clone 或复制旧交接包会漏掉成果。当前交接需同时保留完整工作区快照和必要的 Git 历史或基准信息；不能以交接为由自动提交、推送或合并。

## Acceptance criteria

- 新管理 agent 能从文件得知当前基线、功能范围、授权和首批任务，不要求原会话历史。
- 所有 OPT 保留，OPT-004 的非敏感数据边界不被扩大。
- Claude 不修改需求、授权、验收标准、任务状态或发布配置；管理 agent 检查真实差异。
- 基础验收由管理 agent 独立执行，并绑定具体候选版本。
- 达到 3 轮修复、90 分钟或批次 3 任务上限时停止，不重置计数。
- CLI 权限不足、输出缺失或必要证据未取得时不能标为通过。
- 已有委派证据及审查发现一起移交，不能把成功记录遗漏后回退重做。
- 新机自行发现仓库根目录和 CLI 路径，不依赖原机盘符；全部接手设备按用户确认的 Windows 条件检查工具链。
- 明确交接副本包含及排除的文件，校验文件内容；新机环境结果单独记录，不把旧 PASS 当作新机 PASS。
- BATCH-001 已满额，新机不能自动开启下一批；本次交接准备不改变批次或代码任务授权。

## Risks

文字规则和工作区隔离不能替代操作系统沙箱。CLI 版本、认证和宿主工具能力也可能不同。本机成功调用不能证明新设备已经配置完成；跨机“只保留一个写入者”目前由交接纪律保证，没有分布式锁。

结构化输出只约束格式，不能证明内容真实；管理 agent 必须使用自己的验证计划与报告。新工作区还必须包含未提交的治理文档，否则从旧 HEAD 创建 worktree 会缺少当前规则。

限定工具可减少隐式操作，也可能拒绝必要文件动作。应记录明确阻塞和所需权限，不使用全局绕过。认证方式应在目标机器按真实用户配置确认；历史 R-06 的批准范围仍待补充，不能把本次换设备指令当作复制凭据的授权。

此模式需要管理 agent 保持运行。后台持续推进、硬权限隔离和恢复的程序化保障尚未实现，不能对用户承诺已有。
