# Agent Note: 订阅条目与共享内容身份

Status: proposed

## Problem

当前全局 URL→文章映射先于远端 entry ID，跨源同 URL 被吞成一个条目或 CSV 副本。丢失的 feed/remote ID 所有权导致分类与五布局不可达、收藏互相覆盖；直接抓取 smartDedup 也在入库前丢弃副本。只修 URL 规范化不能恢复这类身份，正文缓存又不能继续把同文与同条目混为一谈。

## Proposal

保留技术栈和外部条目 ID，把订阅条目与内容分成两个连续、可验收的阶段。

第一阶段先确保身份不丢：协议 entry ID 优先，URL 兜底限制在同源，跨源各有持久条目；读广播显式选择同文条目，不让读/藏状态因共用一行而隐式传播。smartDedup 只影响可见集合，不删除条目身份，其列表/计数/分页/批量操作必须使用一致的集合规则。其他布局/源内仍可访问自身条目。旧正文列暂时保留，避免一次不可检查的大迁移；这一中间状态不冒充已共享正文。

第二阶段追加内容实体与引用，实际正文读写、全文和 AI 产物以单一内容所有权收口。URL 只作为候选关系，不用它无条件覆盖不同源的正文或付费 AI 产物；共享策略需要明确内容等价性、修改后分叉/修订和缓存失效。条目 own feed、guid/remote ID、读藏、版本、队列独立保留。最终不得留下两个长期正文真值或只有新表无人消费的接口。

历史已丢弃的副本只能由真实远端重拉恢复；旧 CSV 缺 feed/正文，不能据其猜建完整行。兼容期间不清掉待推用户意图，恢复后精确绑定与队列目标必须可追溯。

## Alternatives considered

### 仅增加 remote_dup_ids 的字段或扩大 URL 映射

改动小，能够继续广播远端 read，但仍无法独立表示副本 feed、收藏和列表可达性；没有解决本卡实际身份丢失问题。

### 一次替换所有表、IPC与前端缓存

可直接得到统一模型，但迁移、同步与渲染一起变动很难定位回归。分两阶段保留可运行中间态，第二阶段仍承担完整内容分离目标，不以第一阶段通过替代最终验收。

### 所有跨源 URL 相同就共用同一份可变正文

存储节省明显，但不同源可能是摘要、全文或更新版本，URL等同不能证明内容等同。内容共享必须有独立安全规则，不能让一个源的抓取反向覆盖另一个源的正文/AI。

## Acceptance criteria

- 两协议、直连抓取的同 URL 跨源条目都可达，各自 remote ID 和收藏独立；read广播与撤销读范围明确，版本/队列仍原子。
- smartDedup 开关不永久丢条目，列表/计数/搜索/keyset分页/批量操作集合一致，五布局和单源可达不回退。
- 历史升级保住 ID、状态、队列、正文与 AI；失败回滚，可重新打开继续；不造缺资料的旧副本。
- 最终 contents 被所有真实正文读写消费者使用，删除/断开不删别的条目仍引用的内容，修订后缓存不串。
- 每阶段本地门禁、独立初审与主控复审；迁移和跨模块风险有真实生产API/隔离库测试，提交级 Windows CI 承担生产平台验证。

## Risks

模型改动可能改变聚合数量、排序、读广播与缓存刷新。两个阶段均要显式描述中间态与未完成部分；阶段一不把新结构标implemented，最终落地后再转换Note状态并更新相关原Note事实。未知真实服务端历史不使用用户账户作破坏性试验。

- 智能去重改为**查询显示聚合**（scope × 视图内按 url 组选最小 id 代表）：列表/计数/keyset 分页/锚定/markAll 共用同一 SQL 谓词族；搜索在**关键词匹配集合内**选代表（同 URL 副本 A 不含词、B 含词时 B 不被隐藏），命中行可真实打开（位置缺失回退按 id 打开）。**R2**：回退打开改为真实组件取证——真实搜索面板点击后 Reader 实际渲染标题/正文、Escape 返回空态、当前布局不伪造他人卡片、注入不动分页游标且可见集合仍按布局过滤（`tools/component-tests/search-cross-layout.test.mjs`）。
- 读政策显式化：用户读入口（单条/批量/markAll）本地半边 = 当前行 ∪ 同 `url_norm` 未读副本，原子更新读值/字段版本/队列（同事务；markAll 冻结一次目标集合后入队+标读同事务，此后该 scope 未读真的为空，不依赖远端收敛）；unread/star 只当前条目；拉取侧同轮**读优先（读到哪算读）**：任何已读信号落定后 own unread 不再翻转（两种处理顺序结果一致，pending/字段版本守卫优先）；unread 永不广播。**R2**：前端经**读写入回执行**（`set_read`/`set_read_bulk` 返回真实翻转行、markAll 返回影响数）让受影响条目/视图缓存/按源计数本地收敛（默认去重关闭时同样成立，不再只改单行/只改计数）；Fever 轮终对账在「翻回未读」方向对**本轮**读信号让位（同轮广播不撤销），下一轮远端显式 unread 正常复活；「同组已读」查询只认本轮信号（`group_has_read_this_round`），历史本地已读不永久阻挡；集合拉取失败整轮跳过对账、完成时间不推进、失败轮广播不回滚。**R3**：回执按**行×字段写序号**逐行判真冲突——无关 URL 组的后续写不再使整批回执行失效；被较新 unread 接管的行不翻状态、计数不无条件扣（回执=请求时刻的后端提交，≠当前状态）；reload/filtered/anchor 在发起时刻捕获本地写前沿，旧响应不得把已被写过的行×字段翻回（未写字段照常取快照真值，新鲜读取仍接受外部状态）。
- 计数口径：`feed_counts` 保持布局无关的按源精确计数（回退底座）；`scope_counts`（全部/分类/源，按布局过滤）存 `scopeCounts` 快照（带 layout/dedup 元数据），选择器**布局与开关都匹配**才消费——旧布局/旧开关口径快照不得显示。**R2**：`counts_snapshot` 单条 IPC（同一 DB 锁内源/聚合同刻、同一开关值）；reload 与写后对账共享提交令牌（发起序号 + 在途未提交读/藏写**引用计数**），旧 reload 不覆盖新对账、反过来亦然，在途意图（含读/藏多笔）期间任何快照不落地；读取失败保留同 scope 已确认值；两套 harness 的 `resetStore` 清快照。**R3**：reload 的计数落地再加「读取发起后的本地写前沿」比对——已提交的点读/藏计数不被旧响应覆盖（web 缓存/条目字段同理，见上条）。
- 设置持久化：`smartDedup` 等 app_settings 写入串行化；**R5 起载荷统一从「已确认基线 + 本笔已校验 patch」生成**——每笔写不再发送「当前乐观全量快照」：确认基线（后端原文，写成功后按提交序推进；新鲜读取/应用回读/有界校准均可刷新）为底，叠加**本笔**键值；待写意图按发起序排队，**乐观 UI = 基线 + 仍有效意图的投影**（失败意图出队即回投，不残留"永远成功"的乐观值；后续失败意图不会被打包进更早请求，旧请求也不偷提交更晚意图）。基线未知（从未读到 / 应用回读失败）时：发送前做**一次有界校准读取**，成功即以原文为底再发；失败则不发送（可见失败、不改库、本笔键按乐观前值回显），持续失败可随下次成功读取/重试恢复——不以旧全量覆盖未读回的远端键。写入仍串行、成功推进确认基线并（含 dedup 的本笔）触发 reload；失败如实 toast，仅该笔出队回投（同键 A 18/B 16 相反序时 A 的载荷=基线+18、B 失败回投到基线，不回退到"点击前旧本值"）。**R6（主控两条真实反例）**：①失败意图的键被更晚未落定意图覆盖时，把**稳定底值**下传给它们的 prev（空/partial/未知基线的同键连续失败回投到初始底值，不经"失败笔乐观后的中间值"残留）；②共享读取（单飞）凭据绑定**发起时**写序号与应用代次——跨提交的等待者不得 join 为新鲜（bootstrap 发现旧读强制发起新鲜读取；校准只复用同代次在途读；应用回读/置未确认推进应用代次）。**配置应用边界**（`runAppSettingsApplyBoundary` + `readBackAppliedAppSettings`，`ConfigSyncSection` 真实 apply/upload 接线）：应用窗口内新点击乐观可见、请求排在应用+回读之后；**回读落地=设置新基线，窗口内点击键由投影保留**（不需专门的保留键集合）；上传只等发起时前沿（`awaitAppSettingsWriteFrontier`），不设门；回读失败经 `markAppSettingsUnconfirmed` 置基线未知（不假称已恢复）。读取侧凭据保留（R3/R4）：写序号+已发出未落定写数+**读取发起序号**（后发起者优先，应用/回读期间更早的启动读取落地即过期）；bootstrap 先等**捕获时**写前沿落定（不依赖 IPC FIFO；提交/回应分离时序有回归）。
