# Agent Note: 画廊列虚拟化及尚未成立的窗口上界

Status: implemented

## Problem

原画廊对全部条目做 CSS 多列布局，缺少规模上限。只渲染其中一个窗口又会令浏览器重新平衡列，无法保留原位置；改等高卡会牺牲自然图片比例。后续异步图片测量还暴露了多列补偿叠加与单帧锚漂移。

## Decision

沿用安装版 @tanstack/react-virtual 3.14.10 的 lanes，按最短列分配条目；2/3/4列断点、14px间距由 GalleryLayout.ts 管理。网格项绝对定位，宽度与左缘由 React 设置，纵向位置和总高交给虚拟化。自然图片比例保留，加载前只用比例占位。

画廊使用 directDomUpdates、containerRef 和 useFlushSync:false，由库维护主轴；overflow-anchor:none 排除浏览器第二次补偿。测量时选择一个可见锚，只补偿它同列前驱的高度变化，滚动或上下文变化后重新选锚。这是当前实现及其意图，不构成过程稳定性已达标的结论。

galleryMountBound 曾按“每列可见量 + overscan”估算窗口，参考视口/卡高得到48的口径。2026-11-06 反例已推翻其普遍有效性：默认 range extractor 返回全局连续索引，列间高度偏差会让这段索引包含大量屏外卡；仅代入最小卡高不能证明逐列上界。该函数和旧均匀夹具只能作为特定分布的检查，不能再称“任何视口/卡高都成立”。

画廊的 J/K 已由[全布局键盘决定](../architecture/2026-11-04-全布局键盘焦点与响应式阅读列.md)接入，按条目索引导航。跨上下文顶条恢复仍保留画廊回落边界；测量锚只服务当前异步测量，不替代返回位置协议。

## Alternatives considered

保留 CSS 多列再截取窗口会重新分列；等高/裁切模型改变既有图片比例体验。自研列分配、测量、可见集和 scrollToIndex 的维护面大于复用已装库，所以选 lanes，但库提供 lanes 不等于默认范围提取器已满足本项目的上界。

默认补偿会把其他列的高度差也加到同一个 scrollTop；只修 flex-shrink 不能解决这一问题。限制为同列锚、禁原生锚是已有选择。固定截断到24或48张则可能小于大视口的实际可见量，不能用删可见卡的方式满足数值。

## Consequences

列分配从 CSS 列优先平衡变成最短列贪心分配，列归属变化是已接受代价。虚拟化减少了均匀场景挂载量，但“只由视口决定”的复杂度承诺尚未成立。

2026-11-06 在5000条混合比例 fixture、1440×900视口、8100px位置实测挂载192、可见17，公式上界48；均匀对照挂载28、上界28。更深位置可达504，且 Tab 可进入屏外挂载项。另一个现有 Edge 门禁反例中同一锚从211px到52px再回211px，恢复终点没有满足每帧漂移≤3px的验收。两项见[界面与媒体路线](../../../../docs/roadmap.md#interface-and-media)，不能把历史零漂移结果覆盖到当前版本。

下一次修正需分别证明可见集/焦点界和测量提交时序；单独切换 flushSync 尚无已验证结论。同时固定一个锚也不意味着所有列的所有卡片都应静止。

## Validation

组件 gallery-virtual 与前端 gallery-window 覆盖装配、索引、灯箱和已设定几何；Edge ui-layout-regression 用真实延迟 HTTP 自然比例图逐帧记录锚、scrollTop和节点。当前反例要求混合高度、深滚动及屏外焦点覆盖，不能只保留均匀估算样本或只验最终帧。Edge不等同于真实Tauri WebView2的合成/字体表现。
