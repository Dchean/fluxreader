# Agent Note: 同步灯与账户状态

Status: implemented

## Problem

侧栏把「等待同步 N 条」「部分失败」和账户连接状态都塞进同一行常驻文字，数量一多就
打断阅读；账户名又只存在于 SyncTab 的局部 state，启动/保存/断开/手动同步结束后没有
一个跨组件的同步账户事实源。与此同时侧栏保留了两个同义的刷新入口（状态行小图标与
「刷新全部订阅源」大按钮），用户无法判断哪一个才是同步。

AddFeed 还有两处会制造错误预期：同步开关默认开，Fever 也显示该开关；`sync_local_feeds`
只返回人类可读字符串，部分失败被前端当成完整成功。Fever 没有订阅写回端点，不能把
「准备入队」或「跳过写回」展示成「已同步」。

## Decision

**账户/协议/上次同步的事实源固定为 `sync_status`。**
`syncConnected/syncAccount/syncProtocol/syncEndpoint/syncLastSync` 由同一动作原子写入；
bootstrap、连接保存、断开、手动同步与 AddFeed 尾链都刷新这一快照。GitHub 的
`githubAccount` 是另一条登录链，禁止作为同步账户回退。

**队列与订阅 outbox 仍是事件驱动。**
`sync_queue_stats` 的完整生命周期分类和 `subscription_outbox_stats` 的当前账号回执
分别经事件、reload 与设置页挂载写入 store；UI 不轮询，也不新增调度器。后端
`sync-running/sync-idle` 只驱动「同步中」展示，成功短窗只来自手动同步或保存并同步的
真实成功终态，不能由后台 idle 推断成功。

**侧栏指示器是展示状态机，不是第二套同步状态机。**
常驻文案优先级为：同步中 > 空闲失败 > 成功短窗（2.4 秒）> 同步账户名；
未连接/无有效账户回落「本地模式」。`syncStatus === 'error'` 与
`backgroundSyncing === true` 同时成立时必须显示「同步中」——本轮仍在运行，
旧失败只能进详情；活动结束后仍为 error 才进入红色失败态。数量、错误与分类只进
tooltip / `aria-label` / 隐藏 live region / 设置摘要，不再把「等待同步 N 条」
写进常驻文字。

成功短窗只在已连接且有账户、队列与订阅 outbox 均无待处理/失败时显示；仍有欠账
保持橙色。已连接但 `account` 为空不是成功态：侧栏显示灰色「本地模式」，
SyncTab 连接状态明确写「未验证（账户缺失）」，不得用 `connected=true` 冒充已验证。
订阅 outbox 为 `null`（未加载/读取失败）同样不是 0：不能进入成功短窗或「本地已保存」，
侧栏保持待处理色并在详情写「订阅状态未加载（未知）」，设置页标签为「订阅未知」。
两类未知同时出现时，**账户缺失优先决定灰色「本地模式」**：只有已验证账户 + outbox
未知才进入橙色 pending；不得让未知 outbox 把无账户状态误报成待同步。
同步活动的终态按 generation 收敛：只有比已发布终态更新的 token 才能写入
`syncSucceededAt`，旧活动的迟到成功/失败不得点亮或清掉较新的成功窗口。

| tone | 条件 | 视觉 |
| --- | --- | --- |
| `syncing` | 手动或后台同步进行中 | 橙色呼吸 |
| `error` | 空闲时手动失败，或存在队列/订阅失败 | 红色 |
| `success` | 成功短窗，或已连接且无待处理/失败 | 绿色 |
| `pending` | 仅本机、待推送、等待绑定、过期未确认或 outbox pending | 橙色 |
| `local` | 未连接且无待处理 | 灰色 |

同步中即使队列里仍有旧失败，也显示「同步中」而不是「同步失败」；新活动开始不会
抹掉上一终态的失败摘要，原因继续可在 tooltip/aria 查询，结束后由新一轮终态替换。
最近错误合并状态队列与订阅 outbox 两个来源（去重后并列），避免一个来源覆盖另一个。
`prefers-reduced-motion: reduce` 关闭呼吸，不改变语义色。

用户可见的同步文案统一使用「同步服务 / 同步账户 / 本地模式」口径，不再把连接对象
写成「后端」；设置分组、地址卡、断开/首连确认框与 AddFeed 开关都遵循同一命名。

**入口语义唯一。** 左侧圆点是手动同步按钮（忙时 disabled），账户文字是同步设置入口；
侧栏小刷新图标与同义大按钮删除。命令面板/右键菜单的既有刷新入口不在此收口范围。

**SyncTab 逐类显示真实欠账。** 「同步状态」同时消费 `SyncQueueStats` 与
`SubscriptionOutboxStats`：状态待推送、订阅变更待推送、仅本机、等待绑定、过期未确认、
失败分别呈现；只要任一 unresolved，标签就不能是「本地已保存」，全文也不出现
「后端已同步」。

**表单刷新不得覆盖用户输入。** SyncTab 挂载、设置重新打开、连接身份
（connected/account/protocol/endpoint）变化时会重读 `sync_status`；用户修改协议、
地址、用户名或密码即标记 dirty。读取返回后必须复核 dirty 与请求序号：dirty 时保留
输入（包括读取发起后才开始的编辑），只有未编辑的最新响应才能回填表单。断开仍显式
清空密码并应用断开状态；成功保存后清除 dirty。

**`sync_local_feeds` 返回结构化回执。**

```text
{ ok, protocol, writeBack, queued, pushed, failed, errors, message }
```

部分失败返回 `ok=false` 且 `failed/errors` 非空；调用方不得按字符串或「命令返回 Ok」
推断全域成功。Fever 在入队前返回 `writeBack=false`（不入队、不发网络请求），不冒充
写回。旧后端只返回纯文本时，前端返回 `structured=false` / `ok=false`，提示
「无法确认同步结果」，绝不把人类可读字符串折叠成成功；可解析为 JSON 且带 boolean
`ok` 的兼容回执仍按结构体接受。

AddFeed 的定向同步传入 `{ feedId?, feedUrl }`：Rust 先按 id 或规范化 URL 解析目标，
再把**精确 scope** 下推到实际执行器，而不是只在入队/计划层做 URL 过滤：
`FeedsPushScope.legacy_add_queue_ids` 限定 `push_feeds` 可消费的 legacy `add_feed`
队列 id，`subscription_outbox_ids` 限定 `push_subscription_outbox` 可消费的
`subscribe` outbox id。定向执行只重绑本次选中的 outbox id，不清理其它僵尸队列；
已有 pending 的 subscribe、edit/move、unsubscribe 与 legacy 队项全部原样保留。
`Some(空集合)` 是合法的「不推任何项」，不得回退成全量；只有 `None` 才保持手工
「同步本地订阅」的全量语义，全量路径仍执行所有预置动作。显式传入但 trim 后为空的
`feedUrl` 在 TS 层发 IPC 前就拒绝，Rust 命令层也返回 `validate` 错误，避免空 selector
被解释成全量同步。AddFeed 的 GReader 开关默认关闭，只控制本次新增；Fever 隐藏开关
并明示仅本地。协议从 GReader 切到 Fever 时前端清空旧勾选，Rust `add_feed` 仍独立
执行写回协议门——两道门都必须在，不能只信 UI。部分失败 toast 为「已添加，N 项未同步」，
保留只重跑同步段的重试入口。

## Alternatives considered

### Why not 保留「等待同步 N 条」并缩短文案？

数量是动态的，任何常驻长度都会在长队列时挤占账户/阅读空间；用户需要知道的是
「账户是否健康」，具体欠账按需在 tooltip 或设置页展开。短文案只降低概率，没有消除
阅读干扰。

### Why not 在前端维护同步调度或定时轮询？

后端已有 scheduler 和队列/outbox 事件；前端再维护一套节奏会产生双写、竞态和额外
网络请求。前端只消费既有事实，成功短窗是纯展示计时，不改变后端任务。

### Why not 用延迟返回的 `sync_status` 无条件回填表单？

读取有网络/锁等待窗口。用户可能在请求发出后开始编辑；返回时无条件 `setState` 会把
新输入改回旧身份，甚至让用户以为凭据已切换。按 dirty + 请求序号复核，才能同时满足
「外部身份 A→B 时重开显示 B」与「正在编辑的草稿不被覆盖」。

### Why not 解析 `sync_local_feeds` 的中文回执判断成功/失败？

文案是展示层，不是契约；拆分字符串无法稳定承载成功数、失败数与错误列表，也会把
未来文案微调变成行为变化。结构化回执让部分失败能被同一份数据驱动 toast、重试和
同步灯。纯文本旧回执无法区分「全部成功」「部分失败」「根本没执行」，只能如实标为
未知并保留重试，不能靠关键词猜测。

### Why not 在 Fever 下保留开关并自动置灰？

置灰仍会让用户以为存在一个可理解但暂不可用的远端写回路径；Fever 根本没有订阅写回
端点，最诚实的是不渲染开关，并在同一位置说明仅本地。

### Why not 用后台 `sync-idle` 直接显示「同步完成」？

idle 只说明调度器当前不在运行，不证明本轮成功；失败也会回到 idle。用 manual /
save-and-sync 的真实成功终态写时间戳，才能把「完成」建立在可验证结果上。

## Consequences

- 侧栏更安静，账户名成为常驻主信息；欠账仍可经 tooltip、aria 与设置页完整追溯。
- 成功提示只持续 2.4 秒，适合确认动作完成，不适合作为长期成功记录；长期事实仍看
  设置页的上次同步时间。
- `sync_status` 与队列事件读取失败时保持原值，不把未知折叠成未连接/无待办。
- 账户缺失优先按「未知/未验证」呈现灰色本地模式；只有已验证账户 + outbox 未加载
  才进入橙色 pending。这是把无法证明的状态从成功色中移出，而不是新增后台任务。
- AddFeed 部分失败不再显示完整成功；用户在 toast 或同步页可重试，重试不会再次
  新增订阅。
- AddFeed 定向同步减少误推已有本地源；手工「同步本地订阅」仍保留全量语义。
- Fever 的「同步本地订阅」按钮不显示，能力卡继续声明仅本地；旧调用方即使直接调用
  `sync_local_feeds` 也只得到 `writeBack=false` 的结构化结果。
- 仍有未知：终端 `failed` 的恢复仍依赖现有全量 states 重排，没有新增清理入口。

## Validation

sync-indicator纯函数/store和真实组件覆盖灯优先级、未知状态、旧终态归属、dirty表单与请求序号；AddFeed和subscription-writeback覆盖默认开关、部分失败、旧文本回执未知及按原目标重试。Rust命令夹具验证精确scope确实下推执行器，Some(空集合)不回退为全量，Fever两层能力门均拒绝订阅写回。

这些用例是该决定的回归入口，不是所有同步路径都无缺陷的证明。后端真实事件、真实账号服务和窗口动效另需运行证据；当前未关闭项见[同步正确性路线](../../../../docs/roadmap.md#sync-correctness)。
