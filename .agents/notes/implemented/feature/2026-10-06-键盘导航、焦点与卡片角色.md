# Agent Note: 键盘导航、焦点与卡片角色

Status: implemented

## Problem

五布局（文章 / 社交 / 画廊 / 播客 / 通知）在无障碍与键盘交互上长期不一致，两个方向的问题同时存在：

**不可达。** 列表卡片是 `div` + `onClick`，键盘无法聚焦，读屏也看不见；J/K 只在文章布局生效，其他布局的用户没有键盘导航；「滚动出列表即标为已读」这类行为在非文章布局上不成立。

**可达但语义错误。** 修可达性的最省事做法是给卡片加 `role="button"`。但社交卡与通知卡内部**嵌套**了动作按钮、链接与重试控件——按 ARIA 规则，`role="button"` 会把交互后代从可达性树里掩蔽，于是卡片可聚焦了，卡内的按钮却从读屏里消失。这是把一个问题换成另一个更隐蔽的问题。

浮层还有第三种：`ModalOverlay` 无条件渲染 children，关闭态只用 `opacity: 0` + `pointer-events: none`。视觉上关闭，但内容仍在无障碍树里，Tab 能进去——用户会 Tab 到看不见的控件上。

## Decision

**卡片维持 `role="article"`。** 需要的键盘行为通过属性与事件实现：`tabIndex` 参与 roving、Enter/Space 触发 `onSelect`、`e.target === e.currentTarget` 守卫防止卡内按钮的点击冒泡后被当成本卡的选中。对齐的是**行为**而不是角色。`role="article"` 对读屏的含义是「独立的内容单元」，与卡片的实际结构一致。

**成组控件用 roving tabindex。** 列表里只有一个卡片可被 Tab 进入，组内方向键移动——这是标准做法，避免「一次 Tab 走过 500 张卡片」的 Tab 爆炸。J/K 与 roving 共享同一套索引计算，两种导航方式不会走到相反方向。

**J/K 的门控用「排除 image」而不是白名单。** 即 `jkLayoutAllowed(layout)` 返回 `layout !== 'image'`（`src/lib/jkNavigation.ts`，纯函数，可单测）。用意是：将来新增虚拟化布局时自动获得 J/K，不需要记得往白名单里加一项。画廊不支持 J/K 是明确的产品判断，快捷键页必须明示这一点。

**浮层关闭态必须显式加 `inert`。** `ModalOverlay` 与 Lightbox 都用 `inert={!open}`；关闭时若焦点正在浮层内，必须移出（回触发元素或 body），不得停在 inert 节点上。`ConfirmDialog` 与 `ContextMenu` 已经条件渲染（关闭时早退 `null`），无需 `inert`——这是「非目标」的判定依据，不是遗漏。

**焦点管理只做最小实现：打开时聚焦容器，关闭时归还触发元素。不做 focus trap。** 这是刻意的范围决定：trap 会与自定义的 roving、画中画播放器、Esc 链互相作用，改造面远超收益；当前的最小实现已经解决「关闭后焦点丢失」这个真实痛点。

**Esc 关闭顺序与视觉层级一致**：确认框（3000）> 弹窗（150）> 全屏播放器（140）。浮层集合由 `OVERLAY_SOURCES` 清单定义、`anyOverlayOpen` 求值（`src/components/shortcutYield.ts`），单键快捷键在这个清单非空时让路——清单是唯一来源，加新浮层要加进清单。

**快捷键提示格式统一为紧凑加号形**：`Ctrl+K`、`Ctrl+,`、`Esc`。禁止 `Ctrl K`、`Ctrl + K`、`ESC 关闭` 这类写法。

## Consequences

**收益**：五布局键盘可达且语义正确；读屏能看见卡内控件；关闭的浮层不再吃 Tab；单键快捷键让路浮层有单点判据。

**代价与已知上限**：

- 没有 focus trap，因此在弹窗里 Tab 到最后会走到弹窗外的元素（视觉上被覆盖但可聚焦）。这是已知的不完美，重访信号是「用户报告在弹窗里 Tab 到看不见的控件」。
- 卡片的键盘行为靠若干条规则（roving、Enter/Space、`e.target` 守卫）共同成立，缺一条就退化；这些规则分散在 `Timeline.tsx` 的各分支里，靠注释与回归断言锁住。
- `OVERLAY_SOURCES` 是手工清单。曾经的失败模式正是清单漏项：`closeAsk` 未进清单，于是确认框打开时单键快捷键仍然生效。
- 「滚动出列表标为已读」**只在「显示: 未读」模式下生效**（`Timeline.tsx` 里的 `if (timelineFilter !== 'unread') return;`），设置页文案至今未声明这个前置条件。这是已知的文案缺口，见 [docs/roadmap.md](../../../../docs/roadmap.md)。

## Alternatives considered

### Why not 给卡片加 `role="button"`？

那是最省事的可达性修法，但会把卡内的动作按钮、链接与重试控件从可达性树里掩蔽——按 ARIA 规则，`role="button"` 的交互后代应被读屏忽略。用户会得到「卡片能聚焦了、但卡内按钮读不到」的结果，比原来更糟。保留 `role="article"` 并在行为层对齐才是正确修法。

### Why not 用 focus trap？

trap 需要与 roving tabindex、Esc 链、全屏播放器、画中画共存，每一对交互都要单独定义优先级（例如播放器展开时 Tab 该去哪）。这套规则的成本与收益不成比例——当前真实的用户痛点是「关闭浮层后焦点丢失」，最小实现已解决。审计也把组件级测试通道列为独立评估项，未把 trap 当作必须。

### Why not 用白名单列 J/K 支持的布局？

白名单的问题是新增布局时会静默丢失能力（忘了加 → 快捷键在新区不生效 → 用户以为是 bug）。排除法的语义是「除了画廊都支持」，与产品意图一致，且新增布局自动获得。

### Why not 给所有浮层统一加 `inert`？

`ConfirmDialog` 与 `ContextMenu` 关闭时不渲染任何内容，加 `inert` 是无的放矢；把它们也纳入会让「哪些浮层需要 inert」这个判断失去含义——判据应该是「关闭时是否仍渲染内容」，而不是「是不是浮层」。
