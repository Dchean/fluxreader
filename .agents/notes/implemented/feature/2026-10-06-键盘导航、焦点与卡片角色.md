# Agent Note: 键盘导航、焦点与卡片角色

Status: implemented

## Problem

五布局（文章 / 社交 / 画廊 / 播客 / 通知）在无障碍与键盘交互上长期不一致，两个方向的问题同时存在：

**不可达。** 列表卡片是 `div` + `onClick`，键盘无法聚焦，读屏也看不见；J/K 只在文章布局生效，其他布局的用户没有键盘导航；「滚动出列表即标为已读」这类行为在非文章布局上不成立。

**可达但语义错误。** 修可达性的最省事做法是给卡片加 `role="button"`。但社交卡与通知卡内部**嵌套**了动作按钮、链接与重试控件——按 ARIA 规则，`role="button"` 会把交互后代从可达性树里掩蔽，于是卡片可聚焦了，卡内的按钮却从读屏里消失。这是把一个问题换成另一个更隐蔽的问题。

浮层还有第三种：`ModalOverlay` 无条件渲染 children，关闭态只用 `opacity: 0` + `pointer-events: none`。视觉上关闭，但内容仍在无障碍树里，Tab 能进去——用户会 Tab 到看不见的控件上。

## Decision

**卡片维持 `role="article"`。** 需要的键盘行为通过属性与事件实现：`tabIndex` 参与 roving、Enter/Space 触发 `onSelect`、`e.target === e.currentTarget` 守卫防止卡内按钮的点击冒泡后被当成本卡的选中。对齐的是**行为**而不是角色。`role="article"` 对读屏的含义是「独立的内容单元」，与卡片的实际结构一致。

**侧栏源行不再把动作按钮嵌套进 `role="button"` 容器（2026-11-04）。** 主选择区改为真实 `button.feed-leaf-select`，刷新/编辑是同级真实按钮；Tab 顺序为“选择 → 刷新 → 编辑”。动作区在 hover 与 `:focus-within` 时可见，键盘路径关闭 `visibility` 过渡以免 Tab 跳过。这样同时消除 DOM/AX 的 button 嵌套，不再需要给 `div role="button"` 手写 Enter/Space。决定与取舍见[全布局键盘焦点与响应式阅读列](../architecture/2026-11-04-全布局键盘焦点与响应式阅读列.md)。

**播放器 Space 先让路原生交互控件（2026-11-04）。** `isInteractiveSpaceTarget` 覆盖真实 button/a/表单/可编辑节点/媒体 controls/菜单项与常见 ARIA 角色；卡片容器虽用 `role="button"` 承载 roving，但刻意不在清单里。播放器激活时卡片处理器直接返回，让 Space 冒泡到 App 切换播放；播放器未激活时卡片的 Enter/Space 语义不变。搜索/刷新/编辑等控件的 Space 只触发自身，不再双重动作。

**成组控件用 roving tabindex。** 列表里只有一个卡片可被 Tab 进入，组内方向键移动——这是标准做法，避免「一次 Tab 走过 500 张卡片」的 Tab 爆炸。J/K 与 roving 共享同一套索引计算，两种导航方式不会走到相反方向。

**J/K 的门控用「排除 image」而不是白名单。** 即 `jkLayoutAllowed(layout)` 返回 `layout !== 'image'`（`src/lib/jkNavigation.ts`，纯函数，可单测）。用意是：将来新增虚拟化布局时自动获得 J/K，不需要记得往白名单里加一项。**（2026-11-04 已被[全布局键盘焦点与响应式阅读列](../architecture/2026-11-04-全布局键盘焦点与响应式阅读列.md)取代：J/K 现覆盖包括画廊在内的五种布局，选中与 DOM 焦点由 Timeline 单点同步；本段保留历史取舍。）**

**浮层关闭态必须显式加 `inert`。** `ModalOverlay` 与 Lightbox 都用 `inert={!open}`；关闭时若焦点正在浮层内，必须移出（回触发元素或 body），不得停在 inert 节点上。`ConfirmDialog` 与 `ContextMenu` 已经条件渲染（关闭时早退 `null`），无需 `inert`——这是「非目标」的判定依据，不是遗漏。

**焦点管理只做最小实现：打开时聚焦容器，关闭时归还触发元素。不做 focus trap。** 这是当时的范围决定：trap 会与自定义的 roving、画中画播放器、Esc 链互相作用，改造面远超收益；当时的最小实现已经解决「关闭后焦点丢失」这个真实痛点。**（2026-11-01 部分取代：trap 已落地并收口为共享 hook，契约与翻转理由见[模态焦点陷阱与 dialog 语义](2026-11-01-模态焦点陷阱与dialog语义.md)——本段保留历史取舍，不再描述现状。）**

**Esc 分支顺序与浮层层级分开表述**：`CloseAskDialog` 与其他 `ModalOverlay` 同为 `z-index:150`，不是 `ConfirmDialog` 的 `3000`；全屏播放器为 `140`。App 的 Esc 分支先取消关闭询问，再按既有顺序关闭搜索/迷你弹窗/错误中心/设置，最后处理灯箱、全屏播放器与阅读器。浮层集合由 `OVERLAY_SOURCES` 清单定义、`anyOverlayOpen` 求值（`src/components/shortcutYield.ts`），单键快捷键在这个清单非空时让路——清单是唯一来源，加新浮层要加进清单。关闭确认框（`closeAskVisible`）与其它浮层同列清单（OPT-012 补入，第 9 项）：确认框打开时 S/M/J/K 一律让路，Esc 仍走 App.tsx 对 `closeAskVisible` 的专门分支。该分支自 2026-11-04 起只取消询问，不提交最小化/退出，也不写 remember；关闭语义见[关闭取消语义与授权关闭守卫](../bug-fix/2026-11-04-关闭取消语义与授权关闭守卫.md)。

**快捷键提示格式统一为紧凑加号形**：`Ctrl+K`、`Ctrl+,`、`Esc`。禁止 `Ctrl K`、`Ctrl + K`、`ESC 关闭` 这类写法。

## Consequences

**收益**：五布局键盘可达且语义正确；读屏能看见卡内控件；关闭的浮层不再吃 Tab；单键快捷键让路浮层有单点判据。

**代价与已知上限**：

- ~~没有 focus trap，因此在弹窗里 Tab 到最后会走到弹窗外的元素~~（2026-11-01 起已解决：`useFocusTrap` 提供打开移入/Tab 循环/关闭还原，ModalOverlay、ConfirmDialog、PlayerFullOverlay、Lightbox 四处共用，见[模态焦点陷阱与 dialog 语义](2026-11-01-模态焦点陷阱与dialog语义.md)）；重访信号（弹窗里 Tab 到看不见的控件）已被审计确认并按该篇收口。浮层关闭态仍靠 `inert`，这一半契约不变。
- 卡片的键盘行为靠若干条规则（roving、Enter/Space、`e.target` 守卫）共同成立，缺一条就退化；这些规则分散在 `Timeline.tsx` 的各分支里，靠注释与回归断言锁住。
- `OVERLAY_SOURCES` 是手工清单，漏项是真实发生过的失败模式：关闭确认框（`closeAsk`）长期漏在清单外，确认框打开时 S/M/J/K 会作用到背后的文章（S/M 改收藏/已读、J/K 换文章，用户看不见），直到 OPT-012（2026-10-08）才补入并由回归网逐项钉死——清单新增项必须同步 `tools/frontend-regression.mjs` 的逐项探针与数量/名称断言。
- 「滚动出列表标为已读」**只在「显示: 未读」模式下生效**（`Timeline.tsx` 里的 `if (timelineFilter !== 'unread') return;`），设置页文案至今未声明这个前置条件。这是已知的文案缺口，见 [docs/roadmap.md](../../../../docs/roadmap.md)。

## Alternatives considered

### Why not 给卡片加 `role="button"`？

那是最省事的可达性修法，但会把卡内的动作按钮、链接与重试控件从可达性树里掩蔽——按 ARIA 规则，`role="button"` 的交互后代应被读屏忽略。用户会得到「卡片能聚焦了、但卡内按钮读不到」的结果，比原来更糟。保留 `role="article"` 并在行为层对齐才是正确修法。

### Why not 用 focus trap？

trap 需要与 roving tabindex、Esc 链、全屏播放器、画中画共存，每一对交互都要单独定义优先级（例如播放器展开时 Tab 该去哪）。这套规则的成本与收益不成比例——当前真实的用户痛点是「关闭浮层后焦点丢失」，最小实现已解决。审计也把组件级测试通道列为独立评估项，未把 trap 当作必须。

### Why not 用白名单列 J/K 支持的布局？

白名单的问题是新增布局时会静默丢失能力（忘了加 → 快捷键在新区不生效 → 用户以为是 bug）。排除法的语义是「除了画廊都支持」，与当时的产品意图一致，且新增布局自动获得。**2026-11-04 起画廊也纳入 J/K，门控改为五种现有布局显式放行；原因与焦点契约见[全布局键盘焦点与响应式阅读列](../architecture/2026-11-04-全布局键盘焦点与响应式阅读列.md)。**

### Why not 给所有浮层统一加 `inert`？

`ConfirmDialog` 与 `ContextMenu` 关闭时不渲染任何内容，加 `inert` 是无的放矢；把它们也纳入会让「哪些浮层需要 inert」这个判断失去含义——判据应该是「关闭时是否仍渲染内容」，而不是「是不是浮层」。
