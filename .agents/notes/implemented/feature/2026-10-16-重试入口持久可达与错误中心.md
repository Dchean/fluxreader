# Agent Note: 重试入口持久可达与错误中心

Status: implemented

## Problem

带重试动作的失败 toast 是很多错误路径的唯一恢复入口（刷新源、加载更多、摘要/翻译、全文提取、手动同步…20 余个 `showToast(text, { label: '重试', run })` 站点）。但 toast 层有两个上限把它们清掉：

- **容量上限**：`showToast` 的 `toasts: [...].slice(-4)` 超过 4 条时**静默丢弃最旧的一条**——后台连续失败（如多源抓取失败）时，最早重试项最先被挤掉；
- **停留时长**：带动作项 4200ms 后照样两段式退场，用户没看到窗口就只能等下一次自然触发。

父卡 OPT-017 的验收明确：不能靠无限堆 toast 解决，不能把回调存进另一个无限数组规避上限；要「统一错误中心或重试项合并/持久可达」。

## Decision

**错误中心 = 有界 + 去重 + TTL 的持久可达层（`src/store/slices/ui.ts`、`src/components/ErrorCenter.tsx`）**：

- `showToast(text, action)` 带动作时，除既有 toast（形态/时长完全不变）外**同时**写入 `errors` 数组：
  - **上限 20 条**（`ERROR_CENTER_MAX`）：超限从最旧逐出——有界内存，条目数与失败总量无关；10 连发这类小批量一条不丢；
  - **去重键 = 显式操作实体/上下文 key 优先、缺省回落文案**（R1 定稿，OPT-020 扩展）：动作对象带可选 `key`（命名 `域:操作:实体` 或 `域:操作:上下文`，如 `feed:refresh:10`、`mark:all-read:10:...`），错误中心按它合并为一条、保留最新动作/文案并落到最新位、`count` 计数；**同文案不同实体或不同操作上下文不合并**——否则多源同类网络失败（`刷新失败：<同一错误>`）或不同范围的分页失败会被并成一条、重试只能重试最新一个（R1 的 P2 / OPT-020 P1-C1）。全部带重试动作的站点都已迁移到显式 key（迁移清单：feeds 4、ai 8、reader 全文/正文 5、list:load-more、mark:all-read、sync:manual、sync:save-and-sync save/phase 常规失败与忙锁拒绝共 4），由域回归 (e9) 的源级守卫钉住；当前守卫固定 24 个 `label: '重试'` 站点；
  - 无 key 的同文案错误仍按文案合并（普通失败的既有语义，falsy key 只可能来自未迁移路径）；显式 key 条目与无 key 同文案条目**并存不合并**（不同去重域）；
  - **TTL 24h**（`ERROR_CENTER_TTL_MS`）：写入时惰性清理超期条目（生命周期上限）；纯函数 `upsertErrorEntry` / `pruneErrorEntries` 是唯一实现，store 与回归网共用。
- **UI**：入口在**侧栏底部固定区**（`sidebar-error-center`，仅 `errors` 非空时渲染，徽标显示条数）；面板是既有 `ModalOverlay` + `mini-dialog` 形态，逐条「重试 / 忽略」+「全部清除 / 关闭」；登记进浮层让路清单（S/M/J/K 让路）并由 App 的 Esc 链关闭。
- **重试语义（两个表示面同一动作 `retryError`）**：错误中心面板与瞬时 toast 的重试按钮都经它派发。**消费先于执行**——先把同 key 条目从错误中心清掉，再执行动作：
  - 成功路径以普通 toast 收尾、不重报 → 条目保持清除（「重试成功后对应条目清除」）；
  - 失败路径（各 call site 的 catch）再次 `showToast` 同 key → 在消费之后写回 → 条目保留（失败不丢入口，为下一次重试）；
  - 动作同步抛错不会触发重报 → 恢复消费前快照（同样不丢入口）。
  - id 先按条目匹配；条目已被同 key 合并/逐出而旧 toast 仍在屏上时回落到同 id 的 toast——旧 toast 的重试在屏期间始终可用（不因中心状态变化而中断）。
- **OPT-020 P1-C1：重试动作携带失败时的不可变上下文快照**：
  - `mark-all-read` 捕获 `scope/feedId/folderId/view/layout/sinceMs/starredOnly + 目标 id 集`；key 带这些范围维度。切到其他视图后重试仍向 A 范围发原参数，只有当前视图仍是 A 时才做本地乐观翻转。每次 attempt 在同一同步窗口建立 `attemptReadById/attemptFeedIdById/expectedVersionById`：当前上下文取 entries，非当前上下文取目标 `viewEntriesCache` 的当前态（版本取当前字段版本）。成功 store/cache 收敛与失败 store/cache/计数恢复都只看本次 attempt 快照并逐 id 比较版本；用户已接管条目跳过。A/B/A retry 绝不复用首次 read snapshot；A 在途切 B 后失败也按 captured feedId 回补未读计数，不依赖 current entries 是否含 A。后端 `affected===0` 只表示目标已全读，不跳过后端权威收敛：仍更新 captured cache 并执行计数对账，覆盖「首次已提交但响应丢失→切 B→重试返回 0」。
  - `load-more` 捕获 `scope/layout/sort/view/scopeKey/queryKey/firstPageGen/keyset 游标 + 完整 listArticles 参数`；key 含上下文、首页代际与锚（同范围/同游标经过一次同数据重载也属于新查询实例，不合并）。重放前校验当前查询上下文、游标和首页代际，任一漂移即安全 no-op，绝不把 A 的续页 append 到 B；失效上下文是**终态**，错误中心先消费后只给普通提示、不重新登记 retry action。若上下文仍匹配但已有续页在途，则按同一 key/动作重新登记入口且不重复发 IPC，若已到底则明确提示失效。每次请求还持单调 token；全局 `articlesLoading` 只允许当前 token 清锁，A 的迟到完成不能清掉 B 的锁。
  - reader content / fulltext / summary / translation 捕获失败文章 id；重试不再调用 `extractCurrentArticle()` / `summarizeEntry(id)` / `translateEntry(id)` 去读取当前 `activeArticleId` 或当前 `entries`，也不再以当前 entries 是否含该 id 判定文章删除——article 只是不在当前视图并不等于不存在。正文重试走 `ensureArticleContent(id, { allowDetached: true })`，即使目标已切出当前视图仍按 id 调 `get_article` 并落 bodyById；后端真实缺行收敛为 missing 且保留同 key 重试入口。全文照常按 id 请求；摘要统一走 detached `retrySummaryFor(id)` → `runSummaryRequest`，翻译统一走 detached `retryTranslationFor(id)`（当前文章走 `runReaderTranslation`，其余走 `runCardTranslation`），连续失败后的新入口也使用同一路径，由后端/真实结果决定。Reader 翻译的 `translating / isShowingTranslatedProse` 是当前文章展示态：done/流错误/Promise catch 只有请求仍 current 且 `activeArticleId===id` 时才修改；A/B 并发时 A 的迟到结束只清 A 的 per-id 状态，不得关闭 B 的生成/译文展示。全文成功只在目标仍是当前文章时切视图，翻译保持 per-id 状态，不污染当前 Reader。
  - `SyncTab` save-and-sync 捕获协议、Endpoint、用户名、密码、连接态和 `activateVersion` 的完整草稿，并为每份草稿分配单调 opaque id（不含密码哈希）。save 与 post-save sync 是两个阶段：save 成功、phase 失败后的重试只重跑 phase，不再二次 `sync_save`；任意一次 `sync_save` 失败都重新写入 save 阶段可重试入口。模块级最新提交代际跨组件重挂保留：任一更新草稿成功 save 后，旧草稿的 save/phase action 均提示失效并 zero-side-effect no-op。
  - 全局忙锁落在 Zustand store（`saveAndSyncBusyOwner + begin/end`），覆盖 save+phase 且跨组件卸载/重挂持续；任何 sync_save/phase 在途时所有 SyncTab 保存按钮禁用。旧草稿 revision 不匹配只撤销 UI 写权，不得提前释放全局锁；较新草稿必须等旧请求 settle 后才能提交。begin 被忙锁拒绝时按原 save/phase key 重报可重试入口，retryError 的消费语义不会丢入口。
  - 草稿同时记录 form revision，`setConnected/setPassword` 等凭据 UI 写入只在 revision 仍归属同一草稿时执行。激活令牌单独用函数式 `setActivateVersion(v => v===draft.activateVersion ? undefined : v)`：成功消费同一 token 时清除，即使 B 已编辑；不同 token 保留，且不触碰 B 地址/用户名/密码。
  - translation retry 统一走 `retryTranslationFor(id)`：当前文章 id 走 `runReaderTranslation`（global translating + isShowingTranslatedProse），非当前 id 走 per-id `runCardTranslation`；两条路径连续失败都继续产生同一 detached 重试入口。
  - 回归覆盖：save 失败连续重试仍保留入口；激活成功后 phase 失败重试不再 `sync_save`；A 成功消费 token 后 B 后续不再发送旧版本且凭据不变；B 成功提交后旧 save/phase 跨重挂均为 0 副作用；请求中编辑字段仍保持按钮禁用且不能二次保存；stale retry 挂起时 B 再点保存为 0 新 IPC；A 在途卸载重挂后 B 仍持锁，A settle 后才可保存；begin 拒绝重报入口；reader content 在目标不在当前 entries 时仍按 id 调 `get_article` 并落 bodyById，真实缺行保留同 key 入口；摘要/卡片翻译/Reader 翻译在 entry 不在当前列表时连续重试仍发 IPC；Reader 当前文章连续失败后成功保持译文展示；mark 用真实 `selectFeed` A→B→A，A cache 全读且重试失败后 entries/cache 恢复未读；mark 成功/失败均尊重用户逐-id接管，A/B/A retry 从 attempt cache 重建快照；A 在途切 B 后失败按 captured feedId 回补未读计数；load-more A/B 重叠时 A 迟到不清 B 锁，重试遇 busy 时同 key 入口保留且不重复 IPC、已到底明确提示；A 不在当前 entries 但后端仍存在时 fulltext 仍按 id 请求。
  - 其余重试点逐项核对：feed add/refresh、summary、card translation、reader content 已捕获实体 id/参数；`sync:manual` 是无实体目标的全局动作，保持原语义。

## Consequences

- 普通提示行为完全不变（形态、2.2s 时长、`slice(-4)` 容量）；带动作 toast 的 4.2s 与既有断言（`(i)` 用例）不变。错误中心只是**追加**的持久入口。
- 内存有界：最坏 20 条 × 一个闭包/条目，且 24h 未更新即被清理。
- **残余边界**（R1 后如实保留）：①未带动作的 `showToast` 不进错误中心（无重试入口可谈）；②**fallback 语义本身仍在**——未来若新增带重试动作却不传 key 的调用点，该错误仍回落文案去重（同文案多实体合并），由 (e9) 源级守卫在测试期拦截，而不是运行时纠错；③`feed:add:${url}` 以 URL 为实体键，同 URL 重复添加失败会合并（视为同一实体，重试重跑最新动作）；④按实体的「在途去重/防双击」未做（条目在重试派发瞬间消费，异步失败由重报写回——承诺给复盘的窗口见 `retryError` 注释）。
- OPT-020 的快照只覆盖本进程错误中心存续期，不持久化到重启；LOAD-MORE 在范围/游标漂移后选择安全 no-op（用户可重新触发当前上下文加载），不会后台请求旧范围。表单 key 只含单调 opaque 草稿 id 与阶段，原始密码不进入错误中心 key 或文案。
- 面板列出的是「错误中心条目」而非完整日志：被上限逐出的最旧条目不可追溯（有界性的必然代价；逐出顺序 = 最旧）。
- 与 toast 双写：一次失败可能出现两条记录（瞬时 toast + 中心条目），重试消费以 key 关联，两者语义一致。

## Alternatives considered

### Why not 把 toast 改 sticky（不自动退场）/提高上限？

粘性 toast 仍受 4 条上限：第 5 条失败会挤掉第 1 条的重试项——「唯一入口被静默挤掉」的问题原样存在，只是延迟发生；提高上限与不设限等价（父卡明确禁止），还会让屏幕常驻一排错误卡。错误中心把「瞬时通知」与「持久恢复入口」分层，两者各自有界。

### Why not 无限数组暂存回调？

父卡明确禁止：注册的回调（闭包持捕获状态）会随失败次数无界增长。本卡的 `errors` 数组有硬上限 20 且去重/TTL 双重收敛。

### Why not 按「重试到成功为止」保留条目（等回调结果再决定清除）？

现有重试回调都是 fire-and-forget（`() => get().refreshOneFeed(feedId)` 形态），内部自报成败（成功=普通 toast、失败=带重试 toast）。要拿到结果需改这些路径的返回契约——**超出本卡范围**（非范围：不改同步/AI/协议路径），且失败路径本来就会重报（重报即保留的机械保证）。消费先于执行正是与该形态配套的最小语义。

### Why not 入口/面板做成右下角悬浮角标？

toast 层（500）与 PlayerBar 已在右下角固定区，新增角标要么互相遮挡（`has-player` 抬高 96px 的状态下更复杂），要么改动既有 toast 层几何（观感回归面变大）。侧栏底部固定区天然常驻、不与任何角区竞争，且「设置中心 / 刷新全部」本就集中在那里，入口语义一致。

### Why not 用「文案 + 实体 id 拼进 key」在 store 内猜实体？／Why not 直接按文案去重（初版方案）？

初版（R1 前）按文案去重：多源同类失败文案逐字相同即合并，10 个源同时 `刷新失败：<同一网络错误>` 只剩 1 条、重试只重试最新动作——与卡内反例 1「连续 10 条带重试错误全部可追溯」冲突（R1 的 P2）。store 内无法从文案猜出实体（错误详情文案可能不含 id，或不同实体给相同文案），所以显式 key 必须由**调用点**给出（它知道自己在重试什么）；实体标识放动作对象而不是拼文案：文案是给用户看的，key 是给去重用的，两者职责分离、互不污染。

### Why not 在每个 call site 各写去重/合并？

重试 call site 分散在同步/AI/刷新路径，逐处改造去重（与单点收口相比）既扩大写集又容易回退不一致；`showToast` 是**唯一入口**（所有失败提示都经它），在那里单点接线保证「任何新增的带重试错误自动获得持久入口」。调用点只承担**给出实体/上下文 key 与捕获动作快照**这项最小职责（迁移 + (e9) 守卫），去重/上限/TTL/消费语义全部仍在 store 单点。

### Why not 重试时重新读取当前 active id/view/cursor/表单？

错误中心可跨视图切换、文章切换、首屏重载和表单编辑存活；重放“当前状态”会把旧失败变成对新目标的未授权操作（例如把 A 的续页拼到 B、把 B 标记已读、用 B 的凭据重试 A 的失败）。调用点最清楚失败目标，因此由调用点捕获闭包快照；上下文已失效时只允许显式提示或安全 no-op，不能 fallback 到当前替代对象。
