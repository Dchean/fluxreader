# Agent Note: 封面代理与失败占位

Status: implemented

## Problem

封面图（文章卡、播客卡、迷你播放条、全屏播放器、灯箱五处）曾各自处理加载与失败，结果是四种表现同时存在：破图、空白、撑破卡片、以及重复请求同一张失败的图。更重要的是**一部分封面根本加载不出来**：带防盗链的图床在没有 Referer 头时直接拒绝请求。

实测数据（同一批 URL，改的只有 Referer 头）：

| 图床 | 无 Referer | 带 Referer |
| --- | --- | --- |
| `cdnfile.sspai.com` | 403（12/12） | 200（12/12） |
| `img*.doubanio.com` | 418（20/20） | 200 |
| `cdn3.ldstatic.com` / `image.woshipm.com` / `s.anyway.red` | 公开可用 | 不受影响 |

推论明确：**白名单式防盗链的封面必须走后端代理**，`no-referrer` 直连必然破图。

此外 `first_image` 提取没有尺寸或角色启发式——真实库里 481 篇把头像、emoji 或 favicon 当成了封面。

## Decision

**五处封面位统一为 `CoverImage` 组件**（`src/components/CoverImage.tsx`），代理判定在 `src/lib/imageProxy.ts` 一处（`needsImageProxy` / `proxyImageUrl` / `fetchProxiedImage`），**组件里不得写死域名白名单**。不扩面：不需要代理的域名保持直连——不为每张封面付 IPC 与字节拷贝的成本。

**失败必须出占位。** 不留空白、不显示破图、不撑破卡片、不阻塞渲染、深浅色主题下都可读；同一会话内不重复请求同一张失败的图。代理返回非图片字节（例如被重定向到登录页的 HTML）同样走占位 + 上报，**不注入 DOM**。

**失效上报必须幂等且不重复。** `report_broken_cover(article_id, url)` 是上报入口（`src/lib/coverImage.ts` 的 `markCoverFailed`），播放条与灯箱展示同一个 `cover` 字段时不重复上报；无 cover（`null` 或空串）不渲染 `img`、不代理、不上报。失败原因分类保留：`unavailable` / `empty` / `not-image` / `error` / `direct-error`——它们对应不同的用户可见文案与不同的处理路径。

**`CoverRoute` 有三态**：`none`（无 cover）、`direct`（直连）、`proxy`（走代理）。这个判定是纯函数（`coverRoute` / `coverView`），可单测，与组件渲染分离。

## Consequences

**收益**：五处封面行为一致；防盗链图床的封面能显示；失败有可读的占位而不是破图；深色浅色都不出现不可读的空槽；失败的图不会被反复请求。

**代价与已知上限**：

- 代理需要经过 Rust 侧（IPC 往返 + 字节拷贝），因此只对白名单域名启用；白名单是手工维护的常量，新图床出现时要手动加入（重访信号：用户报告某图床封面全部不显示，而直连浏览器能打开）。
- `first_image` 仍无尺寸/角色启发式，会出现头像/emoji 被当作封面的情况。这是已知缺口，见 [docs/roadmap.md](../../../../docs/roadmap.md)。
- Miniflux 源的文章不参与封面补全（后端只取 `source='direct'` 的行），真实库 4714 篇中约 16%（757 篇）无封面。这个排除**是有意边界**（同步来源的文章由服务端决定封面），但比例不低，重访信号是「用户报告同步来的文章大量缺封面」。
- 画廊布局的封面**不走** `CoverImage`，它自管代理与失败视觉（有自己的 `onCoverError` 与 `cover-fallback`）。这是一处刻意的例外：画廊的布局与卡片尺寸差异大，复用会引入大量条件分支；代价是失败占位的视觉由两处实现保持一致。

## Alternatives considered

### Why not 全部封面都走代理？

代理能统一解决防盗链、混合内容与隐私问题，但每张图都要经过 IPC 与一次字节拷贝；对公开可用的图床（真实数据里占多数）这是纯开销。选择按域名判定：白名单内的走代理，其余直连。

### Why not 全部直连并加 `referrerpolicy`？

试过。`no-referrer` 直连对防盗链图床是 403/418，而设置 `referrerpolicy="origin"` 又必须让 webview 带上应用自身的 origin（`tauri://localhost` 之类），服务端的白名单不会认。也就是说在 webview 里无法伪装成「来自 sspai 的请求」——只有后端代理能做这件事。

### Why not 把失败状态只放在组件内部 state？

组件会被卸载重建（虚拟化列表），内部 state 一丢就重新请求同一张注定失败的图。缓存放在模块级（`coverImage.ts`）才能跨挂载记住失败。

### Why not 让画廊也复用 `CoverImage`？

画廊的封面占位尺寸与卡片布局强耦合（网格单元、不同宽高比），复用会让 `CoverImage` 增加一组只服务画廊的变体参数。保持两处实现、共享 `imageProxy` 与 `coverImage` 的判定逻辑，是当前成本最低的分工。

## Testing

- `coverRoute` / `coverView` / `getCoverState` 是纯函数，由前端回归覆盖（`npm run test:frontend`），包括「无 cover 不上报」「代理返回非图片走占位」这两类分支。
- 真实加载行为（防盗链、代理返回 HTML）由实机验证：CDP 驱动打开含 sspai 封面的文章，观察占位出现与上报次数。
