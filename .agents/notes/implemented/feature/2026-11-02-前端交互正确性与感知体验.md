# Agent Note: IME、Reader 状态与启动落地顺序

Status: implemented

## Problem

输入法合成期Escape可能误关浮层；Reader未区分正文加载、失败和缺行；启动设置与数据串行读取又容易把查询抢占的静默返回变成无终点splash。这三条路径共同涉及“等待中”与真正业务终态的区分。

## Decision

App原生Escape分支先判isComposing或keyCode=229，把取消选词交还输入法。该守卫放在会关闭浮层的分支，不额外截断所有合成期按键；React合成事件则从nativeEvent取相应信息。

Reader在基础正文视图的调用点展示loading/unrequested占位、failed重试和missing说明。ReaderProse继续只管源码、渲染和流式文本，不引入水合状态机。ready/cleared空正文与失败不同；手动进入译文时仍走译文渲染，因此不能称三态覆盖所有工具栏组合。

启动由bootstrapFromBackend并发发起设置和数据读取，数据落地前等待一次性pendingStartupLandGate，再复核查询代际。设置先接受是因为计数去重、启动筛选和主题都依赖它；只有读取可并行，落地不能任意排序。门在同一bootstrap模块中捕获并消费，后来的独立reload不自动继承。

这也是测试装配约束：组件测试把store入口别名到dist-test，而App源码由加载器转译；App直接import源码bootstrap导出会形成第二个模块实例，门可能写在A、读在B。协调状态由store装配实例内部持有，不能只在源码看见同名变量就认定同一份状态。

查询被更高代际抢占不能伪造bootstrapError；空快照且无接手者才是启动错误。后来[启动抢占期假空态](../bug-fix/2026-11-02-启动抢占期假空态.md)以在途计数补充收尾，取代本篇最初“早退一律关splash”的做法。

## Alternatives considered

只判isComposing漏掉229形态；全局拦所有合成按键则扩大无必要的行为面。把三态塞进ReaderProse会使纯字符串渲染组件承担请求状态，故留在调用点。

App直接Promise.all不能保证设置先于数据落地，且跨测试模块设门有双实例风险。查询前await设置虽安全却仍是串行。所有早退都写错误会让接手查询成功后仍被错误层覆盖，因此必须按请求所有权处理。

## Consequences

并发读取移除了可避免的串行依赖，没有真实启动计时就不能声称固定幅度提速。设置读取悬挂仍会阻塞被门约束的落地，与原串行路径一样需要真实结算。

2026-11-06仍有正文换content_id且摘要变化后不再发请求的加载态反例；另有受控延迟settings IPC与后台reload交叉的假空未读视图，但原生IPC可达性未确立，不能表述成“慢SQL被超车”的安装版缺陷。分别见[阅读与状态](../../../../docs/roadmap.md#reader-and-state)和[验证边界](../../../../docs/roadmap.md#verification-boundaries)。既有三态和门不证明这些竞态已解决。

## Validation

组件覆盖IME两形态及正常Escape负控制、Reader状态和真实重试；前端回归以deferred设置/查询控制落地顺序。jsdom不证明原生输入法实现，受控IPC不证明真实DB锁下所有调度都可发生。
