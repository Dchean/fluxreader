# Agent Note: 封面补全的覆盖面与预算边界

Status: implemented

## Problem

封面后台补全（为没有封面的文章抓文章页 og:image）长期只把 `source='direct'` 的
文章当候选。理由写在旧实现里有两层：「服务端（Miniflux 系）源入库时已用正文
第一图兜底，无需再抓文章页」与「本地补的封面可能被下次同步覆盖回空」。

2026-10-16 复核（OPT-017D）发现两层理由一站一倒：

1. **正文第一图兜底只覆盖「正文里有图」的服务端文章**。各后端入库都做过这个
   兜底（`ingestion/parse.rs` 与 `sync/entries.rs` 都调用 `sanitize::first_image`），
   但正文里没有图片的服务端文章**既没有任何封面、又永远不进入补全队列**——
   它们连一次抓文章页 og:image 的机会都没有，是永久缺口。而 direct 源没有
   这个排除，同类文章会被补上，缺口只落在服务端来源上。
2. **「同步覆盖回空」在当前代码不成立**。两处封面写入都不会把本地封面清成空：
   `refresh_existing_article`（sync 已有行内容刷新）是 `image_url = COALESCE(新值,
   旧值)`——远端给出**非空**新图时覆盖本地值，NULL 才保留本地值；
   `backfill_article_content`（回填路径）是 `COALESCE(旧值, 新值)`——严格只填空。
   即「远端没图 → 本地封面被清空」不会发生；候选排除所要防的一致性分歧不存在。
   （R1-P2-1 修正：此前表述为「两处都只填空、绝不覆盖」，与
   `refresh_existing_article` 的实际语义不符——远端新的非空封面会覆盖本地补的
   封面，属既有同步语义。）

同时该循环还有三处与父卡 OPT-017「预算/生命周期/可观测」要求不符：

- 候选查询失败被 `.unwrap_or_default()` 压成空集合、写库失败被 `.unwrap_or(0)`
  压成 0，随后 URL 仍被记入负缓存——DB 故障会被静默当成「已处理」；
- 进程内负缓存（已尝试 URL 集合）无上限；
- 循环与在途请求没有任何终止信号，应用退出只能靠进程终结硬停。

## Decision

**候选不再按来源过滤**（`db/articles.rs::articles_without_cover`）：判据统一为
「无封面 + 有原文 URL」，直连与服务端文章同列。服务端正文无图文章由补全抓
文章页 og:image 补封面。

**请求预算成为显式常量**（`scheduler.rs`）：每轮批次 20、并发 2、单请求超时
30s（`COVER_BACKFILL_REQUEST_TIMEOUT`）、单轮扫描 4 页（≤80 条候选）、循环
间隔 60s。

**扫描游标跨轮持久**（`CoverBackfillState::scan_offset`，R1-P2-2 收口）：每轮
从上次结束处继续，按**已扫描行数**推进（负缓存命中/同 URL 重复/批次已满都算
扫描过），读到空页回绕到 0。旧实现每轮固定重扫 [0, 80)：窗口内 80 行全部
「已尝试且仍无封面」时（探测前提成立时完全可能）不产生新请求 → 负缓存不再
增长也不逐出 → 更老的候选在本进程内冻结到重启。游标推进 + 回绕保证候选集
在有限轮数内被全覆盖；不落盘。

**负缓存有上限**（`CoverAttemptCache`，默认 `COVER_BACKFILL_ATTEMPT_CACHE_MAX
= 1024`，插入序逐出最旧）。记入时机仍是一次尝试**完整结束后**（成功 / 无
og:image / 抓取失败）；DB 写失败与终止中断**不算**尝试结束、不记。容量满后
逐出把「本进程永不重试」放宽为「至少再经历 CAP 条其它尝试后才可能重试」，
每轮请求量仍由批次/并发/页数上限约束，不存在对单个 URL 的无界重试。

**退出可终止**（`ShutdownToken`，watch 通道实现，保活一个接收端避免通道
closed 丢信号）：应用退出（`RunEvent::Exit`）触发后，循环在等待与请求两处
消费信号——不再发起新请求、在途请求被取消；`cover_backfill_round` 返回前
等待全部子任务结束，不残留后台任务。

**失败必须可诊断，不得压成空后标记已处理**：

- 候选查询失败：`warn` 记录（含底层错误），提前结束本轮扫描，不记任何
  负缓存——下一轮读恢复后照样重试；
- 写库失败：`error` 记录，返回 `DbWriteFailed`，不记负缓存——下一轮重试；
- 抓取失败/无 og:image：`debug` 记录 URL 与原因（HTTP 状态、网络错误、
  「无 og:image」），随后记入负缓存（这是「结果已知的失败」，不重复轰炸源站）。

**保守边界保留**：`clear_article_cover_if_matches` 仍只清 `source='direct'`
的封面（前端失效上报通道对服务端来源不清空）。它不再等价于「服务端文章没有
本地补的封面」——服务端文章本地补上的封面若失效，走前端失败占位，不会被清空
重试。

## Consequences

**收益**：服务端来源里「正文无图」的文章不再永久空缺（真实库历史口径：约
16% 文章无封面，其中服务端无图子集此前无任何补救路径；本次未重测该比例）；
DB 故障不再把任务静默吞成「已处理」；负缓存内存有界；应用退出不再留下
未完成的抓取。

**代价与已知上限**：

- 首次运行请求量上升（服务端无图文章按每轮 20 条、并发 2 的速率补）——真实
  库的请求总量与耗时未实测，是本卡的验收缺口。
- 本地为服务端文章补上的封面**不参与失效清理**（保守边界）：图床 404 时显示
  占位，且本进程内不再重试，直到重启后随窗口重新尝试。重访信号：用户报告
  服务端文章的封面坏图占位长期不清。
- 负缓存逐出意味着同一 URL 在超长会话里可能被重复尝试——间隔至少 CAP 条其它
  尝试，且有每轮上限；这是有界重试与有界内存的取舍。
- 服务端之后在正文里补图时，`refresh_existing_article` 会用远端新的**非空**图
  覆盖本地已抓的 og:image 封面（既有同步语义：非空才覆盖、NULL 保留本地）；
  严格「旧值优先」的只有回填路径 `backfill_article_content`。覆盖前后都是有效
  封面，不涉及内容一致性；若要改为「本地封面永久优先」须先改同步刷新策略并
  重审本 Note。
- `first_image` 无尺寸/角色启发式仍会把头像、emoji、favicon 当封面（历史
  已知项，见 docs/roadmap.md）；本次扩面会让该类误抓也覆盖到服务端文章。
- **隐私边界（R1-P3-2 披露）**：扩面后客户端会直接请求**服务端收录文章的
  第三方源站页面**（抓 og:image），客户端 IP 对更多第三方站点可见——这是候选
  扩展的已知代价，与卡片把「隐私边界」列为扩展依据的要求对应；未提供关闭开关
  （如需回避，只能断开服务端账号或等待后续产品决策）。

## Alternatives considered

### Why not 维持「只补 direct」（不扩展）？

旧理由被复核推翻（见 Problem）：兜底只解决正文有图的情况，「覆盖回空」在当前
代码不成立。维持现状等于把一个永久缺口当成有意边界。请求预算是这个替代方案
唯一站得住的反驳点，但每轮 20 条 × 60s 的速率把「首次补全的历史存量」摊薄到
进程级、可中断、有失败缓存的节奏里，不足以支持继续排除。

### Why not 只扩到「服务端来源且正文无图」的精确子集？

按 source 列分叉会再引入一份「服务端 = 特殊」的判据，而缺口的本质是「没有
封面」，与来源无关。统一判据（无封面 + 有 URL）让两类来源的行为逐字一致，
也让夹具矩阵（direct / greader / miniflux / fever 四形态）共用同一断言。
正文有图的文章本来就已带封面、不在候选里，无需再按来源细分。

### Why not 用持久化（跨进程）的失败缓存？

持久化会把「源站临时失败」记成跨会话的长期状态，掩盖源站恢复；而进程内有界
缓存已经满足「同一会话不无限重试」的目标。持久化还引入 schema 与清理成本。

### Why not 引入 tokio_util 的 CancellationToken？

项目不新增依赖。watch 通道版 token 语义足够（触发即真、wait 立即返回、多
订阅者广播）；唯一坑是「所有接收端 drop 后通道 closed、send 静默失败」，
用保活一个接收端消除，已在类型注释里说明。

### Why not 写库失败也记入负缓存？

那会把「写失败」当成「页面无图」——用户可见的封面永远缺，且没有任何可诊断
信号。写失败是本地存储故障，重试是恢复路径；每轮最多重试一批，代价有界。

### Why not 让候选查询失败返回空集合并继续（原行为）？

空集合与「没有候选」不可区分，任务被静默吞掉且无日志。现在失败会记录并提前
结束扫描；由于不记负缓存，读数恢复后同一批候选下一轮照常被处理。

## Testing

- `src-tauri/tests/cover_backfill_e2e.rs`（默认 `cargo test` 内运行）：
  - 覆盖面矩阵：direct 走真实摄取管线（自托管 feed）；greader（Miniflux 形态）、
    greader（FreshRSS 子路径形态）、fever 走真实同步管线（`mock_greader`，
    Fever 条目服务为默认关闭的可选能力，对既有套件零影响）。每个形态断言
    「正文有图 → 有封面、不进候选、不抓页面」与「正文无图 → 无封面、进候选、
    被 og:image 补上」。
  - 预算：失败三形态（403 / 200 无 og:image / 404）各自只尝试一次、失败被
    记录；负缓存容量 1 时逐出导致有界重试（既有窗口推进/同 URL 分组/空串
    封面等 REQ-106① 回归全部保留）。
  - 生命周期：触发终止信号后一轮零请求；中途触发时在途慢请求被取消、不再
    发起新请求、本轮在远小于慢响应的时间内返回。
  - 可观测：候选读失败记录且不标已处理；写库失败（真 DB 触发器注入）记录、
    不标已处理、下轮重试、恢复后补上。
- 单元测试 `scheduler::cover_attempt_cache_tests::attempt_cache_evicts_oldest_beyond_capacity`
  （默认构造用生产上限常量、逐出顺序、重复记入不改变顺序）。
- 先红后绿与六项变异（source 过滤回退 / 读吞错 / 写吞错 / 去 shutdown 取消 /
  去逐出 / 去无封面谓词）证据在 `tmp/optimization-20261008/OPT-017D/evidence/`。
