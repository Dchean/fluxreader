# Agent Note: 返回位置与列表保位

Status: implemented

## Problem

「我从哪来，回哪去」在列表类界面里是最容易被做错的一类交互，因为触发路径多且各自看起来都是独立的小需求：

- 打开阅读器再关闭，滚动位置应该在哪？
- 切到另一个订阅源再切回来，应该停在原来看的那一条，还是从顶部开始？
- 后台刷新完成（新文章插到顶部），用户正在读的深页文章还在原位吗？
- 排序反了以后，还应该恢复位置吗？

每条路径各自实现「恢复滚动」的结果是互相打架：两种恢复机制同时生效就跳两次；同一个位置被恢复两次就抖动；信号用「当前选中文章的 id」表示时，连续开关同一篇文章不会触发第二次恢复。

深页阅读还暴露了另一层问题：后台刷新固定取 `offset=0 / limit=500`，用户读到第 2000 条时，刷新结果里根本没有他读的那一条，锚点无从兑现——保位机制即便逻辑正确也救不了。

## Decision

**总原则：离开时的阅读位置可恢复；无法可靠恢复时明确归零，不猜。** 猜错的代价是用户在一个陌生的位置阅读，比从顶部开始更糟。

**全场景规则表**（`src/components/timelineAnchor.ts` 的头注是这份表的代码载体）：

| 场景 | 行为 |
| --- | --- |
| 后台刷新（内容更新） | 原位保持，用顶条锚 + `positionRestoreNonce` |
| 切换布局 / 视图 / 范围后**切回** | 恢复顶条位置 |
| 切换排序 | **不恢复**（新语境，filterKey 变化即失效） |
| 首次进入 | 归零 |
| 锚 id 不在新列表里 | 归零 |
| 阅读器 Esc 关闭 | 滚动不动，焦点归还原选中卡 |

**信号用 nonce 计数器，不用 id 字段。** `positionRestoreNonce`、`switchRestoreNonce`、`readerCloseNonce` 都是递增计数器。用 id 表示「恢复这个位置」时，连续开关同一篇文章不会产生新的恢复信号（id 不变）；计数器每次动作都变，语义是「这是一次新请求」。

**`switchRestoreNonce` 与 entries 同一次 set 原子写入**，避免出现「信号已到但列表还没换」的中间态。

**恢复与保位不得叠加滚动。** 切换返回的恢复动作不置 `positionRestoreNonce`；恢复成功后把活锚重锚到落点，后续刷新从新锚出发。

**同上下文重复导航不算「切换返回」**（`contextChanged` 守卫），不 bump 恢复信号。**cache-miss 切回视为归零回落**——恢复列表尚未就绪时不猜位置，但旧键的存档保留，所以下次命中缓存时位置仍在。

**后台刷新围绕已加载窗口按 keyset 续拉重建**，防呆上限 `ceil(target / ARTICLES_PAGE_SIZE) + 1`；锚载荷带 intra-item 像素偏移（用户停在卡片中间，不是停在卡片顶部）。未带恢复信号时行为与修前逐字一致（有断言锁定这一点）。

**列表视图缓存升级为带 `loadedCount` / `exhausted` 的快照**，而不是裸数组。裸数组的失败模式是「截断长度被当成游标」——单键实体预算（`VIEW_ENTRIES_CACHE_ENTRY_BUDGET = 1000`）会截断超长列表，截断后的长度若被读作「已加载多少」，翻页就会算错。`timelineAnchor` 的 250ms 节流窗口有尾沿补记（`commitTopAnchor` + `rearmTopAnchor`），防止窗口内滞留旧位。

## Consequences

**收益**：六种场景各有明确规则且互相不打架；深页阅读的后台刷新不再丢锚；缓存命中与未命中的行为差异可解释；「不猜」这条原则把最难的一类 bug（恢复到一个随机位置）从根上排除。

**代价与已知上限**：

- nonce 计数器的语义是「一次动作一个新值」，调用方必须理解这一点；误用会导致多余或缺失的恢复。
- 三重隔离（仅内容刷新入口传参、仅落地快照即当前视图时 bump、消费侧 filterKey 逐字比对）是为了防误回位而加的，任一条被绕过都可能导致「用户没做任何切换，位置却动了」。
- `ceil(target / PAGE_SIZE) + 1` 是防呆上限，意味着恢复位置极深（超出上限）时不会完全复原——上限触发的表现是回到已重建窗口的边界，而不是原位。
- 缓存单键预算 1000 条与 LRU 8 键的组合在实测中未成为瓶颈（50k 篇文章下堆内存平坦），但它是一个会随列表长度增长的常量，超大列表下重访信号是「切回时位置恢复不完整」。

## Alternatives considered

### Why not 用「记住滚动像素」代替锚？

像素偏移在列表内容变化后没有意义：新文章插到顶部，同样的像素对应的是另一条文章。锚（顶条 id + intra-item 偏移）在内容变化后仍然指向同一条内容，这是它能跨刷新成立的原因。

### Why not 所有场景都恢复位置？

排序反转、范围变化这类操作会重建列表的语义顺序，恢复旧位置等于让用户停在一个与当前排序无关的地方。规则表把「不恢复」的场景明确列出，比统一恢复更符合直觉——用户改变视图时的预期是「看到这个视图的开头」。

### Why not 让 `positionRestoreNonce` 与 `switchRestoreNonce` 合一？

两者语义不同：前者是「内容刷新后回到原处」，后者是「切换后回到离开处」。合一会让「刷新后恢复」与「切换后恢复」互相触发（内容刷新会置位，切换判断误认为是自己的信号）。三个 nonce 分开是承认三种触发源。

### Why not 在 cache-miss 时保留上次位置硬撑？

没有列表数据时无法定位锚，只能猜一个索引。猜错的位置比顶部更糟——用户会以为列表坏了。选择归零并明确告知（列表回到顶部）是可解释的行为。
