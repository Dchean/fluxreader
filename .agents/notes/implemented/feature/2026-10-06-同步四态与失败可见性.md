# Agent Note: 同步四态与失败可见性

Status: implemented

## Problem

同步状态对用户是黑箱。侧栏只有一个「正在同步 / 已同步」的指示，无法回答用户真正关心的问题：

- 我改的已读，到底存下来没有？
- 有多少条还在等着推？
- 推失败了没有？为什么失败？

更糟的是失败被静默吞掉：推送失败的条目标记在队列里，但界面显示「后端同步完成」——用户看到成功，数据却没进去。审计确认这是一个「假成功」类缺陷：数据零进来，提示语说一切正常。

后端侧还有一处语义容易被误改：拉取单项失败时，后端**仍然返回 `Ok(report)`**，把失败细节放在 `report.errors` 里，而不是抛错中断整链。这意味着前端的 `.catch()` 永远不会触发失败路径——必须主动读 `report.errors`。

## Decision

**四态口径，术语与含义固定：**

| 状态 | 含义 | 数据来源 |
| --- | --- | --- |
| 本地已保存 | 状态变更已事务化落库 | 本地写入成功（与队列同事务） |
| 等待同步 | 有待推送的队列条目 | `sync_queue` 待推行数 |
| 部分失败 | 有尝试过且失败的条目 | `attempts > 0` 的行 |
| 远端已确认 | 已被服务端接受 | **不可累计溯源**（成功即出队） |

**「远端已确认」不得虚构总数。** 成功推送的条目会立即从队列里删掉，因此没有任何地方记录了「累计成功多少条」。界面只能以「上次同步」的时间口径呈现这个状态，不能报数——报出来的数一定是编的。

**pill 优先级固定为 `error > syncing > waiting > connected`。** 曾经的实现里失败会被 syncing 覆盖（正在重试时看不到已失败），修好后 `failed > 0` 还会对全部四个分支追加「· 部分失败」，允许「同步失败 · 部分失败」两个事实并存。无队列且无失败时维持「后端已同步」，不新增噪音。

**稳定四态文案收口在 `src/lib/syncPill.ts`**：`syncPillLabel` / `syncStateSummary` 是稳定态与队列摘要的唯一来源。手动同步的四个瞬态阶段另由 `src/store/slices/sync.ts` 的 `manualSyncStageLabel` 统一生成——它必须和阶段推进、终态判定共用同一个 module，避免组件按定时器自行猜测当前阶段。

**手动同步是阶段状态机，不是「队列清空即完成」。** 后端 `states_phase` 是复合操作：先推送状态队列，再执行 `pull_entries`，必要时还会补推。前端因此设置 `syncStage = feeds | states | refresh | reload`；队列事件只能在 `states` 阶段清空且无失败时补记 `syncRemoteWriteConfirmed`（“远端写回已确认”），不能结束 `syncing`。只有 `states` IPC 返回、`refreshAllFeeds` 返回、`reloadFromBackend` 成功后才进入 `synced`；任一阶段 reject 则统一进入 `error`，并保留失败阶段与原因。

**所有 `syncStatus` 生产写入者共享 owner/generation 协议。** 手动同步、`addFeed` 尾链、「保存并同步」尾链和 GitHub 断开都先 `beginSyncActivity(owner)`，后续只以返回的 generation 调 `updateSyncActivity` / `finishSyncActivity`。活动表按启动序号展示最新在途工作；全部结束后只有启动序号更新的终态可发布。较早请求仍能完成自己的业务，但其迟到成功/失败不能覆盖较晚请求已经发布的阶段或终态。手动链另外保持 store 级单飞：重复刷新入口复用同一个 `Promise<void>`，终态后释放忙锁。

**长等待只切换展示语义，不伪造终态。** 侧栏与设置摘要持续显示真实阶段；同一活动等待满 30 秒后改为「同步未返回（阶段，已等待 X）」。此时 `syncStatus` 仍是 `syncing`，在途 Promise 与忙锁原样保留，禁止重叠执行。没有固定前端超时把仍在执行的任务强行标成成功或失败——底层 HTTP timeout 会以 reject 进入 `error`；真正未返回的 Promise 继续以“未返回”展示，直到真实 settle 或进程退出。

**保存后同步不得吞掉 refresh reject。** 「保存并同步」的尾链会保留 `refreshAllFeeds` 的真实错误，继续完成最后一次必要 reload，然后以 `stage='refresh'` 发布 `error` 和重试入口；只有 refresh 与 reload 都成功才允许发布 `synced`。空错误消息也必须按失败处理，并显示“内容抓取失败（原因未提供）”。

**前端必须主动消费 `SyncReport.errors`。** 后端返回 `Ok(report)` 是有意语义（单项失败不中断整链），不是可以改掉的实现细节。失败提示必须含「有 N 项失败」+ 至少一条具体原因，不得只报「后端同步完成」。成功路径的文案与顺序逐字不变：保存链是「已连接 → 已拉取订阅源… → 后端同步完成」，手动链是「订阅同步完成… → 已刷新，新增 N 条 / 无新文章」。

**同步状态变化要主动通知前端。** 队列状态在后端变化（推送成功、失败、阻塞），前端不该靠轮询知道。发射点通过注册表拿到 `AppHandle`（`QUEUE_EVENT_TARGET: OnceLock<AppHandle>`），而不是给 `exec_push` / `states_phase` 加参数——那两个函数的二参签名被集成测试大量锁定，加参会波及不可改的测试面。集成测试不注册目标，发射点自然 no-op。监听器落点写队列三字段，并可在手动同步的 `states` 阶段补记 `syncRemoteWriteConfirmed`；不碰连接态，也不写终态。

**认证失败与网络失败必须分类上报。** 二者对用户的含义不同（一个要改凭据，一个等网络），归在同一个错误里等于没说。

## Consequences

**收益**：用户能分辨「存下来了」和「推出去了」；失败可见且带原因；「远端已确认」不再被编造成一个数字；状态变化是事件驱动而非轮询。

**代价与已知上限**：

- 四态不可累计溯源是数据模型的硬约束，若将来产品要「已同步 N 篇」这类统计，需要新增一个成功计数表——当前没有。
- `last_error` 用「id 最大」近似「最近」：入队互斥合并会删旧插新，因此 id 单调，但没有独立的失败时间戳列。这个取舍写在 SQL 注释里，若将来出现「同一 id 多次失败」的场景，近似会失效。
- 阻塞时对**全部现存队项** `attempts + 1`，且只在确有标记时才发事件——不做周期性噪音，代价是「刚入队就阻塞」的条目要等下一轮才被标记。
- 事件只在真实应用里生效（集成测试不注册目标），因此这条链路的回归覆盖依赖实机验证。
- 同步活动/阶段状态仍是进程内 UI 状态，不持久化；强退后不能据此推断后端任务仍在运行。若底层 IPC Promise 真正永不返回，UI 会在 30 秒后持续显示“同步未返回/已等待”，并继续持有忙锁；在不新增 Rust 取消协议的前提下不能安全结束或重入该任务。

## Alternatives considered

### Why not 把 `Ok(report)` 改成失败时抛错？

抛错会让「一项失败」中断整条同步链——其余订阅源的同步也不做了。单项失败不中断是有意的健壮性设计：网络环境差时，一个源连不上不该阻止其他源完成。前端的正确做法是读 `errors`，不是要求后端改变返回形态。

### Why not 给 `exec_push` / `states_phase` 加 `AppHandle` 参数？

那样发射点最直观，但这两个函数的签名被 `src-tauri/tests/` 下的集成测试大量锁定，改动会连带修改一批测试文件——而测试面的改动本身需要独立审查，成本远超收益。用 `OnceLock` 注册表把「谁有 handle」与「谁要发事件」解耦，集成测试里注册为空即自然降级。

### Why not 前端轮询队列状态？

轮询要在「响应及时」与「请求频率」之间取一个必然不优的值，而且会让空闲时的 IPC 流量与队列长度无关地持续存在。事件是这类状态的正确形态。

### Why not 报「累计已同步 N 条」？

因为数据不存在。队列成功即删，值一旦报出来就是编的。四态里唯一诚实的呈现是时间口径（「上次同步 3 分钟前」）。审计对此的表述是「不得虚构总数」，这条比界面好看更重要。

### Why not 在队列清空事件到达时直接写 `synced`？

因为 `states_phase` 的推送段之后还有 `pull_entries` 与可能的补推，队列清空之后还要执行 `refreshAllFeeds` 和 `reloadFromBackend`。把队列清空当成整轮完成会准确地把“远端已读写回成功”误报成“本地条目、内容与视图均已同步”。

### Why not 拆分 Rust `states_phase` 或给 IPC 增加阶段事件？

已核实的前端缺口不需要改协议或 Rust 阶段边界：现有队列事件足以补充“远端写回”事实，现有 `states_phase` 返回边界足以表示复合阶段完成。拆分阶段会触及 IPC/Rust 引擎与大量锁/集成测试，风险明显高于本轮写集；在没有后端阻塞证据前不扩展。

### Why not 用固定前端超时把未返回的 Promise 标成失败？

手动全刷会按源数量与 `fetchConcurrency` 串行消化网络请求，合法耗时可能远长于任意固定阈值；前端超时既会误报失败，也可能诱导用户重入并与仍在执行的 Rust 任务重叠。因此 30 秒只切换为“未返回”的**展示状态**，不写终态、不释放锁。真实 `reject`（含底层 HTTP timeout）才进入 `error`；持续 pending 则一直显示当前阶段与真实耗时。

## Testing

- 前端回归（`npm run test:frontend`）覆盖 pill 优先级与四态文案的真值表。
- OPT-022 行为回归覆盖：push 已清空但 `states` pull 仍 pending、refresh/reload reject、IPC timeout reject、重复触发单飞、失败后重新发起、切页返回阶段保持、`addFeed` / save-and-sync / GitHub 断开的旧 generation 不得覆盖新终态、长期 pending 显示“未返回”，以及每个成功/失败终态都退出 `syncing`。夹具真实执行 `triggerManualSync` / `addFeed` / SyncTab 保存链，并通过 deferred IPC 控制 pending 边界。
- 组件挂载回归由真实 deferred `sync_phase` 驱动：SyncTab 卸载后全局活动仍在，再次挂载仍显示同一“同步未返回”文案；deferred IPC settle 后才退出并释放忙锁。
- SyncTab 保存链定向反例锁定 `refresh_all_feeds` reject：最后一次 reload 完成后发布 `error(stage=refresh)`、释放草稿锁且不出现“后端同步完成”成功 toast。
- Rust 单元测试覆盖 `push_block_summary` 的 payload 口径与推送阻塞标记（`db/sync_queue.rs`）、认证 vs 网络失败的分类（`sync/push.rs`）。
- 实机链路（事件在真实应用里生效）由 CDP 驱动验证：触发一次同步、观察 set 页摘要与侧栏 pill 随之变化。
