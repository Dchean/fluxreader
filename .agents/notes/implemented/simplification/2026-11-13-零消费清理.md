# Agent Note: 零消费清理

Status: implemented

## Problem

声明了却没有生产消费者的函数、事件、设置和表会把排障引向不执行的路径；直接批量删除也可能误删兼容入口、测试装配或有意保留的能力。另一类问题是同一语义有两份实现：字符串 ID → 数字 ID 的解析曾同时存在于选择器与 internals，任何一边单独修改都会让“范围派生”和“条目写库”对同一形态解析出不同数字。

## Decision

- **按真实消费者处置，不按名称或调用数。** 没有用途的内部包装/变体可删；需要的能力应接线，而不是因为暂未调用就放弃；有兼容或测试用途的成员明确写出用途。零生产调用不足以删除公开签名：要查测试、版本兼容与动态注册。`#[allow(dead_code)]` 只隐藏告警，不证明用途缺失。（原 2026-09-29 simplification/2026-09-29-死代码与空壳集群清理.md）
- **“看起来空”不等于空壳。** `layoutNeedsBody` 恒为 false 是五布局轻列表、按需水合的有意边界；`mockData` 只用于显式浏览器开发环境，后端异常不能回落演示数据。这两者不能仅凭名称或常量返回值判为死代码。
- **ID 解析收敛为单点叶子模块。** `store/scopeId.ts` 实现“第一段连续数字，无数字段 NaN”，行为逐字不变；`selectors.ts` 只 re-export（公共导出面与既有 import 路径不变），`internals.ts` 只 import，私有副本删除。依赖方向是两侧都只依赖叶子，基础设施层不反向依赖选择器层。守卫包括真值表、消费边界字段映射（`feed_id`/`folder_id`）与同形复制源级扫描：`match(/(\d+)/)` 全 `src` 恰一处、`numericId` 定义恰一份；它覆盖同形复制，不覆盖改名/换写法（如另写 `parseInt`）的语义副本。（原 2026-10-16 simplification/2026-10-16-零消费入口清理与id解析单点.md）
- **后端同名解析不合并。** `greader.rs::parse_feed_numeric_id`（只认 `feed/<十进制>`）与 `sync/entries.rs::item_numeric_id`（长格式 tag 尾十六进制 / 无前缀纯十进制）是两个协议形态，不是互相复制；保留两者并在注释中说明差异，防止后续审计误并。
- **删除与保留都要有账。** 历史清理删除过前端 `api.feedCounts`/`scopeCounts`/`setFeedAiFlags` 包装、`greader::tags::KEPT_UNREAD`、`client_login_url` 与零监听的 `close-resolved` 事件；保留 IPC 命令签名、有集成测试消费者的 `sync::phases::sync_now`，以及删除需迁移的 `origin_was_local` 列。历史清点的结论只对当时消费者搜索成立，后续审查仍应重新核对。

## Alternatives considered

- 保留所有死代码并加注释：仍会误导调用链分析，未来恢复真实需求可查 Git 历史，否决。
- 只加 `#[allow(dead_code)]`：隐藏告警而非解决用途缺失，否决。
- 让 `internals` 直接 import `selectors`（当时不成环）：会造成基础设施层反向依赖选择器层；共享叶模块让两侧都只依赖叶子，否决直接依赖。
- 保留 `KEPT_UNREAD` 作为协议预留：没有实现 kept-unread 语义，留常量只会误导，否决。
- 保留重复 ID 解析：两份副本是无行为差异的潜在分叉源，历史 bug 正是这一族，否决。

## Consequences

- 单点解析让“范围派生”与“条目写库”共享同一实现，代价是多一个小文件与一次 re-export 间接；同形复制守卫按源码文本计数，改名/换算法的语义副本仍需评审发现。
- 删除前端包装后，对应 IPC 命令在运行期已无调用方（保留签名与预留）；若未来重接，从前端包装加回即可。
- `origin_was_local` 与 `sync_now` 仍是“零生产消费”状态，处置理由留在路线图；删除列需要迁移，不在普通清理范围。
- 清理记录的结论有时点，不是“以后不用再查”的永久事实；编译与行为回归检验删除影响，注册/公共契约/测试消费需另外核对。
