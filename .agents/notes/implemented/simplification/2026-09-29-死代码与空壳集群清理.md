# Agent Note: 零消费能力按真实用途删除、接线或保留

Status: implemented

## Problem

声明了却没有生产消费者的函数、事件、设置和表会把排障引向不执行的路径；直接批量删除也可能把兼容入口、测试装配和有意保留的能力误删。2026-09-29 的清点暴露了这两种风险。

## Decision

按实际消费者处置：没有用途的内部包装/变体可删，需要的能力应接线，有兼容或测试用途的成员则明确用途。例子包括删除旧 api.syncNow、AiEvent::Error 和 STATE_FILE_NAME；远端编辑订阅应接到真实写回链，而不是因为暂未调用就放弃能力。

layoutNeedsBody 恒为 false 是五布局轻列表、按需水合的有意边界；mockData 用于显式浏览器开发环境，后端异常不能回落演示数据。这两者不能仅凭名称或常量返回值判为空壳。

后继清理由[零消费入口与 id 单点](2026-10-16-零消费入口清理与id解析单点.md)承接：close-resolved、KEPT_UNREAD、client_login_url 已删，前端 id 解析移到共享叶模块。Rust sync_now 仍有集成测试消费者，不能沿用本篇早期“已删”的说法。旧 FTS 表及维护触发器已在 v29 删除；历史迁移里仍存在创建语句不代表当前库仍维护该表。

## Alternatives considered

保留所有死代码并加注释仍会误导调用链分析，且未来恢复真实需求可查 Git 历史。只加 allow(dead_code) 隐藏的是告警，不是用途缺失。反过来，零生产调用也不充分支持删公开签名：要查测试、版本兼容和动态注册。

把 mock 提升为产品演示模式会增加两套数据源契约，当前没有该产品需求；只在开发环境保留即可。

## Consequences

本决定提供逐项处置原则，不宣称全项目已无死代码或空壳。origin_was_local 的历史列仍需单独评估迁移成本，删除常量也没有实现 kept-unread 协议语义。当前未完成项集中在[维护路线](../../../../docs/roadmap.md#maintenance)。

## Validation

消费者搜索用于界定删除范围，编译和行为回归用于核对影响，两者不能互相代替。后端错误不回落 mock 有专门故障注入；FTS 当前存否由 v29 迁移的 sqlite_master 断言验证，不能仅搜索历史 SQL。
