# Agent Note: 死代码与空壳集群清理

Status: implemented

## Problem

项目积累了若干「声明了但没人用」的能力：函数、模块、枚举变体、数据库列、设置项。它们的共同特征是**看起来是功能，实际上从不执行**——排查缺陷时会把审查者引向不存在的代码路径，而用户以为自己拥有的能力其实没有实现。

具体形态有四类：

1. **零生产调用**：`api.syncNow`（前端封装了但从不调用）、`sync/phases.rs::sync_now`（后端保留但无生产调用方）、`greader.rs::edit_subscription`（实现完整、全仓零调用）、`config_sync.rs::STATE_FILE_NAME`。
2. **只写不读**：`github_oauth_client_id` 只写不读；`close-resolved` 事件只 emit 无 listen；`feeds.origin_was_local` 无生产写入方；`folders.remote_id` 的注释自述「不维护」。
3. **只定义不用**：`greader.rs::KEPT_UNREAD` 常量只剩定义行、`client_login_url` 同理；`AiEvent::Error` 变体从不发送。
4. **重复实现**：`numericId`（`store/selectors.ts`）与 `scopeNumericId`（`store/internals.ts`）是两份逐字相同的实现。

清掉它们的意义不只是「少几行代码」，而是**让「能力存在」这件事变得可信**：审查者读到的每个函数都有调用方，每个设置项都有消费者。

## Decision

**按发现逐项处置：删、留、或补说明。** 判定顺序是：

1. **确实是死能力 → 删除**。`api.syncNow`、`sync_now`、`AiEvent::Error` 变体、`STATE_FILE_NAME`、Miniflux 兜底三查询、`fallback_entries`、重复的 id 转换函数都删掉。
2. **能力仍需要但缺消费者 → 接到调用上**（不是删）。`edit_subscription` 属于这一类：它是远端改名/移动目录的唯一实现，删掉等于放弃能力，正解是接线，见[双向同步的写入接线与墓碑](../bug-fix/2026-09-18-双向同步的写入接线与墓碑.md)。
3. **有意保留但容易被误判 → 补说明**。`layoutNeedsBody` 恒返回 false 是**有意设计**（五布局一律走懒水合，列表查询不背 2–3MB 正文），把它从「注释与实现脱节的死函数」改成有文档的单点——**不当回归处理**。

**`mockData` 仍被使用**，但只在浏览器环境的 `dataMode === 'mock'` 分支下（后端异常时**不回退** mock 数据，而是显示错误态 + 重试入口；曾有一处缺陷正是「生产错误回退 mock」，用户会看到演示数据并以为是真的）。删 `mockData.ts` 之前必须知道这条。

**`articles_fts` 的处置留待后续**：表与三个触发器仍在 `migrations.rs` 里被创建和维护，而生产的搜索消费点为 0（搜索不用 FTS5 `MATCH`，原因记录在 `db/articles.rs` 的注释里：中文分词）。它属于「按发现处置」时被判为「暂不动」的一项。

## Consequences

**收益**：生产代码里不再有零调用函数；「能力存在」的宣称与实现对得上；重复实现被合并为单点；`layoutNeedsBody` 这类有意设计有了明确说明，不会被当成缺陷修掉。

**代价与已知上限**：

- 删除意味着这些能力若将来需要，要从 git 历史里找回。选择删除而非保留的理由是：保留的死代码本身会持续误导审查，而恢复历史代码的成本远低于每次审查的认知成本。
- `articles_fts` 的处置是「暂不动」而不是「已决定」——它占着一次迁移与三个触发器的维护面，属于待清理项，见 [docs/roadmap.md](../../../../docs/roadmap.md)。
- `greader.rs::KEPT_UNREAD` 这类「只剩定义」的常量仍在，因为删它需要确认协议语义层级没有隐性依赖；当前已在兼容矩阵里记为已知限制（L4）。

## Alternatives considered

### Why not 全部保留，只加注释说明「暂未使用」？

注释不能阻止审查者顺着死代码走一遍，也无法阻止后来者以为它有调用方而修改它。判据是：这个能力**现在有真实用户场景吗**？有就接线（`edit_subscription`），没有就删（`syncNow`）。

### Why not 用 `#[allow(dead_code)]` 标记？

那只是让编译器闭嘴，死代码仍然是死代码。而且一旦标记存在，后来新增的真正死代码也可能被顺手加进标记里。

### Why not 保留 `mockData` 作为「演示模式」的正式能力？

浏览器环境下的 mock 只服务于开发与冒烟测试；把它提升为正式能力意味着要维护两套数据源与切换逻辑，而产品没有「演示模式」这个需求。当前形态（只在浏览器且显式 `mock` 模式下生效）够用，且生产异常时绝不回退到它。

### Why not 把 Miniflux 兜底查询保留为「未来兼容」？

那三条查询是某个版本的服务端行为兜底，而该服务端行为已不适用（注释已陈旧），保留会让人以为当前仍需兼容。删除后若真需要，从历史找回即可。

## Testing

- 删除类改动由既有集成测试与前端回归保证行为不变（`npm run test:frontend`、`cargo test`）。
- 「前端不因后端异常回退 mock」有专门断言：故障注入（`list_folders` / `list_feeds` / `list_articles` / `sync_status` 全部 reject）后，`dataMode` 不得进入 mock。
