# Agent Note: 零消费入口清理与 id 解析单点

Status: implemented

## Problem

两类「看起来存在、实际没有通路」的代码（OPT-017F，2026-10-16）：

1. **重复实现**：字符串 id → 数字 id 的解析有两份逐字相同的实现——`store/selectors.ts::numericId`（公共导出，AI/布局/折叠等写库路径用）与 `store/internals.ts` 的模块内私有副本（scope 范围派生用，注释自述「避免 internals ↔ selectors 循环依赖」，源起 f75c512/TASK-052）。两份副本眼下无行为差异，但任何一边单独修改都会让「范围派生」与「条目写库」对同一形态解析出不同数字——历史 bug 正是这一族（定长 `slice` 把纯数字 id 截成 NaN，写库全面失败且被乐观更新掩盖）。
2. **零消费入口沉淀**：前端 API 包装、Rust 常量/函数、Tauri 事件里出现没有调用方/监听方的成员。父卡（OPT-017）要求：清理前先搜实际消费者并锁行为；不得删除「暂时未调用但有 public 契约」的接口；不删除 IPC 命令签名与事件名（除非确认内部且无兼容义务并有证据）。

## Decision

**一、id 解析收敛为单点叶子模块 `store/scopeId.ts`。** 实现取「第一段连续数字，无数字段 NaN」，行为逐字不变；`selectors.ts` 只 re-export（公共导出面不变，`slices/feeds.ts` 等既有 import 路径与对象同一性不动），`internals.ts` 只 import，私有副本 `scopeNumericId` 删除。依赖方向核对（导入图）：selectors 不（传递）导入 internals，直接 import 今天不成环；但共享叶模块让两侧都只依赖叶子——不把基础设施层耦合到选择器层，也没有「任一侧未来新增依赖即成环」的路径。守卫：回归域 `scope-id` 锁真值表 + 消费边界字段映射（独立期望表，`feed_id`/`folder_id` 两字段同断言）+ **同形复制**源级扫描（`match(/(\d+)/)` 全 src 恰一处；`numericId` 的 function/const/let/var 定义恰一份）。口径边界：改名/换写法的语义级副本（如另写 `parseInt` 提取数字 id）**不在**源级守卫覆盖内，需评审发现。

**二、后端同名解析不合并（逐一核对结论）**：`greader.rs::parse_feed_numeric_id`（只认 `feed/<十进制>`）与 `sync/entries.rs::item_numeric_id`（经 `parse_item_id`：长格式 tag 尾十六进制 / 无前缀纯十进制）是**两个协议形态**，不是互相复制——保留两者，`parse_feed_numeric_id` 补注释说明差异，防后续审计误并。

**三、零消费清单与处置**（消费搜索日志在 `tmp/optimization-20261008/OPT-017F/evidence/search/`）：

a) 删除（当时经消费者搜索确认的内部死代码）：
- `api.feedCounts` / `api.scopeCounts`（前端包装；OPT-008B R2 起计数只走 `countsSnapshot` 组合快照）；
- `api.setFeedAiFlags`（旧 bool 双字段包装；OPT-011 起唯一真值入口是三态 `setFeedAiModes`）；
- `greader::tags::KEPT_UNREAD`（只剩定义行；「kept-unread 不识别」的限制不变，见兼容矩阵的[状态操作与冲突政策](../../../../docs/sync-compat-matrix.md#状态操作与冲突政策)节）；
- `greader::client_login_url`（零引用；登录实现 `login_at` 内联构造同一 URL，删除的是陈旧副本）；
- `close-resolved` 事件 emit（零监听；Tauri 事件是应用内部 IPC、无兼容义务——前端 `answerCloseAsk` 调用点已自行同步设置镜像，见 `store/slices/ui.ts`）。

b) 保留并注明（public 契约 / 预留 / 有消费方）：
- IPC 命令签名 `feed_counts` / `scope_counts` / `set_feed_ai_flags`：命令注册表不动（本卡非范围）；三者分别仍是 Rust 数据层单测的数据面与旧 bool→显式 on/off 映射的兼容入口（`db/feeds.rs` 单测锁定）；
- `sync/phases.rs::sync_now`：无生产调用方，但有集成测试消费者（`dual_client_e2e` 在 CI 六套件内）——删除会移除该测试面，保留；
- `feeds.origin_was_local`：列存在（migration v9），唯一引用是 `purge_remote_data_in` 中的重置语句（没有任何写入方将其置 1 → WHERE 永不命中）；删除列需要迁移，超出本卡写集，继续留在 `docs/roadmap.md`。

## Alternatives considered

### Why not 让 internals 直接 import selectors（今天不成环）？

评估过的更小改动。否决理由：那会造成反向依赖——基础设施层（被全部 slice 共享）依赖选择器层；共享叶模块让两个消费方都只依赖叶子，依赖图像水位一样平。代价是多一个小文件与一次 re-export 间接，收益是「谁都可以安全地用它」。

### Why not 保留 KEPT_UNREAD 作为协议预留？

它是 Google Reader 的一个状态 tag 字符串，未来实现 kept-unread 时仍可从协议文档或 Git 历史恢复；当前保留会误导读者以为能力已接线。与《死代码与空壳集群清理》的判据一致：没有真实用户场景就删。不识别该标签的边界由兼容矩阵的[状态操作与冲突政策](../../../../docs/sync-compat-matrix.md#状态操作与冲突政策)节维护，不会因删常量而改变。

### Why not 保留 close-resolved（也许将来有人要监听）？

发出后无人接收的 emit 是死通路：观察者不存在，行为等于删掉；留着它还需在注释里解释「为什么没人听」。真要恢复该能力时，emit 与 listen 一起加，才是完整改动。删除时同步核对了事件为应用内部 IPC、本仓即全部观察面、前端设置镜像已有替代路径。

### Why not 一并删除已无前端调用的 IPC 命令签名？

明确非范围（父卡：不删命令签名，除非确认内部且无兼容义务并有证据）。命令签名是应用内外之间的版本化风险点，保留成本低；`feed_counts` / `scope_counts` 的函数体仍被 Rust 单测直接引用，`set_feed_ai_flags` 有兼容语义单测——删签名会连测试面一起砍掉。

## Consequences

**收益**：当前两个消费方共享一个解析实现，减少「范围派生」与「条目写库」分叉的修改面；零消费入口的清点有账（删掉的五项、保留的三项、边界外的两项），后续审查不必重新搜；`close-resolved` / `KEPT_UNREAD` / `client_login_url` 这些长期挂在 roadmap 的「只定义不用」项关闭。

**代价与已知上限**：

- `scope-id` 的同形复制守卫按源码文本计数（`match(/(\d+)/)` 恰一处 + `numericId` 定义恰一份）：它覆盖**同形复制**，不覆盖改名/换写法的语义级副本（如另写 `parseInt` 提取数字 id，守卫不会判红）；整体更换解析写法同样会打红、需同步更新守卫。这是「单点性必要」场景的有意成本（断言纪律允许的例外）。
- 前端 `api` 包装删除后，`feed_counts` / `scope_counts` 命令在应用运行期已无调用方（保留仅为签名与后续预留）；若未来重接，从前端包装加回即可（命令未动）。
- `origin_was_local` 与 `sync_now` 仍是「零生产消费」状态，处置理由记在 roadmap 与本 Note，未被本卡消除。

## Validation

scope-id域用独立真值表覆盖scope形态、feed_id/folder_id消费映射和导出引用同一性；源级计数仅防同形复制，不能证明没有改名或换算法的语义副本。历史正则锚定变异能判红，证据在tmp/optimization-20261008/OPT-017F。

删除前的消费者搜索界定当时范围，不是“后续审查再也不用查”的永久事实。编译与行为回归检验删除影响，注册/公共契约/测试消费需另外核对；当前门禁结果不在专题重复。
