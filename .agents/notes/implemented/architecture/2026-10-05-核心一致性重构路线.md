# Agent Note: 核心一致性重构路线

Status: implemented

## Problem

2026-10-05 对 v0.16.2 的审查发现，反复出错的是状态归属与协议口径：同一开关有多个判断入口，同一动作在五布局中有不同接线，列表快照与实体正文互相覆盖。已有功能、兼容规则和测试已形成维护成本，决定是否重写必须比较这些成本，不能只看文件大小。

## Decision

保留 Tauri 2、Rust、React 19、Zustand 5 与 SQLite 技术底座。先围绕实际缺陷收拢状态所有权、事务和协议规则，再测量性能；没有证据要求通过换框架解决这些问题。

本路线确定了四个方向，具体契约由专题记录承接：

1. [正文实体缓存](2026-10-06-正文与-AI-产物的实体缓存.md)与列表快照分离，以显式状态、请求身份和失效规则管理水合。
2. [查询与分页](2026-10-05-查询与分页契约.md)共用范围模型，写入返回真实回执，计数按快照对账。
3. 本地状态与同步意图同事务提交，[同步冲突政策](2026-10-07-同步冲突政策单点.md)显式区分协议与字段。
4. [订阅条目与共享内容身份](2026-10-12-订阅条目与共享内容身份.md)在后续实施中落地，取代本篇最初的“尚未实现”计划。

“正确性 → 恢复能力 → 操作一致性 → 性能”是当时的实施优先级，不是要求今后全部需求串行的永久流程，也不代表四类问题已消失。五布局的后续焦点、响应式与媒体工作有各自验证范围。性能结论只适用于 [性能记录](../../../../docs/performance.md)中对应构建和数据集。

既有同文政策继续保持：read 可传播到同 URL 副本，unread/star 只作用当前条目。内容共享本身不推导状态共享；如要改为源内隔离，必须明确改变用户行为并同步本地写入、远端目标和说明。

## Alternatives considered

- **推倒重写或换栈**：会重新实现服务端差异、事务边界、状态与焦点规则；当时没有证据表明这些问题源于技术栈，故未选。
- **加入第二套查询缓存**：TanStack Query 可以提供缓存原语，但当时的问题是既有状态的所有权不清。未决定整体迁移所有权前，再加入一套缓存会扩大同步边界；这不是否定该库在其他架构中的适用性。
- **先优化性能**：在分页与存储身份未稳定时优化容易作废。选择先测量；后续已出现需要处理的场景，不能沿用某次夹具“未触线”推断无需优化。
- **立即改为多连接或专用数据库线程**：增加生命周期、事务可见性和 WAL 协调成本。先区分慢查询与锁等待，出现可复现的竞争证据再决定。
- **把同文 read 广播改为布局隔离**：这会改变已读传播的产品语义；当时保持既有规则，没有把架构整理当作修改该行为的授权。

## Consequences

专题边界让后续修改有可追查的责任入口，但引入的请求版本、缓存和回执协议本身也需要验证。统一了入口并不等于所有竞争窗口已经关闭，框架保留也不构成“架构已全面通过”的证明。

2026-11-06 对基线 `91ece562` 的证伪审计仍确认正文失效、乐观回滚、焦点竞争和画廊窗口等问题。当前问题与优化次序集中在 [路线](../../../../docs/roadmap.md)，本篇不把这些建议写成已实现决定。
