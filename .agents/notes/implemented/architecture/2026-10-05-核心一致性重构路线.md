# Agent Note: 核心一致性重构路线

Status: implemented

## Problem

外部审计在 v0.16.2 上给出的结论是：缺陷不集中在某个模块，而集中在**业务状态与协议语义的组织方式**。同一类问题反复出现（同一开关在不同入口口径不一致、同一动作在不同布局行为不同、同一份状态在多个地方各存一份），局部修复能解决一个场景，却无法保证整条链路一致。同时项目已经积累了相当数量的功能与测试，任何大改都必须先回答「要不要推倒重写」。

## Decision

**保留技术底座，不推倒重写。** 继续用 Tauri 2 + Rust + React 19 + Zustand 5 + rusqlite(bundled, FTS5)。审计未发现技术选型问题的证据——问题在状态与协议的组织方式，换框架只会用新框架重新实现同一批规则。

**重构以数据一致性为中心，分四块推进：**

1. 文章实体与视图分离——正文用明确的状态机（未请求 → 加载中 → 成功 / 空正文 / 不存在 / 失败），请求去重、重试、过期响应归同一模块；
2. 查询范围与批量操作共用统一模型——后端返回实际影响条数，前端按操作版本确认或回滚；
3. 统一所有状态写入的事务与同步语义——本地状态与待同步记录同生共死；
4. 「同一篇内容」与「各订阅源条目」分开建模（**未实现**，见 [docs/roadmap.md](../../../../docs/roadmap.md)）。

**阶段顺序：正确性 → 恢复能力 → 操作一致性 → 性能。** 每阶段的完成标准写在下面，前一阶段验证通过后才立项后一阶段，避免规格腐烂。

| 阶段 | 内容 | 完成标准 | 状态 |
| --- | --- | --- | --- |
| 一 | 正文加载、标读范围、状态写入事务与计数 | 刷新不丢正文；操作范围可解释；失败不假成功 | 已交付 |
| 二 | 查询缓存、统一分页、协议对账显式冲突政策 | 快速切换不串数据；旧文章可达；不同协议行为有明确说明 | 已交付 |
| 三 | 五布局交互一致性（加载/错误/重试/快捷键/焦点/返回位置统一） | 同一动作在五布局行为一致 | 已交付 |
| 四 | 大库与媒体性能 | 先按真实数据量测量再决定是否优化 | 已测量，结论为无需优化 |

**协议立场**：Google Reader 是通常优先推荐的协议，Fever 是有明确能力限制的兼容选项。协议间行为差异（对账方向、历史回溯能力）不作为隐式分支存在，而是提升为显式冲突政策，见[同步冲突政策单点](2026-10-07-同步冲突政策单点.md)。

**明确不做（同样重要）：**

- 不更换技术栈、不重写；
- 不引入 TanStack Query 等第二套缓存方案——与「统一所有权」这个目标直接冲突；
- 本轮不做五布局视觉润色与性能优化——顺序靠后，先正确性；
- 不改 Rust 单连接为读写分离或专用 DB 线程——无锁等待证据，等测量结果；
- 同文副本的读状态跨源传播**保持现状**（`sync/push.rs` 把 read 广播给记录的全部同文副本）：owner 不在场时按保守默认处置，显式记录为政策而非默认行为，是否改为「布局隔离优先」留待产品决定。

## Consequences

**收益**：四块重构把「同一件事在多处各写一遍」收敛为单点，后续缺陷的定位面显著缩小。阶段顺序避免了两类浪费——在正确的数据模型建立前做性能优化，以及在交互口径统一前做视觉打磨。协议立场写下来以后，「GR 与 Fever 行为不同」不再是需要每次重新论证的事。

**代价**：

- 四阶段串行，总周期长；期间功能需求只能插在阶段之间；
- 「不做清单」意味着已知的界面不统一（如 `--text-tertiary` 在深色下的对比度约 4:1，处于 WCAG AA 边缘）会保留一段时间；
- 第四项（同文内容与各源条目分开建模）至今未做，因此「跨源同文只广播 read 不广播 star」这类问题会持续存在；
- 同文传播按现状保留是**未经产品确认**的默认，一旦 owner 改主意，受影响面是 push 语义与用户可见文档，不只是实现。

## Alternatives considered

### Why not 推倒重写？

审计明确「有必要重构但没有必要推倒重写，也没有证据支持更换技术栈」。重写会丢失的不是代码行数，而是四年积累的边界知识：哪些服务端有哪种怪癖、哪些操作在锁外做、哪些断言锁的是缺陷本身。这些知识分散在注释与测试里，重写等于全部重学一遍。

### Why not 引入 TanStack Query？

它解决的是服务端状态缓存，而本项目的痛点是**同一份状态的所有权不清**（谁的快照是真值、谁负责失效）。引入第二套缓存会让所有权再分一层，与目标相反。审计的判断是「非必要」，当前结论是按需自研的部分——`bodyCache` 的实体缓存与显式失效——反而更贴合需求（见[正文与 AI 产物的实体缓存](2026-10-06-正文与-AI-产物的实体缓存.md)）。

### Why not 先做性能优化？

审计已确认性能问题的证据薄弱，且性能优化会固化当时的数据结构——若第二阶段要改分页与缓存模型，优化成果会一起报废。第四阶段先测量后决定，实测结论是判定线全部未触发（见 [docs/performance.md](../../../../docs/performance.md)）。

### Why not 同文副本改为「布局隔离优先」？

这是产品语义问题，不是技术问题：跨源同文（同一篇文章被多个订阅源收录）标记已读时，应该只影响当前源还是全部副本？既有设计选择全部广播，理由是双端场景下用户预期「我读过了」。改动它意味着用户在一处标读后，其他源里同一篇仍显示未读——这与多数 RSS 用户的心智模型相反。owner 不在场时不做产品级改动是纪律，故保持现状并显式记录。
