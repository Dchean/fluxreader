# Agent Note: 同步队列生命周期与本地意图

Status: implemented

## Problem

2026-11-03 调查的真实库里有 44 条 direct 文章的状态意图：文章已读，但文章与远端条目没有
`remote_id`。`sync_queue` 只有 `attempts/last_error`，没有「为什么不能推」的
状态；`plan_push` 遇到无 `remote_id` 直接 `continue`，于是这些行既没成功、
也没失败、`attempts` 一直为 0。侧栏仍把它们计入「等待同步 44 条」，而
`prune_stale_unbound` 在 30 天后会直接物理删除整行——本地已读仍保留，但
「这条永远没同步」的事实无提示消失。

这不是一个 ACK 协议问题，而是队列生命周期没有把「可推」「等待身份」「仅本机」
「过期未确认」分开。继续用单一总行数展示，前端无法解释，后端也无法安全清理。

## Decision

`sync_queue` 采用显式生命周期状态。最初的 v32 增量迁移保留全部旧列，目的是让当时的升级可回滚；2026-11-09 用户选择独立新格式且不兼容旧库后，这条升级路径已被取代。当前直接初始化新格式，缺少所需格式或来源证明列的旧库只读拒绝并保留原文件，不执行下述历史迁移。

当前文章状态队列的分类如下；“可推送身份”要求精确 `remote_id`、真实 Content 已确认的 `remote_origin_feed_id` 和当前有效且相容的来源同时成立：

| 状态 | 语义 | 是否计入 waiting / 自动推送 |
| --- | --- | --- |
| `local_only` | 文章没有可推送身份，所属 feed 也未绑定远端 | 否 / 否 |
| `bindable_retry` | 所属 feed 已绑定，但文章尚无当前有效、来源已证明的远端身份 | 否 / 等待绑定或补证 |
| `bound_pending` | 文章有精确 `remote_id` 和已验证 origin，当前来源有效且相容 | 是 / 是 |
| `retry_wait` | 身份及来源证明仍有效，但最近一次推送或读回失败、仍可重试 | 是 / 是 |
| `failed` | 终态失败，等待人工处理 | 否 / 否 |
| `expired_unconfirmed` | 超过 30 天仍无可推送身份；保留本地意图 | 否 / 否 |

历史 v32 迁移按当时的绑定规则分类旧行，不联网、不推送、不删除。`add_feed` 保留为
`kind='legacy_add_feed'`，有 `feed_url` 时为 `bound_pending`，否则
`local_only` 并写 `unbound_reason='no_feed_url'`；其它历史动作保留为
`legacy_other`，写 `unsupported_legacy_action`。两类 local-only 都写
`last_error_class='unbound'`，与运行时 `enqueue_sync` 同口径，不伪造推送失败。
旧 `attempts > 0` 且有身份的行进入 `retry_wait`，`attempts/last_error` 原样保留。

**老化不是删除。** `prune_stale_unbound` 改为把超过 30 天的
`local_only/bindable_retry` 转为 `expired_unconfirmed`，队列行与文章
`is_read/is_starred` 都保留。只有用户显式清理、文章删除或成功确认才可出队。

**推送计划不再静默跳过。** `plan_push` 对缺少可推送身份的项，按同 feed 是否已
绑定写回 `bindable_retry` 或 `local_only`，同时写入 `unbound_reason` 与
`last_error_class='unbound'`；`last_error` 只留给真实推送失败，分类本身不
递增 `attempts`、不伪造网络错误。身份查询失败用 `?` 上抛。
`failed/expired_unconfirmed` 不自动重推，也不被重新改回 pending。
`enqueue_sync` 在入队时完成同一分类；`mark_all_read_with_enqueue` 的集合化
`INSERT ... SELECT` 也按同样规则写状态，避免批量入口短暂制造假 waiting。

**绑定再驱动是数据库单点。** 最初由`articles.remote_id`触发；2026-11-10起改由真实Content响应写入`remote_origin_feed_id`且当前source有效后触发，只把
同一 `article_id` 的 `local_only/bindable_retry` 行恢复为 `bound_pending`。
身份来源仍只能是 pull 已确认的同源远端绑定；不使用全局 URL、标题或时间跨
feed 猜测，也不把旧账号身份迁给新账号。

裸remote ID不再计作可推送身份。入队、全部标读集合SQL、恢复过期意图、计划与30天老化都消费同一来源证明条件；ID或来源生命周期改变清证并将待发项转回等待，意图和终态仍保留。Push捕获来源token，在每次发送前及ACK落库同一DB锁内复核；旧回包不能出队，也不能把等待身份项改成网络重试。Fever原本逐ID发送，新增复核不增加mark数；toggle探测与mark之间也复核。已合法发送的请求可能在来源变化后才远端完成，该现实边界由后续重新补证和读回承担，不宣称撤销。证明来源与冷绑定预算归[运行生命周期](2026-11-05-同步运行生命周期与诊断.md)。

**统计契约按可推送性收口。** `waiting` 只数
`bound_pending + retry_wait`；`local_only`、`bindable_retry`、`bound_pending`、
`retry_wait`、终态 `failed`、`expired_unconfirmed` 分别暴露。`last_error` 只取
`retry_wait/failed` 中 `updated_at` 最新的摘要。前端 store 保留
`syncWaiting/syncFailed` 兼容字段，同时写入各分类字段；`syncFailed` 由
`failed + retry_wait` 合成。2026-11-04 起 Sidebar 常驻只显示同步账户名/本地模式，
`local_only/bindable_retry/expired_unconfirmed` 与 outbox 计数改为橙色 tone +
tooltip/aria 详情（见 [同步灯与账户状态](../feature/2026-11-04-同步灯与账户状态.md)）；
SyncTab 保留完整统计并逐类解释，不把事件载荷降成三字段。终态 `failed` 仍不得
回落为「后端已同步」，摘要明确「终态失败项不会自动重试」且不承诺连接后自动补推。

**手动同步的远端写回确认是可撤销证据。** `states` 阶段收到全零队列事件才把
`remoteWriteConfirmed` 置为 true；同一活动后续收到任一
`waiting/failed/retry_wait/local_only/bindable_retry/expired_unconfirmed` 非零
统计时立即撤销，阶段文案从「远端已写回」回退为普通拉取中。

ACK 读回已由后续实现补齐：写操作返回 200/OK 只代表待确认，逐目标读回一致
后才进入 `done`；当前读回端点无法证明目标已删除，空/短响应、缺字段或
状态不一致统一落 `retry_wait/verification`。`failed/target_missing` 仍是
保留给未来权威删除证据的终态，不由当前读回路径写入。见
[状态写回 ACK 验证与条目三态](../bug-fix/2026-11-03-状态写回ACK验证与条目三态.md)。
时间戳身份与跨 feed 自动绑定仍不引入，继续按
[同步冲突政策单点](2026-10-07-同步冲突政策单点.md)和
[状态写入事务化与对账守卫](../bug-fix/2026-09-18-状态写入事务化与对账守卫.md)
的边界处理。

## Alternatives considered

### Why not 继续用 `attempts` 推断一切？

无 `remote_id` 的项根本没有发出请求，`attempts` 为 0 是事实，不是成功；
继续用 `attempts > 0` 只能识别「尝试过并失败」，无法回答「为什么一直没推」。
状态必须成为持久事实。

### Why not 在 `plan_push` 里只记日志并保留旧行为？

日志不能驱动 UI，也不能让统计区分 local-only 与远端等待；而物理 prune 仍会
静默删除本地意图。状态必须落库，并在绑定后能被消费。

### Why not 30 天后直接删除无身份项？

本地已读/收藏仍在文章行里，删除队列只会让「未同步」事实消失。保留为
`expired_unconfirmed` 才能让用户知道「本地状态保留、自动推送已停止」。

### Why not 由 `plan_push` 再次按 URL/标题/时间找远端条目？

那会把候选匹配变成隐式绑定，并可能在不同 feed 或不同账号间借身份。当前
只消费真实 Content 已确认来源且仍有效的精确远端身份；完成绑定及补证后再驱动状态，
不应在推送计划里增加第二套身份算法。

## Consequences

- 历史 v32 升级把当时采集的 44 条无身份意图所代表的数据类别移出 waiting；当前新格式继续按可推送性分类，但不自动迁移那批旧库。侧栏以橙色未同步 tone（详情在 tooltip/aria）
  阻止误报，设置页逐类显示等待绑定、仅本机与过期项；队列行不会在 30 天时静默消失。
- 本地已读/收藏不因老化回滚；文章若获得来源已证明且当前有效的远端身份，触发器会把原意图送回
  pending 并照常推送。该自动恢复只适用于 `local_only/bindable_retry`；
  `expired_unconfirmed` 已停止自动推送，设置页现提供“重试过期项”：摘要代际
  传入 `sync_retry_expired`，锁内复核当前账号，以当前本地 read/star 创建新操作
  ID 并按 bound/bindable/local 分类，缺文章保留过期，重复点击幂等；见
  [GR 权威集合回补与过期意图恢复](../bug-fix/2026-11-05-GR权威集合回补与过期意图恢复.md)。
  换号或断开仍清旧队列，确认框明确直连 read/star 值保留不等于自动补推。
- 代价：队列会保留 `local_only/expired_unconfirmed` 行，长期使用后表可能变大；
  这是保留用户意图的必要成本，后续只能由显式用户操作或文章删除回收。
- `bindable_retry` 只表示「同 feed 有绑定可能」，不表示远端一定存在该条；
  等待窗口内的身份发现仍依赖现有 pull 路径。
- `failed` 是终态，不会自动重试；`mark_queue_target_missing` 仍保留给未来能
  提供权威删除证据的端点，但当前 ACK 读回不会因 200 空/短响应写入该状态。
  当前读回网络/字段/一致性问题进入 `retry_wait/verification`；若将来写入
  `failed/target_missing`，手动/全量 states 阶段会在推送前做一次显式重排
  （自动同步不重排），提供 UI“重试”入口。
- 最初升级方案只加列、索引和绑定触发器；当前用户已选择独立新格式且不迁移旧库。来源证明列直接属于新格式，缺列旧文件只读拒绝并保留原字节。
- 2026-11-03 制定时 v32 尚未发布，补齐原因只作用于 v31→v32 升级；曾用早期开发 v32 打开的库不会自动回填该原因。此处保留当时迁移的限制和可回滚理由；当前独立新格式不再提供该升级路径，也不授权清理或改写旧库。

## Verification

历史隔离库覆盖无身份分类、老化不删除、绑定触发、过期不自动再驱动、legacy 原因迁移和重复升级；前端逻辑/组件覆盖六态统计、队列变化撤销确认与错误呈现。ACK 端点空/短读回不能证明删除的边界继续有效。2026-11-06 审计未将已有套件数当作生命周期完整性证据；当前缺口和恢复入口见[同步路线](../../../../docs/roadmap.md#sync-correctness)。

历史实现与测试定位见[整理前记录](https://github.com/Dchean/fluxreader/blob/91ece562d79fd909642cd6d570d636e884b7387e/.agents/notes/implemented/architecture/2026-11-03-同步队列生命周期与本地意图.md)。本篇记录决定，不单独维护当前门禁计数。
