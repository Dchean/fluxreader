# Agent Note: 正文与 AI 产物的实体缓存

Status: implemented

## Problem

列表反复刷新、筛选、翻页时，如果正文和 AI 产物随视图行一起替换，会同时出现两类错误：保守 `newValue || oldValue` 合并使已清除产物复活；无条件清空水合标记又会让 id 未变的组件停在加载态而不再发请求。需要独立于列表生命周期的正文归属。

## Decision

`src/store/bodyCache.ts` 保存按条目的正文实体。无记录表示未请求；记录状态为 `loading / ready / cleared / missing / failed`，其中 loading 是进行态，空正文、不存在和失败有独立语义。LRU 当前上限为 2000 项；这是数量预算，不是严格字节内存上限。

列表快照保留轻字段和 URL，正文按需水合，不在 reload 时同时请求所有文章。`reconcileBodyEntities` 处理行真值对齐，显式内容操作也会经 `invalidateContentRevision` 等入口失效；它们必须遵守同一版本协议，不能把某一个函数误称为唯一失效入口。请求携带 `contentRevision` stamp，响应落地前核对。

实体携带产物与签名，同一次更新应对齐两者。命中判定由后端 `ai_cache_check` 负责，显示状态由 AI 切片选择器负责；旧签名/无签名产物的现行标记为“已过期”，具体规则见[AI 完成信号与缓存提交](2026-10-08-AI完成信号与缓存提交.md)。无实体时仍存在视图行兼容回退，不能据此声称所有旧值复活路径都已移除。

`selectArticleBody` 返回新对象，Zustand 5 订阅必须维持稳定的快照比较。现有订阅使用 `useShallow`；历史上漏掉它曾触发 `getSnapshot should be cached` 与 React #185。需要验证所有消费者的订阅行为，不能只给单个组件加临时 memo。

## Alternatives considered

- **引入另一套缓存库**：原问题是列表、实体与同步意图间的所有权；未计划整体迁移时加入另一所有者会增加边界。选择小范围实体缓存，不将此理由推广为库本身不适合本地产物。
- **列表继续带正文并保守合并**：掩盖正文丢失，却无法区分“后端未返回”与“已明确清除”，容易复活已删除内容。
- **每次 reload 全页重拉正文**：会形成大量 IPC、解析与内存分配；按需水合保留较小的工作集。具体滚动性能必须按数据和布局测量，历史 50k 夹具不能证明所有正文/画廊场景无卡顿。
- **组件自行缓存选择器对象**：把缓存键正确性分散给每个组件；浅比较订阅直接解决引用不稳定的来源。

## Consequences

实体与视图分离减少了列表替换对正文的影响，但新增的 stamp、内容身份、AI 校验缓存和组件 effect 必须闭合。2026-11-06 在 `91ece562` 实测：内容身份变化且 snippet 同时变化时，实体记录删除会丢失刚推进的失效版本，导致 Reader 不重新水合、旧详情覆盖新正文；AI 校验状态也有内容变化后过期及清除后迟到恢复的问题。它们登记在[阅读与状态](../../../../docs/roadmap.md#reader-and-state)和[AI 与内容](../../../../docs/roadmap.md#ai-and-content)，不能再写“清理后旧值不可能复活”。

## Verification

纯前端逻辑测试不能证明 React 订阅渲染；现有 jsdom 真实挂载可以验证 effect、订阅和异步接线，真实 Edge/WebView2 才能证明几何与媒体行为。历史 CDP A/B 证据证明过浅比较修复；上述审计反例限定了当前缓存协议的保证。原始设计及测试背景见[整理前记录](https://github.com/Dchean/fluxreader/blob/91ece562d79fd909642cd6d570d636e884b7387e/.agents/notes/implemented/architecture/2026-10-06-正文与-AI-产物的实体缓存.md)。
