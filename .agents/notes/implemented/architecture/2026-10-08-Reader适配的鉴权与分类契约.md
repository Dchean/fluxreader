# Agent Note: Reader 适配的鉴权与分类契约

Status: implemented

## Problem

Google Reader 兼容层有两个被「按 Miniflux 猜」掩盖的兼容缺口（OPT-004，审计 F02/F04）：

1. **认证形态**：旧实现 GET 带 `Authorization: GoogleLogin auth=<auth>`、POST 只发表单 `T=<auth>`。但 FreshRSS 的 `greader.php` 在**所有**请求上靠 Authorization 头设用户上下文（`authorizationToUser`），写端点（edit-tag / subscription/edit）另查独立 action token——客户端经 `GET /reader/api/0/token` 获取，FreshRSS 返回 `str_pad(sha1(salt+user+apiPasswordHash), 57, 'Z')`，与登录 auth 是**两个字符串**；而 Miniflux 的 middleware 对 POST **只读** `T`（不看 Authorization），且它的 `/token` 端点返回登录 auth 本身。同一套客户端代码必须同时满足两种形态，不能按 URL 后缀猜服务端类型。
2. **分类形态**：旧 `pull_feeds` 要求 tag 带 `type:"folder"` 且从 `label` 取分类名、subscription category 也要求 `type:"folder"`。FreshRSS 的实现是：tag/list 的目录 tag 只有 `{id:"user/-/label/名", type:"folder"}`——**没有 label**；subscription/list 的 category 只有 `{id, label}`——**没有 type**。于是 FreshRSS 用户同步后目录可能完全丢失、订阅全部落「未分类」。

## Decision

依据主控保存的固定上游源码（FreshRSS 219eaf58 的 `p/api/greader.php`、Miniflux 的 `internal/googlereader/middleware.go`，见 `tmp/optimization-20261008/upstream/`），客户端按以下契约实现，测试用**严格夹具**锁定：

1. **Authorization 全程携带，T 与 auth 职责分离。** 所有 API 请求（GET 与 POST）都带 `Authorization: GoogleLogin auth=<auth>`；POST 表单的 `T` 用 action token——首次写前 `GET /reader/api/0/token` 换取，`tokio::sync::OnceCell` 单次缓存（同一客户端多次 POST 只取一次；失败不缓存，下次重试）。Miniflux 返回 auth 本身、FreshRSS 返回另一字符串，两种都接受，客户端不解释其内容。
2. **token 回退只对明确 404。** `/token` 返回 404（该实现没有此端点）才退回用登录 auth 当 `T`；401/403/5xx、空响应体、网络失败一律如实报错——不回退、不猜 URL、不吞认证错误。回退条件放宽会把「认证被拒」伪装成「换一种请求形态重试」，掩盖真实故障。
3. **`GReaderClient::new(endpoint, token, http)` public 签名不变**：直接构造路径的现有测试继续可用；action token 惰性获取，不改变构造语义。
4. **分类识别收口为 `greader::category_name(id, label, type_)`**（`pull_feeds` 的 tag/list 与 subscription categories 两处共用）：
   - `type == "folder"`（Miniflux）→ 分类；
   - `type` 缺失但 id 是 label 前缀（`user/<user>/label/<名>`，FreshRSS subscription 形态）→ 分类；
   - label 字段优先；缺失时从 id 的 `/label/` 之后解析，**原样保留中文与斜杠**（`技术/阅读` 是一个目录，不按 `/` 拆层）；
   - 其余（`user/-/state/...` 状态 tag、`type:"tag"` 的用户标签）→ None，**state tag 绝不建目录**。
5. **写操作响应必须验正文，出站分类必须用完整 stream id（R1）**：
   - `post_form_text`（edit-tag / subscription/edit）要求 200 **且**响应体 trim 后等于 `OK`；
     200+`FAIL`、200+空体、其它正文一律报**脱敏协议错误**（只带路径与状态，不回显响应体）——
     调用方据此不得按成功 prune 队列，用户意图不会静默丢失；
   - `edit_subscription(feed, title, dest_label)` 的 `dest_label` 是**用户裸目录名**，
     wire 上的 `a` 无条件前置一次为 `user/-/label/<名>` 再交 `reqwest.form` 编码；
     目录名本身以 `user/-/label/` 开头时也不得按字面判定「已格式化」而少前置
     （名字是用户数据，不是标记）。不在客户端做「入站 label 已是完整 stream id」的推断。
6. **测试锁定分层**：`src-tauri/tests/greader_compat_e2e.rs` 用两个自建严格夹具（Miniflux 形态只认 POST `T=auth`；FreshRSS 形态要求所有请求带 Authorization、写请求 `T` 必须等于 `/token` 返回的另一字符串）驱动**生产** `GReaderClient` / `sync::feeds_phase`；R1 起夹具支持写响应注入（200+FAIL/空体）与 `subscription/edit` 实际移动分类（裸名不移动）。共享 `mock_greader.rs` 补 `/token` 路由并按真实 wire 解析 `a`（不校验认证，也不放宽既有断言）；`sync_gap_repro_e2e.rs` 两处旧断言按真实 wire 形态更新（未减断言）。禁止把夹具成功表述为真实服务端实测。

## Consequences

- FreshRSS 写操作（标读/收藏/订阅编辑）从「可能 401/无效」变为携带 action token 的正常请求；Miniflux 行为不变（其 `/token` 返回 auth，`T` 值与旧实现相同）。
- **代价**：每个客户端实例首次写操作多一次 `GET /token` 往返；对无 `/token` 的实现该请求是 404 回退（一次额外请求后回到旧行为）。
- FreshRSS 的分类（含只在 tag/list 出现、无订阅挂载的空目录）现在会被创建；`label` 与 `id` 两路取名合并为一个单点，后续新形态只改一处。
- 认证失败不再被吞：token 获取失败、写请求 401 都会向上传播为明确错误（错误信息不包含 token/凭据正文，不把敏感值写进错误或日志）。
- 「2xx 即写成功」的旧认知被废弃：`200+FAIL`/空体是协议错误，队列保留待重推；代价是错误响应体不进错误文案（排障时需服务端日志，换取不泄露实现细节与敏感片段）。
- 出站 `a` 形态从裸名变为完整 stream id：FreshRSS 会真正把订阅移动到用户目录（此前裸名被其解析为空名 → 落到默认分类）；接受既有测试的期望值同步更新为 wire 形态（断言未减少）。
- 与 [Endpoint 适配契约](../feature/2026-10-07-Endpoint-适配契约.md) 部分重叠（同属「两种服务端差异」），但**未取代**：那篇管「API 根在哪个路径」（探测/缓存/报错），本篇管「请求怎么认证、分类怎么归一」。改认证或分类不应动端点探测的 404 口径，反之亦然。
- 真实服务端 × 部署版本验收仍单列；本决定只声明固定源码契约 + 严格夹具验证。Fever、队列/账号生命周期不在本契约范围。

## Alternatives considered

### Why not 按 endpoint 后缀/已知域名硬编码服务端分支？

无法覆盖自建与中间层实现，且端点解析（`endpoint_resolve`）已明确「不按 URL 猜类型」；认证与分类差异是响应内容层面的，硬编码分支会在用户升级/换实现时静默失效。

### Why not 继续用登录 auth 当 T（旧行为）？

Miniflux 恰好接受（其 `/token` 返回 auth 本身），但 FreshRSS 的写端点用独立 action token 校验，普通用户提交空 `T`/`x` 虽被其宽容分支放行，严格校验路径（`hash_equals(...)`）则要求真 token；沿用旧行为等于把「FreshRSS 上写操作是否生效」交给服务端的宽容分支，不可依赖。

### Why not 每次 POST 都先取一次 token（不缓存）？

多余往返；且同一客户端并发/连续写会放大请求量。OnceCell 缓存失败不固化，重试语义不受影响。

### Why not token 获取失败时回退 auth 并重试？

会把 401/403（凭据问题）与 5xx（服务端问题）伪装成「另一种请求形态」，把真实故障藏起来；且 token 与 auth 语义不同（FreshRSS 写端点只认 token），回退发出的是无效请求，错误更晚更模糊。

### Why not 容忍 `type` 缺失时把任何 `user/.../label/` tag 都当目录？

Inoreader 形态的用户标签（`type:"tag"`）也是 label 前缀；只看前缀会把用户标签误建为目录。规则限定「type 缺失」或「type == folder」两种，兼由 `state` 路径挡掉状态 tag。

### Why not 把分类名按 `/` 拆成多级目录？

FreshRSS/Miniflux 的分类名就是用户输入的完整字符串，斜杠是名称的一部分（本决定前 mock 的 `a=目标分类` 断言已暴露过中文解码问题）；拆层会造成目录结构与用户意图不符且不可逆。

### Why not 写端点只验 HTTP 状态（旧行为）？

真实生态存在「2xx + 错误体（如 `FAIL`）」表示写未生效的响应；按成功处理会 prune 队列，用户意图静默丢失且永不重试——比错误更糟。严格验 `OK` 的代价是少数实现若用 204/空体表示成功会被判失败（已固定的两服务端都回 `OK`，未观察到该形态；若出现真实案例再按版本收敛）。

### Why not 把响应体原文放进协议错误里方便排障？

响应体可能含实现细节/敏感片段，且调用链会把错误写进 `sync_queue.last_error` 与日志；排障价值不足以换泄露面。协议错误只带路径与状态，另由夹具测试覆盖各失败形态。

### Why not 在 `edit_subscription` 里检测「已格式化」再补前缀？

用户目录名是数据：名字本身以 `user/-/label/` 开头完全合法，按字面检测会少前置一次、把订阅移进错误的分类。无条件前置一次是唯一不会误判的规则（入站方向解析 id 是另一件事，见 `category_name`）。

### Why not 在共享 mock_greader 里直接加严格校验？

共享 mock 被多个套件复用，收紧校验会改变既有契约、放大无关套件的维护面；严格形态放在新套件的独立夹具里。共享 mock 只做两件不改变断言强度的事：补 `/token` 路由、按真实 wire 解析 `a`（此前它不校验 `a`，解析是补齐真实行为而非放宽）。
