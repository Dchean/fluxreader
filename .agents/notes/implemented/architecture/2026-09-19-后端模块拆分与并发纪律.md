# Agent Note: 后端模块拆分与并发纪律

Status: implemented

## Problem

Rust 侧曾有四个单体文件：`db.rs`、`commands.rs`、`sync.rs`、`ingestion.rs`。它们把数据访问、Tauri 命令、同步阶段、抓取解析全塞在一起，导致三个具体后果：

1. 一次改动要在一个几千行的文件里定位，审查者无法只读受影响的领域；
2. 单测只能挂在文件末尾，测试模块随文件一起膨胀，测试与实现互相争夺阅读注意力；
3. 「这个文件多大算过大」没有口径，后续任务想给已有文件补单测都会形式上证成需要拆分。

更隐蔽的问题是并发。Tauri 命令、同步 push/pull、定时调度器、抓取都会碰数据库与 HTTP，而这些路径的锁获取顺序没有任何书写下来的规矩——一旦有人把网络请求写进锁作用域，就会在真实使用中变成随机卡死，而单元测试永远不会暴露它。

## Decision

**按领域拆分为目录模块，公开路径保持不变。** `db.rs` 作为门面只保留子模块声明与再导出（`pub use`），`db/` 下按领域分文件；`commands.rs` → `commands/`（按命令族）；`sync.rs` → `sync/`（按同步阶段与协议）；`ingestion.rs` → `ingestion/`（http / parse / staged / favicon）。拆分的验收标准是**业务代码逐字一致**：公开路径、命令注册表、行为都不变，由既有集成测试保证。

**一个文件不拆的判据是「有没有天然接缝」，不是行数。** `db/articles.rs` 的生产段约 750 行，单一领域高度内聚，没有可分离的状态边界，因此**不拆**；`ingestion/` 拆得动是因为它有四个不共享状态的部件。行数上限按**生产段**（`#[cfg(test)]` 之前的部分）衡量——否则任何「给既有文件补单测」的任务都会形式上违规。

**并发纪律（后加锁的地方必须遵守）：**

- `db` 的 `MutexGuard` **never** 跨 `.await` 持有；
- HTTP 请求一律在锁外发起；
- `PUSH_LOCK` 与 db 锁之间不存在反向获取路径。

这三条是可以在审查里逐条核对的不变量，也是判断「某段新代码能不能在锁内做这件事」的唯一依据。

**刷新写回的边界与不变量（OPT-003 原位补记）：**

- 三段式刷新（`refresh_feed_staged`）形状钉死为「锁内读快照 → 锁外 HTTP+解析 → 锁内写回」：HTTP 永远不在数据库锁内发起（上列纪律的具化），但**锁外不等于可以自由拆分写回**。
- `apply_refresh_result` 的 `Fetched::Body` 分支必须整体在**单一短事务**内提交：源元数据（title/favicon/site_url）、逐条文章 upsert、ETag/last_modified、last_fetched_at/fail_count/fetch_failed 同生共死——任一步失败（含条目触发器/磁盘错误）全量回滚，不得留下「条件头已换新、条目只进一半」的半提交。实现用 `unchecked_transaction`（函数持 `&Connection`）：现有调用方（命令层 refresh_feed、调度器 refresh_all）都不持外层事务，不会嵌套 BEGIN，因此无需 savepoint；将来若有人在事务里调它，BEGIN 会显式报错而非静默降级。`Fetched::NotModified` 分支与失败标记写回是单语句，保持原位。
- 全文保护（OPT-003 R1 修订）：全文写入边界 `update_article_fulltext` 必须 HTML 与 `body_text` **同源**（纯文本由提取 HTML 经 `html_to_text` 派生；旧版只写 HTML+flag，留下「HTML=提取全文、纯文本=旧 RSS」的错配）。条目 `fulltext_extracted=1` 时，抓取重放的 upsert 冻结 `content_html`（优先保持提取全文）、并按保留的 HTML **重算** `body_text`（历史错配行在刷新时恢复同源），不得用 RSS 摘要覆盖任何一列——否则会留下「标志=已提取、正文=摘要」的不一致（基于摘要的 AI 缓存随之失准）。未提取行不受影响（不读全文大列、零额外开销）。

对应反向注释：`ingestion/staged.rs` 的 Body 分支与 `db/articles.rs` 的 upsert 两处 UPDATE 分支均指回本 Note；故障注入回归（BEFORE INSERT 触发器第二篇 RAISE(ABORT)）在 `tests/staged_refresh_e2e.rs`。

**迁移只追加，不重写。** 每次 schema 变更是一条新迁移，不改历史迁移的语句；`user_version` 只作递增标记，不作为「某次回填已跑完」的凭据（后者的用法曾造成半途中断永不重试，见 [路线](../../../../docs/roadmap.md)）。

## Consequences

**收益**：审查面从「几千行」缩到「一个领域文件 + 门面」；单测与实现同域放置；`db/`、`sync/`、`ingestion/` 对 `crate::commands` 的引用为 0，依赖方向单向，模块边界可机械核对（55 个 `#[tauri::command]`、`generate_handler!` 注册表与前端 invoke 三者一致）。

**代价**：

- 多了一层目录与门面，跳转要在 `db.rs` 与 `db/*.rs` 之间走一次；
- 行号引用在文件内部仍然会漂移，跨文件引用必须按符号检索而非行号；
- 「生产段行数」是一个需要人肉数到 `#[cfg(test)]` 的口径，没有脚本守它。

**已知上限与重访信号**：`db/articles.rs` 不拆的前提是它保持单一领域内聚。若它开始出现第二个需要独立生命周期的实体（例如正文与 AI 产物在存储层分离），该前提失效，应重审拆分。

`db/settings.rs` 与 `commands/settings.rs` 是这次拆分留下的边界：settings 的读写在 db 层，命令层只做编排——`get_setting` 会解密敏感值并经通用 IPC 送出 webview，这条边界是有意的威胁模型决定，见[自检缺陷集群](../bug-fix/2026-09-29-发布前自检的缺陷集群与遗留.md)。

## Alternatives considered

### 为什么不用一段大注释代替拆分

在文件头写清「本文件包含哪些领域」成本几乎为零，但它不改变审查面：改动仍然要在几千行里定位，单测仍然挂在文件末尾。注释能承载「为什么」，不能替代结构。

### 为什么不为行数硬性拆 `db/articles.rs`

审计曾提出按 800 行上限拆分。但 `articles.rs` 是单一领域的连续实现，没有不共享状态的部件可切；强行按行数切会造出「上半段查询、下半段写入」这类没有语义的名字，代价是每次改动都要跨两个文件对齐上下文。对照 `ingestion/` 的四个部件（http / parse / staged / favicon）确实互不共享状态，拆了以后每个文件都能单独读懂——这才是拆分的正确判据。附带结论：一旦行数口径按整文件算，补单测就形式上违规，说明口径本身写错了。

### 为什么不开独立线程或读写分离处理数据库

单连接下所有查询都很短，没有观察到锁等待。引入读写分离或专用 DB 线程会带来连接生命周期、事务可见性与 WAL 交互的新问题，而在没有证据的前提下解决的是想象中的瓶颈。这个判断后来在 50k 篇文章的实测下复核过：全部查询低于 70ms，无锁等待证据，维持单连接（测量条件见 [docs/performance.md](../../../../docs/performance.md)）。

### 为什么不让 `db` 依赖 `commands`

拆分时最省事的做法是让子模块按需 `use crate::commands::*`，但那样依赖图会变成环，模块边界失去意义。选择把命令层作为唯一编排点：`db`/`sync`/`ingestion` 只提供能力，不知道谁调用它们。
