# Agent Note: 订阅写回能力矩阵与持久回执

Status: implemented

## Problem

B1/B2 已把订阅写回做成「本地变更与远端意图同事务 + 按账号 key/代际屏障推送 + 精确确认」的 outbox 执行器（见 [订阅写回 outbox 的生产执行器](2026-10-14-订阅写回outbox执行器.md)），但没有把**能力边界**与**持久状态**暴露给用户：

- `Backend::supports_subscription_write()` 只在执行器内部使用——IPC 层没有逐动作能力声明，UI 无从回答「哪个动作会写回远端、哪个仅本地生效」，用户只能从一次性 toast 猜测结果。
- `SubscriptionOutboxStats` 已存在但是**全库口径**且没有任何命令暴露：按 B2 的账号 key 语义，异账号（换号暂停）的队项不该混入当前账号的展示；`local_only` 终态项在 UI 完全不可见。
- `FeedsTab` 删除源确认仍写「同步服务端不受影响」——与 B2 的「本地删除 + 持久退订意图」直接矛盾；分类删除弹窗也没有成员逐源退订与空分类本地-only 边界的说明。

## Decision

**能力矩阵与持久回执都从后端单一事实源发布，UI 只做投影——两处不允许各写一套说法。**

- 只读 IPC `subscription_capabilities`（commands/sync.rs）：逐动作（新增 / 编辑标题 / 移动分类 / 退订 / 分类改名 / 分类级删除 / 空分类远端表达）× 三态（GReader / Fever / 未连接）的结构化枚举 `Supported | LocalOnly | Unsupported`，**枚举的 serde 名称即前后端契约**（Rust 单测锁定名称，前端 `SubscriptionWriteSupport` 联合类型逐字对应）。每个动作带 `detail`（与 support 同一来源计算的如实说明），顶层带 `overview` 概述与 B2 限制清单（结构化 `code + detail`，GReader 六条：逐成员表达 / 空分类本地-only / 分类命令延迟推送 / 400 容忍近似 / 非幂等 quick_add 有界重复 / `r=` no-op 假定）。
- 判据与执行器能力门同源（`Backend::supports_subscription_write`）：GReader 的六个本地可发动作 = `Supported`；Fever 同一组 = `LocalOnly`（无写订阅端点，动作仅本地生效）；未连接 = `LocalOnly`（本地照常、不产生远端写回）。**空分类远端表达两协议均 `Unsupported`**——没有可逐源表达的成员，也没有分类级端点：本地改名/删除照常（墓碑防复活），但不宣称远端已改。
- 只读 IPC `subscription_outbox_stats`：把 `db::subscription_outbox_stats` **收窄为账号限定**（新增 `account_key` 形参、谓词内联 SQL——不是在 IPC 层过滤，口径与索引都留在数据层）；未连接（无当前账号）返回全零（计数无归属）；凭据损坏/表级故障一律 `Err`（**不得返回 0 冒充「无待办」**）。payload 只含计数与错误摘要——不带账号、token 或任何凭据；`last_error` 由执行器错误模板构成，可能包含**自有** feed URL（含其查询参数），该 URL 本就在前端信任域内（feeds 数据已含）。
- 事件 `subscription-outbox-changed`（独立于 `sync-queue-changed`）：payload = 当前账号 `{pending, failed, local_only, last_error}`；发射点 = 入队命令（add_feed / delete_feed / update_feed / rename_folder / delete_folder / opml_import / sync_local_feeds，事务提交后锁外）＋ 执行器（确认出队 / 失败累计 / local_only 标记）＋ `try_push_subscription_outbox` 的兜底广播（离线/认证失败时入队仍要即时可见）。未配置同步静默不发、事件目标未注册 no-op（集成测试零影响）、账号/统计读取失败跳过（不编造零值事件）。
- 前端单一状态源：store 字段 `subOutboxStats` 与 `subscriptionCapabilities`——事件（App.tsx 监听器）与挂载/保存/断开后的主动刷新写入同一处；`src/lib/syncPill.ts` 三个纯函数驱动全部呈现：`subscriptionWriteSummary`（摘要行）、`subscriptionActionLine`（逐动作投影）、`deleteRemoteLine`（确认弹窗远端语义句）。设置页 = 摘要行（无待办不渲染；`local_only` 必须点名「仅本地生效」）＋能力卡（概述 + 逐动作投影）＋限制清单；FeedsTab = 删除源/分类的远端语义句**直接取** `caps.unsubscribe / delete_folder / empty_folder_remote .detail`，Fever 下另有常驻「仅本地」提示。
- **限制清单的落点**：数据在**后端返回结构**（结构化、可单测、可被多处消费），UI 渲染同一份数据（设置页能力卡下方的限制列表）。这不是两处各写一套说法，而是一处数据两处消费——选择后端结构承载内容，是因为它必须能被确认弹窗、摘要卡与未来的其它入口共同消费，且「漏渲染某条」可以在 Rust 单测里断言。

## 为什么独立事件而不是扩展现有 sync-queue-changed

两者 payload 语义与消费面不同：`sync-queue-changed` 是 article 状态队列口径（pill 的「等待同步 N 条」按条计），订阅写回是账号限定的动作计数（pending/failed/local_only）；混流会让两套统计互相污染，且会改动一个被既有测试与前端消费锁定的 payload 契约。新事件复用同一发射模式（set-once 目标注册表 + 锁外发射 + 未配置静默 + 单点 payload 构造），发射点各自独立、互不影响。

## Alternatives considered

### Why not 前端写死能力文案与确认弹窗文案？

前端知道当前协议就能写死两套文案，不依赖新 IPC。放弃：B2 的限制清单有六条、部分与协议无关，「协议事实」会被复制成多处（执行器 / 前端文案 / 测试），任一处漂移都会让用户读到与实际行为不符的说法——本卡要订正的「同步服务端不受影响」正是这种漂移的既有先例。改为后端出结构化枚举 + 说明，前端只做投影；代价是多一个只读 IPC 与一层 store 状态。

### Why not 在 IPC 层按当前账号过滤全库统计？

两种做法都能满足「异账号不混入」。放弃 IPC 层过滤：要把全表行读进内存再过滤（`last_error` 还要按 id 取最新），而表会随 local_only 终态累积——读放大没有理由。收窄到数据层是单条 SQL 带谓词，口径只有一份；代价是既有调用方要传 `account_key`（本仓只有测试与新 IPC 两处消费）。

### Why not 未连接时返回 Err？

「未连接」不是读取失败：没有当前账号，账号限定口径下「无待办」为真；返回 Err 会让设置页把本地模式渲染成读取故障，与 X3「无队列不制造噪音」相冲。真正必须 Err 的是**读取失败**（凭据损坏 / 表级故障）——那会把「未知」伪装成「无待办」，B3 明确测试了这条界线。

### Why not 能力矩阵走 Backend 实例方法（构造客户端后查询）？

`Backend` 在 `build_session` 里构造，依赖凭据解密与端点/网络路径；能力声明是纯事实，不应因离线、认证失败或坏密文而不可读（那会让 UI 把「读不到」误呈为「没有能力」）。矩阵用协议串直接映射（`Some("fever")` / `Some(_)` / `None`），并以反向注释与 `Backend::supports_subscription_write` 互指；两侧同源的纪律由单测的逐动作断言兜住（Fever 全 `LocalOnly` / GReader 全 `Supported`）。

### Why not 把空分类远端表达标成 LocalOnly？

`LocalOnly` 的语义是「动作本地生效、远端不写回」；空分类的**远端表达**本身不存在（无成员、无分类级端点）——把它压进 LocalOnly 会让「远端表达不存在」与「动作仅本地生效」变成同一种说法。改用 `Unsupported`（逐动作行）+ detail 说明「本地改名/删除照常、墓碑防复活」，语义分层更准。

## Consequences

- 能力边界第一次有了机器可读的单一事实源：确认弹窗、摘要卡、能力卡与未来的设置入口都从同一份数据取字，Rust 单测锁文案关键语义（持久退订 / 离线重试 / 成员逐源 / 空分类边界），组件回归锁接线——「文案与行为矛盾」这类缺陷在两层都过不去。
- 回执按当前账号限定且 `local_only` 可见：Fever 连接下用户能看出「编辑/新增/退订为仅本地」，而不是把本地成功误读成远端已同步；换号暂停的队项不再污染当前账号展示。
- 事件链独立成线：入队（含分类命令与 OPML 这类不立即推送的路径）也会即时刷新 UI；`try_push_subscription_outbox` 结束的无条件广播会与执行器内的通知产生重复载荷——同一快照的无害重复，换取「入队后会话构建失败（离线/认证失败）也可见」。
- 已知上限：矩阵判据与执行器能力门仍是两处代码（注释互指 + 单测锁定，非机械同源）；「未连接 = LocalOnly」导致删除在连接后**不**自动补推（detail 已如实说明，这是 B2 的既有语义）；`local_only` 终态行随 Fever 使用累积并持续计入展示（B1 的保留展示语义，B3 不做清理）；caps 未加载时删除弹窗省略远端语义句（挂载即拉取让窗口很小，且省略优于编造）。
