# Agent Note: 同步运行生命周期与诊断

Status: implemented

## Problem

PULL_LOCK/PUSH_LOCK 只保护各自阶段。auto、focus 与前端分次调用 feeds/states 会交错，旧轮的无 ID `sync-idle` 能提前熄灭仍运行的同步灯。ClientBuildFailure::Failed 又被改写为 notConnected；当队列为空时，没有 last_error 承接真实认证或网络错误。后台 report.errors 只进调试日志，发布构建没有可持续诊断记录，退出也只有封面补全消费停止信号。

## Decision

2026-11-05最初用每数据库整轮闸门解决交错活动、游标和代际归属。这保住了生命周期，却让慢full正文阻塞新read的HTTP/ACK，也让已读/收藏权威集合等正文才落地。2026-11-10受控HTTP反例证明了这个代价；当前由同一个`sync/runtime.rs`协调固定的Content、State、Push三条通道，每类最多一个运行操作，内容游标与历史仍由Content串行拥有，原PUSH_LOCK仍串行保护真实写请求及精确ACK。

同runtime且同lane才可task-local重入；Content进入State/Push仍须取得目标许可，且只允许按Content→State→Push方向嵌套，反向调用产生可见错误，避免交叉等待。嵌套阶段共用活动ID/source及Arc持有的账号generation，不能因换通道重新捕获账户。`sync_run`仍以一次IPC拥有feeds→完整states生命周期，各阶段报告和错误保留；前端抓取/reload保持在前端活动内。

已绑定条目的远端flags只有State通道写入。GR仍使用完整unread/starred集合，unread缺席候选保留存在性HTTP验证；Fever仍要求完整unread/saved对成功，失败不视为空集合。State不等待未知身份/正文回补。Content只更新身份和正文；新行初始化和真正首次绑定仍逐字段保留pending/版本守卫，首次绑定判定读提交时的实际DB，不能只信HTTP前maps。完整手动/内容轮先读取状态、处理正文及新绑定补推，再以新请求收敛新身份；前后权威HTTP都承接本轮起点的本机字段版本/source生命周期基线，轮中新见行按已有helper以(0,0)保守补记，不能因后一次请求重采本机版本而洗掉本轮用户操作。独立State轮每轮重新取HTTP前基线。旧正文flags不能覆盖已绑定行，远端合并不借本机版本充当远端事件时钟。

内容时间游标只在完整内容窗口完成后记为候选，最后一次状态读取完成且前后都无状态错误时才提交；Fever页数据/since/history checkpoint保持原有页事务提交。这样后半状态DB失败也不提前确认完整窗口。状态报告保留已提交变化和真实失败，认证重试沿既有preserve_changes_from保留非认证故障事实。

2026-11-10精确CI暴露出三通道拆分后不能把裸`remote_id`当作跨源信任依据。当前用可空的`articles.remote_origin_feed_id`记录真实Content响应的origin；正文存在、feed当前绑定、字段版本或本地source字符串都不能产生凭据。精确entry ID且本机feed远端ID未知的原兼容路径保留，双方已知却冲突则拒绝。article的remote ID/feed变化，以及source的remote ID、稳定ID、生命周期或active变化都会清证；账号purge清remote ID从而清证，单纯换密码不清数据，但旧HTTP仍被账号generation拒绝。当前独立新格式直接包含该列，旧格式在任何写入前只读拒绝，不新增历史迁移。

source的remote ID/稳定ID真实变化还须推进既有`lifecycle_version`，使Some→None→Some的同值回归仍拒绝旧HTTP；只比较最终字段值或只清证明列，旧Content都可能重新补回过期证明。触发器不推进同值UPDATE，若同语句已推进生命周期不再重复加，最大值拒绝并回滚身份变更。初次remote绑定也推进生命周期，因此first-creation回执以事务内插入前确实无行作为依据，回传绑定提交后的版本，不再要求版本为0；复活旧来源仍无回执。文章remote ID的生产写入限定首次Content绑定和账号purge，后者同步推进账号generation；未添加第二套文章版本，不声称防御任意直接SQL伪造article ID的ABA。

GR/Fever的未知源预检共用精确身份的feed兼容谓词：已有精确eid且捕获行feed未知/相容时已经有合法落点，不因`feed_mf_to_id`缺origin就误报为新源。否则会先接受Content证明，再多余发现并把同一本机源None→Some、推进生命周期清证，后置State被旧token拒绝。此修正只避免无用发现，不刷新source/字段基线；提交仍核对实际当前source与feed，冲突旧行拒绝，未知新eid仍发现，已退订源不重新绑定。

State只合并有当前来源凭据的绑定；冷绑定保留本机flags，由Content对确有状态差异或待发意图的冷ID做每轮最多2000条的轮转补证。本轮已经请求过的正文不再换成origin名义重复请求；已证明绑定的后续读藏变化不新增origin补证。GR原有“unread集合消失→contents确认目标仍存在”的探测仍保留，它在State许可内，慢探测仍会排队阻挡同类State操作；零新增origin补证不代表所有状态读取都零正文HTTP。未完成feed绑定或墓碑判断未知时，Content与State共用同一准入检查，不请求条目或状态集合，状态提交边界再次核对。

完整轮只在同一账号、source/字段起点内共享一次权威集合结果。Content借用ID用于发现，不重放旧flags；已失败字段在同轮后置State中不再请求，已成功字段重新取当前远端集合，独立State轮也始终重新请求。GR读/藏成功侧仍独立，Fever仍要求完整对；失败与错误不会被后置空操作改写成成功。这避免同一异常continuation被前置State、Content、后置State重复请求三遍。

Push计划捕获同一来源凭据和source token，每次发送前及ACK落库同一DB临界区复核；失效后队列保留等待重新补证，旧成功或失败都不得回写新来源。Fever底层原本就是逐ID HTTP，调用层显式逐ID复核不增加mark请求数；toggle兼容探测后再次复核再发mark。HTTP期间不持DB锁：合法请求发送后再发生来源变化，远端可能已经执行，能保证的是后续请求停止和本机不误确认，不能撤回已经发送的动作。

Fever读状态复核只拆发送循环，ACK仍维持每50ID一块；51条保持51次mark与2次读回。将整条处理链拆成单ID会额外产生51次读回，静态自核发现该成本后收回该候选。读回域只含实际发出的ID，发送前因proof失效跳过的项不能仅因远端已是目标态而被本次确认；失败保持既有保守队列语义。

独立审计进一步证实GR惰性action token等待也是发送边界：等待期间source或账号失效，旧实现仍会在token返回后新发edit-tag。当前GR采用与Fever相同的会话级逐HTTP账号generation守卫，token/GET/POST都复核，POST在token返回后再查；同一客户的OnceCell缓存保持。文章写另外带本次计划的短生命周期检查闭包，在真实edit-tag发送前复核账号及所有目标来源凭据，不把article条件缓存到长期session，也不跨HTTP持DB锁。订阅edit/quickadd/tag等共享POST因此也获得账号复核，未扩展订阅来源业务。已发认证或写请求无法撤回；登录自动发现的候选流程仍沿原完成后generation拒绝，不能据此宣称取消了此前已经发出的认证。

完整轮遇到新远端源而发现重试时，原source基线只允许按本轮订阅创建回执扩充：创建事务先确认URL此前没有行，再插入、绑定并读出稳定source ID/lifecycle；commit成功且确为首次创建才把回执交给编排层。仅补原基线没有的来源，绝不覆盖已捕获来源的token或本机字段版本；复活旧来源不会产生首次创建回执。条目提交时仍核对token，失配标记绑定不完整，GR不提交时间游标，Fever不提交含失配条目的页/游标；下一轮用新的合法基线补回。这样修复同轮新源被旧基线漏掉却消费窗口的问题，而不放开旧来源退订再订期间的回包。

Fever每个读/藏字段成功写入后立即累计真实变化和计数，再尝试下个字段。后续SQL失败可以保留已提交read的刷新信号与partial错误；不会因star失败把已提交变化误报为零。原先等待读藏都成功再记账的顺序是既有缺陷，在新的独立State事件通道中直接影响刷新。

生产快速入口`sync_states_now`由独立30秒定时轮和聚焦路径调用；失败按30至300秒退避，网络恢复后的下一次请求仍走快通道。内容/订阅outbox有独立单循环，保原游标与发现节流。本机意图沿原mailbox防抖/失败退避；启动时只唤醒一次持久待办，不用周期提醒反复打断退避。旧内部`sync_light`在拆分后无产品消费者，移除；其历史内容测试改调用已有`states_phase(false)`，保全部场景断言。状态真实落库立即发既有数据变化事件，不等手动正文完成，前端仍按ReadingSession属性投影。

整轮第一次读取的账号 generation 固定于 task-local；进入后续阶段和重新认证前检查这一值，账号变更立即结束旧轮。客户端仍经既有会话缓存取得，不把一份客户端引用强行贯穿所有阶段；整轮固定的是身份代际和活动所有权。

活动事件携带唯一 id、单调 sequence、来源、stage 和明确结果。ID分配与started投递、后续sequence分配与同步sink调用使用同一个短事件锁，防止并发通道先发新finish再发旧start；锁不持异步网络等待。前端用活动表收敛，不让一个结束事件清除其他活动；已结束轮次的迟到开始/阶段事件被拒绝。手动链关联前端 owner，后端结束不能提前结束后续抓取/reload。后台 partial/error 即使没有队项也会进入错误中心并提供重试；只有明确 NotConfigured 可静默。

运行协调器使用受管理后台任务：调用方取消等待不丢弃已经开始的轮次，panic 由 Drop 发布失败并释放闸门。退出先关闭准入和取消在途异步链，等待最多三秒；SQLite 同步短事务不会被协程取消切断，已发出的远端请求无法撤回，未确认意图仍留待重试。调度循环在启动等待和 tick 等待期间也消费停止信号；不增加电源事件或改变 v34 抓取 CAS/footprint。

RSS 批次 worker 在等待并发许可和执行抓取两处消费同一停止信号，停止后的批次返回 `syncCancelled`。这是退出准入接线：仍由原 single-flight 任务收集 worker 结果并释放批次，不改变普通调用方取消时继续完成抓取的语义。

发布诊断采用独立的结构化写入器：只记录时间、活动 ID、枚举来源、结果、错误分类，不接受原始错误、URL、用户名、凭据、请求头或正文。每文件最多 256 KiB，最多三份轮转。与完整日志加正则脱敏相比，受控字段无法保留详细远端错误正文，但提供可关联的失败/恢复/取消记录，避免未知格式绕过脱敏。普通详细错误仍在本机界面按现有错误中心处理。

报告内 partial 与单次手动 IPC 内的阶段失败同样产生受控错误分类；队列/订阅通知读取失败进入现有可重试错误事件，事件发射失败记录 `event_failed`。订阅通知的同值缓存仅在发射成功后推进，失败载荷仍可在下一次通知重发。

GReader 的真实 401 为兼容既有 IPC 保持 `code=network`，认证原因来自 `AppError` 内部结构化标记。阶段错误汇入 `SyncRunError` 时一并保留该标记，使用 `serde(skip)` 隔离于 IPC 三字段之外；发布诊断据此写 `auth`，不从 code 或错误正文猜测认证失败。

## Alternatives considered

- 只让push绕过整轮闸门：能缓解发送，却丢生命周期且远端接收仍等正文。采用同runtime固定通道。
- 只拆锁、保留正文对既有flags的写入：两方向白盒HTTP反例均把新远端状态改回旧值，本机版本始终未变，不能用本机版本解决。采用已有绑定状态唯一写入责任，不添加远端事件时钟；后继origin列只证明身份归属，不承担事件排序。
- 每次状态变化都重新拉contents证明来源：会把快状态路径重新绑定到正文延迟及带宽。改为真实Content首次记证、身份变化清证；匹配版本的Miniflux/FreshRSS itemRefs实现未提供可依赖的directStreamIds，不能臆造轻量来源字段。

- 跨 feeds/states IPC 保存锁租约：能保留旧前端调用形态，但页面消失、IPC 失败与超时会制造悬挂租约或提前释放，无法说明整轮终态。采用单次 sync_run，保留旧入口兼容。
- 只把 bool 改计数：可以改善灯色，却仍无法拒绝旧事件或关联失败和具体轮次，后端阶段依然交错。使用活动 ID 和 sequence。
- 发布启用全部 log 再正则脱敏：诊断更详细，但 reqwest/插件错误可包含任意正文和含凭据 URL，正则无法给出稳定边界。仅写受控字段。
- 把真实 401 的 IPC code 改成 auth：会改变既有错误契约，也无法解决以后再次包装时丢元数据的问题。保留现有 code，阶段结果内部传递结构化认证标记。
- 退出硬停所有任务：实现简单，但无法明确活动结束或限制收尾等待。关闭准入、取消异步链与有限 drain 使恢复边界可测试。

## Consequences

同类操作仍排队，内容与状态/推送可重叠。GR缺席存在性证明仍可能访问items/contents且受该请求自身延迟影响；分离不等于服务端响应无时限。订阅outbox与状态真实写共用PUSH_LOCK，保既有写入串行边界；它不阻挡State权威读取。调用方取消不等于停止服务端已发请求；退出取消也不能撤销远端已接受的操作，后续 ACK 验证和持久意图负责恢复。诊断目录不可写时无法落盘，应用不为日志失败中止启动。真实 Tauri 退出窗口效果、真实部署认证响应与跨机器日志权限仍须单独验收，loopback/协调器测试不能替代。

## Verification

2026-11-10在`87119b2`加复制时后端候选的隔离Windows库上，两个生产入口慢pull反例准确失败，释放屏障后正常收敛；两个仅模拟未来并发的白盒HTTP反例确认旧内容覆盖新远端flags。原失败保存在本地忽略目录`tmp/refactor-2026-11-09/state-lane-work/baseline-run/`；白盒不代表旧公共入口可达并发。当前改法的自测、独审与组合验收状态集中在该目录REPORT，不由本篇implemented状态宣称通过。

2026-11-05 在隔离 Windows Rust/MSVC 环境使用临时库和 loopback，验证整轮串行/重入、取消等待、panic、停止与有限 drain、空队列失败、手动阶段报告及跨阶段换代。真实 ClientLogin 401 经手动整轮曾丢认证标记，独立反例和正式红/绿回归推动保留内部 auth 元数据，同时 IPC 仍为 stage/code/message 三字段；原始证据在 tmp/runtime-closeout/ 与 tmp/runtime-closeout-audit/。

诊断器只能记录上游交付的事实。2026-11-06 `91ece562` 仍确认认证重试丢已提交变化、outbox SQL 确认失败和完成时间 SQL 失败未充分进入报告，见[同步正确性](../../../../docs/roadmap.md#sync-correctness)。因此活动表/日志存在不等于错误覆盖完整。真实 Tauri 退出、真实部署认证、发布目录不可写和事件传输故障仍需各自验证；旧 Note 格式计数和整轮门禁状态不在此重复维护。
