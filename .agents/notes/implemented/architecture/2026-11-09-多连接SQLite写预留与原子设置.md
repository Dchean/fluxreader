# Agent Note: 多连接SQLite写预留与原子设置

Status: implemented

## Problem

前台曾由一个数据库连接及异步mutex串行化操作，多个业务事务可以先读版本/成员/账号再写。WebDAV后台为了不持前台mutex处理正文和检查点，引入独立WAL连接；另一连接提交后，DEFERRED事务已读快照升级为写会失败SQLITE_BUSY_SNAPSHOT（517），等待busy_timeout不能刷新这个快照。五万不同正文的真实磁盘测量在body ACK触发该失败，低峰内存不等于任务完成。

前端设置队列另有同源问题：把缓存base叠单笔patch后仍发送完整JSON，另一设备先提交的别键可能被旧base覆盖。写前回读不能关闭回读与写入之间的窗口，前端屏障也不能控制后台独立连接。

2026-11-11的恢复竞争又暴露不同问题：BEGIN IMMEDIATE避免旧快照升级，并不保证多个连接按等待顺序获得写锁。原SLO-B02前台bulk因database locked失败；后继定位中，前台star的BEGIN等待约5.5秒后失败，同一窗口恢复完成676次BEGIN，绝大多数是约15ms的短写段。这个诊断证明连续短事务仍能饿死等待者，不证明原bulk的确切失败phase。原失败证据不由后继候选覆盖。

本决定已落实在隔离候选。其`implemented`不代表全部旧业务/新规模已复验；当前版本、失败和退出条件由[验收入口](../process/2026-11-03-修复波次的分批、证伪审计与证据门槛.md#2026-11-09-已确认重构路线与退出条件)统一记录。

## Decision

核心`db::write_transaction`只为已经确定会写的业务事务执行BEGIN IMMEDIATE，先预留唯一写者，再读决定本次变更的输入；不把整个运行轮或网络加锁。各域保存原事务原子性与代际条件，采用共同写预留原因，不散布忙重试补丁。2026-11-11后继在该入口之前加入同一数据库的进程内FIFO准入，保留本段关于SQLite事务、业务前提和原子性的全部决定。

`db/writer.rs`单独拥有准入顺序。Windows通过bundled SQLite的`SQLITE_FCNTL_WIN32_GET_HANDLE`取得当前main数据库的原生句柄，再用FileIdInfo取得volume及128位file ID；不重新打开路径，也不靠小写字符串推测路径别名。new DB在SQLite真正创建文件后才登记，恢复在同一连接/文件中沿同一身份排队。私有内存与临时main按活连接身份隔离；生产未使用共享内存URI。VFS或文件系统无法提供可靠身份时显式失败，不用可能把同库拆开的fallback继续写。硬链接的准入身份相同不代表SQLite的不同WAL文件名因此安全，生产不新增别名写库入口。

一个等待者只持一个当前同步调用的ticket，不存闭包/重试任务，不建立调度服务。活动持有者与等待者保持gate强引用，弱引用登记表在下一次登记时清除失活项。后来的恢复片不能越过已等待的前台事务；FIFO只约束本进程纳入此边界的连接，外部进程仍由SQLite原有5秒busy_timeout判断。不同文件不互相阻塞。同线程同connection的内部数据函数可以重入；同线程通过另一connection再次写同库本来会自锁，现显式dbWriterReentry拒绝，合法跨库嵌套不受限。

`WriteTransaction`保存SQLite Transaction及permit，成功COMMIT或错误/提前返回时的ROLLBACK完成后才归还准入；Deref保留已有显式`&Transaction`内核。COMMIT错误仍原样传播，并核SQLite已回到autocommit。如果回滚后事务仍active，记录实际file ID为failed-closed并唤醒等待者返回恢复错误，直到进程重启；弱gate清理不能抹掉此故障状态。此路径不伪称已经关闭仍被借用的连接；罕见file ID复用在同一故障进程内也保守拒绝，代价是需要重启。正常关库和不再活跃的等待者不留下强引用。

原隐式写入在实际mutation入口取得`writer_guard`，不在每条SQL机械包锁；它不改变原SQL事务边界。多步原子业务继续走原完整事务。schema初始化、设置/AI/源字段、队列/outbox、同步下载/根/回执等实际写入均须沿同一准入；纯读、WAL快照与TEMP准备不排队。锁顺序为业务锁/connection mutex → writer，底层不反向获取业务锁。异步宿主把会等待的整个同步DB scope交给`state::database_work`的spawn_blocking，底层不依赖Tokio runtime flavor；HTTP、回执/事件和通知仍在原提交后的锁外阶段。

2026-11-11异步宿主闭合后，`state::database_work`内同时取得完整connection lock、执行同步SQL及可能的writer等待，闭包内不再await；纯读也离开异步poll，但不取writer。`try_database_work`只在worker中尝试一次connection lock，维护路径遇忙不运行闭包，也不推进retention游标。GR/Fever页把本轮maps/report所有权先交worker再回交：worker Join失败、入口代际失配和writer等待后的`staleSession`都终止整轮，临时Default maps不能当作新快照续跑；页事务及GR逐成员、Fever权威/回执粒度保持原样。内层`AppResult`也走同一提升规则：states发现/基线/内容游标、Fever恢复/Pending/Complete/正文覆盖游标及GR失败重建中的`staleSession`终止整轮且不进入report；非stale行级失败才保留既有report/重放语义。

local fast把ACK与receive的查询/落库步骤分别交给阻塞worker；ACK在发送后、回执前各核原session，receive在取批前后、seen判定及每次apply前复核，每次writer permit只覆盖当前步骤。共享pacing只保留一个`Arc<Mutex<FastPacing>>`；完成写按DB → pacing取得两锁后核原session与scope，旧轮不能用迟到结果复位或覆盖新session。HTTP、事件与通知均在这些锁外。

取消只作用于恢复闭包下一次准入。等待者每25ms检查原stop flag并移除自己的ticket，这个时间是等待取消探测，不能当作恢复cadence或公平sleep。已经拥有writer的完整事务及内部重入继续完成；前台spawn_blocking已开始的意图不因调用future丢弃而中途取消。正文维护继续用try准入，存在持有者或较早等待者时即busy/skip，保原busy_timeout=0及恢复timeout的语义。

读藏单条、批量与全部标读先预留，再读取真实成员和字段版本，一起改状态、版本、队列。账号保存/断开、分类/源改动、OPML导入、远端绑定、过期队列恢复、抓取落库与Fever页落库同理。旧标签、分类存在性、远端目标和内容提交token必须在预留内读取或复核，不能只把BEGIN换类型而继续使用前面未保护的快照。

正文内容写入复用可嵌套savepoint：autocommit顶层先开IMMEDIATE，已有事务则沿其写预留；内层失败ROLLBACK TO并RELEASE，不丢外层已完成的其他工作。`ROLLBACK TO`、`RELEASE`或panic unwind中的RAII回滚自身失败时，当前file gate立即failed-closed；已有外层`WriteTransaction::commit`只能回滚并返回`dbWriterRecovery`，不能把恢复失败后的事务提交成成功。显式业务错误保留原code/分类和message，恢复失败追加为证据；panic Drop只记录恢复失败，不二次panic覆盖原payload。独立提取的HTML规范化可以事务外完成，但提交时重新读token；upsert/backfill的匹配与写回受同一边界保护。

纯导出与状态/正文封批准备保持只读快照。正文stream编码、HTTP、文件预览/摘要和与DB可变前提无关的HTML处理不因helper而移进长写事务。body ACK先解析目录、向临时表分批写引用，再短写事务更新own/pending并按集合释放holds；本机root清理提交时继续复核generation，远端物理DELETE暂停，不能把写预留当成远端回收许可。原决定允许先写后读的短事务保留DEFERRED，因为它们没有517窗口；FIFO后继将AI清理及Fever游标恢复也接共同write_transaction，理由是完整写入生命周期参与准入，不改变它们的原子集合。

普通设置核心policy归`db/settings.rs`，一次定义名字、值域及同步/便携/本机范围。`patch_app_settings({patch})`在写预留后读取当前JSON，只合并显式已验证键，返回已提交完整JSON。坏当前包返回invalidSettings，未知/非法键返回validate；任何失败保原。通用set_setting的app_settings整包外部入口返回protectedSetting，内部恢复/同步仍在自身事务里调用db setter。设置UI队列以返回包为确认base，显示投影和前沿机制保留。

`resolve_close`对closeToTray/closePromptShown调用同一patch内核，不吞写失败。syncMode提交后的托盘副作用保留。WebDAV只记录本次实际改变的普通字段，启动/首次关闭提示不上传；syncMode便携但不WebDAV；readBodyRetentionDays是0–3650整数，0默认永久；[本机正文保留](../bug-fix/2026-11-05-缓存清理语义与未读保护.md)已经以同一writer保护接入有界分钟维护和恢复续期，前端控件候选已复用原子patch接入，草稿只在合法Enter/blur提交，不另建持久真值；组合/native仍需验证。字体域沿既有前端非空字符串，撤去草稿中未经确认的256-byte限制。

## Alternatives considered

- 仅加busy_timeout或对“database locked”无限重试：517表示读快照已过期，重试同事务不能改变前提；若重开又必须重新读取并验证业务输入，直接明确事务所有权更可靠。
- 全库机械替换为IMMEDIATE：会把纯导出/正文准备变成写者，扩大交互阻塞；只改已核实的读后写边界。
- 仍只依赖前台mutex：它不覆盖后台独立SQLite连接；跨网络持锁则把阅读绑到网络。
- 前端设置写前回读或串行发送完整包：只能控制同一前端，不能原子保护后台别键；后端单事务字段merge才能消除读后写窗口。
- 仅恢复循环yield_now、固定sleep或增加busy_timeout：实际短事务重复抢锁证明yield不保证等待者机会；固定间隔把公平性变成调度巧合，延长timeout只会延后可见失败。选择按同库实际等待顺序准入。
- 每个connection各有一个队列，或只包恢复循环：前者不协调SQLite的同一个writer锁；后者仍遗漏设置、回执和其他隐式写。选择同库登记、数据写入口共同遵守的单一边界。
- 在同步db helper里按Tokio runtime flavor调用block_in_place或拒绝current-thread：会让数据能力依赖宿主执行模型。选择由异步调用层交阻塞线程，db核心只管理同步准入。
- 把GR/Fever整张maps一直留在异步调用方、或为每次短锁复制完整maps：前者无法在worker内按原页/成员边界提交，后者让内存与所有权成本随页数增长；选择本轮状态唯一所有权先回交worker，并以stale/Join外层终止代替空占位续跑。
- 给fast receive的64次本地应用保留一个大writer permit，或让旧pacing token只比较其中部分字段：前者让前台意图越过不了长恢复段，后者会让旧轮迟到写污染新会话；选择每步重新准入/核session，全部pacing写共用同一原session守卫。

## Consequences

数据库冲突在读取业务输入前等待，阻断旧快照升级与一组TOCTOU错误；FIFO消除本进程后来的写入反复越过已排队者。代价是多个写事务仍串行，前面已有的长事务仍会让前台等待，而且每个真实file身份查询及短guard增加少量系统调用。公平顺序不是250/500ms硬时延证明，也不降低全部标读的原子标准。首轮检查点ACK、full projection、初始化、正文批次需按真实规模分别测量，按单读/单藏/批量/全部标读分组报告，不能混合p95或只报最终完成。

这个变化跨过原B1–B5既有事务假设，原语义测试仍有价值但不自动背书新连接并发。回归需同时覆盖外层/内层失败、代际变化、前台真实命令和后台连接写竞争。新增写者或移动读前提时应重新核此契约。

## Verification

2026-11-09：保留的五万磁盘库证明失败时pending正文发布与五万holds仍在；最小两连接WAL反例稳定命中517。修后ACK与40次真实read/star/bulk/mark-all入口竞争无错误，嵌套内容失败保留外层源标题，原子patch保留未回读的远端别键并拒绝坏包/非法补丁。定向编译与portable回归有对应结果；这不代替全Rust、完整规模前台延迟、真实WebDAV或独立审计。

2026-11-11公平性后继基于480产品路径的retention组合实施。最初482路径静态候选随后在当前隔离Windows/Rust环境完成库编译及真实SQLite回归：两连接FIFO、隐式设置、commit失败/rollback/unwind、嵌套savepoint、取消撤票、try策略、WAL读者、不同库/私有memory及重开后读藏保留。真实Windows句柄FileIdInfo覆盖新文件、重开、大小写/canonical扩展路径、hardlink；symlink权限探针另以ignored精确选择真实执行成功，不把默认ignore计为通过。既有retention busy回归确认立即跳过并还原timeout。

首轮新增读藏夹具误用了不在产品枚举内的`list`布局，在initialize前置被校验拒绝，未进入竞争；改为合法`article`后保原断言定向通过，再运行整组通过。原失败输出保留。这次没有产品算法修补，只有核心格式归一和夹具修正。rollback故障登记寿命测试只模拟内部failed标记，不是实际磁盘I/O故障；真实COMMIT失败用DEFERRABLE外键并观察SQLite回滚。整体fmt仍在已移交异步宿主的两文件存在格式差异，由该owner闭合；核心测试通过不能改写为全库门禁或独审通过。宿主异步适配组合、原SLO-B02时延、50k及全Rust/独立审计仍须分别取得最终版本证据，版本/命令/次数集中在当轮验收入口。

异步宿主组合在2026-11-11先完成过174输入闭合的`cargo check --lib`：首轮因所有权移动返回101，修正后重试返回0，但仍有一个未使用会话方法警告。随后静态闭合又移动了全文提取读前scope、补了writer等待后stale/pacing/fast逐步session反例，并修改Note。第一授权窗口内`cargo fmt --all -- --check`通过；`cargo check --all-targets`首轮因queue scope重复移动及会话借用逃逸返回101，修正前项后第二轮仍因SyncSession未实现Clone返回101，按两轮停报规则未继续clippy或测试。第二窗口改为只把generation传入worker、由`ensure_generation`重读数据库代际并删除无消费者便捷方法；该设计已通过rustfmt，但首次全目标check仍因两个测试代码编译点返回101，按要求停止。新增测试用于让“取消半途中止事务”“等待后stale被软失败吞掉”“旧pacing scope覆盖新session”“fast首步后继续取下一批”等反例可证伪，实际结果只以当轮REPORT和原始日志为准。完整会话不应跨blocking边界复制；后续只修测试路径与类型标注，不改守卫语义。
