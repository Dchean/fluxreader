# Agent Note: 可渲染正文安全边界

Status: implemented

## Problem

远端正文补全路径曾把原始 HTML 直接写入空 `content_html`：首次插入有 sanitizer，但补全写入与存量缓存没有——任意 iframe、事件属性和脚本可以一路抵达前端 `dangerouslySetInnerHTML`。iframe 预过滤的手写扫描又用字节切片读取标签名之后的一个字节（`rest[7..8]`），残缺 `<iframe`（EOF）与后继多字节字符都会让清洗 panic：不可信 feed 内容可以打断清洗任务，且「崩溃」与「静默丢弃正文」之间只剩一步。字节切片修掉后，同一预过滤仍是字符串属性扫描，review R1 给出真实绕过：其他属性引号值里的伪 `src=`（如 `<iframe title="src = https://www.youtube.com/embed/a" src="https://evil.invalid/embed">`）会被当成真实 src，把白名单外的 iframe 原样放行——「误判只往安全侧」的假设不成立。改用解析树后，R2 又暴露组合边界：旧 `promote_lazy_images` 把 `data-src` 解码值裸 format 进 `src="…"` 再 `replacen` 回字符串——`data-src='&quot;&gt;&lt;iframe src="https://evil.invalid/embed"&gt;'` 会在 iframe 策略**之后**重新制造真实 iframe，且对单引号占位等序列化形态本就不生效。

## Decision

**可渲染 HTML 的净化口径只有一个：`sanitize()`（`src-tauri/src/sanitize.rs`），写入口与读边界共用，前端不承担重复的清洗规则。** 边界在三处收口：

1. **补全写入即净化。** `db::backfill_article_content` 自身调用 `sanitize()`，基址取该文章的 `url` 列（与抓取入库的相对链接重写口径一致）；DB 错误经 `AppResult` 正常上抛，同步调用点把失败记入 `SyncReport.errors`（不再 `let _` 吞掉）。
2. **读取边界兜底净化。** `get_article` / `get_articles` / `list_articles(with_content=true)` 返回前对 `content_html` 与 `translated_content` 再过一次同一个 `sanitize()`，基址取该行 `url`——存量被污染的正文/译文与历史回填产物不再依赖「写入时点是否干净」。只元数据的列表（`with_content=false`）正文列为 NULL，不做额外处理。
3. **统一 DOM 预处理，先策略、后只做属性赋值（R1/R2 修订）。** `preprocess_html` 用 `Html::parse_fragment` 做一次解析，在同一棵树上完成两件事：(a) **iframe 域名策略**——读取每个 iframe 的**实际 `src`**（实体解码、引号风格、`=` 两侧空白、ASCII 大小写归一、重复属性「首个胜出」全部按 html5ever 语义），白名单内保留，白名单外降级为 `<p><a>▶ 在浏览器打开嵌入内容</a></p>`（无可用 src 整体移除），降级外链由常量模板解析出 `<p>` 子树克隆后 DOM 赋 `href`、再原地替换；(b) **惰性图片恢复**——`src` 为空/data: 时从 `data-src`/`data-original`/`data-lazy-src`/`srcset` 首项取 URL，**用 DOM 属性赋值写回既有 `src`**。所有变换只做「元素级替换 + 属性赋值」，**绝不把来自属性的字符串 format 成标记**，因此策略之后不存在能制造元素/iframe 的步骤——最终输出严格服从白名单，无需也不允许"先验证再拼接"。只有确实发生替换/提升时才 `doc.html()` 重序列化，否则原样透传。

## Consequences

- 新建、补全、存量详情/携带正文列表的恶意 iframe、事件与脚本不抵达可渲染字段；合法白名单媒体与相对 URL 重写保持。存量行读出即安全，不需要数据库迁移或前端改动。
- 读取路径为每篇携带正文的行多做一次 ammonia 清洗（详情与 `with_content` 列表在既有成本之上）；只元数据列表不受影响。清洗对已安全内容稳定（二次清洗不复制文本、不新造危险节点）。
- `backfill_article_content` 的语义从「原样落库」收紧为「净化后落库」：它不再是裸 SQL 写入器，任何新调用点自动继承安全边界。
- 回填失败的可见性从「无」提升为 `report.errors` + warn；本轮不改变游标推进与重试语义（恢复性处理见 OPT-007）。
- iframe 白名单判定不再有字符串启发式：诱饵属性、实体编码、重复属性、引号/空白变体都由解析器裁决，不存在「诱饵放行真实 src」的方向。惰性图片恢复同为 DOM 属性赋值：恶性 `data-src` 只能成为（经序列化转义的）属性值，不可能变成元素；单引号占位、`data-original`、`srcset` 等形态一并被正确提升（旧字符串替换对这些形态本会静默失败）。代价是内容含 `iframe` 或 `img` 时做一次 fragment 解析（仅在确有改动时重序列化），规模为 feed 正文级。

## Alternatives considered

### Why not 只在当前调用点补 sanitize？

最小改动，但公开 DB 补全函数仍接受原始 HTML，下一条调用链或存量行仍可能绕过。边界负责净化比依赖每个调用者记忆更可靠。

### Why not 放宽 CSP 或让前端自行处理？

CSP 是纵深防御，不保证内容符合富媒体白名单；五布局各自清洗容易分叉并引入额外前端依赖。

### Why not 继续字符级扫描（含“安全字符访问”）？

字符级扫描无法回答「这个 `src=` 是不是真的在当前标签的属性位置」——它不跟踪引号与标签边界，其他属性引号值里的伪 `src=` 会被命中。R1 证明误判方向可以是**放行**而不仅是多降级：`title="src=…白名单…"` + 真实 evil src 原样进入渲染。属性语义（实体、引号、重复属性）只有解析器能一致裁决，因此改用 `scraper`（html5ever）解析树 + `ego-tree` 原地替换——两者都是既有依赖，未新增。

### Why not 把 iframe 白名单完全交给 ammonia 配置？

ammonia 没有元素级过滤钩子：`attribute_filter` 只能增删属性、无法按 src 决定保留/降级整个元素，更无法把被拒 iframe 替换为外链。保持「保留/降级/移除」三态只能在其前做一次带策略的树变换；ammonia 仍作为最终兜底清洗（scheme、属性白名单、文本语义）。

### Why not 保留「先 iframe 过滤、再字符串替换提升图片」的两段式？

R2 给出组合反例：字符串替换在 iframe 策略**之后**运行，把 `data-src` 的解码值裸插进标记——策略覆盖不了之后发生的标记注入（`data-src` 可携带 `"><iframe …>` 制造真实 iframe，ammonia 只查 scheme 不查域名，因此防线直接失守）。只要还有任何一步「属性值 → 字符串 → 再被解析成标记」，就必须在每次变换后重跑全部策略，组合边界会持续扩散。统一成一次解析内的元素级替换 + 属性赋值后，策略与被变换对象同源（同一棵树）且赋值不产生元素，不存在「后注入」窗口。
