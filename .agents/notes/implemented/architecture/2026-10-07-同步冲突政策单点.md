# Agent Note: 同步冲突政策单点

Status: implemented

## Problem

Google Reader 与 Fever 两套协议在与服务端对账时，方向并不相同：GR 侧对已读状态只接受远端为真（单向），Fever 侧需要一个双向权威的 unread 集合。这些差异原本散在实现分支里——`if 协议 == GReader { ... } else { ... }` 出现在多个对账阶段，没有一处能回答「这个协议这个字段的权威方向到底是什么」。

后果有三：

1. **政策不可审**。想确认「GR 的对账会不会把本地已读翻回未读」，必须读完整个对账路径并跟踪分支。
2. **用户可见文档与实现脱节**。有人问「Fever 为什么和 FreshRSS 表现不同」，答案只存在于代码分支里。
3. **写失败被吞成「无变化」**。冲突应用函数返回 `usize`（影响条数），内部用 `unwrap_or(0)` 处理数据库写入错误——DB 写失败与「这次没有需要改的行」在返回值上完全一样，上报给用户的同步报告因此显示一切正常。

## Decision

**把冲突政策从实现分支提升为常量单点**（`src-tauri/src/sync/conflict_policy.rs`）：

| 协议 × 字段 | 常量 | 政策 |
| --- | --- | --- |
| GR × 读状态 | `GR_READ_DIRECTION` | 单向 read-wins |
| GR × 星标 | `GR_STAR_DIRECTION` | 双向权威 |
| Fever × 读状态 | `FEVER_READ_DIRECTION` | 双向权威（unread 集合） |
| Fever × 星标 | `FEVER_STAR_DIRECTION` | 双向权威 |

行级落地由 `apply_read_by_policy` / `apply_star_by_policy` 承担，两者返回 `AppResult<usize>`——**数据库写入失败必须 `?` 传播并记入 `report.errors`，不得吞成 0**。为此加了两条反向测试（DB 写失败传播、成功写入行数口径），判别力声明写在注释里。

**三类事实必须分层记录，不得混写**：协议/服务端事实、本客户端实现现状、实际验收过的服务端版本。把「本客户端未实现」写成「协议做不到」会掩盖可补齐的能力——这正是 Fever `max_id` 历史回溯那一格的订正依据（Miniflux 的 `handler.go` 确实支持向更旧翻页，是本客户端未实现）。

**用户可见对照表在 [docs/sync-compat-matrix.md](../../../../docs/sync-compat-matrix.md)**，与政策点同步维护：改政策 = 改政策点 + 改矩阵 + 改对应锁定测试。矩阵的「指定服务端版本已验证」列目前只覆盖测试替身 `src-tauri/tests/mock_greader.rs`——它是唯一被自动化测试锁定的服务端形态；Miniflux / FreshRSS 的具体部署版本未逐一实机验收，这一点在矩阵文首显式声明。

**共享守卫也是政策的一部分**（两个协议都适用，不是某个协议的实现细节）：

- **字段版本守卫 + 字段 pending（OPT-007 原位升级）**：接受远端某个字段前要求「pull 起点版本快照 == 当前 DB 版本 且 该字段无未推送 pending」。本地读/藏写入在同一 SQL 事务里把对应版本 +1（`articles.read_version` / `star_version`），即使随后推送成功、队列已清，版本仍保留——只看当前 pending 的实现挡不住「旧网络快照晚到」。两列独立：本地只改读时收藏照常收敛。快照在任何 HTTP 之前抓取，失败后重建映射不回刷快照；消费点是逐字段判定的 `field_accepts_remote`，不再是 aid 级整行跳过。**快照语义对「合并命中既有行」同样成立（R2，主控 2026-10-10 反例）**：正文合并的 upsert 若命中快照之后直连入库的既有行（inserted=false），状态必须逐字段过守卫、不得整值覆写；唯一不经守卫的整值写是同一 DB 临界区内刚插入的新行（快照 (0,0) 与行初值恒等，其间不可能有本地写入）。**守卫通过 ≠ 数据变化（R3，F11）**：事件判定只认实际变化证据（新插入 / 前后值比对 / 值条件写命中行数 / 绑定变化），经 `SyncReport.entries_data_changed`（serde skip）单点汇聚；`has_data_change()` = 该标记 ∨ `merged_states`（**states 阶段**为对账值条件写命中行数；订阅阶段 subscriptions.rs 为无条件绑定计数且前置写吞错——该判定唯一生产消费者 scheduler 的 `sync_light` 不跑 feeds 阶段，订阅计数不在消费路径上，R5 口径限定）∨ 订阅层增删。**R4（GR 逐语句提交）**：标记在每个成功实际变更点**立即**合并——GR 无页事务，绑定/read 提交后 star 写失败不得让已提交变化失去信号（Fever 仍由外层页事务快照/回滚）。**R5**：binding 置位紧随 `set_article_remote_id` 成功、先于任何后续可失败读取。详见 [状态写入事务化与对账守卫](../bug-fix/2026-09-18-状态写入事务化与对账守卫.md)；
- **失败 ≠ 空集合**：任一集合拉取失败即整轮跳过该对账段，绝不把错误当作空集合——否则一次网络抖动会清空用户的收藏与已读状态。

## Consequences

**收益**：政策可审（四个常量就是全部答案）；行为零变化可证（修前逐列语句对照）；用户能读到协议差异的说明而不是遇到行为不一致；DB 写失败不再被静默吞掉，同步报告如实反映。

**代价**：

- 政策以常量形式存在，**没有测试读取矩阵文档**——同步靠纪律，改了一处忘另一处不会被门禁拦住。
- 矩阵里的外部事实（Fever 的 `max_id`、Miniflux 的时间过滤列）来自一次源码查阅，**没有版本锁定**，服务端升级后必须复核。
- pending/字段版本守卫会让「远端已改、本地待推」的字段在对账轮次里被跳过，因此对账收敛需要等推送成功；如果推送长期失败，这些字段会一直不受远端影响。这是有意的选择（本地意图优先），但意味着同步状态可能长期处于「分歧」而不自知。推送成功后的下一轮 pull 起点快照已推进到新版本，对应字段恢复正常收敛——版本只保护「快照之后、确认之前」的窗口，不是永久屏蔽。

## Alternatives considered

### Why not 让 GR 也做双向权威？

GR 侧的轻量对账只接受远端「已读」，不把远端「未读」传回本地。若改成双向，一个常见场景会立刻出问题：用户换客户端或重装后，服务端上积累的历史条目会成批翻回未读。read-wins 单向是刻意的取舍，代价是「远端显式标未读」这个操作不经轻量对账回流到本地。

### Why not 用 trait 或枚举分派代替常量？

用 trait 为每个协议实现 `apply()`，政策自然就分派到实现里。但那样政策又回到了代码路径中——审查者仍要读实现才知道方向。常量的好处是四个取值一眼可见，且可以被文档逐格对照。分派留在 `apply_*_by_policy` 内部，政策与落地分开。

### Why not 让 `apply_*` 继续返回 `usize` 并用 `-1` 之类表示失败？

用负数表达错误会让调用方必须记得处理这个特殊值，而 Rust 的类型系统本可以强制处理。返回 `AppResult<usize>` 让「忽略失败」在编译期不可能——这是审计点名要修的那条（`unwrap_or(0)` 把 DB 写失败吞成无变化）。

### Why not 把矩阵写进代码注释？

政策点适合代码注释，矩阵不适合：它是给用户和外部读者看的对照表，且含服务端行为这类代码里没有的事实。两边用相对链接互指，各自的读者入口保持清楚。

## 落地事实更新（OPT-008B 第一阶段含 R1，2026-10-12）

政策内容不变（read 广播、unread/star 只当前条目、四格方向常量、字段版本/pending 守卫）。变化的是**广播目标的选择规则**（原由 `remote_dup_ids` CSV 单一承担）：现为 `db::read_broadcast_targets` 单点——同 `url_norm` 兄弟条目的 remote_id（跨源同 URL 现在是各自独立的持久条目，由身份层保证各自绑定；不区分布局）+ 旧 CSV 记账（远端 feed 未绑定、无法成行的历史副本，有限兼容）；该查询失败**透传错误并保留队列意图**（不得失败当空后照推 prune）。

R1 修正（主控反例）：

- **本地半边**：用户读入口（单条/批量/「全部已读」）在本地同样落实读广播——当前行 ∪ 同 `url_norm` 未读副本，读值/字段版本/队列同事务原子更新；unread/star 只当前条目（unread 永不广播）；前端经**读写入回执行**（命令返回真实翻转行，前端让受影响条目/缓存/源计数本地收敛）消费这半边，默认去重关闭时同样成立（见[查询与分页契约](2026-10-05-查询与分页契约.md)）。
- **同轮顺序确定性（读优先）**：拉取侧同轮内任何已读信号（own 或兄弟广播）落定后，own 的远端 unread 不再翻转该行（`SyncMatchMaps.explicit_read_ids` 记录 + 新行落定前查同组已读）；两种处理顺序（A 读→B 未读 / B 未读→A 读）收敛同一结果，字段版本/pending 守卫优先于两者。无任何已读信号的组内条目，own unread 照常生效（unread 只认绑定同源 entry 的边界仍立）。

R2 修正（N4 裁定闭环）：

- **同组读信号的来源校准**：新行落定前的「同组已读」查询只认**本轮** `explicit_read_ids`（own 已读或广播落定），不看历史本地读态——历史已读不得永久阻止之后远端显式 unread 的新副本（无本轮读信号时 unread 权威照旧）。实现名 `group_has_read_this_round`。
- **Fever 轮终对账与同轮广播**：`reconcile_fever_state` 在「把本地已读翻回未读」方向对**本轮已有读信号**让位——同一轮已被字段守卫接受的远端 read/兄弟广播不得被轮终权威集合立刻撤销；无本轮读信号时 Fever 双向 unread 权威照常（本地历史已读不构成阻挡）。下一轮读信号清空后，远端显式 unread 正常复活：真实网络 push（`mark=item`）确认清队后，版本守卫按「快照=当前版本、无 pending」放行远端合并（`read_version` 只记录本地意图、远端合并不递增）。回归：`fever_push_confirmed_read_then_next_round_explicit_unread_revives`（真实 HTTP 推送与清队，非直接 prune 模拟）。
- **集合失败不伪空成功**：unread/saved 拉取失败整轮跳过对账并在 report 显式报「状态对账跳过」、完成时间不推进；失败轮里 items 合并产生的已读广播不回滚，恢复轮读信号仍在 → 不撤销；双方显式 unread（无读信号）轮 → 双向权威恢复。两排列（大 id 读/小 id 未读）顺序无关收敛同一结果。回归：`fever_collection_failure_round_and_next_round_recovery_are_explainable`、`fever_same_round_large_id_read_small_id_unread_stays_read`。
