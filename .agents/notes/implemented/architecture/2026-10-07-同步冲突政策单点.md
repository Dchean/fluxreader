# Agent Note: 同步冲突政策单点

Status: implemented

## Problem

Google Reader 与 Fever 两套协议在与服务端对账时，方向并不相同：GR 侧对已读状态只接受远端为真（单向），Fever 侧需要一个双向权威的 unread 集合。这些差异原本散在实现分支里——`if 协议 == GReader { ... } else { ... }` 出现在多个对账阶段，没有一处能回答「这个协议这个字段的权威方向到底是什么」。

后果有三：

1. **政策不可审**。想确认「GR 的对账会不会把本地已读翻回未读」，必须读完整个对账路径并跟踪分支。
2. **用户可见文档与实现脱节**。有人问「Fever 为什么和 FreshRSS 表现不同」，答案只存在于代码分支里。
3. **写失败被吞成「无变化」**。冲突应用函数返回 `usize`（影响条数），内部用 `unwrap_or(0)` 处理数据库写入错误——DB 写失败与「这次没有需要改的行」在返回值上完全一样，上报给用户的同步报告因此显示一切正常。

## Decision

**把冲突政策从实现分支提升为常量单点**（`src-tauri/src/sync/conflict_policy.rs`）：

| 协议 × 字段 | 常量 | 政策 |
| --- | --- | --- |
| GR × 读状态 | `GR_READ_DIRECTION` | 单向 read-wins |
| GR × 星标 | `GR_STAR_DIRECTION` | 双向权威 |
| Fever × 读状态 | `FEVER_READ_DIRECTION` | 双向权威（unread 集合） |
| Fever × 星标 | `FEVER_STAR_DIRECTION` | 双向权威 |

行级落地由 `apply_read_by_policy` / `apply_star_by_policy` 承担，两者返回 `AppResult<usize>`——**数据库写入失败必须 `?` 传播并记入 `report.errors`，不得吞成 0**。为此加了两条反向测试（DB 写失败传播、成功写入行数口径），判别力声明写在注释里。

**三类事实必须分层记录，不得混写**：协议/服务端事实、本客户端实现现状、实际验收过的服务端版本。把「本客户端未实现」写成「协议做不到」会掩盖可补齐的能力——这正是 Fever `max_id` 历史回溯那一格的订正依据（Miniflux 的 `handler.go` 确实支持向更旧翻页，是本客户端未实现）。

**用户可见对照表在 [docs/sync-compat-matrix.md](../../../../docs/sync-compat-matrix.md)**，与政策点同步维护：改政策 = 改政策点 + 改矩阵 + 改对应锁定测试。矩阵的「指定服务端版本已验证」列目前只覆盖测试替身 `src-tauri/tests/mock_greader.rs`——它是唯一被自动化测试锁定的服务端形态；Miniflux / FreshRSS 的具体部署版本未逐一实机验收，这一点在矩阵文首显式声明。

**共享守卫也是政策的一部分**（两个协议都适用，不是某个协议的实现细节）：

- **pending 保护**：本地有未推送变更的条目跳过对账，防止把「刚标读/刚收藏」的瞬间回滚，也防止两端乒乓；
- **失败 ≠ 空集合**：任一集合拉取失败即整轮跳过该对账段，绝不把错误当作空集合——否则一次网络抖动会清空用户的收藏与已读状态。

## Consequences

**收益**：政策可审（四个常量就是全部答案）；行为零变化可证（修前逐列语句对照）；用户能读到协议差异的说明而不是遇到行为不一致；DB 写失败不再被静默吞掉，同步报告如实反映。

**代价**：

- 政策以常量形式存在，**没有测试读取矩阵文档**——同步靠纪律，改了一处忘另一处不会被门禁拦住。
- 矩阵里的外部事实（Fever 的 `max_id`、Miniflux 的时间过滤列）来自一次源码查阅，**没有版本锁定**，服务端升级后必须复核。
- pending 保护会让「远端已改、本地待推」的条目在对账轮次里被跳过，因此对账收敛需要等推送成功；如果推送长期失败，这些条目会一直不受远端影响。这是有意的选择（本地意图优先），但意味着同步状态可能长期处于「分歧」而不自知。

## Alternatives considered

### Why not 让 GR 也做双向权威？

GR 侧的轻量对账只接受远端「已读」，不把远端「未读」传回本地。若改成双向，一个常见场景会立刻出问题：用户换客户端或重装后，服务端上积累的历史条目会成批翻回未读。read-wins 单向是刻意的取舍，代价是「远端显式标未读」这个操作不经轻量对账回流到本地。

### Why not 用 trait 或枚举分派代替常量？

用 trait 为每个协议实现 `apply()`，政策自然就分派到实现里。但那样政策又回到了代码路径中——审查者仍要读实现才知道方向。常量的好处是四个取值一眼可见，且可以被文档逐格对照。分派留在 `apply_*_by_policy` 内部，政策与落地分开。

### Why not 让 `apply_*` 继续返回 `usize` 并用 `-1` 之类表示失败？

用负数表达错误会让调用方必须记得处理这个特殊值，而 Rust 的类型系统本可以强制处理。返回 `AppResult<usize>` 让「忽略失败」在编译期不可能——这是审计点名要修的那条（`unwrap_or(0)` 把 DB 写失败吞成无变化）。

### Why not 把矩阵写进代码注释？

政策点适合代码注释，矩阵不适合：它是给用户和外部读者看的对照表，且含服务端行为这类代码里没有的事实。两边用相对链接互指，各自的读者入口保持清楚。
