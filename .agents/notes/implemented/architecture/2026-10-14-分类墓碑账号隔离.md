# Agent Note: 分类墓碑的账号隔离与失败关闭

Status: implemented

## Problem

A-4 的分类墓碑（改名/删除分类后阻止 pull 按远端旧 label 复活目录）以「裸 label
数组」存在 `settings['folder_tombstones']`，**没有账号归属**。OPT-009 阶段 B2-4
复审确认三个后果：

1. **跨账号误抑制**：账号 A 删除分类「Tech」→ 切到账号 B（身份变化只清 feed
   墓碑，分类墓碑原样保留）→ B 的远端「Tech」被 A 的墓碑压制，永远导不进来。
2. **静默丢失**：B 的 pull 在远端 tag/list 不含「Tech」时把墓碑按 stale 回收
   ——别的账号把 A 的删除意图删掉了；回 A 后已删分类可能复活。
3. **失败开放**：读取路径是 `folder_tombstones(&conn).unwrap_or_default()`，
   损坏或读失败被当成空表 → 本次 pull 会把已改名/删除的分类按远端旧 label 全部
   复活，而且 `report.errors` 看不到任何线索。

## Decision

**分类墓碑按账号 key 持久化，读取与回收都限定当前账号；读取失败一律失败关闭。**

- **持久形状（v24）**：`settings['folder_tombstones_v2'] =
  [{"account_key": "<协议|规范化服务器根|用户名>", "label": "..."}]`。
  `account_key` 非空 = 只在该账号的 pull 里生效与回收；空串 = **无账号归属**
  （纯本地用户写的墓碑，或 v24 迁移时库内无配置账号），对任何账号生效——本地
  删除意图不得因之后连接账号而失效。
- **写入归属**：命令路径（`record_folder_rename` / `record_folder_delete`）用
  `sync::current_account` 的 key；未配置同步 → 空 key 哨兵。
- **回收判据不变，范围进一步收窄（B2-R2 复审 R2-1）**：仍是「远端 tag/list 已不含
  该 label」，但 `prune_folder_tombstones` 只回收**归属当前账号**的条目（`account_key`
  非空且逐字等于当前账号）；**空 key 的全局墓碑不再被单账号 pull 回收**（B2 初版把
  空 key 视同当前账号的活动墓碑——A 的一次 pull 让全局墓碑消失，之后 B 的 pull 就把
  同名分类按远端 label 导入复活）；异账号条目一个字节都不动。全局墓碑对任何账号
  生效这一读取语义不变。
- **v24 迁移（`M::up_with_hook`，纯数据）**：旧形状每条 label 归属给**迁移时
  配置的账号**（同库凭据快照，`sync::account_key` 单点规范化）；无配置 → 空 key
  哨兵；转换成功后删除旧键（数据已迁移，不是丢弃）。旧键内容损坏 → **原样保留**、
  不产出 v2 条目、启动不阻断；`folder_tombstones` 见到残留旧键即返回可见错误。
- **失败关闭**：`folder_tombstones` 的读取/解析失败原样上抛；pull 的
  `active_folder_tombstones`（回收 + 读取）与账号身份读取任一失败 → 记同步错误并
  **跳过本轮分类与订阅导入**——订阅导入依赖 label → folder 映射，映射不可信时
  不写任何依赖它的本地状态（不建目录、不绑 remote_id、不填标题）。原值保留，
  修复后下一轮自然重试。
- **身份变化保留分类墓碑**：账号切换不再需要清空它们（key 隔离已足够），
  回原账号仍防复活。feed 墓碑维持「切换即清」的既有策略（见 Consequences 的
  不对称说明）。

## Alternatives considered

### Why not 照 feed 墓碑的做法：账号切换时清空分类墓碑？
最简单，但清空是**不可逆**的信息丢失：用户切回原账号后，已删除/已改名的分类会
被远端 label 重新拉回来。feed 墓碑当初选择清空，是因为它没有归属字段、清空是
唯一能阻止「旧账号墓碑压制新账号导入」的手段（F05）；分类墓碑在本次改造里获得了
归属字段，**隔离比清空更强**（既抑制本账号复活、又不影响别的账号），故不复制
清空策略。两者策略不对称是有意的，不许在后续重构里"顺手统一"。

### Why not 旧形状保持全局语义（空 key 视同对所有账号生效）？
那正是缺陷本身：存量库里的旧墓碑会继续压制新账号的同名分类，而要修的 bug 恰恰
发生在这个场景。把历史条目顺手归属给**迁移时配置的账号**既不丢数据、又立刻获得
隔离；只有确实无账号可归属时（纯本地用户）才退回全局语义，方向是保守的（宁可多
防复活，不可让已删分类复活）。

### Why not 迁移时删掉无法归属的旧条目换取隔离？
明确违反任务卡的「不得以静默丢弃历史墓碑换取隔离」。旧墓碑是「用户删除过这个
分类」的唯一本地痕迹，删掉之后远端仍列出同名 label 时目录会被重建——用户看到的
是"我删过的目录自己回来了"。损坏值保留 + reader 报错要求人工修复，比悄悄删除
诚实。

## Consequences

**收益**：

- 跨账号同名分类不再互相压制：B 的远端分类照常导入，A 的墓碑对 B 不可见。
- 异账号的 pull 不再回收本账号墓碑（原来 B 的一次 pull 就能把 A 的删除意图清掉）。
- 读取失败不再按空表复活分类：可见错误 + 跳过导入，且不写依赖该映射的 feed 状态。
- 回原账号仍防复活（墓碑按 key 存活），比 feed 墓碑的「切换即清」更强。

**代价与已知上限**：

- 旧键损坏时其抑制效果暂时失效：字节保留、启动不阻断、reader 报错要求人工清理
  `settings['folder_tombstones']`（无运维入口，与 feed 墓碑同类）。
- 迁移归属是"迁移时配置的账号"的推测；纯本地历史（从未连接过）用空 key 全局生效，
  属于保守方向。
- 分类墓碑与 feed 墓碑账号策略不对称（前者 key 隔离、后者切换即清）：feed 墓碑的
  清空策略与其 v1 legacy 命名空间的字节保留绑定，本卡不动它；若未来要统一，需要
  先把 legacy 命名空间一起按账号归属，属于独立决定。
- 不回原账号的条目会一直留着；**空 key 全局墓碑没有自动解除路径**（B2-R2 复审
  R2-1 接受其永久保留）——见下条代价说明。
- 全局墓碑的寿命代价（B2-R2 复审 R2-1）：`account_key` 为空的条目只由纯本地写入
  （未配置同步时的删除/改名）与「迁移时库内无账号」产生，**不会**被任何账号的 pull
  回收——应用无法枚举所有历史/未来账号，「其它账号也缺席」不可证明，单账号回收即
  违背全局契约。显式解除路径只有人工修复（`settings['folder_tombstones_v2']` 的
  Note 范围内无运维入口，与 feed 墓碑同类）；实际影响是：该 label 在此后连接的
  任何账号上都不会再被导入，直到用户本地重建同名分类（此时本地目录已存在，墓碑
  只是抑制导入，不再有可见影响）或人工清理。方向是保守的：宁可少导一个目录，
  不让已删目录复活；`add_folder_tombstone` 按 (key,label) 幂等去重，重复删除不会堆积。

  账号（多 label 一条不丢）、无账号空 key 哨兵对所有账号生效、损坏旧键原样保留 +
  reader 失败关闭（启动不阻断）。
- `src-tauri/tests/opt009_phaseb_e2e.rs`：`folder_tombstone_read_failure_skips_import_instead_of_reviving`
  （坏墓碑 → 记错误 + 不建目录 + 不导入订阅；修复后收敛）、
  `folder_tombstone_is_account_scoped_across_switch`（A 删 → 切 B 导入同名分类 →
  回 A 仍压制；A 的条目不被 B 回收）、
  `global_folder_tombstone_survives_single_account_pull_and_suppresses_other_account`
  （B2-R2：写全局空 key 墓碑 + A 专属对照 → A 的 pull 后全局墓碑仍在、A 专属按缺席
  回收；切 B 且远端列出同名 label → 不被全局墓碑放行导入、B 的 pull 也不回收它）。
- `src-tauri/src/db/folders.rs::prune_only_reclaims_tombstones_owned_by_current_account`
  （B2-R2）：回收只限归属当前账号的条目——全局墓碑保留、异账号保留、归属账号的
  「远端仍列出」保留；全局墓碑继续对其它账号生效。
- `src-tauri/tests/sync_gap_repro_e2e.rs::folder_tombstone_cleared_when_remote_drops_label`
  按账号 key 写入墓碑，验证「远端已不含 → 回收、仍含 → 保留」判据不变。
