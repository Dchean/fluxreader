# Agent Note: 账号会话与配置应用边界

Status: implemented

## Problem

审计 F05/F06 指出同一族缺口：**「已连接账号」不是一条有生命周期的边界，而是一组随时可被旁路改写的 settings 键**。

1. **F05 —— 配置导入把新连接信息与旧密码、旧映射拼接。** `config_sync::apply_payload` 直接覆盖 `sync_protocol / greader_endpoint / greader_username`，不经过 `sync_save` 的账号变化判断、清理与连接验证；本机密码保持不变。导入后下一次同步就会**把旧密码发给新服务地址**；若新旧服务接受同一凭据，旧的 `remote_id` 映射、游标和队列还会被继续使用（数据可污染到错误账号）。
2. **F06 —— 断开/切换账号后，在途同步仍可能回写旧数据。** 同步是「短锁读凭据 → 锁外 HTTP → 再持锁落库」；断开与换号只清理**当时**的数据库，对已经在飞的请求没有任何失效机制。旧响应返回后照常进入合并/绑定/游标/队列确认路径，旧账号内容会复活、旧游标会被写回、旧推送确认可能落在换号后的队列上。此前的设置页保存链还是 fire-and-forget：`saving` 在真正的同步开始前就归位。
3. 另外两条同族边界：**通用 `set_setting` IPC 是一条完全绕过账号生命周期的写旁路**（任何前端代码都能直接改活动凭据或游标）；**同账号仅更新密码不应被当成换号**（那会清掉阅读数据与 Fever 历史进度）。

## Decision

**一、每库一个同步代际（`sync_generation` settings 键），所有 HTTP→DB 回写边界在同一次持锁内复核。**

- `db::sync_generation / bump_sync_generation`：普通 settings 键，每库独立（不是全局原子计数——多个测试库/客户端互不影响）；缺失/非法按 0，第一次账号提交推进到 1。
- `sync/session.rs` 的 `SyncSession { generation, client }`：`build_session` 在**同一个短临界区**读「凭据 + 代际」，锁外登录/探测；返回前再持锁复核代际（含端点缓存 `remember_base` 的写回——构建客户端期间换号不得把旧端点写进缓存）。会话不携带也不日志输出密码。
- 每个回写边界都在同一次持锁内 `session.ensure_current(&conn)`：push plan 构建、失败标记（`mark_push_failed`）、剪除确认（`prune_sync`）、订阅 pull 的建分类/绑定/远端退订删除、GR 条目合并/状态对账/`set_last_sync_ts`、Fever 页事务（页数据 + since/checkpoint 同事务）/Complete/对账/`set_last_sync_ts`、`push_feeds` 的绑定与剪除。
- **每个新批次发送前检查代际**：`exec_push` 在每个 read/unread/star 批次前后各复核一次（响应返回后仍要复核才计入确认）；GR/Fever 每个 id 页/正文页/历史页请求前复核。已发出的请求不能撤回——守卫阻止的是**后续请求与本地回写**。
- 代际失配 = `staleSession` 可见错误：中止整轮、不落库、**不记录推送阻塞标记**（那会把错误记到新账号队列上）。

**二、账号提交收口为一个事务：身份定义、并发复核与「密码 ≠ 身份」。**

- **身份 = 协议 + 规范化服务器根 + 用户名**（`normalized_server_root`：scheme/host 小写、去尾斜杠）。`identity_changed` 才清远端数据；**同账号仅改密码**保留全部本地数据、游标与 Fever 历史进度。
- 任何成功提交（含仅密码更新）都**推进代际**——同账号换 token 也要让旧的在途请求失效。协议切换属于远端 ID 命名空间变化：清绑定/队列/游标与 Fever 历史（回 `Unknown`）、清旧账号退订墓碑（不压制新账号导入）、清端点缓存，**保守解绑/重拉**，绝不把旧 ID 给新协议。
- **并发复核**：`save_account_settings` 在开始验证（读旧凭据）时捕获代际，提交事务内重新读取比对——两个保存并发时，迟到的验证整体失败（`staleAccountSave`），不覆盖较新的保存。断开同样复核。
- 提交成功同时消费配置导入的待确认建议（同事务清除）。

**三、配置导入只落「待确认连接建议」。**

- `apply_payload` 不再写 `sync_protocol / greader_endpoint / greader_username`；改为写 `pending_connection_config`（非敏感 JSON），并在 `ApplyOutcome.pending_connection` 返回给前端。
- UI（SyncTab）展示建议的协议/地址/用户名，明示「激活需重新输入密码后保存」；「填入表单并激活」只预填表单，「忽略」调 `sync_dismiss_pending_connection`；真正激活走 `sync_save` 专用流程（新增 `sync_pending_connection` / `sync_dismiss_pending_connection` 两个 IPC）。
- **通用 `set_setting` IPC 对活动连接/代际/游标/历史/端点缓存/待确认建议键一律拒绝**（`protectedSetting`）——不是只修 config_sync 而留下旁路；`db::set_setting` 内部函数仍可被受控事务（账号提交、同步引擎）使用。

**四、Fever 历史与断开/换号同事务对齐。**

- `commit_disconnect` 与「身份变化」提交在同一事务里：`fever_history_state` 回 `Unknown`（写空串，读侧即 Unknown）、`sync_last_entry_id = 0`、`sync_last_sync = 0`（断开两者都清；身份变化两者都清）——**不能只重置 GR 时间戳而让新账号继承旧 Complete 或旧页游标**。
- Pending 捕获的页游标只对原会话有效：页事务在同一个持锁内复核代际，失配整页丢弃（不合并、不推进 since/checkpoint）。
- 同账号密码更新的边界：历史进度保留，但代际推进使旧请求失效。

**五、锁纪律不变。** HTTP 绝不跨 DB 锁；代际复核都是新的短临界区；`PUSH_LOCK` 仍是推送互斥的独立小锁，不升级为全局 DB 锁。

## Consequences

- 断开/换号后，旧响应不再可能复活旧账号的订阅、绑定、分类、游标或队列确认；换号后的自动同步（scheduler/即时推送）与新账号数据不被旧会话触碰。
- 配置导入不再能造成「新地址 + 旧密码」；激活必须经过与手填相同的验证+提交路径（并发保存也被代际复核挡住）。
- 代价一：每次回写边界多一次短锁内的轻量读（越界即弃），同步正常路径的锁竞争可忽略（都是微秒级 settings 查询）。
- 代价二：同账号仅改密码也会使在途请求作废（本轮同步多一次 `staleSession` 中止，下一轮自动重来）。这是有意选择：token 轮换后旧会话继续写入同样危险，「代际推进」是唯一不需要逐请求身份比对就能封住的形态。
- 代价三：身份变化清空「旧账号的退订墓碑」——换回旧账号时此前删过的订阅会被服务端列表重新导入一次。断开（未换账号）不清墓碑，仍保留 TASK-055 的防复活语义。
- 设置页保存链改为 `await` 全链路（feeds → states → 直连刷新），`saving` 覆盖真正链路；链路失败返回明确错误并给重试，不再假成功，也不会留下永久 busy（`finally` 复位）。
- 未来任何新的同步入口/回写点必须带 `SyncSession` 并用 `ensure_current` 收口——这条纪律写进了 session.rs 头注，review 时应按「新增无守卫回写点」零容忍检查。

## R1 修订（独立审查 NEEDS_CHANGES 三项）

**1. 代际三态收紧：`present` 非法必须 Err（P2）。**
`db::sync_generation`：缺失/空串 = 0（旧库未初始化）；**现存但非法/负数/溢出 = `protocol` 错误**，绝不按 0 与「旧代际 0」的会话假匹配，也绝不在 `bump` 里顺手覆写成 1 掩盖现场。`build_session` 为该错误单列 `ClientBuildFailure::CorruptGeneration`：phases/save 原样上报（不再伪装 `notConnected`），即时推送只记日志返回，不写推送阻塞标记（坏代际与队列无关）。测试不再固化 `bad = 0`。

**2. 空密码只允许同一身份（P1，后端强制）。**
`resolve_save_plan`：协议/规范化服务器根/用户名任一变化 + 空密码 → `validate` 错误，**在 HTTP 之前拒绝**——旧账号密码绝不随请求发给新服务（无论普通保存还是激活 token）。同身份空密码的既有复用语义保留；用户名变化的 P3[3] 优先级用例改为显式新密码验证。

**3. 建议消费改为「版本 + 身份的 CAS」，且普通保存不触碰（P2）。**
- 落库形态改为 `PendingSuggestion { version, connection(flatten) }`；`store_pending_connection` 每次写入版本 +1（同值重复导入也换版本），旧平铺形状兼容为版本 0。
- 专用激活必须在 `sync_save` 携带 `activate_pending_version`（前端从 `sync_pending_connection().version` 原样回传；后端独立校验，不信任 UI）。**HTTP 前**先校验「版本 == 当前建议 && 建议内容与本次保存目标身份逐字段一致」，不匹配直接拒绝、零请求。
- 提交事务内再做一次同判定的 CAS：命中才消费建议；不匹配**整体拒绝**（活动配置保持、当前建议保持、代际不推进）——B 验证在途时新导入 C 不会被迟到激活覆盖/消费。
- 普通保存（`activate_pending_version = None`，旧调用方兼容）**绝不触碰建议**；同账号改密码、无关导入共存都不会清理它。

R1 判别测试（先 RED 后 GREEN）：`generation_missing_is_zero_and_corrupt_is_error`、`save_plan_blank_password_rejects_new_identity`、`normal_save_preserves_pending_suggestion`、`activation_commit_rejects_stale_version_and_keeps_newer_suggestion`、`activation_commit_consumes_when_version_and_identity_match`、`empty_password_new_identity_sends_no_request_to_new_server`、`activation_stale_version_rejected_before_http`、`late_activation_after_replacement_during_http_keeps_newer_suggestion`、`corrupt_generation_is_visible_error_with_zero_requests`、`pending_suggestion_store_bumps_version_on_every_import`。

## R2 修订（定点 review 三项；部分取代 R1 的对应条目）

**1. 身份规范化必须保留端口与 basepath（P1）。**
`normalized_server_root` = scheme + host（小写）+ **有效端口** + basepath（去尾斜杠）；只归并等价形态（省略端口与显式默认端口 http:80 / https:443）。同 host 不同端口、不同 basepath 都是不同 server——R1 的 host-only 写法会让 `host:8080` 与 `host:8081` 被当同身份复用旧密码。**取代** R1 中「规范化服务器根」的实现细节。
另：**任何显式激活即使身份相同也必须 fresh 密码**（`SavePlan.password_supplied`；HTTP 前拒绝）；只有真正的同身份**普通**保存空密码才允许复用旧密码（R1 语义保留在普通路径）。

**2. 代际三态再收紧（P2）。** 只有**键缺失** = 0；现存空串/空白/非法/负数/溢出全部 Err（R1 的「空串=0」作废）。`bump` 用 `checked_add`：i64::MAX 时 Err 且不改写（不饱和复用同代际）。

**3. 建议 token 由独立持久 serial 发行（P2，防 ABA）。**
- 新键 `pending_connection_serial`（加入受保护键清单）：只增不减、`checked_add` 溢出 Err；`clear_pending_connection` **只清内容不重置 serial**——「清空后重导」不会从 1 重新发行与历史在途 token 撞车。
- `store_pending_connection`：**同值重复导入 = ignore**（不换 token）；换值 / 清空后重导 = 新 token。**取代** R1「同值重复导入也换版本」。
- serial 与建议内容的写入由调用方导入事务（`&tx`）捆在一起提交；serial 先写、内容后写——中途失败只留号段空洞，不会同号两建议。
- 激活的 HTTP 前校验与提交 CAS 都改为「serial token == 当前建议版本 && 内容与目标身份一致」；旧 in-flight token 在「放弃 + 重导」后必然失配：保新建议、保旧账号。

R2 判别测试：`save_plan_identity_keeps_port_and_basepath`、`save_plan_marks_password_supplied_for_activation_gate`、`port_only_change_with_empty_password_sends_nothing_to_new_port`（同 host 不同端口，普通保存 + 激活均零请求）、`activation_same_identity_still_requires_fresh_password`、`pending_suggestion_serial_is_monotonic_and_aba_safe`、`pending_serial_prevents_aba_with_inflight_activation`（屏障）、`generation_missing_is_zero_and_corrupt_is_error`（重写：空白 Err + 溢出不饱和）。

### Why not 让空密码在新身份下复用旧密码（或只在 UI 提示）？

旧密码在语义上属于旧身份；把它发给新地址就是 F05。UI 文案挡不住调度器、其它窗口或直接 IPC ——必须后端在 `resolve_save_plan` 拒绝，保证「HTTP 之前」这条硬边界（R1 测试断言新服务零请求）。同身份复用是安全的既有语义，因此规则收敛为「空密码 ⇔ 身份不变」。

### Why not 保存成功就无条件清空待确认建议？

保存与「消费建议」是两件事：普通保存（改密码、离线修地址等）不应吞掉用户还没确认的导入建议；而激活建议的提交在 HTTP 验证期间可能已有新导入 C 覆盖建议——无条件清除会让迟到激活把 C 删掉。版本 + 身份的 CAS 把「消费」精确限定为「我激活的正是当前这条建议」，不匹配整体拒绝。（R2 起 token 由持久 serial 发行；同值重复导入 ignore 是安全的——消费到的仍是同一内容，ABA 风险由 serial 不重置封死。）

### Why not 用内容 hash 代替版本号？

hash 表达不了「同一条建议被放弃后重新导入」：hash 相同会让旧 in-flight token 命中重导的新建议（ABA），且未来字段/来源扩展后相同 hash 未必代表同一导入意图。独立单调 serial 不依赖哈希碰撞假设，清空不重置、重导必换号，语义最直接。（R2 起同值重复导入本身 ignore、不刷新 token；serial 只保证「重导/换值」永远发新号。）

### Why not 把坏代际继续映射成 notConnected？

notConnected 会让前端「未连接静默跳过」的既有语义吞掉可见故障，也诱导用户去重填凭据而不是修数据。坏代际是数据损坏，必须原样可见（`protocol`），且不得记录推送阻塞标记——那是队列状态，与代际无关。

### Why not 破坏 `sync_save` 的旧签名强制携带激活参数？

旧调用方（既有前端版本、其它入口）不需要激活语义；参数可选（None = 普通保存、不消费建议）既保持兼容，又让「消费」成为一种显式意图。后端不因参数缺失而放宽任何校验。

## Alternatives considered

### Why not 全局原子计数当代际？

任务卡明确「不得全局跨所有 DB 互斥错误影响两个客户端测试」。全局计数会让「测试库 A 的提交」失效「测试库 B 的会话」，也会让两个真实客户端实例（双开/测试夹具）互相踩。代际是**每库身份**，存 settings 是最小改动且天然随库隔离。

### Why not 在每个入口检查一次即可？

检查一次挡不住「检查通过 → HTTP 在途 → 账号切换 → 响应回写」这条正是 F06 的时序。必须每个落库点都在**同一次持锁内**复核；批次发送前也要复核，否则旧会话会继续向旧服务端发后续请求、继续把结果带回来。测试用真实屏障（挂起 HTTP 响应再释放）逐边界锁定，不用 sleep 猜时序。

### Why not 用取消令牌（CancellationToken）统一中止？

取消令牌适合「一个任务树」形态；本问题的请求由多个入口（调度器、即时推送、设置页链、订阅编辑）各自发起，且已经发出的请求无法撤回——关键不是「停任务」而是「停回写」。代际 + 边界复核把不变式放在数据库写入口，覆盖面最完整；取消令牌作为补充没有额外收益。

### Why not 配置导入直接调用账号生命周期（自动换号）？

导入的载荷没有密码（密码永不出本机、也不进远端配置）；自动换号就需要「新地址 + 本机旧密码」，正是 F05 要消灭的组合。落待确认建议、由用户明确重输凭据激活，是唯一不引入旧密码复用风险的路径；UI 必须真实消费（展示+激活入口），不能落库一个没人看的字段。

### Why not 同账号改密码也清本地数据？

密码变化不改变服务端身份与远端 ID 命名空间；清数据会把用户的阅读进度、收藏与 Fever 历史无故清空。边界取「身份变化才清，密码变化只推进代际」。协议变化则相反——远端 ID 命名空间不同，保守解绑/重拉。

### Why not 身份变化保留 feed 删除墓碑？

墓碑记录的是「用户在本机删过这个订阅」。换到另一个账号后旧删除意图不再适用；保留会让新账号的同 URL 订阅被永久压制（F05「旧映射不污染新账号」）。但断开不换账号时保留——重连同一账号必须继续防「已删订阅复活」（TASK-055）。

### Why not 让旧的 push 确认继续剪除队列？

旧计划的 queue id 属于旧账号队列（换号时已清空）。继续剪除在 AUTOINCREMENT（v18）下通常无碰撞，但这是「依赖编号不复用」的隐式假设；且失败标记会把旧错误写到可能属于新账号的行上。守卫按代际直接跳过整段记账，显式消除假设。

### Why not 前端保留 fire-and-forget 链？

审计明确把「saving 不覆盖后台链」列为 F06 的一半。改为 `await` 全链路后，保存按钮的真实含义与用户看到的状态一致；失败给明确错误+重试，不出现「看起来保存成功、实际同步从来没跑完」。
