# Agent Note: 订阅写回 outbox 的生产执行器

Status: implemented

## Problem

本地订阅改动曾只 best-effort 推远端，失败没有重试载体；quick_add 一成功就剪队，后续绑定与分类挂载失败永久丢失；GReader 只发 a= 无法移除旧分类，Fever 无端点却返回 Ok。需要把“本地已改”“远端已创建”“完整意图已确认”区分为可持久恢复的事实。

## Decision

本地改动与类型化订阅意图同事务落库，执行器按不可复用 id 精确确认。新增、OPML、首连、改名/移动、删除、分类改名/级联删除都接入；删除在级联前快照远端目标，outbox 不依赖已被删除的 feed 外键。未连接的新增保留本地语义，坏凭据则失败关闭，不把读错当离线。新命令不再生产 legacy add_feed，但旧队项仍有消费者。

### 账号与操作阶段

计划只消费当前 account_key 的行，同身份旧代际可在计划前重绑；落库、失败记账与确认复核代际。入队合并不跨账号删除同 URL 行。在途响应不得推进异账号/新代际意图。2026-11-02 的[生命周期终点](../bug-fix/2026-11-02-订阅outbox生命周期终点.md)已取代最初“换号暂停、回号恢复”：账号提交事务主动清旧身份 outbox，同身份重连与断开保留。切换时未收敛的远端创建可能成为需手动清理的孤儿，不能宣称切换后仍会自动退订。

subscribe 分 pending/remote_created。pending 先查远端订阅列表的同规范化 URL；确认缺席才 quick_add，失败或没有 streamId 后再查一次列表。列表读取失败不能证明缺席，不发 quick_add。取得 id 后先持久化 remote_created，再绑定、补标题/分类；绑定失败保留阶段，重启不再创建。2026-10-31 的[订阅恢复](../bug-fix/2026-10-31-fever推送幂等与订阅恢复收敛.md)用此逻辑取代旧“quick_add-by-URL 必幂等”的假定，固定服务端重复 URL 会拒绝。

网络窗口内目标可变，所以计划快照不是最终发送依据：绑定的同一短锁内重读当前 pending subscribe。发送使用最新 desired_title/desired_folder/prev_folder，确认逐字段 NULL 敏感比较实际发送值；行被替换或目标又变就不出队。阶段推进失配时，已创建 id 尝试交给同账号同代际的替代意图；本地源已删则结转退订，写失败继续保留重试。

Fever 没有订阅写端点，能力门把意图记 local_only，调用底层 edit/unsubscribe 明确 unsupported。空分类无法用逐成员操作表示远端改名/删除，只保留本地动作和防复活墓碑，不能声称远端完成。跨后端可验证的分类操作采用逐成员 a/r/unsubscribe，不采用只在部分固定服务端找到的 rename-tag/disable-tag。

### 移动链的移除基准

GReader 编辑发 t=标题、a=目标 label、r=远端实际持有的旧 label，只移除这个基准，保留其他标签。未发送 A→B→C 合并须保留链起点 A；仅改名或无链起点 subscribe 才采用调用方旧 label。remote_created 窗口的挂载同样带 r=，prev_folder 取首值并参加确认比较。

发送成功是新事实：若已发送 A→B 后在途被 B→C 替换，旧确认落空时执行器把后继移除基准重定为 B。重定覆盖同账号同 URL 的 edit、subscribe、unsubscribe 三类 pending 行，空/非空旧基准都改写；其作用域是账号 key，不能被同账号换密码的 generation 变化丢弃。确认与失败记账仍守 generation，异账号不重定。

删除快照需优先继承未发送链的起点，无链起点才用本地当前分类。快速重加继承 pending 退订的移除基准，却不盲继承 remote_id/resolved_remote_id，因为退订可能已生效。挂载成功与 edit 成功同样触发重定。网络成功与重定之间进程死亡仍会丢这一发送事实，不能由本地行猜回；同账号切走再切回也需承认历史发送事实与新建意图的边界。

### 退订恢复与确认

已知 remote_id 直接退订；未知 id 的退订只由删除前同账号同 URL pending 创建证据产生，普通从未发出创建的本地删除不制造恢复请求。

未知目标的解析与重复目标发现共用一次 subscriptions 列表：读失败保留 Retry，本轮不发退订；同 URL 首 id 持久化 resolved_remote_id 后，逐一退订发现的所有同 URL id，并把已持久化目标也纳入。没有列表目标且没有已持久化目标时确认意图已满足。这是 2026-10-31 引入的缺席证明，依赖订阅列表一致性；原“绝不按列表缺席清队、先创建再删除”已被取代，不得同时当现行规则。

GReader 2xx 响应仍须正文 OK；退订的 400/404 特例视为目标已不存在，网络/5xx 仍失败。固定 FreshRSS 的 400 也可能代表 deleteFeed 失败，故该容忍可能留下远端残留；它不证明整个 URL 已缺席。源墓碑仍由 pull 的列表缺席证据回收，而非任何单 id HTTP 响应。

### 调度、保护与可见性

即时命令尝试一次，后台 tick 检查当前账号 pending 后再构建会话；无 pending 零网络。会话构建 Failed 为当前账号 pending 累加 attempts 并记录失败会话身份摘要，NotConfigured/Stale 不记到新队列。重试判据的结构化来源见[认证回落判据](../bug-fix/2026-11-02-认证回落判据结构化.md)，但 outbox_block_summary 的摘要分类仍使用 code=auth 或 ClientLogin 文案，不能把两者当同一实现。失败会话与记账时账号可能变化的摘要归属边界也不能靠日志文字当精确事务事实。

pull 删除保护集合只读当前账号 pending；身份/保护集合读取失败跳过删除，不能按空集合删除。分类映射读取失败也跳过依赖导入，见[分类墓碑](2026-10-14-分类墓碑账号隔离.md)。legacy add_feed 挂载失败保留并记失败，恢复经列表查既有 id，避免剪队丢分类。

回执按账号统计，local_only 与错误可见，见[能力与回执](2026-10-15-订阅写回能力矩阵与持久回执.md)。同值通知去重与失败重发遵循[运行生命周期](2026-11-05-同步运行生命周期与诊断.md)：事件发射成功后才推进缓存，不能把失败发射记成已通知。

## Alternatives considered

- **直接扩展 legacy add_feed**：缺少账号指纹与类型化阶段，且旧消费者已有兼容责任；新意图用独立 outbox，旧行只保留必要恢复。
- **绑定/挂载失败也剪队靠 pull 修**：pull 不能补偿分类目标，剪队后丢失未完成意图。
- **UPDATE 合并保留 id**：旧响应可能确认新动作，故替换意图换 id；subscribe 原地目标更新则增加发送值逐字段条件。
- **一次发两个 r=**：当时固定上游没有一致证据证明移除不存在 label 恒为无害，未扩 wire；仅发送已知基准。
- **从本地状态猜上次已发移动**：两种网络历史可留下相同本地字段，只有执行器的成功响应能重定。
- **退订恢复调用幂等 quick_add**：早期选择为避免依赖列表缺席，但真实重复 URL 拒绝否定其前提，后继改为列表先行；保留这一原因，不能把原方案写成从未采用。
- **重加直接继承退订 id**：退订是否已生效不可从行推断，盲转会绑定已删除目标；重新用列表解析。
- **Fever 伪造 Ok 或只在命令层拒绝**：持久 local_only 先明确欠账与能力，UI 再投影；不能把不支持当远端成功。
- **给 legacy 再复制完整 remote_created 状态机**：新增路径已有类型化执行器，legacy 保留失败和列表恢复足以处理存量，复制状态增加维护面。

## Consequences

阶段化保存使网络失败具备恢复载体，代价是账号、阶段、目标与发送事实共同构成确认条件。列表恢复减少重复创建，但接受列表缺席作为证据，不能保证服务端语义性遗漏可检测。400/404 容忍、进程死亡前未重定、账号切换弃账均有明确残余风险。

2026-11-06 `91ece562` 仍实测远端操作成功后 SQL outbox 确认失败保留行，却未进入 report.errors；不能将“持久队列保留”推导为“失败已对用户完整呈现”。该问题与 feed URL 身份冲突集中在[同步正确性路线](../../../../docs/roadmap.md#sync-correctness)。
