# Agent Note: 订阅写回 outbox 的生产执行器

Status: implemented

## Problem

OPT-009 阶段 A 交付了类型化订阅 outbox 表与数据层原语（`db/outbox.rs`），但没有生产消费者：本地新增/改名/移动订阅仍以「本地改完 best-effort 推一次」的方式回传远端（`sync/subscriptions.rs` 的 `push_feeds` / `edit_remote_subscription`），失败只留日志；`quick_add` 成功后立刻把队项加入 done，绑定失败或分类挂载失败仍会 prune——「源已创建」被当成「完整订阅意图已完成」。同时 GReader 的 `ac=edit` 只发 `a=`（追加分类），没有 `r=`（移除旧 label），跨服务端无法表达真实「移动分类」。Fever `edit_subscription` 直接返回 `Ok(())`，把「没有端点」冒充成「远端已完成」。

## Decision

**订阅写回的心智模型：本地修改与远端意图同一事务落库，远端确认按不可复用队列 id 精确出队。** 执行器 `push_subscription_outbox`（`sync/subscriptions.rs`）在 feeds 阶段运行，状态机：

- **账号屏障**：计划只取 `account_key`（协议 + 规范化服务器根 + 用户名）等于当前会话账号的行；同 key 旧代际在计划前**明确重绑**到当前代际（同账号改密码后旧意图仍有效）；异 key 一律不 touch（换号暂停、回原账号恢复）。拉取/确认边界在每次回写前复核库代际（既有 OPT-006 纪律）。
- **subscribe(pending)**：`quick_add` → 成功先 `advance remote_created` 记下 `remote_id`（**重启后不得重复 quick_add**）→ 绑定本地 feed（写失败保留队项、累计 attempts，下轮只重试绑定）→ 有目标标题/分类时补发一次 `edit_subscription` → 全部确认才 `prune(id, generation)`。
- **subscribe(remote_created)**：只做绑定与目标挂载，绝不重发 `quick_add`。
- **edit**：`t`=标题、`a`=目标 label、`r`=**编辑前的旧 label**。只发 `a` 是追加分类不是移动；`r` 只移除旧 label，其他 label 不被触碰。
  **移除基准（`r`）必须指向「远端实际持有的 label」，而不是「新操作读到的本地旧 label」**（B1-R3 复审 P2-1）：既有 pending edit 行仍带未发送移动目标时，远端尚未收到任何移动，它持有的是那条未发送链的**起点**（既有行的 `prev_folder`）——A→B 未发送再 B→C 的合并必须保留链起点 A（用 B 会让远端的 A 永不移除）。既有行只是改名、或既有行是 subscribe（remote_created 窗口）时，远端持有的就是新操作读到的旧 label，用新 `prev`。
  **发送成功后的重定**：链起点只在「没有任何发送成功」时等于远端状态。旧编辑已推达（远端已在 B）而在途又入队 B→C 时，替代行必须改用它移除 B——执行器在确认落空（被处理的 id 已不在队）且本轮发送的是移动时，把替代行的 `prev_folder` 重定为已发送目标（`rebase_successor_edit_prev`）。合并本身无法分辨这两种时序（库里状态逐字相同，只有网络历史不同），故该信息只能来自执行器。
  **重定的作用域是账号 key，不是 (key, generation)**（B2-1）：同账号改密码/重连也会推进代际，而「远端已接受该目标」是**账号作用域**的事实；确认/失败标记继续按 OPT-006 纪律在代际失配时整段丢弃（队项保留待下轮重发），但**后继意图的重定不受代际守卫阻断**——否则换代后下一轮会按过期链起点发 `r=`，远端长期残留已发送的中间 label。跨账号安全由 key 守卫保证（异账号同 URL 的队项一个字节都不动）。
- **subscribe 的挂载也带 `r=`**（B2-3）：`remote_created` 窗口的分类改名/移动经 `update_pending_subscribe_desired` 把旧 label 并入订阅行（`prev_folder` 取**首值** = 链起点），挂载时按 `a=` 新 + `r=` 旧发送；确认比对 `desired_title/desired_folder/prev_folder` 三字段（NULL 敏感）——发送时无 r 而在途期间补上旧 label 时确认必须落空，否则远端残留该旧 label。
- **unsubscribe**：`ac=unsubscribe`（2xx-strict）；墓碑仍只由 pull「远端列表确认已不含」清除（既有 TASK-055 判据不变）。
- **Fever 能力门**：`Backend::supports_subscription_write()` 为假时全部计划项置 `local_only` 终态（保留展示、不重试、不冒充远端完成）；`Backend::edit_subscription`/`unsubscribe` 对 Fever 返回 `unsupported` 错误，不再 `Ok(())` 冒充。

**OPML 导入与 add_feed 同一接线（B1-R3 复审 P2-2）**：`opml_import` 的本地新增（建目录 → 插 feed → 清墓碑）与**类型化 subscribe 意图**在同一事务落库（`enqueue_subscribe`，携带账号 key/代际与目标目录 label），不再写 legacy `sync_queue.add_feed`——legacy 路径在 `quick_add` 成功后立即剪队，「源已创建」被当成「完整订阅意图已完成」，绑定/分类挂载失败的任务从此消失且无重试载体。未连接 → 仅本地（首连弹窗的 `sync_local_feeds` 再推）；凭据读取失败 → 整体回滚（失败关闭）。

**生产者全集（B2）**：本地变更与远端意图同事务的入口现在是四类——新增（`persist_new_feed`/OPML/首连）、改名/移动（`record_feed_edit`）、**删除（`record_feed_deletion`：墓碑 + 本地删除 + 退订意图，离线/重启由执行器重试）**、**分类改名/删除（`record_folder_rename`/`record_folder_delete`：改名逐成员发 `a=` 新 + `r=` 旧、删除在级联前取成员与远端目标快照并逐成员建独立退订意图）**。分类级端点（`rename-tag`/`disable-tag`）在固定上游里只有 FreshRSS 实现，其余后端无可核验支持，**不使用**；空分类没有成员可表达 → 本地改名 + 墓碑防复活，如实记为本地/远端不支持（不伪造成功）。Fever 全部 `local_only`。
**订阅的标题目标（B2-5）**：`enqueue_subscribe` 携带 `desired_title`——OPML 的非空导入标题与新增源的命名标题在 `quick_add` 后用真实 `t=` 写回；标题等于 URL（解析兜底、不是用户意图）时**不**产生标题目标。

**pull 删除对账的保护集合（B1-R3 复审 P2-3 / P3-4）**：`pull_feeds` 的「本地动作尚未回传则不删」保护集合有两处纪律——
① **只算当前同步账号**的 pending 意图（`subscription_outbox.account_key = 当前账号`）：异账号的暂停行不属于本账号快照，否则换号后本账号的远端删除对账永久失效（B 永远删不掉自己已退订的源）；
② **fail-closed**：保护集合读取（含账号身份读取）任一 prepare/query/row 错误 = 状态未知，记同步错误并**跳过本轮删除对账**，绝不能把「未知」当「空集合」继续删除（那会误删本地订阅）。`sync_queue` 的 article 级与地址型队项沿用原语义，同样纳入这一读取边界。
**分类墓碑同样按账号 key 作用域且失败关闭（B2-4）**：读取失败不得按空表继续（会复活已改名/删除的分类），异账号墓碑不生效也不回收——独立决定见 [分类墓碑的账号隔离与失败关闭](2026-10-14-分类墓碑账号隔离.md)。

**跨账号同 URL 政策：删除/替换只限同账号。** `enqueue_subscribe/edit/unsubscribe` 的 DELETE 都带 `account_key`——B 的本地动作不得删除 A 的 `remote_created` 意图（否则远端孤儿，回 A 后无从收敛）；异账号行并存、各自按 key 执行。`account_key` 与 OPT-006 的账号身份判定共用 `sync/credentials.rs::normalized_server_root`，不各写一份。

**孤儿防护（响应在途替换）**：`advance_subscribe_stage` 带 (id, generation, action, stage, status) 守卫；推进失败时把 `quick_add` 已建的 `remote_id` 补给同账号同代际的替代 pending 行（`adopt_remote_id_for_pending`：退订行填 id、subscribe 行填 id 并推进 remote_created）；本地订阅已被删除则结转同账号退订意图。绑定失败是重试不是放弃：`mark_outbox_failed` 只累计 attempts/last_error（带代际守卫），不改队项身份。

**未知远端目标的退订意图（B2-R1 复审 P2；恢复契约经 B2-R2 收窄）**：删除发生在同账号同 URL 仍有 pending 队项时（`quick_add` 已发出、响应在途/丢失/重启），远端可能已经存在这次创建——`enqueue_unsubscribe` 采集这一**创建证据**（删除前读取，key 作用域）并写入 `remote_id IS NULL` 的退订行；没有证据（从未推送过，含「删除先于 quick_add 发出」的普通场景）不写行，本地墓碑已足够。执行器的恢复规则（B2-R2 复审 P2 修订）：
1. **解析**：幂等 `quick_add`-by-URL 取回已验证 id（订阅已存在 → 返回既有 id；不存在 → 创建一个随后立即退订的订阅）——契约来自固定上游 `quickadd → addFeed → feed/<id>` 形态、`mock_greader` 的幂等登记（B2-R1 起创建即登记，重复 quick_add 返回同一 id）与既有用例（`subscribe_bind_failure_*`、`opml_import_*`）。解析成功**立即持久化**（`advance_unsubscribe_resolution` → `subscription_outbox.resolved_remote_id`，v25 纯追加列；守卫 id/generation/action='unsubscribe'/pending/remote_id IS NULL，写不进去 = 行已被替代 → 已验证 id 交给 `adopt_remote_id_for_pending` 结转替代行、本轮不发）；
2. **发现**：读远端订阅列表收集**同 URL 的其它 id**（只作「还要移除谁」的正面证据）。列表读失败 = 重复目标发现未完成 → `Retry` 保留 pending 队项，**本轮不发送任何退订**；解析失败同理 `Retry`。**持久化解析结果是防重复创建的唯一手段**：本仓 pinned 上游未证明所有 GReader 服务端对重复 quick_add 幂等（非幂等实现每次调用都会新建订阅），列表长期失败或重启后每轮重试都重新 quick_add 即无界造重复项——持久化后重试只重读列表；
3. 两段都成功后才对「解析 id ∪ 列表同 URL id」逐一退订，全部真实 2xx 才 `Confirmed`。**绝不在「列表不含该 URL」这类观察上清队**——远端列表没有可用的一致性界，按缺席清队等于把可能存在的远端订阅留成孤儿；解析不到目标就 `Retry`（attempts/last_error 可见，墓碑继续挡复活）。
   **目标已不存在（400/404）视为已满足（B2-R2 复审 P2-C）**：pinned FreshRSS 的 `subscriptionEdit` 对不存在/删除失败的 id 走 `badRequest()` → HTTP 400（`freshrss-greader.php` 的 `!($feedId > 0 && deleteFeed($feedId))` 分支）；把 400 当可重试失败会让「解析目标被外部删除」的队项**永久 Retry**，同一意图里其它同 URL 目标也永远发不出去。`GReaderClient::unsubscribe` 因此把 400/404 映射为「目标不存在 = 退订意图已满足」返回 Ok（5xx/网络仍是 Err、2xx 仍要求正文 `OK`），列表恢复后的一轮把它与其它目标一起收敛。墓碑不受影响：仍只由 pull 的「远端列表确认已不含」回收——400 只说明**那个 id** 不存在，不构成「列表已不含该 URL」的证明。
旧账号的 id 与意图始终按 key/代际屏障隔离：换号后旧行暂停、代际变更时 adopt 被拦下（行保持未知 id，等回原账号用幂等解析收敛），不会把旧 id 发给新账号；解析落库带代际守卫，换号/换代后的行不得被旧响应推进。

**重定的第二类替代行（B2-R1 复审 F-1）**：`rebase_successor_edit_prev` 除移动链上的 `edit` 后继外，也覆盖**删除/退订后重新添加**留下的 pending `subscribe` 后继——它的 `prev_folder` 为空而远端仍持有已接受的目标 label；补填后，重加挂载发 `a=新 + r=已接受`，远端不会残留中间 label。

**删除时快照的移除基准、链起点优先与重定统一（B2-R2 复审 R2-3 / P3-A/D）**：
- 重定只能在「移动成功响应确认」那一刻补填当时存在的后继行；移动**已确认出队之后**才发生的「删除 → 快速重加」没有这一刻——删除时把「远端当前 label」快照进退订行 `prev_folder`（本地当前分类 label；分类级联删除用被删目录名），`enqueue_subscribe` 替换同账号同 URL 的 pending 行时继承该基准，重加挂载即发 `a=目标 + r=旧 label` 并保留其它 label。退订已确认出队的普通重加没有可继承的行 → 不带基准、不发多余 `r=`（两种时序在 e2e 中分别断言）。
- **链起点优先（P3-A）**：删除时若被替换的 pending 行仍带 `prev_folder`（未发送移动链的起点 = 远端实际持有的 label，B1-R3 合并教义），它优先于调用方快照——本地已 A→B 但移动未发送时本地是 B、远端仍是 A，用 B 发 `r=` 是 no-op、远端 A 永不移除。没有链起点才退回调用方快照。
- **重定改写非空基准（P3-A/D）**：发送成功的 2xx 是「远端当下持有该目标」的账号作用域事实，链起点/快照在它面前已过期。`rebase_successor_edit_prev` 因此把**三类**同账号同 URL 的 pending 后继行统一改写为已接受目标：`edit`（移动链）、`subscribe`（重加后继：为空补填、非空改写——改写前只补空，P3-A 起删除基准可能是链起点快照）、`unsubscribe`（删除撞上在途移动、尚未被重加替换的退订行——它将来被继承时基准必须是远端当下的 label）。
- 若替换发生时退订**尚未生效**（远端旧订阅仍在，窗口未及收敛），继承的基准恰是远端当下持有的 label，`r=` 正常移除；反之若退订其实已生效，`r=` 是不存在的 label 的移除——与 `remote_created` 窗口挂载的既有 no-op 假定同级，不额外引入新假设面。
- 已知上限（P3-B，B2-R2 复审登记）：`enqueue_subscribe` 替换 pending 退订行时**只继承移除基准，不结转 `remote_id`/`resolved_remote_id`**——「退订可能已生效」与「目标仍存在」两义并存，盲目结转会把本地绑定指向已删除的远端 id。因此重加路径只承诺**幂等 official GReader 语义**（quick_add 对已订阅 URL 返回既有 id）+ 有界条件（若服务端非幂等，且替换时退订尚未生效、远端同 URL 订阅仍在，重加会新建一个订阅；重复项随删除/重加次数线性、不静默累积意图）。解析推进的持久化（`resolved_remote_id`）只服务退订行自身的收敛，不跨动作类型借用。

**计划快照不是发送依据（B1-R2 复审 P2）**：`remote_created` 窗口的编辑经 `update_pending_subscribe_desired` **原地**更新同一 subscribe 行（id/代际不变），所以 (id, generation) 不足以识别「发送后目标又变」。执行器在 quick_add 返回后，于**绑定的同一 DB 临界区**重读当前行（id + generation + action='subscribe' + status='pending'）：行被替换/删除/动作改变 → 安全跳过（不发送、不确认）；否则挂载/补 edit 以重读后的最新目标发送，且确认走 `confirm_subscribe_if_desired_unchanged`——只有行仍在且 desired_title/desired_folder/prev_folder 与**实际发送**逐字段相等（NULL 敏感）才出队。发送后目标再变时确认落空、队项保留，下一轮发送最新目标（最后写入者获胜）。

## Consequences

- 离线改名/移动/新增在重启后仍可收敛；`edit_remote_subscription`/`push_feeds` 的 legacy 路径保留给直接调用方与旧版遗留的 `add_feed` 队项，新命令路径不再使用它们。
- 命名命令路径的即时 UX：命令入队后调用 `try_push_subscription_outbox` 立即尝试一次（失败静默，由下一轮同步重试）——与旧 best-effort 调用成本同量级，但不再有「网络失败即永久丢失意图」的窗口。
- `mark_outbox_local_only` 与 `advance_subscribe_stage` 的入参带代际：过期响应既不能推进也不能标记新行。
- 连续移动的远端收敛不再依赖「新操作的 prev」这一在两种时序下都会出错的猜测：未发送链折叠保留链起点，发送成功的中间目标由执行器在确认落空时重定移除基准（B1-R3）。
- pull 删除对账的保护集合既是**账号内**的（异账号暂停意图不保护本账号），也是**fail-closed** 的（读取失败跳过本轮删除）——保护语义不会因一次查询错误退化成「无保护」。
- 生产者全集在 B2 补齐：删除、分类改名/删除都走「本地变更 + 墓碑 + 远端意图同事务」，离线/重启由执行器重试；删除的退订目标（remote_id）在级联/删除前快照，每个实际远端成员各有独立意图，本地订阅消亡不带走退订意图（outbox 与 feeds 无外键）。
- 已知边界：`record_feed_deletion` 的即时 UX 只触发一次执行器尝试（`try_push_subscription_outbox`），失败由下一轮同步重试；`sync::unsubscribe_remote` 与 `edit_remote_subscription` 一样保留为**直接调用入口**（生产命令层不再调用，2xx 不清墓碑的判据由它和 pull 两侧共同锁定）。
- 已知上限（B1-R3 / B2-1）：移除基准重定依赖「本轮 HTTP 2xx = 远端已应用」这一既有确认口径（与退订 2xx-strict 同源）；若后端返回 2xx 但未应用，替代行的 `r=` 会指向一个远端不存在的 label（该 label 的移除成为 no-op，中间 label 残留）——与既有 best-effort/2xx 边界的风险同级，未额外引入新证据通道。
- 已知上限（B2-1）：重定按账号 key 作用域、不受代际守卫阻断——若同一账号在同一库内经历「切换离开再切回」并在此期间重建了同 URL 意图，重定仍会按**上一次成功发送的目标**改写它的移除基准；该事实本身是账号作用域的真值，故接受（比按过期代际跳过更安全）。
- 已知代价（B2-R1）：`remote_id` 未知的退订意图（删除撞上在途 `quick_add`）恢复时会对该 URL 做一次幂等 `quick_add`，于是「在途创建其实没生效」的那部分场景会在远端**先创建再删除**（一次多余的建源+退订）。这是换取「不依赖任何列表一致性界、也不留孤儿」的代价；没有创建证据（无 pending 队项）的普通删除不走这条路径，代价只落在窄窗口。
- 已知上限（B2-R1）：解析不到目标（`quick_add` 失败且远端列表无同 URL 条目）时队项保留重试（attempts/last_error 可见）——这是重试语义而非缺席清队；远端始终不可达时行会一直等待，与其它写回意图的失败语义一致。
- 已知代价（B2-R2 复审 R2-2）：解析结果持久化 + 「发现未完成不发送」意味着**订阅列表长期不可用时退订也不发出**（意图保留、attempts 可见）——相比「先退掉已知的一个」，这是为了防止非幂等服务端上漏删与重复创建；`resolved_remote_id` 是 v25 纯追加列，旧行 NULL = 未解析。
- 已知上限（B2-R2 复审 R2-3/P3-A）：删除时的移除基准优先取被替换 pending 行的链起点、否则用本地当前分类名快照（信任远端与本地在该 label 上已一致）。若远端另有本应用不认识的同订阅标签，`r=` 只移除基准的那一个、其余标签不被触碰（与移动的既有语义一致）；重加时若退订其实已生效，`r=` 是不存在 label 的移除（no-op 假定）；被替换行的 `desired_folder`（remote_created 窗口）与链起点都可能与远端当下 label 有偏差，由发送成功的重定兜底、进程在重定前死亡时信息丢失（与 B1-R3 同级）。
- 已知上限（B2-R2 复审 P2-C）：400/404 容忍把「服务端删除失败」（FreshRSS 的 `deleteFeed` 返回 false 不区分原因）一并当作「目标已不存在」。若远端订阅实际仍在，队项仍会出队、墓碑继续挡本地复活——本地上是「已删除」、远端残留孤儿，直到用户重加（quick_add 幂等命中）或远端自行消失；判据是墓碑仍只由 pull 的列表确认回收，孤儿不会被本地重新导入。
- 已知上限（B2-R2 复审 P3-B）：重加替换 pending 退订行时不结转 `remote_id`/`resolved_remote_id`（退订是否已生效两义并存，盲转会把绑定指向已删除的远端 id）——只承诺幂等 official GReader 语义；非幂等服务端且**替换时退订尚未生效（远端同 URL 订阅仍在）**时会新建一个订阅（重复项随删除/重加次数线性）。
- 分类级操作没有可移植的远端端点：`rename-tag`/`disable-tag` 在固定上游里只有 FreshRSS 实现、其余后端无可核验支持，故分类改名/删除一律逐成员用 `a=`/`r=`/`unsubscribe` 表达；空分类只有本地语义（本地改名 + 墓碑），**不宣称远端已改**——B3 已按这条边界向用户展示（能力矩阵 `empty_folder_remote = Unsupported` + 概述/限制清单，见 [订阅写回能力矩阵与持久回执](2026-10-15-订阅写回能力矩阵与持久回执.md)）。

## Alternatives considered

### Why not 在 push_feeds 里原地扩展 legacy add_feed 流程，而是另建执行器？
`sync_queue` 的 add_feed 行没有账号指纹、payload 非类型化、且被「pending 保护」等既有回归直接断言（如「push 失败时 sync_queue 行保留」）。另建类型化 outbox + 执行器让新增能力可独立验证，legacy 行继续按旧语义消费，互不纠缠。

### Why not 移动时一次发两个 r=（链起点 + 新操作的 prev），让两种时序都覆盖？
GReader 的 `subscription/edit` 支持重复 `r` 参数，看似能同时覆盖「未发送链」（要移除链起点）与「已发送成功后的在途替换」（要移除已发送目标），且多移除一个不存在的 label 在多数后端是幂等 no-op。放弃：删除一个**不存在**的 label 是否恒为成功，在固定上游版本之间没有被本次可核验的证据一致证明（Miniflux 的分类成员删除按分类存在性走不同路径）；把「不存在的 label 必然 no-op」当成契约写入 wire 会制造一个无证据的假设面。改用「合并保留链起点 + 发送成功后由执行器重定」——只用既有单 `r` 形态，判定依据是执行器已掌握的事实（本轮发送成功）。

### Why not 合并时读本地 feeds 状态判断「上一次移动是否已发送」？
库里状态在两种时序下逐字相同（本地 folder 已改、队项的 desired/prev 相同），差别只在网络历史；本地读不出「HTTP 是否成功」。已发送的事实只有执行器在确认阶段持有，故重定必须放在执行器。

### Why not 绑定失败也 prune、靠 pull 重新绑定？
pull 只在远端列表出现该 URL 时绑定；分类挂载没有 pull 补偿，且 prune 后无法重试——「远端已创建」与「期望状态」之间的差距就永久丢失。保留 `remote_created` 行是唯一能表达「还欠一次绑定/挂载」的载体。

### Why not 用 UPDATE 合并编辑（保留 id）？
id 不复用是「旧 HTTP 成功不得确认新意图」的前提：响应在途期间入队的新编辑必须换新 id，旧确认才会落空。字段级合并（未给出的字段沿用旧行）与换新 id 并行，两个目标都保住。

### Why not Fever 的 command 层直接拒绝（B1 就返回结构化 Unsupported）？
命令层返回结构与 UI 呈现落点属于 B3（能力矩阵 `subscription_capabilities` 与持久回执，见 [订阅写回能力矩阵与持久回执](2026-10-15-订阅写回能力矩阵与持久回执.md)）；B1 先在执行器落 `local_only` 持久终态，保证既不重试也不冒充远端完成——数据层语义先于展示语义。
