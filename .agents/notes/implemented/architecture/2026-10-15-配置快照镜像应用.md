# Agent Note: 配置快照镜像应用

Status: implemented

## Problem

F18：配置同步一直是「手动快照传输 + 保守合并」——下载只做 upsert，删除收敛完全缺失。
由此产生的三方矛盾：

1. **本地已删除的对象在其它设备永远残留**：合并模式不删本地独有对象是安全默认，但用户
   需要一条「以远端快照为准」的显式路径（换机、回收误配置），否则只能逐个手删。
2. **朴素的「下载即覆盖（含删除）」不可接受**：删除会级联本地文章与读藏状态；直接执行
   等于把用户的真实数据交给一次未经确认的覆盖。而且配置同步与真实 RSS 账号是两件事
   ——镜像删除绝不能顺手变成远端退订（那会波及服务端订阅），也不能因级联误删与保留
   对象共享的正文。
3. **确认后并发变更**：用户看到「将删除源 X（含 3 篇文章）」再确认；若期间新增/编辑了
   源、文章新增或读藏翻转、又出现了未推送的写回意图，旧预览的删除集与数字已不代表
   现状。仅比对源数量不够——必须有一条可复核的签名。

同时（跨卡核对发现）：`ConfigSyncSection` 的确认文案「已存在的源会跳过；本地设置与
AI 配置将被远端覆盖」与后端行为矛盾——实际有 updated 计数、`ai_config` 在白名单外
（含模型/密钥的 AI 服务配置从不同步）。用户按错误预期确认删除/覆盖。

## Decision

**应用改为两段式：只读预览（plan）→ 用户确认 → 单事务复核签名后执行（apply）；合并
是安全默认，镜像必须经预览 + 单独确认。** 实现收口在 `config_sync/plan.rs`：

1. **两种模式**：`merge`（默认；只更新远端列出的对象，本地独有对象保留，行为与既有
   语义一致）与 `mirror`（以远端为准，删除本地多出的源与分类）。mode 进 wire 契约，
   前端下拉显式选择，换模式即作废旧预览。
2. **结构化预览**：`config_sync_plan(payload, mode)` 返回 additions / updates / removals
   （feed/folder；removal 带 affectedArticleCount，folder 另带 feedCount）、
   settingsChangedKeys / settingsRemovedKeys、pendingConnection、warnings。`affectedArticleCount`
   按被删源计一次，目录项只做展示归组，不重复计数。
3. **双签名 CAS**：`snapshotHash` = payload 规范化序列化后的指纹（替换快照即失效）；
   `currentVersion` = 本地配置状态签名。`config_sync_apply(payload, mode, expectedSnapshotHash,
   expectedVersion)` 在**单事务内**重算计划并复核两个签名，任一不符返回 `stalePreview`
   且零写入——失效预览只能重新预览确认，绝不重算后直接删。镜像缺签名直接 `validate`
   拒绝；`apply_payload`（库级兼容入口）保留 merge 免 CAS 路径给既有调用方/测试。
4. **版本签名覆盖「会改变删除后果」的本地状态**：全部分类（含 sync_id/位置/标志）与源
   （URL/标题/归属/布局/AI 模式/站点字段）、白名单 app_settings 投影、**被删源**的文章
   数/已读/收藏聚合、**被删源**相关的 pending 写回行。预览后新增/编辑源、被删源文章新增
   或读藏翻转、pending 意图出现 → 旧预览失效；与被删对象无关的源的抓取状态/新文章不
   参与 → 不制造无谓失效（变更范围是保守设计的：删除后果相关的一律纳入）。
5. **schema2 分类稳定身份**：`folders.sync_id`（v26 迁移回填 + 创建即分配）随快照携带；
   匹配优先级 = 身份 → 名称兜底（仅在双方其一没有身份时，且**只填空**——采用远端身份，
   绝不改写既有身份）。同名但双方身份不同 = 不同对象：预览显式列冲突（新增 + 镜像删除）
   并出 warning，绝不猜「相同名字就同对象」（跨重命名身份变化的正确处置）。schema1 快照
   无身份，按 URL（源）/名称（分类）保守匹配，继续可合并；**导入新建的分类在 INSERT 时
   一次落定身份**——远端有身份直接采用、无身份才随机分配（`create_folder_with_sync_id`），
   重放按身份命中、幂等。
6. **镜像删除的纪律**（"只删列出对象"的完整含义）：
   - 不调用 `enqueue_unsubscribe`：不产生远端退订 outbox；**既有** pending 写回意图
     一个字节不动（保留未推意图，预览在 warnings 里如实提醒）。
   - 不直接删 contents：条目级联由 FK 完成，「最后引用才回收」由既有触发器兜底——
     与保留对象共享的正文天然保活。
   - 先移动后删目录：匹配的源先更新归属（移动），再删未匹配源、最后删未匹配目录——
     目录删除时成员已清空，不误级联。
   - 被删源落 **feed 墓碑**（防 pull 复活）：这是「本地删除意图」，与远端退订是两件事
     （OPT-006 换号清墓碑、pull 远端确认后回收的既有判据不变）。分类不落墓碑：分类是
     服务端命名空间，重连后按服务端 label 正常导入是既定语义。
   - merge 的「导入」兜底目录保留（schema1 兼容）；**mirror 对源引用未知/空分类整体
     拒绝**（不引入本地兜底目录——否则「导入」会在镜像里被反复删除/重建）。
7. **设置与连接**：`app_settings` 白名单合并与增量（changed/removed 键）同源计算；连接
   信息仍只落 OPT-006 待确认建议（apply 才写，plan 只读并提示）——活动凭据永不被导入改写。

前端（`ConfigSyncSection`）：「下载预览」→ 只读预览卡（新增/更新/删除计数、关键对象与
文章数、界面设置键数、连接建议、warnings、镜像警示）→「确认应用 / 确认镜像应用」或
「取消」；取消 = 清除预览零写入；apply 失败（含 stalePreview）也清除预览并要求重新预览。
文案订正：同步的是分类/源的 AI 开关与界面设置，**含模型/密钥的 AI 服务配置不在同步
范围**；镜像明确「仅影响本机，不会退订服务端订阅」。

## Alternatives considered

### Why not 保留「下载即应用」（无预览直连）？

无法在删除前展示后果；也无法给「确认后并发变更」任何复核点。两段式预览是产品范围
（F18 要求删除收敛 + 确认展示数量/关键对象且能取消）的最小满足形态。

### Why not 只做快照 hash CAS（不含本地版本签名）？

hash 只绑定远端快照，管不住「预览后本地新增了源」——旧预览的删除集已经不含新源，
确认后新源会被静默保留（好的情况）或被新计划删掉（若 apply 重算）——两种都不是用户
确认过的后果。本地版本签名把「确认时看到的世界」与「执行时的世界」绑在一起，失配
即拒绝。

### Why not 版本签名覆盖全部源的全部文章聚合？

任何后台抓取（与被删对象无关）都会让预览失效，在 5 分钟刷新间隔下确认窗口变得不可用。
签名按删除后果作用域（只聚合被删源）是保守性与可用性的折衷；与被删对象无关的变化
不影响本次删除的正确性。

### Why not 让 apply 直接执行前端回传的 plan items？

前端可篡改、可与当前数据库失配（预览后本地变更），后端将被迫信任一份过期清单。
现在 apply 只收 payload+mode+两个签名，计划在任何时刻都由后端从同一事务读快照重算——
「所见即所执行」由签名相等保证，不靠客户端诚实。

### Why not 镜像删除同时写 unsubscribe outbox（把本地删除当远端退订）？

这正是产品边界：镜像只影响本机订阅/客户端设置；真实 RSS 账号的退订必须由 OPT-009 的
显式操作（逐条删除/分类删除的持久意图）另行确认。镜像 bulk 删除若推远端退订，一次
误操作就会把服务端订阅批量退掉。既有 pending 意图也不清理——那是用户先前的意图，
不属于本次镜像操作的范围（预览提醒其存在）。

### Why not 分类也用名称墓碑防复活（与手工删分类一致）？

镜像删除的分类是「配置快照里没有」的对象，不是「用户要对抗服务端 label」——重连后按
服务端导入是既定语义；而全局（空 key）分类墓碑没有回收路径，会给未连接用户留下永久的
副作用。源的墓碑不同：它是 pull 防复活与「重新添加才解除」的既有纪律，且换号会被清除，
语义已被 OPT-006/OPT-009 冻结。

### Why not 严格按身份匹配分类（不做名称兜底）？

名称兜底只在**双方其一没有身份**时生效：(a) 远端无身份（schema1 快照）→ 按名称命中、
本地身份原样保留；(b) 本地无身份（v26 之前的残留行/手工行）→ 按名称命中并采用远端身份
（只填空）。两台都已迁移（各自随机身份）的设备之间，名称兜底**不生效**：同名不同身份
即显式冲突（合并列出新增远端对象；镜像列出「新增远端对象 + 删除本地对象」并预警）——
不猜「同名即同对象」。冲突的收敛路径是「应用带身份快照后采用远端身份」（P0-1 修复后
新建与空身份采用两条路径都真实落库）；在此之前，导入侧根本不采用远端身份，重放会
反复落入冲突（r1 初审 P0-1 的缺陷，见该轮 RESULT-rework-r1）。不做「双方都有身份、
仅名称相同就合并」的另一个理由：那正是跨重命名身份变化时最危险的一猜——把两个实际
不同的对象并成一个。

### Why not 导入创建时先随机分配、再「只填空」采用远端身份？

首轮实现曾经如此，是 r1 阻断缺陷（P0-1）：`create_folder` 创建即写随机身份，
随后针对同一行的 `set_folder_sync_id`（谓词 `sync_id IS NULL OR trim=''`，为保护
既有本地身份而设）对刚创建的行**恒为 no-op**——远端身份永远落不了库，重放时远端 R
与本地随机 W 双方非空且不等，按冲突处理（合并每次 +1 重复目录；镜像每次删建往复）。
修复：新增 `create_folder_with_sync_id`，身份在 INSERT 时一次落定（远端有身份直接
采用、无身份才随机）；「只填空」谓词只保留给**匹配既有行**的采用路径，两条路径职责
分离。约束：导入永不改写本地既有非空身份——远端身份若已被本地其它对象占用，降级为
随机新身份并显式预警（身份唯一性纪律，绝不让两个对象共享同一身份）。

## Consequences

- 用户第一次能看到「将发生什么」再决定：合并/镜像分开，删除数量、关键对象、受影响
  文章数与界面设置键数全部如实展示；取消与预览本身零写入。
- 并发变更不再能造成「确认后静默删除未列出对象」：stalePreview 零写入是硬边界（已用
  退化实现复跑证明断言有判别力：常量签名下旧预览会删掉新源）。
- 镜像删除与远端退订彻底解耦：不产生 outbox、不清既有意图、不推远端；被删源由墓碑
  挡 pull 复活，重连同账号仍可正常导入服务端的其它订阅。
- 共享正文安全：镜像删除从不直接删 contents；与保留对象共享的行由「最后引用才回收」
  兜底（隔离库回归锁定：共享行保留、独占行回收）。
- 代价一：签名包含全部分类/源列表，任何源编辑都会使预览失效（重新预览即可，行为
  保守但安全）。代价二：v26 迁移为 folders 增加一列并回填（纯追加，旧库升级无损；
  物理回拨夹具已同步补 v26 回拨）。代价三：mirror 对未知分类引用整体拒绝，手工构造
  的畸形快照只能走合并——这是有意的（镜像禁止本地兜底目录）。
- 已知上限：被删源文章中「预览后新写入的 AI 产物」不单独使预览失效（文章数/读藏聚合
  已覆盖主要状态；LLM 迟到的产物会随级联删除消失，与直接删源同级）。镜像不做「预览
  里的对象在 apply 时已不存在」的宽容处理——它们随签名复核一起失效（保守）。版本签名
  与文章聚合的 `IN (...)` 列表一次性绑定被删源集合（r1 复审 P3-4 登记）：源数超过
  SQLite 变量上限（bundled 默认 32766）时整条 plan/apply 报错——方向 fail-safe
  （报错零写入），个人规模不可达；outbox 查询已按 200 分块，此二处未分块。
- 已知边界（r2 复审 P3-1 登记）：**自相矛盾的混合快照不收敛**——同一身份既被无身份
  槽位按名称占用、又被另一槽位声称时，占用护栏每次把被降级对象列为新增（merge 每轮
  重放 +1 空分类；镜像每轮删旧建新）。唯一性优先于收敛是刻意取舍：宁可多出用户可见、
  可手动清理的空对象，也不让两个对象共享同一 sync_id（共享会把一次数据异常拖成持续
  的匹配错乱）。过程不静默——新增/删除与「身份已被本地其它对象占用」预警每次都在
  预览里列出、需用户确认；该输入形态只有手工/损坏数据可达（`build_payload` 产物不
  携带空身份槽位，v26 回填后无 NULL 身份行）。行为已由
  `import_never_reuses_identity_taken_by_another_local_object` 的重放断言钉住
  （第二次 plan 仍按契约列出新增 + 预警）。
- 已知边界（r2 复审 P2-1 修复）：Match 空身份采用路径与 New 分支同口径做**全局占用
  检查**——命中占用不采用（本地行保持空身份）+ 预警；全库非空 sync_id 唯一性在两条
  导入路径上都成立（各有专项回归）。
