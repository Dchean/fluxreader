# Agent Note: 订阅条目与共享内容身份

Status: implemented

## Problem

当前全局 URL→文章映射先于远端 entry ID，跨源同 URL 被吞成一个条目或 CSV 副本。丢失的 feed/remote ID 所有权导致分类与五布局不可达、收藏互相覆盖；直接抓取 smartDedup 也在入库前丢弃副本。只修 URL 规范化不能恢复这类身份，正文缓存又不能继续把同文与同条目混为一谈。

## Decision

保留技术栈和外部条目 ID，把订阅条目与内容分成两个连续、可验收的阶段。

第一阶段先确保身份不丢：协议 entry ID 优先，URL 兜底限制在同源，跨源各有持久条目；读广播显式选择同文条目，不让读/藏状态因共用一行而隐式传播。smartDedup 只影响可见集合，不删除条目身份，其列表/计数/分页/批量操作必须使用一致的集合规则。其他布局/源内仍可访问自身条目。旧正文列暂时保留，避免一次不可检查的大迁移；这一中间状态不冒充已共享正文。

第二阶段追加内容实体与引用，实际正文读写、全文和 AI 产物以单一内容所有权收口。URL 只作为候选关系，不用它无条件覆盖不同源的正文或付费 AI 产物；共享策略需要明确内容等价性、修改后分叉/修订和缓存失效。条目 own feed、guid/remote ID、读藏、版本、队列独立保留。最终不得留下两个长期正文真值或只有新表无人消费的接口。

历史已丢弃的副本只能由真实远端重拉恢复；旧 CSV 缺 feed/正文，不能据其猜建完整行。兼容期间不清掉待推用户意图，恢复后精确绑定与队列目标必须可追溯。

## Alternatives considered

### 仅增加 remote_dup_ids 的字段或扩大 URL 映射

改动小，能够继续广播远端 read，但仍无法独立表示副本 feed、收藏和列表可达性；没有解决本卡实际身份丢失问题。

### 一次替换所有表、IPC与前端缓存

可直接得到统一模型，但迁移、同步与渲染一起变动很难定位回归。分两阶段保留可运行中间态，第二阶段仍承担完整内容分离目标，不以第一阶段通过替代最终验收。

### 所有跨源 URL 相同就共用同一份可变正文

存储节省明显，但不同源可能是摘要、全文或更新版本，URL等同不能证明内容等同。内容共享必须有独立安全规则，不能让一个源的抓取反向覆盖另一个源的正文/AI。

## Consequences

- 两协议、直连抓取的同 URL 跨源条目都可达，各自 remote ID 和收藏独立；read广播与撤销读范围明确，版本/队列仍原子。
- smartDedup 开关不永久丢条目，列表/计数/搜索/keyset分页/批量操作集合一致，五布局和单源可达不回退。
- 历史升级保住 ID、状态、队列、正文与 AI；失败回滚，可重新打开继续；不造缺资料的旧副本。
- 最终 contents 被所有真实正文读写消费者使用，删除/断开不删别的条目仍引用的内容，修订后缓存不串。
- 每阶段本地门禁、独立初审与主控复审；迁移和跨模块风险有真实生产API/隔离库测试，提交级 Windows CI 承担生产平台验证。

## Risks

模型改动可能改变聚合数量、排序、读广播与缓存刷新。两个阶段均要显式描述中间态与未完成部分；阶段一不把新结构标implemented，最终落地后再转换Note状态并更新相关原Note事实。未知真实服务端历史不使用用户账户作破坏性试验。

## 第二阶段契约（已落地）

以下为 008B 第二阶段经主控授权的最终方案（细化既有决定，不另立提案）：

**1. 存储与迁移（只追加迁移 v22，不改旧迁移）**
- 新表 `contents(id INTEGER PRIMARY KEY AUTOINCREMENT, identity TEXT NOT NULL UNIQUE, url_norm TEXT, content_html TEXT, body_text TEXT NOT NULL DEFAULT '', extraction_source TEXT NOT NULL DEFAULT 'rss', fulltext_extracted INTEGER NOT NULL DEFAULT 0, revision INTEGER NOT NULL DEFAULT 1, created_at TEXT, updated_at TEXT)`。**R3：id 为 AUTOINCREMENT**——普通 rowid 在删除表内最大行后会复用 id，前端以 `(content_id, revision)` 判定正文失效，复用会在「删除+重建恰好同快照窗口」读到同值对；AUTOINCREMENT 借 sqlite_sequence 保证删除最大内容后新内容取更大 id（新建库与 v21 迁移库各有一条隔离回归：`contents_ids_are_not_reused_after_max_delete_and_after_migration`）。
- `articles` 追加 `content_id INTEGER REFERENCES contents(id)` 与 `ai_epoch INTEGER NOT NULL DEFAULT 0`；**删除旧列 `content_html/body_text/fulltext_extracted`**（先删 FTS 触发器/旧外部内容表再 DROP COLUMN；这消除「两套正文真值」，不做兼容列、不做双向触发器）。全部读写走 contents。
- 回填（迁移事务内）：按 identity 归并现有行——identity 规则见 §2；空内容行按条目独立 identity（`e|<article_id>`）；设置 `articles.content_id`。
- FTS 改为**独立（非 external-content）派生表** `articles_fts(title, body_text, author, ai_summary, translated_content)`，由迁移创建的触发器维护（`trg_articles_fts_ai/ad/au` + `trg_contents_fts_au`：入库/条目级字段或 content_id 变化/共享内容变化/AI 写/清理/删除都保持**每个引用条目**的索引行正确），并提供全量重建入口 `rebuild_fts`（迁移内调用一次）。FTS 是可重建索引，不再是正文权威；生产搜索入口保持 LIKE（中文分词原因，见 articles.rs 决策注释），FTS 承担派生索引的维护与可重建契约。**（OPT-017B v29 已把该表与四个触发器整体删除——它是零 MATCH 消费者的纯写放大；`rebuild_fts` 仅保留为不可改 v22 迁移的实现细节，见文末「OPT-017B 追加」。本节其它事实仍按 v22 当时现场有效。）**
- 迁移单事务整体回滚；中途失败（含回填后 DROP COLUMN 失败）→ 版本与数据原样、重开可重试；不改动旧条目 ID/feed/guid/remote 身份/读藏/队列/正文/AI。

**2. 内容身份与等价共享（URL 只是候选）**
- `identity = 'h|' + md5(extraction_source + 0x1f + sanitized_html + 0x1f + body_text) + '|<html_len>|<body_len>'`（任意正文非空时）。md5 在此是**内容等价指纹**而非安全原语（md-5 本就是既有依赖）；哈希命中后**必须再做字节级复核**（html/body/source 全等）才复用——碰撞退化为加盐新行，绝不误并。`extraction_source` 进 identity → RSS 原文与 Readability 提取、不同 HTML/纯文各自成行（确定分叉边界）。
- 空 URL/空正文（html 与 text 皆空）→ identity = `'e|' + article_id`：条目私有不聚合，不误并无关条目。
- 同 URL 不同 HTML/纯文/提取来源 → identity 不同 → 不共享（反例锁定）；内容真正等价（同来源同字节）→ 共享同一 contents 行（跨源同文聚合即目标路径，不再一 entry 一行）。
- contents.url_norm 仅作展示/参考（首次写入值）；不放 identity（URL 不参与等价判定）。条目 title/author/summary/AI 产物**保持条目级**（依赖标题的 AI 不因正文同一共用产物——见 §4 输入键）。

**3. 修订与分叉**
- `contents.revision` 单调递增：内容被真实替换时 +1。
- RSS 刷新保护上移：contents 上已有 `fulltext_extracted=1`（提取来源）时，RSS 刷新**不得**覆盖它；条目刷新只更新条目级字段与 content_id 指向（若 RSS 内容等价同一行则复用）。
- 条目级全文提取 = 「确保存在 (readability, 提取后内容) 的 contents 行（无则创建，有则复用）→ 条目重指新行」；若旧行仍有其他引用则保持（**单引用修订分叉**），最后引用消失时回收。
- **重指即回收无引用旧行**：条目重指新内容（refresh / 全文提交 / 回填）时，旧行 `NOT EXISTS` 其它引用即删除——「最后引用才回收」不因重指路径留下孤儿行（条目删除的触发器兜底不变）。
- **R3 故障原子性**：`ensure_content` 的 INSERT 与随后的条目重指/回填是复合写，三条路径（新条目插入 `insert_new_article`、RSS 刷新重指、提取提交 `replace_article_content_checked`）及回填重指都用 `contents::with_write_savepoint` 包住整组语句（SAVEPOINT 可嵌套于 sync 调用方的既有事务）：任一步失败整体回滚，不留「已 INSERT 的 contents 行无任何引用」（孤儿只能由同身份复用吸收、无清理入口）或「条目已插但 content_id 未回填、FTS 正文为空」的半提交态；清障后同一前提可直接重试（故障注入 RAISE(ABORT) 回归三条：refresh/insert/extract）。
- **R3 历史异常 Readability 保护**：回填（`backfill_article_content`）对当前指向的**受保护提取行**（readability + fulltext_extracted）不做 RSS 合成——就地把异常 body 按保留 HTML 同源重算（`revision+1`，来源/标志保持 readability）。修前「html 非空但 body 缺失」的历史形态会合成 `(提取 HTML, RSS 纯文本)` 的 rss 源新行并丢 fulltext_extracted（常规提取被防退化拦截，仅该形态可达）。
- 内容替换（同 identity 行被新内容取代只可能因同 identity；实际替换经新 identity 分叉，除提取原位更新场景）按 revision+1 暴露给所有引用条目（前端失效依据见 §7）。
- 013 复用接口：内容版本 = `(contents.id, contents.revision)`；提交前提校验 `expected (content_id, revision) + 清除代次`；013 只扩展生成签名/分段恢复，不另造版本体系。

**4. 异步写与提交守卫（网络期间不持 DB 锁）**
- 全文提取：发起前读 `(content_id, revision, html)`；网络后提交 `replace_content_checked(article_id, expected_content_id, expected_revision, new_html)`——事务内校验 articles.content_id 未变、contents.revision 未变、行未被清除；不符则拒绝（迟到不得写到已删除/分叉/替换行）。提交成功 → 新/复用 readability 行 + 条目重指 + FTS 更新；拒绝时命令层如实返回 degraded（"内容在提取期间已更新"），不冒充成功。网络在途窗口由真实 loopback mock 断言「DB 锁可获取」。**R3 wire**：`ExtractOutcome` 成功时新增 `contentId`/`contentRevision`（提交后的实际身份，serde camelCase；降级为 null/0）——前端 `applyExtractedFulltext` 以此落 bodyCache 记录，下一次 reload 对值相等，不会把刚成功提取的正文按「修订变化」清空重取；旧后端/降级缺省时前端保持记录现值（行为不变）。
- AI（条目级产物）：发起前读 `(ai_epoch, content_id, revision)`；网络后提交 `set_ai_checked(article_id, expected_ai_epoch, expected_content_id, expected_revision, ...)`——清理（cleanup_cache ai 分支）使 `articles.ai_epoch+1`；内容被替换/条目重指 → revision/content_id 校验失败 → 拒绝落旧产物（不复活已清除产物、不写已替换内容；命令层返回明确 aiStale 错误，不发 Done 假成功）。
- AI 输入键：摘要输入 = `(title, contents.body_text)`；翻译输入 = `(title, contents.content_html, target_lang)`；产物仍存条目行（标题不同 → 输入键不同 → 产物不共享；013 的一致性签名在其上扩展）。

**5. 引用生命周期（最后引用才回收）**
- `AFTER DELETE ON articles` 触发器：删除无引用的 contents（`NOT EXISTS(SELECT 1 FROM articles WHERE content_id=old.id)`），并清 FTS 行。**OPT-017B v29 起为独立命名的 `trg_articles_recycle_ad`（只做回收，不再顺带清 FTS——FTS 已删除）**。
- 源删除/分类级联/账号断开（purge_remote_data）→ 条目级联删除 → 上述回收自然生效；共享 contents 被其他引用保活。**R3**：delete_folder 级联与 purge_remote_data 各有一条「删一个引用仍保活、删最后引用回收」的隔离回归（`contents_ownership_e2e`），不再只靠触发器路径静态推导。
- `cleanup_cache('articles')` 删老条目 → 回收同上；`cleanup_cache('ai')` 只清**条目行** AI 字段（按原年龄范围，天然不误清年轻兄弟；被清条目 `ai_epoch+1` 使迟到 AI 提交被拒），回执数量与实际一致。

**6. 实际消费者（全部走 contents）**
- 列表：snippet = `COALESCE(NULLIF(a.summary,''), substr(c.body_text,1,280))`；`with_content` 时 `content_html` 来自 c；`fulltext_extracted` 来自 c；`ai_summary/translated_content` 仍在 a。
- 详情/批量水合(`get_article(s)`)、LIKE 搜索（a.title/summary/ai/translated + c.body_text；生产搜索入口保持 LIKE，中文分词原因见 articles.rs 决策注释）、分页/keyset/计数/定位（谓词不变，snippet 走 JOIN）、全文/AI 输入输出、入库与回填（sync_map/entries/push/conflict_policy/ingestion/staged/scheduler）全部经 contents。
- FTS 维护点：入库新行、RSS 刷新变更条目字段、内容变更（对**每个引用条目**重建其 FTS 行）、AI 写、清理、删除；提供 `rebuild_fts`（迁移与维护路径消费）。共享变更 → 所有引用条目都可搜到（不只代表），源内可达性不丢。**OPT-017B v29 起维护面换成 `articles_trigram_idx` 候选索引的四个触发器（`trg_articles_trigram_ai/ad/au` + `trg_contents_trigram_au`），语义契约「共享变更 → 每个引用条目可搜」不变。**

**7. 前端失效消费**
- 行数据新增 `content_id/content_revision`（列表/详情同源 JOIN 出），前端条目模型带 `contentId/contentRevision`；bodyCache 记录保存二者。后端快照落地（mergeSnapshotEntries 的 fromBackend 路径）逐行比对 (contentId, revision)：不等即 `invalidateContentRevision` 置 cleared、清正文并 bump 显式失效计数——snippet 未变但正文后半变更（revision 变）→ 失效重取；共享兄弟内容变更同理（同 contentId 新 revision，每个引用条目都失效）。在途旧详情/水合响应按 stamp 比对整体丢弃（请求代次保护不退化）。
- **R3 条目身份锚**：记录水合时写入 `entryAnchor = feedId|title`；既有条目对值未变也查锚——同 id 条目「快照缺失后重新出现/删除重建」且 (contentId, revision) 巧合相等（文章删除重建复用 rowid）时锚不符即失效清空，不继续旧正文；锚相等（同一条目返回窗口）不误失效。仅对持有真实内容身份（contentId 非 null）的记录启用；内容 id 复用一侧由 AUTOINCREMENT 关闭。
- cleared 的两种形态：AI 产物被清理（正文保留）不触发重取；**正文修订失效（content 已清空）**由 `entryNeedsHydration`（cleared 且 content 为空）与 reader.ts 的 cleared 重入队路径共同按需重取——懒水合卡片不因失效停在空正文。**R3 Reader 自愈**：Reader 对 activeArticleId 的「cleared 且正文空」加幂等 `ensureArticleContent` 观察——重水合不依赖被虚拟化移出挂载窗的卡片（否则打开中的文章停在空正文直到用户交互）；cleared→loading 的重入队由 `markBodyLoading` **保留显式失效计数**（不归零），失效前发出的旧戳在途响应落地时仍被丢弃（真实组件回归 `reader-revision-recovery.test.mjs`：不挂 Timeline、无卡片的自动恢复 + 在途旧响应丢弃后新响应落地）。
- Reader 安全渲染与五布局键保持：`selectArticleBody` 订阅 useShallow 约定不变，视图行不携带正文（正文只经水合链路落 bodyById）。**R3 五布局回归**：五布局各条目引用同一 contents 行，revision 推进后逐布局失效清空、真实重水合落地、Reader 实际渲染新修订（social 另证同窗口兄弟条目与卡片 DOM），见 `revision-shared-layouts.test.mjs`。

**8. 迁移与旧 AI 共存**：正文迁移不改 AI 行；旧 AI 产物保留在条目行（不丢）；新内容版本到来时按 §4 守卫使**仅**受影响产物的后续迟到写被拒——「保留旧 AI」与「新版本失效」共存：保留=不主动清除存量，失效=不允许新写入落到旧身份上（前端按 revision 重取输入后由用户/自动流程重新生成）。

验收映射：卡末尾五项必测（迁移无损/回滚重试、等价共享与分叉、删除与最后引用、snippet 相同后半变更、FTS 每源可达、异步迟到拒绝、五布局独立）全部进回归；使用隔离库与本地 HTTP 夹具。

## OPT-017B 追加（2026-10-16）：删除零消费 FTS，改 trigram 候选索引

**决定**（追加迁移 v29，不改历史迁移）：
- 删除 `articles_fts` 及 `trg_articles_fts_ai/ad/au`、`trg_contents_fts_au`。该表自 REQ-104/SRH-2 起没有任何 MATCH 消费者（生产搜索是 LIKE），只由触发器维护——纯写放大 + 磁盘占用，且 v3 的宽 UPDATE 触发器历史上曾对未入索引行做 FTS 'delete' 触发 `database disk image is malformed`（v14 注释）。
- contents 生命周期回收改独立触发器 `trg_articles_recycle_ad`（语义逐字保留：最后引用消失才删行）；`rebuild_fts` 仅为不可改 v22 迁移的回填细节保留，运行时不消费。
- 新增**候选索引** `articles_trigram_idx`（FTS5 trigram、`detail=none`、`content='' + contentless_delete=1`，迁移回填 + 四触发器维护：入库/条目列变更/content_id 变更/共享正文变更）。`search_articles` 对 ≥3 字符词加 `a.id IN (SELECT rowid ... MATCH '…' AND …)` 候选（AND-of-trigrams = 包含全部三元组的**超集**），结果仍由既有 LIKE 逐行验证；词 <3 字符（2 字中文等）、索引对象缺失或 MATCH 报错时回落纯 LIKE。候选存在时 `INDEXED BY idx_articles_published_id` 固定上表访问路径（防止规划器反转为 FTS 驱动半连接 + 临时排序，丢掉排序索引的 LIMIT 提前停止）。
- 等值契约：候选只收缩不判定——id 集合/顺序/去重/字段/转义/AI 字段命中与实现前逐字等值（冻结 LIKE 参考实现矩阵回归 + v27/v28 含数据升级等值回归；含 2 字回落与索引缺失/损坏回落两组）。

**Alternatives considered**：
- ①只删 FTS 不加候选索引：同构建 50k×8KiB 的 LIKE-only db 层中位 779/846ms，处于判定线（端到端 >1000ms）压线区间，且 017A 记录 1161/1345ms 已超线；未选。
- ②保留 unicode61 FTS 并启用 MATCH：分词对中文形同虚设（整段一个 token），且 FTS 语法转义反直觉；未选。
- ③`detail=full`（存位置）或保留正文副本的 trigram：体积与写成本倍数上升——合成语料探针中，保留正文副本（默认 content）的索引体积为 contentless 版的约 41 倍（正文副本占绝对多数），`detail=full` 又比 `detail=none` 大约 60%；未选。
- ④自定义 n-gram 表：SQL 触发器无法生成 n-gram，维护面必须侵入所有写路径；未选。

**测量与边界**：数字、语料与未测边界见 docs/performance.md「搜索与 FTS 写放大处置对照（OPT-017B）」；同语料触发/参考实现回归在 `db/articles.rs`、`db/migrations.rs` 的 opt017b 测试模块。合成语料高重复（contents 去重后 17 行正文），索引体积/写成本不可外推自然语料。

## OPT-017G 追加（2026-10-16）：读闭包部分索引

**决定**（追加迁移 v30，不改历史迁移）：新增部分索引 `idx_articles_url_norm_unread ON articles(url_norm) WHERE is_read = 0`，支撑读闭包查询（`read_targets_with_state`：同 `url_norm` 未读兄弟行、`ORDER BY id`）的计划——`url_norm` 等值前缀 + `id`（rowid 隐式）覆盖 + 免排序。读闭包查询文本、写路径与语义**零改动**；`idx_articles_unread` 保留（mark_all_read 的 UPDATE 计划消费，v14 注释）。

- 背景：修复前该查询规划为 `SEARCH articles USING INDEX idx_articles_unread (is_read=?)`——逐条扫描全部未读行并回表过滤 `url_norm`，批量标读把一次用户动作放大为 O(未读行数)/条（50k×8KiB 同构建实测闭包 ≈24–60ms/条，占 set_read_bulk 单条成本 99% 以上）。按 OPT-017B 范围外发现复现取证（EXPLAIN 原文 + per-item 拆分 + 候选对照落盘）后按证据实现。
- 等值契约：索引存在与否不改变闭包集合/回执行/逐行状态（read/read_version/star）/队列/计数（双库逐字等值回归 `opt017g_read_closure_tests`）；索引缺失自动回落旧计划（只慢不变义）；迁移在含数据 v29 旧库上幂等（`opt017g_migration_tests`）。
- **Alternatives considered**：①`(url_norm, id)` 部分索引——计划/耗时等价而体积更大（50k 1.65MB vs 1.53MB；20k 0.67 vs 0.55MB），未选；②非部分 `(url_norm, id)`（2.45MB/50k）——无 ANALYZE 统计时规划器**不选它**（仍是旧全未读扫描计划），不能消除慢路径，未选；③`INDEXED BY idx_articles_url_norm` 查询改写——闭包同样快（≈0.002–0.005ms/条）但索引缺失时直接报错（丢失回落），未选。
- **测量与边界**：数字、轮次与未测项见 docs/performance.md「读闭包查询规划与批量标读成本（OPT-017G）」；同构建 A/B 对照 50k×8KiB 1000 条标读中位 736.20ms（索引在场）vs 65772.05ms（删索引），20k 为 237.75 vs 24981.10ms。合成语料 `url_norm` 每篇唯一（闭包命中恒 0 行），多行传播的写入成本未在大库放大测量；同计划存在 ≈2.4× 的机器状态漂移，绝对值引用须带轮次与同运行 A/B。
