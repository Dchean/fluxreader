# Agent Note: 刷新编排、代际写回与源名分域

Status: implemented

## Problem

直连抓取此前有三个互相放大的缺口：

1. 每次全刷各自创建 `Semaphore(fetchConcurrency)`。托盘、手动与后台调度可以同时进入，单个入口的有界并发在入口叠加后失效；同一源也能被并发抓取，旧请求晚完成时会覆盖新 ETag、失败状态与文章。
2. `feeds.title` 同时承担「源站抓取标题」和「用户自定义标题」。编辑源写入同一列，刷新又对非空抓取标题执行 `COALESCE(?1, title)`，下一次刷新会覆盖用户改名。
3. hybrid/跟随服务端的实际全刷排除 `origin='remote'`，但调度器注释、托盘与前端入口仍写「全部」，用户看到的范围与真实行为相反。

## Decision

### 一、全刷 single-flight + 共享批次闸门

- `scheduler::refresh_all` 以数据库身份为键维护一个进程级在途 flight。领跑者执行批次；并发的后到调用订阅同一结果，不再各建信号量或重复抓取。
- flight 的发布与移除由后台任务自身持有，并用 RAII 守卫覆盖正常完成、错误、panic 与 future 取消。调用方 future 被取消不会留下无人清理的 flight；watch 通道传递可失败的批次结果，查询失败与任务异常不会再伪装成 `(0, 0)` 成功。
- 手动全刷、托盘全刷与调度器到期批共享同一数据库级异步闸门。不同批次类型不互相冒充结果：到期批仍只抓 due，manual 仍按自己的源集合执行；后到批次等待前者结束，不并发叠加。
- 每个批次区分三种结果：`Applied`（真正写回）、`SkippedInFlight`（同源已有请求在途）与 `Superseded`（写回前代际已被更新轮次取代）。只有 `Applied` 把规范化 feed URL 记入数据库级 90 秒 footprint；在途跳过、代际取代与失败都不记账，失败源在下一批仍可重试。
- footprint 键是规范化 feed URL，不是 SQLite rowid：删除最大 id 后新增源可能复用同一 rowid，不得因此继承旧源的“刚刷新”状态。footprint 仍是进程内、`Weak` 数据库身份。
- 手动/托盘全刷是用户的显式刷新请求，批次以 `force=true` **绕过 footprint**；每次顺序 manual 都会重新抓取，只有并发 manual 复用同一 full-refresh flight。调度 due 批是自动入口，仍读取 footprint 去重，所以 due→manual 可以再抓一次，但不是静默 0；manual→紧随 due 在成功 footprint 窗口内不会重抓。两种入口的语义明确为“显式刷新强制、调度自动去重”。
- 批次内仍使用 `fetchConcurrency` 上限。该设置现在约束整个数据库同时进行的直连请求，而不是每个入口各一份。

### 二、按源在途去重

- `ingestion::refresh_feed_staged` 在进入三段式管线前认领 `(数据库身份, 规范化 feed URL)`；同 URL 的已有请求在途时，后到请求返回 `SkippedInFlight`（`new_articles=0`），由首轮完成写库与既有事件。
- 在途键不能用 SQLite rowid：删除最大 id 后新源可能复用同一 id，旧 URL 的在途请求不能因此阻塞新 URL。写回除 `fetch_generation` 外还核对 `feed_url`，避免新行从同一 generation 数值重新开始时，旧请求把数据写进复用行。
- 认领用 RAII 守卫在正常完成、错误与 future 取消/panic 展开时释放，不把源永久卡在「在途」。
- 该去重只覆盖**同时并发、选择同一 feed** 的调用；它不是跨批次的永久缓存。跨批次自动去重由上一节的 90 秒 Applied footprint 承担，手动显式全刷刻意绕过它；失败、在途跳过与代际取代都不进入 footprint。

### 三、抓取代际 CAS

- v34 给 `feeds` 增加 `fetch_generation`。每轮开始前在同一事务内自增并读取 URL/条件头快照。
- 304、成功 Body 与失败写回都先执行
  `WHERE id=? AND fetch_generation=?`，并复核发起时 feed_url，避免 rowid 复用时旧 URL 回写。命中 0 行即本轮已被更新的一轮取代：不得写 ETag、`last_fetched_at`、失败退避、标题或文章。
- 成功 Body 的状态、标题/图标与文章 upsert 仍在同一事务；CAS 是事务内第一条写，命中后持写锁到 commit。

### 四、抓取标题与用户标题分域

- `fetched_title` 只存源站/远端提供的标题；`title_custom` 只存显式用户/配置标题；`title` 保留为显示缓存，继续兼容既有读取方。
- 刷新只更新 `fetched_title`；`title` 在有 `title_custom` 时保持自定义值，否则跟随抓取标题。
- v34 迁移用旧 `title` 回填 `fetched_title`，`title_custom=NULL` 表示「旧库未知」。新插入的已知无自定义行写空串。旧行首次刷新时若抓取标题改变，就把旧 title 固化为自定义（宁可暂时冻结一个自动标题，也不吞掉无法反证的历史改名）；标题未变则把 NULL 收敛为空串。唯一例外是旧 `title == feed_url`：URL 是导入解析器的缺省兜底而非用户改名，因此不固化，首次刷新直接跟随 `fetched_title`。
- 添加表单、OPML 与配置导入只有在标题去空白后非空且不等于 `feed_url` 时才写自定义标题；空标题与 URL 兜底始终留在抓取标题域。配置更新对空标题/URL 不清空既有 `title_custom`，也不把它计入每次 `updated`。
- 不提供「恢复跟随源标题」的 UI 入口：当前编辑源名即写自定义标题，把名称改回自动抓取值也不会清除 `title_custom`。这是已知限制；需要恢复跟随时只能直接修正数据或等待后续专门入口。
- v34 插入触发器用旧列回填新列，保证旧二进制仍能插入/回滚；但旧二进制的插入标题无法区分用户改名与抓取标题，后续刷新仍可能覆盖。回拨脚本同步删除新列与触发器，迁移测试继续覆盖物理回退。

### 五、hybrid 的“全刷”改为“刷新本地订阅源”

- 代码、调度器/数据库注释、命令面板、右键菜单和托盘文案统一按当前 `syncMode` 表达：direct 是「刷新全部订阅源」，hybrid 是「刷新本地订阅源」。
- hybrid 全刷与到期批都排除 `origin='remote'`（保留 local 及非 remote 的其它本地来源），避免直接抓服务端来源造成 direct/remote 重复文章；direct 仍包含全部来源。前端右键菜单、命令面板在 `settings.syncMode` 变化时实时重渲染；托盘在设置命令与配置同步应用成功后计算新文案。托盘原生 `MenuItem::set_text` 的生产分支未在本机自动化或实机验证，测试只通过注入 hook 验证“读取 syncMode → 计算菜单文案 → 调用写入点”的调度逻辑，不能宣称原生菜单渲染已验证。
- 刷新结果仍通过既有 `feeds-updated` 事件返回，不改变同步队列、时间身份或授权边界。

## Alternatives considered

### 只在每个全刷入口内保留 Semaphore

这是修前现状：单个入口有界，入口之间无界。并发点击两次仍会产生两份 `fetchConcurrency` 请求，且同源写回仍靠最后完成者，无法满足「不叠加」。因此增加跨入口 flight/闸门，而不是继续调低每入口并发。

### 重复刷新排队后重新抓取

排队能避免并发，但用户连续点击若每次都串行重抓，会放大站点压力且没有新信息。并发 manual 因此复用同一 flight；批次完成后的下一次 manual 是新的显式请求，允许重新抓取。自动 due 批才用 90 秒 Applied footprint 跳过刚成功的源，避免“到期批刚完成、下一 tick 又抓”。把手动也纳入 footprint 会让用户点击刷新却静默得到 0 次请求，语义不可接受。

### 只用进程内互斥，不落 generation

单进程在途表能挡住当前路径，但写回与 HTTP 完成之间仍有竞态窗口，且未来的跨进程/恢复路径不能依赖内存锁。把代际落到数据库并让每个写回 CAS，正确性不依赖调度器是否先挡住了重复请求。

### 只给 title 加「是否自定义」布尔标记

布尔标记仍无法解决旧库回填：迁移时不知道当前 title 是抓取名还是用户改名。文本 `title_custom` + `fetched_title` 让显示值直接可推导；旧行的 NULL 哨兵再配合首次刷新保守固化，避免把无法反证的用户改名当自动标题覆盖。

### 用 UPDATE 触发器兼容旧二进制的改名

旧二进制的刷新路径同样执行 `UPDATE feeds SET title=...`，与用户编辑共用同一列。若用 UPDATE 触发器把该写入解释为自定义标题，就会把每次抓取标题都误标成用户改名，反而冻结标题。因此只保留插入触发器兼容旧二进制新增源；**明确不支持旧二进制的改名语义**。升级后旧客户端写入的标题可能在下一次新客户端刷新时被抓取标题覆盖。

### hybrid 全刷强制包含远端源

能让「全部」字面成立，但服务端来源与直连抓取的 guid/正文/状态是两套真相，会产生重复文章与未读不一致。保持 hybrid 排除服务端来源，并把所有入口与注释改成真实语义；direct 用户仍可抓全部来源。

## Consequences

- 收益：共享批次覆盖的并发 manual 不再各自放大连接数；自动 due 批不会在短窗口重复抓刚成功的源；显式 manual 不会静默跳过；只有真正 Applied 的源才去重；查询失败/后台任务 panic 可见且 flight 可恢复；旧请求不能回写新状态；用户改名有持久身份；hybrid 行为与文案一致。
- 代价：v34 增加三列与一个插入触发器；每次抓取开始多一次短事务（自增代际）；旧库中无法反推的历史标题在首次出现不同抓取标题时会被保守保留为自定义，可能暂时冻结自动更新；成功 footprint 是 90 秒进程内状态，重启后不保留；显式连续 manual 会按用户意图重新抓取。
- 边界：在途集合与成功 footprint 都是进程内的；跨进程仍由数据库代际 CAS 保证旧结果不能覆盖。旧二进制可插入/回滚，但不支持改名，插入标题也不保证被当作自定义；空标题/URL 兜底不会成为自定义；没有清除自定义标题以恢复跟随的 UI。托盘原生 set_text 仅验证调度副作用，未实机验收。刷新不改变同步队列与事件契约。
- 测试：`refresh_coordination_e2e` 锁定发生 due→manual 时 manual 显式重抓、manual→due 自动去重、并发 manual 复用 flight、在途跳过/失败后可重试、rowid 复用不继承 URL footprint 且旧 URL 在途时新 URL 仍可刷新、调用方取消与后台 panic 后 flight 回收、查询失败上抛、批内并发上限、hybrid/direct 源集合、迟到代际与标题保护；`config_sync_e2e` 锁定空/URL 标题不覆盖既有自定义且重复应用幂等；`context-menu` 真实挂载锁定右键菜单与命令面板随 `syncMode` 更新；`config_sync` 单测通过注入 hook 锁定配置应用后托盘文案调度路径；`staged_refresh_e2e` 锁定三段式/304/事务回滚；迁移单测锁定 v34 回填与旧插入触发器；`contents_ownership_e2e`/`url_identity_e2e` 锁定 v34 物理回拨。
