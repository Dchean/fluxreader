# Agent Note: 同步会话复用、独立请求有界并发与窗口聚焦同步

Status: implemented

## Problem

审计修复路线 W3 卡（[路线与派发纪律](../process/2026-11-01-审计修复路线与子代理派发纪律.md)）
点名的三个同步即时性/速度瓶颈，各自有结构性成因：

1. **逐轮重认证**：`build_session` 在每次同步、每次即时推送、每次订阅写回都被
   调用，每次都做 GR ClientLogin / Fever verify 全链。会话本体（token / api_key）
   在改密前长效，逐轮认证是纯固定成本；但会话又不能无脑缓存——OPT-006 的代际
   守卫（[账号会话与配置应用边界](2026-10-08-账号会话与配置应用边界.md)）要求
   换号/改密后在途请求立即失效，缓存不得弱化这条语义。
2. **独立请求串行**：GR 主列举正文的 100 条/块「锁外拉取→锁内合并」逐块串行，
   B2 权威集合回补与 Fever `with_ids` 回补同样串行。这些块之间没有依赖
   （id 集合已完整在手），RTT 排队完全白白叠加；但分页列举本身
   （continuation 链 / since_id / max_id 游标链）必须保持串行。
3. **固定节拍轮询**：后台自动同步只看 30 分钟周期与独立发现节流；用户切回
   窗口时明明是最想看到新内容的时刻，却要等下一个周期。

## Decision

### 一、会话缓存：进程级单槽，键 = 身份 + 代际，TTL 10 分钟

- `sync/session.rs` 新增 `SessionLease` 与 `acquire_session`：锁内快照
  「凭据身份（`account_key`）+ 代际」→ 命中缓存零网络返回 → 未命中走既有
  `build_session` 全链（端点缓存、构建期代际复核原样保留）→ 构建成功按
  构建时点身份写缓存。`ensure_current` 的边界复核逐字未动——代际失配即
  缓存 miss 的语义只被加强（身份也参与命中判定），不被弱化。
- 缓存形态是 **sync 模块内的进程级单槽**（`OnceLock<Mutex<Option<_>>>`），
  与 PULL_LOCK / PUSH_LOCK / QUEUE_EVENT_TARGET 同类；未注册（集成测试不调用
  `init_session_cache`）时查找/写入全部 no-op，引擎行为与无缓存时代逐字一致。
- **401/认证类失败回落（只重试一次）**：phases/push/subscriptions 六个推送·
  拉取入口统一改经 `acquire_session`；当「租约来自缓存」且本轮出现认证类失败
  （Fever `code=auth`，GReader 会话内 `→ 401/403` 文案）时，剔除该账号的缓存
  条目、重认证并重放同一阶段体一次。重试租约 `from_cache=false`，不再触发回落
  ——重试仍失败则按既有 fail-closed 语义计入失败、游标/队列保留。重建会话
  本身失败（凭据已不存在/代际损坏/网络失败）只记日志并保留首轮既有结果。
- 认证失败的检测点在**报告层**（`report_has_auth_failure` 扫描 `report.errors`）：
  pull/push 的认证失败按 fail-closed 语义本就不中止本轮、只进 `report.errors`，
  Err 通道上没有可供检测的对象。错误串的两个成分（`AppError` Display 的
  `[code] ` 前缀、greader.rs 的状态码文案）都是仓内单点。
- **与绑定不完整 marker 的交互**（CI run 41278414748 教训，行为核实为既有
  fail-closed 设计而非重放链路缺陷）：`pull_feeds` 认证失败会写入「绑定不完整」
  持久 marker（A-P2-3），清除条件是**成功的 pull_feeds**。重放链路在发现已
  尝试时会重跑 `pull_feeds`——服务端仍拒绝则 marker 保留（正确），服务端放行
  即收敛。注意轻量同步的只读发现受 5 分钟节流
  （`ZERO_BINDING_DISCOVERY_INTERVAL_SECS`）：失败轮后恢复的首个 light 可能
  不跑 feeds 阶段，marker 会保留到下个发现窗口或手动 sync_now 的 feeds 阶段
  才清除——条目拉取在此期间被既有守卫阻断，属 marker 生命周期的既有形态。
  `session_cache_e2e` 的恢复段据此先显式跑 `feeds_phase` 收敛 marker 再断言
  条目恢复。

### 二、独立请求有界并发：批内 ≤3、按原块顺序合并

- 新常量 `PULL_FETCH_CONCURRENCY = 3`（greader_pull.rs 定义，fever_pull 共用）：
  任务卡给定 2–4 区间中值，服务端友好（个人规模 Miniflux/FreshRSS 实例），
  在途响应内存有界（≤ 并发度 × 单请求块大小）。
- GR 主列举正文分块、GR 权威集合回补（100 条/块）、Fever `with_ids` 回补
  （50 条/块）三个通道改为：**批内并发拉取（`tokio::join!` 定元数展开）→
  批间按原块顺序逐块短事务合并**。失败计数（chunk_failures / fetch_failures /
  binding_failures）、映射重建、代际复核、游标守卫的语义与串行版逐字一致；
  合并仍串行（maps 就地突变与失败重建依赖块顺序）。
- **分页列举保持串行**：continuation 链、since_id / max_id 游标链、
  `i64::MAX` 顶覆盖不变；PULL_LOCK 仍覆盖整个 pull 编排，DB 锁纪律不变
  （HTTP 段并发互不持锁，合并各自短临界区）。

#### 屏障同步点契约（并发化后写屏障测试的人必读）

`mock_greader` 的 contents 响应屏障按**请求到达序**计数。串行流下「第 N 个
contents 请求到达」蕴含「前 N-1 块已合并」；批内并发后同批请求在**任何合并
发生之前**全部到达，该蕴含对批内序号失效（CI run 41276949973 的
`local_change_after_new_insert_survives_rest_of_round` 红，正是这一时序假设
失效，不是守卫语义被破坏）。新契约：

- **可靠的合并进度锚点只有批边界**：第 `k·W + 1`（k ≥ 1，W =
  `PULL_FETCH_CONCURRENCY`）个 contents 请求 = 后继批的首请求，只在块
  `1..=k·W` **全部合并完成后**才发出——要在「某块已合并」时点做本地写入，
  把屏障武装到其后继批的首请求序号（例：400 条 4 块、W=3，屏障武装第 4 个
  请求 ⇒ 停靠时块 1-3 已合并、块 4 与权威对账未跑）。
- **阶段锚点不变**：reading-list ids 屏障 = 轮起点（零合并）；read/starred
  权威集合 ids 屏障 = 全部正文批合并之后（权威阶段仍在正文循环之后）；
  subscription/edit 与 quickadd 屏障在 feeds 阶段推送路径，与本轮无关。
- **全库用点审计**（批内并发落地时逐点核对）：`arm_contents_barrier` 仅
  `pull_field_versions_e2e` 一处（已按批边界重锚）；`arm_stream_ids_barrier`
  六处全部按流名匹配、阶段锚定，不受批内并发影响；`opt009_phaseb_e2e` 的
  edit/quickadd 屏障同样无关。后续新增屏障用例按本契约选锚点，不得假设
  「请求到达 ⇒ 更早块已合并」。

### 三、窗口聚焦触发 light 同步：60s 节流 + 前置判定 + 周期零改动

- lib.rs `on_window_event` 捕获主窗口 `Focused(true)` → `scheduler::on_window_focused`：
  节流判据抽成纯函数 `focus_sync_due(now, last)`（≥60s 才允许），触发时刻用
  `AtomicI64` CAS 认领——并发焦点事件只有一个胜出，判定与计时同一原子操作。
  认领后即使前置判定不通过也不回滚窗口（节流按「焦点事件」计；代价只是启用
  autoSync 后首窗最多顺延 60s）。
- 异步执行体与 `auto_sync_backend` 的 normal_due 分支同链：前置判定
  （autoSync 开启 + 有可用凭据，凭据读取失败按失败关闭口径跳过）→ outbox
  pending 检查（有 pending 才发请求）→ `sync_light` 全链 → 同款
  `has_data_change` 事件判定。`sync-running` 事件 payload 用 `source: "focus"`
  （前端 `listen('sync-running')` 不消费 payload，无契约影响）。
- 30 分钟周期、独立发现节流、refresh 调度循环零改动；聚焦同步推进
  `last_sync_ts` 后周期判据按真实同步时间自然顺延，调度器 next_tick 节奏不变。

## Alternatives considered

### Why not 并发整个 pull？

pull 的阶段间有真实依赖：订阅层绑定先于条目合并（binding_incomplete 重试链）、
状态对账要在条目合并后做、Fever 三段式（增量 → 历史 → with_ids → 对账）共享
`seen`/maps/cursor。并发整个 pull 要么把这些依赖显式建模成 DAG（复杂度暴涨），
要么接受交错下的游标/绑定竞态。只并发「块级独立请求」（id 集合已在手、块间
无依赖）是收益/风险比最高的一层；模块头 PULL_LOCK 的串行约束注释因此原样保留。

### Why not 预取滑窗（futures buffered）或全量并发预取？

- 全量并发预取（把所有块的响应都拉完再统一合并）内存无界：20 万条增量时
  在途正文可达 GB 级，而串行版内存上界是单块。直接否决。
- 滑窗（完成一块立刻补发下一块，如 `futures::stream::buffered`）比批内 join
  少一次「批内互相等慢块」的头阻塞，但仓库没有 futures 直接依赖（加依赖会动
  Cargo.lock，本卡禁止），手写滑窗要管理在途句簿与早退 abort（JoinHandle
  drop 只 detach 不取消），复杂度显著更高。批内 join 的批间屏障在 RTT 均匀的
  个人服务端上墙钟差异可忽略，且实现/审计面最小——取简单者。

### Why not 去掉 PULL_LOCK（改按游标粒度互斥）？

cursor/history 的失败恢复依赖本轮快照不被另一 pull 交错改写（模块头注释的
既有论证）；按游标粒度拆锁等于重新发明「单写者」语义，还要处理两个 pull 各自
失败计数的归并。本轮锁的持有量没有增加（HTTP 段本来就不持 DB 锁），PULL_LOCK
仍只覆盖 pull 编排；收益为零、风险为正，维持原状。

### Why not 会话缓存放 AppState 字段并穿参？

任务卡原始设想。`(db, http)` 二参签名被 tests/ 大量集成测试锁定（push.rs 头注
明示），把缓存穿参需要改动全部 sync 入口（sync_now/sync_light/feeds_phase×2/
states_phase/push_states_now/订阅编辑/退订/outbox）与既有测试调用面，churn 远超
收益。进程级静态与 AppState 同生命周期（单 AppState、启动即注册），且与仓内
QUEUE_EVENT_TARGET 的「setup 注册、引擎读静态」先例同构。代价：缓存的注册点
在 lib.rs setup 而非 AppState 构造器，读代码时需要经 mod.rs 的重导出注释定位。

### Why not 会话缓存只按代际做键？

生产单库下代际与凭据一一对应（每次账号提交同一事务推进代际），代际单独成键
是充分的；但缓存是进程级单槽，测试进程里多个测试库各自的代际会互相撞号。
身份（`account_key`）参与命中判定后，同代际异账号必然 miss——对生产语义零影响
（同账号同代际才命中），对测试是确定性的第二道键。

### Why not 缓存条目过期后后台异步刷新（stale-while-revalidate）？

TTL 过期条目直接 miss + 同步重建，会把过期后的第一次同步拖回全认证成本。
后台刷新需要额外的后台任务与「刷新期间用旧会话还是等待」的语义决策，而
TTL=10 分钟的过期频率极低（典型 30 分钟同步间隔下最多每三轮多一次认证），
不值得为它加机制。

### Why not 改造 greader.rs/fever.rs 的错误码（401/403 → code="auth"）替代报告扫描？

错误码改造能让检测更结构化，但会改变既有错误的对外分类（push_block_summary、
前端错误文案、大量锁定错误文案的测试），本机不可编译验证的情况下回归面太大。
字符串扫描的两个锚点（`[code] ` Display 前缀、状态码文案）都是仓内单点且有
单测锁定；误报（URL 恰含标记）的后果只是多一次有界的剔除重认证，无循环。

### Why not 401 回落在 exec_push / 每个请求点就地重试？

请求点就地重试需要把「重建的会话」传回每个拉取/推送循环，且失败半程的本地
状态（已合并块、已标记失败项）与新会话的重放边界难以界定。阶段级重放把重试
粒度收敛到「从干净状态重跑同一阶段体」——所有写路径本就按幂等合并 + fail-closed
设计（游标/队列在失败轮保留），重放是既有恢复语义的自然复用，且「只重试一次」
可以在入口处用 `from_cache` 一位布尔锁定。

### Why not 聚焦同步走前端事件/命令触发？

tauri 窗口焦点事件在 Rust 侧 `WindowEvent::Focused` 直接可达（lib.rs 已有
on_window_event 接线点），零前端改动、零新 IPC 面；经 commands/sync.rs 加触发
命令则要前端监听 webview 焦点再调命令，多一层且时序受前端装载影响。选侵入
最小的 Rust 侧接线。

## Consequences

- 收益：常态同步零认证请求（ClientLogin/verify 每轮一次 → TTL 内零次）；
  三个独立请求通道的往返时延约压到串行版的 1/2–1/3（250 条增量实测路径由
  3 块串行变 2 批并发）；回窗口 60s 内可见服务端新状态，不再等 30 分钟周期。
- 代价一：会话 token 被服务端吊销（改密）后，缓存窗口内第一次同步会先失败
  再回落（多一次认证与一轮重放）；TTL 上限 10 分钟兜底，401 回落把实际窗口
  压到一次失败以内。
- 代价二：401 回落重放会重复执行首轮已成功的段（幂等合并、幂等推送确认），
  report 计数以重试轮为准（首轮计数被丢弃）——对外统计在「回落发生」的轮次
  只反映重试轮，属可接受的诊断口径偏移。
- 代价三：并发度是进程级常量而非设置项；个人实例上 3 是保守值，不做 UI 暴露
  （fetchConcurrency 的 UI 只管直连抓取，不扩语义）。
- 测试锁定：`session_cache_e2e.rs` 锁缓存命中零认证、401 回落恰好一次重认证
  + 恢复轮零认证、代际失配 miss、250 条三分块全失败时的失败计数/游标保留
  与恢复轮全量重拉；`session.rs` 单测锁 TTL 边界、认证失败判定、剔除的账号
  限定；`scheduler.rs` 单测锁聚焦节流判据（含 last=0 与边界值）。行为验证由
  CI rust job（windows-latest）承担。
