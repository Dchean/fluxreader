# Agent Note: 查询与分页契约

Status: implemented

## Problem

列表查询曾有三处各自为政的口径问题，任何一处单独看都像小毛病，合起来是「界面显示的东西和列表实际装的东西不是一回事」：

1. **全库近似全集**：筛选视图用一个极大 `limit`（`limit:100000`）当「不分页」用。这个调用点让 `articlesExhausted`（是否已到末尾）永远算不出真值，也让旧文章在大库下不可达——用户翻不到底，界面却认为已经拉完。
2. **OFFSET 分页在可变集合上不成立**：`WHERE is_read=0` 这类集合会随用户操作收缩。加载前 500 篇未读 → 全部标读 → 再翻页，集合只剩 700 条而游标仍在 OFFSET 500，于是跳过剩余前 500 篇、只取最后 200 并宣告到底。收藏视图取消收藏同理。OFFSET 表达的是「用户已看过的条数」，而用户从未看过被同一操作移出集合的那些行。
3. **迟到的响应覆盖新状态**：同一查询的旧版本与「A → B → A」这样的往返，用「查询参数是否相同」无法区分，于是旧响应能覆盖新结果；续页请求若被当作新查询实例，还会把自己的代际当成新的。

## Decision

**查询范围从单点派生。** `QueryScope`（`src/store/internals.ts`）提供 `args` / `markScope` / `pageKey` / `viewKey` 三把键，所有查询参数只从这一处派生；发起请求时把当时的 scope 快照下来（`scopeAtStart` / `layoutAtStart` / `sortAtStart`），响应对不上快照就丢弃。`scopePageKey` / `viewCacheKey` 的字符串形态被**逐字兼容锁定**（有变异验证），改动它们会同时打到缓存键与筛选语义。

**分页改为 keyset 游标，谓词必须与 `ORDER BY` 逐字同构。**

```rust
pub(crate) const PUBLISHED_ORDER_DESC: &str = "a.published_at DESC, a.id DESC";
const KEYSET_PREDICATE_DESC: &str =
    "(a.published_at < ? OR (a.published_at = ? AND a.id < ?))";
```

谓词与排序用同一对列、同一方向，缺了 `id` 兜底就会在时间并列处跨页重复或漏读。`last_published` 是 RFC3339 TEXT，比较**必须是裸字符串比较**——它是外部字符串，只经绑定参数进入 SQL。`last_published` 与 `last_id` 必须成对给出，只给一个就回落 OFFSET（兼容窗口）。索引 `idx_articles_published_id (published_at, id)` 承接该谓词。

**续页携带首页代际，而不是自增代际。** 续页是同一查询实例的继续，不是新查询；给它新代际会让自己的响应被判过期。首页落地时记录 `firstPageSerialByKey`，续页请求带上它，落地时比对。

**游标按实际拉取行数推进，不按 offset 加页大小。** 去重会吃掉行，offset 漂移量等于去重量；`advanceArticlesCursor` 是唯一的推进点，`articlesExhausted` 由后端返回行数是否满页判定。

**后台刷新围绕已加载窗口重建，固定 `offset=0/limit=500` 不再够用**（深页阅读时锚点根本不在刷新结果里）。刷新按 keyset 围绕目标位置续拉，带防呆上限 `ceil(target / ARTICLES_PAGE_SIZE) + 1`。

## Consequences

**收益**：可变集合上连续翻页不再丢文章；旧文章在大库下可达（`limit:100000` 调用点被废除，`articlesExhausted` 变成真值）；迟到响应与 A→B→A 往返不再串数据；深页阅读的后台刷新能保住阅读锚。

**代价**：

- keyset 游标要求排序键可比较且唯一（`published_at` + `id`）；将来若引入新的排序维度（例如按源内序号），必须为每个维度各定义一对谓词与索引，不能复用。
- 前端多了一份游标状态（`ArticlesCursorState`）与代际簿记，错误使用会退化成「永远不加载」或「重复加载」。这是必要的复杂度：没有它就无法区分旧响应与往返。
- 兼容窗口（只给 `last_published` 或只给 `last_id` 时回落 OFFSET）意味着错误用法不会立刻失败，而是静默变差。
- 存量 OFFSET 语义的注释与断言必须一起更新，否则会锁住已废弃的行为。审计期间确实发现过一条断言锁的是缺陷手法本身（「新快照清空 hydratedIds」），修的时候按行为变化更新了它。

## Alternatives considered

### Why not 固定查询快照 ID 序列？

审计给出的备选是：首次查询时把匹配的 id 序列存进一张快照表，翻页时按序列位置取值，这样集合变化不影响分页。它确实彻底解决漂移，代价是多一张表、一套生命周期管理（快照何时失效？用户回到旧查询时用哪份快照？），以及每次查询写一份序列的成本。keyset 用排序键的稳定性换取「不存序列」，在「时间 + id」这个天然全序上够用，故选择 keyset。

### Why not 继续用 OFFSET，只在客户端补偿？

客户端补偿的做法是：发现集合规模变化就重算 offset。但客户端不知道有多少行被移出集合（标读发生在别处、同步拉取也会改状态），补偿值只能猜。分页谓词的正确性必须在 SQL 里成立。

### Why not 给续页自增代际？

「每个请求一个新代际，落地时取最大的」看起来更简单，但续页会把首页的代际顶掉，导致首页响应在续页之后到达时被判过期——而这恰好是正常时序（首页先发、后到）。选择让续页继承首页代际，是承认「这些响应属于同一个查询实例」。

### Why not 用 `date(published_at, 'localtime')` 之类表达式排序？

表达式排序会让索引失效（`SCAN` + 临时 B 树），而且 `date()` 是非确定性函数，表达式索引根本建不出来。详见[时间比较与时区口径](../bug-fix/2026-09-23-时间比较与时区口径.md)。
