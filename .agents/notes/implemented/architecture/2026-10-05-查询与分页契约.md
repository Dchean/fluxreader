# Agent Note: 查询与分页契约

Status: implemented

## Problem

列表查询曾有三处各自为政的口径问题，任何一处单独看都像小毛病，合起来是「界面显示的东西和列表实际装的东西不是一回事」：

1. **全库近似全集**：筛选视图用一个极大 `limit`（`limit:100000`）当「不分页」用。这个调用点让 `articlesExhausted`（是否已到末尾）永远算不出真值，也让旧文章在大库下不可达——用户翻不到底，界面却认为已经拉完。
2. **OFFSET 分页在可变集合上不成立**：`WHERE is_read=0` 这类集合会随用户操作收缩。加载前 500 篇未读 → 全部标读 → 再翻页，集合只剩 700 条而游标仍在 OFFSET 500，于是跳过剩余前 500 篇、只取最后 200 并宣告到底。收藏视图取消收藏同理。OFFSET 表达的是「用户已看过的条数」，而用户从未看过被同一操作移出集合的那些行。
3. **迟到的响应覆盖新状态**：同一查询的旧版本与「A → B → A」这样的往返，用「查询参数是否相同」无法区分，于是旧响应能覆盖新结果；续页请求若被当作新查询实例，还会把自己的代际当成新的。

## Decision

**查询范围从单点派生。** `QueryScope`（`src/store/internals.ts`）提供 `args` / `markScope` / `pageKey` / `viewKey` 三把键，所有查询参数只从这一处派生；发起请求时把当时的 scope 快照下来（`scopeAtStart` / `layoutAtStart` / `sortAtStart`），响应对不上快照就丢弃。`scopePageKey` / `viewCacheKey` 的字符串形态被**逐字兼容锁定**（有变异验证），改动它们会同时打到缓存键与筛选语义。

**分页改为 keyset 游标，谓词必须与 `ORDER BY` 逐字同构。**

```rust
pub(crate) const PUBLISHED_ORDER_DESC: &str = "a.published_at DESC, a.id DESC";
const KEYSET_PREDICATE_DESC: &str =
    "(a.published_at < ? OR (a.published_at = ? AND a.id < ?))";
```

谓词与排序用同一对列、同一方向，缺了 `id` 兜底就会在时间并列处跨页重复或漏读。`last_published` 是 RFC3339 TEXT，比较**必须是裸字符串比较**——它是外部字符串，只经绑定参数进入 SQL。`last_published` 与 `last_id` 必须成对给出，只给一个就回落 OFFSET（兼容窗口）。索引 `idx_articles_published_id (published_at, id)` 承接该谓词。

**续页携带首页代际，而不是自增代际。** 续页是同一查询实例的继续，不是新查询；给它新代际会让自己的响应被判过期。首页落地时记录 `firstPageSerialByKey`，续页请求带上它，落地时比对。

**游标按实际拉取行数推进，不按 offset 加页大小。** 去重会吃掉行，offset 漂移量等于去重量；`advanceArticlesCursor` 是唯一的推进点，`articlesExhausted` 由后端返回行数是否满页判定。

**后台刷新围绕已加载窗口重建，固定 `offset=0/limit=500` 不再够用**（深页阅读时锚点根本不在刷新结果里）。刷新按 keyset 围绕目标位置续拉，带防呆上限 `ceil(target / ARTICLES_PAGE_SIZE) + 1`。

## Consequences

**收益**：可变集合上连续翻页不再丢文章；旧文章在大库下可达（`limit:100000` 调用点被废除，`articlesExhausted` 变成真值）；迟到响应与 A→B→A 往返不再串数据；深页阅读的后台刷新能保住阅读锚。

**代价**：

- keyset 游标要求排序键可比较且唯一（`published_at` + `id`）；将来若引入新的排序维度（例如按源内序号），必须为每个维度各定义一对谓词与索引，不能复用。
- 前端多了一份游标状态（`ArticlesCursorState`）与代际簿记，错误使用会退化成「永远不加载」或「重复加载」。这是必要的复杂度：没有它就无法区分旧响应与往返。
- 兼容窗口（只给 `last_published` 或只给 `last_id` 时回落 OFFSET）意味着错误用法不会立刻失败，而是静默变差。
- 存量 OFFSET 语义的注释与断言必须一起更新，否则会锁住已废弃的行为。审计期间确实发现过一条断言锁的是缺陷手法本身（「新快照清空 hydratedIds」），修的时候按行为变化更新了它。

## Alternatives considered

### Why not 固定查询快照 ID 序列？

审计给出的备选是：首次查询时把匹配的 id 序列存进一张快照表，翻页时按序列位置取值，这样集合变化不影响分页。它确实彻底解决漂移，代价是多一张表、一套生命周期管理（快照何时失效？用户回到旧查询时用哪份快照？），以及每次查询写一份序列的成本。keyset 用排序键的稳定性换取「不存序列」，在「时间 + id」这个天然全序上够用，故选择 keyset。

### Why not 继续用 OFFSET，只在客户端补偿？

客户端补偿的做法是：发现集合规模变化就重算 offset。但客户端不知道有多少行被移出集合（标读发生在别处、同步拉取也会改状态），补偿值只能猜。分页谓词的正确性必须在 SQL 里成立。

### Why not 给续页自增代际？

「每个请求一个新代际，落地时取最大的」看起来更简单，但续页会把首页的代际顶掉，导致首页响应在续页之后到达时被判过期——而这恰好是正常时序（首页先发、后到）。选择让续页继承首页代际，是承认「这些响应属于同一个查询实例」。

### Why not 用 `date(published_at, 'localtime')` 之类表达式排序？

表达式排序会让索引失效（`SCAN` + 临时 B 树），而且 `date()` 是非确定性函数，表达式索引根本建不出来。详见[时间比较与时区口径](../bug-fix/2026-09-23-时间比较与时区口径.md)。

## 落地事实更新（OPT-008B 第一阶段含 R1/R2，2026-10-12）

智能去重从「入库丢身份」改为**查询显示聚合**（`db/articles.rs` 的 `dedup_exists_clause`）：代表 = 同 `url_norm` 组内 id 最小者，且组在**当前 scope（feed/folder/layout）与视图筛选（未读/收藏/今天）内**形成——单源/单布局永不被其它源的副本吞掉，未读视图不会因代表已读而整体消失。谓词进 SQL 本体并与外部 WHERE 逐项同构，`list_articles`（keyset/OFFSET 两形态）、`article_index`、`feed_counts` 与 `scope_counts` 共用同一生成器，不做「分页后数组去重」（那会跳页/漏项）。

R1 修正（主控反例）：

- **搜索**：代表必须在**关键词匹配集合内**选（内层 EXISTS 复用同一组 LIKE 条件）——同 URL 组里最小 id 副本不含词、较大 id 副本含词时，含词副本不得被隐藏；命中行必须可真实打开（`anchorToArticle` 位置缺失时回退按 id 取详情并注入视图行，不再静默不打开）。
- **搜索候选索引（OPT-017B）**：v29 起 ≥3 字符词可走 `articles_trigram_idx` 候选过滤，但 LIKE 逐行验证仍是唯一判定；候选只收缩行数、不改变结果集与既有排序/去重语义（含 2 字中文回落、索引缺失/损坏回落——回归 `db/articles.rs` opt017b 等值矩阵）。
- **markAll / 未读集合**：显示去重不参与操作集合——「全部已读」的目标 = 范围未读 ∪ 同组闭包，冻结一次后 标读/字段版本/入队同一事务（该 scope 未读真的为空，不依赖推送/拉取远端收敛）；`list_unread_ids_scoped` 返回范围未读（不含闭包），读目标集合见 `list_read_target_ids_scoped`。
- **计数**：`scope_counts`（全部/分类/源，按布局过滤）存入独立 `scopeCounts` 快照（带 layout/dedup 元数据）；`feedCounts` 保持布局无关的按源计数作为回退底座；单条/批量/回滚/全部已读之后按**真实计数有序对账**（折叠组非线性，不做逐条 ±1 推算）。

R2 修正（N1/N2 与搜索跨布局组件取证）：

- **计数快照来源单一化与选择器来源校验**：`counts_snapshot` 单条 IPC 在同一 DB 锁内返回源计数 + scope 计数（同一开关值）；选择器消费 `scopeCounts` 要求**布局与开关都匹配**（`snap.layout === activeContentLayout && snap.dedup === settings.smartDedup`），旧布局或旧开关口径的快照一律不消费。两套测试 harness 的 `resetStore` 清 `scopeCounts`，杜绝跨用例快照按匹配被消费。
- **读写入回执（N1）**：后端读入口返回**真实翻转行**回执（`ReadWriteReceipt`：`set_read`/`set_read_bulk` 为 `[{id, feed_id}]`，`mark_all_read` 为实际影响数）；前端 `applyReadReceipt` 据此让受影响**条目/视图缓存/按源计数**本地收敛（同 URL 副本一并翻已读），「全部已读」成功后再按范围×视图×布局同构谓词收敛已加载窗口。默认去重关闭时同样成立——不再出现「标读一条、同文另一条仍显示未读、计数偏大」。
- **计数的提交协议（N2）**：reload 与写后对账是同一协议的写者——`beginCountsFetch` 发起序号 + 在途未提交读/藏写**引用计数**（`beginLocalFlagWrite`/`endLocalFlagWrite`），`canLandCounts` 要求「仍是最新一次读取 且 无在途意图」。旧 reload 落地不覆盖新对账，旧对账落地也不覆盖新 reload；在途意图（含读/藏多笔同时挂起）期间任何快照不得落地，全部落定后由最后一笔自身对账收敛；读取失败保留同 scope 已确认值（可解释滞后，下次 reload/对账自愈）。组件夹具同步迁移到 `counts_snapshot`（原 `feed_counts` 计划不再被 reload 消费）。
- **搜索跨布局的真实组件取证**：`anchorToArticle` 回退注入的跨布局行必须**真的可见**——真实挂载 App + 搜索面板的回归断言 Reader 实际渲染标题/正文（不止「数组有行 + activeArticleId」）、Escape 返回空态、当前布局不得伪造成另一布局的卡片；注入**不动分页游标**（keyset 锚保持），在途续页响应被锚定推进的代际守卫丢弃、自动重试落地推进（`search-cross-layout.test.mjs` 以两个独立 deferred 区分两次请求），可见集合仍按布局过滤。

R3 修正（P2-1/P2-2，并发窗口收口）：

- **回执行逐行凭据（P2-1）**：回执承载的是后端**请求时刻**已提交的翻转，不等于当前状态。`applyReadReceipt` 改为按**行×字段写序号**（`entryFieldWrittenAfter`，随每次真实本地读/藏写入推进）识别真冲突：无关 URL 组/无关行的后续写不再让整批回执行失效；被较新 unread 接管的行不翻状态、**计数不无条件扣**（计数只随实际应用的行扣减；已是已读的行也不重复扣）。单条/批量/打开三入口、窗口外兄弟与视图缓存共用同一契约。
- **reload/filtered/anchor 的读取时刻写前沿（P2-2）**：三处后端快照在发起时捕获本地写前沿（`currentLocalFlagWriteSerial()`）。reload 的计数落地要求「前沿未推进」，被写过的行×字段在 `mergeSnapshotEntries(..., { writtenAfterSerial })` 中保留本地值——旧响应不得覆已提交的读/藏（007 字段独立性保持）；读取发起时刻晚于写入的新鲜读取照常接受外部状态（本地值不是永久权威）。缓存恢复路径由写入时的 `syncCurrentViewCache` 保持同步（切走/切回回归锁定）。

R4 修正（并发窗口的最小硬化，不依赖 IPC FIFO；R5 补充见末）：

- **读取失效依据不止写序号**：app_settings 读取（启动读取/应用回读）新增**读取发起序号**（后发起者优先）——应用/回读期间的旧启动读取落地即过期（主控真实探针关闭）；设置 bootstrap 还先等**捕获时**写前沿落定（读取请求晚于这些写发出；提交/回应分离两时序均有回归：已提交回应延迟→结算后读新值；未提交→等落定后收敛/失败回滚）。**R5 补充**：app_settings 的读取（bootstrap/回读/写前校准）收口为**单飞共享**（并发调用复用同一在途读取；回读强制新鲜发起）——写路径在基线未知时优先复用/等待在途读取（不重复发 IPC）；被期间写入作废的 bootstrap 读取不替换基线/UI，但等这些写落定后再返回，调用方观察到一致终态。**R6 补充**：共享读取凭据绑定**发起时**的写序号与应用代次——跨提交（新写/新应用）的等待者不得 join 为新鲜（bootstrap 检测到旧读时强制发起新鲜读取；校准只复用同一应用代次内发起的在途读；应用回读与「置基线未确认」推进应用代次）。
- **articles 快照对「读取发起时已在途」的行×字段保护**：`mergeSnapshotEntries` 新增 `opts.inFlightAtStart`（`entryInFlightFieldKeys()`，与 beginLocalFlagWrite/endLocalFlagWrite 同点配对登记）——在途写的乐观值不被读前快照翻回，且**不 bump 版本**（写失败时回滚仍有效；写成功由后续新鲜读取收敛）；若快照行值与保留的本地值相同（后端已含该值，如外部写入者已落库）则仍 bump，迟到失败回滚不得把已生效值踩回（t104 迟到回滚语义保持）。非保护字段照常 bump（t118 版本真值表按「已落定声明」语义迁移夹具）。
