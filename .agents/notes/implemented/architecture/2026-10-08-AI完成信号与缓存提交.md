# Agent Note: AI 完成信号与缓存提交

Status: implemented

## Problem

`stream_chat` 的完成判定只看「HTTP 流干净结束」：`consume_sse` 在 `resp.chunk()`
返回 `None` 时无条件返回 `completed=true`。由此一整套失败模式全部被误报为成功：

- 模型因 `finish_reason=length` 截断、被 `content_filter` 过滤、以 `tool_calls`
  结束，或连接中途断开（EOF 无完成标记）——前端都收到「完整摘要/译文」，且
  `ai_summarize`/`ai_translate` 会把它写进 AI 缓存，重试被缓存短路，用户永远
  拿不到完整产物。
- `[DONE]` 被当作普通行跳过；非 JSON 的 data 行、JSON 解析失败被静默丢弃；
  坏 UTF-8 经 `from_utf8_lossy` 替换成 U+FFFD——正文损坏但流程照常「成功」。
- finish 之后的越界数据帧会被继续拼接进全文。
- 累计文本无预算：故障/恶意端点持续推 delta 可拖爆内存。
- 命令层缓存写入用 `let _ = db::set_article_ai_fields(...)` 吞掉 DB 错误后照发
  `Done`：用户看到「成功」，缓存实际未写，属假成功。

R1 review（2026-10-09，实测反例）补充的帧框架与终态缺陷（均已按下方 Decision 修复）：

- **P2-1** 合法 UTF-8 BOM 开头的流（含 BOM 跨 TCP chunk）：BOM 让首行不再是
  `data:` 前缀，首个 delta 被静默吞掉，流仍报完成并可能缓存。
- **P2-2** 行缓冲预算只查「未结束残留」：`8 MiB-ε` 残行 + 下一 chunk 补 `\n`
  后整行在检查前被 drain，超限的**完整行**（含注释行）绕过预算；text 预算只
  覆盖正文，替代不了框架预算。
- **P2-3** stop+DONE 已收到仍等 HTTP EOF：keep-alive 端点不关连接时，正常完成
  会一直挂到请求超时。
- **P2-4** 声明的「stop/DONE 顺序不限」与实现不符（DONE 先到应 aiIncomplete）；
  DONE 后仍要求「未来网络数据全部拒绝」会引入不必要的读等待；事件框架未按
  SSE 规范（空行分隔事件、多行 data 合并），逐行独立 parse 会丢事件语义。

R2 review（2026-10-09）收窄到两处帧边界（已最小修复，未重构引擎）：

- **R2-P2-1** `line.trim().is_empty()` 把纯空白行当事件分隔符：标准 SSE 只有
  去掉行结束符后长度为 0 的空行才派发；多行 data JSON 中间夹一个空格行会提前
  派发半截 JSON。
- **R2-P2-2** 行结束符没有真正剥除（`trim_end_matches('\r')` 作用于仍以 `\n`
  结尾的串，实际什么也没剥），data 值残留 EOL：join 再插 LF 造成双换行、事件
  预算按脏字节多算（恰好 8 MiB 的合法载荷被误拒）、无冒号 `data` 行因残留
  EOL 匹配不上。

## Decision

**完成信号只有一个：模型显式给出 `finish_reason:"stop"` 且流正常收尾。次序契约
固定为 stop 先、DONE 后。HTTP EOF 本身不是完成信号。** `src-tauri/src/ai.rs` 的
`SseParser` 按 SSE 规范切帧并逐事件裁决完成语义；`consume_sse` 负责字节层
（流首 BOM、行切分、三层预算、严格 UTF-8、终态返回）。

终态语义表：

| 输入 | 结果 |
| --- | --- |
| stop 事件后收到 `[DONE]` | `Ok(completed=true)`——**权威终态：立即返回、释放响应、不再读取任何网络数据**（含同一 chunk 的尾随字节，直接丢弃） |
| stop 事件 + 干净 EOF（合法兼容形态，无 `[DONE]`） | `Ok(completed=true)` |
| `[DONE]` 先于 stop（或从未见 stop） | `Err aiIncomplete`（次序契约，立即终态） |
| 无 finish 的干净 EOF | `Err aiIncomplete` |
| `finish_reason:"length"` / `"content_filter"` | `Err aiTruncated` / `Err aiFiltered` |
| `finish_reason:"tool_calls"` 或其他未知值 | `Err aiIncomplete` |
| 重复 / 冲突 finish_reason | `Err aiStream`（协议拒绝） |
| stop 之后、`[DONE]` 之前的文本增量 | `Err aiStream`（拒绝越界拼接） |
| data 载荷不是合法 JSON | `Err aiStream`（不静默丢弃） |
| 行内含非法 UTF-8 | `Err aiStream`（不 lossy 替换） |
| `"error":null` | 忽略（兼容中转成功帧） |
| `"error"` 非 null | `Err aiStream`（对象取 message，其余取 JSON 文本） |
| sink 返回 false（消费方取消） | `Ok(completed=false)`，立即停止读流 |

帧框架（WHATWG SSE 规范，`SseParser` + `consume_sse`）：

- 流首可选 BOM `EF BB BF`（可跨 TCP chunk），只在流首剥一次；流中出现不特殊处理。
- 行以 `\n` 分隔；行结束符在切帧时真正剥除（一个 LF 及其紧邻前的一个 CR；
  EOF 残余剥尾部单独 CR），字段行与 data 值都不携带任何 EOL 字节。
- 只有**真正空行**（去行结束符后长度 0）派发当前事件；纯空白行按规范是未知
  字段行，忽略——不得当分隔符（否则多行 data JSON 会被提前截断）。
- `data:` 值剥一个前导空格；无冒号的 `data` 行 = 空值 data 行；同一事件的多条
  `data:` 行以 `\n` 连接为一个载荷再解析（不逐行独立 parse）。
- 心跳例外（不影响完成语义）：真正空行、空 `data:` 行、`choices:[]` 的 usage
  帧、注释（`:` 开头）与其他字段行（`event:`/`id:`/`retry:`）。
- 兼容偏离：规范在 EOF 丢弃未以空行收尾的事件；本实现按「单行 JSON 单帧可在
  事件空行或 EOF 时派发」处理（否则尾帧无空行会丢 finish 帧，违反「尾帧无换行
  照样正确」的既有承诺）。该偏离只放宽派发时机，不放宽完成条件。

预算（三层独立生效，`consume_sse`/`SseParser`）：

- 单条**完整行**在复制/解析前检查 ≤ 8 MiB（按缓冲中的物理字节计、含 EOL；
  含注释行；覆盖「残行 + 补 newline」的绕过路径），恰好 8 MiB 合法；无换行的
  残留 ≤ 8 MiB；
- 单个事件的 data 载荷 = 各 data 行值字节 + join 插入的 LF（首行不插；**空
  data 行也计入**），≤ 8 MiB（防无空行分隔的多行洪泛）；恰好 8 MiB 合法，
  超 1 字节拒绝；
- 累计正文 ≤ 256 KiB（`MAX_OUTPUT_TEXT`，与完成语义无关的防内存上限，不替代
  上述框架预算）。
- `SUMMARY_MAX_TOKENS=1024` / `TRANSLATE_MAX_TOKENS=4096` 与请求参数保持原样
  （完成正确性不许靠调大 token 掩盖）。

命令层（`src-tauri/src/commands/ai.rs`）：`stream_chat` 的 Err 经 `?` 原样传播
到 invoke rejection，前端既有 `.catch` 显示失败并可重试——流式 delta 已渲染的
文本保留可见，不新增 UI 接口。完整产物（`completed=true` 且非空）经
`commit_summary_cache` / `commit_translation_cache` 落缓存，**保存失败必须
Err，不得再发送 `Done`**；**取消（`completed=false`）不发送 `Done`、不写
缓存**；缓存命中完整结果走 delta+Done 且零网络请求。`AiEvent::Delta/Done` 的
IPC 形状与 `stream_chat` 签名不变，提示词配置不变。

证据：`src-tauri/src/ai.rs` 单测 30 项（BOM 剥除/跨 chunk 等待、真·空行判定、
多行 data 合并、join LF 预算边界、语义表逐项）+ `tests/ai_stream_completion_e2e.rs`
29 项真实 loopback（规范帧分隔、空格行非分隔符、无冒号 data 空值、BOM 首帧与
跨 chunk、keep-alive 用 2s 测试级超时判定 DONE 立即返回、同 chunk 尾随不消费、
CRLF 恰好 8 MiB 事件载荷/注释行边界与 +1 拒绝等）+ `commands/ai.rs::ai_commit_tests`
6 项（真实 Channel + DB 触发器注入：取消无 Done、缓存命中零网络、保存失败无
Done 无缓存）+ `tests/ai_e2e.rs` mock 补齐真实 finish 帧后原断言不变。

## Consequences

- 「HTTP 断开」「DONE 未到」「DONE 越过 stop」与「模型自然结束」在类型层区分：
  截断、过滤、工具调用、断流、次序错误都会让命令层返回可重试的显式错误，
  不再写入缓存、不再显示成功。
- 合法且常见的兼容形态保持可用：stop 后可跟 `[DONE]` 或直接关流；`error:null`、
  `choices:[]` 的 usage 帧、空 data 心跳、无 choices 的合法 JSON 帧、单行 JSON
  单帧（空行/EOF 派发）、CRLF、跨 chunk UTF-8 与 BOM 都不误报。
- keep-alive 端点不再因等待 socket close 而把正常完成拖成超时；`[DONE]` 到达即
  释放响应。
- 损坏输入（坏字节、坏 JSON、超预算的完整行/残留/事件载荷）从「静默丢帧→假
  完成」变为「显式失败→可重试」，错误码 aiStream/aiIncomplete/aiTruncated/
  aiFiltered 便于诊断。
- 保存失败语义从「静默忽略」变为「Err」；取消不再多发一次注定失败的 Done。
- 父卡 OPT-013 的长文分块、缓存版本键与前端恢复入口不在本子卡范围；本卡不
  宣称 F15 完毕。

## Alternatives considered

### Why not「clean EOF 即完成」（旧行为）或反过来「必须 `[DONE]` 才完成」？

旧行为把网络中断当成功，是被修复的缺陷本身。反过来强制 `[DONE]` 会拒绝掉
一类真实存在的兼容端点：OpenAI 官方流以 `[DONE]` 收尾，但多数 newapi 类中转
在 `finish_reason:"stop"` 后直接关流。因此确定策略取交集最稳的形态：
finish_reason=stop **且**（`[DONE]` 或干净 EOF）。只有 `[DONE]` 没有任何 reason
不算——多家中转在截断上游时也会补发 `[DONE]`，它不能承担完成证明。

### Why not 继续逐行独立解析 / 静默跳过坏行？

逐行独立 parse 会把规范允许的「一个事件多条 data 行」拆散：每条前缀都是
残缺 JSON，要么误报协议错、要么被迫静默丢弃（R1 P2-4 明确要求合并）。静默
跳过坏行/坏 UTF-8 让「丢了内容」与「本来就没有」在结果上不可区分，且失败会
伪装成 `completed=true` 进入缓存。宽容解析与「不得假完成」不可兼得；对坏输入
显式失败，把判断交还给用户（错误 + 重试）是唯一不撒谎的语义。

### Why not 用 `trim().is_empty()` 判空行、或让 data 值保留 EOL 靠 `payload.trim()` 兜底？

空行判定必须严格（去行结束符后长度为 0）：`trim()` 会把纯空白行也算分隔符，
多行 data JSON 只要中间出现一个空格行就会被提前派发成半截 JSON（R2-P2-1）。
data 值保留 EOL 同样不可取：join 会再插 LF 造成双换行，预算按脏字节多算——
恰好 8 MiB 的合法载荷会被误拒（R2-P2-2）——且无冒号 `data` 行因残留 EOL 匹配
不上。正确边界是切帧时就剥掉行结束符，让状态机只面对真实的字段行内容；
「靠 trim 兜底」会把协议字节与内容字节混为一谈。

### Why not 容忍 finish 之后的增量、或者冲突的 finish_reason？

finish 是模型的结束声明；其后的文本只能来自协议错乱或拼接攻击（中转缓存
串流）。继续拼接会产出「比模型实际生成更长」的文本并可能进缓存，越界数据
语义无法验证，拒绝是唯一安全终态。

### Why not DONE 后继续读到 EOF 并拒绝尾随数据（R1 前实现）？

keep-alive 端点会在 DONE 后保持连接，等待 EOF 会把「正常完成」拖成超时
（R1 P2-3）；DONE 是协议定义的流结束信号，其后的字节不属于本次产物。
「拒绝尾随数据」的本意是防止越界拼接——「立即返回、不再读取」同样（甚至
更强）保证不拼接，且与连接生命周期自洽。因此改为：DONE 为权威终态，立即
返回并释放响应；同一 chunk 的尾随字节直接随缓冲丢弃，声明为「不再消费」。

### Why not 在每行解析时 `trim_start` 吃掉 `\u{FEFF}`？

BOM 只允许出现在流最前（RFC 8259/UTF-8 惯例），流中的 U+FEFF 是内容或协议
异常，不应被默默吃掉；按字节在流首剥除还天然处理了「BOM 三字节跨 TCP
chunk」——解析器层面看不到字节切分点，做不到「只等够 3 字节再判定」。

### Why not 按 provider 自动切换严格/宽松模式？

协议帧里没有可靠的 provider 标识，按 URL 猜厂商会把同一语义分叉成多套；
且任何「宽松分支」都会重新引入本次修复的误报。取而代之的是对所有端点使用
同一严格状态机，只对明确的成功附属形态（null error、usage 帧、心跳、尾帧无
换行/无结尾空行）做帧内容忍，并在本 Note 与测试中逐项锁定。

### Why not 用调大 max_tokens 或去掉预算来「避免」截断/超限？

max_tokens 是成本与行为的显式旋钮，而不是正确性开关；调大它既不修复完成
判定，也会掩盖 length 分支。三层缓冲预算相反——它们防的是突破 max_tokens 的
失控/恶意端点，触达时显式失败正是期望行为；8 MiB/256 KiB 都远离正常流量
（4096 token 的真实输出在 ~64 KiB 内），不构成功能删减。

### Why not 为「不完整」新增前端 API/事件？

命令层 Err 已经走既有 invoke rejection，前端 `.catch` 有失败与重试入口；
`AiEvent` 增加新变体会扩大 IPC 契约面且与「不新增 UI 接口」的任务边界冲突。
