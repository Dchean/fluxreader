# Agent Note: Fever 身份与完整历史回溯

Status: implemented

## Problem

Fever 协议层有两个被「按 Miniflux 猜」掩盖的兼容缺口（OPT-005，审计 F03/F19），另有一组「缺字段当空集合」的静默风险：

1. **id 类型与进制（F03）**。客户端把所有 Fever id 直接反序列化为 `i64`，而 FreshRSS 的 `p/api/fever.php` 把 64 位 id 作为 PHP numeric-string 序列化——`json_encode` 输出的是 **JSON 字符串**（如 `"1791440000000000"`），不是数字；Miniflux 输出 JSON 数字。字符串形态在旧实现下直接令整个响应反序列化失败（同步当场报错、条目一条也进不来）。
2. **十六进制误判（F03 的另一半）**。旧 `greader::parse_item_id` 对「16 位且全 hex 字符」的 id 一律按十六进制解释。FreshRSS 的 greader `stream/items/ids` 返回的是 64 位**十进制**字符串（固定上游源码 `219eaf58` 的 `streamId` 构造 `'id' => '' . $entryId //64-bit decimal`），Fever 条目 id 同样是十进制字面值：16 位纯十进制被按十六进制解释后会**静默落成另一个 id**，`remote_id` 绑定、已读/收藏对账、跨轮去重全线错位。
3. **完整历史取不到（F19）**。Fever 协议与当前 Miniflux 服务端都支持 `items&max_id` 向更旧翻页（`id < max_id` 取紧邻的最近 50 条），重复请求直到空数组即取尽保留历史；旧实现只有 `since_id` 增量与「最近 50 条」首种子——最近 50 以外、且不进 unread/saved 集合的（已读非收藏）历史条目**永远到不了本地**。把「未读/收藏集合」当作历史全集是错误等价。
4. **缺字段/非法项当空集合**。`unread_item_ids`/`saved_item_ids`/`items` 响应缺字段时旧实现（serde default + `filter_map(..ok())`）静默得到空集合/空列表：空 unread 集合在 Fever 的双向对账里意味着「远端全部已读」，会清掉本地未读状态；非法 CSV 项被静默过滤会把协议错误伪装成「更小的集合」。
5. **R1 追查出的分页/恢复/资源边界**（独立 review P1/P2 + 主控追加）：
   - `since_id` 短页被当结束。FreshRSS `getItems()` 先 `LIMIT 50` 再由 `EntryBeforeDisplay` 扩展 hook 过滤——49 条非空短页后面仍可能有页；提前停会把其后整段（如 201..224 已读非收藏）永久漏掉。
   - 全历史 HTML 在 `all_items` 累计到阶段结束才落库，大账号可达数 GiB 内存。
   - `max_id = i64::MAX` 严格 `<` 漏掉**恰好等于 i64::MAX** 的条目；已读非收藏的它不在权威集合里，`with_ids` 补齐也摸不到。
   - full 第二页失败时 `last_sync_entry_id` 仍被推进到已拉页的最大 id，之后的自动 light 只走 `since_id` 增量、**永远不会自动补旧页**；增量失败后 `with_ids` 补到的大 id 同样会把游标推过未拉区间。
   - 模块注释/Note 把「升序」归因成 Miniflux 事实——固定源码里 Miniflux 的 max_id 页同为 `ORDER BY id DESC`；升序仅是测试夹具的泛化鲁棒性对照。
   - 响应体无读取上限，超大致命。
6. **R2 追查出的事务/状态根因**（独立 review P1/P2）：
   - checkpoint 写失败时 `last_sync_entry_id` 仍可能已推进——「恢复状态」与「增量游标」不在同一事务，任一侧失败就出现「游标过了、续取点没留下」的不可恢复窗口。
   - 页内单条 INSERT 失败只记 report 后继续：该页的已读非收藏条目未入库，但历史 bound 照常推进、甚至最终写「完成」——失败被后续状态掩盖。
   - `resp.bytes()` 后再量长度不是**读取硬界**：无 Content-Length（chunked）或压缩（解压后膨胀）的响应会先整段进内存。
   - 夹具把 with_ids 豁免于 EntryBeforeDisplay hook——固定源码 `getItems()` 对所有分支统一过 hook，被丢弃条目对 Fever 整体不可见。
7. **R3 追查出的最后根因：DB map 读取失败被降级成空映射**（独立 review 唯一 P1）：
   - 初次 `sync_match_maps` 读取失败时旧实现 `unwrap_or_else` 回退空映射继续拉取：空 feed 映射让每条 merge「合法跳过」（找不到本地 feed 就跳过 upsert，这是合法未绑定策略），但页事务照常提交 since/checkpoint，最终写 Complete——本地 0 篇而游标认为历史取尽（永久数据丢失）。
   - 页失败后重建 map 失败同样只置空并继续：增量第二页失败后，顶部回溯以空映射「成功走完」，把 since 伪推进到更大值 + Complete——空洞区间（未合入的页）被伪确认。
   - 根因共性：**DB 错误被当成数据形态处理**（空集合），与「缺字段当空集」「失败 ≠ 空集合」同一族。

## Decision

依据固定上游源码（FreshRSS 219eaf58 的 `p/api/fever.php`；Miniflux `internal/fever/handler.go` 约 227-267 行，见 `tmp/optimization-20261008/upstream/`）与实际测试锁定的形态，代码按以下契约实现：

1. **`FeverId` 单点解析（`src-tauri/src/fever.rs`）**：`id`/`feed_id`/`group_id` 接受合法 JSON 整数与十进制数字字符串（含 `1791440000000000` 量级），一律按十进制解析——**不按十六进制猜、不经 f64 中转**（`visit_u64` 显式检查 i64 范围；实现上有 2^53+1 的单元用例锁「不经 f64」）；非法（`0x` 前缀/空串/非数字）、负值、溢出 i64 全部显式报错（自定义 visitor，错误信息带字段值，不静默过滤）。
2. **`greader::parse_item_id` 按协议形状解析**：规范长格式 `tag:google.com,2005:reader/item/<hex>` 尾部按十六进制（纯数字与含 a-f 都合法）；**无前缀纯数字串按十进制**（FreshRSS greader 十进制长 id、Fever 十进制字面值都是这个形状）；其余形态返回 None——删掉了 `len == 16` 的进制猜测。`ItemContent.id` 仍是十进制字符串字面值，`entries.rs` 的消费点（`remote_id` 绑定/状态合并/guid）不改语义。
3. **字段存在性是协议契约**：`items`/`unread_item_ids`/`saved_item_ids` 方法响应缺对应字段是**协议错误**，不得当空集合/空数组；auth-only 响应（无数据字段）只在认证方法（探测/`resolve`）合法。CSV（权威集合与 `feeds_groups.feed_ids`）中的非法项显式报错，不做 `filter_map(..ok())`。
4. **完整历史回溯（`items_before(max_id)` + `fever_pull` 三段式循环）**：
   - **分页终点是空页，不是短页**：`since_id` 与 `max_id` 两个方向都非空即继续——服务端可先 `LIMIT 50` 再经 `EntryBeforeDisplay` 过滤，非空短页不代表没有后页；把短页当结束会永久漏掉其后整段。
   - 首连/full 从 `max_id = i64::MAX` 顶走；`i64::MAX` 本身由 `with_ids(MAX)` 显式顶覆盖（严格 `<` 摸不到它，且已读非收藏的它不在权威集合里）。游标取**页内最小 id**（两家固定实现页内顺序均 DESC；取 min 对任何顺序都正确）。游标必须严格减小；分页失败或游标不前进（服务端忽略 `max_id` 等）显式记入 `report.errors` 并保留已拉进度，绝不无限循环。
   - **逐页落库释放正文**：合并按页进行（`merge_fever_page` 后该页 `ItemContent` 即释放），内存只留 `seen` 的 id 集合与当前页——不累计全历史。响应体读取有 16 MiB 上限（`MAX_RESPONSE_BYTES`，Content-Length 预检 + 读取后复核），超限显式协议错误。
   - **显式三态 + 页事务（R2；map 失败传播为 R3）**：历史状态为 `fever_history_state` 单键三态——缺失 = **Unknown（绝不当完成**，旧库只有 since 时也据此自动从顶部补旧历史）；`pending:<max_id>` = 未完成；`complete` = 已取尽；其余取值（损坏）**显式报错且不动任何游标、不擅自覆盖**（读取失败同样整轮跳过、游标保留）。每页的「页内所有 DB 写 + 该页 checkpoint/since」在**同一短 SQLite 事务**里提交：任何行/绑定/状态/回填/游标写失败 → 回滚整页，并回滚内存统计与 `seen`，maps 按回滚后的 DB 重建——未提交的绑定绝不进入 `maps`。**R3：map 错误停止传播**——初次 `sync_match_maps` 失败即记 report 并 `return`（本轮不拉取/不合并）；页失败后重建失败同样 `return` 终止整轮，不执行后续 history/with_ids/完成时间。Pending 与已确认 since 保留，由下一次同步重试；绝不再退化空映射。
   - **200 页预算 + 自动续取**：每轮历史阶段至多 [`HISTORY_MAX_PAGES_PER_SYNC`] 页（1 万条）。到达预算 / 分页失败 / 游标不前进都保留 Pending=当前页输入游标（**可重拉**）并记「未完成」；`last_sync_ts`（完成时间）不推进。下一次同步——**包括自动 light**——从 Pending 继续；只有真正走到空页才写 Complete；用户手动 full 从顶部重放（幂等，覆盖旧状态）。**不是**永久只留一万条，也不需要用户手动 full 才能补。
   - **游标只由连续成功范围推进**：`last_sync_entry_id` 只在成功提交的增量页（或从顶部连续走下的顶部页）事务内推进；`with_ids` 补齐、Pending 续取页与失败回滚页都不推动它——增量第二页失败时，被 `with_ids` 补到的大 id（收藏）不得让游标跳过错过的区间；「先初始化 Pending 成功」先于任何更大的 since 落库。
   - 重复条目（历史页重叠、with_ids 与历史页重叠）按 id 去重，不重复处理。
   - **共享合并链路全 Result 化（R2，自 OPT-007 前置吸收）**：`sync/entries.rs` 的 `merge_pulled_entry`/`upsert_remote_entry`/`backfill_entry_content`/`merge_remote_status` 所有 DB 写失败透传 `AppResult`（不再 warn/`let _` 吞）；Fever 侧据此整页回滚；GR 调用点最小适配——记录带条目 URL 的错误并使该块计入失败（时间戳游标不推进），细粒度恢复仍归 OPT-007。
   - **响应硬界（R2）**：`read_envelope` 用 `Response::chunk()` 逐块累计 16 MiB（chunk 上自动解压透明生效，覆盖无 Content-Length 与压缩膨胀），不是「`bytes()` 读全再量长度」。
   - **夹具事实（R2 更正）**：EntryBeforeDisplay hook 对 items **全分支（含 with_ids）**统一生效；125 篇历史用例改用无过滤正常样本；「列表窗口遗漏但 id 可取」只作为**合成形态**单独标注。
5. **同一整数定义贯穿全链**：`mark=item` 的 `id`、`with_ids` 的 CSV、数据库 `remote_id`、权威集合比较都用 `FeverId`/`parse_item_id` 解析出的同一 `i64`；`mark=item` 仍是**逐条单 id**（逗号批量不被协议支持）。
6. **测试锁定分层**：新增 `src-tauri/tests/fever_compat_e2e.rs` 严格夹具（FreshRSS 形态：`id` 为 JSON 字符串、`max_id` DESC、`api_key` 只读 POST body、`mark` 只收单个 `ctype_digit` id、**列表先 LIMIT 再应用 hook 过滤**；可选数字 id / 升序页/重复页/忽略 max_id/故障注入/17 MiB 超大响应），驱动**生产** `FeverClient`/`sync::sync_now`/`sync::sync_light` 真实过 HTTP 层：长 id 往返、125 篇历史全可达（含最近 50 外已读非收藏）、幂等、增量只走 `since_id`、分页失败可重试、游标不前进快速失败、重叠页去重、with_ids 补齐、缺字段/非法 id/非法 CSV 显式错误、mark 逐条；R1 增：短页继续、full 失败→light 自动续取、增量失败游标不被 with_ids 大 id 推动、`i64::MAX` 已读非收藏顶覆盖、200 页预算→下轮续取 10050 条、17 MiB 响应拒绝；R2 增：页事务回滚（真 DB trigger）、状态写失败、三态、预算续取、chunked/brotli 超限拒绝；R3 增：**map 读取失败两个反例**——初始读取列类型错误（url_norm=BLOB）立即终止、页失败后重建列类型错误（页 1 成功提交的 trigger 污染）终止整轮，均断言无假 Complete/since/time 推进、无后续 items/with_ids 请求。共享 `mock_greader.rs` 只补 action 对应字段（宽松空集），不放宽既有断言。

## Consequences

- FreshRSS 与 Miniflux 两种 Fever 实现的 id 都能正确解析：长 id 不再令同步失败，也不会被十六进制误判落成错误 `remote_id`（旧行为下的错绑会在后续同步里持续错位）。
- 首连/full 同步的深度从「最近 50」变为**服务端保留的全部历史**；代价是 full 同步的请求数约 `ceil(N/50)`，手动同步（`full=true`）会付出该成本。轻量后台同步仍只走 `since_id` 增量。
- 失败可见且可恢复：分页失败/预算到达/游标不前进会出现在同步报告里并保存 checkpoint，已拉取的条目保留；`last_sync_ts`（完成时间）在未完成时不推进；下一次同步（含自动 light）自动续取，取尽才清除 checkpoint。游标不前进的服务器得到明确错误而不是死循环或静默截断。
- 内存与响应有界（R2）：历史阶段内存 ≈ 当前页 + id 集合（不再累计全历史 HTML）；单响应 16 MiB 为**读取中硬界**（`chunk()` 逐块累计 + Content-Length 预检快路径；无需新增 feature——reqwest 的 `chunk()` 不在 `stream` 门后）。单轮至多 1 万条不是永久上限（Pending 续取）。
- 事务一致性（R2）：页数据与游标同 commit；失败页全有全无（含内存统计/`seen`/`maps` 回滚重建），不会出现「条目没入库但游标/状态已推进」「未提交绑定被当事实」两个根因。
- map 错误不再退化（R3）：DB 读取失败（初始构建或页回滚后重建）立即终止本轮并保留 Pending/已确认 since，不出现「空映射合法跳过 + 游标/状态伪确认」的数据丢失路径；下一次同步自然重试。
- 游标语义更严格：`last_sync_entry_id` 只反映「连续成功范围」，`with_ids` 大 id 不再能把它推过未拉区间——跨协议切换与后续增量不会因此跳段。
- 缺字段不再可能触发「空集合对账」清状态；非法集合/非法 id 从静默过滤变为显式协议错误（排障看报告即可定位）。
- 与 OPT-007（可恢复 pull）的关系（R1 后更新）：本卡已吸收 **Fever 的 checkpoint/自动续取** 部分（内部 settings 键，无 DB 迁移）；OPT-007 仍负责 GR 侧与所有 DB merge 失败/冲突守卫的细粒度恢复。
- `docs/sync-compat-matrix.md` 的 §1/§5/§6-L2 同步更新（Fever 历史回溯从「未实现」改为「已实现 + checkpoint 自动续取 + 严格夹具验证」；Miniflux max_id 页序更正为 DESC；真实部署版本仍未实机验收）。

## Alternatives considered

### Why not 继续用 `i64` 字段 + 按 `len == 16` 猜十六进制（旧行为）？

字符串 id 直接反序列化失败（FreshRSS 上整轮同步报错）；而 16 位纯十进制按十六进制解释是**静默错误**——比报错更糟：`remote_id` 落成另一个数，对账按错误的键匹配，条目状态与去重都会错。按长度猜进制没有协议依据，「协议形状」（前缀 tag / 无前缀十进制）才是可判定的依据。

### Why not 用 serde `untagged enum`（Num(i64)/Str(String)）？

`untagged` 的错误是统一的「data did not match any variant of untagged enum」，非法/负值/溢出/浮点无法区分、信息也弱；自定义 visitor 可以给每种非法形态明确文案（含字段值），且能挡住 `0x`/`-`/f64 这些歧义输入。契约要求「非法/溢出/负值有明确错误」，visitor 是直给解。

### Why not 全链路保留字符串 id（不转 i64）？

`articles.remote_id`/`feeds.remote_id` 是 SQLite INTEGER，`mark`/`with_ids`/去重/排序比较都依赖整数语义；全链路改字符串会把写集扩大到 DB、命令层与 OPT-004 刚验证过的读出路径，收益只是「省一次解析」。在本卡写集内单点转换（`FeverId`/`parse_item_id`）即可保证「所有比较使用同一整数定义」。

### Why not 保留「最近 50 + 未读/收藏集合」当首同步（旧行为）？

最近 50 以外、且不在 unread/saved 集合里的已读非收藏条目没有任何路径能到达本地（`with_ids` 只按已知 id 补正文）——这正是 F19；把「未读/收藏集合」当历史全集是错误等价，卡片明确禁止。

### Why not 历史回溯只在本地空库（`last_sync_entry_id == 0`）时做？

翻页中途失败后游标已被写成「已拉到的最大 id」，下一次同步就走增量分支，缺失的老历史永远不会再补——不可恢复。full/手动同步每次从顶部重走（幂等合并 + 按 id 去重），失败可重试，是有恢复语义的实现。

### Why not 用「页内第一条/最后一条」当游标（依赖页内顺序）？

两家**固定实现**的 max_id 页均为 `id < max_id ORDER BY id DESC`（R1 更正：此前误记 Miniflux 为升序；升序只是测试夹具的泛化鲁棒性对照）。取**页内最小 id** 不依赖「第几条」的位置语义，对任何顺序都正确，且对「同页重复条目」也稳定（min 不受重复影响）。

### Why not 对缺字段回退成空集合、只记日志？

空 unread 集合在 Fever 双向对账里语义是「远端全部已读」，会把本地未读批量翻成已读；空 `items` 会静默结束历史回溯。两者都是数据损坏而用户只看到「同步成功」。协议错误必须向上传播（`report.errors`），对账守卫（reconcile_ok）随之中止本轮。

### Why not 对不支持 `max_id` 的服务器无限重试或把游标 +1/−1 硬推？

硬推会在服务端语义为「含边界」时漏条目、在「忽略参数」时无限循环或拉重复页。实现选择「游标必须严格减小，否则显式失败」：服务器实现不符时用户看到明确错误，重试留给 full 同步；不会死循环，也不会静默丢历史。

### Why not 把重复页条目也重复合并（幂等所以无所谓）？

合并本身幂等，但重复处理会撑大 `pulled_entries` 等统计、做无谓的状态写入，还把「服务端分页异常」掩盖成正常流量。按 id 去重后，`pulled_entries == 唯一条目数` 本身成为可分页异常的可断言信号（夹具用例即以此锁去重）。

### Why not 把 `since_id` 短页（<50 条）当拿完（旧增量行为）？

真实服务端可「先 LIMIT 50 再 hook 过滤」，短页是**过滤结果**而非「数据见底」；把短页当结束会漏掉其后整段（R1 的 151..224 反例），且这些已读非收藏条目没有其他路径可达。分页终点只认空页；代价是每轮多一次「空页探测」请求。

### Why not 全历史先收进内存再统一落库（旧 `all_items` 行为）？

5 万条 × 100 KiB 正文可达数 GiB，一次同步就能把桌面端打爆。逐页合并后内存 ≈ 当前页 + id 集合；合并本身幂等且 maps 增量更新，逐页与批量在结果上等价。

### Why not 预算到达时按「成功」收尾、把完成时间推进？

那会把「只拉了一万条」伪装成「历史已同步完成」，用户看到成功但旧文章永远缺（除非再等一个 full）。预算到达必须记入报告、不推进完成时间、保留 checkpoint——诚实反映未完成。

### Why not 历史未完成只支持「用户手动 full」来补？

主控明确要求自动恢复：普通定时 light 同步打开应用时就会续取，用户无需任何操作；手动 full 保留为「从顶部重放」的选项（幂等，覆盖 checkpoint）。仅当自动路径失败（如 checkpoint 损坏）时才退化为 top walk。

### Why not 让 `with_ids` 补齐的结果也参与推进 `last_sync_entry_id`？

`with_ids` 是按 id 的点查（可返回远超增量窗口的大 id），把它计入游标就等于宣布「大 id 以下全部已拉」——增量第二页失败时会把 151..224 永久跳过（R1 反例）。游标只认「连续成功范围」，with_ids 与 checkpoint 续取页都是旁路。

### Why not 用 `max_id = 0`（或某个自定上限）当历史起点来覆盖 `i64::MAX` 边界？

`max_id = 0` 的含义是「id < 0」→ 永远空页，不是「从头」；自定上限则依赖服务端 id 域假设。`i64::MAX` 是解析层的合法上界，顶走 + `with_ids(MAX)` 显式覆盖边界是唯一不猜服务端域的写法。

### Why not 页内单条失败仍记 report 后继续（R1 行为）？

那会出现「条目没入库但游标/状态已推进」：失败条目既不在重拉窗口里，又可能被最终 Complete 掩盖（R2 反例：remote-100 INSERT 失败后 124 条入库、状态照常推进）。页事务让失败页整体留在「未完成」状态、下次原页重拉——代价是一页 50 条随一条坏行重拉（幂等，无副作用），换的是不丢数据。

### Why not checkpoint/since 在阶段末尾统一写（而不是页事务内同 commit）？

末尾统一写存在两个失败窗口：checkpoint 写失败时 since 已推进（不可恢复），或 since 已推进而页数据未落（重复/交错）。页事务把「该页数据 + 该页游标」绑成原子提交，失败时两侧一起回到页前状态；「先初始化 Pending 成功才允许更大的 since 落库」封掉最后一个顺序窗口。

### Why not 损坏状态按 Unknown/完成处理、或静默 reset？

按完成 → 旧历史永远不补；按 Unknown → 用「从顶重放」掩盖现场，且与「键值损坏」这一异常混为一谈。显式 Err + 不动任何游标 + 不覆盖现场，让用户/排查者能看到真实状态；同步在修好前不拉取条目是安全侧（下一次照样重试）。

### Why not 用 `resp.bytes()` 后量长度当 16 MiB 硬界？

`bytes()` 是「先整段读进内存」——无 Content-Length（chunked）或压缩膨胀的响应在被拒绝前就已占用内存，界只在事后成立。`Response::chunk()` 逐块累计把它变成读取中的硬界；reqwest 的 `chunk()` 不需要 `stream` feature，`gzip`/`brotli` 解压在其上透明生效，因此压缩炸弹同样被拦住（夹具用 40 字节 brotli → 17 MiB 解压验证）。

### Why not 夹具继续把 with_ids 豁免于 hook？

固定源码 `getItems()` 对含 with_ids 在内的所有分支统一调用 `EntryBeforeDisplay`；豁免会造出「hook 丢弃的条目仍能按 id 取回」的伪事实，并让「列表遗漏」类用例冒充 FreshRSS。R2 起 hook 统一施加；真正「列表覆盖不到但按 id 可取」的形态（保留/窗口差异）只作**合成**开关，用例名与注释均标注不代表 hook。

### Why not map 读取失败退化为空映射继续（R2 行为）？

空 feed 映射不是「保守的空状态」而是**主动的错误事实**：merge 因找不到本地 feed 而「合法跳过」（这正是未绑定 feed 的正常策略），但页事务会照常提交游标——初次失败时顶部回溯空走到底并写 Complete（本地 0 篇）；重建失败时增量空洞区间被顶部回溯伪确认（since 推到更大值 + Complete）。两者都是「DB 错误被当数据形态」，必须错误传播、立即终止本轮；保留 Pending/已确认 since 让下一次同步自然重试，代价只是一轮同步推迟，换的是不丢数据。注意：**不改**合法未绑定 feed 的跳过策略——只禁止把 DB 错误转成空映射。
