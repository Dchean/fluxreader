# Agent Note: 乐观写入的版本守卫

Status: implemented

## Problem

读状态与收藏先在界面显示，再异步落库。旧请求失败时若直接写回旧值，会覆盖用户在等待期间的新动作；只比较值又分不清“没操作过”与“操作后恰好回到同值”。文章级共享版本还会让读与收藏这两个独立字段互相作废。

## Decision

按条目×字段保存内存版本，键为 `${id}|${field}`。真实字段翻转推进版本；完整会话全读对每个捕获成员登记本次意图，即使该ID尚未驻留或当前已读。`EntryRollbackClaim`记录发起时版本，`rollbackEntryClaims`只接受仍匹配的凭据。回滚本身不推进版本，避免同一次操作的清理相互作废。

单条、批量与打开文章的乐观路径复用同一套助手。后端真实写入回执、读取发起时的写前沿、在途字段保护以及 `counts_snapshot` 有序落地，是版本守卫之外的契约，见[查询与分页契约](2026-10-05-查询与分页契约.md)。计数不能从可折叠副本的显示行简单加减；当前会话全读即使返回空翻转回执，仍收敛捕获成员并对账，不能把“已无新翻转”当作计数已新鲜。旧范围命令的affected=0处理理由继续适用于这一空回执边界。

版本相等只回答“此失败是否仍有资格回滚”，没有给出“应该回滚到哪一份已确认真值”。2026-11-06 基线的双失败探针确认：连续相反操作都失败时，第二笔保存的旧值可能是第一笔尚未提交的乐观值，最终数据库为 false 而界面为 true。原文把这一类窗口写成“有意保留、增加值比较即可解决”不成立。

同日首批修复将连续 toggle 的暂存归属绑定到条目×字段的当前版本，修复双失败目标。2026-11-07 独立审计又证实两笔成功若在后端逆序执行，原末次 false 意图仍会被旧 true 写覆盖；仅使 UI 回读为 true 虽能消除分叉，也会丢失用户最后意图，未采用。

后续修复在 API 的第一个 await 之前登记两条 Promise 前沿：`setRead / setReadBulk / markAllRead` 共用读前沿（也包含同文读闭包），`setStarred` 使用独立收藏前沿。后笔在前笔成功或失败后才实际进入 IPC；前笔失败继续后笔，错误仍回到各 action 可见处理，尾引用只由自己清理。界面乐观翻转仍立即执行，read/star 互不阻塞。不依赖 IPC FIFO 或 DB Mutex 的竞争顺序；范围/批量覆盖未知行或闭包兄弟，因此选择按字段共享前沿，而非只给单篇 toggle 排队。

失败投影扩展为所有本机标读入口共用的 `trackEntryFlagWrite`：首笔保存链基线，每笔保存目标值与结算结果；失败只排除本笔意图，按发起顺序求最后仍有效目标，全部失败则回到基线。2026-11-07 R1复审在范围标读成功、后续未读失败且已切源时证伪了“可见行由助手恢复、离屏由原范围上下文恢复”的分工：链正确求出已读目标，但助手只遍历活跃entries，原范围又已被后续版本接管，最终离屏缓存与计数无人恢复。回页reload才修正不满足过程验收。

随后将字段提交收敛到 `projectEntryFlags`。乐观翻转/批量标读、真实读回执和失败投影在同一资格下更新活跃entries及所有现存视图缓存副本；同一条目×字段只计算一次按源计数差，不按副本数量增减。`rollbackEntryClaims`保留字段版本资格而委托该提交点。2026-11-09会话全读的目标改为已捕获完整memberIds，不能再按动态收藏/今天/布局scope扩大成功投影；未实际写入的搜索实体不跟随，成员外真实组兄弟只根据后端回执更新。已读保留上下文的恢复仍由nav处理，因为它不是条目标志字段。

在途链保存基线、意图和源计数实际已经反映的值，故LRU淘汰不丢计数归属，也不重建已淘汰键或插入窗口外成员。完整成员的未驻留基线可以未知：首次真实属性补入原值并被pending意图覆盖显示；失败时恢复真实基线，属性尚未到则撤销未知目标。可见true不等于已对源计数扣过1，计数差以实际已投影值为准，避免失败时501虚增成502；该边界不依赖权威计数此刻可用。已有驻留/缓存副本仍照常参与乐观投影。

同id多缓存来源冲突、来源接管或离屏归属不确定时，不把差值强行归给扫描到的旧来源，最后一笔写结算后沿既有`counts_snapshot`协议权威校准；过期只做有界补查，新在途写则由其最后结算接手。scopeCounts仍由后端非线性聚合提供，从不按字段或副本数线性推算。读取失败保留最后已知计数与已确定本地差值，后续刷新恢复。

外部快照/非本链写入推进字段版本后，旧链仍不能恢复自己的值；这不扩大旧视图快照的成员/新鲜度语义。链内全部结算后释放pending记录。为保护可能随后首次出现的旧尾页，轻字段值与版本前沿继续由当前有效成员/驻留实体/有界缓存/在途读写持有；引用全部结束后统一回收，不永久保存所有未来条目。新鲜读取仍可接受后端值。测试的只读前沿等待函数仅等待实际IPC，不能清空队列或取消用户意图。

## Alternatives considered

- **只比较当前值与请求值**：无法区分同值的新操作，不能替代版本身份，也不能解决连续失败缺少已确认基线的问题。
- **文章级共用版本**：收藏更新会无端使读回滚失效；字段独立版本保留了必要的并行性。
- **失败后只等 reload**：会长期展示未落库的结果，故保留及时回滚；reload 是恢复手段，不能证明回滚正确。
- **每次后端返回整份计数与状态**：扩大命令返回和查询成本；当时选择真实影响回执加独立计数快照。若未来收拢状态基线，应同时评估读取时序，不能直接整体覆盖。
- **重叠写后只回读/反复校准末意图**：只回读仍可能把旧写覆盖后的值当最终结果；额外校准又需代次、失败、重入与重试边界。现有四个 API 共用两个 Promise 前沿更小，代价是同字段不同条目也按序等待。
- **离屏失败只失效缓存再等回页reload**：会让回页第一态丢失已可确定的字段投影，单独刷新计数也不能修缓存。选择同一提交者发布可见与离屏副本，淘汰时保留轻量在途账本。
- **只保护当前驻留行/给所有成员永久保存字段shadow**：前者漏掉先发迟到的未驻留尾页，后者把每次全读变成长会话无限累积。采用完整成员声明及读取租约，由实际会话/缓存/在途生命周期持有。

## Consequences

按字段版本缩小了旧失败覆盖新操作的范围，代价是必须协调回执、快照与回滚三类写者。每条在途链保留基线与意图直到全部结算，轻字段前沿则延续到相关读取/成员/缓存释放；完整成员全读的轻状态随有效成员数线性增长。字段发布扫描有界视图缓存（最多8键，每键1000条），本轮没有用此数量上限替代真实长会话性能测量。API同字段写执行有序，但它们不共享事务，也不对远端同步、其它窗口或进程建立全局顺序。慢读态请求会延后其它本机读态写，也会延长保护前沿寿命；UI仍即时反馈，收藏独立。版本只在本进程存活，重启真值仍来自数据库。
