# Agent Note: 乐观写入的版本守卫

Status: implemented

## Problem

读状态与收藏先在界面显示，再异步落库。旧请求失败时若直接写回旧值，会覆盖用户在等待期间的新动作；只比较值又分不清“没操作过”与“操作后恰好回到同值”。文章级共享版本还会让读与收藏这两个独立字段互相作废。

## Decision

按条目×字段保存内存版本，键为 `${id}|${field}`。真实字段翻转推进版本，`EntryRollbackClaim` 记录发起时版本，`rollbackEntryClaims` 只接受仍匹配的凭据。回滚本身不推进版本，避免同一次操作的清理相互作废。

单条、批量与打开文章的乐观路径复用同一套助手。后端真实写入回执、读取发起时的写前沿、在途字段保护以及 `counts_snapshot` 有序落地，是版本守卫之外的契约，见[查询与分页契约](2026-10-05-查询与分页契约.md)。计数不能从可折叠副本的显示行简单加减；现有 `affected === 0` 省略对账仍可能保留已有陈旧计数，后续读取才纠正。

版本相等只回答“此失败是否仍有资格回滚”，没有给出“应该回滚到哪一份已确认真值”。2026-11-06 的双失败探针确认：连续相反操作都失败时，第二笔保存的旧值可能是第一笔尚未提交的乐观值，最终数据库为 false 而界面为 true。原文把这一类窗口写成“有意保留、增加值比较即可解决”不成立；已改为待修缺陷，见[阅读与状态路线](../../../../docs/roadmap.md#reader-and-state)。确认基线与未提交意图的方案尚未实施。

## Alternatives considered

- **只比较当前值与请求值**：无法区分同值的新操作，不能替代版本身份，也不能解决连续失败缺少已确认基线的问题。
- **文章级共用版本**：收藏更新会无端使读回滚失效；字段独立版本保留了必要的并行性。
- **失败后只等 reload**：会长期展示未落库的结果，故保留及时回滚；reload 是恢复手段，不能证明回滚正确。
- **每次后端返回整份计数与状态**：扩大命令返回和查询成本；当时选择真实影响回执加独立计数快照。若未来收拢状态基线，应同时评估读取时序，不能直接整体覆盖。

## Consequences

按字段版本缩小了旧失败覆盖新操作的范围，代价是必须协调回执、快照与回滚三类写者。版本只在本进程存活，适用于会话内竞争；重启后的真值仍来自数据库。它是必要的局部守卫，不能单独保证任意并发序列收敛。

## Verification

历史回归覆盖跨字段、旧失败与批量回执；2026-11-06 基线 `91ece562` 的反例以两个真实拒绝顺序检验回滚目标，证明上述剩余边界。验证状态集中在路线与审计交付，历史理由见[整理前记录](https://github.com/Dchean/fluxreader/blob/91ece562d79fd909642cd6d570d636e884b7387e/.agents/notes/implemented/architecture/2026-10-05-乐观写入的版本守卫.md)。
