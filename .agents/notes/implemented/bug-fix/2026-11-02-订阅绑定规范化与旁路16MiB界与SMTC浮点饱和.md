# Agent Note: 订阅绑定规范化、旁路 16MiB 界与 SMTC 浮点饱和

Status: implemented

## Problem

2026-11-01 审计 P3 的三个缺口，同批收口：

1. **push_feeds 绑定查找漏判**：quick_add 成功后的本地绑定用
   `feed_id_by_url` 精确匹配且 `.ok()` 吞掉 DB 错误。legacy add_feed
   队列携带的 URL 与本地入库字符串常有尾斜杠/www. 差异，精确匹配漏判成
   「本地已删除」→ 订阅推送成功却永不绑定，该源在 pull 侧被当未绑定源
   重复处理；DB 错误被吞后问题现场不可见。
2. **两条旁路读取无大小上限**：feed 主管线有 16MiB 界
   （`ingestion/http.rs` 的 `read_capped`），但 favicon 站点首页
   （`favicon.rs`）与全文提取（`commands/settings.rs`）都直接
   `text().await` 无界读取——恶意/异常站点可用超大响应撑爆内存。
3. **SMTC 浮点 panic 静默失效**：`media.rs` 三处
   `Duration::from_secs_f64(x.max(0.0))` 只防了负值——`from_secs_f64` 对
   超范围有限值（如 1e30）与 +inf 同样 panic，而 panic 发生在 SMTC 专用
   线程的指令循环里，线程静默死亡，此后媒体键/进度条全部失效且无日志。

## Decision

1. 绑定查找改 `db::feed_id_by_url_normalized`（与 pull_feeds、OPML 去重
   同一规范化口径）：`Ok(Some)` 走既有绑定写回，`Ok(None)` 维持无绑定，
   `Err(e)` 复用 folder_label 解析失败的处置——warn + `report.errors.push`
   + `continue`，队项不进 done、下轮重试。
2. `read_capped` 泛化为 `pub read_body_capped(resp, max_bytes)`（tests 是
   独立 crate，必须真正 `pub` 才能从 `app_lib::ingestion` 访问），
   `conditional_get` 内部改调用（fever.rs 自有的 Fever 协议读取不动）；
   favicon 首页与全文提取改经该 helper：favicon 超限并入既有「任何失败
   返回 None」负缓存，全文提取超限映射
   `AppError::new("responseTooLarge", "网页正文超过 16 MiB，已放弃提取")`。
   收字节后的解码经 `decode_body_bytes` 按 Content-Type charset 进行
   （encoding_rs 升为直接依赖，语义与 `reqwest::text()` 一致：无 charset
   头默认 UTF-8、BOM 优先、无效字节 lossy）——GBK/GB2312 站点按 UTF-8
   硬解会把乱码写进 content_html 并推进修订。
   loopback mock 的超量响应**不得声明 Content-Length**：hyper 客户端按
   CL 定界，谎报小 CL 只会让 body 提前完成（截断），「谎报绕过上限」
   不可达；超量数据用 `Connection: close` + EOF 定界发送，累计分支的
   防线语义是「无 Content-Length 定界（chunked/EOF）的超量流式响应」。
   连带修复 `discover_favicon` 的 base 丢显式端口——丢端口会把带端口的源
   （含 loopback 测试）探到默认端口的另一个 origin 上，也让超限回归测试
   根本无法指向 mock；保留端口后探测严格回到源站同一 origin。
3. `media.rs` 顶部（cfg 之外）加 `media_secs`：NaN 归 0（`f64::clamp`
   对 NaN 返回 NaN，须先单独判）、负值归 0、超大有限值与 +inf 钳到
   `MAX_MEDIA_SECS = 7 天`（播客单集时长的语义上界），三处
   `from_secs_f64` 入参全部经它，保证构造器不 panic。
4. **订阅 outbox 已消失账号生命周期延后**（登记进 docs/roadmap.md）：
   可选处置是身份切换即清账，但必须放弃「换号 → 回原账号恢复 pending
   意图」的语义——这是产品级取舍，不属本轮修缺陷的裁量范围，待产品
   拍板后另行立项；本轮不动 `db/outbox.rs` 与 `commands/sync.rs`。

## Alternatives considered

### 绑定查找失败改为中断整轮推送

单条 DB 错误说明库侧有系统性问题，中止整轮更保守；但 push_feeds 本就是
best-effort 阶段，既有口径是「单条失败保留队项下轮重试、不阻塞其余
订阅」，中断反而扩大失败面。沿用单条 continue，否决整轮中止。

### favicon 超限走独立的小上限（如 1 MiB）

首页 HTML 真实极少超 1 MiB，小上限更省内存；但引入第二个界就多一条要
维护的事实，且 favicon 读取在 5s 超时内、非关键路径，16MiB 共用界足够
防耗尽内存。共用 `MAX_BODY_BYTES`，否决独立上限。

### SMTC 饱和上界取 i64::MAX 秒等「永不截断」口径

语义上 7 天已是荒谬的单集时长，截断到它不损任何真实场景；而把
`Duration` 顶到 `u64` 秒级上界会让系统媒体浮层显示出荒谬进度条。7 天
上界 + 注释说明 panic 条件，否决。

### 本轮顺带清账已消失账号的 outbox

见 Decision 4：清账隐含放弃回原账号恢复语义，属产品决策；越权清账会把
「待恢复」的合法 pending 意图不可逆删除。仅登记，不动 outbox 代码。

## Consequences

收益：URL 变体订阅的绑定缺口闭合（与 pull/OPML 同口径）；三条无界读取
全部收到 16MiB 界内；SMTC 线程对任意浮点入参免疫，媒体控制不再静默死亡。
代价：favicon 对带端口源的行为变化（探测 origin 修正，严格更正确）；
全文提取超限时用户看到显式错误而非挂死。验证：`cargo fmt --all --
--check` 本机必过、`rg` 确认两条旁路无 `text().await`；行为断言由新增
单测/e2e 锁定并由 CI 承担（本机不可链接 Rust）：`push_feeds` 绑定规范化
用例（`opt009_phaseb_e2e.rs`）、`read_body_capped` 预检/累计/通过三分支
单测（`http.rs`）、全文提取谎报 Content-Length 超限用例
（`settings.rs`）、favicon 超大首页负缓存用例（`favicon.rs`）、
`media_secs` 纯函数单测（`media.rs`）。
