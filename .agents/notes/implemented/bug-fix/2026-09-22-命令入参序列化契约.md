# Agent Note: 命令入参序列化契约

Status: implemented

## Problem

列表查询命令的入参结构 `ArticleListArgs` 上带了 `#[serde(rename_all = "camelCase")]`，而前端按 snake_case 发字段。运行时没有报错——当时该结构的 9 个字段里有 7 个被**静默丢弃**（`feed_id` / `folder_id` / `only_unread` / `only_starred` / `only_today` / `newest_first` / `limit` 等筛选与排序参数），后端于是恒按「全局、降序、无筛选」查询。

用户可见的表现有三个，看起来毫无关联：单源视图空白、社交布局「一直加载正文」、某些筛选条件完全不生效。它们同源于一个序列化属性。

根因是一条容易被忽略的 serde 规则：**`#[serde(rename_all)]` 只作用于命令形参名，不作用于形参内部对象的字段**。也就是说，`#[tauri::command] fn list_articles(args: ArticleListArgs)` 上的属性不会传播到 `ArticleListArgs` 自己的字段上；而这个结构体自身若带了 `rename_all`，它的字段就必须按 camelCase 传。

## Decision

**删掉 `ArticleListArgs` 上的 `rename_all`，与前端现有的 payload 一致。** 前端发的是 snake_case，结构体字段也是 snake_case，两边对齐即正确。

**命令形参名与结构体字段名的命名空间是两件事**，Tauri 命令层要遵循前端调用约定，但结构体自身的 serde 属性是独立决定。这条区分写在这里，是因为它容易被「统一改成 camelCase」这类看似整洁的改动破坏。

## Consequences

**收益**：列表查询的筛选、布局、排序参数真正生效；三个看起来无关的用户可见缺陷同时消失。

**代价与已知上限**：

- 前端 payload 与 Rust 结构体的字段名必须逐字一致，而这类不一致在 Rust 侧**不会编译报错**，只在运行时静默丢弃字段。这是本类缺陷的根本风险。
- 备选中提到的「改前端发 camelCase」方向同样能修好，但它会打红 8 处既有断言并连带修改假后端（mock）——那是把一致性成本转移到测试面上。

## Alternatives considered

### Why not 保留 `rename_all` 并改前端发 camelCase？

两个方向在功能上等价，但成本不同：改前端要同时改 8 处断言与假后端的反序列化逻辑，而这批断言锁定的正是「前端如何调用后端」这个契约——改它们意味着一次契约迁移。删属性则是最小改动，且让属性与既有前端一致。

### Why not 在 Rust 侧加运行时校验，字段不匹配就报错？

对每个命令结构体加校验是可能的（比较反序列化后的字段数与默认值），但会给所有命令引入运行时代价与样板代码。更实际的做法是在协议层保持简单：字段名一致，靠集成测试覆盖真实调用。当前由 `src-tauri/tests/` 下的 mock 集成测试覆盖真实调用形状。

### Why not 两边都不用 snake_case，全用 camelCase？

可以，但同样是一次契约迁移，且会把上面那条「形参名与字段名是两个命名空间」的规则藏得更深——下次有人在命令上加属性时仍会犯同样的错。

## Testing

审计时用状态探针复现了这个缺陷（探针发出的 payload 与前端一致、观察后端实际收到的筛选条件）。修复后的回归保障是 mock 集成测试：假后端逐字复刻被验证方的反序列化与默认值逻辑，字段被丢弃时测试会失败。这条「mock 必须逐字复刻被验证方」的纪律写在[验证方法与复核纪律](../testing/2026-09-22-验证方法与复核纪律.md)里——如果 mock 比真实实现「更宽容」，它会掩盖这类缺陷而不是暴露它。
