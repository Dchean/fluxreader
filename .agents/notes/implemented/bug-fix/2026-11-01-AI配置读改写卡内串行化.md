# Agent Note: AI 配置读改写卡内串行化

Status: implemented

## Problem

AI 服务设置（AiTab）的三个写入口——「测试连通性并保存」（testAndSave）、「保存提示词」（savePrompts）、「切换模型」（selectModel）——各自独立 `getAiConfig → saveAiConfig`。并发时后完成者覆盖先写者：testAndSave 更是整包快照落库（`JSON.stringify(cfg)`，闭包捕获点击时的表单），在途期间用户对 Key 或提示词的编辑会被旧快照冲掉。库里的 ai_config 是一个 JSON blob，任何写入口都是整 blob 覆写，冲突面是全字段。

与 feed 级 AI 开关的写协议（[AI配置写入与快照对账](../architecture/2026-10-10-AI配置写入与快照对账.md)，`aiConfigWrites.ts`）不是同一层：那份协议管 `set_feed_ai_modes` 的多键意图队列；本篇管 AiTab 对 ai_config 单 blob 的读改写，blob 没有键级队列可挂。

## Decision

**卡内模块级 promise 链**：`aiConfig.ts` 新增 `enqueueAiConfigWrite(op)`——三个写入口全部入队，前一笔写（含失败）落定后下一笔才执行。

- **执行时重读**：队列里的写入执行时才 `getAiConfig`，基于库内最新配置合并自己的字段（`mergeConfigFields`/`mergePromptsOnly`）——后写者不再用发起时的旧快照整包覆盖。
- **字段收窄**：testAndSave 从「整包快照」收窄为端点四字段（preset/baseUrl/apiKey/model），不再顺手覆盖提示词与模型并发写入；savePrompts 只重放两个提示词字段（既有语义）；selectModel 只重放 model。
- **草稿与测试快照分开**：2026-11-09 以已确认的测试身份一致契约取代早期“测试落库取执行时刻表单”。测试捕获点击时的端点四字段与编辑代次，排队、测试返回、配置回读后均复核；草稿变化时拒绝陈旧结果进入保存，提示重新测试并保留草稿。保存已发出后才编辑则已测快照仍可落库，但明确提示新草稿未保存，不把成功身份移给新草稿。提示词保存仍按执行时刻的最新草稿合并，模型选择只重放该次 model。
- **初始快照的字段资格单调失效**：初始回读仅能恢复“本挂载仍存活且未被用户意图接管”的字段。接管不仅是敲过键，也包括已明确测试/保存的默认值；接管不因成功、失败或请求结束而释放，初始读取不能充当隐式回滚。字段变更后的测试代次仍检查新编辑，但不能代替初始读取资格。
- **跨挂载的读取前沿**：新页面先在现有模块写链插入一个空屏障，等挂载时已经排队的写入结束，再发自己的初始读取；真正的 `getAiConfig` 不放进写链，慢读取不会阻塞当前编辑、测试或提示词保存。旧页面的初始响应按实例失效；已经授权的写入继续安全完成，但卸载后不更新旧页面状态或发成功提示。
- **读取失败可恢复，写前不伪造空配置**：初始读取拒绝、坏 JSON、非对象或已知字段类型错误显示简短错误与“重试读取”。重试仍遵守相同字段资格。三个写入口都会校验自己新读到的存储值，失败则不发覆盖写；真正的 `null` 才表示未配置。修复不把损坏配置交给旧 merge helper 的重建回退。
- **点击顺序即落库顺序**：入队的是整个入口（含连通性测试的 await），不只落库段——若只排落库段，后点先测完的写入会先执行，乱序依旧。

字段归属如下，只有最后一列允许初始读取落地；其余时候字段保持现有草稿，持久化由显式操作负责：

| 动作/阶段 | 接管的字段 | 初始读取仍可恢复 |
| --- | --- | --- |
| 页面初始读取 | 无 | 全部尚未被操作的字段 |
| 输入单字段 / 更改服务商预设 | 实际编辑字段；预设同时接管 preset/baseUrl/model | 其它未接管字段 |
| 输入有效后点击测试并保存 | preset/baseUrl/apiKey/model 四项，包括未手工改过的显示默认值 | 未编辑、未保存的提示词 |
| 点击保存提示词 | summaryPrompt/translatePrompt 两项，包括未手工改过的显示默认值 | 未接管的端点字段 |
| 选择模型 | model（端点的测试前置已经接管其余端点字段） | 未接管的提示词 |
| 测试/写入进行中、成功或失败 | 保留已取得归属，不释放 | 仍未接管的独立字段 |
| 卸载 / 新挂载 | 旧读取失效；新实例重新建立归属 | 新读取等既有写前沿后，仅恢复新实例未接管字段 |

反向注释：`src/components/settings/aiConfig.ts` 的 `enqueueAiConfigWrite` 头注。

## Alternatives considered

### Why not 接入 aiConfigWrites.ts 的意图队列协议？

那份协议面向「按键独立的实体字段写」（feed AI 开关），提供乐观落地、per 键队列、快照对账；ai_config 是单 blob 整读写，没有键级意图可言，接入要先把 blob 拆成键级模型——超出本卡边界且改变持久化格式。模块级串行链覆盖本卡列明的三个入口；其他直接写入ai_config的入口需另行协调。

### Why not 互斥锁（禁用其它两个入口直到在途写完成）？

测试在途时「保存提示词」按钮必须可用（用户路径：在途改 Key 后保存提示词）；UI 互斥把并发问题变成入口可用性编排，且卸载重挂后 busy 状态丢失。promise 链与挂载解耦（模块级），行为与 UI 状态无关。

### Why not 只把落库段入队（保留测试并发）？

串行化判据会退化成「落库发起顺序」而非「点击顺序」：后点先测完的写入先落，先点的旧值后落——正是要修的错序。整入口入队牺牲一点并发度（测试在途时后续写排队），换来可推理的顺序不变量。

### Why not 初始加载完成前禁用测试和保存？

能防止初始响应跨越操作，但慢读取会阻塞用户已经输入的有效草稿和独立提示词保存。明确操作本身已经说明用户要使用哪份显示值，按字段接管可保留编辑能力，又不会让旧读取覆盖已测试或已保存值。新挂载仅等已有写前沿，避免读取已知尚未落定的存储；不新增全局事件系统或第二条写队列。

## Consequences

**收益**：三个入口按入队顺序合并各自字段，测试与保存使用同一端点身份；用户在途编辑保留在草稿并可重新测试。testAndSave 不顺手持久化提示词，提示词与模型并发写入也不丢字段。

**历史取舍与后继**：早期为防止在途新 Key 被旧闭包覆盖，选择落库时读取最新表单，并接受测试 A、保存 B。2026-11-08 审计实际复现身份错配，2026-11-09 已确认草稿应保留但未测试配置不能沿用成功提示。首轮以编辑字段和测试代次保护，第二轮补初始恢复推进代次，都只能保护尚未完成的测试；独审继续复现“测试 A 已保存成功，再来旧初始 B，UI 变成 B 而存储为 A”。因此改用上表统一的初始读取资格，取代“仅保护手工编辑字段”的规则。固定测试快照、串行字段合并和新编辑使测试失效的原理由继续有效。

**代价与已知边界**：编辑后需重新测试才保存新端点；已经发出的保存不能撤回，但落库身份始终是已测试快照。显式测试失败后也保留该次显示的端点草稿，不让旧初始值替换它；用户可修正重试，重新打开页面才重新读取完整已存配置。队列是模块级单链，跨 AiTab 挂载存活；已结算链不另存历史任务，仍在等待的操作可持有其捕获上下文。回归 `tools/component-tests/ai-config-race.test.mjs` 覆盖初始读取在测试前/中/写前/写中/成功后/失败后的到达、不同字段编辑、默认提示词保存、卸载重挂、读取/格式失败重试，以及既有提示词/模型真实并发和后笔失败恢复。IPC 被替身，不代表任意 AI 服务端或真实 SQLite 时序已验证；当轮结果和独审状态只记于交付入口。
