# Agent Note: 发布前自检的缺陷集群与遗留

Status: implemented

## Problem

发布前做过一轮三路自检（前端状态、界面一致性、Rust 后端），共发现 56 项（P0×0 / P1×6 / P2×12 / P3×38）。逐项修完后，有三类东西值得留下：

1. **反复出现的根因模式**（比单个缺陷更值得记）；
2. **显式不修的边界**（不记下来会被后人当成遗漏，然后「顺手修」）；
3. **仍未修的真实遗留**（避免被误认为已收口）。

## Decision

### 三条根因模式

**同一个校验在两层都缺**：`folderId = 0` 从前端直通到后端。前端未把「无分类」转成 `null`，后端 `add_feed` 也不校验 `folder_id` 是否存在——两侧都假设对方会挡。修法是双层都补：前端 `Number.isFinite(parsed) && parsed > 0 ? parsed : null`，后端 `persist_new_feed` 加 `folder_exists` 校验并报可读的 `folder_not_found`（含单测 `add_feed_with_missing_folder_id_is_rejected`）。

**程序性滚动被当作用户滚动**：J/K 导航、回绕、搜索锚定都会让列表程序化滚动，而「滚动出列表即标为已读」把这类滚动也当成用户行为，于是整段文章被误标已读并推送到远端。修法是引入**真实输入闩**（wheel / touchmove / pointerdown / 翻页键）与 `isUserScrollEvent` 判定：只有真实输入触发过的滚动才算用户滚动。

**同一开关在不同入口口径不一致**：这是本项目最反复出现的一类缺陷。「刷新全部」忽略 `smartDedup`、`config_sync_apply` 无事务、`refreshInterval` 前后端值域不同——都是同一开关在不同路径下判据不同。修法是让判据单点化（例如统一走 `viewFilterArgs`、统一走 `folder_exists`）。

### 显式不修的边界（**不要顺手改掉**）

**流式翻译的 delta 不经过 sanitizer**，依赖 CSP `script-src 'self'` 作为纵深防御。原因：逐 delta 过 sanitizer 可能切断跨 delta 的 HTML 标签，破坏流式渲染。行为上的折中是「流式期间按纯文本渲染，`done` 后切 HTML」。若无法在不破坏流式渲染的前提下安全实现消毒，就记录为跳过——这是评估过的取舍，不是遗漏。

**`get_setting` 对敏感键解密后可经通用 IPC 出 webview**。这是威胁模型边界的说明：webview 内运行的代码本来就能调用这个命令，加密保护的是磁盘上的静态数据（DPAPI），不是 webview 的运行时。改法需要给敏感键单独开命令并做调用方校验，收益与改动量不成比例。

### 仍未修的真实遗留（见 [docs/roadmap.md](../../../../docs/roadmap.md)）

- 布局/范围切换的缓存未命中窗口内，`loadMoreArticles` 不被「reload 在途」拦截，续拉可能把新口径的一页追加到旧口径 entries 后（有 `paginationStale` 与代际守卫兜底，属瞬态错排）；
- `reader.ts` 详情成功路径不清 `hydrationErrors[id]`（滞留错误在分支重排后不可见，纯卫生问题）；
- 三条前端观察项见 roadmap：关于页「检查更新」被自身 CSP 拦死、`refreshInterval` 值域前后端不一致、「滚动出列表标读」的「仅未读模式」前置条件未在文案里声明。

## Consequences

**收益**：三类根因模式写下来以后，同类缺陷的定位有起点（先看「是不是又一处入口口径不一致」）；两条不修边界的理由被保留，避免被当成遗漏重复评估；遗留项有明确出口。

**代价与已知上限**：

- 「双层都假设对方会挡」这类缺陷只在两侧都不校验时才出现，审查时需要同时读前端与后端才能发现——单侧读代码都会觉得没问题。
- 真实输入闩依赖具体事件类型（wheel / touchmove / pointerdown / 翻页键）；新增滚动来源（例如触控板的惯性滚动在某些平台上报为其它事件）时闩可能失效。
- 两条不修边界都是「安全性靠另一层兜底」的结构，CSP 一旦放宽（例如引入需要 `unsafe-inline` 的功能），流式翻译的消毒缺口就会立刻变成真实漏洞。

## Alternatives considered

### Why not 把全部 P3 都修掉再发布？

P3 里有相当一部分是文案与视觉细节，修它们的边际收益低于发布节奏的价值，而自检已经把每项记录在案。选择逐条处置（修 / 明确不改 / 移交）而不是「全修」，是为了让范围可控且理由可追溯。

### Why not 在流式期间给 delta 做保守消毒？

保守消毒（剥掉所有标签）会让流式期间的译文失去格式，而用户看到的是「流到最后突然变样」。按纯文本渲染流式内容、`done` 后切到消毒过的 HTML，视觉上是平滑的，且 CSP 兜住了脚本注入。这条折中写在代码注释里。

### Why not 给 `get_setting` 加敏感键白名单校验？

校验调用方需要知道调用者的身份（哪个窗口、哪个命令链路），而 Tauri 命令层拿不到可靠的调用方标识。做一层「只在设置页调用」的约定是纪律而非机制，收益有限。当前的处置是把边界写清楚：加密保护静态数据，不保护 webview 运行时。
