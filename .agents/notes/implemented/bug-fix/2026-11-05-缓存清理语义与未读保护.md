# Agent Note: 缓存清理语义与未读保护

Status: implemented

## Problem

2026-11-05 的「清理旧文章」后端谓词是「早于阈值、已读、未收藏、且不在
`sync_queue`」，因此未读文章永远不会被清理。界面却只写「删除该时间之前的
本地缓存（收藏文章与待同步状态始终保留）」，用户会自然理解为所有旧文章都会
被删，无法解释为什么未读文章一直留着。

当时清理后的已读文章仍存在于远端。下一次 full sync 按服务器状态重新导入时，
它们可能再次出现。原确认框只写「不可撤销」，没有说明该远端回灌边界；这不是
本地删除可撤销，而是同一内容可能以新拉取结果回来。

## 2026-11-09部分后继

用户已要求普通已读正文回收后仍保存可同步的读藏身份，后继为[源内等价组与持久状态](../../proposed/architecture/2026-11-09-源内等价组与持久条目状态.md)。当时后继清理资格继续是早于阈值、已读、未收藏、无待确认队项；实现改为释放RSS/展示正文、媒体和AI大字段，保留GUID/远端ID/read/star版本。回执的数量是释放正文的条目数，不是删除文章实体数。未读/收藏/pending保护仍有效，历史反对分层缓存的理由已因新多端目标改变；新正文缺失状态须有恢复入口。下述2026-11-10决定进一步区分自动计时与手动年龄，并替代此阶段的媒体全部释放做法；身份与未读/收藏保护不变。

## Decision（2026-11-10本机正文保留）

普通已读、未收藏正文的自动保留配置为整数 `readBodyRetentionDays=0..3650`，默认0永久。自动维护使用唯一新增本机字段 `articles.body_retention_since`（nullable UTC秒）；手动清理仍使用发表时间。时间不进入read/star寄存器、正文身份或portable内容记录。原生SQLite快照保存本机时间，portable恢复按本机时间重新开始；缺字段旧开发库在只读结构探针处明确拒绝，文件命名仍为`fluxreader-v2.db`，不自动迁移或删除旧库。

- 首次接受已读、离开未读/收藏保护、缺失正文实际恢复为非空，开始本机保留期。远端同值快照、普通已有正文刷新、同值物化不续期；显式本机标读（包括同值）可启动一次新期。失败的字段版本守卫不触发计时。
- 当前L决定保护资格。accepted/folding、bootstrap、本地投影与计时work、尚未接纳的intents没有闭合时暂停清理；原runtime继续推进这些持久工作。新接管的read寄存器通过原`local_sync_work`的`retention/<wire field>`接线，排在依赖物化之后；其既有cursor保存本机`since/after`，避免本地即时标读到延迟物化时再次续期，或覆盖后来恢复开始的新期。新候选计时从接受后的work开始。任何同戳重放都不新建计时工作。
- 已封存的state/body待发布包不全库阻断清理。实际候选在writer事务内重新检查L、队项、等价组与真实body hold，包含已经没有article定位的hold；最后正文引用释放也遵守hold所有权。持有记录必须由原body回执流程收敛，不按年龄删除。若未接纳intent一直缺因果依赖，维护仍暂停；离线时已有未确认hold的正文也继续保留。它们是数据保护边界，不宣称所有断网库都能按期释放所有普通已读正文。
- 分钟维护独立于autoRefresh，不增加后台服务。先按部分索引取固定候选，再做保护检查，初始化与到期游标交替推进；每批最多64候选、8次真实释放、15ms软预算。预算不能中断一条SQL或大载荷解析，不是硬持锁时延保证。前台mutex忙则跳过，SQLite等待临时为0并还原原值。超过64个物理成员的等价前缀保守跳过，以免保护判断变成无界扫描；必要时再设计持久分组工作，不能直接去掉保护。
- NULL起点首次观察只初始化，不在同一批删除；未来时间或时钟倒退保守保留。进程重启从持久起点继续，游标重置只会重复资格检查，不会延长已有起点。任意向前调墙钟不在此保证内。
- 释放展示/RSS HTML、body_text、摘要、AI摘要/翻译/签名及片段，推进AI清除代次；保留身份、读藏版本、原文链接、有效HTTP(S)封面、原`images_json`外链顺序及图片计数、enclosure与播放时长。画廊首图与封面各自保留；已有媒体触发器的临时重算在同事务恢复外链列表，内嵌data URI随载荷释放。不删除用户下载文件，不制造同步删除意图，不改列表成员或读藏计数。真实释放与刷新合并一次`feeds-updated`，清理不产生新文章通知。
- 收藏先提交则L/hold保护现有字节；合法清理先提交后再收藏不能保住已不存在的正文。恢复入口需如实呈现缺失，网页提取受既有ContentCommitToken限制；恢复失败、没有原文或服务端已无内容时，不保证全文可重新取得。退订收藏已有正文仍永久保护。

2026-11-10 的界面后继明确把这项手动操作标为“按发表时间清理”，确认框使用“发表于 N 天前”，不把它说成新的本机已读保留期。缺正文的 Reader 提供受检原网页提取和真实失败重试，契约见[正文实体缓存](../architecture/2026-10-06-正文与-AI-产物的实体缓存.md)。自动期限维护、恢复提交后的本机计时续期和轻媒体定位保留现已按上述后端决定接入组合。

2026-11-11 的设置后继启用“已读正文保留”：默认“永久保留”（0），切换“限定天数”立即保存30天；自定义只接受1–3650整数。输入草稿由当前页面持有，可删除重输；Enter或失焦才提交有效值，无效值就近提示并留给用户纠正。转到模式选择时由该动作决定，选择永久不先提交尚未保存的短期草稿。保存沿用`updateSettings → patch_app_settings`原子队列与乐观投影，失败由既有链回滚并提示；设置回读不会覆盖活动草稿。草稿带资料库代次，恢复忙态与已换库的旧事件不能提交旧天数，不引入第二份全局设置真值。

自动保留说明区分已有未读/收藏正文的长期保护与普通已读计时；手动清理的发表时间、确认框和“事务已完成但回读失败时只重试刷新”保持原语义。控件专项与真实调度/事件、缺正文恢复、原生宿主及最终组合须分别验证，不能由后端专项通过推导整版或UI可用。

## Decision（2026-11-05历史选择）

**保留现有删除谓词，不改用户数据规则；把真实条件与远端回灌边界写进设置页、
确认框、回执与 API 注释。**

- 只删除「早于阈值 + 已读 + 未收藏 + 无待同步状态」的文章。
- 未读文章永不清理；收藏文章与 `sync_queue` 中待同步文章保留。
- 确认框明确「此操作不可撤销」与「远端仍有的内容可能在同步后重新导入」。
- 清理回执说明「已读文章 N 篇（未读/收藏/待同步保留）」。
- 不实现 tombstone 防回灌。本地删除没有远端删除意图时，远端仍是事实；用
  本地墓碑压制远端同 URL 会改变同步冲突政策，超出「清理本地缓存」语义。

## Alternatives considered

2026-11-10真实考虑过：复用`published_at`、`first_seen_at`或共享contents更新时间。它们分别代表源年龄、首次见到和共享正文修订，不能表示独立条目本次退出保护的本机保留期；因此使用一个本机字段。仅给物理is_read加触发器也不足以覆盖L先接受、投影后执行以及短暂未读再已读的路径，故把计时完成工作放进既有持久队列。没有增加第二套正文表或全局阅读时间服务。

### Why not 删除未读文章？

未读是用户尚未消费的内容。删除后 full sync 会按远端 unread 状态重新拉回，
既无法真正省空间，又制造「阅读列表突然少了一截、过一会又回来」的体验。保留
未读也是当前实现的既有承诺。

### Why not 给清理过的文章写 tombstone 防回灌？

这会把一次本地缓存维护变成远端内容删除意图。FluxReader 的 feed 墓碑用于
「删除订阅」这一显式操作，且与远端退订分离；文章级内容墓碑会压过正常的同步
拉取，用户无法从 UI 区分「我删了缓存」与「我永久不想再看到这篇」。要支持永久
抑制，需要新的产品语义与远端协议/墓碑生命周期，不在本卡范围。

### Why not 只改文案、不补测试？

清理谓词是用户数据的破坏性路径；文案与行为都可能在下一次重构中漂移。新增
数据库级保留边界测试和真实组件确认框测试，确保「未读/收藏/待同步不删」与
「远端回灌说明」同时存在。

### Why not 让清理只删正文而保留列表行？

那会改变本地存储形态与列表来源，且用户点开旧文章仍需正文；当前「删文章行」
同时回收独占内容（共享正文由最后引用规则保活）。本卡只澄清边界，不扩展成新的
分层缓存协议。

## Consequences（历史选择及后继边界）

2026-11-10后继使正文可释放而身份可继续同步，刚标读或恢复的古老文章仍有完整本机保留期。代价是L未闭合、pending保护、巨大等价组和离线hold可能延后回收，且逐候选L/媒体处理仍需实测时延。正常同步物化可能为现有正文重新建立保护hold，只有实际回执覆盖后才可释放；不能用“已读”绕过未确认持有关系。2026-11-11控件后继允许用户选择期限；未提交草稿与已保存设置有意分离，只有有效提交才影响保留策略，组件卸载或切换页签会丢弃尚未提交的草稿。以下各项保留2026-11-05历史语境，删除实体的描述由上述后继替代。

- 用户能看到真实清理条件，不再误以为未读文章会被清掉。
- 未读、收藏与待同步文章继续保留；这些保护项限制「清理旧文章」可回收的
  数据量。
- 远端仍存在的已读文章可能在同步后重新出现；文案已说明，不把它伪装成永久删除。
- 未实现文章级 tombstone，若未来要做「清理后永不回灌」，必须另立决策并明确
  远端协议与 UI 契约。
