# Agent Note: 安全横向面收口（通用 IPC 敏感键 + body_text script/style，B4）

Status: implemented

## Problem

2026-10-31 审计确认两个「用户可见口径」不一致的安全横向缺口（路线见
[审计修复收敛路线](../process/2026-10-31-审计修复收敛路线.md) B4 项）：

1. **通用 `get_setting` 可读出 DPAPI 保护的敏感键明文**。`db::get_setting`
   对落盘密文读时透明解密（SEC-2），而通用 IPC 命令 `get_setting`（commands/
   settings.rs）对任意键透传——前端一条 invoke 就能拿走 `ai_config`（含 API
   key）、`config_sync_credentials`（Gist PAT）、`miniflux_token`、
   `greader_password` 的明文。DPAPI 静态加密防的是「DB 文件被拷走」，通用 IPC
   面却把解密结果原样交回 webview：前端被攻破（XSS/供应链/恶意 IPC 调用）即
   全部凭据失守，加密存储形同虚设。写侧已有账号生命周期拦截（OPT-006 的
   `apply_setting`），但 `ai_config`/`config_sync_credentials`/`miniflux_token`
   不在其清单内，读侧完全无拦截。
2. **`body_text` 混入 script/style 子树文本**。`body_text` 由
   `sanitize::html_to_text` 从原始 feed HTML 提取，scraper 的 `ElementRef::text()`
   遍历全部后代文本节点、不排除 script/style（scraper-0.21.0
   element_ref/mod.rs:83-87）。内联脚本与样式文本在渲染链里用户不可见
   （ammonia 剥离 script、style 不在保留标签内），却随 body_text 进入搜索
   索引与 AI 摘要输入（commands/ai.rs 摘要输入 = `get_article_for_summary`
   的 body_text）——用户不可见的内容对模型可见，提示注入面扩大。

## Decision

现在的契约：

- **通用 IPC 敏感键双向收口**（commands/settings.rs）：`get_setting`/`set_setting`
  命令的真实实现（`read_setting`/`apply_setting`，与单测/e2e 共用）对
  `credentials::SENSITIVE_KEYS` 全部键拒绝读写，返回 `protectedSetting`
  （与账号生命周期拦截同码，语义同属「通用设置命令不得触碰该键」），错误文案
  指向专用流程且不回显存量值。合法消费方走专用命令：AI 配置走
  `get_ai_config`/`save_ai_config`，config_sync/github_auth/同步连接走后端内核
  （`db::get_setting`/`db::set_setting` 不受影响——拦截点只在 IPC 边界）。
  全仓核实：前端经通用 IPC 只读写 `app_settings` 与 `last_playback`
  （src/store/slices/settings.ts、PlayerBar.tsx），`ai_config` 已走专用命令
  （src/lib/api.ts），无合法调用方被破坏。
- **`html_to_text` 跳过 script/style 子树**（sanitize.rs）：body 内改为
  逐文本节点上溯祖先判定，任一祖先是 script/style 即剔除；body-only 口径、
  空白归一不变，渲染链 `sanitize()` 一字未动（正文渲染消毒行为不改变）。
  GR 拉取（sync/entries.rs）与全文提取（extraction.rs）共用同一函数，口径
  自动同源。
- **门禁**：credential_safety_e2e 锁定通用读/写拒绝（存量行存在时读拒绝、
  写拒绝不改写、错误不回显）+ 专用内核往返可用；content_safety_e2e 走真实
  摄取链（parse_feed → upsert）断言 body_text 不含隐藏文本，再经生产输入源
  （get_article_for_summary）与 ai_summarize 同构拼装、真实 `stream_chat`
  发往捕获型 mock，断言模型请求体不含隐藏文本且可见正文保留。

## Alternatives considered

### Why not 只改前端、不再请求敏感键？

缺口本质是通用 IPC 面允许**任何** webview 代码读凭据，不是某个调用点犯了错。
前端被攻破（XSS、依赖供应链、恶意扩展注入页）后，「正规调用点不请求」毫无
约束力——攻击者自己发 invoke。收口必须在后端 IPC 边界一刀切，否决。

### Why not 加密返回 / 遮蔽返回（如打码 API key）？

AI 设置页本就需要明文 key 供用户查看与编辑，遮蔽值要么让编辑路径坏掉，要么
「编辑时解密」又把明文交回前端，等于没拦；且遮蔽/解密逻辑仍在前端，攻击者
改一行代码即绕过。真正的缺口是「通用命令能碰到敏感键」，专用命令白名单才是
正确边界，否决。

### Why not 在 `db::get_setting`/`db::set_setting` 层拦截？

后端内部消费方（config_sync、github_auth、同步凭据内核、ai 命令）合法需要
明文，DB 层拒绝会破坏全部内部路径，还得给它们逐一开「后门参数」。拦截点必须
在 IPC 命令边界——这正是 OPT-006 写保护已采用的分层（`apply_setting` 单点），
读侧对齐同一分层即可，否决。

### Why not 用独立错误码（如 sensitiveSetting）？

前端/测试对「通用设置命令被拒」只需一个语义；与账号生命周期拦截同码
（protectedSetting）避免出现两套判定，差别保留在文案（指向各自专用流程），否决。

### Why not 字符串切片先剥 `<script>…</script>` 再喂 html_to_text？

重复 html5ever 已做的解析，且会被注释、属性引号值、大小写、CDATA、svg 内
style 等变体欺骗（与 iframe 策略 R1「字符串扫描被伪 src 诱骗」同款失败模式）。
按解析树上溯祖先判定与渲染链共用同一解析器语义，否决。

## Consequences

**收益**：DPAPI 加密的真实边界恢复为「静态落盘 + 后端内核使用」，webview 不再
存在任何读出凭据明文的通用通道；body_text 与用户可见正文同口径，搜索索引与
AI 摘要输入不再携带 script/style 隐藏文本；两条 e2e 门禁把上述契约锁死。

**代价与已知上限**：`contents.identity` 含 body 哈希，body_text 口径变化带来
一次性 identity 漂移——升级后首次重摄取时，含 script/style 文本的旧内容行按
新口径计算身份、新建等价行，旧无引用行由既有重指+回收路径删除
（db/articles.rs contents_refresh_repoint），revision/前端缓存重取一次，可接受；
存量未重摄取的行其 body_text 仍含旧文本，属惰性收敛（与修复 Extracted 行的
`repair_extracted_body_if_mismatch` 同策略，RSS 行不做发布期回填）。
留给后续任务（B2）的注意点：`db::get_setting`/`db::set_setting` 签名与语义
未变，settings 命令签名未变（仅 `read_setting`/`apply_setting` 由 pub(crate)
 放宽为 pub 供 e2e 复用），sync 域调用方无需改动。
