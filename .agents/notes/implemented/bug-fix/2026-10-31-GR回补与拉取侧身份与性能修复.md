# Agent Note: GR 回补与拉取侧身份/性能修复（B2）

Status: implemented

## Problem

[审计修复收敛路线](../process/2026-10-31-审计修复收敛路线.md) 的
B2 项：阶段 A 把门禁对齐真实服务端语义后，拉取侧四项缺陷在真实语义下显形，
均有审计证据锚点——

1. **GR read/starred 集合 contents 回补缺口**（用户核心症状）：轻量对账
   `reconcile_reader_state` 只遍历 `mf_id_to_article` 映射；权威集合里「从未
   被列举窗口绑定」的 id 没有本地行，read 永远收敛不到、starred 的双向判定
   也摸不到——审计探针判定的**永久漂移**。ot 窗口按 `published_at >` 严格
   过滤（阶段 A）后，published 早于游标的集合成员只能靠手动全量，症状放大。
2. **fever_pull 回补无预过滤**：④ 段注释声称「本地还没有正文的条目」才
   with_ids 补齐，实现却只排除本轮 `seen`——权威集合（unread∪saved）里
   已有正文的条目每轮全量重拉。审计实测：2 万条库最坏 403 次串行往返/轮
   的固定成本。
3. **空 link 跨源塌缩**：`normalize_url("")` 返回 `''`，入库路径
   `a.url.as_deref().map(normalize_url)` 让所有无 link 条目共享同一
   `url_norm=''` 匹配键——3 个不同源的空 link 条目在 smartDedup 下塌缩成
   1 行显示、标读其一经读闭包/读广播传播到其余。
4. **F1 scope 计数慢路径**：`scope_counts_sql` 的 dedup EXISTS 模板
   `SELECT 1 FROM articles b JOIN feeds fb ON fb.id = b.feed_id` 在真实语料上
   触发逐行扫描（feed 级 + layout 变体甚至丢失 url_norm 索引），50k 行
   实测 155.4s/轮；列表/源计数用的 `dedup_exists_clause`（标量子查询形态）
   无此问题。

## Decision

**① GR 权威集合回补**：light 轮 read 对账采用
[未读差分](../architecture/2026-11-01-GR未读差分对账.md)，不再拉 read 集合。
2026-11-05 起完整 unread 与 starred 都回补缺身份或正文的成员，轮转防止空正文
或缺 feed 永久占满预算；这部分扩展的取舍见
[GR 权威集合回补与过期意图恢复](2026-11-05-GR权威集合回补与过期意图恢复.md)。
`pull_entries_greader` 在 light 对账前对
集合中「无本地绑定行或绑定行缺正文」的 id 逐块拉
`stream/items/contents`（镜像 `fever_pull.rs` 的 with_ids 回补结构），走
`merge_pulled_entry` 既有四分支匹配链自然绑定并应用状态——**不新增任何
匹配/写状态逻辑**，冲突方向仍只消费 `conflict_policy.rs` 单点；full 同步的
ot=0 列举已覆盖全部条目，回补集合恒空，不进 full 路径。参数取舍：块大小
100（与主列举正文分块一致）、每次 pull 每集合预算 2000 条（至多 20 请求/集合）。
预算到达**不是失败**——集合 id 列表本身完整（`fetch_stream_ids` 自带截断
守卫），已回补子集照常参与对账，剩余下轮续补；只有单请求/合并失败才
fail-closed（该侧本轮跳过对账 + 游标经 `authority_cursor_failures` 保留），
对齐主窗口的失败守卫。成功回补保存本代际遍历位置，不独立推进主窗口游标。

**② Fever 回补预过滤**：need 构造改为「unread∪saved − seen − has_body」，
has_body 是 DB 单点 `db::remote_ids_with_body` 返回的**已有正文**绑定行 id
集合（content_html 或 body_text 任一非空，判定与 `contents::content_non_empty`
同口径，500 id/块避免变量上限），调用方在内存取补集。取补集而不是直接查
「缺失集合」有硬理由：缺失集合的 SQL 只能扫到**已有行**，无绑定行（从未
拉过的远端条目）天然不在查询结果里，直接当缺失集会把它们从 with_ids 通道
漏掉（CI 第 2 轮用例钉住的返工点）；补集形态下无绑定行 id 不在 has_body
里，天然留在 need。DB 读失败 **fail-open**：has_body 按空集处理 → 全量
重拉——无法判定哪些已有正文时，宁可多打请求也不漏补正文（与回补缺字段
当空集的 fail-closed 相反方向：这里是「少拉」的风险不是「误清」的风险）。
状态对账由 ⑤ 的权威集合独立承担，跳过正文往返不丢状态语义；请求失败守恒
（游标不动、页事务回滚）沿用既有结构未动。

**③ 空 link 归一 NULL**：入库单点 `normalized_url_key`（trim 后为空 →
None），覆盖 insert/refresh 的 4 个 `map(normalize_url)` 调用点与两条 upsert
的 by-url 前置过滤（改为 trim 判空）；`sync/entries.rs` 的拉取匹配键同口径
过滤（否则同轮多条空 link 条目经 `feed_url_to_id[""]` 互相借位绑定）；guid
命中刷新的 `url_norm` CASE 改以**归一键 ?11 判空**——修前以原始 url 判空，
空白 link 通过 `?2 != ''` 检查后把既有 url_norm 覆盖成 `''`。迁移 v31 幂等
清洗存量（`UPDATE articles SET url_norm = NULL WHERE url_norm = ''`），
**不动 contents**：contents 行身份由内容哈希承担、url_norm 只是附带列，
B4 已改 body_text 口径，再动 contents 会扩大共享内容行的身份漂移面；
`ensure_url_norm_backfill` 同步加 `TRIM(url) != ''` 守卫（否则空白 url 会在
回填时把 v31 清洗过的键写回 ''）。READ_CLOSURE_SQL 与读目标谓词确认无需
改动——它们只防 NULL，'' 键消失后天然安全。

**④ F1 计数改写**：feed 级 EXISTS 去掉 `JOIN feeds fb` 与组内布局复核——
等价性论证：内层约束 `b.feed_id = a.feed_id` 使 fb 与外层 fa 是同一行，
布局条件与外层 WHERE 逐字同构，layout 给定时外层已把不匹配的 feed 整组
排除，组内 b 的布局复核恒真。All/Folder 级的 b 可能来自其它 feed，保持
原模板。SELECT 列表布局占位随之消失，绑定数由 `scope_counts_sql` 同源给出；
`counts_snapshot` 返回形状与键名不变，`set_read` 共享同一把 DB 锁的结构
不变。本地 50k 探针（Python sqlite3 同构 schema）：修前 11.7s（无 layout）/
15.8s（layout，且丢失 url_norm 索引）→ 改写后 0.21s/0.21s，四视图 × 100 源
逐字段一致。计划断言禁 TEMP B-TREE、禁 `SEARCH b USING INTEGER PRIMARY KEY`
（逐行 rowid 搜索形态）、必须走 `idx_articles_url_norm[_unread]`。

## Alternatives considered

### Why not 回补改在 reconcile 后二次全量对账？

对账后再跑一轮「全量拉取 + 二次 reconcile」能收敛同样的行，但把回补变成
两遍网络 + 两遍对账的固定成本，且二次对账必须重新解决「集合快照 vs 中途
本地写入」的版本/pending 守卫，等于把 reconcile 的守卫逻辑复制一份；更关键
的是失败语义会变模糊——第一遍对账已落地的行与二次对账的行无法共享同一份
「该侧失败跳过」的边界。回补前置走 merge_pulled_entry 既有匹配链，reconcile
自然消费更新后的 maps，零新逻辑、零守卫复制，否决。

### Why not F1 用 ANALYZE 统计而非改写查询？

ANALYZE 只影响规划器选路，不改变查询形态——本机探针实测 layout 变体在
`JOIN feeds fb` 形态下**连 url_norm 索引都会丢**（每行再叠 fb/fo5 两次 PK
回查），统计信息不保证规划器回到索引路径，且 `sqlite_stat1` 需要 maintained
（库增长后统计过期即复发）、ANALYZE 本身在大库上是一次全表扫描成本。改写
把「不需要的 join」从查询里删掉，形态即计划，无运行时前提；两者不互斥但
改写是根治，否决纯 ANALYZE 方案。

### Why not 回补失败仍跑该侧对账（read 侧部分回补是安全的）？

GR read 是单向 read-wins，集合完整时部分回补只「少收敛」不「误清」，继续
对账在 read 侧语义安全。但 starred 是双向权威，两套失败语义并存会让
「回补失败」的处理按侧分裂，审计与回归都要分别论证；统一 fail-closed
（该侧跳过 + 游标保留）只多付一轮延迟，换取与既有 C-1 守卫完全同构的
单条规则，否决按侧分裂。

### Why not 预算到达也按失败处理、跳过该侧对账？

预算限制的是回补的**请求量**，不是数据完整性：集合 id 列表来自
`fetch_stream_ids`（截断即显式失败），到达预算时集合仍完整，已回补子集
照常对账不会引入截断误判；跳过对账反而让「预算 + 网络抖动」叠加成无限
推迟收敛。失败（单请求/合并错误）与预算（容量边界）必须分开处理，否决。

### Why not 「已有正文」把 enclosure/封面也算进去？

回补的主目标是正文（merge_own_entry 的 backfill_entry_content 补 html/
body_text/封面/enclosure，但每轮重拉的成本由正文体量决定）。与
`content_non_empty` 同口径（html 或 body_text 任一非空）最简单可测；
播客类空正文条目会每轮重拉一次 with_ids，量级小（且有 enclosure 的条目
本来就需要 contents 通道补 enclosure），可接受，否决扩大口径。

### Why not 改 `normalize_url` 本身让空串返回 None？

`normalize_url` 是纯 `&str -> String` 函数，feed_url 归一匹配（sync_map）、
墓碑键回填等调用方都依赖现签名；把「空 link 无身份」这一**调用方语义**
塞进纯函数要么改返回类型（波及全部调用点），要么返回 `""` 维持现状（等于
没修）。空 link 处理收敛到入库/拉取两侧各自的调用点单点
（`normalized_url_key` / entries.rs 过滤），否决改纯函数。

### Why not 迁移顺带清洗 contents.url_norm 的 ''？

contents 行身份由内容哈希承担、url_norm 只是附带列；B4 刚改过 body_text
口径，共享内容行的身份已经经历一次漂移，再动 contents.url_norm 会把
「同 url_norm 共享行」的复用判定再洗一遍，收益（空 link 的 contents 附带
列归一）远小于风险。存量空 link 条目的 contents 行保持原状，新写入走
ContentInput.url_norm = NULL，否决顺带清洗。

## Consequences

**收益**：GR read/starred 集合中未绑定行经 light 同步收敛（用户核心症状：
直连入库行不再永久漂移；read 集合回补退场，2026-11-05 起补齐 unread 通道，
收敛通道变化见
[GR 未读差分对账](../architecture/2026-11-01-GR未读差分对账.md)）；Fever with_ids 不再每轮
重拉已有正文（403 次往返 → 只补缺正文 id）；空 link 条目各自独立成行、
读状态不跨源广播；feed 级 dedup 计数回到秒级（与无去重变体同量级）。

**代价与已知上限**：GR 回补每轮每集合至多 2000 条预算——超大库首次收敛
需要多轮 light 同步逐批补齐（可预期、有 report 可见）；回补失败轮该侧
对账推迟一轮；空 link 行的 `url` 列仍保留原始空白串（只清匹配键，展示列
不动）；Fever 空/纯空白正文条目每轮仍重拉一次 with_ids（真实空正文无法
与「未拉过」区分，量小可接受）。残余收敛场景（既不在窗口也不在两个权威
集合的条目）见 `docs/sync-compat-matrix.md` §6-L1 收窄段与 L7。
