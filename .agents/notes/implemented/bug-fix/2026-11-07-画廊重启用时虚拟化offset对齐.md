# Agent Note: 画廊重启用时虚拟化 offset 对齐

Status: implemented

## Problem

@tanstack/virtual-core 3.17.8 在虚拟化器被 `enabled` 停用期间不清理内部
`scrollOffset`：`observeElementOffset` 重新订阅时没有初始回调，`getScrollOffset()`
也只有在被调用且发现 `enabled=false` 时才把 offset 置空，而 `_willUpdate` 在
停用后的后续渲染里因 `scrollElement` 已相等而跳过 `maybeNotify`。因此画廊从
其他布局切回（重启用）时，虚拟化内部 offset 可能停留在上次画廊的深滚位置，
而滚动元素真实位置已是 0。首个真实 scroll 事件之前，窗口按陈旧 offset 计算：
深部卡片被短暂挂载（观察证据：ui-layout 980x640 loading check 中同 runKey
仅深部 image-061..073 发出 HTTP 请求，顶部卡从未请求），懒加载判定被引向屏外，
屏内卡片可能整段不被加载；对真实用户则是切回画廊后首帧窗口错位。

## Decision

Timeline 在布局切换的首帧向滚动容器派发一次 `scroll` 事件（`activeLayoutRef`
检测 `activeContentLayout` 变化，首挂载不派发）。虚拟化的 scroll 处理器会
回读元素真实 `scrollTop` 并重算窗口，内部状态与元素立即对齐。该 effect 同时
保留每次渲染的 `syncGalleryGeometry`（image）或行侧 pending 兜底消费
（非 image），并对停用方实例调用 `forceResetStaleScrollOffset` 置空内部
offset。派发的事件不带输入闩（wheel/触摸/按键才置闩），`isUserScrollEvent`
判为非用户滚动，不会误触发标读或分页。

演进说明（2026-11-07 复审核对）：本段最初记录为「`galleryActiveRef` 只放行
一次」的画廊单侧派发，变量名与「仅画廊激活派发」的细节已与当前代码不符。
根因定位后机制已扩展为分层封堵：row 侧 pending+consume 守卫（见下方
「row 侧同根因扩展」），以及焦点侧上下文门控——`FocusedCard.filterKey`
记录产生焦点的阅读上下文、恢复 effect 按当前 filterKey 门控、`focusCardAt`
任务的 `isCurrent` 按实时 store 校验并使跨上下文任务过期（详见下方
「根因插桩证实」段）。本段为更正后的现状描述。

## Alternatives considered

- 夹具在 `__uiLayoutSelect` 里派发同名事件：只修测试不修产品，真实用户切回
  画廊仍会首帧错位；该缺陷同时污染 Tab 候选几何（候选集按陈旧窗口过滤），
  不是测试独有问题。
- rangeExtractor / galleryWindowKey 改为直接读元素 `scrollTop` 而不用实例
  offset：能修正本侧窗口计算，但 TanStack 内部（scrollToIndex 的可见性判断、
  补偿数学）仍消费陈旧 offset，J/K 定位与 G2 补偿仍可能按错误基准决策；
  属局部绕过而非根因。
- 升级 virtual-core 或上游修初始回调：版本升级超出本批范围；上游行为在
  3.17.8 实测如此，修复应先在本仓库落地并留证。

## Consequences

画廊每次重新激活会多一次同步窗口重算（首帧两次提交），换取窗口与元素位置
一致。对 `loading=lazy` 的画廊图：激活首帧挂载的就是屏内窗口，懒加载在插入时
即可判定，不再依赖后续滚动事件纠偏。验证边界：修复后单场景探针
（tmp/frontend/gallery-ui-r1/final-r1/probe-980-gallery-http.mjs 及其变体）
与完整 `npm run test:ui-layout` 的结论以当次运行记录为准；本 Note 只固化
机制与取舍，不宣称某次运行已通过。

row 侧同根因扩展（2026-11-07，同日续派）：row 虚拟化器采用同型机制——
scrollToFn 对非零 adjustments 走 `rowPendingScrollRef` 延迟、`onChange` 里经
`consumeDeferredScroll` 消费（offset 与元素 scrollTop 偏差 >1.5px 时丢弃）、
filterKey 变化时清除、行布局激活兜底消费。覆盖面是行虚拟化器这一个公共实例
（article/social/podcast/notification 四布局共用），无 podcast 专用分支。

机制精化（同日第三轮实证后补充，部分取代上面对修复主体的描述）：完整套件里
980x640 的 image/podcast 激活仍确定性滚向上次布局的深滚位置（6686/10762，
各为当时 scrollHeight 的 max），且在「停用方主动调用 getScrollOffset 强制置空
内部 offset」之后依旧复现——说明跳转写入者不是（或不只是）重启用时对内部
offset 的回写，dispatch、pending 守卫与置空都未拦到它；滚动写入者需在共享
封装层面带插桩的套件运行里定位（候选：重启用分支的无 adjustments 直通写、
ResizeObserver 对 detached elementsCache 的测量路径、或浏览器滚动锚定）。
探针（简化前置）不能复现该跳转，探针通过不构成套件层面的验证结论。

数值更正（2026-11-07 复审核对）：上句「6686/10762，各为当时 scrollHeight 的
max」口径有误——image 侧当时实测最大 top 为 6835，6686 是某次运行的观察值
而非底值；podcast 侧 10762 为底值无误。原始观察记录按约定保留不改写，
以本段更正为准。

根因插桩证实（2026-11-07 第四轮，r7 带插桩完整套件）：上段列出的候选写入者
已定位，确定性跳转是**跨上下文的删除焦点恢复链**，不是单一代码点——

1. 1440 window check（flat 形状）真实 Tab 聚焦 `window-412`
   （`focusedCardRef = { window-412, 412 }`）。
2. 980 fixture 整体替换 entries（5000 个 window-* → 400 个 article-*）的
   commit 里，恢复 effect 判定「持焦卡被移除且焦点已甩到 BODY」，发起
   `focusCardAt(min(412, 399))` → `scrollToIndex(align:'auto')` 滚向新列表
   末段（12328/12352）。
3. 同 commit 的 filterKey 归零 `scrollTo(0)` 随后被三个写入者反复击败：
   scrollToIndex 尚未对账的 virtual-core `reconcileScroll`；跨上下文存活下来
   的 focusCardAt 任务的原生 `el.focus()`（`isCurrent` 未校验阅读上下文）；
   `resizeItem → applyScrollAdjustment → consumeDeferredScroll` 对底部位置
   的补偿锚定。
4. 980 随后的 top 测量读到 footer 进入滚动视口 → 断言失败。r7 失败点从
   podcast 前移到 article，是插桩开销改变时序所致，机制相同。

修复：焦点恢复只在**同一阅读上下文**内生效——`focusedCardRef` 记录产生时刻
的 filterKey（布局|视图|订阅|筛选|排序），恢复 effect 与 focusCardAt 任务的
`isCurrent` 都以实时 store 派生的 filterKey 校验，上下文切换即视为过期并
终止原生 focus 链；同 filterKey 内的条目移除（收藏/已读筛选、后端刷新）恢复
行为不变。实施依据与判定表见独审报告
`tmp/frontend/gallery-ui-r1/final-r1/audit-row-root/REPORT.md`；其首选细节
「跨上下文恢复 effect 单独作案」被插桩证据精化——恢复 effect 是第一环，须与
过期任务、补偿写回两条支线一并封堵，单一改动不充分。

备选（真实考虑过）：仅给 `isCurrent` 加上下文校验——挡不住恢复 effect 本身
发起的 scrollToIndex（链条第 2 环照旧）；仅门控恢复 effect——过期任务的
原生 focus 与补偿写回仍在（第 3 环）；删除恢复 effect——破坏同上下文删除
焦点恢复的既有回归与体验，未采纳。

插桩插件缺陷（如实记录）：产品侧 `timelineProbe`（src='timeline'）的条目在
r7 metrics.json 中为 0，但原生包装（NATIVE_PROBE_INIT）的调用栈明确出现
`focusCardAt` 与恢复 effect 的调用帧。原因未查明（疑与模块作用域
`window.__scrollProbe` 的引用时机有关），不影响结论——原生栈链已闭合，
但该缺陷意味着当时产品侧探针数据不可用作反证。插桩在修复后已全部移除。

行侧保留项复核：`rowPendingScrollRef + consumeDeferredScroll` 与
`forceResetStaleScrollOffset` 在焦点根因修复后不构成冗余——前者继续服务
同上下文内 J/K 定位与社交卡测量产生的 adjustments 消费（上段第 3 条正是其
1.5px 守卫对象），后者继续拦截 virtual-core 重启用对内部 offset 的回写。
没有「移除后探针等价」的证据（需要再跑一次完整套件，超出当轮唯一一次运行
的约定），按裁决保留。

验证边界：修复后唯一一次完整 `npm run test:ui-layout` 通过（证据目录
`tmp/frontend/gallery-ui-r1/final-r1/ui-layout-r8/`）；同轮 lint、build、
`test:frontend`、`test:components`（含 keyboard-a11y 删除焦点恢复回归）
通过。历史失败原件 r3/r5/r6/r7 保留未覆盖；本 Note 固化机制与取舍，
具体通过结论以当次运行记录为准。

日志留存边界（2026-11-07 复审补记）：r8 完整运行日志未保留（stdout 未
重定向落盘，会话捕获输出被截断），`ui-layout-r8-run.log` 仅含未保留标记与
