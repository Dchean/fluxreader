# Agent Note: 保守 URL 匹配与版本化重建

Status: implemented

## Problem

把t/s/ref/group_id等通用参数当跟踪参数删除，会把论坛主题、章节或不同订阅归成同一键。url_norm落库存储，仅改函数不会改存量；旧布尔完成标记还会阻止重算。旧内容墓碑和退订墓碑只有规范键，丢失的原始参数无法反推。

## Decision

通用规则只删明确营销参数，业务含义不确定的名字保留。唯一站点例外是严格X/Twitter状态页；用归一前URL判http(s)、允许主机、默认端口和严格路径，空路径段、相似域、附加photo路径不套用。

算法变化递增NORM_VERSION，存量从原始URL重算，变更和版本标记同事务。v19清旧完成键和旧内容去重墓碑，将退订墓碑原字节移入legacy命名空间；目录墓碑不丢弃，后由v24迁为账号隔离形态。

新墓碑按新算法匹配，legacy按冻结legacy_v1_normalize匹配和回收；旧算法仅服务墓碑兼容，不回流到文章身份。任一命名空间读取/解析失败表示未知，保留损坏原值、停止相关订阅导入；缺key才是合法空表。prune先读完两侧再写，显式重加解除两个命名空间，避免半清理。

条目身份后来独立于规范URL：精确协议entry id优先，同feed URL只作保守兜底，跨feed同URL保留独立条目。deduped_urls不再是新入库闸门，历史迁移清理仍是兼容事实。身份模型详见[订阅条目与共享内容身份](../architecture/2026-10-12-订阅条目与共享内容身份.md)。

## Alternatives considered

把旧规范键再按新算法重算等于编造已丢的raw URL；隔离旧字节和旧算法才保留原删除意图。让旧算法继续参与所有匹配又会恢复误并，因此必须缩小作用域。SQL重写一份规范算法容易与Rust漂移，迁移只触发由单点函数重算。

扩大站点规则表需要逐站依据；当前仅保留已有高置信例外。保留无法判定的旧内容墓碑会继续误压文章，清理最多给予重拉机会，却不能恢复上游已消失的正文。

## Consequences

旧墓碑可能保守多拦：同一旧键下不同raw URL会一同被挡，直到按旧算法的远端全集确认消失。损坏墓碑会暂停导入，这是避免把未知改成无删除意图的代价。参数保守化也可能多保留同文变体，优先避免吞掉不同内容。

该URL决定不证明订阅remote_id与URL兜底的全链优先级正确。2026-11-06仍有弱规范URL碰撞导致远端源换绑/删除及本地布局丢失，见[同步正确性路线](../../../../docs/roadmap.md#sync-correctness)。后续full能重拉服务器仍保留的文章，也不能恢复已经丢掉的本地布局。

## Validation

url_identity_e2e用新/legacy命名空间、畸形JSON/BLOB、重加和事务失败核验原值保留与回滚；entry_identity_e2e核对同feed不同精确id及真实直连刷新。后台现在会做节流订阅发现，早期“light永不绑定新feed”的描述已被[集合失败关闭决定](2026-10-19-同步集合失败关闭.md)取代。
