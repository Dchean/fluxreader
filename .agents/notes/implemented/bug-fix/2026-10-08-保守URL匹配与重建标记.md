# Agent Note: 保守 URL 匹配与版本化重建

Status: implemented

## Problem

审计 F12（P2）：通用 TRACKING_PARAMS 对所有站点剥 t/s/ref/group_id/web_chapter_id 等参数，把论坛 `/viewtopic.php?t=123` 与 `?t=456` 这类不同主题归到同一匹配键——智能去重按此键跨源吞文章，同步 URL 匹配同受其害；`?s=`（会话）、`?group_id=`/`?web_chapter_id=`（章节）也被一并抹掉。

更隐蔽的一半：url_norm 是「写入时算一次、落库存储」的匹配键，只改算法函数不会修正任何存量键；旧布尔完成标记 `url_norm_backfill_done` 还会让升级后的重算永远被跳过。而 `deduped_urls` 内容去重墓碑只保存旧算法键、原始 URL 未保存，旧键残留会按错误键继续压制文章，且无法反向重算。

R1（审查追加）：**退订墓碑同样按旧算法键存储**。算法收敛后新键 ≠ 旧键——pull 若只用新键匹配、按新键全集判 stale，会把旧墓碑当过期清掉，已删除的订阅在远端列表里被复活（用户意图被违反）。只把旧字节「保留」不够，必须保住匹配语义。X 状态页例外还有两处不严：空段路径（`/u//status/123`）被当成状态页把参数抹掉；`https://x.com:80` 因先 `set_scheme("http")` 把端口当默认值归一掉，绕过非默认端口约束。

R2（审查追加）：**墓碑读取把「未知」当「没有」＝错误放行**。`read_tombstones` 把 JSON 解析失败吞成空表；pull 对读错误只 warn、匹配读错误 `unwrap_or(false)` 继续导入——墓碑存储损坏（畸形 JSON；或 BLOB 类型值使 String 读取失败）时状态被当作「无墓碑」，已删除订阅照样复活。**缺 key 是合法空表**（从未删过），**读/解析失败是未知**，两者必须区分且未知必须失败关闭。

## Decision

**通用删除只保留明确归属的营销参数**：utm_*、gclid/gclsrc/dclid/gbraid/wbraid、fbclid/fb_action_ids/fb_action_types/fb_source、igshid/igsh、twclid、mc_cid/mc_eid。t/s/ref/ref_src/ref_url/referrer/spm_id/scm/share_token/nsfrom/nstoken/share_source/tt_from/group_id/web_chapter_id 等通用名字一律保留（站外可能是业务参数）。

**X 状态页例外**（唯一高置信站点规则）且必须**用未归一的原始 URL 判定**（早于 set_scheme/host 改写，端口与 scheme 是身份信号）：http(s)、无显式非默认端口、host 恰为 twitter.com / x.com（含标准 www./m./mobile. 子域）、路径**严格**为 `/<user>/status/<纯数字 id>`（不滤空段，`/u//status/123`、`/u/status//123`、`//status/123` 均不套用）。x.com.evil、evil.x.com、/i/web/status、/user/status/123/photo/1 均不套用。

**版本化存量重建**：url_norm.rs 新增 `NORM_VERSION`（算法语义变化必须递增，本次 "2"）；`ensure_url_norm_backfill` 从布尔标记改为版本标记（settings.url_norm_backfill_version）：缺失或不等即从原始 url 逐行重算（只 UPDATE 有变化的行），回填与写标记同一事务，失败整体回滚、下次启动按「标记缺失/旧值」重试。v19 迁移（纯数据，旧 SQL 未动）：删除旧 `url_norm_backfill_done` 键 + 清空 deduped_urls + **旧退订墓碑迁入独立 legacy 命名空间**（`feed_tombstones_legacy_v1`，字节保留——不反推原始 URL）；用户目录删除墓碑（folder_tombstones）绝不删除。

**退订墓碑跨算法版本匹配（R1）**：新删除按新算法键写 `feed_tombstones`；匹配/回收在 db/feeds.rs 收口——`feed_url_tombstoned` 当前键空间按新算法比对、legacy 命名空间按冻结的旧算法快照 `legacy_v1_normalize` 比对；`prune_feed_tombstones` 各命名空间只按**自己的算法全集**判 stale（legacy 键只有「远端旧规范全集确实不含」时才清）；`remove_feed_tombstone`（用户显式重新添加原 URL 的真实调用点）同时解除两个命名空间。`legacy_v1_normalize` 是唯一允许的旧算法用法，只服务墓碑，**绝不允许回到文章/订阅身份匹配**。

**墓碑读取语义（R2 失败关闭）**：缺 key = 合法空表；存在但读/解析失败 = 未知 → `read_tombstones` 返回 Err 且**不写任何 setting**（损坏值原样保留，含类型）；`prune_feed_tombstones` 先读完两侧命名空间再写（任一读错零副作用）；pull 对任何墓碑 Err 记入 SyncReport 并**停止本轮订阅导入**——不 `unwrap_or(false)`、不把未知当空表；修复后下一轮自然重试。写路径（删除/重加墓碑）同样把未知当 Err 上抛，绝不静默覆盖。该行为由真实 DB 锁定：四组损坏组合（新/legacy 命名空间 × 畸形 JSON / BLOB 值）+ readd 双非空命名空间与回滚可补用例（url_identity_e2e 7/7 实跑绿，具体数字见 RESULT）。

## Consequences

- 存量 v18 库升级即重算：不同主题号恢复为不同键；原始 url、读/藏状态、分页/状态索引原样；重开幂等零重复工作。
- 清空 deduped_urls = 内容去重墓碑失效一次：被错误压制/误合并而未入库的条目，**只有在「上游仍提供该条目」且实际发生重拉时才有机会补回**；上游已删除/不保留的内容无法恢复，补全依赖后续重拉（父卡 OPT-008 的内容/条目身份分离）。
- **已被误合并且正文从未存入本地的历史内容无法由迁移凭空恢复**：原始 URL 与正文都不在库内，没有反向重建的依据。
- 退订墓碑的保守权衡（R1）：旧墓碑键丢失了参数原值（原始 URL 不可反推），同一旧键的全部候选订阅会被一同抑制（如旧键 `feed` 会同时拦下 `feed?t=123` 与 `feed?t=456`）——宁可保守多拦，也不猜 raw 放行；远端旧规范全集确认消失后自动回收。无参数 URL 的旧墓碑（新旧键相同）行为与从前逐字一致。
- 墓碑存储损坏时（R2）：订阅导入该轮整体停止并在 report 可见报错（不复活、不改写损坏值含类型）、删除/重加等写路径同样可见 Err——宁可停摆一轮，也不静默覆盖未知状态；值修复后无迁移、无特殊操作，下一轮自动恢复。
- 收敛会损失部分「同文变体」自动去重（带 t/s/ref 等参数的同文链接会被视为两篇）：按卡方向「不把可能不同的文章合并」接受该成本。带通用参数的罕见 feed_url 也按同一方向视为不同订阅。

## Alternatives considered

### Why not 只保留 utm_ 前缀匹配、其余全删？

group_id/web_chapter_id 等无前缀业务参数会被继续误删。F12 要求通用规则只删「明确归属」的名字；前缀式扩删方向相反、更激进。

### Why not 站点专用规则表（按域名声明可删参数）？

维护面与判定面大幅扩张（任意站点、任意参数组合），当前证据只支持 X 状态页这一条高置信例外；其余同文/身份判定交给父卡的身份分离模型。

### Why not 迁移 SQL 里直接重算 url_norm？

规范化逻辑在 Rust（url crate 解析 + 多步归整），SQL 重写一份必然与生产逻辑漂移。迁移只负责「让重算发生」（清旧标记、清旧键墓碑、迁旧墓碑），重算仍走唯一实现，且带上版本标记与事务回滚语义。

### Why not 保留 deduped_urls 中「按新算法仍能对上」的行？

墓碑键是旧算法产物、原始 URL 已丢，无法判定哪些还能对上；不清则错误键继续压制，清掉最多多拉一次——用户可见成本远低于永久吞文章。

### Why not 对旧退订墓碑按新算法重算键（迁移里重建）？

旧墓碑只存了旧算法规范化后的键，原始 URL（含被剥掉的具体参数值）已丢；任何「重算」都是编造 raw URL，会把不同订阅猜成同一个。字节迁入 legacy 命名空间 + 隔离旧算法快照匹配，是不假装恢复数据的唯一保真路径。

### Why not 让 legacy 算法在所有匹配路径继续生效，免得升级出问题？

那等于把 F12 的缺陷保留在身份匹配里（t=123 与 t=456 继续同键），只是把问题藏起来。旧算法只隔离给墓碑兼容匹配这一处，作用域和理由都能在代码里一眼看清。
