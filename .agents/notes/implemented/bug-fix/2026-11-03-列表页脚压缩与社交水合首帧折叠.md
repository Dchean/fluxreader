# Agent Note: 列表页脚压缩与社交水合首帧折叠

Status: implemented

## Problem

审计与后续返工在同一组 UI 几何取证里复现了四个相关缺陷：

1. **五布局的「没有更多了」在首屏底部错误出现。** `.timeline-scroll-body` 是纵向 flex 滚动容器；行虚拟容器 `.timeline-virtual-wrap` 与画廊容器 `.gallery-masonry-grid` 的内联 `height` 是完整内容总高，但它们保留默认 `flex-shrink: 1`，被父级压成可视高度（实测约 732px）。页脚因此紧跟被压缩的容器出现在首屏，而不是完整列表末尾。
2. **社交长文水合出现完整正文中间帧。** `SocialCard` 初始 `isLong=false`，`body.content` 落地时先按未折叠高度进入布局；随后普通 `useEffect` 安装的 ResizeObserver 才判定长文并加 `.collapsed`。延迟 IPC 实测卡片高度 `190px → 约 1050px → 约 303px`，中间帧可见相邻卡片重叠。问题在布局时序，不在列表入场动画。
3. **首轮修复未覆盖图片正文，第二轮仍依赖列表行特征。** `-webkit-line-clamp` 对块级 `<img>` 不生效，图片正文实测可到 1095px。更关键的 P1 是「正文含 `<img>`、列表行 `imageUrl=null`、摘要短」：占位按短正文预留，水合后正文变成图片长内容，审计实测外高 `220.14px → 310.14px`，出现 1 帧重叠、最多 11 处；本轮同 fixture 复现最大 2 处重叠。按摘要/封面特征猜测高度无法成为不变量。
4. **固定 150px 外框不是可靠的测量目标。** 收起后外框高度恒定，`<img>`/`<video>` 解码、失败或元数据到达只会改变内层自然高度；只观察外框的 `ResizeObserver` 不会再次回调，延迟图片或视频就会被漏判为不可展开。测量必须落在 `.social-text-inner`，并对媒体自身的 `load`/`error`/`loadedmetadata`/`loadeddata`/`durationchange` 事件重新取样。
5. **展开/收起等无关 render 会重建 `<video>`。** `dangerouslySetInnerHTML={{ __html: body.content }}` 的内联对象每次 render 都是新引用，React 按引用比较后重设 `innerHTML`；视频因此重新加载，`readyState` 归零、poster 短暂丢失。逐帧证据记录到视频节点 `21 → 23 → 25 → 27`，并在展开 commit 与虚拟化回写之间留下 1 帧重叠。仅延长等待或放过首帧会把真实缺陷留在产品里。

## Decision

### 1. 虚拟容器明确拒绝纵向 flex 压缩

`.timeline-virtual-wrap` 与 `.gallery-masonry-grid` 增加 `flex-shrink: 0`。两者的内联高度本来就代表完整虚拟滚动总高，参与父级 flex 收缩没有语义；修复后五布局的容器实际高度与内联高度逐项相等，页脚只在完整内容末尾出现。

**不把「没有更多了」做成 sticky。** 它是列表终态标记，不是持续可见的状态栏；sticky 会让它在用户仍处于列表中段时悬浮，改变“到底”的空间语义。页脚错误提前出现的原因是容器被压缩，不是标记缺少吸附。

### 2. 折叠态使用统一固定外高

折叠态不再是「估算 + 事后校正」，而是直接固定：社交卡 `310px`、正文区 `150px`、按钮槽 `26px`；`.timeline-virtual-item` 原有的 `padding-bottom: 12px` 使整行固定为 `322px`。占位、长文、图片正文、行无 `imageUrl` 但正文含图、短文、空正文全部使用同一外高。正文是否溢出只决定展开按钮和底部 fade，不参与高度计算；标题单行省略并提供全文 `title`。

**展开或显示译文时退出固定外高。** 这两个动作本来就会按真实内容增长；收起后恢复 310/150/26。卡片 310px 由 React 内联样式提供，`.social-card-collapsed` 只负责 `overflow:hidden`，不重复声明高度；正文 150px 同时由组件内联样式与 `.social-text.collapsed` 兜底，但 TS 常量仍是测量和虚拟估算的唯一决策源，JS 不读取 CSS 猜测值。

### 3. 虚拟估算与固定外高同源

所有社交行的 `estimateSize` 固定为整行 `322px`，不再读取摘要、`imageUrl` 或按 id 缓存猜测值。首帧虚拟总高与真实测量一致，滚动条不会在占位→水合时跳变；`scrollHeightSpread` 因此可以为 0。

### 4. 交互变化仍在同一 paint 内回写虚拟项

水合本身已不改变折叠外高。用户展开/收起或显示译文时，`SocialCard` 仍在 layout effect 中测量外层虚拟项高度并调用 `rowVirtualizer.resizeItem`；父级同步回写容器高度与兄弟项 `transform`。这层机制现在只承担真实的用户交互增长，而不是替内容特征猜测兜底。

### 5. 媒体重新测量绑定自然高度内层

`SocialCard` 的测量对象改为 `.social-text-inner`：它没有固定高度，媒体加载后 `scrollHeight` 才会变化。初始测量继续在 `useLayoutEffect` 内同步执行，保证首帧已有折叠结论；媒体事件通过 `requestAnimationFrame` 合并后再读一次，避免多个视频事件在同一帧反复 setState。`img`/`video` 节点既直接挂监听，也在内层挂捕获监听；正文 HTML 替换时 effect 以 `body.content` 重新建立监听，因此短→长→短会重新出现/移除展开按钮和裁切渐变。

### 6. 正文 HTML 注入对象按内容稳定

`SocialCard` 用 `useMemo(() => ({ __html: body.content }), [body.content])`（译文同理）锁住 `dangerouslySetInnerHTML` 的对象引用。正文未变时 React 不再重设 `innerHTML`，`<video>` 才能跨展开/收起、测量 setState 与其他无关 render 存活。测试同时记录媒体节点身份：初始→metadata→poster→展开→收起必须保持同一节点；这条断言与几何断言一起防止回归。

**不删除 160ms 列表入场动画。** 动画只改 opacity/translateY，不改变卡片在文档中的高度；本轮重叠在动画之外即可复现。删除它既不能修复几何，又会掩盖真正错误并损失既有的切换过渡。

**产品代价是短/空卡的正文区留白。** 短文和空正文仍占 150px 正文区，截图 `1440x900-social-collapsed-short.png`/`-empty.png` 与 980×640 同名证据显示留白明显但卡片节奏统一、操作栏仍可达；本轮接受该代价，换取水合零跳变、零重叠与正文外零 CLS。若产品要求短卡紧凑，必须采用 B（预取/预测量后再挂载），不能回退到按摘要估算。

- 证据边界：Edge headless 是 Chromium，不是 Tauri WebView2；脚本不启真实 IPC、数据库、网络账号，也不覆盖真实 WebView2 的字体/合成差异。jsdom 的布局 API 是替身，不能替代本几何证据。

## Alternatives considered

### Why not 把页脚设成 sticky？

sticky 会让终态文案在列表任意位置持续悬浮，用户无法再从视觉上判断“是否到底”。而且五布局的根因已经由容器压缩解释，吸附只是掩盖错误位置。

### Why not 删除或缩短列表入场动画？

入场动画只有 opacity/translateY，不参与卡片高度计算；审计确认它不是根因。删除正常动效会破坏布局切换的视觉连续性，且无法阻止“完整正文先布局”的时序缺陷。

### Why not 继续用 useEffect + ResizeObserver 首次判定？

普通 effect 在首次 paint 之后运行，长文已经以完整高度参与布局与虚拟行测量；随后再折叠必然产生可见中间帧和重叠。ResizeObserver 适合后续校正，不适合承担首帧定性。

### Why not 继续观察固定 150px 的 `.social-text`？

固定外框的尺寸在收起时不会变化，媒体加载只会撑开内层；观察它等于把 `load`/`error`/`loadedmetadata` 后的重新测量全部交给浏览器是否恰好改变外框。观察自然高度内层并给媒体事件补一条重新测量路径，才能同时覆盖延迟图片成功、失败、视频 poster 与元数据到达。

### Why not 只保留 `-webkit-line-clamp: 6`？

它只裁文本行，块级 `<img>` 仍能按自身高度撑开容器；审计实测图片正文可达 1095px。必须由固定 `max-height` + `overflow:hidden` 提供对所有后代内容都成立的上限。

### Why not 让高度随正文内容变化，只靠 useLayoutEffect 同帧修正（方案 C）？

P1 已证明这条路径会留下 1 帧重叠：子卡外框在水合 commit 时变化，`resizeItem` 与兄弟 `transform` 的回写即使都在 layout effect 内，也存在虚拟化快照与浏览器几何的不同步窗口。用户交互增长仍需要这套同帧回写，但把「占位→水合」的正确性建立在它上面，就等于继续依赖估算与调度时序。

### Why not 预取/预测量正文后再挂载可见社交卡（方案 B）？

B 能保留自然高度，但要为每个可见条目先等待正文 IPC，再在不展示的情况下完成布局测量，才能决定是否挂载；这会阻塞首屏、放大 IPC 风暴，并为「等待中的骨架占多高」重新引入同一类高度问题。当前虚拟列表与懒水合架构下，B 的改动面和性能成本都高于统一固定外高。

### Why not 继续用摘要/封面特征估算？

正文是 HTML，图片、引用、换行与样式都会改变高度；字符数、摘要长度和行 `imageUrl` 都不足以判断正文是否含图。`imageUrl=null + 短摘要 + body <img>` 正是估算失败的 P1。固定外高把正确性与「猜中内容」解耦。

### Why not 只放宽重叠断言，让视频展开的那一帧过去？

逐帧证据显示视频节点在展开 render 中被重建（`21 → 23 → 25 → 27`），这不是采样早了一帧的误报：节点重建意味着视频重新加载、播放进度与 poster 状态丢失，真实用户也会看到媒体闪烁。只延长等待或放过首帧会把缺陷留在产品里；稳定 `dangerouslySetInnerHTML` 的对象引用才是根因修复。

### Why not 给 fixture 恢复 800×1100 宽高，把 CLS 压回 0？

显式宽高会让视频从首帧就占据 poster 比例，覆盖不到 `readyState=0 → metadata → poster` 的真实媒体增长，也会掩盖媒体重新测量与节点重建问题。新 fixture 保留这条路径，改为把「列表几何稳定」与「裁切正文内媒体自然增长」分开取证：前者用卡片高度/虚拟起始位置 spread、重叠与滚动总高锁死，后者保留原始 CLS 数值并只对正文外 shift 设零容忍。

### Why not 直接删掉 CLS 断言？

删除会丢掉「水合把卡片或列表整体推走」的守卫。当前做法保留原始 CLS，同时按 shift rect 是否落在 `.social-text-inner` 过滤媒体内部增长；正文外 CLS 仍必须是 0，并额外断言卡片外高与虚拟起始位置 spread。

## Consequences

- 五布局页脚位置恢复为“完整内容末尾”；不再有首屏提前出现「没有更多了」的假到底。
- 社交卡折叠态统一为整行 322px（卡片 310px + 行距 12px）、正文区 150px、按钮槽 26px；长文/图片/短文/空正文/行无封面但正文含图都不再改变外高。
- 水合期间重叠帧、图片边界违规、横向溢出、槽高违规、正文外 CLS 与滚动总高变化全部为 0；裁切正文内媒体自然增长会记原始 CLS，但不推动卡片外框或相邻项。展开/收起仍按真实内容增长并恢复原高度。
- 延迟 HTTP 图片成功加载、404 失败、视频 poster 与 MP4 元数据到达都会重新测量内层；短→长→短正文替换会重新出现/移除展开按钮和裁切渐变。
- 产品代价是短卡/空卡正文区留白明显（最多约 90px），标题也改为单行省略以守住固定外框；截图证据已记录。若产品不接受这一密度，应整体转向 B，而不是重新引入内容估算。
- 固定外高使社交列表比旧版更高；这是用统一节奏和稳定性换取的可见空间成本，不是隐藏的布局跳变。
- 浏览器门禁每次多一次 `npm ci` 与约两分钟的 Windows job；artifact 保留截图/metrics。它证明 Chromium 布局，不证明真实 WebView2。真实 Tauri 窗口的最终观感仍应由实机验收补充。
