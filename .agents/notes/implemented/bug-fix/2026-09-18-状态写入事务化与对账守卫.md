# Agent Note: 状态事务、字段版本与不可复用的操作身份

Status: implemented

## Problem

文章状态与待推队列分开写会留下半边数据；把集合失败当空集会清掉本地状态；只在在线时登记意图又丢掉离线操作。网络期间用户替换队项时，普通ROWID复用还会让旧推送确认误删新意图。

## Decision

读/藏值、对应字段版本和队列变更在同一事务完成，批量操作全有全无。是否已配置凭据不决定是否保存本地意图；之后按bound_pending、local_only、bindable_retry等真实生命周期处理，不承诺每个离线意图都能自动推送。

pull在任何HTTP前捕获read/star版本，合并逐字段要求版本仍匹配且该字段无pending；读与收藏互不连坐。HTTP期间新出现的既有行也过守卫，只有同一DB临界区刚插入的新行可按初始状态接收整值。重建匹配映射不重定义旧快照；缺失基线可保守补0，不能拿网络之后的版本当请求之前的版本。

集合缺失、解析失败或分页未完成不等于空集，相关对账段失败关闭。已经完成的内容合并是否保留取决于提交模型：GR逐语句提交，Fever按页事务；不能说任何失败都会撤销整轮数据。

数据事件依据实际变化标记而非处理数量。同值UPDATE、读过一行都不证明数据改变；绑定、条件状态写或正文变更成功后立刻置位，必须早于后续可失败读取。Fever页回滚同时还原页内标记；GR已提交变化不能因后续失败丢失信号。跨阶段/重认证仍须显式传递标记，本地置位不是整链保真证明。

v18把sync_queue.id改为AUTOINCREMENT；显式保留已有id/payload/错误信息，SQLite维护后续序列。旧计划只按自己的操作id确认，用户删旧插新后获得新身份。迁移与索引重建同事务，FK坏数据导致整体失败而非静默丢意图；不复用保证从迁移后建立，不能恢复迁移前已消失的历史id。

## Alternatives considered

UI回滚只能修显示，不能补回后端半边事务；后端事务也不能证明前端所有乐观竞态正确。联网时锁整库会阻塞本地阅读和抓取；让push锁覆盖用户写入同样把交互绑到网络，因此用操作身份与字段版本隔离。

按payload/action/时间确认无法区分read→unread→read产生的相同目标，时钟精度不是操作身份。重新联网时全库重建差异也不如按操作保存意图直接。批量逐行提交虽可定义为另一种产品语义，当前“全部标读”没有承载部分结果的契约，故选择原子批量。

## Consequences

pending与版本保证的是每次请求快照的写权，代价是远端变化可能延后一轮。过期意图仍占库空间；迁移有一次队表复制成本，不凭“队列通常小”承诺耗时。

2026-11-06已确认双次乐观读/藏写均失败后UI与DB可不一致，重认证也可丢失此前已提交的数据变化标记。见[阅读与状态](../../../../docs/roadmap.md#reader-and-state)及[同步正确性](../../../../docs/roadmap.md#sync-correctness)，本篇不再宣称界面成功/回滚与DB全链一致。

## Validation

pull_field_versions_e2e覆盖在途本地写、缺失快照、提交后失败与真实前后值；Fever页回滚用例核对标记回滚。特定SELECT读取失败缺少确定注入时，只能记录行序核查边界，不能伪造测试证明。队列迁移及原子写用真实SQLite验证，协议对账与UI乐观回滚需各自证据。
