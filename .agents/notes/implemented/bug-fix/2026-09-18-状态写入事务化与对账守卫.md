# Agent Note: 状态写入事务化与对账守卫

Status: implemented

## Problem

文章的读/收藏状态写入分成两步：更新文章行、写待同步队列。两步之间没有事务，于是第二步失败时留下「本地状态已改但没有待同步记录」——这条变更永远不会被推送到服务端，用户以为标读同步了，实际上没有。

另一个方向的错误更危险：**对账把「拉取失败」当成「空集合」**。服务端返回错误时，对账逻辑拿到的是一个空集合，于是把本地所有「服务端说已读」的条目回滚——一次网络抖动就能清空用户的收藏状态。这是审计给的 P0 级判断。

第三个问题：离线期间的状态变更**不入队**。入队决策取决于「变更瞬间是否已配置凭据」，未配置时直接 return，于是离线做的标读在联网后不会补推。

## Decision

**状态写入与入队必须同事务。** `set_read_enqueue_in_tx` 是事务内核，三个入口共用它：

```rust
pub fn set_read_with_enqueue(conn: &Connection, id: i64, read: bool) -> AppResult<()>
pub fn set_starred_with_enqueue(conn: &Connection, id: i64, starred: bool) -> AppResult<()>
pub fn set_read_bulk_with_enqueue(conn: &Connection, ids: &[i64], read: bool) -> AppResult<()>
```

**批量路径全有全无，不产生部分成功。** 逐条执行、部分成功会让用户在界面上看到「一半标读了」，而计数对不上账时无从判断后端改了哪些行。语句顺序与既有的 `mark_all_read_with_enqueue` 逐列对齐——两个批量入口的行为必须一致。

**离线变更一律入队。** `set_read` / `set_starred` **无论是否已配置凭据都入队**；凭据缺失时 `push_states_now` 静默跳过即可（队列本身有清理机制）。判据从「变更瞬间是否已配置」改成「这次变更需要被推送」——后者才符合用户意图。

**失败 ≠ 空集合。** 任一集合拉取失败即**整轮跳过该对账段**（`reconcile_ok` 守卫，`sync/fever_pull.rs`），绝不把错误等同空集合。这是两个协议共用的守卫，属于冲突政策的一部分，见[同步冲突政策单点](../architecture/2026-10-07-同步冲突政策单点.md)。

**pending 保护**：本地有未推送变更的条目跳过对账，防止把「刚标读/刚收藏」的瞬间回滚，也防止两端乒乓。

**分页拉取的中断必须报错。** GReader 的 `fetch_stream_ids` 分页若 continuation 解析失败、或 continuation 非空但本页返回 0 条，必须 `return Err` 让整轮对账跳过——否则一个被截断的 starred 集合会被当作完整集合，用它去对账就会清掉用户的收藏。

## Consequences

**收益**：离线变更不再丢失；批量操作要么全成要么全败，界面的成功提示与后端实际状态一致；网络抖动不会破坏本地状态；分页中断不再静默清空收藏。

**代价与已知上限**：

- 「无论是否配置凭据都入队」会让未配置同步的用户也积累队列条目。队列有 TTL 清理，但如果用户长期不使用同步，队列会有一批最终被清掉的记录——这是可接受的代价，换来的是「先离线操作、后配置同步」这个真实场景的正确性。
- 整轮跳过对账意味着一次失败会让这一轮的所有条目都不更新（包括本来能成功的那部分）。这是保守取舍：宁可少做，不可错做。
- pending 保护会让「远端已改、本地待推」的条目在对账中一直跳过，直到推送成功。若推送长期失败，这部分条目会保持本地优先且不被远端纠正。
- `let _ =` 形式的吞错在少数位置仍有残留（例如 `sync/entries.rs` 的 `backfill_article_content` 调用），见 [docs/roadmap.md](../../../../docs/roadmap.md)。

## Alternatives considered

### Why not 让状态写入失败时回滚 UI？

UI 侧的乐观写入本来就有回滚（见[乐观写入的版本守卫](../architecture/2026-10-05-乐观写入的版本守卫.md)）。Rust 侧的事务是同一件事的另一半：UI 回滚解决「显示不对」，事务解决「数据半边」。两者都需要，不能互相替代。

### Why not 保留 `let _ =` 吞掉队列写入失败？

吞掉后接口不需要返回 `Result`，调用方更省事。代价是「本地改了但不会同步」这种状态下没有任何信号，用户与开发者都不知道。审计点名这类吞错为缺陷模式，改法是把错误传出去并记入 `report.errors`。

### Why not 只在「已配置凭据」时入队，另设一个「联网后全量对账上传」？

全量对账上传需要在联网时重建「本地与远端的差异集」，而这个差异集只能靠比对全部文章状态得出——代价远高于按操作入队。入队是增量且精确的。

### Why not 让批量操作逐条提交，失败的单独上报？

部分成功在数据层是合法的，但在用户界面上不可解释：用户看到「全部已读」的提示，而实际只读了一部分。审计的完成标准写的是「失败不假成功」——要么整体成功，要么整体失败并如实上报。
