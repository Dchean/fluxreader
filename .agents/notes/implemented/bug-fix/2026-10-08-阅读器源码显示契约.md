# Agent Note: 阅读器源码显示契约

Status: implemented

## Problem

审计 F14（P2，浏览器演示模式实测）：“源码/渲染”按钮只切换 CSS——正文在点击前后走同一条 `dangerouslySetInnerHTML` 路径，`innerHTML` 与 `textContent` 完全一致，仅容器 className 多了 `raw-render-mode`。用户看不到任何 HTML 源码：这是有入口、没有承诺行为的功能空壳。

同一切面还有两个相邻问题，决定“源码态”必须选对内容与路径：

- **图片代理会改写正文。** 防盗链域名（少数派等）的 `<img src>` 会被 `proxyImagesInHtml` 换成后端抓取后的 `data:` base64 产物。若源码态复用它，用户看到的是代理产物的大块 base64 而不是原始 `src`——那不是源码。
- **流式译文是未消毒产物。** 翻译进行中（`rawTranslatedIds` 命中）模型输出按纯文本渲染（TASK-065 N11 契约）。源码态必须同样坚持纯文本——把未消毒输出转成“HTML 源码”展示，等于给它开了第二条 HTML 路径。
- **切回渲染必须无损。** 渲染态要保持现有 `.article-prose` 阅读样式、外链处理与图片灯箱点击代理，不能被源码态改造降级。

## Decision

**源码态 = 转义文本展示，与 HTML 渲染路径在结构上分离。** 三条呈现路径收口到新的生产组件 `ReaderProse`（`src/components/ReaderProse.tsx`）：

- 源码态：`<pre class="reader-source-view">` 内**文本节点插值**，转义由 React 单点完成——源码里的 `<p>`/`<b>`/`<img onerror=…>` 只作为字面文字可见，不创建元素、不执行属性；
- 流式译文：纯文本插值（N11 契约从 Reader.tsx 移入本组件，语义逐字保留）；
- 渲染态：保持原 `dangerouslySetInnerHTML` + `.article-prose` 与点击代理，行为不变。

**源码内容取“当前用户选择的原始文本”，且不经图片代理。** `renderHtml`（可含代理产物）只给渲染态；`sourceText` 取基础 HTML（提取全文或 RSS 原文）或已消毒译文——原始 `src` 可见，代理 base64 不会冒充源码。流式期间两者都是纯文本。

**回归按证据强度分层**：源码态转义无标签、渲染态 DOM 照旧、流式纯文本、源码态不含代理 base64，全部由 `react-dom/server` 的**真实 SSR 输出**断言（`tools/frontend-regression.mjs` OPT-012 块，与 `probe-before.mjs` 的修前复刻对照）；值传递接线（模式/内容选源）由 Reader.tsx 参数级源码断言钉住——zustand v5 的 SSR server snapshot 恒读 `getInitialState`（t116 注既定边界），SSR 看不到真实 store 状态。

## Consequences

**收益**：源码按钮有真实承诺行为；源码/渲染两条路径在组件结构上分离，后续改进渲染路径不会悄悄改变源码路径；转义责任单点交给 React，没有手写 HTML 转义函数可漏。

**代价与已知上限**：

- 源码态是纯文本 `<pre>`，没有语法着色；真实需求出现再加，当前不做。
- 无浏览器级交互回归（仓库无 jsdom 类依赖）：SSR 输出断言覆盖结构与转义，点击/滚动仍靠手工验证。
- `Reader.tsx` 不再直接持有 `dangerouslySetInnerHTML`；回归网原 (n11) 的源码形态断言按新结构改写（行为覆盖保留并升级为 SSR 输出断言，理由写在 harness 注释里）。
- 源码容器样式仅新增 `.reader-source-view` 局部规则（折行 + 超长 token 断行），不动既有正文排版。

## Alternatives considered

### Why not 转义成字符串后继续塞 `dangerouslySetInnerHTML`？

手工转义是易错点（`&`、引号、`<`、`>` 全都要处理，顺序还不能错），而且“转义字符串 + dangerouslySetInnerHTML”在代码结构上仍是一条 HTML 创建路径，审查与回归很难区分两种意图。React 文本插值把转义交给框架单点完成，源码分支与 HTML 分支在结构上可见地分开。

### Why not 源码态先用隐藏 DOM 渲染再取 `textContent`？

那要求源码先被创建成真实元素（`onerror` 等属性存在且有执行窗口），与“不创建标签、不执行源码中的标签”直接冲突；还要处理不可见节点的副作用。文本插值是同一目的的无副作用路径。

### Why not 源码态显示净化后译文的 HTML，而不是译文文本本身？

源码语义是“当前内容的源文本”：用户选择译文时给译文，选择 RSS 原文/提取全文时给对应原文。译文在流式期间是未消毒产物，绝不能进 HTML 创建路径；已消毒译文与原文走同一条转义展示路径，无需区分。

### Why not 把源码态做成独立弹窗/路由？

保持“同屏切换查看”的既有交互；独立弹窗会引入新的浮层登记与焦点/Esc 规则（浮层清单是手工维护的，关闭确认框刚被漏项咬过一次，见[键盘导航、焦点与卡片角色](../feature/2026-10-06-键盘导航、焦点与卡片角色.md)），收益不足。
