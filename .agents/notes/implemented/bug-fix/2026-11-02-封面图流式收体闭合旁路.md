# Agent Note: 封面代理在读取响应期间限制字节数

Status: implemented

## Problem

fetch_image 原先仅先检查 Content-Length，再完整读取 bytes 后检查25MiB。无长度或流式响应会在拒绝前占用完整响应内存，预检不能承担读取期间的上限。

## Decision

HTTP 内核 fetch_image_inner 经 ingestion::read_body_capped(resp, MAX_IMAGE_BYTES) 收体，复用长度预检和累计上限。图片是二进制，直接返回 bytes，不走文本 charset 解码。

超限使用 responseTooLarge。前端 imageProxy 三条调用路径都捕获拒绝并降级为隐藏或占位，没有按旧 imageTooLarge 码分支；统一错误码不改变这些降级路径。

## Alternatives considered

保留旧码需要无人消费的错误映射；自行写 chunk 循环会复制已经遗漏过的防线。read_body_capped 已接收上限参数，图片25MiB与文本16MiB由调用方选择，无需再扩展签名。

## Consequences

此上限限制封面代理收体，不等于所有网络读取都由本篇覆盖。2026-11-06 审计时 WebDAV、模型列表和 AI 错误响应仍存在无累计上限路径；后继 AB 修复已将 WebDAV/Gist 读取及模型列表成功响应接入 16MiB 收体界，Gist 创建成功响应同样有界，AI 与相关 Gist 创建错误详情只保留 8KiB 前缀并标明截断。配置上传不读取成功响应正文，已有仅报告状态的错误分支也没有新增整页读取。scheduler 文章页随后以 16MiB 复用同一 helper；封面图片仍用本篇的 25MiB，不混淆图片与网页预算。

这些后继修复没有改变本篇选择共享累计读取 helper 的理由。单请求上限不是进程整体内存上限，响应解压、已交付网络块、解码和并发仍各有成本；不能由这些调用点外推任意未来网络读取已受保护。当前验证缺口与边界见[AI 与内容路线](../../../../docs/roadmap.md#ai-and-content)。

## Validation

image_proxy_tests::oversized_image_body_without_content_length_aborts_midstream 用真实 loopback EOF 响应验证 responseTooLarge，并断言服务端未发送完计划块数；这证明读取中断，而非仅凭完整读取后的错误码。2026-11-07 AB/C/D 的限定自测与独立审计又覆盖新增调用点的 CL/EOF 超限和正常响应对照；精确版本与运行证据保留在本轮交付，不把分批通过写成最终整合或原生通过。真实图床兼容和 WebView 图片解码是另外的验证面。
