# Agent Note: 封面图代理的响应体读取闭合——经 read_body_capped 流式收体

Status: implemented

## Problem

`commands/settings.rs` 的封面图下载（`fetch_image`）是三条响应体读取旁路里最后一条：先做 Content-Length 预检、再 `resp.bytes()` **完整收体**，收完才检查 `MAX_IMAGE_BYTES`（25 MiB）。CL 预检只挡「诚实」的大响应——无 Content-Length 定界（chunked / EOF 收尾）或谎报小 CL 的超量流式响应会先把内存吃满才被拒。与已修复的两条同族旁路（favicon 探测、全文提取，2026-11-02 统一经 `read_body_capped` 的 16 MiB 界）同源，图片路径因字节上限不同（25 MiB）此前未接入。

## Decision

`fetch_image` 拆出纯 HTTP 内核 `fetch_image_inner(http, url, page_url)`（命令层只做 State 解包），收体改经 `crate::ingestion::read_body_capped(resp, MAX_IMAGE_BYTES)`：CL 预检与累计上限两道防线由 `read_body_capped` 单点承担，图是二进制——bytes 直接返回，**不经** `decode_body_bytes`（那是文本路径的 charset 解码）。

超限错误**对齐 `responseTooLarge` 口径**（替换原 `imageTooLarge`/「图片过大」）：与 favicon（并入「任何失败返回 None」负缓存）、全文提取（返回 `responseTooLarge` 业务文案）的既有降级路径同族。图片场景的具体落点：`fetch_image` 对前端是 invoke rejection，`imageProxy.ts` 的三处调用（HTML 注入、`proxyImageUrl`、`fetchProxiedImage`）全部 catch 后降级（隐藏图片 / 返回 null / `reason: 'error'`）——错误码不参与前端分支，仅用于诊断，行为面零变化。

## Alternatives considered

- **保留 `imageTooLarge` 错误码，把 read_body_capped 的错误映射回去**：维持前端可诊断的专用码，但前端根本没有按码分支（三处 catch 都不看 code），映射层是无人消费的死代码；统一口径后三条旁路同族同码，排查时不必记忆两套语义。
- **给 read_body_capped 加可选的「图片界」参数/泛化上限**：上限是调用方的策略，函数已按参数接收；为图片场景复制一个常量参数即可，不该为调用方便利改公共函数签名。
- **在 read_body_capped 之外手写 chunk 循环**：绕开文本路径的关注点（decode），但复制了 CL 预检 + 累计分支的防御实现——旁路的存在正是复制实现漏掉防线造成的，这次必须收敛到单点。

## Consequences

- `image_proxy_tests::oversized_image_body_without_content_length_aborts_midstream`（模块单测，真实 loopback mock）：无 Content-Length 的 EOF 定界流实发超过 25 MiB——客户端返回 `responseTooLarge`，且 mock 实发块数少于计划量（连接被客户端中止，不再完整收体）。
- 行为验证由 CI 的 rust job（windows-latest）承担；本机不可链接，仅 `cargo fmt --all -- --check`。
