# Agent Note: Fever 推送幂等与订阅恢复收敛（B1）

Status: implemented

## Problem

阶段 A 用真实服务端语义（固定上游源码证伪，见
[测试替身对齐真实服务端语义](../testing/2026-10-31-测试替身对齐真实服务端语义.md)）
重建门禁后，两个推送缺陷在门禁下显形，10 个登记的红门禁候选在真实语义下必然红：

1. **Miniflux 星标翻转**：Miniflux 的 Fever `mark=item&as=saved/unsaved` 都走
   `storage.ToggleStarred` 取反（internal/fever/handler.go:443-467），而产品推送
   无条件按本地意图发 mark——推送响应丢失后重发、或另一设备已把条目改到目标态
   时，stale 队列项把星标**翻反**。FreshRSS（api_version 实测 4）是绝对赋值
   （`markFavorite(id, true/false)`），同型请求幂等，不受影响。
2. **quick_add 跨重启卡死**：pending subscribe 与退订恢复行把「幂等
   quick_add-by-URL」当解析通道，而真实服务端对重复 URL 一律拒绝（FreshRSS
   200+numResults=0 无 streamId、Miniflux 500 feed_already_exists）——崩溃窗口
   内 quick_add 已被服务端执行的行，重启后永久 Retry。

写域约束：greader_pull.rs / fever_pull.rs / db/** / ingestion/** 属 B2，前端
属 B3，本修复只动 fever.rs / sync/push.rs / sync/subscriptions.rs 与相应测试。

## Decision

现在的契约：

- **Fever 星标推送按服务端变体收敛**（`FeverClient::push_star_state`，push.rs
  分派，GReader 路径逐字不变）：api_version >= 4（FreshRSS 家族）mark 是绝对
  赋值，保持总是发送（零探测开销）；api_version 3（Miniflux 家族，固定源码
  `baseResponse` 恒为 3）或版本未知（本轮尚无任何响应）先以 `items&with_ids`
  探测当前 is_saved，**仅当当前态≠目标态才发 mark**——「响应丢失重发」与
  「另一设备已改到目标态」都收敛到用户意图。探测失败或条目在响应中不可见 →
  保守报错（队列保留，下轮重试），绝不盲发。返回「是否实际发送」，Ok 一律按
  已收敛确认出队。
- **quick_add 恢复路径以订阅列表为唯一证据源**：pending subscribe（含 legacy
  add_feed 路径）在 quick_add 前先按规范化 URL 解析远端列表——已存在直接收敛
  （`resolve_existing_feed_id`），quick_add 未返回 id 或失败后再解析一次（创建
  可能已在错误返回前落地）；列表读失败 = 无法确认缺席 = **不发 quick_add**
  （fail-closed），保留队项下轮重试。仅确认不存在时才重发。
- **退订恢复解析+发现共用一次列表读取**：列表同 URL 的第一个 id 即已验证目标，
  成功后先持久化（`advance_unsubscribe_resolution`，按 account_key+generation
  严格限定作用域）；列表读成功但无同 URL id = 远端没有可退订目标 = 意图已满足，
  直接确认；已持久化的解析目标仍参与退订，其在远端消失由客户端 2xx-strict 容错
  （400/404 = 已满足）吸收，不得永久 Retry。`quickadd_non_idempotent` 注入与
  mock 的 `ReturnExistingId` 旧契约随之删除。

## Alternatives considered

### Why not 盲发 + 依赖服务端幂等？

对 FreshRSS 成立（绝对赋值天然幂等），对 Miniflux **不成立**：ToggleStarred 下
「已处目标态再发同向 mark」正好翻反——审计已实测钉死该高危缺陷。无差别盲发等于
把星标正确性押在服务端变体上，而变体在协议层不可知（只能靠 api_version 判别），
否决。

### Why not 每次推送前全量对账（拉全量权威集合再决定）？

星标推送只需**单条**条目的当前态，`items&with_ids=<id>` 一次请求即可；全量
`saved_item_ids` + 逐条比对的成本随收藏数线性增长，且把推送语义耦合进对账语义
（对账是双向权威策略，推送是单向意图落地），两套判定混在一起会让「推送翻反」
与「对账收敛」互相掩盖。单条探测是最小充分检查，否决。

### Why not 保留 quickadd-by-URL 解析、仅在失败时回退列表？

quickadd 的「失败」无法与「已创建但响应丢失」区分——失败后回退列表虽然能收敛，
但每次恢复都会先打一发真实服务端必拒的 quick_add（Miniflux 每轮 500、FreshRSS
每轮 numResults=0），既污染服务端日志又依赖错误形态解析；列表先行一次请求即可
同时完成「解析」与「重复目标发现」，否决。

## Consequences

**收益**：10 个候选测试全部回到真实语义并转绿（opt009_phaseb_e2e 9 个 +
account_lifecycle_e2e 1 个，含更名）；新增覆盖——星标响应丢失重发收敛、stale
队列不翻反（双向）、重复 URL 拒绝保留意图（两变体）、quick_add 响应丢失跨重启
列表证据收敛（零二次 quick_add、零重复行）；legacy add_feed 路径获得同样的
跨重启收敛（此前 numResults=0 会被剪队静默丢绑定）。

**代价与已知上限**：Miniflux 型星标推送每次多一个 `items&with_ids` 探测请求
（低频操作，可接受）；星标变体判定依赖 api_version——api_version >= 4 且实现
toggle 语义的未知服务端会被误判为绝对型（两家 pinned 上游无此形态，live 验收
归 §5 的「未实机验收」口径）；退订恢复的「列表读成功但 URL 缺席 = 意图满足」
是新增的缺席证明路径，依赖订阅列表的最终一致性（与 pull 的墓碑回收同口径）。
留给 B2 的接口注意点：`resolve_existing_feed_id` 与退订恢复都只消费
`Backend::subscriptions()`，B2 改动 greader_pull/fever_pull 时不得改变该端点的
失败语义（读失败必须保持显式错误，fail-closed 依赖它）。
