# Agent Note: Fever 星标兼容与订阅列表证据恢复

Status: implemented

## Problem

2026-10-31所核验的旧Fever变体把saved/unsaved都实现为toggle，盲目重发可翻反用户星标。订阅创建的另一问题是quick_add并非通用幂等查找：重复URL可能返回无id或失败，创建已成功但响应丢失时，继续quick_add会卡住或制造重复。

## Decision

Fever api_version≥4直接发目标态，3或未知先with_ids读取is_saved，不同才发mark；缺条、缺状态或请求失败保留队项，不盲发。后继[ACK验证](2026-11-03-状态写回ACK验证与条目三态.md)再读回确认目标态才出队。

版本号只是当前保守分支，不能作为toggle存在性的充分证据。2026-11-05固定上游复核中Miniflux faecfa2已是条件绝对赋值，api_version仍为3；FreshRSS 4e8a258也是绝对赋值。旧toggle夹具作为兼容变体保留，来源见[兼容矩阵](../../../../docs/sync-compat-matrix.md)。

订阅恢复先读远端列表，规范URL已存在则复用；未确认缺席前不发quick_add。创建失败/无id后再读列表处理“已创建但响应丢失”。退订恢复共用一次列表发现，已验证id先按账号/代际持久化；成功列表无同URL目标可确认意图满足，已持久目标的400/404兼容语义由协议层处理。列表读失败仍是未知，不能结算。

## Alternatives considered

盲发依赖服务端幂等，对旧toggle变体不成立。推前拉全量收藏集合又把单条写入绑到集合规模，单条读取更小。失败后才回退列表仍会每轮先发一笔可能有副作用的quick_add，故列表先行。

## Consequences

版本3绝对赋值服务仍付额外探测成本。读到发送之间存在TOCTOU，读后确认不能将请求变成服务器条件写；≥4但实现toggle的未知变体也超出当前分支假设。

2026-11-06证明断开后Fever客户端内部多请求链仍可发后续请求，外层代际守卫不足以守住每个HTTP边界，见[同步正确性路线](../../../../docs/roadmap.md#sync-correctness)。列表缺席证明同时依赖服务端列表完整性/一致性，不能作为所有部署都严格原子的保证。

## Validation

fever_compat和opt009/account_lifecycle夹具覆盖响应丢失、目标已达、重复URL拒绝及跨重启恢复；固定上游源码用于校准夹具，不等于当前用户真实账号已跑过。应保留绝对赋值与旧toggle两种行为，而非用版本号把后者冒充当前Miniflux事实。
