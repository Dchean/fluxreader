# Agent Note: 清除与在途流式互斥

Status: implemented

## Problem

`clearAiProduct`（src/store/slices/ai.ts）先 `await` 后端 `ai_clear_cache`，返回后才清前端状态并删除 `rawTranslatedIds[id]`。若该条目的翻译正在流式生成，删除标记后后续未消毒 delta 仍会追加进 `translatedContent`，而 Timeline 的卡片渲染（`rawTranslatedIds` 未命中时）走 `dangerouslySetInnerHTML`——未消毒模型输出直接进 HTML 路径（XSS 窗口）。同一组合还有一层后端竞态：清除删掉缓存后，生成完成回写（Done + 回读落账）会把刚清空的缓存复活。

独立审计复审（2026-11-01）补出三个边界，随本篇一并收口：

- **跨 kind 击穿**：清除路径的 `delete rawTranslatedIds[id]` 不分 kind——清除 summary 也会删译文的未消毒标记。译文流失败留半截时（「半截+标记」成对保留的重试语义），summary 清除把标记拆掉后没有任何后续 delta 来补回，未消毒半截**长期**滞留 Timeline 的 HTML 渲染路径（持续态，不是竞态窗口）。UI 当前只接线 `'translation'` 故不可达，但 `clearAiProduct` 是公开 store API（types.ts）。
- **硬闸文案引用不存在的入口**：「先等完成或停止」——全库没有停止生成的入口，挂死的 IPC 会让该 (条目, 产物) 的清除被永久拒绝。
- **Done 后回读尾巴不在 trackAiRequest 链上**：invoke settle 即摘除在途（b1-2 契约），硬闸放行的清除完成后，挂起中的旧回读携**清除前**行数据落地，会把已清产物复活到前端（无 XSS——回读内容是 DB 消毒版；下次 reload 经 reconcile 自愈）。

## Decision

**清除与在途生成互斥，双侧设防：**

- **硬闸（a）**：`clearAiProduct` 在发起后端调用前检查在途表 `aiInFlight`（验签 + 条件生成整链，键 = `aiKeyOf(id, kind)`）；命中即拒绝——不调后端、前端状态一字不动，toast「生成进行中，完成后再清除；若长时间无响应可重启应用」。摘要与译文同闸（摘要无 XSS 面，但后端清除与生成落库同样互斥）。文案不承诺「停止」：不存在停止入口，只给可自愈的出路。
- **自愈（b）**：`streamAiDelta` 对 `translatedContent` 的每个 delta 先检查 `rawTranslatedIds[id]`，缺失即补回 `true` 再追加。任何路径在流式在途期间丢掉标记（含清除 await 竞态残留），下一个 delta 都会把渲染拉回纯文本分支。**顺序契约：补回先于追加**——追加落地时标记必须已为 true（回归断言经 store 订阅钉住这一帧）。

**不变量：凡 `translatedContent` 可能含未消毒 delta，`rawTranslatedIds[id]` 必为 `true`。** a 挡住已知的制造窗口的组合，b 让不变量对流式期间的一切标记丢失自愈，不依赖「今后不再新增会删标记的路径」这一全局论证。**边界（跨 kind）：未消毒标记的生命周期只挂在译文上**——summary 清除不触碰译文侧的任何状态（标记、错误、展示态都不动），「半截+标记」的失败重试语义成对存活；译文清除也只删译文自己的标记。

**回读尾巴收口（代次推进）**：清除成功后，若该 (条目, 产物) 的请求代次自清除发起以来未变（await 期间没有更晚请求接管），则把代次 +1——挂起中的旧回读经 `isCurrentAiRequest` 失配被整体丢弃，不再复活已清产物。回读本身的语义不动（守卫机制原样复用，清除只是成为又一个推进代次的事件，与 `beginAiRequest` 同型）。

回归钉在 `tools/frontend-tests/ai-cache-signature.mjs`（b3-6）：在途清除被拒（不调后端、标记保留）、拒绝后流式继续按纯文本口径、标记丢失后 delta 自愈补回且补回先于追加、摘要在途同闸、跨 kind 清除不拆译文标记、清除后迟到回读不复活产物。

## Alternatives considered

- **只做自愈（b）**：改动最小、不新增用户可见拒绝，但窗口只是收窄而非消除——清除的 set（删标记 + 清产物）与下一个 delta 到达之间，渲染路径短暂回到 HTML 分支；且后端清除与生成落库互相复活/清空的竞态完全没堵。作为独立方案不充分，保留为纵深防御。
- **只做硬闸（a）**：挡住本缺陷的组合，但不变量的成立依赖审计「所有删标记路径」，未来新增清理入口时不设防；与 b 组合后才能宣称不变量。
- **清除排队等待在途流结束再执行**：避免拒绝用户，但「已清除」反馈时刻与真实清除时刻分离，还要处理流失败/重试与清除动作的交叉状态机；拒绝 + 提示的语义最小且可预期，用户等生成收尾后重按即可。
- **回读纳入 trackAiRequest 链（P3-3 的另一方向）**：让在途表覆盖到回读完成，硬闸自然不放行。否——b1-2 回归锁定了「invoke settle 即摘除在途、第二笔可发起」的契约（逆序回读场景依赖它），改链要重构三个 run* 的 promise 结构并翻转既有锁定行为，牵动面远大于缺陷本身。
- **清除成功后无条件推进代次**：实现更短，但清除的 `await` 窗口内可能有新请求接管同一 (条目, 产物)——无条件 bump 会把新请求的流内回包全部判旧丢弃，`translatingIds` 卡死。带「代次未变」守卫的 bump 只丢弃确属旧代的回读。

## Consequences

生成/验签在途期间清除入口返回 `false`（不执行），提示文案为「生成进行中，完成后再清除；若长时间无响应可重启应用」——验签窗口（毫秒级）也按此文案拒绝，覆盖面略宽于字面「生成中」，可接受。delta 路径每发多一次 map 查找，标记健在时零写入、无额外渲染。清除 summary 时译文侧状态零触碰；清除译文后，挂起中的旧回读被代次失配丢弃，不再有「清除被回读复活」的窗口。Timeline/ReaderProse 的渲染口径不变，本契约由标记单点保证。
