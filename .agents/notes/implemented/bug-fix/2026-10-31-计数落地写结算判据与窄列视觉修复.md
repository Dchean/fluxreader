# Agent Note: B3 计数落地写结算判据与窄列/画廊视觉修复

Status: implemented

## Problem

审计修复收敛路线（[审计修复收敛路线](../../proposed/process/2026-10-31-审计修复收敛路线.md)）阶段 B3 的三个实测复现缺陷：

1. **reload 计数陈旧落地窗口（P2）**：单条 toggle 在途时发起 reload，`set_read`
   结算于 `counts_snapshot` 的取数窗口内，陈旧计数照常落地——unread 回退而条目
   `isRead=true`；smartDedup 关闭时无任何后续计数写者，不自愈。根因：现有落地守卫
   （读取令牌最新 + 写前沿未动 + 落地时无在途写）对该窗口全盲——写发起时的 bump
   已计入 `flagSerialAtStart`，结算又让在途计数归零，两判据在落地时刻均判「新鲜」。
   后端前提（只读确认）：`counts_snapshot` 与 `set_read` 共用同一把
   `AppState.db` 锁（src-tauri/src/commands/articles.rs），快照读取与写提交的
   服务端先后序由锁竞争决定，前端无法从响应到达顺序推断快照是否已含该写。
2. **视图筛选后标题截断（P2）**：320px 最小列宽下「文章 · 收藏」被截成「文…」
   （1440px 宽屏同样发生）。根因：`.view-title-text`（min-width:0 + shrink:1）
   允许收缩至任意窄，而 `.filter-sort-group` `flex-shrink:0` 优先占位，三按钮
   （约 230px）挤掉标题。
3. **画廊图片加载塌缩（P3）**：`.gallery-card img` 无占位，加载期卡片塌到
   63.5px、加载后跳到 427px，瀑布流整体重排。

## Decision

1. **计数落地第三判据（写结算序号）**：`endLocalFlagWrite` 推进
   `localFlagWriteSettleSerial`；reload 与 `reconcileCountsOrdered` 在取数发起时
   快照该序号，落地时刻不一致即拒落——「取数窗口内发生过写结算」⇒ 快照相对终态
   可能陈旧（服务端锁序不定向，宁可多一次 IPC，不落可能陈旧的数字）。仅因本判据
   拒落（令牌仍最新、写前沿未动、无在途写）时安排 `scheduleCountsReconcile({ force: true })`
   权威对账自愈；其余拒落原因（更新的读取 / 在途写）已有各自收敛路径，不重复安排。
   判据对称应用于 reload 与写后对账两个计数写者；对账侧兜底必要，因为触发结算的
   写自身调用的 `scheduleCountsReconcile()` 在 dedup 关闭时是 no-op。
2. **窄列标题换行**：`.control-bar-main-row` 加 `flex-wrap: wrap`，标题保持
   max-content（自身超宽才合理省略），三按钮掉到第二行；`.filter-sort-group`
   加 `margin-left: auto`（换行后贴右缘，单行时与 space-between 同形）。
   宽列单行形态逐字不变，980 最小宽布局不受影响。
3. **画廊加载占位**：`.gallery-card img` 加 `aspect-ratio: auto 4 / 3`——
   `auto <ratio>` 语义为「有固有比例用固有，无则回落声明比例」：加载完成后
   自然比例优先（瀑布流观感不变），加载期按 4:3 占位，与
   `estimateGalleryCardHeight` 的估算口径（列宽×0.72 + meta ≈ 64）一致，
   消除塌缩/跳变；虚拟化测量（measureElement/ResizeObserver）不受影响。

## Alternatives considered

1. **计数窗口**：
   - a) 字段写落定后无条件补一次计数对账——实现最简（把 dedup 门控去掉/补 force），
     但每次 toggle 恒多一条 IPC，稳态成本换极小概率窗口；否。
   - b) 第三判据（本方案）——仅在「结算落入取数窗口」这一重叠态补一次对账，
     稳态零成本、窗口态一次 IPC；代价是新增一个序号与两处比对，拒落粒度是
     「整块计数」而非逐字段（整块粒度与既有 R2/N2 协议一致）；取 b。
   - c) 后端让 counts_snapshot 携带「含哪些已提交写」的序号/时间戳供前端比对——
     需要后端新协议且写与读仍可能在锁边界交错，复杂度不成比例；不做
     （本轮不改后端行为语义）。
2. **窄列标题**：
   - a) 媒体查询/容器查询下按钮改纯图标——保留单行但引入第二套按钮形态，
     可达性（文字标签消失）与实现面都更差；否。
   - b) 标题设 min-width 下限硬挤按钮——按钮区溢出或换行行为不可控；否。
   - c) 换行（本方案）——单行形态不变，窄列退化行为可预测；取 c。
3. **画廊占位**：
   - a) 组件加 onLoad 状态 + data 属性切 CSS——JS 状态、重渲染与 React 19
     缓存图 onLoad 边界都要处理；否。
   - b) 固定 `aspect-ratio: 4/3` + object-fit: cover——统一裁切破坏瀑布流
     自然比例观感（与既有「不裁切」契约冲突）；否。
   - c) `aspect-ratio: auto 4/3`（本方案）——纯 CSS、加载前后语义都对；取 c。

## Consequences

- 回归锁定：`tools/frontend-tests/mutations-and-counts.mjs` 新增 (e2-b3)——
  挂起 counts_snapshot → set_read 窗口内结算 → 释放陈旧快照（COUNTS 静态值，
  = set_read 提交前读数）→ 断言终态 unread=后端口径 1 而非陈旧 3（修前必红）；
  `tools/frontend-tests/ui-contracts.mjs` 新增 (b3-ui1/b3-ui2) CSS 形态契约
  （无 DOM 布局引擎，证据形态与 fix-11/12、opt012-e1 一致）。
- 成本：稳态无新增 IPC；仅「结算落入取数窗口」多一次 counts_snapshot；
  失败回滚结算也推进序号 → 在途计数拒落 + 权威对账，语义保守正确。
- 遗留：陈旧计数拒落后的补对账仍是一次异步收敛（拒落瞬间显示旧值），与既有
  「失败保守保留现值」语义一致；后端锁序不改变，本判据对两个方向的锁竞争
  （快照先/后于提交）都成立——快照若已含该写，补对账只是冗余一次 IPC。
