# Agent Note: GitHub 设备流后端取消与代次

Status: implemented

## Problem

前端取消 GitHub 登录时只递增本地代次、清定时器并清空 `githubFlow`。这只阻止
前端继续展示或重排轮询，却没有改变 Rust 中仍可继续执行的设备流。轮询已经拿到
token 后，即使前端刚刚点击「取消授权」，`github_login_poll` 仍会向
`config_sync_credentials` 与 `github_login_name` 写入旧账户，并返回成功。
取消后立即重新发起也相同：旧 poll 可能在新 start 之后完成并覆盖当前状态。

网页侧的 GitHub 设备授权本身没有客户端撤销端点。因此问题不能靠「清前端状态」
解决，必须由持有设备码与数据库写入权的 Rust 侧定义取消/替换语义。

## Decision

**设备流槽与 HTTP 网络请求分离，代次在 Rust 单槽锁内所有权唯一。**
`GithubFlowSlot` 保存 `generation`、当前 `flow`、仍在请求设备码的
`pending_start` 以及最近被取消的 `cancelled_generation`。`github_login_start`
一进入就推进代次、立即作废旧 flow 并登记 pending start；设备码返回后必须仍在
同一代次才能绑定，否则返回 `cancelled`/`stale`，不能复活旧流。

**poll 在每次异步边界后复核。** `github_login_poll` 捕获当前 flow 的
generation；token 响应后（请求 `/user` 之前）、`/user` 验证之后、最终写库前
共三处重新检查槽。最终写库前取得槽锁，先 `consume(generation)` 复核并清槽，
再在同一把槽锁内完成三项设置写入。cancel
要么先取得槽锁并令 poll 失败，要么等待本次已完成的提交；旧 poll 不能在新流
存在时清掉新槽。

**取消是后端命令，不是前端假动作。** 新 IPC
`github_login_cancel` 清 flow/pending start、递增代次并返回
`{ cancelled: boolean }`。没有活动流时返回 `false`，前端必须按「授权可能已完成
或已无流」处理，不能显示取消成功。旧 poll 被取消时返回结构化错误
`code=cancelled`，被新 start 替换时返回 `code=stale`。

**前端取消串行化。** `githubLoginCancel` 返回 Promise，调用期间
`githubLoginCancelPending=true`，`githubLoginStart` 与取消按钮均被阻塞，直到
后端 cancel 结算。成功才显示「已停止本机等待」；命令失败显示可见错误、不显示
成功文案。用户的选择优先于卡住的显示，因此失败后清本地 flow/logging，允许关闭
设置并重试；原有 `githubLoginStartPending` / `githubPollPending` 仍在旧 IPC
结算前阻止新 start。

**wire/API/types 同步。** `src/lib/api.ts` 增加 `githubLoginCancel()`；
store 增加 `githubLoginCancelPending` 与 `githubLoginCancel(): Promise<void>`；
组件显示「取消中…」并禁用重复取消。取消只作废本机设备流，**不撤销网页上已经
发生的 GitHub 授权**；设备码仍按 GitHub 自身生命周期过期。

## Alternatives considered

### 只保留前端代次，不加后端 generation

前端代次能丢弃迟到的 IPC 回包，却不能阻止 Rust 在回包前已经写库。IPC 断连、
窗口关闭或多入口并发时，数据库状态尤其不可由 UI 层保证。安全边界必须靠近
凭据写入点。

### 取消只清 `Option<DeviceFlowState>`，不递增 generation

清空槽只能让「取消后旧 poll」看到没有 flow；如果新 start 已经绑定了一个新
`Option`，旧 poll 无法区分自己拿到的是旧设备码还是新设备码，可能误清/误用新
流。generation 让替换有可比较的身份。

### 用独立 AtomicU64 与 `Option` 两把锁

代次与 flow 若分属不同同步原语，start/cancel 的检查与写入会被拆成两个非原子
步骤，仍存在检查后代次变化、随后写入旧槽的窗口。单槽 `Mutex` 把「比较代次 +
清/绑 flow + 最终写库」排序在同一所有权边界内。

### 取消时调用 GitHub 撤销网页授权

GitHub 设备流没有供该客户端调用的撤销端点；网页是否已授权由 GitHub 控制。
客户端能做且必须做的是立即作废本地设备码、代次和写库权，并明确告知用户网页
授权未被撤销。

### 取消失败后假装成功并静默重试

这会让用户把「后端仍可能等待/提交」误认为已停止，也会掩盖失败证据。当前实现
保留可见错误；只有用户主动重试或新 start 成功后，才由新代次替换旧流。

## Consequences

- 在 token 响应门控场景中，先 cancel 或新 start 再放行旧 poll，分别返回
  `cancelled` / `stale`，且不请求 `/user`、不写旧凭据或覆盖新 flow。若取消发生在
  `/user` 已发出之后，不能倒称该请求从未发生；后续守卫保护尚未获得的提交权。
- `github_login_cancel` 的 `cancelled=false` 明确区分「没有可取消的活动流」，
  前端会重新读取登录状态而不是宣称取消成功。
- 后端写库与取消共享同一槽锁；一旦 poll 已取得最终写库权，cancel 需等待本次
  提交结束。锁外无法安全回滚已经提交的数据库写入，这是取消与提交的自然排序。
- 真实 Rust 回归用门控 mock 把旧 poll 停在 token 响应处，分别执行 cancel 与新
  start，再放行旧响应；断言 `cancelled`/`stale`、DB 无旧账户、槽无旧 flow/
  新 flow 未被清除。真实组件回归验证取消调用后端、失败可见、可关闭设置并重试。
