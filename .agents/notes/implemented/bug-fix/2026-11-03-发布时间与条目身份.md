# Agent Note: 发布时间与条目身份

Status: implemented

## Problem

审计 #P1-6 复现了两个互相放大的缺陷：直连解析在源缺 `pubDate/updated` 时把
`Utc::now()` 写进 `published_at`，刷新路径又用 `COALESCE(新值, 旧值)` 覆盖；
同时无稳定 id 的 guid 兜底是 `title + 抓取时间`。结果是无日期条目「永远今天」，
且发布时间每次刷新变化会让条目身份漂移，无 URL 时必然重复入库。

真实库与实时 feed 证据见 `tmp/audit-sync-core/AUDIT-REPORT.md` #3：一个 20 条
条目的 feed 全部无日期，库内发布时间集中在抓取窗口；旧辅助探针还复现了无 URL
条目两次抓取产生两行。

## Decision

**发布时间与首次见到时间分离。** `articles.published_at` 仍是列表排序/显示的
非空时间；新增永久 `first_seen_at` 与 `published_at_source`。

- 源提供日期：`published_at` 用源日期，source=`feed`；`first_seen_at` 为新行
  插入时间。
- 源提供未来日期：仍按既有策略钳制为当前时间，但实际值已不是源日期，source
  必须标 `feed_clamped`，不能伪装成普通 `feed`。钳制标记由解析层显式携带到
  DB，不通过比较时间反推；未来日期不参与身份构造。后续出现真实非钳制日期时，
  `feed_clamped` 可升级为 `feed`；再次收到未来日期不得让已有真实日期降级。
- 源未提供日期：新行 `published_at = first_seen_at`，source=`inferred_fetch`。
  两者只写一次，后续刷新不覆盖。
- 后续源补上真实日期：`inferred_fetch` / `legacy_unknown` / `feed_clamped`
  可升级为 `feed`；已有 `feed` 日期不被推断值、钳制值、抓取时间或后续刷新覆盖。
- 存量行：`first_seen_at` 从 `fetched_at`（历史插入时间，从不更新）回填，空格
  格式归一为 RFC3339；`published_at_source` 一律 `legacy_unknown`。旧库无法
  区分源日期与抓取兜底，禁止猜成 `feed` 或 `inferred_fetch`。
- 旧二进制兼容：v33 的 AFTER INSERT 触发器在 `first_seen_at` 为 NULL/空时，
  依次取 `fetched_at`、`published_at`、当前时间并归一为 RFC3339；source 仍取
  列默认 `legacy_unknown`，不伪造日期证据。

**条目身份只由稳定来源构成。** 直连身份顺序：

1. 真实 feed id/guid；
2. 同 feed 规范化 URL（合成键，哈希规范化 URL）；
3. 有源日期且无 URL 时 `title + 源日期`；
4. 无 URL/date 时 `title + HTML + 正文` 的确定性指纹（MD5）。

合成键带控制字符前缀；抓取时间、当前时间和钳制后的未来时间都不进入 guid。
匹配始终限定同一 `feed_id`；跨 feed 同 URL 不共享身份。既有弱身份只在出现真实
feed id 时升级，弱身份之间不来回改写，避免日期/URL 增补造成二次漂移。

## Boundary

- 无 id/url/date 时，内容指纹明确包含标题、净化后的 HTML 与提取正文；HTML-only
  变化即使提取正文相同也会形成新身份。指纹相同的两条条目会被视为同一条：同
  feed 内标题/HTML/正文都相同的两条真实不同条目无法仅靠 RSS 区分；MD5 的偶然
  碰撞与选择前缀碰撞也会落入同一边界。该 MD5 只用于本地确定性身份，不是抗
  对抗性摘要或安全边界。跨 feed 即使指纹相同也不共享身份，唯一键仍由
  `(feed_id, guid)` 隔离。
- 同一无 URL 条目的正文发生实质变化时指纹变化，会产生新行；这是「没有完美身份」
  的明确代价，不用抓取时间或模糊标题匹配去掩盖。同一份已变化内容再次刷新会
  复用其指纹行；但若源每次刷新都改写正文，行数仍会随不同正文指纹增长，这是
  不可消除的上游行为边界。
- 有源日期但无 URL 的条目以 `title + date` 为身份，正文不在身份内：同标题同
  日期的正文变化会复用同一行并覆盖为新正文；同 feed 内两条真实不同条目若标题
  与日期相同，也会发生声明式碰撞并合并。上游修正日期会形成新身份，撤回日期会
  退回内容指纹身份，二者都可能新增一行。已有 `feed` 日期本身不被刷新回退，但
  旧身份不会因为日期变化被猜测重建。
- 升级前已按旧 `title + 抓取时间` 落库、且无 URL/date 的条目，旧抓取时间不可
  恢复；升级后首次刷新可能新增一行。该历史身份无法在不误并的前提下重写，明确
  保留为迁移边界。

## Alternatives considered

### 继续用发布时间/抓取时间做冲突或身份键？

拒绝。发布时间不是稳定身份：缺日期时它就是抓取时间，每次刷新变化；未来日期
钳制还会引入当前时间。用它做身份会让「刷新」变成「换文章」，并制造重复行。

### 缺日期时保留 NULL，显示层再兜底？

拒绝。现有排序/「今天」/keyset 契约要求 `published_at` 非空；保留 NULL 会让
这些查询退化并再次引入 `COALESCE(published_at, fetched_at)` 的混合语义。分离
`first_seen_at` 与来源标记，既保留非空排序键，又能让 UI 区分推断时间。

### 用标题或 URL 无限制跨源匹配？

拒绝。同 feed 内 URL 可以兜底，跨 feed 同 URL 可能是不同订阅源的不同条目
（摘要/全文/不同编辑版本）；标题更不具备唯一性。身份必须 feed-scoped。

### 把存量 `published_at_source` 猜成 `inferred_fetch` 或 `feed`？

拒绝。旧库没有「源是否提供日期」的证据；按 `published_at == fetched_at` 猜测
也会把真实恰好同秒的源日期误判。统一 `legacy_unknown` 是唯一不伪造历史的做法。

## Consequences

- 无日期条目不再每次刷新变「今天」；排序稳定，无 URL 条目不再必然重复。
- 首次见到时间永久保留，UI 后续可据 `published_at_source` 标「推断时间/首次见到」；
  本次只暴露字段，不改布局。
- 迁移 v33 只增列并回填，旧列全部保留；迁移在单事务内执行，失败（含触发器
  创建失败）整体回滚，`user_version` 不推进。旧二进制在 v33 库按旧列集插入
  时，`first_seen_at` 由触发器回填而非永久 NULL；source 保持 `legacy_unknown`。
- 历史无 id/url/date 条目的一次性重复边界、内容指纹碰撞边界、日期修正边界均已
  在上文和测试中明确，不再假装存在完美身份。
- 验证：`time_identity_e2e` 覆盖无日期/连续刷新/补日期/未来日期钳制来源/
  legacy_unknown/title+date/远程无日期/URL 与 id 顺序/跨 feed 隔离/HTML-only
  指纹与正文变化；`v33_time_identity_migration_tests` 覆盖旧库回填、来源不伪造、
  旧 schema 风格插入的非 NULL 回填、重复升级单触发器与触发器创建失败回滚。
  相关门禁在交付时全量执行。
