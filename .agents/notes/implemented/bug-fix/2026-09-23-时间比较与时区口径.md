# Agent Note: 时间存储、索引排序与本地日期各守其口径

Status: implemented

## Problem

SQLite时间TEXT混用空格与T格式会破坏字节排序；只对今天判定的一侧做localtime转换会错一天。ORDER BY COALESCE(published_at,fetched_at)又不能复用为裸列建立的索引。

## Decision

列表用非空published_at与id建立全序，分页谓词同源，避免在热查询排序键外包函数。这个设计依赖可比较时间基准与一致格式，不能仅凭“都带RFC3339 offset”就认定字典序等于时间序：不同时区offset的RFC3339字符串不具备该性质。当前同步写入把epoch转UTC，直连解析使用feed解析器的UTC日期，新增路径应保持同一基准。

“今天”按用户本地日期比较，published_at与now两侧一致做localtime转换；缓存清理需要比较历史混合格式时用datetime归一，不把冷路径的归一规则套进热列表索引。SQLite限制非确定性日期表达式作索引，不是所有表达式索引都不可建。

前端parseTs把历史空格时间按UTC兼容；游标仍传后端原始时间串，不经前端重格式化。后继[发布时间与身份](2026-11-03-发布时间与条目身份.md)区分feed、feed_clamped、inferred_fetch和legacy_unknown，非空排序值不再冒充有真实源日期。

## Alternatives considered

统一迁移epoch整数能消除格式歧义，但要改全链读写、分页和fixture，当前保留既有TEXT模型。热查询全面julianday/datetime可归一值，却需要与排序表达式一致的索引策略，不能免费沿用裸列索引。

CHECK只保护新写入，也不能替远端解析做格式适配。用UTC定义“今天”虽简单，却改变用户本地日历含义，因此仅存储/排序采用统一基准，日历视图显式转换。

## Consequences

旧4992行样本全部带offset是历史样本事实，不证明未来或所有存量格式都一致。写入绕开UTC规范、手工导入或历史异常值仍需数据证据；本篇不以约定宣称排序永无错乱。

查询计划与正确性须分别验证：索引命中不证明时区正确，样本日期正确也不证明大库计划有效。格式改变时应联查排序、keyset、今天和清理边界。

## Validation

查询/分页回归覆盖游标与计划，时间身份测试覆盖缺失/未来源日期；前端parseTs兼容测试只证明解析，不证明数据库排序。真实库计划与时区样本的测量范围由性能文档记录。
