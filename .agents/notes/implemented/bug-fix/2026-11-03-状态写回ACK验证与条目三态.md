# Agent Note: 状态写回 ACK 验证与条目三态

Status: implemented

## Problem

GReader `edit-tag` 与 Fever `mark=item` 都可能对不存在/已删除的目标返回
成功外观：前者 HTTP 200 + `OK`，后者 HTTP 200 + `auth=1`，但服务端实际没有
改变任何条目。原推送路径把这层 ACK 直接当成用户意图已应用，随后按队列 id
`prune_sync`；远端已删除、错误账号绑定或旧 `remote_id` 因此会永久丢失队列
中的本地读/藏意图，用户也不会再看到可重试的失败。

同一条链路的读侧还有另一种静默回滚：GReader 的 `ItemContent.categories`
与 Fever 的 `is_read/is_saved` 原来都带 `serde(default)`。字段缺失被解析成
空分类或 0，合并逻辑再把它当作明确的“未读/未收藏”，可能覆盖本地已经标读、
收藏的状态。HTTP 200 的成功外观与“缺失字段即 false”的解析共同制造了假成功。

## Decision

2026-11-09 部分继承：以下三态字段、写后读回、未知不判删除、同轮只尝试一次和版本保护继续有效。广播副本的主目标结算被[源内等价组决定](../../proposed/architecture/2026-11-09-源内等价组与持久条目状态.md)取代：每个真实成员独立队项、独立 ACK；新格式不保存 CSV 别名。原选择的原因保留在下方历史段。

**条目状态字段改为缺失 / 明确 false / 明确 true 三态。** `greader::RemoteState`
承载三态；`ItemCategories` 保留字段是否出现。GReader 的显式 `categories: []`
是明确 false，缺失或 null 是 Missing；Fever 的 `is_read/is_saved` 缺失是
Missing，0/1 是明确状态，其它数值按协议错误拒绝。合并路径统一通过
`ItemContent::read_state()` / `starred_state()` 取值：

- Missing 只允许回填正文/封面等内容，不调用读/藏状态写；
- 明确 false/true 仍逐步走既有字段版本、pending 与冲突政策守卫；
- 集合级拉取缺字段继续按[同步集合失败关闭](2026-10-19-同步集合失败关闭.md)
  失败关闭，不把集合未知当成空集。

**写请求成功只进入“待读回确认”，不直接出队。** `exec_push` 在 read/unread
批次和每个 star/unstar 成功后，用同一会话按目标 id 读回：

- GReader：`stream/items/contents` 的逐条目状态（专用验证入口允许响应只含
  存在条目；正文 pull 仍拒绝短响应）；
- Fever：`items&with_ids` 的 `is_read/is_saved`。

只有目标存在且三态字段等于 desired 才进入 `done`，随后才 `prune_sync`。
读回的完整性按「请求 id 是否逐个出现」判定，而不是按返回条数：重复条目或
无关条目凑够数量仍算短响应。当前 GReader/Fever 的这两个读回端点都没有
「目标已删除」的权威信号——200 空数组、短数组、缺少 `items`、非法 JSON、
字段缺失或状态相反，全都只能进入 `retry_wait/verification`，不得升级成
终态 `failed/target_missing`。网络/解析错误由同步报告记录；缺目标时摘要
明确写 `inconclusive`，避免把「没读到」伪装成「服务端确认删除」。

**历史决定（2026-11-09 已取代）：广播聚合只由主目标决定队列结算。** `status.entry_ids[0]` 是当前队列行的
主目标；它确认后即可 `prune_sync`。同文副本（read 广播）缺失或未确认只产生
`partial` 警告：写入 `report.errors`、即时推送同时发 `sync-error`，但不会让
整行永久失败，也不会每轮重发全部副本。其它独立队列行仍各自按自己的主目标
判定；同批中一个目标缺失不会连坐别的行。

**同一 states 轮不重发已尝试项。** 首推会记录 `PushOutcome.attempted` 的
queue id；pull 后补推构建新计划时用 `PushPlan::remove_attempted` 过滤。这样
首推已发送但读回未确认的行（尤其 Fever toggle）不会在同一轮的第二次 push
中再发一次，留给下一轮重新收敛。

**错误落库复用 v32 队列状态，不做迁移。** 读回未确认/不一致写
`status='retry_wait'`、`last_error_class='verification'`。队列行与本地
`is_read/is_starred` 都保留，`sync report.errors`、`sync-queue-changed` 的
`retry_wait` 与 `last_error` 负责让用户看到未确认，不再只写 `log::warn!`
或 `.ok()`。`mark_queue_target_missing` / `retry_target_missing` 保留为未来
“可证明目标已删除的权威证据”端点的入口；当前空/短响应不会写入
`failed/target_missing`，因此自动/手动同步都不会因一次缺条就把用户意图
永久搁置。

当前协议身份使用 `remote_id` / 同 feed 已确认绑定；没有引入 `published_at` 仲裁。后继决定已取消跨源已读广播，源内等价组的每个成员按自己的字段版本和待确认意图保护。

## Alternatives considered

### 继续相信 200/OK，只在 UI 提示“可能未生效”

这不能阻止 `prune_sync` 删除最后的本地意图；目标缺失后用户没有队列行可重试，
再准确的提示也无法恢复。确认必须发生在出队之前。

### ACK 后把队列行留在原地，等下一轮 pull 自然读回

下一轮 pull 可能很久才发生，且 pull 的集合窗口/分页失败会让确认不可判定；
本轮手动同步仍可能报告成功。写后立即做一次有界读回，才能把成功/失败落在
当前同步报告和当前队项上。读回失败仍保留到下一轮，不伪造成功。

### 读回失败时重新发送同一写请求

Fever 旧版 `saved/unsaved` 是 toggle，重发可能把用户刚设置的状态翻反；即使
GReader 的 tag 是绝对语义，网络未知时重发也没有新增确认证据。保留
`retry_wait`，下一轮按协议能力重新收敛。

### 把缺失 `categories` / `is_read` / `is_saved` 当作 false

这把“服务端没给字段”与“服务端明确说未读/未收藏”混为一谈。服务端版本差异、
代理截断或局部响应都会静默回滚本地状态；三态是唯一能区分未知与 false 的
模型。

### 直接新增 `ack_pending` 列/状态

当前 v32 的 `retry_wait` 已能表达“本轮未确认、保留待重试”，`failed` 能表达
`target_missing` 的终态；新增状态会要求第二次迁移并扩大前端状态矩阵。
本任务的确认窗口在 `exec_push` 内完成，复用现有状态足够，也回滚安全。

## Consequences

- 收益：未知 ID 的 200/OK、`auth=1` 不再清队；空/短响应保留为可见
  `retry_wait/verification`，正常目标在确认后才出队。缺字段的条目只更新
  内容，不再回滚本地读/藏。
- 当前收益：每个成员有自己的确认结果；批量请求中一个目标未确认只保留该目标的队项，不影响其他身份。历史广播采用主目标结算是为了避免一个无独立身份的副本拖住主行；保留每个实体后，这个折中不再适用。
- 代价：每次成功写多一次只读请求；读回端点不可用或持续返回未知字段时，
  队项会停在 `retry_wait`，需要服务端/网络恢复后再次同步。当前协议无法
  证明目标已删除，所以不会自动落入永久终态。
- 版本边界：当前假设 GReader 服务端支持 `stream/items/contents`、Fever
  服务端支持 `items&with_ids`。未对具体 Miniflux/FreshRSS 部署版本做真实
  服务端实测；夹具覆盖固定源码形态。读回不支持时按验证失败保留，不冒充成功。
- 格式边界：原决定沿用 v32 队列；2026-11-09 当前独立数据格式保留其状态语义，旧库不迁移。`target_missing` 仍是保留入口，当前读回路径不产生该分类。

## Testing

以下为可执行覆盖入口；2026-11-03 的历史结论不外推到 2026-11-09 新格式，当前执行证据集中在本轮验收入口。

- `src-tauri/src/greader.rs`：缺 `categories`=Missing、显式 `[]`=False、
  read/starred tag=True。
- `src-tauri/src/fever.rs`：缺 `is_read/is_saved`=Missing、0/1 明确、
  非法数值协议错误；`push_star_state` 缺字段不盲发。
- `src-tauri/src/sync/entries.rs`：本地 read=true/star=true 遇缺字段保持
  (1,1) 且正文仍可回填；显式 `[]` 与 Fever Missing override 分别验证。
- `src-tauri/tests/sync_ack_verification_e2e.rs`：GReader 正常读回才出队、
  未知 target 的 200/OK 进入 `retry_wait/verification`、读回 500 进入
  `retry_wait/verification`、短响应只保留缺失目标、`items:[]`/缺 `items`/
  非法 body 均为 verification 失败、重复/无关条目不能凑完整性、另一源缺失不影响当前精确目标、star 也需读回。源内组部分 ACK 与旧 pull 的保护由 `refactor_acceptance_e2e` 承接。
- `src-tauri/tests/fever_compat_e2e.rs`：Fever 正常读回、未知 target、
  `with_ids` 读回失败、短响应只保留缺失行、`push_star_state` 缺 `is_saved`
  不发送 mark，以及同一 states 轮只发送一次 `mark=item`。
- star读回为空、缺categories、状态相反，以及重复条目不能凑足ID、同轮pull新绑定后补推均有判别用例。历史链接失败未取得变异red/green的记录不能提升为变异验证通过；当前执行结果由统一验收入口维护。

本篇的逐条目读回不是服务端原子条件写；Fever探测到mark之间仍有并发窗口。当前部署版本与读取端点支持度见兼容矩阵，不从HTTP成功或mock通过推导真实账号确认。
