# Agent Note: 订阅写回接线与防复活意图

Status: implemented

## Problem

底层有push/pull和编辑API，不代表用户操作已经走通。最初删除、改名、移动只改本地，新增丢分类；下一轮pull会重建已删源或旧分类。依赖远端先成功又会让离线用户无法操作。

## Decision

本地变更立即生效，生产命令把本地变更、墓碑和类型化订阅outbox放进同一事务；执行器在网络边界按账号和代际重试。新增/OPML以desired_folder保存目标label，改名/移动表达a=新label与r=旧label。分类改名逐成员表达；分类删除在级联前快照成员，每个远端成员各有退订意图。空分类没有成员可写回，只保留本地语义。

墓碑表达“本地有意不存在”，outbox表达“远端仍需完成动作”，两者不能互当确认。退订响应被执行器接受后也不直接清墓碑；pull以完整远端列表确认该URL不再存在才回收。退订400/404的兼容上限与其他协议细节由[订阅outbox决定](../architecture/2026-10-14-订阅写回outbox执行器.md)及兼容矩阵维护，不能写成仅2xx才确认。

在途创建撞上本地删除时仍保存未知remote_id的退补意图。当前目标恢复以远端列表和持久resolved_remote_id收敛，不能继续沿用早期“未知id先quick_add找id”的假设；非幂等服务会因此制造额外订阅。旧folder移除基准需随链保存，快速重加继承基准，防止旧label残留。

显式添加和OPML重加会解除相同URL的新/legacy墓碑；分类墓碑按账号隔离并失败关闭。legacy add_feed队列的folder_id属于兼容消费，新生产者走类型化outbox。状态队列的无身份项另按[生命周期](../architecture/2026-11-03-同步队列生命周期与本地意图.md)分类，过期保留意图而非物理删除。

## Alternatives considered

远端成功后再允许本地删除会阻塞离线操作。没有墓碑而只看“远端有、本地无”无法区分未拉取与用户主动删除。队列只存id、推时再查分类会丢掉那次操作的目标，尤其本地行已删除时无从重建。

早期锁外best-effort接线能避免阻塞DB，却没有重启后的重试；后续持久outbox因此取代命令路径的一次性尝试。分类级端点缺少统一兼容依据，采用逐成员表达并承认空分类限制。

## Consequences

本地成功不等于远端完成，Fever墓碑也不会变成协议不具备的退订能力。网络长期不可用时意图和墓碑保留是恢复条件；旧算法墓碑可能保守多拦，见URL规范化决定。

2026-11-06配置同步“镜像删除→恢复”仍可留下feed墓碑；添加/OPML已清墓碑不能推出所有恢复入口都正确。订阅确认失败可见性也有未关闭反例，见[同步正确性](../../../../docs/roadmap.md#sync-correctness)和[导入与备份](../../../../docs/roadmap.md#import-and-backup)。

## Validation

sync_gap_repro、opt009_phaseb和订阅outbox集成夹具覆盖生产命令到队列/请求/DB。测试应以真实目标和最终意图验证，不能让mock预先写成期望状态，使守卫有无都通过。具体部署行为仍受兼容矩阵的版本边界限制。
