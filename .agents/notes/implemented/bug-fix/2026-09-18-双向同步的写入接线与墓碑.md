# Agent Note: 双向同步的写入接线与墓碑

Status: implemented

## Problem

同步的底层管线一直都在：队列、push/pull 两阶段、绑定回填、pending 保护都实现了。但用户真实报告「订阅操作与文章状态变更没回传到同步后端」——机制存在，端到端不生效。逐个定位后发现缺口都在**接线**层：既有能力没有调用方，或调用条件恰好过滤掉了真实场景。

四个具体缺口：

1. **删除订阅不回传，且会被 pull 复活**。`delete_feed` 只删本地，注释明说「本地删除 ≠ 强删远端」；pull 按 URL 匹配不到已删的 feed 就重建它。GReader 的退订能力已实现但全仓零调用。
2. **改名/移动目录不回传**。写路径只落本地，靠 pull 对账收敛——但 pull 的回填条件是「本地标题等于 URL 时」才生效，所以双端永久分歧。
3. **push 丢弃分类**：入队时没带 `folder_id`，远端因此建不出正确目录。
4. **目录改名/删除后被 pull 按旧 label 复活**成重复空目录。

以及一个队列卫生问题：无绑定的队项永久滞留（`plan_push` 跳过但保留 + pending 保护挡住清理）。

## Decision

**删除写入墓碑，墓碑是 pull 防复活的唯一防线。** 删除订阅时若已绑定 `remote_id` 且已配置同步，先尝试远端退订；Fever 没有退订端点，则写删除墓碑（`feed_url` + 时间戳），`pull_feeds` 建 feed 前先查墓碑并跳过。墓碑在**远端订阅列表确认不再包含该 URL** 后清除。目录的改名/删除共用同一机制。

**墓碑清除的判据必须是「远端列表实际已不含该 URL」，不能是「退订请求返回 2xx」。** GReader 兼容后端在 token 失效、权限不足、订阅不存在等情况下都可能返回 2xx + 错误体。以 2xx 为判据会误清墓碑，于是「删了又被拉回来」。这条是审查中发现的残留缺陷，也是最容易在重构时改错的一处。

**加回订阅必须清墓碑。** `add_feed` 与 `opml_import` 插入后调 `remove_feed_tombstone`，否则「删了又加」的同一个 URL 会被 pull 永久跳过，而队列项在 30 天后被物理删除，两端状态永久分裂。

**改名/移动目录走锁外 best-effort 推送。** `edit_subscription` 已实现但从未被调用，接线后：若已配置同步且 `remote_id` 非空，在锁外推送新标题与目标分类 label；失败只记 `report.errors` 与日志，不影响本地生效。Fever 降级跳过。**本地写入永远是权威**——远端推送是尽力而为的对账动作，不是写操作的前提。

**push 带上分类。** 入队时带 `folder_id`，远端才能把订阅放进正确目录。

**队列卫生**：无绑定条目按 TTL 老化清理（`stale_unbound_queue_items_are_pruned`），吞掉的读取错误改为记录日志而不是静默丢弃。

## Consequences

**收益**：删除、改名、移动目录在双端收敛；墓碑机制同时解决了订阅与目录两类「pull 复活」；离线或后端不支持某些操作时，本地操作仍然立刻生效。

**代价与已知上限**：

- 墓碑需要清理时机，而清理判据依赖远端列表——在网络长期不可用时墓碑会一直留着（这是正确行为，但意味着「删除后重建同名订阅」在远端恢复前不会被同步）。
- best-effort 推送失败只记报告，不重试。也就是说改名/移动目录在推送失败后不会自动收敛，只能等下一次 pull 对账或用户再次操作。
- 墓碑表没有独立的运维入口；如果墓碑被误写（例如同 URL 不同源），用户可见的表现是「新订阅加了但同步不到」，排查需要查表。重访信号是这类支持请求出现。
- Fever 缺退订能力这件事是协议与服务端层面的，墓碑只是补偿手段，不是等价方案。

## Alternatives considered

### Why not 在删除时强制远端先成功再删本地？

那样离线或凭据失效时用户就删不掉订阅。用户的删除意图是明确的，不该被网络状态阻塞。墓碑机制让本地立刻删、远端尽力推，代价是需要墓碑表。

### Why not 用「远端多次确认」代替墓碑？

「发现远端已不含该 URL」本身就需要一次拉取才能知道，而在拉取完成之前 pull 已经在建 feed 了。墓碑把「此处有过一次删除」这个本地事实持久化，不需要额外往返。

### Why not 让 pull 用「本地不存在则重建」以外的策略？

pull 的职责是把远端的订阅列表拉成本地状态，因此「远端有、本地没有」时的默认动作必然是新建。在这种语义下，唯一能表达「本地有意没有」的载体就是墓碑——这也解释了为什么墓碑是必需品而不是优化。

### Why not 把分类信息在 push 时从本地查出来？

入队时查比推送时查更可靠：推送发生在稍后的时点，此时用户可能已经改了分类，而队项表达的是「那次操作」。入队时带上目标分类，语义上是「这次操作想让它变成什么」。

## Testing

- `src-tauri/tests/sync_gap_repro_e2e.rs` 是缺口复现的固化点：缺口存在时以 `#[ignore]` 的复现测试记录，修完后去掉 ignore 并把断言**反转为期望行为**。当前该文件无 `#[ignore]`，20+ 个用例全部默认运行（含 `deleted_feed_revives_on_pull` 的反转版、`folder_*` 系列、`stale_unbound_queue_items_are_pruned`）。
- 隐藏缺陷的风险点：mock 的 `edit-tag` 在 push 成功时会把远端翻成 `read=true`，导致某些 pending 守卫的断言在「有守卫」和「没守卫」两种情况下都通过（断言恒真）。补强这类用例时需要确认变异能让断言变红。
