# Agent Note: 同步集合失败关闭

Status: implemented

## Problem

同步协议的权威集合字段此前在 GReader/Fever 解析结构里带 `serde(default)`：
GReader 的 `subscriptions`、`itemRefs`、`items` 缺失会变成空数组，Fever 的
`feeds`、`groups`、`feeds_groups` 缺失也会变成空数组。HTTP 200 `{}` 因此被
误解释为“服务端明确返回空集”：订阅对账会删除本地 `origin='remote'` 源，读藏
对账会清空状态，历史回溯还会把缺失当成取尽并写完成态。

另有两个会把“没有数据”误当“已经同步”的路径：

- `sync_light` 只跑 states，不跑 feeds；数据库尚没有任何远端 feed 绑定时，
  GReader 仍会请求条目并推进 `last_sync_ts`，Fever 仍会请求历史窗口并推进
  `last_sync_entry_id` 或写 `fever_history_state=complete`。
- Fever 的 map 构建晚于 history Pending 初始化；即使 map 失败或没有可绑定源，
  也可能先改写历史状态。

返工审查又发现四个同族边界：

- 仅以 `feed_mf_to_id` 非空作为整体守卫仍不够：一个 feed 已绑定、另一个
  `origin='remote'` 源缺 `remote_id` 时，条目窗口会继续并推进游标。
- 零绑定直接跳过 pull 会让空账号的自动同步永远无法发现服务端后来新增的首个
  订阅；若仍由 scheduler 用 `last_sync_ts=0` 判断到期，还会每个 TICK 重复。
- 把主 item id/正文失败扩大成跳过 read/starred 对账是过度守卫；权威集合是
  独立请求，成功时应独立落地。
- GReader 的 HTTP 200 JSON 解码/schema 错误经 `Response::json()` 被包装成
  `network`，不利于区分传输故障与协议故障。
- read/starred 仍用 `join!(Ok, Ok)` 共同门控，单侧失败会连带跳过另一侧；
  订阅发现仍只覆盖“零绑定”，已有绑定时无法发现远端新增 feed；订阅绑定写
  错误还被 `let _` 吞掉。非法 `itemRefs.id` 与 continuation 也未统一为
  `protocol`。

## Decision

1. GReader 权威集合字段改为反序列化必填（`subscriptions`/`itemRefs`/`items`，
   2026-11-01 补口：`tag/list` 的 `tags` 同口径必填，缺字段/显式 null 均为
   协议错误；`stream/items/contents` 非空普通拉取请求必须逐个覆盖全部唯一请求 ID；重复或无关条目不能凑数，
   缺条按 `protocol` 拒绝，不当作权威空集）；显式 `[]` 仍成功，HTTP 200 的 JSON
   解码/schema 错误统一映射为 `protocol`。非法 `itemRefs.id`/continuation
   在客户端即按 protocol 拒绝并保留游标。主 item id/正文失败仍保留
   `last_sync_ts`；读/藏按字段独立 fetch/apply：成功侧照常对账，
   失败侧单独记错，不再用 `join!(Ok, Ok)` 共同门控。
2. Fever 信封仍允许认证/`mark` 等 action 不带订阅字段，但消费方按 action
   检查存在性：`feeds` action 要求 `feeds` + `feeds_groups`，用于映射分类的
   `groups` action 要求 `groups` + `feeds_groups`。任一缺失都在本地写路径前
   以 `protocol` 错误中止；`[]`/空 `unread_item_ids`/`saved_item_ids` 保持
   原有权威空集语义。
3. 最初由`sync_light`承接的只读订阅发现不再依赖“零绑定”；该旧入口已在
   2026-11-10三通道拆分后移除。当前发现入口为`sync_subscription_discovery`，
   `states_phase(false)`的完整内容轮也按同一节流判断是否发现，独立
   `sync_states_now`只读取状态。只读发现无论当前是否已有绑定都可调用
   `pull_feeds`，自身不执行`push_feeds`/subscription outbox，不绕过首连确认；
   完整轮的其他推送阶段仍由原编排负责。发现键按
   `sync_zero_binding_discovery_at:<account_key>` 隔离账号，发起请求前写尝试
   时间（失败也占窗口），受通用 IPC 保护并在换号/断开时清理。条目页出现未知
   feed且确实缺少可接受的精确身份落点时，设置内部`binding_incomplete`，
   本轮最多再`pull_feeds`并重试一次条目pull。持久准入拒绝另记
   `pull_admission_blocked`，不借该重试绕过发现节流。发现时间绝不写条目游标。
   scheduler 在“仅发现到期、正常刷新未到期”时走
   `sync_subscription_discovery`：只读订阅发现；若绑定数增长才补拉一次条目，
   避免把发现节流误当成完整刷新频率。
4. 当前Content与State入口共用`pull_admitted`：在构建各自`sync_match_maps`
   和发起条目/权威HTTP前，先核账号代际、持久绑定不完整标记及活跃的
   `origin='remote' AND remote_id IS NULL`源。标记存在或仍有这类未绑定源时，
   显式阻断且不写游标/checkpoint；没有任何有效远端feed绑定时良性跳过。
   State提交边界再次复核准入。条目页若出现未知remote feed且没有可接受的
   精确身份落点，也记录失败并保留窗口：GReader 保留既有有限兼容合并但
   `last_sync_ts` 不前移；Fever 不提交该页游标/checkpoint，并恢复同步前的
   `last_sync_entry_id`与history snapshot。精确eid已匹配且本地feed未知或相容
   时不误触发新源发现；提交仍复核当前source token及feed冲突，退订源不复活。
5. Fever 的 map 构建前移到 history Pending 初始化之前。map 失败时保留同步前
   的 history 状态，避免“先写 Pending、再发现没有可信映射”。失败后的
   cursor + history 恢复改为单事务，并由全局 `PULL_LOCK` 与其它条目 pull
   串行；第二写失败时第一写也随事务回滚。
6. Fever 测试夹具把 `feeds`/`groups` 两侧的 `feeds_groups` 省略开关分开；
   显式三空数组用例预置既有远端源/文章，证明合法空集仍执行权威删除。
7. 订阅发现中的 `set_feed_remote_id` 错误不再 `let _`：既有源与新插入源都
   显式写入 `report.errors`，且失败分支不增加成功计数。
8. 绑定失败还需要跨 feeds/states 分步命令持久化：
   `sync_binding_incomplete:<account_key>` 在任何绑定/新源插入失败时写入，
   完整成功绑定后清除。Content的`pull_entries_*`和State的`pull_states_*`
   均通过共享准入在首个HTTP前检查该标记，存在即不请求条目或权威集合，
   不推进GReader `last_sync_ts`或Fever since/history；
   换号/断开清理，通用设置 IPC 保护。
   实现用显式“订阅导入已完整遍历”状态收口：目录创建/查找失败、分类或 feed
   墓碑读取未知、远端 URL 本地匹配失败、已有 `origin='local'` 源绑定失败、
   新源插入失败，以及任何 `break/continue` 未完成路径都保持 incomplete；
   只有遍历完整且每个远端订阅匹配/绑定成功才 clear。不得再靠
   `unbound_remote_feeds` 猜测本轮是否成功。
   唯一例外：`feed_url_tombstoned == Ok(true)` 的 known tombstone continue 是
   用户已在本机删除该订阅的预期决策，不要求本地绑定，也不标记 incomplete。
9. GReader 主 itemRefs 与 read/starred 权威集合都记录已见 continuation，并在
   重复、未前进或超过 200 页时以 protocol 失败关闭；主列表/权威集合的该失败
   均保留条目游标。发现时间戳若位于未来（时钟回拨）按首次到期处理。
10. 新远端 feed 的 insert + remote_id bind 在同一事务内完成，绑定失败回滚
    新行，不产生 `origin='remote' AND remote_id IS NULL` 孤儿。历史上已存在的
    这类孤儿，仅在当前远端 URL 集合不再包含它时删除；`origin='local'` 永不
    由该清理触碰。空 itemRefs + 合法 continuation 同样视为 protocol 结构错误
    （主列表与 read/starred 一致）。

2026-11-03 补口：条目级状态字段（GReader `ItemContent.categories`、
Fever `is_read/is_saved`）也改为三态解析。字段缺失只表示未知，合并时只允许
更新内容、不得改写本地读/藏；集合级字段仍按本篇的失败关闭规则处理。写回
ACK 后还必须按目标 id 读回确认：这里的“确认”不是把 200 空/短响应当空集，
而是要求每个请求 id 逐个出现且状态字段明确等于目标态；空数组、短数组、
缺 `items`、非法 body 都归入 `verification/inconclusive`。

**历史结算选择（2026-11-03，2026-11-09已取代）：** 当时GReader读广播只以主目标确认结算该队列行，缺失副本记partial警告，目的是避免一个没有独立队项的广播副本长期拖住主行、导致整批重复发送。当时的原因与测试边界保留在
[状态写回 ACK 验证与条目三态](2026-11-03-状态写回ACK验证与条目三态.md)。
当前已取消跨源读广播；源内等价组的每个真实成员都有自己的队项与精确远端目标，必须逐目标读回确认，只出队该已确认成员。一个成员缺失、状态未知或不一致时保留它的意图，其他成员的ACK不替它结算；原三态与“未知不判删除”的协议边界继续有效。

该决定与 [Fever 身份与历史回溯](../architecture/2026-10-08-Fever身份与历史回溯.md)
及 [同步冲突政策单点](../architecture/2026-10-07-同步冲突政策单点.md) 的
“失败 ≠ 空集合、权威快照不得被未知状态伪造”一致；状态写事务与对账守卫的
既有边界见 [状态写入事务化与对账守卫](2026-09-18-状态写入事务化与对账守卫.md)。

当前 GR 读对账使用完整 unread 的差分，而非下载历史 read 全集；发现与回补的后继边界见[GR 权威集合回补](2026-11-05-GR权威集合回补与过期意图恢复.md)。本篇保留“字段独立失败”的原则，不把早期 read 集合请求写成当前实现。

2026-11-10三通道后继：`sync_light`旧内部入口已移除，完整内容轮由`states_phase(false)`承接，独立`sync_states_now`只取状态。两入口共用`pull_admitted`，持续绑定标记、未绑定远端源或墓碑未知仍在首个条目/权威HTTP之前阻断，State每个提交边界复核。完整轮复用前置集合用于Content发现；同轮失败字段不在Content和后置State重复请求，成功字段在后置State重新读取，独立State不借旧快照。Fever一侧集合失败保留已绑定flags；正文页也不能代替失败的State修改它们，恢复轮完整集合再收敛。原“主列表失败不连坐成功State字段”继续适用于来源已证明的绑定；裸ID须先由真实Content origin建立凭据。详见[运行生命周期](../architecture/2026-11-05-同步运行生命周期与诊断.md)。

## Alternatives considered

### 缺字段继续当空集合并只在 report 里记一条日志

这仍会先执行删除/清状态/完成态写入，日志无法撤销静默数据损失。协议字段
缺失与显式空数组必须区分：前者是未知，后者是权威空集。

### 把 GReader 主列表/正文失败扩大成跳过 read/starred 对账

三者是独立请求/独立权威集合。主列表或正文失败只应保留条目游标；read/starred
自身成功时仍应落地。只有对应权威集合请求失败，才按“失败 ≠ 空集合”跳过该
字段对账。

反过来，也不能让 read 单侧失败吞掉 star 或反之；两字段必须分别 fetch、
分别 apply，才同时满足“失败 ≠ 空集合”和字段独立性。

### 零绑定时仍拉取条目，只保证游标不推进

这会重复消费历史窗口、发出无意义的 items/权威集合请求，Fever 还可能初始化
或完成 history。没有可归属 feed 时，保守且一致的边界是整段条目 pull 不开始。
但“不拉条目”不能等于“永不发现订阅”：后台需要在独立节流下只读拉订阅并建立
绑定，随后同轮进入正常 pull。

### 零绑定时每 TICK 都重新发现，或把发现时间写进 `last_sync_ts`

`last_sync_ts` 是条目时间游标，混入订阅发现会污染增量窗口；每 TICK 重复还会
造成认证/订阅请求风暴。独立时间戳 + 5 分钟节流既保证最终发现，又不改变条目
语义。

### 只检查整体 feed map 是否为空

一绑定一未绑定时整体 map 非空，空映射守卫完全失效；未绑定源的条目会被跳过，
但游标仍前移，之后无法自动补回。必须检查每个 remote 源及条目 origin feed 的
绑定完整性。

### 只在零绑定时发现订阅

已有绑定不代表远端订阅集合没有新增。发现必须独立于 `feed_mf_to_id` 是否为空，
但用账号级时间键限制为每窗口最多一次；否则空账号会永远发现不到首个订阅，
已有账号也永远发现不到后续新增 feed。

### 用两次独立写恢复 Fever cursor/history

第二次写失败会留下 cursor 已回退、history 未回退的半恢复现场；并发 pull 还
可能覆盖更新进度。恢复收进单事务，并以 `PULL_LOCK` 串行整个条目 pull。

### 只在当前 states 轮内记住绑定失败

`syncPhase('feeds')` 与 `syncPhase('states')` 是独立命令，进程内/单轮 report
无法跨命令阻断后续条目窗口。账号级持久标记把“绑定未完成”变成 feeds 与
states 共用的门闩，直到一次完整成功的订阅发现清除它。

### 只校验 continuation 是否为数字

合法但重复的数字仍可无限分页。必须保存已见集合、要求严格前进并设置页数上限；
否则客户端会在“c=0 + 非空 itemRefs”一类服务端缺陷上无限请求。

### 先初始化 Fever Pending 再构建 map

Pending 是“本轮历史已经开始”的状态；在确认 map 可读且存在远端 feed 绑定前
写入它，会把失败轮次伪装成已进入历史阶段。先构建 map，失败或零绑定都保留
同步前状态，下一次同步可无歧义地重试。

## Consequences

- 收益：HTTP 200 的缺字段、非法集合字段、非法 ID/continuation 和未完成绑定
  都不再被伪装成空集或成功；GReader/Fever 的条目窗口、读藏状态和 Fever
  历史态在失败时保持可重试。
- 代价：订阅发现多了按账号隔离的 5 分钟节流；绑定不完整时会暂时停止条目
  pull，必须等下一次完整订阅导入或用户修复远端订阅。这个停顿是用短暂同步
  延迟换取不把游标推过未知窗口。
- 验证：GReader/Fever 严格 HTTP 夹具（含 tag/list 缺 `tags`、正文短响应
  两个 2026-11-01 补口夹具）、分步 feeds/states、账号切换、空集、
  绑定失败孤儿清理、continuation 循环和 Fever 恢复第二写失败均有反例。
  这些夹具验证协议结构与本地提交，不代替真实部署验证。
- 已知边界：本篇所述协议结构回归使用HTTP夹具，不构成当前版本真实Miniflux/FreshRSS账号验证；scheduler的长时间wall-clock
  运行只由节流纯函数、scheduler 用例和 `sync_subscription_discovery` E2E 覆盖。
