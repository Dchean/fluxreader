# Agent Note: 封面补全的候选窗口饥饿

Status: implemented

## Problem

封面补全（为没有封面的文章抓取页图）在真实库上几乎不产出：52 条候选中 32 条**从未被尝试过**。

根因是两个机制的组合：

1. **负缓存先记后请求**：候选被选中的瞬间就记入「已尝试」，然后才发请求；
2. **候选窗口不推进**：每次补全都从头取同一批候选（按时间倒序的前 N 条）。

于是最新 N 条整批失败时（它们的页面结构恰好抓不到图），后续候选**永远进不了窗口**——它们在「已尝试」集合里不存在，但也没有机会被选中。这不是「补全效果不好」，是补全机制被饿死。

同类问题还有：失效封面没有纠正通道（图床改了文件名或删了图，本地记录的 URL 永远 404）、封面 URL 没有 `onError` 回写。

## Decision

**负缓存只在一次尝试结束后记录。** 请求失败也记，但记的时机是「结果已知」而不是「即将请求」——这样中途崩溃或超时的候选下次仍有机会。

**候选窗口按 `(limit, offset)` 推进**，每次补全处理窗口内未尝试过的候选，窗口随处理进度前移。这样最新 N 条全失败也不会挡住后面的候选。

**失效封面有专门的纠正通道**：前端在封面加载失败时调 `report_broken_cover(article_id, url)` 上报（幂等，见[封面代理与失败占位](../feature/2026-10-07-封面代理与失败占位.md)），后端据此清空该文章的封面字段，让它重新进入候选集。这条通道把「死链」从一次性问题变成可自愈的问题。

**Miniflux 源的文章一度不参与封面补全**（后端只取 `source='direct'` 的行），当时
的理由是「同步来源的文章封面由服务端决定，客户端不该用自己的抓取结果覆盖远端
状态」。**该排除已由 [封面补全的覆盖面与预算边界](../feature/2026-10-16-封面补全覆盖面与预算边界.md)
（OPT-017D，2026-10-16）移除**：那个兜底只覆盖正文里有图的服务端文章，正文
无图的服务端文章此前永久无封面；且「本地补的封面会被同步覆盖回空」在当前代码
不成立（两处封面写入都不会把本地封面清成空：回填路径 `COALESCE(旧值, 新值)`
严格只填空，内容刷新 `COALESCE(新值, 旧值)` 只在远端给出非空新图时覆盖）。
本节保留原决策的历史记录。

## Consequences

**收益**：补全窗口会推进，没有候选被永久饿死；死链封面能自愈；负缓存与请求的顺序不再决定候选的命运。

**代价与已知上限**：

- `first_image` 提取仍无尺寸与角色启发式，会把头像、emoji、favicon 当成封面（真实库 481 篇）。它不是本 Note 解决的问题，见 [docs/roadmap.md](../../../../docs/roadmap.md)。
- 补全窗口推进意味着失败候选会被反复重试（每次经过窗口时），因此需要负缓存持续生效，否则会对同一批失败页面反复请求。两者的配合是本方案成立的前提。
- 封面字段被清空后，文章会重新进入候选集，若页面确实抓不到图，会形成一个「清空 → 重试 → 再失败」的循环。抑制它依靠负缓存的时间窗，而不是永久排除——永久排除会让页面后来补了图也无法被识别。该循环只对 `source='direct'` 成立：失效上报通道不清服务端来源的封面（保守边界，见新 Note）。
- 进程内负缓存当时无上限、循环也不可终止；两者已在 OPT-017D 收口（`CoverAttemptCache` 上限逐出、`ShutdownToken` 退出终止）。

## Alternatives considered

### Why not 在候选选择时就标记已尝试？

那正是饿死的成因：标记发生在请求之前，而失败率高的头部候选会一次性占满标记集合，后续候选永远排不上。改为「尝试结束后标记」后，即使请求失败也能记录，不必靠预标记。

### Why not 一次把所有候选都试一遍？

对 5000 篇文章意味着 5000 个页面请求，对目标站点不友好，也拖慢本地资源。窗口 + 推进的语义是「每次处理一批，批次前移」，长期收敛且速率可控。

### Why not 让 Miniflux 来源的文章也参与补全？

**（2026-10-16 复核：此问题已不再成立，排除已被 [封面补全的覆盖面与预算边界](../feature/2026-10-16-封面补全覆盖面与预算边界.md) 移除。）** 原始回答是：它们的封面来自服务端，客户端补全会造成「本地有封面、远端没有」的分歧，而下次同步可能又把本地封面覆盖回空。复核发现两点：「服务端已有封面」只对正文有图成立（正文无图的服务端文章没有任何封面），且「覆盖回空」在当前代码不成立（两处封面写入都不会把本地封面清成空——回填路径严格只填空，内容刷新只在远端给出非空新图时覆盖，R1-P2-1 修正）——分歧与覆盖回空都不存在，排除反而制造了永久缺口。候选现按「无封面 + 有 URL」统一判据，并按每轮批次/并发/超时/失败缓存约束请求量。

### Why not 用页面元数据的启发式直接判断封面质量？

启发式（尺寸阈值、排除小图、排除方形小图）能提升准确率，但需要下载图片本身（多一轮请求）或依赖页面里的尺寸标注（不可靠）。当前先做「抓不到就上报」这条正确性链路，质量启发式留作后续。
