# Agent Note: 封面候选遍历不能停在失败前缀

Status: implemented

## Problem

历史真实库52条候选中32条未尝试，原因是每轮固定取最新前缀，而失败前缀仍无图、继续占据候选窗口。预先标记已尝试也把“选中”与“请求已经完成”混为一谈。

## Decision

按已扫描行数推进候选窗口，一次尝试结束才加入失败/无图缓存。HTTP失败属于已知结果可缓存，DB写失败和退出取消不算完成。当前跨轮游标、有界负缓存、请求预算及退出信号由[封面补全覆盖面](../feature/2026-10-16-封面补全覆盖面与预算边界.md)维护，取代本篇早期无界进程缓存。

前端失效上报按article_id与当前URL幂等；后端仅清direct来源且URL仍匹配的封面，使它重新成为无图候选。服务端来源已允许后台补图，但坏封面仍不由该通道清空，这两条边界不能混同。

## Alternatives considered

一次请求所有历史候选会放大网络与内存开销；只取固定头部则无法穿过持续失败项。窗口推进与失败缓存各解决不同问题，必须同时存在。预先缓存选中项不能证明请求已经执行或结果已落库。

早期排除服务端来源是担心远端会清空本地补图；复核刷新只用非空新图覆盖、回填优先旧值后，后继决定撤销了排除。封面质量启发式另需页面/图片信息，本决定只解决机会和恢复通路。

## Consequences

固定候选集可随扫描轮转获得机会；这不是持续变动集合下无条件公平性的数学保证。失败缓存当前按容量逐出，不是固定TTL；重启或逐出后可再次尝试。封面为空不意味着页面一定有可用图，头像/emoji误选仍是质量边界。

## Validation

cover_backfill_e2e覆盖失败前缀后的候选、缓存逐出、同URL分组、DB失败和退出。测试结果仅在给定候选与调度条件成立，不能用“有推进变量”代替请求日志证明候选实际被尝试。
