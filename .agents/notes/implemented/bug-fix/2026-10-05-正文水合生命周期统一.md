# Agent Note: 正文水合生命周期统一

Status: implemented

## Problem

用户报告：「社交布局下正文经常一直加载，切换一下布局又能秒加载」。审计给出了完整的因果链：

1. 列表刷新产生了新快照；
2. 快照替换时清空了 `hydratedIds`；
3. 组件按 id 保持身份（React key 不变，实例不重建）；
4. 水合 effect 的依赖只有 `[id]` —— id 没变，effect 不重新执行；
5. 于是界面回到「加载正文」，但**没有任何请求在跑**。

切换布局之所以能立刻恢复，是因为换布局换了组件实例、id 变了，effect 重新触发。

相邻的两个缺口让这个 bug 更难被发现：

- 批量水合收到空数组时直接返回，不产生任何状态变化；
- 部分 id 没有返回行时，条目不进入「不存在 / 失败」终态，界面永远停在「加载中」。

也就是说，水合的状态机是不完备的：**「请求没发出」和「请求发出但没结果」在状态上不可区分**。

## Decision

**水合状态机完备化。** 每条正文记录的状态是 `loading | ready | cleared | missing | failed` 之一（见[正文与 AI 产物的实体缓存](../architecture/2026-10-06-正文与-AI-产物的实体缓存.md)）。「不存在」与「失败」是明确终态，各自有对应的界面文案与重试入口；空数组入队不产生状态变化，但「请求过且无结果」必须落到 `missing`。

**水合触发判定收敛为纯函数单点**：`entryNeedsHydration`（`src/store/selectors.ts`）决定某条目是否需要拉正文。它读的是实体缓存的状态，而不是「快照是否被替换过」——后者是缺陷的来源。

**六个快照替换点统一按 id 继承重字段。** `mergeSnapshotEntries`（`src/store/internals.ts`）在所有替换路径上保留同一 id 已加载的正文与 AI 产物，并区分「后端真值」（bump 版本）与「UI 回放」（不 bump）。`url` 也必须继承——漏掉它会让「查看原文」在某些路径下失效。

**选择按需水合，不在 reload 时统一重拉。** 卡片进入可视区域且需要正文时才请求；刷新后不重拉全部正文。

**列表查询不携带正文**（`layoutNeedsBody` 恒返回 false）。五布局一律走懒水合。这个函数曾经是实现与注释脱节的死代码，现在是有意的设计单点。

## Consequences

**收益**：刷新不再丢正文；「加载正文」只在真的有请求在跑时出现；不存在与失败都有明确终态与重试入口；整页背正文的请求洪峰被避免。

**代价与已知上限**：

- 「请求过且无结果」与「确实不存在」需要区分，这要求后端在水合响应里明确表达「这个 id 没有内容」而不是省略它。若后端改成省略，前端会退回把两者混淆。
- 按需水合意味着快速滚动时正文是渐次出现的。这是有意的视觉折中（避免洪峰），代价是截图类场景下可能拍到未水合的卡片。
- 「无记录时回退视图行 AI 列」的过渡兼容位仍存在（等 Rust DTO 分离后删除），它是当前唯一可以让旧 AI 产物复活的路径。
- 断言「新快照清空 hydratedIds」被证明锁的是缺陷手法本身，修复时按行为变化改写了它——这是「既有断言不回退，但允许附理由更新锁旧缺陷的断言」这条纪律的实际适用。

## Alternatives considered

### Why not 让水合 effect 依赖快照版本号？

依赖快照版本会让每次刷新都触发全部可见条目的水合——即整页重拉正文。这正是选择按需水合要避免的。用「实体缓存里有没有内容」作为判据，语义是「这条数据缺不缺」，而不是「快照换了没有」。

### Why not 在快照替换时保留 `hydratedIds`？

保留标记不会恢复内容——内容已经随快照丢了。标记与数据分开维护是问题的根源，把两者合并到实体缓存（内容就是状态）才是解法。

### Why not 把正文继续留在列表行里，用保守合并处理刷新？

保守合并（新行没有就留旧的）能盖住丢正文，但会让已删除文章的正文一直留在内存里，也会让「清理缓存」无法生效。正文是重字段，它的生命周期必须独立于列表快照。

### Why not 用 `useEffect` 的 cleanup 或 key 强制重建组件？

强制重建组件（用快照版本做 key）会导致整列表重新挂载，滚动位置与展开状态全丢，性能上也是灾难。问题的正确位置在数据层，不在组件生命周期。
