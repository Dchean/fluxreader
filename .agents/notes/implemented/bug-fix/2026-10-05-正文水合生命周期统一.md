# Agent Note: 正文水合生命周期统一

Status: implemented

## Problem

列表快照曾清掉 hydratedIds，而卡片 effect 只依赖不变的 id；界面因此显示“加载正文”却没有请求。空响应和部分缺行也没有明确终态。问题不应通过强制重新挂载列表解决，否则滚动位置和展开状态会一同丢失。

## Decision

正文和 AI 重字段归模块级实体缓存，列表条目只承载轻字段及内容身份。缓存状态为 loading、ready、cleared、missing、failed，无记录表示未请求；entryNeedsHydration 统一决定卡片是否需要正文。已经请求但响应缺行落 missing，真实错误落 failed，并提供对应提示/重试。

列表查询不批量携带正文，卡片按需水合；详情和 AI 产物的生命周期不随每次列表快照重建。mergeSnapshotEntries 通过内容身份、修订和轻字段事实协调失效，不能再描述为“六个快照点按 id 继承正文”——那是实体缓存引入前的方案。完整所有权见 [正文与 AI 实体缓存](../architecture/2026-10-06-正文与-AI-产物的实体缓存.md)。

## Alternatives considered

- effect 依赖快照版本，或 reload 后重拉所有正文：每次刷新都会制造额外 IPC，并把“缺正文”错误地等同于“换过快照”。
- 只保留 hydrated 标记：标记不能恢复已经丢掉的内容，反而可能阻止补取。
- 把正文留在视图行做保守合并：容易让删除/清理后的旧产物继续存活，失效责任不清。
- 以快照版本作为 React key：重新挂载会掩盖状态机缺口，同时丢失局部交互状态。

## Consequences

实体缓存让按需水合、错误终态与刷新解耦，代价是每个失效入口和消费者都必须遵守同一协议。后端省略某个已请求 id 时，前端把它判为 missing；不能要求后端凭空返回不存在行。

2026-11-06 对当前生产 App 的反例仍发现：content_id 与 snippet 一起变化时，失效记录被删除，Reader 持续显示加载而未自动重取；另有旧详情能覆盖新正文。该缺口不否定缓存分层选择，但推翻“加载提示只在请求真正进行中”和“刷新永不丢正文”的无条件保证。详情与证据见 [正文与状态缺口](../../../../docs/roadmap.md#reader-and-state)。

相关回归位于前端 bootstrap/query、reader/body 与组件挂载用例；jsdom 不承担真实滚动几何，当前宿主覆盖边界见 [验证边界](../../../../docs/roadmap.md#verification-boundaries)。
