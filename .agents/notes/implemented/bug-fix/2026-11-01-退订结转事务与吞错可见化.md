# Agent Note: 订阅结转退补事务补口与两处吞错可见化

Status: implemented

## Problem

2026-11-01 第五轮细粒度审计（同步侧）暴露三个小缺口：

1. **结转退订无事务**：`sync/subscriptions.rs` 的
   `db::enqueue_unsubscribe` 调用点（subscribe 快速创建成功但本地订阅已被
   删除的结转分支）内部是「DELETE pending 队项 + DELETE add_feed 队项 +
   INSERT 退订意图」三写。该点是全库**唯一**不在事务内执行它的调用方
   （`commands/folders.rs` 的退订命令等均已自带外层事务）。进程在三次写
   之间崩溃会留下「旧创建意图已删、退订意图未落」的半程状态——远端订阅
   永久无人退订，且没有队列记录可供自愈。
2. **游标推进写失败静默**：`greader_pull.rs` 的
   `db::set_last_sync_ts` 用 `let _ =` 吞掉 DB 写失败——窗口已拿全却没写上
   游标时，日志与 report 都无从区分「推进成功」与「写入失败」。
3. **清墓碑失败静默**：`commands/settings.rs` 关闭 smartDedup 时
   `db::clear_dedup_tombstones` 失败被 `let _ =` 吞掉——用户看到「已关闭」，
   墓碑却仍在拦截重复文章。

## Decision

1. 结转退订调用点包 `conn.unchecked_transaction()`：入队成功后显式
   `tx.commit()`；开事务/入队/提交任一步失败按既有软失败语义处理
   （`log::warn!` + `OutboxOutcome::Skipped`），事务对象 drop 自动回滚，
   三写同生共死，与其余全部调用方的事务口径对齐。
2. `greader_pull.rs` 游标推进写失败改 `log::warn!` + `report.errors.push`；
   游标不前进的语义不变（本轮没写上，下一轮窗口起点不变）。
3. `commands/settings.rs` 清墓碑失败改 `log::warn!`；行为其余不变
   （设置写入继续成功返回，不因墓碑清理失败而失败）。

## Alternatives considered

### 把事务下沉进 `db::enqueue_unsubscribe` 内部

单点修最省调用方纪律；但 rusqlite 不支持嵌套事务，其余调用方
（`commands/folders.rs` 等）已把该函数包在外层事务里，内部再开会直接报错，
等于改写全部调用方的事务边界假设。对齐口径改调用点，否决下沉。

### 两处吞错改成 Err 上抛

游标推进失败上抛会把「窗口已拿全、合并已完成」的一整轮同步判为失败，
与「失败 ≠ 丢成果」的既有恢复语义冲突；清墓碑失败上抛会让设置保存因一个
附带清理失败而整体失败，行为面扩大。两处本质是「附带写失败需要可见」，
warn + report 是最小充分改动，否决上抛。

## Consequences

收益：退订结转的崩溃窗口闭合（与全库事务纪律一致）；两类静默失败在日志/
report 可见，问题现场可定位。代价：结转退订多一次事务开销（纳秒级，路径
低频）；无其他行为变化。验证：`cargo fmt --all -- --check` 本机通过；结转
分支的直达 e2e 落在 `opt009_phaseb_e2e.rs` 的 R1-2 两用例（成功路径三写
原子提交 + RAISE(ABORT) 注入 INSERT 失败的三写整体回滚）——更正：此前
opt009 既有用例只覆盖相邻的 adopt 结转分支（响应在途形态），并不覆盖本
分支；行为断言由 CI 承担（本机不可链接 Rust 无法运行）。
