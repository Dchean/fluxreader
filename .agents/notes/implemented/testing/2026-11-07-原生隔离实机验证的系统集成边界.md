# Agent Note: 原生隔离实机验证的系统集成边界

Status: implemented

## Problem

SMTC、系统通知、开机自启、托盘与窗口几何只能在真实窗口和系统服务上观察，单元与组件测试无法覆盖；直接以正式身份（`com.fluxreader.app`）运行又会写用户数据与注册表。2026-11-07 的原生验证批次需要隔离方案，同时要弄清未打包 Win32 应用在系统集成上的真实注册行为，否则会把“系统没显示”误判为产品缺陷，或把系统策略限制误记为产品通过。

## Decision

用双字段隔离身份构建 release exe（identifier `com.fluxreader.validation.*`、独立 productName、`TAURI_CONFIG` 合并、冻结工作区源码与 dist），CDP 走隔离 `--remote-debugging-port` 且只监听 loopback；批次前后对日常 APPDATA/LOCALAPPDATA 与注册表 Run/StartupApproved 做哈希级对照，证明零改动。验证辅助脚本（守卫放行、BOM 剥离等）不进产品代码。隔离与证据边界方法沿用[窗口启动隔离驱动的证据边界](2026-10-15-窗口启动隔离驱动的证据边界.md)。

实测确立、长期有效的系统集成事实：

- **SMTC AUMID**：未打包 Win32 应用的 SMTC 会话按 exe 文件名注册（实测 `app.exe`），不等于 identifier/productName。定向 Play/Pause 与元数据在该 AUMID 下验证通过；打包（MSI/NSIS）后 AUMID 可能改变，重验不能沿用本次假设。
- **系统通知**：`notify` 的 OS 投递可用 identifier/AUMID 历史证实，但横幅可见性受系统通知策略/勿扰控制（本批发送后 2 秒 UIA/截屏均未见横幅，注册表无法确证原因）；产品通知走 `builder().show()` 默认路径，无点击激活处理器，点击默认只关闭/聚焦、不打开界面。验证“可见/可点击”必须先约定系统通知设置边界。
- **开机自启**：auto-launch 0.5.0 disable 后会在 StartupApproved 留隔离名残留（Run 值已删除、is_enabled=false 正确）；残留属上游行为，按注册表实际值判断开关状态，不据残留推断失败。

## Alternatives considered

- 直接以正式身份跑实机：省去隔离成本，但任何写库/注册表动作都会污染用户日常数据，且无法做哈希级零改动证明，放弃。
- 只靠静态代码审查断言集成正确：AUMID 注册、通知策略、StartupApproved 行为都不在产品源码内，静态审查得不出这些事实。

## Consequences

后续原生批次可复用隔离身份与前后对照方法，并按本篇三个事实设计系统集成断言；代价是每批都要维护构建绑定（160 文件清单）与前后清理。已知上限：本批为直接构建 exe，未做 MSI/NSIS 安装器验收、物理拔插与真实注销/登录自启；横幅不可见的确切系统原因未确证。重访条件：打包身份变化、通知/自启相关依赖升级或系统版本更新时重验 AUMID 与策略行为。17 项结果与证据在本机 `tmp/repair-2026-11-06/environment/evidence/native-verify-r1/`（忽略目录，不随仓库分发）；开放缺口见 [roadmap](../../../../docs/roadmap.md)。
