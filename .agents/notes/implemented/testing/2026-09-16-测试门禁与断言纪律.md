# Agent Note: 测试门禁与断言纪律

Status: implemented

## Problem

CI 曾连续 5 次失败，而每次失败的表现都在同一个地方：`Format (cargo fmt --check)`。原因是 rust job 的步骤顺序把 fmt 排在 clippy 与 cargo test **之前**——fmt 一红，后面两步根本不执行。被它掩盖的是两个真实缺陷：`clippy::type_complexity`（一个函数返回元组过长）与 `clippy::await_holding_lock`（`MutexGuard` 跨 `await` 持有）。这两个缺陷一路穿过了当轮的验收。

根因是一次文本替换：把测试常量换成更长的占位符，使原本恰好等于 `max_width = 100` 的行超限。也就是说，一个与行为无关的编辑让格式门禁变红，进而让两个真实的并发缺陷隐身。

另外两件事让门禁的可信度进一步下降：

1. **`#[ignore]` 被当成「有外部依赖」的通行证**：23 个 ignored 测试里，14 个的理由（「需要启动本地 mock 服务」）不成立——同目录另一个测试文件用**同一个** mock 模块且默认全跑。
2. **转正 ≠ 有保护**：把 ignored 去掉后，对 4 个代表用例做变异测试，只有 2 个能捕获变异；另外 2 个的断言恒真。

## Decision

**中间门禁挡住后置门禁，等于没有门禁。** 这一条是本次最核心的教训：任何「本地只跑 A，B 交给 CI」的分工，一旦 A 在 CI 里排在 B 前面，B 的实际保障就归零。职责分工只能是「谁在什么地方跑」，不能是「谁靠谁兜底」。修复动作是让每个门禁独立可跑且失败信息指向自己的原因。

**探针 → 回归纪律**：外部审计的行为探针证明了的行为缺口，修复任务**必须**把它转化为真实的行为回归断言（修什么锁什么）。静态分页断言与单路径断言不再视为充分验收。验收对象扩展到操作序列场景：阅读中连续翻页、跨字段并发、迟到响应、缓存清理失效。

**源级字符串断言降级**：只保留「单点性必要」的场景（例如「这个入口必须唯一，防止回退」）。理由是机械锁定源码文本会限制必要的改进——改一处实现就会打红，而红的原因与行为无关。新任务默认不要求这类断言。

**文档契约按语义 + 代码事实检查（2026-11-03）**：README 的「配置同步」契约不再锁某一句固定文案。`tools/frontend-tests/ui-contracts.mjs` 的 D29 断言按分句要求同一正向分句同时包含「订阅源」与「客户端设置」，并排斥含「不参与同步/不同步/不进行同步」的分句；AI 配置与模型、敏感凭据则分别要求本机保留语义。真实 README 与全部自检样本统一经过 `readmePasses(markdown)`（四个字段聚合）；完整正向为 true，AI/凭据正确但含旧模型说法为 false，三类否定、仅单对象和跨分句均为 false。

同一测试从 `src-tauri/src/config_sync.rs` 的 `build_payload` 函数体提取 `db::get_setting` 键，确认白名单键存在且不出现 `ai_config`、`greader_password`、`config_sync_credentials`、`miniflux_token` 四个凭据直字面量，并检查排除清单登记四项。这是**直接字面量守卫**：不覆盖别名、间接构造或序列化后的 payload；真实 payload 的排除行为由 `src-tauri/tests/config_sync_e2e.rs::payload_excludes_all_credential_fields` 管理，不能把静态守卫说成全量覆盖。

上述跨语言检查只是静态佐证，不是 Rust 运行时验证：真正的 payload 行为由 `src-tauri/tests/config_sync_e2e.rs::payload_excludes_all_credential_fields` 承担，必须在 CI 的 Rust job 执行。前端测试通过不能替代 Rust 集成测试；反之，Rust 集成测试通过也不能替代 README 对用户表达的语义检查。

**既有断言不回退**：修复缺陷时不允许弱化断言来换绿；如果某条断言被证明锁的正是旧缺陷本身（例如「新快照必须清空 hydratedIds」），允许按行为变化更新它，但必须附理由。

**本地门禁与 CI 门禁的分工写清楚**：分工必须随实机能力更新——2026-10-08 曾实跑完整 `cargo test` 与 `cargo clippy --all-targets -- -D warnings` 并成功链接，本地一度承担 Rust 全量；2026-10-31 实测本机重新不可链接（三项独立确认：零依赖探针、hello-world cargo build、VS 目录为空），`cargo test`/`clippy`/`check` 一度回归 CI 的 rust job（windows-latest）。2026-11-03 独立代理在当前工作区补齐隔离 Rust/MSVC 环境（`tmp/rust-env/`，rustc/cargo `1.98.1`，clang-cl + lld-link），通过 `tmp/rust-env/run-with-rust-env.ps1` 本机已真实执行 Rust 编译、测试、check 与 clippy；这是当前工作区的证据，不外推到其他机器。当前分工：本地必须跑 fmt 与前端门禁，Rust 全量在当前工作区经隔离环境执行，CI 的 windows-latest rust job 仍是最终跨环境门禁。这不是以一次本地通过替代 CI，而是依据实际环境更新分工——**每一项都必须有承担者**（当前分工见 AGENTS.md 门禁表）。

**前端门禁独立执行（2026-11-03）**：`.github/workflows/ci.yml` 的 frontend job 给 lint、build、`test:frontend`、`test:components` 四步分别设置 `(success() || failure()) && checkout/node/install 正常` 条件。任一非安装门禁失败时，后续门禁仍执行并留下自己的结果；安装失败才统一跳过后续步骤（没有可执行前提），任一失败仍使 job 变红，不使用 `continue-on-error` 掩盖。保持单 job 是为了复用一次 `npm ci`，不拆成四个重复安装的 job。

**Node 版本差异是证据边界（2026-11-03）**：本机实测 Node `v24.19.0` / npm `11.17.0`；仓库 `.node-version` 为 `22`，CI 通过 `node-version-file` 使用 Node 22。`package.json` 中的四条前端命令没有绑定 Node 版本，`jsdom@^28.1.0` 的 engines 同时覆盖 Node 22 与 24。本次没有改版本，也没有改命令；因此本地全绿只能证明 Node 24，不能外推为 Node 22 runner 已通过，CI 的真实结果仍以 GitHub run 为准。

**jsdom 不承担几何验收（2026-11-03）**：`test:components` 能证明 DOM 结构、effect、事件与异步接线，但 jsdom 没有布局引擎；`offsetHeight`/`getBoundingClientRect`/滚动/字体等是最小替身。审计证据（`tmp/audit-copy/copy-audit-report.md`、`tmp/audit-ui/`，只读）记录的 980×640 阅读器被压到 160px、溢出/裁切与真实 WebView2 字体/滚动差异，不会因为本门禁全绿而消失。2026-11-03 起，`npm run test:ui-layout`（Windows Edge headless + CDP）为五布局页脚位置与社交水合逐帧几何提供固定 Chromium 回归：覆盖七类社交正文、固定 322px 行高、加载/空态、横向溢出、按钮槽、`aria-controls`、短→长→短正文替换，以及 HTTP 延迟图片成功/失败、视频 poster/MP4 元数据和展开/收起往返。视频 fixture 不设宽高，先取 `readyState=0` 的零高初始态，再取 metadata 自然尺寸 `176×144` 的中间态（此时 poster 仍 pending，Chromium 渲染盒仍为 0），最后等 poster 撑高后才要求内层/视频高度增长、按钮、渐变与 `aria`；同一视频节点的初始/metadata/poster/展开/收起身份必须保持，防止 `dangerouslySetInnerHTML` 重设导致媒体重建。`UI_LAYOUT_MUTATION=no-social-media-remeasure` 必须由视频专项断言判红，而不是被通用 missing 计数或等待超时掩盖。2026-11-04 增加键盘/焦点/响应式/AX 专段：在 1536×900、1280×800、980×640 三档断言列表/阅读器真实宽度、页面无横向溢出、五布局 J/K 的选中/焦点/`aria-current`、收藏移除后的焦点迁移、Sidebar Space，以及设置页 `Accessibility.queryAXTree` 的表单名称；原有 1440×900 / 980×640 五布局与社交几何回归继续保留。它仍不覆盖 Tauri WebView2 实机。凡是改变布局、尺寸、裁切或滚动几何的修复，必须另交真实 Chromium/WebView2 的截图与量测，或明确标为未验证；jsdom 断言只能作为辅助。

波次级的写集分批、独立证伪审计与证据边界见[修复波次的分批、证伪审计与证据门槛](../process/2026-11-03-修复波次的分批、证伪审计与证据门槛.md)。

**ignored 测试的判定要按属性行机械计数**（`l.strip().startswith("#[ignore")`），不能按文档注释里的字样数——曾按字样粗数得到「8」，与真实数字不符。判定每个 ignored 的理由是否成立时，必须核实「该理由描述的环境依赖是否真实存在」：同机制一半跑一半不跑（同一个 mock 模块，一个文件默认跑、另一个文件靠 ignore 跳过）就是理由不成立的证据。

**CI 覆盖的 mock 子集必须真的跑起来**：`--include-ignored` 会跑「非 ignored + ignored 全部」，而 `--ignored` 只跑被标 `#[ignore]` 的用例——这 6 个自托管 mock 套件里一个 `#[ignore]` 都没有，写成 `--ignored` 会匹配 0 个用例却依然绿灯，等于整条 mock 集成测试通道从未在 CI 里真正跑过。

**真实挂载证据的边界要写清楚（OPT-016B，2026-10-09）**：`npm run test:frontend` 是纯逻辑状态机回归（无 DOM、不跑 effect、组件侧只有 SSR 形态断言）；`npm run test:components`（入口 `tools/component-regression.mjs`，用例在 `tools/component-tests/`）用 jsdom + React `createRoot`/`act` 真实挂载生产组件，effect/事件/异步链按真实路径执行，两条通道共用同一份 loader 实现（test-loader/ui-loader，不复制第二套）与同一个 dist-test store/bodyCache 实例（组件经既有 ui-loader 别名拿到的就是断言的那份）。它的证据边界：

- jsdom ≠ WebView2：无布局引擎、无网络栈。ResizeObserver/matchMedia/offsetHeight/getBoundingClientRect/scrollTo/scrollIntoView/DOMParser 等缺失浏览器 API 做**最小环境替身**（只补尺寸与滚动语义，不替身应用逻辑）；
- 外部 IPC 全部 fake：`@tauri-apps/api/core` 走既有 test-loader 的 `__INVOKE__` mock，event/window/app/autostart 由 `tools/component-tests/tauri-compat-loader.mjs` 桩成无副作用；不启真实 Tauri IPC、不访问真实网络；
- React 19 中 `onUncaughtError` 在 act 队列内会被改道（react-dom 内部 `logUncaughtError` 的 actQueue 分支收进 act 的 thrownErrors），故 componentStack 捕获路径用两条 canary 分开取证：边界捕获走 onCaughtError（act 内），无边界错误走 onUncaughtError（act 外渲染）——「生产树零错误」的断言因此不是恒真；
- 判红能力用条件变异证明：把 ReaderProse 源码态文本插值改成 `dangerouslySetInnerHTML` 的 tmp 副本必须被**同一组** DOM 断言抓红（变异只写 tmp、用后即删，测试末尾逐字节复核生产源码未变）；
- jsdom 版本按 npm 元数据选择：`jsdom@^28.1.0`，engines `^20.19.0 || ^22.12.0 || >=24.0.0`，覆盖 CI Node 22（setup-node 经 `node-version-file: .node-version` 读取 22，取最新 22.x）。
- act 与真实动画帧（2026-10-10，Node22 入口复跑修复）：生产组件的 rAF 状态更新（如 App.tsx ToastPill 进场 `requestAnimationFrame(() => setShown(true))`）是真实帧回调，`flush` 的 `setTimeout(0)` 回合不覆盖动画帧——Node22 时序下帧回调可能落在两次 act 之间，统一错误账本按「act 外更新」判红（用例断言本身全过）。需要该状态落进证据窗口的用例必须在 act 内等待一次真实 rAF（`await act(async () => { await new Promise((resolve) => requestAnimationFrame(() => resolve())); })`；jsdom 帧内回调 FIFO，注册更早的 ToastPill rAF 先执行）；不得用关闭警告、扩大白名单或随意长 sleep 假绿。2026-10-19 起，本条的「act 外更新即判红」部分由 [组件回归 act 警告分级](2026-10-19-组件回归act警告分级.md) 取代：act 警告改为计数留证、不再自动判红；关闭警告与扩大白名单仍禁止，需要 rAF 落进证据窗口的用例继续按本条等待。
- 生命周期与清理协议（R1 复审加固，2026-10-09）：**ref 看门狗**（旧 unref 实现实测 `after(() => new Promise(() => {}))` 仍 5pass exit0——悬挂被事件循环空转伪装成绿灯；ref 定时器主动保活，正常收尾显式解除）；用例统一经 `componentTest` 包装，body/卸载清理/错误账本三路失败**聚合且任一即红**；`unmountAll` 对毒树（效应清理抛错）继续清理其余树、登记移除在 finally、最后聚合抛错，不 `catch{}` 吞；`runFinalTeardown` 显式 `process.exitCode=1`——node:test programmatic 模式在 after 钩子失败时**不**改进程退出码（实测 hook reject 后 exit 0）。
- 统一错误账本：console.error / jsdom 未捕获（真实 DOM listener throw 走这条）/ React 三通道错误默认判红；预期错误（canary）用 one-shot **精确例外**登记并消费，**未消费例外同样判红**（防止注册宽泛例外把整类错误全屏蔽）。唯一窄例外是 React act 警告——只计数、不判红，见 [组件回归 act 警告分级](2026-10-19-组件回归act警告分级.md)。
- 终态运行时错误守卫（R2 复审加固，2026-10-09）：finalcheck 之后到达的异步运行时错误（真实形态：React effect cleanup 里 `setTimeout(…100ms)` 晚发 console.error）此前只被采集器记录、终检已过 → 退出码 0 假绿（实测：用例本体 pass 1、进程 exit 0）。修法：`runFinalTeardown` 通过终检后**武装守卫**，此后 console/jsdom/React 三通道任何新错误都立即「同步写诊断（writeSync 直写 fd 2）+ `process.exitCode=1`」——不 sleep、不等待、one-shot 例外只作用于用例预期窗口、finalize 之后不再被任何过时例外掩盖。
- 防护自身有黑盒自检：`tools/component-tests/runner-probes/`（after 悬挂、body 悬挂、毒 cleanup、DOM listener 抛错、非预期 console、例外消费/未消费、R2 晚异步错误）由 `runner-selfcheck.test.mjs` 以真实子进程断言**退出码 + 真实错误消息**（3=看门狗强杀、1=判红、0=例外消费后绿；晚错探针要求用例本体通过仍 exit 1）。

**前端逻辑回归网的分域拆分与数据所有权（OPT-016C，2026-10-09）**：`npm run test:frontend` 的单文件回归网拆为「harness + 功能域模块」，入口 `tools/frontend-regression.mjs` 只做编排（创建 harness → 按固定顺序 await 域模块 → 统一汇总/非 0 退出）。当前用例分布在 17 个功能域模块：smoke-baseline、bootstrap-and-query、timeline-and-playback、reader-and-ai、mutations-and-counts、settings-and-feeds、pagination-and-cache、scroll-position-restore、ui-contracts、subscription-sync、dedup-display、subscription-writeback、ai-cache-signature、gallery-window、error-center、scope-id、sync-indicator；787 条断言的名称/条件在拆分时逐条迁移，数量与名称集合经 AST 解析与拆分前后实跑双向核对（既有 26 + 新增 761 的通过口径不变；这是拆分时的历史口径，当前总数见 Verification）。数据所有权与隔离边界：

- 共享可变夹具（invokeCalls、backendRows、listPlan/pendingList、rejectCmds、getArticlesPlan、feedCountsImpl、heldAi、settingsRaw、articleRow 等）与两套假后端统一归 `tools/frontend-tests/harness.mjs` 的 `S` 对象（含 `useMainBackend()` 切换、`resetStore()/bootFixture()` 复位、`check/checkNew` 记录）；域模块只经 ctx 注入的读写接口访问共享状态，不 import 第二份 store、不复制 harness；
- 域内自带的夹具（大行集等）由各域自行构造与复位；临时全局替换（`__INVOKE__`/`window`/`confirm`/`console`/process 监听）统一经 harness 的 `ctx.overrideGlobal(target, key, value)` 注册、并在 `finally` 调用其返回的 `restore()`——原属性存在则按原 descriptor 还原，原本不存在则 delete（不留影子属性），成功/异常都保全（R1 复审收口；仅存量已带 try/finally 的值级还原点保留原形态）；唯一保留的顺序前提是 smoke 域使用初始假后端（其余域进入即 `useMainBackend()`），不依赖「前一个域恰好留下的 fixture」；
- 每个域可独立运行：`node --loader ./tools/test-loader.mjs ./tools/frontend-regression.mjs --domain <域>`，各域独立进程矩阵全绿（通过数=该域 AST 计数、退出 0），默认无参数仍全量顺序执行；
- 判红能力用真实变异证明（只 tmp/内存，生产源码字节复核未变）：读状态回滚失效、续拉空页不收敛、ReaderProse 源码态改回 `dangerouslySetInnerHTML` 三组变异，分别使 mutations-and-counts、pagination-and-cache、ui-contracts 独立运行非 0 退出；临时全局覆盖的恢复契约另有失败注入自测（成功/异常路径均恢复、原本不存在→delete、真实 smoke 域跑完 `confirm` 不泄漏）；逐断言映射与运行/变异台账在 `tmp/optimization-20261008/OPT-016C/`（一次性产物，不入主线）。

## Consequences

**收益**：门禁的失败信息指向真实原因；行为缺口在修复时有断言锁住；不会因为「改了实现文本」而打红；ignored 测试的数量与理由都可核；CI 的 mock 通道确实在执行。

**代价与已知上限**：

- 源级断言的降级意味着「某处实现被整体换掉」这类回退不会被自动发现，只能靠行为断言间接覆盖。判据是「单点性必要」——这个判断需要人来下。
- 前端四个门禁在单个 job 内顺序执行：一次性 run 能看到多项独立结果，但前置红项不会缩短后续执行时间；分 job 并行会重复安装，当前不以总时长换取重复成本。
- README 语义检查与 `config_sync.rs` 的静态检查不能证明 Rust 运行时行为；Node 22 runner 与真实 WebView2 几何仍需各自的执行证据。
- 探针 → 回归的转化责任在修复者身上，而探针本身是一次性产物（在存档分支里）。若修复者忘了转，缺口就只存在于一次性的证据里。
- 本机环境可能变化，不能仅凭历史机器描述跳过可运行门禁；不可用时要保留实际错误并指明 CI 承担者。2026-10-08 的本地完整运行验证过当时可用，2026-10-31 曾不可链接；2026-11-03 起 `tmp/rust-env/` 隔离环境可在当前工作区执行 Rust 全量，CI 的 windows-latest 仍是最终跨环境门禁。

## Alternatives considered

### Why not 把 fmt 放到最后跑？

顺序调换只是把「谁挡住谁」换了个方向。真正的问题是三个门禁共用一条流水线且互不独立——修法是让每步都能单独运行并给出自己的失败原因。2026-10-09（OPT-016A）已落地：`ci.yml` 的 fmt / clippy / 默认 test / 6 套件 mock 四步各带 `if: (success() || failure()) && checkout/toolchain 正常` 的执行条件——任一前置门禁红时后续门禁仍运行、失败信息指向自身，job 因红步骤整体失败；未用 `continue-on-error` 掩盖。tag `v*` push 同时触发 `ci.yml`，补上 release 门禁对「tagged commit 无 CI run 可等」的缺口。

### Why not 加强源级字符串断言，防住所有回退？

审计的结论相反：机械锁定字符串会限制必要的改进。曾经的一条断言锁的正是缺陷本身（「新快照清空 hydratedIds」），如果它足够强，正确修复反而会被它拦住。断言应当锁定**行为**，源码文本只在「必须唯一」这类结构性约束上使用。

### Why not 把所有 ignored 测试都删掉？

`ingestion_e2e` / `scheduler_e2e` 各自的 1 个 ignored 理由是不成立的「必须先启动外部 8765 服务」——OPT-016A（2026-10-09）改为测试自托管（绑定 `127.0.0.1:0`、自生成固定内容与条件响应、结束时关停），去 `#[ignore]` 后由默认 `cargo test` 在 CI 真实执行；判定与执行都按真实运行取证，不再依赖会 0 匹配假绿的 `--ignored`。其余 7 个 ignored 的理由仍然成立，全部是需要真实服务端的 live 测试（`fever_live_e2e` 3 个、`fever_sync_live_e2e` 1 个、`greader_live_e2e` 3 个）：不能默认跑，也不该删——它们是真实服务端行为的唯一覆盖，必须在具体任务里单独约定读写边界后执行，不作为统一门禁。

### Why not 用 CI 的失败数当门禁基线（「通过数可增不可减」）？

基线数字（当时的 655 条、cargo 161 等）会随修复不断变化，写进断言就得每次更新。更重要的是「条数不减」并不等于「保护不减」——20 个恒真断言比 10 个有效断言更差。当前的做法是用变异测试抽样验证断言的**判别力**，而不是统计条数。
