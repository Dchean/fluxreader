# Agent Note: 窗口启动隔离驱动的证据边界

Status: implemented

## Problem

OPT-015Q 需要在**生产自动建窗路径**（Tauri 按 `tauri.conf.json` 自动创建 main，再由 `setup`
调用一次 `window_startup::restore_and_show`）上验证「挪动位置后下次启动会先居中再跳位」是否
仍存在。既有 OPT-015N 驱动只覆盖手工建窗路径——它在运行时 `context.config_mut().app.windows.clear()`
后手工 `from_config` 建窗，因此八场景全绿与用户实测矛盾；差异可能落在创建/恢复时序上，旧证据
不能复用。窗口几何又只在真实 HWND 上可见，单元测试和 SSR 都无法冒充首帧。

驱动需要同时满足两个互斥的诉求：贴近生产创建路径，和不触碰正式 `com.fluxreader.app` 数据。

## Decision

**差集设计：同一 driver、最小页面、隔离 state 文件、同一 `restore_and_show`，只切换建窗开关。**

- `manual` 臂：复刻 OPT-015N 手工建窗（`windows.clear()` + `from_config`），作为必须绿的对照。
- `auto` 臂：不清空 config windows，由 Tauri 按配置自动创建 main，再对既有窗口调用同一
  `restore_and_show`——即生产创建路径。

判据是**物理事实**，不是口径字符串：首次可见（`IsWindowVisible` 0→1）瞬间的窗口矩形、
隐藏期 `Moved`/`Resized`/`WINDOWPOSCHANGING` 轨迹、首次可见前的 `WM_SHOWWINDOW` 次数，以及
进程退出后 state 文件是否被居中/默认几何覆盖。取消状态文件、离屏、损坏、最大化、全屏等初值
都纳入场景，异常值走生产兜底路径。

**接受有边界的隔离，而不是伪造隔离。** tauri 2.11.5 在 `from_config → build` 路径上忽略
`WindowConfig.data_directory`，所以 auto 臂的 WebView2 UDF 实际落到
`%LOCALAPPDATA%\com.fluxreader.opt015q-diff.<mode>.<scenario>.<pid>\EBWebView`，
而 manual 臂按 `--webview-dir` 落到任务 tmp。该物理落点差异被**如实记录**并计入未排除因素
（冷/热目录未构造），不因为「想让它指向 tmp」而改 runner、改 build 路径或写死参数。

状态文件使用插件同款 filename 写到任务 tmp 绝对路径；identifier 用隔离前缀
`com.fluxreader.opt015q-diff.*`，正式 `com.fluxreader.app` 数据零接触；每次 run 结束后按前缀
清理由本驱动产生的 AppData 目录。

## Verification

R2 主差集 run `R-20261015-091053-50124`：6 场景 × 2 模式 = 12 run 全绿（`overall=completed`）。
两臂 saved_position 首次可见均为 (200,150)+1600×1100（隐藏期完成移动），可见后零事件，退出后
state 未被居中值覆盖；maximized 首见即 zoomed，fullscreen 首见为显示器完整 bounds。
OPT-015N 八场景回归 8/8 PASS（run `R-20261015-091140-8888`）。auto+生产插件集探针绿
（`R-20261015-091219-35500`）。auto UDF 落点由主 run 原始 JSON + 文件系统直测确认存在。

结论：**dev HEAD 的 auto 生产建窗路径未复现「先居中再跳」**，按任务卡「不做无依据的修复」，
生产代码零改动。证据与驱动留在 `tmp/optimization-20261008/OPT-015Q/`（不进主线）。

## Alternatives considered

### Why not 让两臂共用同一 WebView2 数据目录？

这是最初的设计意图，也是 R1 报告失实的地方：R1 以为 auto 的 UDF 进了 tmp，据此宣称「两臂共用
目录、冷/热已排除」。实际每 run 用新 pid，auto 每次都落一个新的 `%LOCALAPPDATA%` 目录，
warm 根本没形成热目录、shared 也没真正共用。强制共用要么 patch 上游 crate，要么改 Tauri
build 路径绕过 `from_config`，两者都改变被测对象的创建路径——测的就不再是生产路径。选择承认
边界，把冷/热移入未排除因素。

### Why not 只跑 auto 臂（省掉 manual 对照）？

auto 单独绿无法区分「自动建窗路径确实没问题」与「隔离方式本身掩盖了现象」。manual 对照复刻
已被接受的 OPT-015N 路径，两臂在同一 runner/页面/state 写法下只有建窗开关不同，才能把差异
锁定到创建路径本身；也是 R1 UDF 口径被发现的原因。

### Why not 改用完整生产进程（真实 dist 页面、db、调度、托盘）做验收？

那会需要用户真实 profile、真实状态文件历史和真实网络，且会写正式 `com.fluxreader.app` 数据，
违反任务卡不触碰正式数据的边界。生产进程里 db/调度/托盘/真实页面都在 `restore_and_show` 之后
运行，改变的只是同步 create→restore→show 之后的事；它们是形式未排除项，由真实构建复测承担。

## Consequences

**收益**：结论建立在消息级首帧事实而非源码意图；两臂差集把差异锁到创建路径，而非 Cargo.lock、
隔离方式或页面伪影；证据边界写清楚，后续维护者能分辨「已排除」与「未排除」。

**代价与已知上限**：auto 臂 UDF 落 `%LOCALAPPDATA%\<隔离 identifier>`，与 manual 臂物理落点
不同，冷/热目录未排除；驱动不是完整生产进程，真实前端页面、真实 profile 的 WebView2 热态、
DPI 动态变化与多显示器物理拔插都在范围外。用户复现的确切构建归属（dev 打包 / v0.17.1 发版）
仍待核实：窗口修复只在 dev（`8d863ae`/`af09d62`），v0.17.1 早于修复，发版构建复现属预期，
但未证实用户装的就是发版。若用户在 dev 构建复现，需现场录屏/事件日志再开新卡。
