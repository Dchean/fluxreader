# Agent Note: 验证方法与复核纪律

Status: implemented

## Problem

在多轮审计与修复中反复出现同一类问题：**验证手段本身不可靠**，于是结论也是错的。有过这些实例：

- 一个探针脚本因缩进假设错误（硬编码 8 空格，实际 12 空格）触发了内部的 `count != 1 → SKIP` 守卫，**静默跳过**，却把结果写成「未捕获」。负面结论与正面结论用了不同强度的证据。
- cargo 的 mtime 指纹让变异测试用了**陈旧的 `app_lib` rlib**——还原代码后没有重新编译，测试结果不可信。
- 假后端（mock）比真实实现「更正确」，造出了生产环境不存在的现象；报告作者据此撤回过一条结论。
- 合成 `.click()` 不构成用户手势，`<audio>` 播放验证必须走 CDP 的 `Input.dispatchMouseEvent`。
- `ModalOverlay` 无条件渲染 children（关闭态仅 `opacity: 0` + `inert`），程序化点击可以绕过 `inert`，于是探针「点错弹窗」却没报错。
- IPC Channel 流式的 shim 若只接受字符串形态，会造出「摘要一直生成中」的假缺陷——真实 Tauri 会先序列化 Channel。

共同点：**验证失败与验证未执行这两种情况被混同了**，或者验证工具自身的偏差被当成了被测对象的行为。

## Decision

**探针必须区分「未执行」与「执行后未捕获」。** 跳过要显式报错，不能把 SKIP 记成「未捕获」。任何内部守卫触发的跳过都必须让整个探针失败退出。

**变异测试必须确认重新编译。** 采信结果的前提是构建输出里出现 `Compiling app`。没有重新编译的结果一律作废。

**按同一语义的全部调用点核对，而不是按 diff 行数核对。** 「修好了」的判据是该语义的所有调用点都符合预期，不是「这次删了几行」。曾经有一处缺陷有 6 处平行调用点（`let _ =` 吞错），只按 diff 核对就会漏掉其余 5 处。

**假后端必须逐字复刻被验证方的反序列化与默认值逻辑。** mock 比真实实现更宽容会掩盖缺陷（例如字段被静默丢弃这类问题，宽容的 mock 不会暴露）；mock 比真实实现更严格会造出生产不存在的现象。

**按属性行机械计数，不按文档字样计数。** 统计 `#[ignore]` 数量用 `l.strip().startswith("#[ignore")`；按注释里的字样数曾得到错误的「8」。同类原则适用于任何「从文本里数出某类结构」的统计。

**证据类型必须匹配结论类型：**

| 结论 | 需要的手段 |
| --- | --- |
| 代码路径存在 / 不存在 | 源码检索（含符号而非行号） |
| 动态效果生效 | 实机观察，静帧截图不能证明动态 |
| 用户手势相关行为 | 真实输入事件（CDP `Input.dispatchMouseEvent`），合成 `.click()` 不算 |
| 属性生效 | 实机 Tab 遍历，脚本读属性只能证明属性存在 |
| 渲染类缺陷（如 React #185） | 真实渲染环境，node 回归无法覆盖 |

**行号不可作为定位依据。** 源码文件持续变动，所有跨文件引用按符号检索。文档与注释里的行号只在写入时有效，改写时一并去掉或改为符号名。

**环境限制要如实记录，不能当成结论。** 例如「本机没有 MSVC 链接器导致 cargo test 无法运行」是环境事实，不是「项目没有 Rust 测试」；「审计环境缺 `link.exe`」同理。

## Consequences

**收益**：验证失败与验证未执行不再混淆；结论的证据强度与其类型匹配；mock 与真实实现的偏差不再造出假象。

**代价与已知上限**：

- 每类结论都要匹配对应手段，因此一次完整的验证往往需要两三种工具（源码检索 + 实机 + 真实输入）。成本比「跑一次测试」高。
- 变异测试必须等待重新编译，反馈循环变慢；采信条件（`Compiling app`）需要人工确认。
- 真实渲染验证依赖 CDP 与本地浏览器，无法进 CI（需要应用实例与副屏）。因此这类验证的结论依赖执行者的记录，复核需要重跑。
- 存档分支里保留了一次性探针与测量工具，但这些工具的使用前提（浏览器版本、应用窗口位置、测量方法）记录在当时的报告里，重新使用需要读那些报告。性能测量方法论在 [docs/performance.md](../../../../docs/performance.md)。

## Alternatives considered

### Why not 只靠单元测试，取消探针类验证？

单元测试覆盖不了「真实渲染 + 用户手势 + 事件序列」这类场景，而缺陷恰恰集中在这些地方（React #185 打开文章即崩，node 回归全绿）。两者的分工是：单元与逻辑回归覆盖状态机，真实渲染验证覆盖运行时集成。

### Why not 把探针固化进 CI？

探针需要启动应用实例、真实浏览器与特定窗口位置，且部分会修改本地数据库。放进 CI 的代价（启动 WebView2、管理数据备份还原）远超收益。当前选择是把探针留在存档分支，使用时按当时的报告重跑。

### Why not 让 mock 更宽松一点，减少测试维护？

宽松的 mock 会让「字段被静默丢弃」这类缺陷隐身——那正是项目里实际发生过的缺陷。mock 的价值在于忠实，不在于好维护。

### Why not 用源码字符串断言代替行为验证？

它便宜且稳定，但锁的是文本而不是行为：改实现就打红，而打红的原因与行为无关；更糟的是它可能锁住缺陷本身（曾有一条断言锁的是「新快照清空 hydratedIds」这个缺陷手法）。源码断言只保留「单点性必要」的场景。
