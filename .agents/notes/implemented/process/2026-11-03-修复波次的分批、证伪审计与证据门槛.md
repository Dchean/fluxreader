# Agent Note: 修复波次的分批、证伪审计与证据门槛

Status: implemented

## Problem

跨同步、数据、界面与运行时的修复共享文件和验证资源。一次性全修会混淆写入归属与证据版本，历史绿灯又容易被误作当前全功能证明。早期主控/编码工具限定和逐轮任务卡也不适合作为永久执行指令。

## Decision

按关键接口、写入边界与可验证结果分批：一个写域一个负责人，依赖未稳定的下游不占共享资源等待；强耦合修复由同一实现者完成调查、修改、验证和记录。并行只用于独立写域，真实UI/端到端与共享构建按当前项目规范预留。

实施与独立审计分开；审计者未参与实现，核对真实输入、当前差异和原始证据，不能只采信实现者PASS、Note状态或CI绿。修复复用适合的原负责人，补查由证据缺口和变化决定；不为重复全套仪式增加成本。具体角色、确认、冻结及升级诊断服从当前适用AGENTS，不由旧Note覆盖。工具名、模型、会话ID或历史日志体积阈值不再成为跨任务规则。

测试要对应所声称的层次：类型/格式、状态、挂载、真实布局、生产数据库/网络与真实部署各有边界。Node24结果不冒充Node22；jsdom不冒充布局引擎；mock不冒充真实服务器；同提交旧二进制复跑不冒充新编译。CI需实际执行适用门禁，失败与未验证分别保留，不能降阈值或多sleep掩盖。

每次修复携带最小有判别力的反例与正常对照。README文案契约检查应验证“同步什么/留在本机什么”，不锁旧完整句；Rust payload行为测试仍负责实际上传面。基础门禁可执行不等于业务缺陷已修。

文档按[索引](../../../../docs/README.md)分工：长期理由在归属Note，事实在docs，当前缺口在roadmap，轮次状态只在本入口或当次交付。历史审计与任务卡从固定Git提交恢复；不复制完整日志或建新台账。清理前先承接独特约束，不按年龄或篇幅归档。

## Alternatives considered

- 一张总卡修全部域：协调少，但共享写入和证据版本难区分，选按职责分批。
- 实现者同时完成最终证伪：上下文可能只支持自己的假设，保留未参与实现的审计角色。
- CI绿或CLI退出0直接验收：只能说明实际执行的断言，不能证明全部用户操作或外部版本。
- 为恢复绿灯改回README旧句、跳过归档失败或重算旧seal：掩盖契约/历史问题，改为语义检查并保留原始失败。
- 固化旧工具、模型和每轮重开规则：与实际能力及任务大小脱节，改由当前协作规范安排；历史选择仍可追查。
