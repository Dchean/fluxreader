# Agent Note: 主控与代码执行分离

Status: implemented

## Problem

审计揭示测试通过与真实功能可靠之间存在缺口。用户要求 Codex 持续主控、CodeBuddy 编写、独立子代理逐卡 review，且限定模型和 fallback；只把自然语言任务丢给 CLI 无法证明产物符合卡片或写入没有越界。

## Decision

Codex 拥有路线、任务卡、验收与 Git/CI；CodeBuddy 只编写明确写集内的代码/测试/归属 Note，不提交或改变分支；独立初审会话只读 review，每次返工后复审。用户已明确允许常规采用「CodeBuddy 编码 → 另一未参与实现的只读 CodeBuddy 会话初审 → Codex 主控复审」；不必等独立审查服务限流后才启用。初审禁用写入/命令/嵌套代理工具，明确标注来源；已有 Codex 独立审查继续收取并优先复用，不为切换流程重复派发。不把任何失败的审查当作通过，最终验收责任仍在主控。该模式已由烟测验证过一次 NEEDS_CHANGES→同会话返工→PASS，正式产品任务仍逐卡验收。逐卡独立审查源自本次用户明确要求，不作为所有普通任务的默认额外步骤。

CodeBuddy 的只读审查是候选结论，不是独立验收的终点。主控依据其发现逐条回查对应源码、基线与测试证据；有矛盾或高风险缺口才补定向反例，不因此重跑全量审计。不同会话不能消除同一模型的判断偏差；“R1 之前就存在”也不等于可以违反整张任务卡的验收契约。

CodeBuddy 使用 deepseek-v4.1-flash + max；配额/token 耗尽才以 custom-local:deepseek-v4.1-flash + max 继续。使用显式 CLI 参数，不修改用户全局模型/凭据配置；日志不公开 token/key。超时观察不代表任务停止，先验证原 PID/会话终态再决定重试。

会话隔离有硬边界，不靠默认的 `--continue`/`--resume` 隐式续接：每一轮 CodeBuddy 审计都用**全新会话**（派发脚本显式 `--session-id`，不带 `--resume`/`--continue`），审计 prompt 首行声明本轮是否参与实现；同一张卡的返工复用原**编码**会话，使实现者保有自己上一轮的完整上下文；只有跨到新任务卡、或原会话上下文已明显过重（经验值约 4–5 MB 日志、已跨多个卡）时才为编码另起新会话。复用前先确认该会话未同时承担审计职责，避免实现与审查互相污染。此硬边界已由会话文件核实：B2 初审、R1 复审、R2 复审、R2 返工增量复审四个审计会话 id 互不相同且均异于编码会话；B1-R3、B2 R1+R2 返工则各自复用了原编码会话。

会话 id 前缀区分职责，便于脚本一眼判定复用是否越界：**编码**用 `code-<卡号下写>-<yyyyMMdd>`（同一张卡续用同一 id），**审计**用 `audit-<卡号下写>-r<轮次>-<yyyyMMdd>`（每轮不同）。2026-10-15 核查发现历史编码会话曾复用平台自动 uuid（如 `01a13a8d-…`，3.57 MB）跨卡返工，虽未达体积阈值但已跨卡，故自本轮起该会话进入禁用名单，不得再复用。禁用名单：`01a13951`(5.55 MB)、`f8f27880`(8.92 MB)、`eaf41e7f`(9.14 MB)、`772b15a4`(8.00 MB)、`96a57229`(11.97 MB)、`01a13a8d`(3.57 MB，跨卡)。

### 派发前清单（每次派发前照单核验，主控本人执行）

不依赖人工记忆，主控在每次 `codebuddy ... cmd` 发出前核对以下四项；任一项不符即停止本次派发并修正脚本：

1. **审计一律新开**：审计脚本必须用全新 id，命名 `audit-<卡号下写>-r<轮次>-<yyyyMMdd>`，命令行只含 `--session-id <新id>`，**禁止**出现 `--resume` 或 `--continue`；prompt 首行必须写明“本会话未参与该卡实现，只读审查”。
2. **编码按卡复用、按卡命名**：编码脚本引用本卡既定的 **编码** 会话 id（`--session-id <编码会话id>`），命名 `code-<卡号下写>-<yyyyMMdd>`。**本卡首次派发前，该 id 不得在任何既有 `.jsonl` 或既往派发脚本中出现**（即不许挪用自动 uuid 或他卡 id）；跨到新任务卡必须另起新编码会话；编码会话 id 不得与任何审计会话 id 相同，也不得在禁用名单内。
3. **复用前查体积**：复用编码会话前打印该 `.jsonl` 体积；**≥4 MB 即视为过重，禁止复用，另起新编码会话**（跨卡时无论体积都新开）。审计会话本就用一次即弃，不受此阈值约束。
4. **确认无并行写入**：同一张卡同一时刻只有一个 CodeBuddy 进程持有写入权限；审计与编码不得在同一卡上并行运行；确认上一个进程已终止再起下一个。

会话文件位置：`C:\Users\A\.codebuddy\projects\d-fluxreader\<session-id>.jsonl`。查体积命令（PowerShell）：

```powershell
Get-Item 'C:\Users\A\.codebuddy\projects\d-fluxreader\<session-id>.jsonl' | Select-Object Name,@{n='MB';e={[math]::Round($_.Length/1MB,2)}}
```

违规处理的判据：脚本里出现同时含 `--session-id` 与 `--resume`/`--continue`、或审计脚本的 id 与任一既有会话文件同名、或复用体积 ≥4 MB 的编码会话、或编码会话 id 在首次派发前已存在于既有会话文件/派发脚本，均视为派发错误，必须先纠正再执行，不能靠事后解释。

用户已要求自主按审计推进，因此在保留原功能和技术栈的边界内无需逐卡再次问确认。真实用户数据、实际账号写操作、发布标签仍不因为这项授权而自动开放。改动在原 checkout 的 dev 上串行集成，不创建 worktree。

路线与卡片位于 docs/optimization；临时 CLI 日志位于忽略的 tmp，不进入主线。现有 .agents/notes 的事务、查询、缓存等领域决定优先原位更新。

## Alternatives considered

### Why not 主控同时写代码并自行 review？

可以更少切换上下文，但会让实现与验收来自同一个判断，且不符合用户指定分工。主控只制定任务与独立验证，代码返工仍交 CodeBuddy。

### Why not 创建工作树和复杂工作流引擎？

隔离有价值，但用户已明确拒绝新的 worktree，仓库也刚清理复杂工作流。限定不重叠写集、必要的基线 diff 和简单 Markdown 卡片足以支撑本轮，不引入第二套任务数据库。

### Why not CodeBuddy 独立会话给出 PASS 就直接验收？

上下文隔离能降低实现者自证偏差，也可在独立审查服务限流时保留审查入口；但同一模型仍可能把已发现的失败恢复问题判成“不阻塞”。因此由主控定点验证结论和优先级，既不直接背书，也不默认重跑一次全项目审计。

### Why not CLI 退出 0 或自报测试通过即验收？

烟测已出现测试全绿但具体输入漏字符的情况。独立 reviewer 检查实现与需求，主控核对最终交付版本、测试日志与集成风险；证据充分且版本对应时不默认重跑同一命令。证据缺失、验证后改动、高风险未覆盖或规定门禁才触发补测。

## Consequences

收益是需求、实现、审查与最终证据分离；代价是每卡增加独立 review/返工时间，且 tmp 原始日志不是永久验收记录。卡片保存提交和检查结果，Note 保存决定，不记逐 token 流水账。同一任务复用原执行者与 reviewer，结果通过完成通知接收；不为催促发送无新信息的消息，不额外制造普通步骤的摘要/备份文件。工具白名单不是 OS 沙箱，必须持续核对实际写集；CI 失败与实机未验收如实保留，不允许以局部测试替代。

## Verification

派发烟测完成过 NEEDS_CHANGES→同会话返工→PASS。正式执行 primary deepseek-v4.1-flash 的日志明确返回 429 用量耗尽后，主控改用用户指定 custom-local:deepseek-v4.1-flash + max，保留原 session 继续；备用连接实测返回 FALLBACK_READY，响应报告模型 deepseek/deepseek-v4.1-flash。当前选用的模型与每次参数保存在任务派发记录，不因观察超时随意换模型。

2026-10-10 的定向核验验证了这一边界：OPT-007 所报既有行无守卫回写可由 mock HTTP + SQLite 复现；OPT-011 两项返工确实关闭，但连续失败后 UI 与持久化值分叉也可由真实 store + 失败 IPC 复现，因此主控拒绝其无阻塞 PASS。证据与返工边界保留在两张原卡，不另建重复审计报告。
