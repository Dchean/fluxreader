# Agent Note: 发布说明取自 tag 附注

Status: implemented

## Problem

发布说明曾有两处来源：annotated tag 的附注，以及 GitHub Release 的 web 正文（由 `tauri-action` 用一份静态文案生成）。两者会不一致——tag 附注写的是这一版的真实变更，web 正文是模板。用户从 Releases 页面看到的和从 tag 看到的不是一回事，而维护者要改两处。

## Decision

**发布说明只有一处来源：annotated tag 的附注。** `release.yml` 有专门的步骤通过 GitHub API 读取 tag 对象的 `message` 作为 Release 正文，并在遇到轻量 tag 或空附注时**直接失败拒绝发布**；随后还有「Ensure release body matches tag annotation」作为双保险回写。手动触发（`workflow_dispatch`）时回退到静态说明。

**发布序列四步：**

```text
1. 起草附注到 tmp/release-notes-vX.Y.Z.md
   （提交数用 git rev-list vX.Y.Z-1..HEAD --count 实测，不估）
2. bump 提交单独推送，等 CI 绿
3. git tag -a vX.Y.Z <bump提交> -F <附注文件>，推送 tag
4. Release 工作流自动构建（Release 正文取 tag 附注）
```

**附注结构：**

```text
FluxReader vX.Y.Z

距 v(X-1).Y.Z 共 N 个提交，主题是「…」。

行为修复：
- …

健壮性（Rust）：
- …

一致性统一（UI）：
- …

测试与基建：
- …

门禁数字与独立审查结论
已知限制（沿承上版）
```

**历史提交哈希不重写。** 这条是硬约束，理由具体：重打历史 tag 会逐个重触发 Release 工作流，而旧提交上没有 CI 记录，门禁步骤必然超时失败。

**存量说明**：v0.8.0–v0.16.0 的 GitHub Release web 正文仍是旧的 `tauri-action` 静态文案；这些版本的完整说明以 tag 附注为准。需要修正 web 正文时用：

```bash
gh release edit vX.Y.Z --notes-file <(git tag -l --format='%(contents:subject)%0a%0a%(contents:body)' vX.Y.Z)
```

## Consequences

**收益**：发布说明只有一个维护点；Releases 页面与 tag 附注永远一致；漏写附注会在发布前失败而不是发布出一份空说明。

**代价与已知上限**：

- 门禁要求「tagged commit 上 CI 必须全绿」，而 `ci.yml` 只触发于 `push: branches: [main, dev]` 与 PR → main，**没有 `push: tags: ["v*"]` 触发**。因此当 tag 指向非 main tip 的提交时，该 SHA 上永远不会有 CI 运行，门禁会空等到 45 分钟超时后报错。当前实践是「tag 一律指向 main tip 的 bump 提交」以规避，但这是纪律不是机制，见 [docs/roadmap.md](../../../../docs/roadmap.md)。
- 附注结构是书面惯例而非强制；已有一次发布（v0.17.0）改用主题式叙述，未按分节模板写。格式的一致性靠人，没有脚本核对。
- 存量说明会长期存在（历史版本的 web 正文不可批量修正而不触发门禁问题）。

## Alternatives considered

### Why not 让 Release 正文由 workflow 从提交历史自动生成？

自动生成的说明只能列出提交标题，而发布说明的价值恰在于「这一版的主题是什么、哪些是行为修复哪些是健壮性、已知限制继承了哪些」。这些判断需要人写。选择的结构是：**人写附注入 tag，workflow 负责搬运与校验**。

### Why not 手工在 GitHub 页面上写 Release 正文？

那就是双轨的起点，也正是这条决定要消除的问题。手工写意味着 tag 附注与 web 正文的内容会分叉，而且没有东西保证它们一致。

### Why not 对历史版本批量修正 web 正文？

批量修正需要重打 tag 或逐个 `gh release edit`；重打 tag 会触发 Release 工作流并因旧提交无 CI 记录而失败，而逐个 edit 是 9 次手工操作。留一条 `gh release edit` 命令供需要时单点修正是成本最低的折中。

### Why not 允许轻量 tag？

轻量 tag 没有附注对象，Release 正文就没有来源。门禁直接失败比发布出一份空的 Release 说明更好——后者会让用户以为这一版没有任何变更。
