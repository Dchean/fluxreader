# Agent Note: 发布说明取自 tag 附注

Status: implemented

## Problem

annotated tag 与 GitHub Release 曾分别维护说明：tag 记真实变更，web 正文由静态模板产生。双份来源会漂移，用户与维护者看到不同版本描述。

## Decision

新发布以 annotated tag 的 message 为正文来源；release工作流读取它并在后续步骤再次核对。轻量tag、空附注失败关闭；手动workflow_dispatch保留静态回退。具体发布操作与用户文案格式只维护在 [docs/release.md](../../../../docs/release.md)。

历史边界有两次明确变化：2026-09-29采用这一来源单点时，旧web正文仍有模板；2026-11-02按用户要求编辑旧Release web正文、保留原tag不动，历史版本因此允许不同。后继[历史文案与提交史边界](2026-11-02-历史文案规范化与提交史边界.md)只取代旧文案格式和“不批量改旧web正文”的选择，不取代后续新发布以tag为源。

不重写历史提交或重打tag：SHA是文档、版本与资产的追溯依据，重打还可能触发旧构建并覆盖资产。当前ci.yml已含v* tag触发，旧“tag不会产生CI”仅是当时限制，不再作为现行事实；Release仍须对应SHA的门禁成功。

## Alternatives considered

- 自动从提交标题生成：便于枚举，却不能表达真实用户收益及限制；采用人写附注、工作流搬运核对。
- 手工维护两个新版本说明：容易重现双轨漂移，未采用。
- 接受轻量tag或空正文：缺少可靠说明来源，选择直接失败。
- 当时不批量修旧web正文：减少操作成本；该取舍后来由用户的文案整理要求取代，原理由在固定历史原文中保留。

## Consequences

新发布只有一个文本源，漏写附注能在发布前暴露。维护者仍需核对说明与实际改动，tag机制不能证明功能或版本正确。历史web正文例外与手动触发回退意味着“永远逐字一致”并不成立。

改变说明来源、workflow读取方式或历史资产策略时重访。当前实现可沿 `.github/workflows/release.yml` 核查；2026-11-06文档整理未执行发布、重打tag或编辑外部Release，历史原文见[固定基线](https://github.com/Dchean/fluxreader/blob/91ece562d79fd909642cd6d570d636e884b7387e/.agents/notes/implemented/process/2026-09-29-发布说明取自-tag-附注.md)。
