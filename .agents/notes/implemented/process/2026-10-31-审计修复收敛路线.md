# Agent Note: 审计修复收敛路线（门禁先行）

Status: proposed

## Problem

2026-10-31 的两轮证伪审计（4 个专项 + 13 个专项，全部新开代理、真实证据判定）确认了四类测试替身语义失真：`mock_greader` 的 `ot` 过滤列（`src-tauri/tests/mock_greader.rs:1316`）与真实 Miniflux 的 `published_at >` 不一致；Fever 星标 mock 为绝对赋值而真实 Miniflux 是取反切换（`fever_compat_e2e.rs:656`）；`quick_add` mock 默认幂等而真实服务端会拒绝重复 URL（`mock_greader.rs:116`）；compat 套件的 `/stream/items/ids` 无窗口语义（`greader_compat_e2e.rs:517`）。叠加确认的 5 项高危缺陷（Miniflux 星标翻转、quick_add 跨重启卡死、空 link 跨源塌缩、GR 身份桥接缺口、smartDedup 计数 155s/次）与一批 P2，用户指令明确：先修门禁、再动源码、稳定收敛、防无限修复。前一轮收敛路线见 [核心一致性重构路线](../../implemented/architecture/2026-10-05-核心一致性重构路线.md)，其"政策单点 + 事务守卫"底座保留，本篇只规划本轮缺陷收敛，不推翻该路线。

## Proposal

三阶段波次推进，每阶段有独立验收，固定范围防扩散：

1. **阶段 A（门禁对齐，可与任何源码修复并行派发前完成）**：只改 `src-tauri/tests/**` 与 AGENTS.md 门禁表，不改 `src/` 与 `src-tauri/src/`。四类替身语义修正为真实服务端语义；受影响旧用例按真实语义重写并保持 CI 绿（凡当前源码行为本就正确的重写后仍绿；当前源码行为错误的场景不进本阶段）。AGENTS.md「本机已可链接」更正为实测不可链接、cargo test/clippy/check 由 CI 承担（每项检查仍有承担者）。落地与契约见 [测试替身对齐真实服务端语义](../../implemented/testing/2026-10-31-测试替身对齐真实服务端语义.md)。
2. **阶段 B（源码修复，红门禁与修复原子提交）**：固定清单为 B1 Fever 推送语义（星标判向 + quick_add 跨重启收敛，含其红门禁）；B2 拉取侧（GR read/starred 集合的 contents 回补、`fever_pull` 本地已有正文预过滤、url_norm 空串规范化、F1 计数查询改写 + EXPLAIN QUERY PLAN 计划断言，落地见 [GR 回补与拉取侧身份/性能修复](../../implemented/bug-fix/2026-10-31-GR回补与拉取侧身份与性能修复.md)）；B3 前端（计数陈旧落地窗口 + P2 标题截断 + 画廊加载占位，落地见 [B3 计数落地写结算判据与窄列/画廊视觉修复](../../implemented/bug-fix/2026-10-31-计数落地写结算判据与窄列视觉修复.md)）；B4 安全横向（`get_setting` 敏感键过滤、AI body_text 剔除 script/style）。每项同批交付 implemented Note 与受影响文档同步（sync-compat-matrix、performance.md、roadmap.md）。
3. **阶段 C（收敛审计）**：每轮审计代理全新开辟（不复用），对固定清单逐项证伪复核 + CI 证据核对；清单外新发现只登记 `docs/roadmap.md` 不修。

派发纪律：编程代理视上下文复用（门禁代理顺延承接 B1，其已持有 Fever 夹具上下文）；审计代理必须新开；不频繁催促，等待完成通知。

## Alternatives considered

- **直接修源码、门禁后补**：见效最快，但这正是本轮审计暴露的失败模式——门禁继续锁定错误语义，修复无法被证伪，必然反复回归。否。
- **全部缺陷交一个代理大爆炸式修完**：无并行收益，上下文必膨胀，写冲突面最大。否。
- **红门禁先推送 dev、源码后补**：dev CI 长期红违背稳定收敛；改为红门禁与对应修复同批原子落地。否。
- **只修 P1、P2 留待下轮**：计数窗口与标题截断是已实测复现的用户可见缺陷，留着必然再开一轮；纳入 B3。P3 与美观批次（对比度、aria、焦点陷阱、ErrorBoundary）本轮不做。

## Acceptance criteria

- 阶段 A：origin/dev CI 全绿；全新审计代理对照真实服务端源码证据确认四类替身语义一致；AGENTS.md 门禁表与实机能力一致。
- 阶段 B：固定清单每项 = 源码修复 + 同批 implemented Note + 配对门禁转绿 + CI 绿 + 文档同步。
- 阶段 C：全新审计代理逐项复核通过、无新增高危；`docs/roadmap.md` 登记本轮不做项；本篇转 `implemented/process/`。

## Risks

- 本机无 MSVC 链接器（三轮独立实测确认），Rust 侧验证只能走 CI 往返，单轮修正周期长；门禁语义修正可能牵出连锁红夹具（如 `pull_window_e2e` 的 published==changed 恰好掩盖分歧），需逐个按真实语义重写。
- 红门禁与修复同批提交会增大单提交体量；B1/B2 拆分为独立提交序列缓解。
- 并发名额有限（实测上限 5-6），波次内并行度受限，按互不重叠写域分组。
