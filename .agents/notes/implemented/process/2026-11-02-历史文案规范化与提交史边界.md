# Agent Note: 历史文案规范化与提交史边界

Status: implemented

## Problem

用户要求遍历全部 commit 与 Release 文案并规范化重写，同时重写 README。全库 511 个提交中 42 个不合 `<type>(<scope>): <中文主题>` 约定（全部集中在 v0.13 之前与 workflow 英文时代），但 docs/release.md 明文「历史提交哈希不重写」——重写提交史会作废全部 28 个 tag 与 Release 的 SHA 溯源（2026-09-16 的一次历史重写已付出提交号对照代价，roadmap §七有载）。

## Decision

1. **Release web 正文全量规范化**：v0.8.0–v0.16.2 与 v0.17.0 共 19 版按 docs/release.md 附注结构重写并经 `gh release edit` 写回——素材仅取 tag 附注、提交范围（`git rev-list --count --no-merges` 实测提交数）与旧 web 正文，无门禁证据的版本不写门禁数字；每版文末保留溯源注（重构来源与原 web 正文性质，v0.11.0/v0.12.0 的原正文为早期手写而非静态模板，v0.16.1/v0.16.2 已是手写规范正文只做归一）。v0.17.1–v0.18.7 已合规不动。
2. **提交史不重写**：42 条不合规范提交保持原样，作为历史记录保留；此后提交遵循约定（现状即合规）。
3. **README 重写**：面向用户为主贡献者其次的标准结构（定位/功能七组/安装/快速开始/开发/项目文档/License），剔除全部内部决策口吻；「读状态与收藏双向同步」的过度宣称改为中性表述并指向兼容矩阵。

## Alternatives considered

- **强制重写提交史（filter-repo/rebase）**：会作废 28 个 tag、触发 Release 工作流对旧 tag 的重构建、破坏 Note 与 roadmap 中的 SHA 引用，被 docs/release.md 成文规则直接排除。
- **重打历史 tag 附注使其与新版 web 正文一致**：同样触发 Release 工作流重构建并覆盖既有资产（docs/release.md 明文禁止），不采。
- **旧版 Release 正文原样保留**：与「文案规范化」目标冲突，且 docs/release.md 本就载明了修正旧版本 web 正式的既定命令，采编辑而非重打。

## Consequences

- 收益：28 个 Release 的 web 正文全部符合统一结构且事实可溯源；README 成为面向外部读者的标准仓库首页；提交约定现状（436/478 非 merge 合规）与 42 条历史例外有明确登记。
- 代价：v0.13.0–v0.14.0 的正文由提交范围重构，粒度依赖当时提交信息的质量；早期版本无门禁数字可考，验证面留白。
- 边界：tag 附注原文未动（不可变）；web 正文与 tag 附注在旧版本上允许分叉，分叉事实由溯源注声明。
