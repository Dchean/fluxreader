# 提问、补充信息，再确认执行

每轮最多三个短问题。先问一件明确的事，再给少量可理解的选项、推荐理由和影响，最后允许用户补充或修改。宿主支持选择题和自由补充时使用对应入口；不支持时用短文本。不硬编码厂商的问答工具名，不把整份配置表交给用户。

推荐项是建议，不是默认同意。用户之前明确表达的意向和授权可以直接引用；没回答、等待超时、工具已安装、旧文档的执行器都不是新决定。技术事实由 Agent 检查，在已确认边界内的日常实现选择自行处理。

## 第一轮：意向与目标

先只读辨认目录及 README，确认是新项目还是已有项目。已有项目在深入分析前先问重构意向；用户已说清时直接沿用。

> 对这个项目，你希望先评估再由你选方案、先解决具体问题，还是已经决定重构？
> 补充：可以说明当前痛点或近期计划；不知道技术原因没关系，我会检查并解释建议的收益和代价。

保存 refactor.intent：assess（先评估）、targeted（解决具体问题）、refactor（已决定重构）。kind=refactor 只表示已有项目，不代替用户意向。意向未确认时，start/next 优先给出该问题。

新项目先问用途、目标用户和第一条核心使用流程。已有项目补问实际痛点、近期计划和必须保留的行为，不默认套用“第一版做什么”。不要让零基础用户填写语言、数据库版本或 Git 状态。

明确补问：“除了已说明的目标，还有哪些现存 Bug、想增加的功能或其他要求？”允许回答暂无、补充，或先由 Agent 排查。Bug 补触发条件、实际/期望结果和影响；功能补用途与优先级；其他要求包括数据、平台、使用习惯和不能改的部分。未知技术原因由 Agent 调查，不要求用户先给定位结论。

requirements 是统一需求清单，Agent 填写 id、kind（bug/feature/improvement/constraint）、description、in_scope 和 acceptance。用户已确认的主目标与补充项一并归入清单；暂缓项 in_scope=false，不静默丢弃。没有补充也记录实际回答，不能把空数组默认成用户说过“没有”。后续发现的新问题按当前范围判断，实质扩展先提问确认。

按 [BOOTSTRAP](BOOTSTRAP.md) 完成已选择的工作流接入，再按 [REFACTOR](REFACTOR.md) 做针对性分析。记录实际证据、推荐路线和代价，然后以提问方式请用户选择：仅评估、保持现状、局部修补、渐进重构或替换迁移。分别保存 assessment 和 refactor.decision，不能把 recommendation 自动当作用户决定。选择仅评估/保持现状时 code=false，不制造编码任务。

只有用户明确仅参考方法时才不接入，并如实标注；没有调用本包的普通小修复不强行升级为完整流程。

## 检索参考

需求大致明确后按 [RESEARCH](RESEARCH.md) 检索。把有价值的现成方案呈现给用户，说明可减少哪些工作、有哪些限制，再完善需求。不要在产品尚不清楚时就下载大仓库或选定技术栈。调研结果不代表实现方案已经获准。

## 第二轮：范围、界面与交付

默认以可维护、稳定和性能为优化目标，不以少写代码、少花工时或快速交差决定方案。先规划完整目标，再把实施分成可验证阶段。避免过度工程化指的是不增加无必要的依赖、抽象、服务和维护负担；有证据收益的必要重构即使工作量大也应提出。

补齐 quality：maintainability、stability 的可检查目标，以及 performance 的负载与目标。用普通语言询问常用设备、数据规模、并发/离线场景和不可接受的卡顿/故障，技术指标由 Agent 检查后提出。性能相关时 mode=measure 并填 workload/targets；不影响运行性能时可 not_applicable，但必须有 rationale。不能把“最好、最快”直接当成已验证事实。

确认必须有的功能、优先级、暂时不做的部分和可观察的验收标准。重构额外确认保留的接口、数据、行为和 UI。只评估时，验收对象是有依据的建议及其适用范围。

用户说“重构”但同时改变功能时，先给新旧行为对照，再提问补齐未决项。例如“原先按发布时间排序，你这次希望默认按未读优先，对吗？补充：这会改变原排序测试的预期，其他筛选行为仍保留。”需求已明确就直接引用。Agent 据此按 GATES 分析旧测试和门禁、决定必要的新测试，不让用户逐条选择断言。

有界面时，以提问确认风格、目标设备和推进方式。Agent 推荐一套方向及相应 ui.mode：新界面/明显改版推荐 preview_first，局部维护推荐 existing，无界面为 none。用户选择后保存，已有明确要求直接沿用。style_intent 和 target_devices 不能为空；无界面项目可依据已确认范围标记不适用并说明原因，不必追问配色。

按 [FRONTEND](FRONTEND.md) 先展示可点击预览，确认控件展开、弹窗、焦点、报错和目标设备效果，再接入真实功能。用户不用先选 CSS 库或组件版本。UI/UX 与视觉审查职责明确，仍可由三个执行单元承担。

补齐交付方式：本机运行、安装包或部署目标。delivery.external_services 标记 none / sandbox / production；需要真实外部服务时，补问具体服务、账号/数据的读写边界和可能费用，保存 data_boundary。不要索取密钥写进文档。没有外部服务时跳过该轮问题。

## 第三轮：执行与自动推进

必须明确提出执行方式问题，不能只介绍能力：

> 编程由当前 Agent 全部处理，还是让它调用 CLI 协作？
> 补充：个人项目可先选 Agent 全部处理；CLI 可分担编码或审查，但需要本机可用，并可能增加配置和调用费用。可以指定工具，也可以先听我的推荐。

答案保存为 execution.mode=agent_only 或 agent_cli，并确认实际 coder/reviewer。选择 CLI 后补齐具体执行器及分工，再核验能力。宿主名称、已安装的 codex/claude、旧角色文档都不能代替这次选择。工具不可用时给出调整选项，不静默换执行方式。

审查安排也要明确，和是否使用 CLI 是两个独立选择。Agent 包办时，如果宿主有未参与实现的新上下文，可以由同一模型或另一个 Agent 独立审查；具备能力时优先推荐。无此能力且用户选择自审时，使用真实测试加五项有证据的检查。高风险任务仍要求独立审查；不能同一上下文改名字冒充独立。

用一份短摘要确认时间、修复上限、费用和自动推进边界，不逐项询问内部参数。推荐每任务修复 3 轮、90 分钟、每批 3 个任务、单写入者；默认短时网络退避 5、15 秒，CLI 单次上限 600 秒。展示实际准备采用的数值，让用户接受或调整。

这些是防止死循环和未知消费的运行上限，不是项目工作量上限。较大工作应在完整目标下分段验证与接续，不能因单轮额度不足就降级验收。额外费用和权限仍按实际授权处理。

明确要求在已确认范围自动推进、且不设工具额外美元上限时，可将 batch_rollover 保存为 allowed；其他情况用 ask。“不确定费用”不能写成不限额，none 也不表示免费。权限、费用或耗尽预算需要新决定时，给出具体已完成内容和下一步选项。

代码、依赖、CI、提交、推送和发布分别沿用已有授权，只补未知边界。不涉及的动作可保持 ask，到需要时再具体询问。接入不授权业务改造，计划部署也不自动授权正式发布。

retry_safe 由 Agent 检查任务和门禁的重复执行语义后决定，不让用户替工具证明安全，也不能把有真实副作用的任务标成可重复。恢复边界见 [RECOVERY](RECOVERY.md)。

## 保存答案与最后核对

简短展示目标、范围/优先级、验收和交付、非目标、参考、兼容性、UI、执行/审查、预算、操作边界及未决问题。一次“按这份摘要执行”可覆盖摘要中明确列出的多项选择，不能覆盖未展示的默认项。已有答案不重复问。

Agent 使用 .workflow-kit/tasks/templates/BRIEF.json 准备答案，分轮用 intake --file ... --write 保存到 .workflow-kit/tasks/BRIEF.json，未答完也能保存。intake 不带 --write 只审计；start/next 返回缺项和下一轮最多三个问题，齐备后才返回 onboard。问题仍由当前 Agent 提给用户，脚本不启动新聊天窗口。

每个已确认主题在 confirmations 保存 status=confirmed、实际 answer 和 source。技术建议用 proposed，不批量伪造“用户已同意”。下面只是字段形状，真实项目必须替换为实际回答与来源：

~~~json
{"confirmations": {"execution": {"status": "confirmed", "answer": "由当前 Agent 全部处理", "source": "实际用户消息的引用"}}}
~~~

工具自动把确认与对应数值绑定。预算、执行器或范围后来改动时，旧 value_digest 不会自动更新，该主题重新变为待确认。只有收到新的适用回答，才替换该主题的确认记录（不手填摘要）；其他已答内容继续沿用。保存草稿不授权业务工作。onboard --source 在必要答案齐全后记录最终确认，缺执行选择、回答来源或重构路线会被拒绝。

仅无界面 ui 主题允许 status=not_applicable，必须有 reason 且 ui.mode=none。外部服务为 none 时不要求 services 确认；需要 sandbox/production 时必须有 data_boundary 和对应真实回答。

有旧流程时先完成 legacy_review：已读路径、保留约束、旧任务处置与当前角色由 Agent 核对。实质冲突用“提问＋补充”交用户选择；冲突未解决时不能开启代码权限。不要把总控错当成旧文档中的 Worker。

已经 onboard 的项目不重新开始问卷。范围或执行方式确需改变时，追加适用用户决定及更新后的 confirmed_brief、BRIEF、POLICY.intake.decision_id 和授权引用，保留旧决定/任务/预算，只更新变动主题的确认，见 [DECISIONS](DECISIONS.md)。

产品事实默认集中在 .workflow-kit/docs/PRODUCT.md，BRIEF 是确认快照。技术取舍复用已有 ADR/Notes，不再机械抄到 Memory。

按 [PRESENTATION](PRESENTATION.md) 在对话中展示阶段目标、任务进展、未拆分需求和下一步。有真实原生任务工具就同步，没有则直接显示卡片；保存文件不等于完成用户展示。

## 开始前的漏问检查

| 主题 | 需要补问的情况 | 可复用或不必问的情况 |
| --- | --- | --- |
| 重构意向与路线 | 已有项目意向未知；分析后的路线尚未选择 | 已明确目标与试点不重复证明 |
| 目标、范围、验收 | 用户、优先级、完成标准或非目标有空白 | 技术目录等可在边界内检查推荐 |
| Bug、功能和其他补充 | 已有问题、新增能力和其他诉求未明确收集 | 暂无或先排查也可回答，已有内容直接引用 |
| 质量与负载 | 维护、稳定和性能目标无法验证，负载/设备不明 | 技术指标由 Agent 提案；不为无运行影响的改动强造基准 |
| 兼容与数据 | 既有行为、接口、数据、UI 将受影响 | 新项目不编造兼容性问题 |
| UI 与设备 | 界面方向、保留范围或预览安排不明 | 无界面有依据地标记不适用 |
| Agent / CLI 与审查 | 执行方式、具体工具或审查独立性未选 | 当前目标适用的真实回答沿用 |
| 预算与自动推进 | 时间、修复/恢复上限、费用、续批方式不明 | 数值合并展示确认，不逐项考试 |
| 操作边界 | 代码、依赖、CI、提交、推送、发布权限不明 | 已授权的工作直接推进，未涉及发布可保持 ask |
| 使用与交付 | 本地运行、安装包或部署目标未知 | 不为本地工具询问云服务套餐 |
| 外部服务与真实数据 | 需要账号、外部服务、生产读写或迁移 | 本地无外部服务不追加这轮 |
| 旧规则冲突 | 原业务限制与本次目标/角色实质矛盾 | Agent 核对文档，只交用户决定未决取舍 |
