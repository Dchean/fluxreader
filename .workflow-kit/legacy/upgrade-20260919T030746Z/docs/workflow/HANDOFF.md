# 接手、恢复与分发

1. 先定位目标项目并核验接入回执；按其中入口与状态路径读取 AGENTS、PROJECT、POLICY、DECISIONS、批次和任务。不能凭旧文件同名猜测当前工作流。用户新指令优先，保留旧业务约束，明确流程冲突。
2. 检查 Git、当前快照和所有未提交文件；不能用冻结 SHA 重置工作区。哈希清单只能核对变化，恢复源码需要实际代码副本、补丁或相应 Git 版本。
3. 扫描 `.workflow-kit/tasks/runs/` 中所有当前 task_id 的记录，与 task.run_ids 核对；再检查引用的原始执行器输出和候选。缺一个最新汇总不代表过去从未执行。
4. 验证真实进程是否仍在运行。锁、PID 或 run 的 running 字段过期时先辨认进程，不能接手就启动第二个写入者，也不能终止不属于本任务的进程。
5. 重新核对已有候选与验证证据。能接续的就继续验证；相关代码变了才重跑受影响检查，不为证明“是我做的”而回退重做。
6. 保持原 task_id、首次开始时间、原截止时间、修复轮和批次历史；必要时依据新决定用 extend 追加额度。start/next 会区分活动运行、孤立锁和预算耗尽，不靠某个 CLI 的 --last/--continue 自动猜会话。
7. 在既有授权和剩余预算内继续；缺失必要事实再提问。结尾说明当前版本、已做/未做、证据、阻塞和下一允许动作。

有未结束 RUN 时用 recover --run --source；只剩孤立控制器锁时可省略 --run。先确认所有相关进程退出，不能因为控制器已结束就忽略仍运行的子进程。已经记录为网络失败的运行不需要重复 recover；核对现场、排除阻塞后直接继续原任务。验证/审查中断优先恢复验证，避免重新编码。

恢复后先给用户展示 progress：当前阶段目标、原任务、已完成与未完成、阻塞和下一步。requirements 中未拆分的 Bug/功能仍保留；不能只恢复已建任务而遗漏完整目标，也不能只在文件里更新状态。

## 移交清单

携带需求、架构、策略与实际批准、唯一任务记录、所有相关尝试、候选差异与安全快照、工具版本及必要的脱敏日志、未决问题和下一步。便携的是协议和证据，不是电脑用户名、全局 CLI 设置、秘密或依赖缓存。

不要直接打包整个项目目录、用户主目录或 .cache。用明确允许清单，排除真实数据库、账号、token、.env、私钥、会话认证和构建依赖；附文件哈希。原始日志如果含敏感内容，只移交脱敏副本和受控原件引用。

新环境核对路径、依赖与权限；旧环境的 PASS 仍是历史证据，不能假称新环境已运行。保留真实时间与环境信息，缺少凭据时请用户在相应工具里完成配置，而不是复制进文档。

## 重要决策

复用目标项目已有 ADR/Note 系统。每个重要决定记录问题、选择、替代方案（含不做/复用的最强理由）、后果、验证和真实批准依据。提案、接受和已实施分开；替换旧决定时说明取代关系，维护一个有效归属。

没有已有体系时，使用 .workflow-kit/docs/ADR/ 的轻量模板即可；不要求同时维护 ADR 与另一套 Note。若启用特定 Note 技能，按其合法分类和生命周期执行，不自行发明校验器不支持的类别。
