# TASK-047 实施报告：关闭态浮层不可聚焦（inert）

**性质**：可访问性修复（B-3）。**结论**：契约 §4 的 8 条验收标准**全部实测成立**。

## 0. 证据边界（先声明）

- 全部证据来自**真实 Tauri WebView2**，经 CDP（`Input.dispatchKeyEvent` / `Runtime.evaluate` /
  `Page.captureScreenshot`）驱动：**未注入系统级键鼠、未抢占用户焦点**（用户在用屏幕 A）。
- 测试数据经 Vite 模块图 `setState` 注入，**纯内存**；用户库实测仍 `feeds=0 / folders=0 / articles=0`。
- 未覆盖项见 §5，不冒充通过。

## 1. 改动（2 个文件，各加一处 `inert`）

| 文件 | 改动 |
| --- | --- |
| `src/components/primitives.tsx` | `ModalOverlay` 根节点加 `inert={!open}`（含注释说明为何必需） |
| `src/components/Overlays.tsx` | `Lightbox` 根节点加 `inert={!lightboxUrl}` |

**根因**：这两个浮层**无条件渲染** children，关闭时只摘掉 `.open` 类名；
而 `.modal-overlay` 关闭态只有 `opacity: 0; pointer-events: none`（`base.css:1962`），
**不改可聚焦性**，故关闭后内部控件仍被 Tab 命中。

**未改**：`ConfirmDialog`（`primitives.tsx:279` 已 `if (!open) return null`）与
`ContextMenu`（`ContextMenu.tsx:77` 已 `if (!menu) return null`）本就条件渲染，无需改动。

按契约 §3.1 **刻意不实现 focus trap**（不在打开时把焦点困在浮层内）——那会改变既有交互习惯。
由此产生的既有局限见 §5.1。

### 2.1 消融对照（证明 `inert` 就是生效点）

同一状态、同一遍历方法，三次走满一圈（数字取自重生成的实机日志）：

```
[有 inert]                     停靠点 32（主视图 32），浮层内 0，不可见 0
临时移除 8 个节点的 inert 属性 → [移除 inert] 停靠点 69（主视图 32），浮层内 37，其中 37/37 有效不透明度为 0
还原 8 个节点的 inert 属性     → [还原后]     停靠点 32（主视图 32），浮层内 0
```

即：**移除 `inert` 后关闭态浮层控件立刻重新进入 Tab 序列（37 个，且全部位于不可见区域），
还原后再次消失**——证明改动确实改变了行为，而非环境差异。可复现。

**关键点：主视图停靠点在两态下同为 32**——差异**全部**出现在浮层内（0 ↔ 37）。
这既证明 `inert` 是唯一生效点，也证明本次改动**没有增删任何主视图停靠点**（验收第 8 条）。

> **更正说明（审查 finding 02）**：本节初版写「有 inert 31/0、移除 inert 27/1、还原 31/0」，
> 并把「主视图 31 vs 26」解释为「动态内容浮动」——**那是错的**。
> 真实原因是我的遍历脚本有缺陷：把元素标记写成 JS 属性却用属性选择器清理，清不掉，
> 于是新一轮遍历计数器重置后与旧标记**撞号**，遍历被误判为已绕回起点而**提前终止**。
> 这既低估了效应量（1 vs 真实 37），也伪造了「主视图在变」的假象（真实两态都是 32）。
> 独立审查者在同一候选上测得 33/0 与 70/37、主视图同为 31，与本日志 32/0 与 69/37、
> 主视图同为 32 属**同量级差异**（主视图停靠点随同步状态胶囊等动态内容小幅浮动）。

## 4. 实施过程中的返工（留痕）

1. **第一版验证脚本误判第 2 条**：遍历的循环判定写成「连续两个停靠点同类名即视为循环」，
   而设置弹窗的 7 个导航项类名相同（`settings-nav-item`）→ 遍历在 4 步后提前终止，
   报出「浮层内 0 个」。改为**用稳定元素身份**（首次聚焦时打唯一标记）后才正确。
   **这是脚本缺陷，不是应用缺陷**——我先用独立调试脚本（直接读 15 次 Tab 的落点）确认
   应用侧 15/15 都落在浮层内，才回头修脚本。
2. **第二版仍误判**：把遍历上限设为 30，而弹窗是 portal 渲染在 `<body>` 末尾、
   主视图有 32 个停靠点 → 30 步内根本走不到弹窗。提高到走满一圈后得 20/20 通过。
3. **删掉两张名不副实的证据图**：首轮产出的 `TASK-047-01-closed-tab-walk.png` 与
   `TASK-047-02-settings-open-focus.png` 出自有缺陷的遍历（后者拍到的是「Tab 还没进浮层」的画面），
   已删除；保留的两张经目视核对内容真实。

## 5. 未覆盖 / 已知局限（不冒充通过）

1. **未实现 focus trap（按契约 §3.1 刻意不做）**：弹窗打开时**背景未 inert**，
   实测需先经过 **25 个主视图停靠点**才轮到弹窗内控件（浮层 portal 渲染在 DOM 末尾；
   该数值随动态内容小幅浮动，独立审查者测得「全部 31 个主视图停靠点都排在浮层内控件之前」，方向一致）。
   即键盘用户可用 Tab 走到弹窗背后的主界面。这是**既有行为**，本次只修「关闭态不可聚焦」，
   不扩大范围。若要一并解决，需另立任务明确「打开时背景 inert 或焦点陷阱」的交互语义。
2. **浅色主题未核对**：`inert` 不产生视觉变化，但浅色下焦点环样式本轮未复测。
3. **未做右侧栏/其他布局的全布局遍历**：第 1 条在全关态下覆盖主视图，但未对
   社交/画廊/播客三种布局分别各走一圈。
4. **未跑冷编译**：`npm run build` 命中 Vite 增量，但产物确实重建（`index-*.js` 更新）。
5. `tools/frontend-regression.mjs` 对可聚焦性**不能提供证据**
   （grep `focus|querySelector|tabIndex|role=` 命中 0），故第 2–8 条完全依赖本报告的实机证据。
