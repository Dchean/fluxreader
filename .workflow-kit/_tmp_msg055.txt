fix(sync): TASK-055 修墓碑误清除导致已删订阅被 pull 复活（P1）

缺陷
- sync::unsubscribe_remote 把 HTTP 2xx 当作「远端已确认退订」，据此
  db::remove_feed_tombstone。而该 Ok 来自 greader::post_form_text，判据只有
  resp.status().is_success()——看不到响应体。真实 GReader/MiniFlux 兼容后端在
  token 失效、权限不足或 s=feed/<id> 不存在时可能返回 2xx + 错误体。
- 墓碑是 pull_feeds 防复活的唯一防线；一旦被误清而远端仍列出该订阅，
  已删订阅会被重新建回本地（用户现象：「删掉的订阅自己回来了」）。
- 既有测试漏掉的原因：deleted_feed_stays_deleted_and_unsubscribes 只覆盖正常路径
  （mock 确实把订阅从远端列表移除），且其旧断言「2xx 后墓碑应清除」正是在断言
  这个过宽判据本身。

改动（4 文件）
- src-tauri/src/sync/subscriptions.rs：删除该清除点；重写文档注释说明返回值语义
  （仅表示请求被后端接受，不等于远端已删除）。墓碑清除条件收口为唯一一处——
  pull_feeds 中「远端订阅列表实际已不含该 URL」（读响应体，唯一有证据的判据）。
- src-tauri/src/commands/folders.rs：更新调用处注释（不再声称成功即清墓碑）。
- src-tauri/tests/mock_greader.rs：新增故障注入 unsubscribe_returns_2xx_without_removing
  （置位后退订回 200 但保留订阅），仿既有 fail_stream_ids 写法。
- src-tauri/tests/sync_gap_repro_e2e.rs：新增复现测试并适配 A-1 的过时断言。

验证
- fail-before/pass-after 均已证明：回退修复后新测试 exit 101 失败
  （panic「2xx 但未确认远端已删除时，删除墓碑必须保留」），还原后 exit 0 通过。
- A-1 断言适配为增强而非削弱：原「墓碑应清除」检查移到远端确认移除之后，
  该测试墓碑断言由 1 条增至 2 条；其余三组断言与 HEAD 逐字节相同。
- 同类路径核对：目录墓碑判据取自远端 tag/list 的实际 label，与 2xx 无关，无同类缺陷。
- 门禁：cargo test 137 passed/0 failed/9 ignored（=136 基线+1）、lint 0/0、
  build exit 0、frontend 241/241。
- 独立审查 PASS：审查者自行复现 fail-before/pass-after 各两次（强制重编译），
  并独立枚举全仓清墓碑调用点确认已无任何以 2xx/Ok 为依据的清除点。

协议影响：不改任何对外请求的内容与顺序，只改收到响应后的本地处理。
