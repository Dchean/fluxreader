# UI 契约：TASK-058（同步失败对用户可见）

目标设备：Windows 桌面端（Tauri）。UI 模式：existing（沿用现有布局与交互习惯，**不改版**）。
范围：**同步结果提示**（设置 → 同步 的「保存并同步」后台链；侧栏「刷新全部订阅源」的手动同步链）。
其余区块与控件不得改动。

## 背景（已实证）

TASK-056 让后端把 pull 失败写入 `SyncReport.errors`，但**前端没有任何代码读取该字段**。
端到端实测（测试库触发器注入真实插入失败）：

```text
后端返回：{"pulled_feeds":0, "errors":["拉取订阅 …/uncat.xml 建本地失败: [db] e2e injected insert failure",
                                      "拉取订阅 …/cat.xml 建本地失败: [db] e2e injected insert failure"]}
界面提示：「后端同步完成」        ← 用户看到成功、数据零进来
```

根因：`phases.rs` 在 errors 非空时仍返回 `Ok(report)`（有意设计：单项失败不中断整链），
故 `.catch()` 永不触发；两处调用点都丢弃了 report。

## 需要核对的状态

### A. 失败可见（核心）

1. **保存并同步链**（设置 → 同步 → 「保存并同步」）：后端返回非空 errors 时，
   最终提示**必须**明示「有 N 项失败」，**不得**再显示为纯粹的「后端同步完成」。
2. **手动同步链**（侧栏「刷新全部订阅源」）：同上，必须消费并呈现 errors。
3. **错误明细可获知**：不能只给一个孤立数字——须能看到**具体原因**
   （至少首条原因，或可展开/可复制的明细）。
4. **不覆盖既有失败信息**：手动同步链末端已有「已刷新，新增 N 条，M 个源直连失败」；
   当同时存在同步 errors 时，两类信息**都要出现**，不得互相吞掉。

### B. 成功路径不变（防回归）

5. **errors 为空时，既有文案逐字不变**，且顺序不变：
   - 保存链：`已连接：<user>（N 个订阅）` → `已拉取订阅源，正在同步文章状态…` → `后端同步完成`
   - 手动链：`订阅同步完成，正在同步文章状态…` → `已刷新，新增 N 条` / `已刷新，无新文章`
6. **既有按钮状态不变**：`测试连接` / `保存并同步` 的禁用态、加载态（`testing`/`saving`）不受影响。

### C. 视觉与主题

7. **深色主题**：失败提示完整可读，长文案（含原因）不截断、不溢出。
8. **浅色主题**：同上。
9. **窄窗口**：提示换行正常，不撑破容器。
10. **形态一致**：沿用既有 `showToast` 与既有 toast 外观，**不新造控件或弹窗**；
    若提供「查看明细」入口，须复用既有交互（如 toast 的 action 按钮）。

## 明确不改

- **不改 Rust**（`src-tauri/**` 零改动）：后端已在 TASK-056 上报，本任务只做前端消费。
- **不把 errors 非空改成抛错**：`Ok(report)` 语义是有意的（单项失败不中断整链）。
- 不改成功路径文案与顺序。
- 不改本范围之外的任何设置区块或侧栏控件。

## 验证方式

- 代码层面：`npm run lint`（0 警告）、`npm run build`、`npm run test:frontend`
  （既有 255/255 不回归 + 本次新增断言**修前失败、修后通过**）
- **端到端（本契约要求必做）**：用真实运行的应用 + 本地 GReader 协议服务端，
  注入真实插入失败，实测**界面出现失败提示**，并给出实际 toast 文本
- 证据：深/浅主题实机截图（非设计稿）+ 交互报告说明操作路径与观察结果
- 复查：独立上下文审查核对 diff 与上述状态的可实现性，并验证成功路径未被改动
