# 真实验证与审查

按项目技术栈和改动风险定义具体命令，不从其他项目照搬 npm/cargo/pytest。记录每项适用性，代码 → 可信命令 → 原始结果 → PASS / FAIL。不存在的测试不能标 SKIPPED 来伪装覆盖，应登记 NOT_RUN / 缺口并安排补齐。

| 类别 | 能证明什么 | 不能代替什么 |
| --- | --- | --- |
| 格式 | 按选定格式规则一致 | 逻辑正确 |
| 类型/编译 | 静态类型与编译约束 | 业务行为与运行环境 |
| 静态分析/lint | 已启用规则下的问题 | 所有错误、安全保证 |
| 单元测试 | 单个行为及边界 | 模块协同 |
| 集成/契约测试 | 数据、接口、协议与模块协同 | 真实 UI 和所有外部服务 |
| E2E | 指定环境中的完整用户路径 | 未覆盖的平台与业务情形 |
| 构建/安装 | 目标产物可生成、必要时能安装启动 | 发布批准、运行期质量 |
| 回归 | 已知问题或关键行为不会在这些情形复发 | 永久无 Bug |
| 架构/代码审查 | 边界、可维护性、测试有效性与改动范围 | 自动工具或实际验收 |

PASS / FAIL / NOT_RUN / SKIPPED / BLOCKED / NOT_APPLICABLE 分别报告。没有执行就不写 PASS；环境阻塞不直接称为产品失败；本地通过不等于托管 CI 或目标平台通过。

## 先判断旧检查是否仍然适用

“选择重构”不让原有测试自动失效。先区分保持既有行为的结构调整，以及新增、改变或删除产品行为；按已确认需求判断测试，不能只根据当前实现或失败结果改断言。

基线记录旧版本做了什么，不证明那就是现在应该做什么。旧测试可能固化旧需求或错误行为；以当前有效需求和仍需保留的兼容/安全约束确定预期，不能让遗留实现反过来覆盖用户的新目标。

盘点受影响的测试、门禁脚本、CI、fixture/mock、快照、构建和数据迁移检查。优先按业务路径或测试套件分组，不逐个用例建卡，也不默认全项目重写。

| 处置 | 适用情况 | 实际要求 |
| --- | --- | --- |
| keep 保留 | 测试仍保护当前需求、兼容或安全边界 | 继续运行，保留原判定标准 |
| adapt 适配 | 行为不变，测试依赖旧路径、内部接口、mock 或实现细节 | 调整入口/夹具，或换成能证明相同行为的测试；不能顺便弱化契约 |
| replace 替换 | 用户已确认的新行为与旧断言冲突 | 引用对应需求决定，用新断言及相关回归替代 |
| retire 退役 | 用户已确认删除该行为，旧检查已无业务对象 | 记录移除的覆盖和理由，其他仍有效检查继续执行 |
| add 补充 | 新需求/边界未覆盖，或重构前缺少必要保护 | 补行为、接口、迁移或交互测试；不为覆盖率和形式新增测试 |

旧失败、环境阻塞与未运行另记为基线事实。它们不自动证明测试过时，也不自动成为本次修复目标。保留原命令、输出和输入版本，说明新门禁怎样区分已知失败与新增回归；不能只忽略退出码或把失败改写为 PASS。

Agent 在 prepare 前填写任务 test_review：行为是否变化、原始基线证据、测试处置与有效门禁的映射。已有项目的业务/CI/UI 任务需要该记录，纯文档或基线采集任务可先进行。新项目通常复用常规 gates；需求变化或调整前序门禁时也用 test_review。

修改业务期望须引用覆盖该任务或需求的真实用户决定；一般“允许重构”不代表允许删除业务保护。已有明确回答直接引用，不为改一个测试再次审批。技术适配和补测试由 Agent 在既有授权内处理；发现业务冲突时，用“提问＋补充”询问新旧行为怎么选，不让用户判读测试代码。

默认继承前序必需门禁。确需适配、替换或退役时，actions 用 from_task/from_gate 指明原门禁；适配/替换必须映射到本任务的有效必需门禁，退役须有相应需求决定。没有这份记录仍继承旧门禁；未涉及的检查与历史结果保留。命令相同但测试内容改变时，也要审查断言语义，脚本不能自动证明等价。

任务开始前冻结这份计划。运行后发现测试与需求冲突时，保存失败并交总控重新核对范围；不得在自动修复轮中删断言、重写基线或改门禁给自己放行。原任务预算与历史继续保留。字段示例见 [TOOLING](TOOLING.md)。

## 界面质量

UI 变更同时检查实际视觉和交互。构建、lint 和单元测试不能证明下拉菜单、弹窗或默认控件与整体一致。按 [FRONTEND](FRONTEND.md) 维护一份 UI 约定，检查真实组件的展开、焦点、禁用、错误和响应式状态。

ui_change 任务的 PASS 要有对应当前候选的截图与交互报告，ui_review.checked_states 覆盖 ui_checks。工具保存这些证据的摘要，改动后不能沿用旧审查。新界面预览还须由用户实际确认，再进入真实功能实现；预览通过不代表后端或数据流程通过。

## 把 Bug 变成保护

Bug → 编号与复现 → 有效回归证据 → 修复 → 验证。尽量证明修复前失败、修复后通过；已有有效测试可以引用。保留仍然有效的行为保护；需求确实改变时通过需求变更记录更新测试，而非承诺所有历史测试永远不能变。

非确定问题记录触发条件、观测和复跑策略；不能为了“每个 Bug 一个测试”编写总是通过的断言。无法自动化时给出可重复的人工验收、原因与未来补齐条件。

## 证据绑定

使用本次任务的输入快照与最终候选摘要。快照选择相关源码、测试、锁文件与构建配置；额外保存全仓差异以发现范围之外的改动。

```text
python .workflow-kit/scripts/project_workflow.py snapshot --root . --paths <源码目录> <测试目录> <锁文件> --output .workflow-kit/tasks/evidence/<唯一名称>.json
```

命令只针对已存在的明确路径，不扫描凭据目录。输出被任务/运行记录引用；同名快照拒绝覆盖。检查候选文件新增、删除或内容变化时，旧验证不能继续满足 verified。

各任务验证通过后，合并到里程碑候选仍须做组合验证，用户批准绑定该版本。格式任务优先在基线副本运行同一格式化工具，比较完整输出；不要用“标识符/断言数量没变”证明语义不变。

## 自审与独立审查

相同上下文的角色扮演是 self_review。independent 至少要有没有参与实现的新上下文、实际需求/差异/原始验证输入及自己的审查结论。不给审查者暗示“结果应当通过”，不把作者的总结当成全部证据。

单 agent 模式可以采用自审加真实工具测试，前提是项目策略明确允许；高风险或策略要求独立时，不能自动退化为自审。必要时由用户或另一个上下文补齐。

Agent 包办也支持独立审查。review-packet 提供当前需求、候选、原始验证与必要输入，交给未参与实现的新上下文；同模型可以，不要求 CLI，也不复制作者会话和“应当通过”的结论。

所有 PASS 审查都需要 review_checks 覆盖 requirements、regression、failure_paths、maintainability、performance，写明 analysis 与 evidence_files，并引用当前 verification_run。需求和回归不能标不适用，高风险的异常路径也不能；其他确实不适用的项需解释。未检查完就不能 PASS。报告和证据绑定当前候选，修改后旧审查失效。

自审时先暂停实现，从原需求和完整差异重新核对，包括新增、删除、重命名、未跟踪文件、错误/空态、恢复与重复执行、测试断言有效性。针对实际风险寻找反例，不能只重复编码时的成功路径。发现问题回到原任务修复并重新验证；用清晰的依赖方向、职责和测试保护维护性，不以文件越少或抽象越多作为质量结论。

性能判断使用代表性负载、环境、基线和当前测量；比较时说明延迟、吞吐、内存等指标及波动，确认优化没有破坏正确性或稳定性。仅做静态分析时注明范围，不把算法推测写成实测加速。无运行影响的工作可解释不适用，不能为了形式新增基准或未经测量宣称“性能最好”。

完整目标优先，小步执行控制风险；验证和审查不因实现工作量大而省略。缺少独立上下文时，自审不能变得真正独立：展示实际限制、证据与待审事项，不假称质量已被保证。
