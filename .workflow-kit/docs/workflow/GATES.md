# 真实验证与审查

按项目技术栈和改动风险定义具体命令，不从其他项目照搬 npm/cargo/pytest。记录每项适用性，代码 → 可信命令 → 原始结果 → PASS / FAIL。不存在的测试不能标 SKIPPED 来伪装覆盖，应登记 NOT_RUN / 缺口并安排补齐。

| 类别 | 能证明什么 | 不能代替什么 |
| --- | --- | --- |
| 格式 | 按选定格式规则一致 | 逻辑正确 |
| 类型/编译 | 静态类型与编译约束 | 业务行为与运行环境 |
| 静态分析/lint | 已启用规则下的问题 | 所有错误、安全保证 |
| 单元测试 | 单个行为及边界 | 模块协同 |
| 集成/契约测试 | 数据、接口、协议与模块协同 | 真实 UI 和所有外部服务 |
| E2E | 指定环境中的完整用户路径 | 未覆盖的平台与业务情形 |
| 构建/安装 | 目标产物可生成、必要时能安装启动 | 发布批准、运行期质量 |
| 回归 | 已知问题或关键行为不会在这些情形复发 | 永久无 Bug |
| 架构/代码审查 | 边界、可维护性、测试有效性与改动范围 | 自动工具或实际验收 |

PASS / FAIL / NOT_RUN / SKIPPED / BLOCKED / NOT_APPLICABLE 分别报告。没有执行就不写 PASS；环境阻塞不直接称为产品失败；本地通过不等于托管 CI 或目标平台通过。

## 界面质量

UI 变更同时检查实际视觉和交互。构建、lint 和单元测试不能证明下拉菜单、弹窗或默认控件与整体一致。按 [FRONTEND](FRONTEND.md) 维护一份 UI 约定，检查真实组件的展开、焦点、禁用、错误和响应式状态。

ui_change 任务的 PASS 要有对应当前候选的截图与交互报告，ui_review.checked_states 覆盖 ui_checks。工具保存这些证据的摘要，改动后不能沿用旧审查。新界面预览还须由用户实际确认，再进入真实功能实现；预览通过不代表后端或数据流程通过。

## 把 Bug 变成保护

Bug → 编号与复现 → 有效回归证据 → 修复 → 验证。尽量证明修复前失败、修复后通过；已有有效测试可以引用。保留仍然有效的行为保护；需求确实改变时通过需求变更记录更新测试，而非承诺所有历史测试永远不能变。

非确定问题记录触发条件、观测和复跑策略；不能为了“每个 Bug 一个测试”编写总是通过的断言。无法自动化时给出可重复的人工验收、原因与未来补齐条件。

## 证据绑定

使用本次任务的输入快照与最终候选摘要。快照选择相关源码、测试、锁文件与构建配置；额外保存全仓差异以发现范围之外的改动。

```text
python .workflow-kit/scripts/project_workflow.py snapshot --root . --paths <源码目录> <测试目录> <锁文件> --output .workflow-kit/tasks/evidence/<唯一名称>.json
```

命令只针对已存在的明确路径，不扫描凭据目录。输出被任务/运行记录引用；同名快照拒绝覆盖。检查候选文件新增、删除或内容变化时，旧验证不能继续满足 verified。

各任务验证通过后，合并到里程碑候选仍须做组合验证，用户批准绑定该版本。格式任务优先在基线副本运行同一格式化工具，比较完整输出；不要用“标识符/断言数量没变”证明语义不变。

## 自审与独立审查

相同上下文的角色扮演是 self_review。independent 至少要有没有参与实现的新上下文、实际需求/差异/原始验证输入及自己的审查结论。不给审查者暗示“结果应当通过”，不把作者的总结当成全部证据。

单 agent 模式可以采用自审加真实工具测试，前提是项目策略明确允许；高风险或策略要求独立时，不能自动退化为自审。必要时由用户或另一个上下文补齐。
