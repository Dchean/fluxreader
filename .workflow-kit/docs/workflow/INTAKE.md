# 先问业务，再确认执行

每轮最多三个短问题；问题有推荐项和简单影响说明，宿主支持选择题就使用选择题，不支持时用普通文本。不要硬编码某个厂商的问答工具名。

## 第一轮：目标

先检查目录、README、已有规则及包/测试入口，再询问仍然未知的内容：

1. 想解决什么问题，主要给谁使用？
2. 新建项目，还是改善现有项目？已有项目先说明观察到的现状。
3. 第一版最重要的使用流程是什么？

不要让零基础用户填写语言、数据库版本或 Git 状态；这些优先由你检查、分析和推荐。

已有项目不再问“第一版做什么”作为默认起点。先区分用户是在评估是否值得重构，还是已经决定改造；补问项目用途/近期计划、实际维护痛点和必须保留的行为。用户不知道技术问题在哪里是正常输入，由你检查；没有明确问题时也可以建议保持现状。

只请求评估时，先按 [BOOTSTRAP](BOOTSTRAP.md) 完成已选择的工作流接入，再按 [REFACTOR](REFACTOR.md) 给出有证据的结论，业务代码可保持未授权。只有用户明确仅参考方法时才不接入，并如实标注；常规小修复没有调用本包时不强行升级为完整流程。

## 检索参考

需求大致明确后按 [RESEARCH](RESEARCH.md) 检索。把有价值的现成方案呈现给用户，说明可减少哪些工作、有哪些限制，再完善需求。不要在产品尚不清楚时就下载大仓库或选定技术栈。

## 第二轮：范围与验收

确认必须有的功能、暂时不做的部分，以及用户能观察到的完成标准。重构额外确认必须保留的接口、数据和行为。问答可继续分轮，已有答案不用重复。

技术细节在已有约束内由你决定并记录依据。只有影响费用、使用体验、兼容性或业务范围的取舍才需要用户决定。

有界面时确认目标设备、视觉偏好和已有参考，优先推荐一套风格。由 Agent 选择 ui.mode：新界面/明显改版用 preview_first，局部维护用 existing，无界面用 none。UI/UX 与视觉审查职责必须有人承担，具体执行单元仍可保持三个。按 [FRONTEND](FRONTEND.md) 先展示可点击预览；用户不用先选 CSS 库或组件版本。

## 第三轮：运行安排

根据宿主能力推荐执行方式：

- 快速个人项目：宿主 Agent 实现，真实测试加明确标记的自审。
- 需要独立检查：主 Agent 协调，编码执行器和审查上下文分开。CLI 是可选执行器。

确认可自动完成的工作、模型费用控制与任务预算。推荐初始任务预算为修复 3 轮、90 分钟、每批 3 个任务、单写入者；用户可调整。用户明确要求在已确认范围自动推进、且不设本工具额外美元上限时，可将 batch_rollover 保存为 allowed，减少重复确认；其余情况使用 ask。不要把“不确定费用”写成不限额，none 也不表示免费。

单个任务的时间和修复额度耗尽时，展示已完成内容与还需多少预算，再依据实际新决定追加。确认过的技术细节和正常检查点不用反复询问。提交、推送和发布分别沿用已有授权。

默认网络退避为 5、15 秒，CLI 单次上限 600 秒。是否能自动重试由 Agent 检查任务与门禁的重复执行语义后决定，不能把有真实副作用的操作标成 retry_safe。边界见 [RECOVERY](RECOVERY.md)。

## 确认并保存

展示简短摘要：目标用户、首个功能、验收标准、非目标、参考方案、兼容性、执行方式、预算和未决问题。必要问题未答清时保持 intake。

重构场景把“首个功能”替换为“改造目标与首个试点”，说明为何值得改以及如何证明旧行为仍然成立。若结论是不值得改，评估即可结束，不为了流程制造编码任务。

由 Agent 使用 .workflow-kit/tasks/templates/BRIEF.json 准备已确认答案，经 onboard 保存；source 引用真实会话决定。首次 init/adopt 只创建记录，代码工作需要对应授权。调研可在确认前进行，不能因此视为实现方案已获批准。

有旧规则和状态时，onboard 先检查 legacy_review。已读路径、保留约束、旧任务处置与当前角色结论由 Agent 填写；影响业务实现的未决冲突没有解决时，不能启用代码权限。不要把 WorkBuddy 主会话错误地当成旧 CLAUDE 文档中的 Worker，也不要借接入取消安全与数据边界。

产品事实默认集中在 .workflow-kit/docs/PRODUCT.md；较大项目再拆 FEATURES 等文档。.workflow-kit/tasks/BRIEF.json 保存确认快照。有变化时同步引用新决定，不靠聊天记忆，也不机械复制到 Memory。
