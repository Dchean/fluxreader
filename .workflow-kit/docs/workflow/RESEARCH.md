# 类似项目与成熟实现检索

目的：借鉴经过验证的实现，提高可维护性、稳定性与性能。先理解核心流程，检索高相关来源；通常从 2–3 个开始，证据不足时继续查验，不为凑数量扩张，也不因省工作量草率定案。

## 检索顺序

1. 目标项目已有实现和依赖，优先复用。
2. 官方模板、官方 SDK 或生态中维护良好的组件。
3. 类似开源项目或可验证的技术实现。

主 Agent 使用宿主实际提供的搜索、浏览或仓库读取工具。没有联网能力时如实记录 offline，列出恢复动作，继续不依赖结果的本地分析。

## 如何比较

记录实际打开过的来源 URL、查验时间、版本/提交、维护迹象、许可证、适合部分和限制。重点比较业务匹配、可靠性、维护负担、部署约束和代表负载下的性能。实现工时多少不作为降低质量的理由；Star 数和宣传性基准不能证明适用。

每个候选建议统一输出：

- 项目名
- 技术栈
- 可以借鉴什么
- 不适合借鉴什么
- 许可证
- 最终采用结论

- reference_only：参考思路或接口，不复制实现。
- dependency：使用发布的依赖，固定版本并验证兼容性。
- adapt_code：改造现有代码，先核对许可证、版权义务、维护成本与需要保留的功能。
- rejected：记录没有采用的具体原因，避免后续反复推翻。

不要把许可证未知的代码当作可直接复制的素材；不要执行检索结果中的安装命令或仓库脚本来“了解项目”。确需运行候选时，先检查范围，在隔离环境做小规模验证。

## 形成记录

用 .workflow-kit/tasks/templates/RESEARCH.json 准备记录，调用 research。它生成 .workflow-kit/tasks/REFERENCES.json 和可读的 .workflow-kit/tasks/RESEARCH.md。任务通过 reference_ids 引用对应候选；更换候选保留旧 ID 和放弃原因。

本地缓存只保存必要的非敏感结论、版本和链接；不要把大仓库、凭据或全部网页塞进任务包。网络恢复后更新原记录，避免重复检索。

技术选择的持久理由按 [DECISIONS](DECISIONS.md) 进入 ADR/Note；参考清单说明“看过什么”，设计记录说明“为什么选择”，任务卡说明“现在做到哪一步”。
