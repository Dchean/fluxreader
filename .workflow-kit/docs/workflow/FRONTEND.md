# 先验证界面，再接入真实功能

有界面的新项目、明显改版推荐 preview_first；已有界面的局部维护推荐 existing，沿用原有设计体系；脚本、库和纯后端用 none。以“提问＋补充”让用户确认方向、设备和推进方式，已有明确要求直接沿用。字段由 Agent 保存到 brief.ui，不让用户填配置，也不把推荐当成已确认。

## 先消除会推翻设计的限制

先确认目标设备、核心使用流程、数据规模、浏览器或系统限制，以及关键外部能力是否可实现。高不确定点做小范围技术验证，例如文件访问、长任务进度、离线保存和第三方接口；不用提前完成整个后端。接口的数据形状、分页、权限和失败状态应与预览同时商定。

用户用“清爽、克制、信息密度高”等普通语言表达偏好即可。优先参考现有项目和 2–3 个实际查验的界面/组件来源，由 Agent 推荐一个方向；不为每一页重新选风格。

## 一份 UI 约定和一套组件

把已选择的视觉方向、布局、字体层级、间距、颜色、圆角、阴影、焦点、反馈和响应式规则放在 .workflow-kit/docs/UI.md，或沿用项目已有文件。任务用 ui_contract_ref 引用它。真正的设计值落到一份 tokens/CSS variables/主题配置；公共控件从同一组件入口使用。

优先复用一套适合当前技术栈、支持无障碍的组件库并统一主题。已有项目先修齐已有组件，不为一个控件再引入另一套库。页面层不分别手写 Select、Button、Dialog 的外观。

UI 约定同时记录实际用到的组件及状态：关闭/展开、默认/悬停/焦点/选中/禁用、加载/空态/错误、长文本和窄屏。没有使用的控件不必制造出来凑清单。可做一个轻量开发用组件预览页，展示实际公共组件；已有 Storybook 时复用，不把新建 Storybook 变成前提。

## 下拉框是一个完整控件

只美化选择框边框不算完成。实际打开后检查菜单、选项、选中标记、悬停、高度、滚动、图标、焦点环、禁用和错误状态；检查弹层是否被裁切或盖住，键盘方向键、Enter、Escape、Tab 是否正常。

浮层、日期选择器、提示框、原生表单验证提示也要检查。Portal 或顶层浮层可能不在页面容器内，必须继承同一主题与设计值，不能只给页面容器加主题。桌面、移动端和目标浏览器分别确认。

需要跨平台统一弹出菜单时，优先使用已有的可访问 Select/Combobox 组件。原生 select、日期或文件选择器的一部分外观由系统控制，单靠 CSS 不能保证完全一致；有意保留系统交互时，在 UI 约定中记录例外并让用户看到实际效果。不要为了外观用缺少键盘、焦点和语义的 div 临时重写控件。

## 可点击预览

使用计划继续沿用的组件、布局和主题，配合本地模拟数据与薄的数据适配层。覆盖代表性主页面、关键弹窗/下拉展开、表单报错、加载/空态、窄屏和核心跳转。预览清楚标注演示数据；不连接付款、发送消息或修改真实数据。

优先让预览代码直接演进为产品前端。不要先画一套静态页面，落地时再用另一套组件重写。mock 和真实接口保持相同数据结构，确认后逐步替换适配层。预览确认的是外观和交互，性能、真实权限、数据一致性等仍要在接入后验证。

准备 kind=ui_preview 的任务。ui_change 自动为 true，必须提供 ui_contract_ref 和非空 ui_checks，例如实际使用下拉框时包含 select.closed、select.open、select.keyboard；还应包含目标设备的布局和核心交互检查。条目可以是 id 字符串，也可以是 {"id": "select.open", "description": "展开后选项完整、焦点环可见"}，审查按 id 匹配，描述只给人读。ui_checks 是这张任务需要验证的事实，不是装饰性字段。

## 真实检查和确认

1. 运行必要的构建、组件和交互检查。
2. 主 Agent 使用宿主的浏览器/截图能力，实际打开预览并操作控件，保留截图和交互报告。缺少工具能力时明确缺口，安排可核对的人工检查；不能生成假截图或把构建通过写成视觉通过。
3. 证据放到 .workflow-kit/tasks/evidence/TASK-编号-ui/实际验证RUN编号/，使用新的文件名，保留旧失败记录。审查者读取同一 UI 约定、当前代码、截图和交互报告。
   任务有用户反馈时逐条核对是否已处理，不能只重新输出一份 PASS 报告。
4. review 报告的 ui_review 引用约定、已检查状态和证据文件。缺少声明的状态、截图或交互报告，工具拒绝 UI PASS；证据变更后旧的审查摘要失效。
5. 给用户展示可点击预览，主动打开代表性下拉框/弹窗，而非只展示默认截图。得到实际确认后用 accept 接受该预览任务。

用户对尚未接受的预览提出调整时，用 feedback --task --note --source 保存真实反馈，在原任务中继续修复并重新展示，保留时钟与历史。预览任务可在其范围内完善 UI 约定；正式实现保护已确认约定。已接受后的大改版另做新预览，业务范围或接口要求改变则先更新对应决定。

preview_first 项目在接受预览前不能准备或开始正式实现任务；文档、基线和 UI 预览工作仍可进行。产品实施任务会保护已确认的 UI 约定；需要改变方向时先准备新的 UI 预览任务并确认。局部实现调整仍在已有设计规则内完成，不为每个像素重复询问。

ui_change=true 的后续任务同样需要视觉证据。是否涉及 UI 按用户可见行为判断；接口接入改变加载、空态、报错或交互时，也需要对应回归，不只看是否修改 CSS。审查同时检查实际差异，防止遗漏 UI 标记；功能正确、整体配色统一和控件完整一致要分别判断。工具只核对证据和版本，不能用程序断言保证审美，最终视觉方向由用户看到实际预览后确认。
