# 设计依据与用户决定

吸收 write-notes-like-deepseek 的核心方法：保留真实取舍、就地更新已有依据、处理替代关系、从代码入口能找到原因。目标项目不需要因此安装另一份技能。

## 三种记录分别负责什么

| 记录 | 用途 |
| --- | --- |
| .workflow-kit/tasks/DECISIONS.json | 用户实际授权、产品确认和验收依据，POLICY/TASK 引用它 |
| 已有 ADR/Notes，或 .workflow-kit/docs/ADR/ | 技术选择、备选方案、约束与代价 |
| TASK 与自动任务卡 | 工作目标、依赖、状态、证据和下一步 |

由 Agent 作出的技术建议不要冒充用户批准。已有授权范围内的日常技术选择由 Agent 完成；改变功能、兼容性、费用或权限边界时再核对用户决定。

## 何时留下设计记录

未来接手者可能会问“为什么这样改”时记录：重要技术选型、非显然约束、值得防止重犯的缺陷、较大的结构调整。纯格式修改和小动作不用逐一新增 ADR。

先查已有记录，优先更新同一决定的路径、事实和验证结果。比较至少包括不做/复用与其他方案的最强理由，写清收益和代价，避免把备选方案写成明显不合理的陪衬。

提议、已接受、已实施和已替代应区分。已实施记录以现在时描述事实；不能因为没有 Git 提交就把已运行的实现永久留在 proposed。完全替代旧方案时维护引用和有效归属；不把没有价值的旧提案不断堆积。

在核心模块入口用一行注释指向相关 ADR/Note；有稳定的已有体系就沿用其路径和生命周期。任务可用 decision_refs 指向设计依据，不在代码每一行重复相同说明。

没有现有体系时使用生成项目 .workflow-kit/docs/ADR/ 中的轻量模板。它需要说明问题、决定、备选方案、后果、验证和适用范围；用户授权仍单独引用 .workflow-kit/tasks/DECISIONS.json。
