# 按可运行功能推进

个人项目使用下面的循环，不为每个小编辑重做整套产品设计。

已有项目先按 [REFACTOR](REFACTOR.md) 判断是否值得改；如果只需评估或保持现状，不进入编码循环。已经明确且授权的重构范围直接从必要基线和试点开始。

| 步骤 | 要交付的事实 |
| --- | --- |
| 明确目标 | 新项目的第一版，或已有项目的改进目标、保留范围、验收和非目标 |
| 找参考、验证关键限制 | 真实来源、复用方式、技术可行性；重构先记录已有基线 |
| 新界面/明显改版先预览 | 沿用的组件、主题与模拟数据，完整控件状态和可点击流程 |
| 用户确认视觉与交互 | 根据反馈在原预览任务调整，确认后 accept；此时不宣称后端完成 |
| 实现真实功能 | 接入数据/接口、保持 UI 约定、补充有效测试 |
| 检查、展示与接续 | 真实测试、代码与视觉审查、有限修复、可运行成果和下一任务 |

无界面项目跳过视觉步骤。已有界面的局部维护沿用既有设计，检查受影响控件即可；大范围改版再用 preview_first。预览前先核对会推翻设计的关键技术限制，不把模拟数据做得像已经验证真实服务。

同一源码的后续增量依赖最新已验证任务，继承回归检查。短时网络故障可在已确认安全的任务中有限重试；相同失败没有进展时，主 Agent 先改变方案。

已建任务全部通过不等于全部需求完成。最终核对 BRIEF、PRODUCT、真实运行方式与未完成项，才记录项目级验收。详见 [前端流程](FRONTEND.md)、[状态](STATE.md)、[恢复](RECOVERY.md) 和 [命令](TOOLING.md)。
