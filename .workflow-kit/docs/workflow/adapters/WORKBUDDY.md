# WorkBuddy 作为总控宿主

本包按具备文件与终端能力的普通宿主接入 WorkBuddy。执行配置仍使用 current_agent 或已经确认的编码 CLI；bootstrap 的 --host workbuddy 只记录宿主提示，不是一个新的可执行程序。

## 推荐调用方式

1. 在真正的项目目录打开一个新会话，明确提供启动包和目标项目的完整路径。
2. 辨认已有项目后先问重构意向或引用已有回答；bootstrap 仅接入工作流和规则入口，保留原任务、文档与业务代码。
3. 检查真实 connected 回执、入口和状态路径。新布局根入口是 WORKFLOW-KIT.md，工作流文件在 .workflow-kit/。
4. 接入完成后重新开一个项目会话，先读该入口、运行 start，再开始评估或已确认的开发目标。

新会话可以用以下指令：

> 你是当前项目总控。先读 WORKFLOW-KIT.md，运行 start 并报告 integration.connected、项目路径、阶段和任务来源。读取已保存的问答，用提问＋补充继续补缺项；已有项目先确认重构意向，分析后让我选路线，明确 Agent 全部处理还是 Agent + CLI。保留旧业务约束，核对角色/任务源冲突。未连接或校验失败先处理该问题，不改走旧流程。

若当前版本有项目级固定指令功能，可把这段要求保存到客户端实际提供的入口。这里不假定 WorkBuddy 一定自动加载某个文件名或特定规则目录；显式首条消息和真实命令回执才是可核对的起点。

## 发现旧 Agent 文档时

旧 README、AGENTS、CLAUDE、交接文件和任务 JSON 都可能描述另一套工作流。即使同样有 manager/worker、预算和任务卡，也不代表它们与本包契约兼容。特别注意旧文档把当前会话固定成 Worker，或指定某个 CLI 为唯一代码执行器的情况。

由总控填写 legacy_review，保留实际业务、安全与数据约束，解释当前角色和旧任务处置。没有确定的代码执行器时先完成只读/文档评估，不把“已接入”说成“已获准改业务代码”。

这里提供通用接入路径，不假定某个 WorkBuddy 版本的自动加载顺序。应核验当前客户端的文件、命令和问答能力；本地协议测试不证明宿主中的所有工具、模型或权限已适配。
