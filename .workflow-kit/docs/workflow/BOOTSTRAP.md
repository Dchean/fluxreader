# 先确认接入，再开始业务工作

显式使用 workflow-kit 默认意味着实际接入。只参考方法必须由用户明确选择，并标注“未接入”；不能因短评估、已有旧文档或工具失败悄悄降级。

只读辨认出已有项目时，先询问重构意向或引用已明确的回答，再深入分析。接入的 kind 和 host 是技术标签，不是用户的改造决定或编码执行方式；接入后仍需按 INTAKE 明确提问并保存选择。

## 一个可核验的启动结果

由主 Agent 使用完整包运行 bootstrap，目标目录必须明确，先预览再在用户已授权的接入范围写入。新项目 kind=new，已有项目 kind=refactor；--host 只是宿主标签，不是编码 CLI 的名称。

bootstrap 不带 --write 只预览；初次写入需要 --source 引用实际用户选择。已接入时重复调用只检查，不初始化、重设预算或重写历史。

主 Agent 报告实际结果：

- integration.connected 是否为 true，而非只说“读过文档”。
- 目标项目、入口文件、状态文件、所用工具摘要与当前阶段/任务。
- 当前主会话的总控身份，以及编码/审查执行方式是否已确认。
- 旧规则来源、保留约束、旧任务处置、已解决和未解决的流程冲突。

身份、配套工具、入口和受管理文件校验失败时，start/next 给出接入问题；业务工作先不开始。源码改动、范围与验收仍受独立的任务/政策检查，不能用 connected 替代它们。

## 新旧记录共存

新接入放在独立的 .workflow-kit/；根入口为 WORKFLOW-KIT.md。旧任务目录和业务文档不移动、不删除，也不自动转换为当前队列。对同名但格式不同的 PROJECT，工具明确报告 foreign_workflow，不能因为存在文件就恢复它。

AGENTS.md、CLAUDE.md 的当前入口位于顶部，原内容保留，初次接入前原文也有副本。业务文档有合适的原版本时使用引用，避免再复制一套事实。根 README 和应用代码不被初始化模板覆盖。

经典 init/adopt 布局仍可使用，但只能在回执确认为相应布局时按其路径工作。旧版 workflow-kit 无标识、工具版本不配套或集成中断时，需要具体迁移/修复；不能另建同目标任务来清空已有运行和预算。

## 旧规则怎样处理

当前用户明确选择的工作流决定本次流程入口；这不覆盖宿主系统约束，也不自动取消原有业务、数据、安全、兼容或费用边界。

主会话默认是总控。只有明确 task_id/run_id 的执行包才指定 Worker，不能因旧 CLAUDE 文档写着“你是代码执行器”而错把总控当 Worker。旧模型/CLI 选择需要按当前适用授权核对，不自动换账号、模型或计费方式。

有遗留流程时，onboard 需要 legacy_review：reviewed_paths 覆盖回执列出的来源；preserved_constraints 说明保留什么；task_disposition 解释旧任务和未完成工作怎样处理；workflow_resolution 说明当前流程与角色；unresolved_conflicts 列出未决事项。只读/文档评估可以记录未决项，开启业务代码前必须解决相关冲突。

这些字段由 Agent 根据实际读取填写，不让用户编辑 JSON。旧工作确实尚未完成时，要保留其身份、预算和证据或准备明确迁移，不把同一个工作包装成新任务重新计数。

## 防止再次偏离

每个新会话先读回执中的根入口并运行 start；恢复先核对真实进程和文件，再按当前任务继续。进入实现前应有当前工作流的任务、RUN 与允许范围；结束时给出这些记录和实际验证证据。

如果 Agent 不能执行接入命令、没有文件权限或开始按旧队列工作，先报告具体阻塞。不要用更长的口头承诺代替接入，也不要删掉旧业务约束让新流程显得通过。

本包验证文件和进程记录，不是整个宿主的权限沙箱。仍需依赖宿主按用户指令调用这些工具；更强的只读总控、隔离执行器或宿主 hooks 必须根据实际平台能力另行验证，不能假称已经强制生效。
