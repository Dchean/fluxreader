# 先判断是否值得重构，再决定怎么改

“已有项目”不等于“必须重构”。用户可能需要诊断、补保护、修一个 Bug、降低维护成本或大范围改造。先分清目的，不把“请评估”理解为已经批准结构替换。

## 入口与判断责任

- 用户不确定是否需要重构：先走下面的价值评估，只做已授权的检查与记录，给出结论和具体方案。
- 用户已经明确重构目标：保留必要的现状核对，直接围绕已授权范围设计试点，不重复要求用户证明同一个决定。
- 普通小修复：按已有规则处理，不强行启动全项目评估或完整新流程。

判断由主 Agent 结合业务、代码和实际检查完成。脚本提供记录、接入、验证和恢复，不会自动算出“这个项目必须重构”。

先读原项目规则、README、已有 ADR/Notes 和当前任务。已确认的约束与用户授权继续有效，缺少信息才补问，每轮最多三个业务问题。

## 第一步：确认重构能解决什么

重点确认项目现在做什么、近期准备怎样使用或扩展、哪里经常出问题/改起来困难，以及哪些行为必须保持。用户说不清技术原因时，由你检查代码后用业务语言解释。

不要要求用户先填写模块图、数据库版本或重构方案；也不要在没有实际需求时预设要换框架、拆服务、引入设计模式或重做 UI。

## 第二步：小范围盘点与真实基线

先沿一条代表性业务路径检查入口、核心模块、数据、外部边界及现有验证；有跨模块证据再扩大范围。说明检查了哪里、哪些还没验证，不把抽样结论包装成全项目保证。

检查已有设计记录，弄清当前实现是否承担兼容、部署、性能或运维约束。在已有授权内运行可控的本地测试、构建或必要测量，记录真实输入、环境、命令和结果；环境不足就写 NOT_RUN/BLOCKED。

已有测试失败是基线事实，不自动成为本次必须修复的 Bug。评估/基线任务不要因为旧测试非零退出就进入自动修复循环；先记录原因与可确认程度。正式重构的门禁再明确原本通过的关键检查、行为对照和新旧失败的比较，不能临时删除断言或把旧失败写成 PASS。

没有测试不等于应该重写。必要时建议先补关键行为保护，或缩小范围；新测试只覆盖会影响判断或后续改动的实际行为，不追求统一覆盖率数字。

## 第三步：按证据比较选项

| 可选结论 | 适用依据 | 下一步 |
| --- | --- | --- |
| 保持现状 | 当前使用稳定，没有足以抵消改造成本的具体问题 | 说明判断覆盖范围，保留观察项，不凑重构任务 |
| 补保护或局部修补 | 缺少可验证基线，或问题局限于少数位置 | 先补必要测试、观测或针对性修复 |
| 渐进重构 | 已有重复规则、依赖牵连、边界混乱等证据，影响真实维护或计划中的变更 | 选择一条业务路径或一个模块做试点 |
| 替换/迁移 | 渐进修补确实无法满足关键约束，替换收益与迁移成本有依据 | 单独说明兼容、迁移、回滚与授权范围 |
| 证据不足 | 尚不能区分代码问题、环境问题与产品需求变化 | 列出最少的下一步调查，不先得出重写结论 |

每个主要发现连接“具体位置/复现 → 对当前使用或维护的影响 → 最小有效改法 → 收益与代价 → 如何验证”。文件长、技术旧、与个人编码风格不同，本身不是重构理由。小工具和很少变化的项目应特别重视维护负担。

需要参考时优先看本项目已有实现，再查少量相关成熟实现；记录可借鉴的具体机制，不整套照搬架构。分析“保持现状/复用”“局部修补”“渐进调整/替换”的最强理由，不用总分或字母评级直接决定重写。

## 第四步：给用户可决定的结果

输出一份简短结论，优先沿用已有文档；没有合适位置时可用 .workflow-kit/docs/REFACTOR-REVIEW.md，不要求生成另一套报告体系：

- 总体建议、依据和判断范围。
- 少量最重要的问题：证据、影响、建议和不确定性。
- 保留范围、非目标、预期收益、成本/风险及验证方式。
- 如果要改，第一步试点是什么；如果不改，何时值得重新评估。

用户明确选择 workflow-kit 时，评估前先按 [BOOTSTRAP](BOOTSTRAP.md) 完成接入并报告真实回执；只开放相应文档/基线权限，未批准的业务实现保持 code=false。用户不用编辑这些字段。只有用户明确仅参考方法、不要接管时才省略接入，并说明程序门禁未生效。

已有状态先识别是否属于本包，不能凭文件名沿用。其他工作流的记录保留在原位置，新流程独立保存，并在 legacy_review 解释旧任务处置；已接入本包的记录不能重新初始化。kind=refactor 表示已有项目路线，不是重构方案已经获批。评估完成后，仅对真正新增的必要授权展示具体方案并确认。

## 第五步：决定执行后的最小试点

1. 明确可观察的改进目标和必须保持的功能、接口、配置、数据及 UI 行为。Bug 修正、产品变化和结构调整分别说明，不顺手混入。
2. 建立真实可恢复点：使用适合本项目的 Git 提交/补丁、独立工作区或代码副本，保留未提交工作。本包 snapshot 是哈希清单，只能核对变化，不能恢复被改掉的源码，不能拿它代替备份。
3. 通过已核验的工作流接入路径管理任务，保留原项目结构。以原本有效的测试和必要行为对照保护试点；事实进入 BASELINE，重要取舍沿用 ADR/Notes。
4. 准备一张范围明确的任务卡，从一条业务路径、一个边界或一处重复规则开始。不要按目录把全项目先拆成几十张已冻结的任务。
5. 验证旧行为保持、目标收益是否出现、是否引入新失败；同时检查实际差异和复杂度。只有有证据的改善才扩大到下一部分，收益不足时可收窄或停止。
6. 在既有范围和预算内持续推进；新增重大范围、技术栈替换或数据迁移再依据具体方案处理授权。评估阶段已 onboard 时不能再次 onboard 清空状态，由主 Agent 记录新决定并更新必要策略和阶段，保留旧任务、时钟与证据。

内部逻辑重构默认保留 UI。已有 UI 的局部维护用 existing，只对受影响页面和控件做回归；明显改版才用 preview_first。触及渲染、组件、交互或会影响界面状态的接口时，按 [FRONTEND](FRONTEND.md) 保留真实视觉与交互证据，而不是因为“有前端”就重做整站。

后续按 [LIFECYCLE](LIFECYCLE.md) 交付；中断按 [HANDOFF](HANDOFF.md) 和 [RECOVERY](RECOVERY.md) 恢复。用户只需关注判断是否有依据、试点是否有价值、原有功能是否保留。
