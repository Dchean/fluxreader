# 保留三个执行单元，明确专业职责

manager、coder、reviewer 是执行单元，产品、架构、UI/UX、前端、后端和 QA 是职责。个人项目不需要固定启动七个进程，但必须明确谁对每项结果负责。

Agent 包办表示不需要编码 CLI，不表示只能有一个上下文。实现和独立审查可以由宿主的不同 Agent 上下文承担，使用同一个模型也可以。独立性的依据是未参与实现、输入可核对、结论独立形成，不是角色名称或模型厂商不同。

当前主会话先承担 manager，只有明确的任务执行包才将会话指定为 Worker。旧 CLAUDE/README 的角色文字不能自动决定当前宿主身份；接入后依据回执与 legacy_review 明确分工，不删除仍然有效的业务和安全约束。

| 职责 | 默认负责者 | 必须交付 |
| --- | --- | --- |
| 产品与需求 | manager | 业务目标、范围、可观察验收、实际参考 |
| 技术方案与重构评估 | manager | 用户意向、检查证据、带依据的选择问题、已确认路线、兼容边界与复用方式 |
| UI/UX 设计 | manager 协调，coder 实现预览 | 一份 UI 约定、沿用的组件、可点击流程和控件状态 |
| 前端实现 | coder | 统一主题与公共组件；展开、焦点、禁用和错误等状态完整 |
| 后端与集成 | coder | 保持既有兼容约束；需要界面预览的项目确认后接入真实数据 |
| QA 和测试运行 | manager 调用工具 | 可信命令、真实日志、回归与交互证据 |
| 代码与视觉审查 | reviewer | 当前代码、截图、交互报告与验收的核对结果 |
| 用户验收与交付 | manager 协调用户 | 真实反馈、预览确认、功能与最终交付决定 |

总控还负责按 [PRESENTATION](PRESENTATION.md) 展示阶段目标和任务卡；不能只维护机器记录。质量取舍以可维护、稳定、性能及实际需求为依据，不以减少 Agent 工作量为理由裁剪范围。

UI 不是最后“美化一下”。按 [FRONTEND](FRONTEND.md) 在前期确认视觉与交互，reviewer 必须检查完整控件，而非只看页面配色。既有代码审查职责和新的视觉验收职责可以由同一审查者承担，证据分别说明。

界面密集、交互复杂或关键质量风险较高时，可以按需增加独立的 UI/UX 设计、前端或 QA 上下文。输入仍是同一份 UI 约定、任务卡和真实证据，结果回到原任务；不要另起一套需求、预算或进度记录。仅有单一上下文时如实标 self_review，不能把改角色名称当成独立审查。

默认一个写入者。主 Agent 安排依赖、预算和接续；网络退避、无进展诊断与恢复按 [RECOVERY](RECOVERY.md) 执行。普通技术决定和已授权工作自行推进，真正影响范围、费用、体验或兼容性时再请用户决定。
