## 总体判断

项目有必要做核心架构重构，但没有必要推倒重写，也没有证据支持更换技术栈。保留 Tauri、Rust、React、SQLite，重点重构前端数据状态、批量操作语义和同步领域模型。理由：关键业务规则分散在多个状态、组件和协议分支里，局部修复可解决一个场景，却难以保证整个链路始终一致。

## 社交正文问题链路（审计原文）

1. 卡片显示正文。
2. 后台刷新或手动同步调用 `reloadFromBackend`。
3. 新列表快照不含正文，替换原来的文章，同时清空 `hydratedIds`。
4. 虚拟列表按文章 ID 保持组件身份。
5. 加载正文的 effect 只有 `[id]` 依赖，同一 ID 不会重新触发。
6. 卡片重新显示"加载正文…"，但实际上没有正文请求在运行。

对应位置：列表快照替换（src/store/slices/bootstrap.ts:126 一带）与卡片正文加载 effect（src/components/Timeline.tsx:424 一带，`useLazyHydrate`）。

探针结果：`同 ID 刷新后：content=""，hydrated=false，新增正文请求数=0`。

相邻缺口：批量加载正文（src/store/slices/reader.ts:215 一带 `hydrateArticleContent`）收到空数组直接返回；部分 ID 没有对应返回行时也不进入"文章不存在"或失败终态，留下没有实际请求的加载占位。

## "全部已读"结论

当前入口（src/store/slices/nav.ts:190 一带）已把布局传入后端，数据库操作（src-tauri/src/db/articles.rs:862 一带）按范围筛选并在事务内完成标读与入队。**不能把旧的全库误标问题视为当前已证实的缺陷。**

仍存在的两件事：

1. **计数更新不完整**：后端处理当前范围的全部未读文章，前端只按已加载的文章扣数字。探针：范围 600 条未读、前端加载 1 条，模拟后端成功处理 600 条后，界面仍显示 599 条未读。
2. **同文副本存在跨源传播**：同步推送（src-tauri/src/sync/push.rs:48 一带）把"已读"广播给记录的同文副本。若副本属于其他布局的源，远端副本也会被标读。属既有设计，但与"只影响当前布局"的直觉冲突，需要显式产品语义。

## 结构性诊断（为何重构而非继续修补）

| 方面 | 已具备的合理基础 | 当前主要问题 |
| --- | --- | --- |
| 技术路线 | Tauri 桌面壳、Rust 业务、SQLite 本地库适合 RSS 客户端 | 本次缺陷并非这些技术的能力限制 |
| 前端状态 | 已拆成 Zustand slices，已有缓存和虚拟列表 | slices 仍共同操作全局状态；文章实体、查询快照、正文终态之间缺少统一约束 |
| 数据查询 | 列表、布局、范围已有收口 | 分页、筛选全集、缓存、计数仍由不同路径协调 |
| 同步 | 已有持久化队列、重试、分阶段同步、待推保护 | 协议能力、冲突规则、去重传播混在具体执行分支中 |
| 数据一致性 | "全部已读"已经事务化 | 单条标读、收藏和另一条批量标读路径没有统一事务保证 |
| 质量保障 | 前端回归和 Rust 测试积累较多 | 缺少组件生命周期、真实协议差异与完整用户旅程的验证 |

一致性问题实例：单条状态写入（src-tauri/src/commands/articles.rs:109 一带 `record_read_state`）先改文章状态再写同步队列，无外层事务；第二步失败时"本地状态已改但没有待同步记录"。批量路径逐条执行，可能部分成功。

## 同步技术路线

继续同时支持 Google Reader 和 Fever，但把 Google Reader 作为通常优先推荐的协议，Fever 作为有明确能力限制的兼容选项。外部依据：FreshRSS GR 文档提醒客户端注意同步策略；Miniflux 实现的是兼容子集，其时间过滤应用于发布时间——"用本机时间推进游标"不能单独证明不会漏掉晚到的旧文章。应建立"服务端 × 版本 × 协议 × 操作"兼容矩阵。

现存协议间差异：Google Reader 轻量对账只接受远端已读、Fever 对账双向恢复读状态——应成为显式冲突政策而非隐性切换行为。

推荐同步边界（Rust 枚举即可实现，不引入插件体系）：

```text
协议适配器：认证、分页、远端 ID、能力限制
             ↓
同步引擎：拉取、重试、游标、完整性判断
             ↓
领域规则：本地意图优先级、读状态冲突、同文副本传播
             ↓
事务提交：文章状态 + 待同步操作 + 对账进度
```

## 建议重构的四块

1. **文章实体与视图分离**：文章按 ID 保存一份，列表查询只保存文章 ID、分页信息和查询状态；刷新列表不丢已加载正文。正文使用明确状态：`未请求 → 加载中 → 成功 / 空正文 / 不存在 / 失败`。请求去重、重试、过期响应处理归同一模块。
2. **查询范围与批量操作共用一个明确模型**：布局、订阅范围、视图、时间条件组成统一查询范围，列表、计数和批量操作从它派生。后端成功后返回实际影响数量或计数变化；前端按操作版本确认、回滚或重新读取。
3. **统一所有状态写入的事务和同步语义**：单条标读、收藏、滚动标读、全部已读都经过同一业务服务；本地状态与待同步记录一起成功/失败；网络失败保留本地操作恢复后补推；迟到响应不覆盖更新操作；未完整取得远端集合时不把"缺失"解释成取消收藏或已读。
4. **"同一篇内容"与"各订阅源中的条目"分开建模**：保留各源条目身份与状态，建立同文关联；展示可合并，标读是否传播由明确策略控制。

## 阶段顺序与完成标准

| 顺序 | 重点 | 完成标准 |
| --- | --- | --- |
| 第一阶段 | 正文加载、标读范围、事务与计数 | 刷新不丢正文；操作范围可解释；失败不假成功 |
| 第二阶段 | 查询缓存、统一分页、协议对账 | 快速切换不串数据；旧文章可达；不同协议行为有明确说明 |
| 第三阶段 | 五布局交互一致性 | 加载、错误、重试、快捷键、焦点和返回位置都有统一规则 |
| 第四阶段 | 大库与媒体性能 | 根据真实数据量测量内存、滚动、查询和同步耗时后优化 |

纳入优化目标：筛选视图真分页（替代 `limit: 100000`）；稳定排序与游标；缓存按实体数量/内存预算约束；同步界面区分"本地已保存/等待同步/远端已确认/部分失败"；加载占位只在确有请求时显示；后台刷新保留当前阅读位置。
