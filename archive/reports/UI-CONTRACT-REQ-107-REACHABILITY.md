# UI 契约：TASK-094（三布局列表可达性，REQ-107）

目标设备：Windows 桌面端（Tauri WebView2）。UI 模式：existing（沿用现有时间线列、卡片、哨兵的布局与样式，**不改版**）。
范围：时间线列表的分页加载行为与底部哨兵（`.timeline-load-more`）的表现；五种布局（文章/社交/画廊/播客/通知）。

## 背景（已实证）

审计 round-4 §2.2（s7b B1）：画廊 5/44、播客 6/119、通知 1/20，容器 `scrollHeight == clientHeight` 不可滚动，
而哨兵仍显示「滚动加载更多」。根因与代码事实见 `.workflow-kit/tasks/evidence/TASK-094-baseline-reachability.md`。

## 需要核对的状态

1. **可达**：任一布局在后端还有条目时，用户通过滚动（或点击可见的加载按钮）能触达该布局的全部条目；渲染卡片数最终等于后端该布局在当前范围与视图下的条目数。
2. **不足一屏**：条目少于一屏时，不要求用户滚动，列表应自动加载到撑满视口或到底；到底后哨兵显示「没有更多了」。
3. **提示可执行**：「滚动加载更多」只在容器可滚动时出现；容器不可滚动且未到底时，哨兵为可点击的「加载更多」按钮（沿用现有 `toggle-action-btn` 或同体系按钮样式，键盘可聚焦，Enter/空格可触发）。
4. **加载中**：沿用现有 `load-more-spinner`，不出现布局跳变。
5. **空态**：真正没有内容时只显示既有空态文案，不同时出现承诺性的加载提示。
6. **切换布局**：切到另一布局时从该布局首批开始；切回原布局时不出现重复卡片、不跳过条目。
7. 文章/社交布局既有的滚动加载体验不回退。

## 明确不改

- 不改卡片结构、样式、文案、间距；除哨兵外不新增控件。
- 不改「全部已读」、排序、筛选按钮的行为。

## 验证方式

- 代码层面：cargo test / fmt / clippy、`npm run lint`、`npm run build`、`npm run test:frontend`（新增断言修前失败、修后通过）。
- 界面层面（必做）：`tmp/audit-r3/harness/` 的 Chrome CDP + 忠实假后端，构造与 s7b B1 同形的数据（稀疏布局条目分散在全局较老的位置），修前复现、修后逐布局记录：可见卡片数 / 后端条目数、scrollHeight 与 clientHeight、list_articles 调用次数与参数（含 layout、offset）、哨兵形态；浅色与深色主题截图各一张。
