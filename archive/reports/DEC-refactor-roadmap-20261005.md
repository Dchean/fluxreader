## 决定

1. **保留技术底座，不推倒重写**：继续使用 Tauri + Rust + React + SQLite + Zustand。审计证据表明问题集中在业务状态和协议语义的组织方式，不在技术选型；换框架只会重新实现同一批规则。
2. **重构以数据一致性为中心**，按审计四块推进：①文章实体与视图分离；②查询范围与批量操作共用统一模型；③统一状态写入的事务与同步语义；④"同一篇内容"与"各订阅源条目"分开建模。
3. **阶段顺序与完成标准**（正确性 → 恢复能力 → 操作一致性 → 性能）：
   - 第一阶段：正文加载、标读范围、事务与计数（TASK-103/104/105）。完成标准：刷新不丢正文；操作范围可解释；失败不假成功。
   - 第二阶段：查询缓存、统一分页（替代 limit:100000 近似全集）、协议对账显式冲突政策。完成标准：快速切换不串数据；旧文章可达；不同协议行为有明确说明。
   - 第三阶段：五布局交互一致性（加载/错误/重试/快捷键/焦点/返回位置统一规则）。
   - 第四阶段：大库与媒体性能，先按真实数据量测量再优化。
   - 第二阶段及以后的卡片在第一阶段验证通过后立项（避免规格腐烂），本决定先锁定阶段目标与顺序。
4. **执行方式**：主控（当前会话）只做路线、立项、派发与验收；编码由编程子代理承担；**每轮独立审查必须新开未参与编码的子代理**（与 POLICY `host-agent-independent-review` 一致）。
5. **协议立场**：Google Reader 为通常优先推荐协议，Fever 为有明确能力限制的兼容选项；协议间行为差异（如对账方向）在第二阶段成为显式冲突政策并写入文档。
6. **同文副本读状态传播语义**（审计点名需产品决定的点）：owner 不在场，主控按保守默认处置——**保持现状（读状态向同文副本跨源传播，push.rs:48 既有设计，注释载明双端场景动机），显式记录为政策并同步进用户可见文档；是否改为"布局隔离优先"由 owner 后续决定**，第二阶段 TASK（同文建模分离）落地策略开关时不预设结论。

## 不做 / 替代方案

- 不更换技术栈、不重写：审计无证据支持；重做成本高且不解决规则分散问题。
- 不在本轮引入 TanStack Query 等第二套缓存：与"统一所有权"目标冲突；Zustand 内部建立统一水合/终态约束即可（第二阶段再评估是否值得引入）。
- 不在本轮做五布局视觉润色与性能优化：顺序靠后，先正确性。
- 不把 Rust 单连接改为读写分离/专用线程：无锁等待证据，第四阶段测量后再定。

## 影响范围

- 第一阶段任务：TASK-103（正文水合生命周期）、TASK-104（全部已读计数一致性）、TASK-105（Rust 状态写入事务化），全部在 dev 分支实施，验证通过后按分支协议合并 main。
