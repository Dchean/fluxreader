# 性能基线与测量方法

性能结论必须附日期、构建、语料与测量范围。本页保留仍适用的判定线、方法纪律、当前基线与资源预算；构建或输入变化后旧数字不能直接比较，历史任务卡只用于定位固定材料。

## 判定线（触发优化才动手）

| 指标 | 阈值 |
| --- | --- |
| 内存随文章数 | 超线性增长 |
| 滚动帧间隔 p95 | > 50ms |
| 视图切换 / 搜索端到端 | > 1000ms |
| 长会话 | 首末内存增量显著为正且 DOM 节点同向增长（缓存无界） |
| 两档规模之间 | 指标超线性恶化 |

## 当前本地同步基线（2026-11-12，组合候选实测）

- **前提。** 全部数字来自 debug 构建的 `cargo test`（opt-level=0、无内联、无优化）与隔离 Windows Rust 窗口的合成语料；发布给用户的是 release 构建，同一路径通常快一个数量级，不能用这些耗时推算用户换机恢复或首同步体验。
- **规模判定标准。** 10k distinct 4KiB 正文的全流程（4KiB 正文、全部相位、全部断言、2 秒前台门槛、仍为 ignored 容量测试）是当前规模验证标准；50k distinct-body 是开放边界，**未验证**。裁定理由见[资料库决定](../.agents/archive/legacy-workflow/notes/implemented/architecture/2026-11-09-纯本地资料库同步与便携恢复.md)；逐相位明细属一次性材料，位置见本页「证据位置」。
- **10k 结果。** 同一最终源码（审计修复后）自然 exit 0：墙钟 1,442,330 ms；9 个源的前台阶段单次最大 358,782 µs，全部低于 2 秒门槛。
- **50k 结果。** state-only exact（小 delta，非整库 apply）同一源码自然 exit 0，墙钟 65,019 ms；50k distinct-body 在 accept 后的整库 apply（物化 + retention）未在 60 分钟硬上限内完成，因此 **50k distinct-body 容量未验证**。
- **WAL。** 便携导出期间源库 `.db` 与 `-wal` 大小恒定，WAL 不随导出时长增长；**“回落为 0”发生在连接正常关闭时，而不是导出结束**；被外部终止的运行保留 WAL 文件、不归零。
- **内存。** 50k 运行的单进程峰值 2.36 GiB 出现在启动后约 13.5 秒的编译期（采样中 `known_pids` 含 cargo/rustc），不是 apply；apply 期测试进程的实测峰值为 401,154,048 B。两者差异不作归因，不构成“apply 占 2.36 GiB”的结论。
- **已知规模瓶颈（既有缺陷，本轮未修）。** 整库 state 应用到新库会为每条被应用的 read/star 字段生成一个 `retention/` 工作键：10k 库约 20,001 个，debug 构建下实测排空 306,998 ms；50k 约 100,002 个，未在 60 分钟硬上限内完成。只影响“一次性整库应用”的耗时，不影响便携导出、前台延迟或正确性。`retention_work` 按 `feed_url+guid` 找物理文章的查询分支没有 `articles(guid)` 索引，按 feed 扫描；retention 也只在整库 state 应用时成批产生，日常增量 state 只覆盖变化条目。修复需 schema 索引与迁移并补旧库兼容验证；后续方向（不承诺）是该索引或把 retention 按 key 查询批量化。
- **方法与边界。** 整库 state 应用阶段走 `merge_apply` 测试入口（不是生产恢复），其无前台写者的原因与生产同步 receive 入口相同：候选折叠期间逻辑修订必须稳定，持续写只会可重试失败、停写后收敛；生产便携恢复 `backup::restore` 另有独占锁/`capture=0` 语义。源半程保留 20 写/秒负载。不外推自然语料、真实 WebDAV、IPC/渲染、前台等待 SLO 或真实存储介质 I/O 损坏。
- **证据位置。** 逐相位耗时、WAL `dbsize` 采样（4,825 点）、内存样本与 50k 任务卡的原始日志在本机 `tmp/refactor-2026-11-09/` 的容量测试日志（任务卡 `r9-i1-10k-*` / `r9-i1-50k-*`），**不入库、不在主线**；早期测量工具与任务包在存档分支 `archive/tooling-and-reports`。

## 查询与搜索预算

- 列表、搜索、成员捕获和计数在完全投影态直接读取物理 `feeds`/文章状态；初始捕获期（`capture=1 AND initialized=0`）、存在普通工作、候选接受、folding/applying 或待处理意图时回落到本地同步逻辑视图（`local_sync/logical.rs` 的 `query_requires_logical_state`）。两条路径的可见性、去重、排序与计数必须同值；计划回归要求稳定态无 TEMP B-TREE、无 `MATERIALIZE local_sync*`，并用一个待物化反例证明确实切回逻辑视图。
- 搜索的 trigram 索引只是 ≥3 字符的候选加速，LIKE 才裁决匹配；短词、索引缺失或 MATCH 失败回落 LIKE，不改变顺序、去重或字段语义。索引体积与写入成本不可外推到自然语料。
- 读闭包查询按源内 RSS 等价组连接（同 feed + 同 rss_content_id + 同标题/附件），计划消费与去重显示聚合共用的 `idx_articles_rss_group`；该索引缺失时回落为不引用它的计划，回落只变慢、不变义。批量标读不得逐条扫描全部未读行。v30 曾建的 `idx_articles_url_norm_unread` 部分索引已于 2026-11-15 删除（全库无消费查询）：新库不再建立、无迁移，既有库不自动删——存量索引只多付写维护成本，且该索引自始没有运行时回落实现。
- 计数由后端非线性聚合，前端不能按字段或副本数线性推算；读取失败保留最后已知值，写后以权威快照收敛。
- 以下历史只作为方向性结论保留（同构建前后对照、合成语料、db 层中位）：trigram 候选把 50k×8KiB 唯一词搜索从数百毫秒级压到毫秒级；部分索引把 1000 条批量标读的逐条闭包成本从约 25–66 ms/条降到约 0.2–0.7 ms/条。归属说明：后一组的数字测于 2026-10，针对的是已删除的 v30 `idx_articles_url_norm_unread` 与其时代按 url_norm 键合的闭包实现，不代表现行 RSS 等价组闭包的计划。绝对数字不可跨构建比较，端到端（IPC/渲染）未测。

## 封面补全请求预算与生命周期

**每轮预算（`src-tauri/src/scheduler.rs` 常量）：**

| 项 | 值 | 约束的东西 |
| --- | --- | --- |
| 每轮批次 | 20 个 URL | 单轮最多发起 20 次文章页请求（同 URL 的多个条目共享一次请求） |
| 并发上限 | 2 | 与 feed 抓取（默认 4）错峰 |
| 单请求超时 | 30s | 慢页面不拖住整轮 |
| 单轮候选扫描 | 4 页 × 20 条 | 每轮的 SQL 与候选评估成本上限；游标只在进程内保存，动态集合不保证固定轮数全覆盖 |
| 循环间隔 | 60s | 补全速率上限约 20 URL/分钟 |
| 结果缓存上限 | 1024 | 成功与失败共用条目上限，按插入序逐出；是条目数，不是字节硬界 |
| 失败/无图缓存 | 10 分钟 | 实际尝试完成后计时，命中不续期 |
| 文章页正文 | 16 MiB | Content-Length 预检与累计流式收体，超量不采用前缀中的 og:image |

- 启动后首轮先等 45s（`scheduler.rs` 的 `spawn_cover_backfill`）：避开启动期 UI 抢锁并让 feed 抓取先落库；等待期可被终止信号打断，未开始首轮即退出。
- 候选是全来源的“无封面 + 有原文 URL”；回填用守卫 UPDATE（`scheduler.rs` 的 `fill_cover`：以 article id 与扫描 URL 为条件，且仅 `image_url IS NULL OR image_url = ''` 时写入），不覆盖已有封面。弃用 `COALESCE(旧值, 新值)` 的原因：`COALESCE` 只判 NULL，空串行会每轮留在候选队列里且被算作已补全。内容刷新只在远端给出非空新图时覆盖。
- 正文首图、OG 和 RSS 媒体按显式尺寸及角色跳过小图、头像、emoji；无尺寸正常图保留，不另发尺寸探测。
- 本机封面按 article ID 与当前图片 URL 精确 CAS 清除，并撤销共享成功缓存、设短期失败屏障；旧图迟到不能清新图。
- 应用退出触发终止信号：不再发起新请求、取消在途请求，单轮返回前等待子任务结束；中断的尝试不记负缓存。
- 客户端会直接请求服务端收录文章的第三方源站页面，暴露客户端 IP，这是候选扩面的既有隐私取舍；真实库请求总量、补完耗时与图床解码未测。

## 画廊布局预算

画廊使用 `@tanstack/react-virtual` 的 lanes 模型，按视口 4/3/2 列、14px 间距与图片自然比例渲染。挂载量由列数、可见高度与 overscan 决定，不是全量挂载：参考视口 768、卡高 ≥150 时，测试口径按 48 项作为检查界，但 48 不是任何视口的绝对上限。虚拟化不能测量未挂载内容，列归属依赖已测高度；自然图片分批到达时，几何发布与滚动补偿必须先于测量更新，避免可见锚漂移。

- 当前门禁在真实 headless Edge 中跑两视口、图片两波异步到达，要求指定可见锚漂移 ≤3px；历史失败（159px、295px）保留在 commit 与 CI，不用后续本地结果覆盖。
- 5000 条合成数据、程序化滚动实测的 rAF 回调间隔接近 60Hz 帧周期；这是回调时间戳间隔，不是硬件 FPS、INP 或真实库持续性能（一次性单点值见本页「证据位置」）。
- 真实 WebView2 滚动 p95、解码与自然语料仍未测；相关缺口见 [roadmap](roadmap.md#interface-and-media)。

## 图片代理编码资源预算

代理四个 active、32 个 queued 不同 key；单图 25 MiB，后端整条 Referer 链总寿命 30s。前端 ready（含在用及退休版本）与 active 每个 25 MiB 预留合计 ≤128 MiB；无人使用 ready 子集 ≤64 MiB 且 ≤256 条；服务持有代理 lease ≤256，失败/上报元数据分别 ≤1024 条，普通失败 30s/明确对象失效 10min 冷却。普通直链不占代理 entry/lease 或字节预算，本地失败状态仅随消费者保存。

解码失败在真实 DOM 移除 Blob src 后归还该消费者的票，健康共享消费者继续保护同一版本；失败占位不阻止原有 LRU 和新请求回收无人使用 bytes。只有无人用的 Blob 能淘汰，超额代理消费者由容量释放自动唤醒，保持真实可见图最终可加载。预算是资源规格，不能冒充 WebView/native/GPU 进程内存硬界。

## 测量方法纪律

- **切换延迟用双判据。** 记录 `firstResultMs`（卡片 ID 集合变化）与 `stableMs`（连续 3 帧 rAF 无 DOM 变更）；只看“存在卡片”会把旧卡当结果，超时只写 `timedOut`，不给毫秒值。
- **搜索必须断言结果归属。** 输入前结果不含该词、输入后结果确实在文章区域内；否则计时可能测到背景文本。
- **条件分段记录。** 起点条件与每段条件分开，结论只引用本段条件；锁等待段自己触发同步，不借用起点条件。
- **JS 堆与进程 RSS 分列，不可换算。** 进程 RSS 按应用父子进程/命令行过滤；同名 WebView2 可能来自其他应用。
- **崩溃布局的堆值写 null 并附原因**，不填数字；中断则本段作废，不输出假值。
- **证据对应固定 SHA 与输入**：本地未提交改动或不同构建的数字不能与 CI 结果混用；旧任务卡的测量工具在存档分支，复用前核对 schema 与读写边界。
