## 本地同步闭包与稳定态查询路径（2026-11-12，组合候选实测）

50k本地同步诊断确认：单条收藏候选曾建立约150,019字段的proposed view，随后按约50,002个实体重复投影；隔离运行在300秒时仍停在preflight，CPU接近全程饱和。修复后的契约按候选字段与durable旧/新工作计算有限目标闭包：单文章变化只验证相关实体；source展开到成员文章；旧/新URL展开到同URL的source与文章；group展开到成员source与文章，并用有序集去重。闭包仍需完成revision、pending、clock、alias和显式依赖验证，不能以少扫为由跳过合法性。初始化既有大库只建立逻辑winner/journal/clock与必要body hold，不再为已存在物理行排队逐文章`job=''`物化；真实本地编辑仍正常捕获和物化。

列表、搜索、成员捕获和计数在完全投影态直接读取物理`feeds`/文章状态；只要存在普通工作、候选接受、folding/applying或待处理意图，就回落到本地同步逻辑视图。pending态下筛选、定位、去重代表、计数和返回读藏值都取同一逻辑赢家，同组去重内层也按逻辑状态判断；稳定态仍走直接索引路径，避免每个文章行重复物化整组source窗口。

当前组合的无探针50k exact自然exit 0：墙钟272.985秒、累计CPU269.906秒、峰值单进程695,832,576字节；initialize 236,187毫秒、seal 14,580毫秒、click 12,727微秒、delta 1,523毫秒，`fast_apply_us=3,412,283`、`idle_us=2,035`；发布状态45,214,445字节、64个shard、稳态delta 192字节。项目bundled SQLite的真实Rust计划测试同时覆盖小型、20k与50k形状：稳定态列表/搜索/scope count无TEMP B-TREE、无`MATERIALIZE local_sync*`，待物化工作反例回落到逻辑视图；索引缺失回落保持相同成员与顺序。

该结果只覆盖合成50k状态测试和当前隔离Windows Rust窗口，不外推自然正文、真实WebDAV、IPC/渲染或前台等待SLO。后续完整门禁在工作区稳定后通过fmt、all-targets check、clippy `-D warnings`、单线程完整测试和默认并行完整测试；前端/Native/CI与真实存储介质I/O故障仍由[路线边界](roadmap.md#verification-boundaries)维护。

### 2026-11-12 整合候选 r9：导出读快照、50k 状态与 10k distinct-body 容量

**构建与前提。** 以下数字全部来自 debug 构建的 `cargo test`（opt-level=0、无内联、无优化），
且是隔离 Windows Rust 窗口的合成语料；发布给用户的是 release 构建，同一路径通常快一个数量级，
因此不能用这些耗时推算用户的换机恢复或首同步体验。

**导出截止点改为读快照。** 便携导出不再等待 work 队列清空的 settled 状态：只等待已接受候选
（300 秒上限、50 ms 轮询），随后 deferred 读事务首条语句固定 `local_sync_revision` WAL 快照，
流式写出并在末尾 commit 释放。后台同步继续、队列非空时也能完成导出；导出正确性由快照保证。
50k distinct-body 实测导出文件 480,327,791 B、耗时 141,445 ms（r8 因等待队列清空在 1714 秒后被
外部停止，保留为历史失败）。

**范围裁定（2026-11-13）。** 本版 v0.19.0 的规模验证标准正式定为 10k distinct 4KiB
全流程（4KiB 正文、全部相位、全部断言、2 秒门槛不变，仍为 ignored 容量测试）；50k
distinct-body 记为本版**开放边界**，不写成通过或已验证（`r9-i1-50k-03/04` 证据保留）。
依据：用户口径“以实际使用为参考，不需要考虑太多极端情况”；50k 在 debug 构建下整库应用约
2 小时量级，且 state-only 50k 主测已通过；连续两轮向用户确认范围未得到回复，按已给出的推荐
继续。该裁定不改变任何测试强度。

**10k distinct-body exact（最终源码，审计修复后）与 50k 状态 exact。** 10k distinct-body 以
4KiB 不同正文、全部相位与 2 秒前台断言自然 exit 0：墙钟 1,442,330 ms；initialize 24,653 ms、
state_seal 4,812 ms（11,915,932 B/64 对象）、state_ack 46 ms、seal 22,954 ms（88,032,541 B/144
对象）、ack 5,167 ms、delta 4,405 ms（3 对象/155,724 B）、portable_export 30,568 ms
（96,021,252 B）、portable_preview 10,486 ms、preflight 46,242 ms、state_first_apply
1,254,000 ms（其中 retention 排空 306,998 ms）、state_metadata_apply 69,320 ms（preflight
52,930 ms）；9 个源前台阶段单次最大 358,782 µs，全部低于 2 秒。50k 同源复测

`idle_us=1,530`；此前 272.985 秒的 50k 状态记录保留为历史，不覆盖。preflight 从旧记录的数分钟
级降到 3.1 s，是该路径在状态测试上的直接收益。

**WAL 时间序列（r9-i1-10k-02 采样，约 0.3 s 间隔，共 4,825 个样本）。** 窗口边界完全按

文件已不可见，不参与上述三个窗口。

**内存。** 进程内存按采样阶段区分：r9-i1-50k-03 的 2.36 GiB 单进程峰值出现在启动后约
13.5 秒的编译期（样本 27/2084，known_pids 含 cargo/rustc），不是 apply；测试进程 apply 期的
实测峰值是 r9-i1-50k-04 的 401,154,048 B（样本 2296/3955）。两者不构成“apply 占 2.36 GiB”的
结论，差异不作归因，也不外推。

**已知规模瓶颈（既有缺陷，本轮未修）。** 整库 state 应用到新库会为每条被应用的 read/star
字段生成一个 `retention/` 工作键：10k 库约 20,001 个，debug 构建下实测排空 306,998 ms
（约 15.3 ms/键）；50k 约 100,002 个，r9-i1-50k-04 的整库 apply drain 在 60 分钟硬上限内未
完成，故 50k distinct-body 未验证。只影响“一次性整库应用”（换机恢复/首次合并整库）的耗时，
不影响便携导出，也不影响前台延迟（10k 9 个源相位单次最大 358,782 µs，全部 <2s）或正确性
（10k 自然 exit 0、全部断言通过）。`retention_work` 按 `feed_url+guid` 找物理文章的查询
分支没有 `articles(guid)` 索引，按 feed 扫描；retention 也只在整库 state 应用时成批产生，
日常增量 state 只覆盖变化条目，数量级不同。它是既有行为而非本轮引入；修复需 schema 索引与
迁移并补旧库兼容验证，本轮不做。后续方向（不承诺）是 `articles(guid)` 索引，或把 retention
的按 key 查询批量化、去掉 LIKE 前缀扫描。

**方法与边界。** 该结果只覆盖合成 distinct-body 语料与当前隔离 Windows Rust 窗口。整库 state
应用阶段走 `merge_apply` 测试入口（不是生产恢复），其无前台写者的原因与生产同步 receive
入口相同：候选折叠期间逻辑修订必须稳定，持续写只会可重试失败、停写后收敛；生产便携恢复
`backup::restore` 另有独占锁/`capture=0` 语义。源半程保留 20 写/秒负载。不外推自然语料、
真实 WebDAV、IPC/渲染、前台等待 SLO 或真实存储介质 I/O 损坏；其他主机 CI、native UI 与真实
服务端仍由[路线边界](roadmap.md#verification-boundaries)维护。

## 封面补全请求预算与生命周期（OPT-017D，2026-10-16；2026-11-07更新）

**变更**：候选集合从「`source='direct'` 的无封面文章」扩展为**全来源**的「无封面 + 有原文 URL」（服务端正文无图文章此前永久无任何封面——正文首图兜底只在正文有图时成立；两处封面写入都不会把本地封面清成空：回填路径 `COALESCE(旧值, 新值)` 严格只填空、内容刷新 `COALESCE(新值, 旧值)` 只在远端给出非空新图时覆盖，R1-P2-1 修正）。本节记录其**请求预算与生命周期语义**；这是预算规格，不是性能基准数字。

**每轮预算（`src-tauri/src/scheduler.rs` 常量）**：

| 项 | 值 | 约束的东西 |
| --- | --- | --- |
| 每轮批次 | 20 个 URL | 单轮最多发起 20 次文章页请求（同 URL 的多个条目共享一次请求） |
| 并发上限 | 2 | 与 feed 抓取（默认 4）错峰，避免抢带宽 |
| 单请求超时 | 30s（`COVER_BACKFILL_REQUEST_TIMEOUT`） | 慢页面不拖住整轮 |
| 单轮候选扫描 | 4 页 × 20 条 | 每轮的 SQL 与候选评估成本上限；游标按已扫描行推进、扫到底回绕，仅在进程内保存；动态集合不保证固定轮数全覆盖 |
| 循环间隔 | 60s | 补全速率上限 ≈ 20 URL/分钟 |
| 结果缓存上限 | 1024（`COVER_BACKFILL_ATTEMPT_CACHE_MAX`） | 成功与失败共用条目上限，按插入序逐出；限制条目数，不是严格字节内存上限 |
| 失败/无图缓存 | 10分钟 | 实际尝试完成后计时，命中不续期；到期或被逐出后可重试 |
| 文章页正文 | 16MiB | Content-Length预检与累计流式收体，超量不采用前缀中的og:image；相对图片按最终响应URL解析 |

**结果与恢复语义**：成功缓存保留图片URL，同文章URL的后来条目或此前未扫到的条目在正常扫描到时可复用，不扩大扫描页数或额外发HTTP。失败/无图使用上表TTL，部分取代旧“本进程不重试”的决定。候选查询失败记录 `warn` 并提前结束本轮扫描，写库失败记录 `error` 且不记完成结果，下轮可重试；抓取失败/无图记录 `debug`。DB故障不得压成空集合或0后标记已处理，退出中断也不记完成结果。

**候选与失效**：正文首图、OG和RSS媒体按可用的显式尺寸及角色信息跳过小图、头像、emoji等；无尺寸正常图保留，不另发尺寸探测请求。全来源本机封面按article ID与当前图片URL精确CAS清除，并撤销共享成功缓存、设短期失败屏障，防在途旧结果或缓存立即回填；旧图迟到上报不能清新图，不向远端推送失效。该政策部分取代旧direct-only清理，后续远端pull仍可提供权威图片。scheduler和命令共用AppState中的一份结果状态，网络不持DB锁。

**生命周期**：应用退出（`RunEvent::Exit`）触发终止信号；补全循环在等待与请求两处消费——不再发起新请求、在途请求被取消，单轮返回前等待全部子任务结束，不残留任务。终止中断的尝试不记负缓存。

**证据与边界**：历史预算夹具在 `tmp/optimization-20261008/OPT-017D/evidence/`；2026-11-07后继固定版本的候选、TTL/容量、并发失效屏障、URL变化、SQL恢复与CL/EOF预算已有限定独审，见[验收入口](../.agents/notes/implemented/process/2026-11-03-修复波次的分批、证伪审计与证据门槛.md#本轮修复的限定验收2026-11-07)。真实库补全请求总量、补完耗时和真实图床解码未测；质量启发式不能识别全部视觉角色，也不迁移清扫所有既有图片。客户端仍会直接请求服务端收录文章的第三方源站页面，暴露客户端IP，这是候选扩面的既有隐私取舍。无src的data-src图片兼容范围未扩大，静态候选覆盖不保证动态集合严格公平。

- 测量环境**无真实同步后端**，同步耗时未测。
- JS 堆与进程 RSS 是不同量纲，不可互相换算。

这些记录只支持当时文本夹具中的14–22卡、有限规模堆值和首页查询耗时；“无>50ms样本”不证明物理显示无掉帧，也不保证当前画廊或任意大库无退化。

## SQLite 单连接：维持不变

审计原话是「单连接是否改读写分离应根据锁等待和查询耗时决定」。历史 v0.17.0 夹具下所测查询低于 70ms，没有锁等待证据；该数字不能外推到当前大正文语料。OPT-017A 已显示搜索和计数查询耗时显著上升，但未测并发锁等待。当前先定位查询/索引与内容存储的确定性成本，**暂不以这些数据直接引入读写分离**；若优化后仍出现实际锁竞争，再评估连接方案。`sync_queue_stats` 的 IPC 往返只能作代理指标，不能冒充 DB 锁计时。

## 测量方法纪律

这些是纠正过程中得到的教训，重新测量或阅读历史数据时都适用。

**切换延迟用双判据。** `firstResultMs`（卡片 id 集合发生变化）与 `stableMs`（连续 3 帧 rAF 无 DOM 变更）。只看「是否存在卡片」会把旧卡当成结果；只看一帧会把动画中间态当成稳定态。超时只写 `timedOut`，不给毫秒值——编一个数比留空更糟。

**搜索必须断言结果归属。** 搜索段的 `ownership.tokenAbsentBeforeTyping` 与 `negativeProbe` 用于证明：输入前结果里不含该词、输入后结果确实在 `[role=group][aria-label=文章]` 内。没有归属断言，搜索计时可能测的是背景文本里恰好出现的同一个词。

**条件要分段记录。** `conditions` 是起点条件，`conditionsBySection` 是每段自己的条件；结论行只引用本段那份。锁等待段会自己触发一次同步，借用起点条件会与 JSON 自相矛盾。

**JS 堆与进程 RSS 分列，不可互相换算。** 进程 RSS 须按本次应用父子进程/命令行身份过滤；同名 WebView2 可能来自其他应用，不能按进程名求和。

**崩溃布局的堆值写 null 并附 `heapInvalidReason`**，不填数字。

**中断则增量作废，不输出假值。** 电池可被打断（用户操作、应用退出），此时该段的数字无效。

## 历史测量工具的数据安全纪律

本节的 `--seed`、`--restore` 与 `--no-sync-probe` 是存档分支 `archive/tooling-and-reports` 的测量工具参数，不是 FluxReader 产品命令，也不是当前备份/恢复入口。复用旧工具前须核对其版本与当前 schema；产品快照及退出应用后的恢复步骤以 [backup.md](backup.md) 为准。

**历史测量电池不是全只读。** `lockWaitProxy` 段曾通过命令面板触发一次真实联网刷新，`--no-sync-probe` 用于跳过该段。该工具可能写本机库、触发已连接账户的同步；旧按钮文案和点击路径不能直接假定适用当前版本。

**旧 `--seed` / `--restore` 使用文件副本与 SHA256 清单。** 它曾备份 `.db` / `-wal` / `-shm` 并在还原后逐字节复核；哈希只能证明拷贝一致，不能证明运行中分别复制的三文件来自同一数据库时点。不能用这条历史工具约定代替当前 `VACUUM INTO` 自包含快照。

**旧工具还原前也必须完全退出应用。** 运行中的 SQLite 连接持有文件句柄，覆盖可能失效或被后续 WAL 写入破坏；哈希通过不等于恢复后的逻辑状态已验收。

**失败处置一律「先退应用再还原」**，`skipped` / `timedOut` / `invalid` 按原样记录，不手填数字。
