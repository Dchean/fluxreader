# 性能基线与测量方法

性能结论必须附带构建、数据与测量范围。历史 v0.17.0 的文本布局测量不能证明媒体或当前大正文场景无需优化；OPT-017A 的隔离基线已发现搜索、计数和批量标读的慢路径。本文分列历史应用级数字与新的生产 DB API 基线，不能混用，也不以基线完成代替性能优化完成。

测量工具（CDP 测量电池、合成规模数据注入、owner 实机清单）已移到存档分支
`archive/tooling-and-reports`（`archive/tools/phase4_measure.mjs`、`phase4_seed.py`、
`phase4_checklist.md`），原始输出在 `archive/measurements/phase4/`。重新测量前请先读那份清单——它有若干条前置条件（窗口必须在副屏、磁盘余量、Node 版本）。

## 判定线（触发优化才动手）

| 指标 | 阈值 |
| --- | --- |
| 内存随文章数 | 超线性增长 |
| 滚动帧间隔 p95 | > 50ms |
| 视图切换 / 搜索端到端 | > 1000ms |
| 长会话 | 首末内存增量显著为正且 DOM 节点同向增长（缓存无界） |
| 两档规模之间 | 指标超线性恶化 |

## 画廊布局有界渲染（OPT-017C，2026-10-16）

**变更**：画廊（image 布局）此前用 CSS 多列（`column-count` 4/3/2 + `break-inside: avoid`）全量 `items.map` 渲染——DOM 随条目线性增长，注释自述「图片数量通常较少」但没有规模证据；父卡 OPT-017「必须消除的确定性成本」第 2 条要求可验证的窗口上限。本卡改为**列模型 + 垂直虚拟化**：列数按与旧 CSS 媒体查询同断点解析（≤800 → 2、≤1200 → 3、否则 4），窗口内条目由 `@tanstack/react-virtual` 的 lanes 能力（贪心最短列分配）渲染，挂载后按 `offsetHeight` 测量校正；列宽/列距公式 `(W − (n−1)×14px) / n` 与旧 `column-count/column-gap` 逐字等价。

**「最大同时挂载卡片数」的常量与依据**（`src/components/GalleryLayout.ts` 单点）：

- 渲染集 = 每列可见条数 × 列数 + 两端 overscan，每列可见条数由 `视口高 / 卡片高` 决定——**上界随视口高与卡片高表达、与条目总数无关**，这是「有界渲染」的可验证含义；
- **通用式**（任何视口高/卡片高都成立，`galleryMountBound()` 实现）：`lanes × (⌈视口高 / 卡片高度⌉ + 3 行边界余量) + 2 × overscan`；
- **参考口径上界**：参考视口（`GALLERY_REF_VIEWPORT_HEIGHT = 768`）× 卡片高度 ≥ `GALLERY_CARD_MIN_HEIGHT = 150`（无图占位 120 + 元信息 ≈ 60 的下沿）前提成立时，`galleryMountBound(768, 150) = 4×(⌈768/150⌉+3)+8 = 44`，断言口径取 `GALLERY_MOUNT_BOUND_REF = 48`。**48 是带前提的参考口径、不是无前提绝对上界**：模型层不强制卡片高度下界（保持图片自然比例与旧观感），`loading="lazy"` 未加载（仅 alt 文本）或极扁图片的实测高可 < 150px，此时窗口按通用式变宽（方向性：同视口下 h=100 → 52；视口更高同理）——方向性已由域回归真值表钉住（`galleryMountBound(768, 100) > 48`、`galleryMountBound(2160, 150) > 48`）；
- 估算高度（未挂载条目）= 列宽 × 0.72 + 64（下限 200）——只影响窗口定位与滚动总高，挂载后的真实高度由测量修正；估算误差由 overscan（4 条/边）与窗口余量承担。

**测量方法与证据**（`tools/component-tests/gallery-virtual.test.mjs`，真实挂载 React 树 + jsdom）：

- 节点数 = `container.querySelectorAll('.gallery-card')` 的真实 DOM 计数（非 SSR、非数组长度自证）；5000 项 + 跨滚动偏移（0…34 万 px）扫描，实测同时挂载 ≤ 32（harness 测量高 260px；探针归档输出在 `evidence/probe-outputs/`，测量高 160px 的最坏假设下 ≤ 40），全部 ≤ 48；
- **通用有界性断言**（不依赖 150px 前提）：每个扫描点用夹具**实测**视口高与 `min(估算, 实测最小卡高)` 现算 `galleryMountBound(...)` 并断言挂载数 ≤ 该值——任意高度下都成立且公式不含条目总数；同时保留参考口径 ≤ 48 断言（夹具实测卡高 ≥ 150 时 48 才适用，实测不满足会先判红前提行）；
- 直接对照：同一视口下 200 项与 5000 项的初始挂载数**相等**（不随总数线性增长）；基线（全量 `items.map`）同断言以 5000 挂载判红（先红后绿，证据在 tmp/optimization-20261008/OPT-017C/evidence/）；
- 窗口内挂载数在滚动中保持有界的同时，键盘焦点（roving tabindex 窗口兜底）、灯箱开合返回、触底加载更多追加批次的渲染与索引映射由同文件其余用例覆盖；纯函数真值表（列数断点/估算/放置/兜底/上界通用式）与灯箱/分页状态迁移在 `tools/frontend-tests/gallery-window.mjs`。

**未测边界（验收缺口，不以此节关闭）**：

- jsdom 无布局引擎、无图片解码——上列证据证明**节点数有界与结构/交互正确**，不证明真实 WebView 的滚动帧率、图片解码与瀑布流布局性能；真实窗口下的滚动 p95 未测（判定线 50ms 不适用本卡证据）。
- 真实图片高度分布下的列均衡度与测量-滚动锚定表现未实测（估计→测量的修正路径只在 jsdom 统一高度替身下验证）；真实渲染节点数的测量方法是「挂载真实组件树后数 `.gallery-card` 节点」，受限于同一环境边界。
- **lazy 未加载/极扁图片的高度方向未实机取数**：真实场景中卡高小于 150px 时窗口按通用式变宽（见上），48 不再适用——本卡的实机边界只覆盖「卡片高度 ≥150px 的参考口径」，矮卡实机分布与窗口宽度需要后续实机测量（若需要收紧，候选是给卡片加高度下界或改参考口径，本卡按「不改用户可见观感」裁决未动 CSS）。
- 列分配由「CSS 列优先平衡」改为「贪心最短列（行优先起步）」——同一组条目在两套模型下的列归属不同（列宽/列距/自然比例/错落观感一致）；有界渲染无法对未挂载内容做浏览器列平衡，这是本卡的裁决取舍（见归属 Note）。

## 封面补全请求预算与生命周期（OPT-017D，2026-10-16）

**变更**：候选集合从「`source='direct'` 的无封面文章」扩展为**全来源**的「无封面 + 有原文 URL」（服务端正文无图文章此前永久无任何封面——正文首图兜底只在正文有图时成立；两处封面写入都不会把本地封面清成空：回填路径 `COALESCE(旧值, 新值)` 严格只填空、内容刷新 `COALESCE(新值, 旧值)` 只在远端给出非空新图时覆盖，R1-P2-1 修正）。本节记录其**请求预算与生命周期语义**；这是预算规格，不是性能基准数字。

**每轮预算（`src-tauri/src/scheduler.rs` 常量）**：

| 项 | 值 | 约束的东西 |
| --- | --- | --- |
| 每轮批次 | 20 个 URL | 单轮最多发起 20 次文章页请求（同 URL 的多个条目共享一次请求） |
| 并发上限 | 2 | 与 feed 抓取（默认 4）错峰，避免抢带宽 |
| 单请求超时 | 30s（`COVER_BACKFILL_REQUEST_TIMEOUT`） | 慢页面不拖住整轮 |
| 单轮候选扫描 | 4 页 × 20 条 | 每轮的 SQL 与候选评估成本上限；扫描游标跨轮持久推进（R1-P2-2：按已扫描行前移、扫到底回绕，保证有限轮数内全覆盖） |
| 循环间隔 | 60s | 补全速率上限 ≈ 20 URL/分钟 |
| 负缓存上限 | 1024（`COVER_BACKFILL_ATTEMPT_CACHE_MAX`） | 进程内「已尝试 URL」内存有界；逐出最旧 |

**失败与恢复语义**：一次尝试**完整结束后**（成功 / 页面无 og:image / 抓取失败）URL 才记入负缓存——本进程内不重试；容量满后按插入序逐出，被逐出的 URL 只有在再经历 ≥1024 条其它尝试后才可能重试，每轮请求量仍受上表约束（不存在对单个 URL 的无界重试）。**候选查询失败**记录 `warn` 并提前结束本轮扫描（不记任何「已处理」，下轮重试）；**写库失败**记录 `error` 且不记负缓存（下轮重试）；抓取失败/无 og:image 记录 `debug`（含 URL 与原因）。DB 故障不得压成空集合或 0 后把任务标记为已处理。

**生命周期**：应用退出（`RunEvent::Exit`）触发终止信号；补全循环在等待与请求两处消费——不再发起新请求、在途请求被取消，单轮返回前等待全部子任务结束，不残留任务。终止中断的尝试不记负缓存。

**未测边界（验收缺口，不以此节关闭）**：真实库的补全请求总量与全量补完耗时未实测（本卡的证据是本地 mock 服务器下的确定性夹具与红绿/变异日志，见 `tmp/optimization-20261008/OPT-017D/evidence/`）；**隐私边界**：扩面后客户端会直接请求服务端收录文章的第三方源站页面（抓 og:image），客户端 IP 对更多第三方站点可见，这是候选扩展的已知代价；**扫描游标**（`CoverBackfillState::scan_offset`，R1-P2-2）保证候选集在有限轮数内全覆盖（按已扫描行推进、扫到底回绕，不落盘）；「服务端文章本地补上的封面不参与失效清理（404 时显示占位、进程内不重试）」是保留的保守边界；`first_image`/og:image 的质量启发式仍缺（见 [roadmap.md](roadmap.md)）。

环境：本机实装 v0.17.0，WebView2 远程调试端口 9222，应用窗口置于副屏，合成为 20k / 50k 篇文章（RFC3339 时间戳）。

| --- | --- | --- | --- | --- | --- | --- |

**受测条件的边界（引用这些数字时必须一并带上）**：

- 延迟类数字（切换 59–78ms、搜索 ~510–556ms）含 IPC 与渲染，且切换延迟的旧判据（「存在任意卡片」）在旧卡未换掉时即成立——**数字主要反映 50ms 轮询粒度，不是真实的界面就绪时间**；新版电池改用双判据（见下）。
- 覆盖范围是文本布局；**无媒体解码压力**（播客/画廊的音频与图片负载未测）。
- 只测了列表顶部约 3 秒的滚动；长会话（数小时）只测了内存增量趋势。
- 测量环境**无真实同步后端**，同步耗时未测。
- JS 堆与进程 RSS 是不同量纲，不可互相换算。

## SQLite 单连接：维持不变

审计原话是「单连接是否改读写分离应根据锁等待和查询耗时决定」。历史 v0.17.0 夹具下所测查询低于 70ms，没有锁等待证据；该数字不能外推到当前大正文语料。OPT-017A 已显示搜索和计数查询耗时显著上升，但未测并发锁等待。当前先定位查询/索引与内容存储的确定性成本，**暂不以这些数据直接引入读写分离**；若优化后仍出现实际锁竞争，再评估连接方案。`sync_queue_stats` 的 IPC 往返只能作代理指标，不能冒充 DB 锁计时。

## 测量方法纪律

这些是纠正过程中得到的教训，重新测量或阅读历史数据时都适用。

**切换延迟用双判据。** `firstResultMs`（卡片 id 集合发生变化）与 `stableMs`（连续 3 帧 rAF 无 DOM 变更）。只看「是否存在卡片」会把旧卡当成结果；只看一帧会把动画中间态当成稳定态。超时只写 `timedOut`，不给毫秒值——编一个数比留空更糟。

**搜索必须断言结果归属。** 搜索段的 `ownership.tokenAbsentBeforeTyping` 与 `negativeProbe` 用于证明：输入前结果里不含该词、输入后结果确实在 `[role=group][aria-label=文章]` 内。没有归属断言，搜索计时可能测的是背景文本里恰好出现的同一个词。

**条件要分段记录。** `conditions` 是起点条件，`conditionsBySection` 是每段自己的条件；结论行只引用本段那份。锁等待段会自己触发一次同步，借用起点条件会与 JSON 自相矛盾。

**JS 堆与进程 RSS 分列，不可互相换算。** 进程 RSS 需按命令行含 `com.fluxreader.app` 过滤——本机同时有 47 个同名 `msedgewebview2.exe` 进程。

**崩溃布局的堆值写 null 并附 `heapInvalidReason`**，不填数字。

**中断则增量作废，不输出假值。** 电池可被打断（用户操作、应用退出），此时该段的数字无效。

## 数据安全纪律（必读）

**测量电池不是全只读。** `lockWaitProxy` 段会通过命令面板点一次「刷新全部订阅源」——即一次**真实的联网抓取**（拉取全部订阅源、写本机数据库、可能向已连接的后端推状态）。`--no-sync-probe` 可跳过该段。在一台连着真实同步后端的机器上跑测量之前，必须知道这一点。

**`--seed` 前强制备份** `.db` / `-wal` / `-shm` 三件套并生成 SHA256 清单；`--restore` 逐字节拷回复核哈希。

**`--restore` 之前必须先完全退出应用。** 运行中的 SQLite 连接持有文件句柄，覆盖可能静默失效或让 WAL 恢复改坏数据库——而 SHA256 校验的是目标文件，这种破坏下照样通过。

**失败处置一律「先退应用再还原」**，`skipped` / `timedOut` / `invalid` 按原样记录，不手填数字。
