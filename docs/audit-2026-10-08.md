## 1. 执行摘要

### 1.1 是否有重构必要

**有，但必要的是范围受控的核心重构，不是重写项目或更换框架。**

| 选项 | 审计判断 | 主要依据 |
| --- | --- | --- |
| 换成 Electron、WPF、Qt，或重写全部应用 | 不建议 | 现有主要缺陷是操作身份、账号隔离、协议假设和事务边界问题，换 UI/桌面框架不能自动修复 |
| 保持全部实现，只做样式、重命名和文件拆分 | 不足以解决问题 | F01、F05–F10 涉及跨模块运行时不变量，不是单文件整洁度问题 |
| 保留模块化单体，重构同步确认、账号生命周期和内容写入边界 | **建议** | 能保留已有功能和回归积累，同时封住反复出错的契约 |
| 立即做 DB 读写分离、替换状态库、增加第二套查询缓存 | 暂无充分依据 | 本轮未获得真实同步负载下的锁等待基线；增加新的状态所有者可能继续放大一致性问题 |
| 将同文内容与各源条目分开建模 | 有价值的后续路线，不作为所有修复的前置条件 | 应先确认跨源已读/收藏传播的产品语义，再设计迁移；队列和账号边界可以先独立修复 |

### 1.2 最高优先级

1. **F01：旧推送确认可能删除新的用户操作**，已在内存 SQLite 复现生产 SQL 组合的误确认机制；完整 Rust/Tauri/HTTP 交错尚未端到端复现。
2. **F02–F04：FreshRSS 的 Google Reader / Fever 适配存在实质差异**，已对照固定版本官方源码；现有 mock 不足以证明真实兼容。
3. **F05–F06：配置导入与在途同步缺少统一账号边界**，可能混用旧密码、旧远端编号和新服务地址。
4. **F07：正文回填绕过 sanitizer**，不安全 HTML 可以进入实际渲染路径。
5. **F08–F09：ETag / 同步游标确认没有完整绑定持久化成功**，失败后可能跳过尚未可靠保存的数据。

### 1.3 对项目成熟度的判断

- **功能广度已经具备**：不是只有外观和按钮的演示工程。
- **核心可靠性仍有缺口**：离线操作、多端同步、失败重试和账号切换不能仅凭当前门禁判定可用。

## 3. 实际架构与技术路线评估

### 3.1 当前结构

~~~text
React 五布局 / Reader / 设置 / 播放器
                  ↓
Zustand slices + 查询快照 + bodyCache + 派生 feedIndex
                  ↓
              Tauri IPC
                  ↓
commands / ingestion / sync / AI / config_sync / scheduler
                  ↓
        rusqlite 单连接 + SQLite + 本地 outbox
                  ↕
       Google Reader / Fever / 原始 RSS / AI HTTP
~~~

网络和 DB 临界区多数已分开，属于合理基础；但“网络在锁外”也意味着旧响应回写前必须再次校验账号、操作版本和同步快照。当前缺陷正集中在这些校验未贯通之处。

### 3.2 应保留的选择

| 现有选择 | 判断 | 原因与注意事项 |
| --- | --- | --- |
| Tauri 2 + Rust | 保留 | 与 Windows 系统能力、本地资源访问和离线使用相符；没有证据表明桌面框架是缺陷主因 |
| SQLite / rusqlite | 保留 | 适合单用户本地数据、事务和离线队列；先修事务/确认语义，再讨论连接池 |
| React 19 + Zustand 5 | 保留 | 已能支持五布局和交互；应减少派生状态与源状态分离写入，不必为了统一而立即替换状态库 |
| 正文实体缓存与分页列表分离 | 保留方向 | 比把整篇正文混在列表快照里更清晰；需要继续限定失效、账号和 AI 产物归属 |
| 模块化单体 | 保留 | 当前规模不需要微服务或重型领域框架；可用小型类型化边界实现相同约束 |
| Google Reader 优先、Fever 兼容 | 可以保留定位 | 先完成真实服务端差异适配；Fever 的历史回溯缺口不能归因于协议不支持 |

### 3.3 需要改变的组织方式

1. **同步协调单点**：账号代际、取消/失效、阶段推进、数据变更事件由后端统一管理，而不是前端设置页、后台调度器和即时推送各自拼接。
2. **可靠 outbox**：操作身份不可复用，确认精确匹配版本；支持重试的订阅写操作也应纳入同一可靠机制。
3. **独立协议 DTO**：Fever 不应通过伪装成 Google Reader ItemContent 而继承它的十六进制 ID 假设。远端身份至少包含账号/协议上下文，线上值应保真。
4. **内容写入边界**：统一清洗后的 HTML 类型/入口；原始内容与可渲染内容的职责明确。
5. **持久化确认单点**：ETag、分页游标、成功统计必须服从事务或已持久化检查点，而不是 HTTP 成功。
6. **前端派生状态一致性**：categories 与 feedIndex 不能随调用入口不同而有时一起更新、有时只更新一份。

单纯拆小 [Timeline.tsx](D:/fluxreader/src/components/Timeline.tsx) 或搬运 Rust 模块不会实现以上保证，不宜把文件数量或行数下降作为核心重构的验收指标。

## 5. 核心数据、安全与协议发现

### F01 — 旧推送确认可能删除用户刚提交的新操作

**P1｜A（内存 SQLite 最小复现）+ B（生产调用链）**

**机制：** sync_queue 使用普通 INTEGER PRIMARY KEY；入队时先删除同一文章的旧同类/相反操作，再插入新行。SQLite 允许复用刚删除的最大 ROWID。推送完成后仅按旧队列 id 执行删除，无法区分同一编号是否已经属于新操作。

**实际观测：**

~~~text
read 开始推送：                 [{ id: 1, action: "read" }]
用户改为 unread，重新入队：    [{ id: 1, action: "unread" }]
旧 read 请求成功后 prune(1)：   []
~~~

**影响：** 最新 unread/star/unstar 意图可能未被发出就丢失。之后即使网络恢复、重复同步，也没有对应待推记录。PUSH_LOCK 只约束推送任务，不能阻止网络期间的本地入队。

**代码：** [表定义](D:/fluxreader/src-tauri/src/db/migrations.rs#L94)、[删除旧项后插入](D:/fluxreader/src-tauri/src/db/sync_queue.rs#L20)、[仅按 id 确认](D:/fluxreader/src-tauri/src/db/sync_queue.rs#L74)、[推送计划](D:/fluxreader/src-tauri/src/sync/push.rs#L35)。SQLite 官方规则见参考资料 S4。

**建议：** 操作使用不可复用标识，或使用持久化递增版本并按版本确认。追加迁移而不是修改已发布迁移。AUTOINCREMENT 可以解决普通 ROWID 复用这一具体问题，但不能代替账号归属、操作版本与重试幂等性设计。

**回归验收：** 用可控服务端屏障暂停旧请求，插入新相反操作后再确认旧请求；断言新队项保留、最终远端状态等于最新用户意图。不能只断言“推送函数成功”。

### F02 — Google Reader POST 认证与 FreshRSS 不兼容

**P1｜B（生产代码 + 固定版本官方实现）**

当前 GET 带 Authorization，POST 则只发送 T=登录 Auth，不带 Authorization。所查 Miniflux 实现使用 POST 表单 T 完成认证；所查 FreshRSS 通过 Authorization 建立用户上下文，edit-tag 等部分修改端点校验 T；普通用户还接受空 T 或 T=x 的兼容例外。当前客户端传的非空“用户名/hash”不属于兼容值，也不是该实现的 action token。不能把“所有 POST 都必须获取独立 token”当作协议通则，两种实现不能混为一个不变契约。

**影响：** FreshRSS 上连接测试和 GET 订阅列表可以成功，但 POST 正文获取、标读、收藏等路径失败。不能以“能登录”推断“协议已支持”。

**代码：** [GET / POST 封装](D:/fluxreader/src-tauri/src/greader.rs#L364)、[item_contents](D:/fluxreader/src-tauri/src/greader.rs#L452)、[edit_tag](D:/fluxreader/src-tauri/src/greader.rs#L467)。外部参照：S1、S2。

**建议：** 明确 auth token 与 action token 的职责，统一携带必要授权头，按服务端兼容策略获取/发送写 token。不要粗暴地只为 FreshRSS 改一种格式而破坏现有 Miniflux 路径。

**回归验收：** 固定两类服务端响应/鉴权夹具，分别验证登录、订阅 GET、正文 POST、read/unread/star/unstar 往返；真实服务端测试另行约定账号与写入边界。

### F03 — Fever ID 类型不兼容，且十六位十进制 ID 会误解码

**P1｜B（生产类型与解析分支 + FreshRSS 官方源码）**

所查 FreshRSS Fever 输出的文章 id 来自返回 string 的 Entry::id()，JSON 也未强制转换为数字。本客户端 FeverItem.id 直接要求 i64，不兼容该字符串形态。

修好反序列化还不够：Fever 被转换成 Google Reader ItemContent，之后共用 parse_item_id。该解析器把长度为 16 且字符都属于十六进制字符集的字符串优先按十六进制解码。

~~~text
Fever 十进制线上值：     1791440000000000
按当前十六进制分支：     1698213301286076416
~~~

**影响：** 先表现为正文反序列化失败；仅补“字符串转数字”后，仍可能出现错误远端绑定、状态集合匹配错误和回传错误。此处数字计算验证了解码差异，没有冒充真实 Rust/FreshRSS 端到端测试。

**代码：** [FeverItem](D:/fluxreader/src-tauri/src/fever.rs#L93)、[Fever 转公共条目](D:/fluxreader/src-tauri/src/fever.rs#L477)、[共用 ID 解码](D:/fluxreader/src-tauri/src/greader.rs#L552)、[实际消费](D:/fluxreader/src-tauri/src/sync/entries.rs#L19)。外部参照：S3。

### F06 — 断开/切换账号后，在途同步仍可能回写旧数据

**P1｜C（高可信时序风险，未完成整条故障注入）**

**建议：** 定义能力矩阵和结果类型，区分“本地完成”“等待远端”“远端不支持”。支持重试的动作使用 outbox；不能把 unsupported 伪装成成功，也不能用日志中“下轮收敛”替代实际重试实现。

**回归验收：** 网络失败后重启仍保留可重试意图；Fever 明确本地范围；本地删除、远端删除、远端仍存在、墓碑解除四种状态分别覆盖。

### F18 — 配置同步是传输与导入合并，不是删除收敛协议

**能力边界｜B**

Gist/WebDAV 上传、下载、应用的实现存在，不是空壳。但配置应用对订阅和分类主要按名称/URL 更新或新增，没有删除传播。两端删除、改名、旧快照回放的冲突语义不足以保证最终一致。

**代码：** [配置数据结构与应用](D:/fluxreader/src-tauri/src/config_sync.rs#L138)。

**影响：** 用户若把“同步/覆盖本地”理解成完整镜像，两端会逐渐保留不同集合。若产品定义本来是“导入合并”，可以不实现删除传播，但名称和确认文案必须准确。

**建议：** 在“配置备份/导入”与“多设备状态同步”之间明确范围。若选择后者，再定义稳定身份、修订号、墓碑、冲突与回放；不建议直接用“远端没给就删除本地”作为修补。

### F20 — iframe 预过滤存在切片越界

**P2｜A（2026-10-08 反馈复核补证：从生产源码提取原表达式，rustc 1.98.0 独立编译并运行；不代表完整应用复现）**

### F23 — 启动时先显示居中窗口，再恢复上次位置

**P2｜用户实测反馈 + B（应用配置与锁定版本依赖源码）**

**用户实际观察：** 将客户端窗口移动到非居中位置，退出并再次启动时，窗口先出现在屏幕中央，随后跳到上次关闭位置。本会话中由用户反馈；审计者没有重新启动真实应用，以免后台抓取或同步对用户数据产生副作用。

**源码机制：**

1. 主窗口配置 center: true，未显式设置 visible；所用 Tauri 配置的默认可见性为 true，因此创建后即可显示居中窗口。
2. 应用注册默认 window-state 插件。Cargo.lock 锁定 tauri-plugin-window-state 2.4.1，它在 on_window_ready 中调用 restore_state，恢复是在窗口创建之后进行。
3. restore_state 再设置保存的位置、大小、最大化等状态。窗口已经可见时，用户便能看到从初始居中位置移动到保存位置。

**判断：** 现象说明保存的位置后来被成功读到，不是简单的“窗口位置没保存”；缺少的是首次显示之前的恢复屏障。这是原生窗口时序问题，不是 React 布局闪动或 RSS 数据加载造成的位置变化。

**代码：** [初始窗口配置](D:/fluxreader/src-tauri/tauri.conf.json#L13)、[默认插件注册](D:/fluxreader/src-tauri/src/lib.rs#L97)、[锁定版本](D:/fluxreader/src-tauri/Cargo.lock#L4703)。已核对本机依赖源码：[Tauri 可见性默认值](C:/Users/A/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tauri-utils-2.9.3/src/config.rs#L2029)、[插件恢复入口](C:/Users/A/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tauri-plugin-window-state-2.4.1/src/lib.rs#L407)、[恢复位置与显示](C:/Users/A/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tauri-plugin-window-state-2.4.1/src/lib.rs#L179)。依赖链接是该机器上的审计定位，不代表所有机器都有相同缓存目录。

**建议方案（尚未实施）：** 窗口初始不可见，由 Rust 统一顺序执行位置/尺寸/最大化恢复，再显示窗口。没有有效记录、状态恢复失败或原显示器不再存在时，回退到可见屏幕中的默认居中位置。不能仅改为 visible=false 后完全依赖插件默认 VISIBLE 标志：上次退出时处于托盘隐藏状态的记录可能使下次手动启动也不显示；首次启动和恢复失败同样需要显式显示兜底。

**不建议：** 只删除 center=true（仍可能从系统默认位置跳到保存位置）；增加固定 sleep/setTimeout（只是改变闪跳时机）；等前端网络/正文加载完成才显示（无关失败可能让窗口长期不可见）。

**回归验收：** 非居中位置冷启动时第一帧可见窗口就在恢复位置；首次运行、最大化后退出、多显示器/不同 DPI、拔掉原显示器、损坏状态文件、托盘退出后手动启动均不出现不可达窗口。托盘唤起和第二实例唤起不回归。Rust 编译与单元门禁由 Windows CI 承担；最终无闪跳必须用打包客户端实测，而不是浏览器 mock 或仅看配置断言。

## 8. 测试与工程门禁评估

### 8.1 当前门禁的价值和盲区

现有回归网确实覆盖了大量状态机、分页、缓存和 IPC 形态问题；不能因发现漏测就否定全部测试。但是通过 759 条断言并不能证明：

- mock 的鉴权、ID 和分类字段与目标服务端一致；
- 请求在途时用户再次操作不会丢失；
- 账号切换会使所有旧任务失效；
- SQL 第 N 次写入失败后可以恢复；
- React effect 和实际挂载生命周期没有错误；
- Tauri 生产 CSP、Windows SMTC、DPAPI 与浏览器模拟一致。

[frontend-regression.mjs](D:/fluxreader/tools/frontend-regression.mjs) 约 7600 行，混合状态测试、SSR、源码字符串和文案结构断言。应按领域拆分，并区分“保护业务不变量”和“锁住某种具体写法”。例如为关闭确认框补入第九个 overlay 是合理修复，却会被固定 length===8 的断言阻止。

### 8.2 Rust CI 的正确解读

[CI 配置](D:/fluxreader/.github/workflows/ci.yml) 包含默认 cargo test，以及六个显式 mock 集成套件的再次执行。默认 cargo test 会运行未标记 ignore 的单元/集成测试，**不能误读为整个项目只运行六个测试文件**。

真实服务端 live 测试和需要显式启动 HTTP 服务的 ignored 测试不会因为默认门禁就自动覆盖。每个这样的测试应有单独启动/停止服务、验证边界和执行责任人；不能盲目全局 include-ignored 而连到真实服务。

Rust 固定 Windows CI 是合理选择，它才能覆盖 DPAPI/SMTC 生产 cfg 路径。需要补的是证据与场景，不是改到 Linux 获得一个跳过生产代码的绿灯。

## 9. 性能、维护性与文档可信度

### 9.1 性能结论必须限定范围

[性能文档](D:/fluxreader/docs/performance.md) 的历史测试基于 v0.17.0 和合成 20k/50k 数据，提供了有价值的局部证据，但同时明确说明：

- 一部分旧视图切换计时受到 50ms 轮询粒度和就绪判据影响；
- 主要覆盖文本布局，没有完整媒体解码压力；
- 没有真实同步后端负载；
- JS 堆不等于 WebView2/进程 RSS；
- 顶部短时滚动不代表深度翻页和数小时长会话。

因此可以暂时保留单连接、继续利用虚拟化，但不能推导出“所有布局、同步、媒体和长会话均无需优化”。本轮也没有新的性能回归数据，不能反向声称必须立即上连接池。

### 9.2 推荐优化顺序

1. **先修正确性并降低写放大**：单源刷新事务化、精确确认、失败重试；这同时有潜在性能收益。
2. **测清不用的 FTS 成本**：当前搜索使用 LIKE，而文章更新会维护 FTS 触发器；评估取消、限定触发列或改搜索策略。中文搜索要单独评估分词、子串和查询语义，不能因默认 unicode61 不合适就推断所有 FTS 都不可用。
3. **给 DB 加观测而非先换模型**：记录等待锁、持锁、SQL、批次大小和 HTTP 时间；同步进行时对列表/详情延迟分别测量。
4. **画廊和媒体单独测**：画廊没有虚拟化，滚动加载后 DOM 可以继续累积；应测图片解码、可见节点、内存和返回位置，再决定瀑布流虚拟化。
5. **控制 UI 更新范围**：实体缓存通知与订阅选择器的重新计算范围可测量优化；避免以新的全局缓存掩盖派生数据不同步。
6. **最后做结构整理**：拆出布局组件与领域测试，保留共享交互规则，不复制五套各自演化的状态逻辑。

若真实负载显示 UI 被同步 SQL 阻塞，再比较专用 DB 执行线程、有限读连接与现有单连接的成本；数据库执行模型与连接数量是两个独立决策。

## 10. 建议执行路线与退出标准

### 第一批：正确性与安全止损

**范围：** F01、F02–F09，以及 F20 这样的不可信输入边界。

- 不可复用操作身份与按版本确认。
- 固定服务端契约夹具，修复认证、分类和 ID 编码。
- 账号代际与配置导入隔离。
- 所有正文写入的统一清洗边界。
- 单源刷新事务，以及已持久化范围的游标确认。

**退出标准：** 旧请求不能确认新操作；旧账号响应不能回写；旧密码不能因导入被发往新 endpoint；正文补全与首次插入同样安全；写失败不会被后续 304/增量游标永久跳过。

### 第二批：用户行为闭环

**范围：** F10–F17、F21–F23，及第 7 节设置/遮罩问题。

- 本地操作版本保护与明确的数据变化事件。
- AI 开关、分类继承、源码模式、截断状态。
- 订阅写入的本地/远端状态、重试和 unsupported 提示。
- 更新检查、媒体键幂等、凭据失败提示。

**退出标准：** 用户看到的设置就是行为使用的设置；“完成/同步/源码/播放”等文案能被可执行断言证明；失败具备可见恢复入口，不用永久假成功掩盖。

### 第三批：产品范围和结构优化

- 决定 F18 配置同步究竟是备份导入还是完整多设备收敛。
- 决定 F19 历史回溯范围、默认上限和后台资源预算。
- 确认同文跨源 read/star 传播语义后，再设计内容实体与各源条目分离。
- 拆分回归网与布局组件，基于真实负载评估 FTS、画廊、缓存和 DB 执行模型。

**退出标准：** 优化有基线、对照和回归指标；新模型有迁移/回滚策略；没有未定义的状态所有者或隐式协议分支。

### 不建议做的事

- 为获得“重构完成”标签而大面积搬文件、换框架或重写播放器。
- 仅修 mock 使 CI 变绿，不验证目标服务端差异。
- 在生产 CSP 中放开所有连接/脚本来掩盖更新检查问题。
- 把增量失败通过一次全量同步偶尔补救，视为已经恢复可靠性。
- 把完整历史/删除同步等尚未确认的产品扩展偷偷捆进第一批修复。

### 交付纪律

后续产品变更遵循仓库 dev → CI 验证 → main 的既有规则，追加迁移，不修改已发布迁移。每批以反例与退出标准收口，不以“增加了多少测试/减少了多少代码行”代替效果。涉及真实后端、数据种子、配置上传和删除前，应另行确认访问与恢复边界。

## 附录 A：F01 可独立复核的最小 SQL 反例

此例用于说明队列身份错误，**只能在新建内存数据库执行，不要复制到真实用户数据库**。表定义做了最小化，ROWID、删除替换和按 ID 确认与生产机制一致；不声称这是项目完整 Rust 集成测试。

~~~sql
CREATE TABLE articles (id INTEGER PRIMARY KEY);
INSERT INTO articles (id) VALUES (1);
CREATE TABLE sync_queue (
    id INTEGER PRIMARY KEY,
    article_id INTEGER REFERENCES articles(id),
    action TEXT NOT NULL
);

-- 旧 read 开始网络推送，调用方记下 queue_id = 1。
INSERT INTO sync_queue(article_id, action) VALUES (1, 'read');
SELECT id, action FROM sync_queue;

-- 网络期间用户改成 unread：现行入队规则删除旧项，再插入。
DELETE FROM sync_queue
WHERE article_id = 1 AND action IN ('read', 'unread');
INSERT INTO sync_queue(article_id, action) VALUES (1, 'unread');
SELECT id, action FROM sync_queue;

-- 旧请求成功，只按它保存的 queue_id 确认。
DELETE FROM sync_queue WHERE id IN (1);
SELECT COUNT(*) AS remaining FROM sync_queue;
~~~

实际观测的三个关键结果依次为 (1, read)、(1, unread)、remaining=0。修复后测试应保护新的 unread，而不是将队列清空。
