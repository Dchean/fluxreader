# 测试基线与门禁计划

TASK-002 已获批准并完成测量，结果见 BASELINE。本文保留使用的命令及后续测试方向；新任务按 EXECUTION-POLICY 的风险授权执行，不再把初始阶段的待批准状态当作当前状态。

## M1 的第一步：测量现状

1. 接受用户明确的基线授权并同步 PROJECT；核实源码仍对应 BASELINE，已有修改单独记录。
2. 记录 OS、Node/npm/Rust/Cargo、锁文件、提交和环境差异。本机 Node 24 与 CI Node 22 不同，不能把二者的结果直接认定等价。
3. 只按锁文件准备依赖；不升级依赖、不修改清单/锁文件，不修改全局工具链设置。需要额外安装或平台权限时遵循实际授权要求。
4. 核对默认测试与选定 mock 测试的副作用、端口及临时数据库范围，然后运行下面的已存在检查。
5. 保留首次结果，包括失败、跳过、零用例和环境阻塞；不给结果补写“通过”。
6. 输出基线报告和按影响排序的后续任务建议，不在测量任务中修产品代码、断言或 CI。

TASK-002 的目标是得到真实的测量结果。即使发现失败，也可以完成诊断交付；这不代表应用门禁通过或已经可以重构/发布。

```text
cargo test --manifest-path src-tauri/Cargo.toml --locked --test account_lifecycle_e2e --test ai_e2e --test dual_client_e2e --test sync_content_e2e --test sync_e2e --test sync_phases_e2e -- --ignored
```

执行器应逐条运行、分别记录退出码，不能用 shell 管道最后一个命令的成功掩盖前面失败。编译失败导致测试没运行时，编译记 FAIL，测试用例执行状态记 NOT_RUN/BLOCKED。

本仓库测试存在固定临时数据库名称。第一轮不同时启动多个相同测试进程或多个工作区的同一套基线，避免相互干扰。源码中对测试临时文件的清理需要确认落在测试临时目录。

## 此任务不运行的检查

- fever_live_e2e、fever_sync_live_e2e、greader_live_e2e：需要真实服务与测试账号，另行安排。
- ingestion_e2e / scheduler_e2e 的 ignored 场景：需要显式启动本地 feed 服务；先登记未运行，随后单独补齐 fixture 方案。
- 完整桌面 UI E2E：尚无已核实的自动化入口；不能把浏览器回退或 mock 测试充当此项。
- 真实 AI 内容质量评估：与确定性的协议/缓存测试分开，需要数据集、指标和费用预算。
- 新的前端格式器、依赖边界检查器：当前没有配置，不在测量时临时引入。

未运行项保持可见。缺少测试实现不属于“不适用”，也不能记为通过。

## 报告最小内容

每条记录包含 run_id、源码 SHA/快照、工具链、实际命令与工作目录、开始/结束时间、退出码、执行状态、用例执行/失败/跳过统计（工具能提供时）、原始日志引用及失败分类。

原始日志/安装包可放在 .cache/baseline/<run-id>/ 等被忽略目录；tasks/runs/ 保存不含凭据的简短报告与引用。报告需注明本机结果与 CI 的环境差异。

## 第二步：根据测量结果建立保护

保留范围已按 DEC-008 / DEC-009 明确为核心能力与 OPT-001～010；OPT-004 仅同步订阅源与客户端设置。先澄清具体行为，再按风险提出独立任务；保留决定不表示这些能力已经通过测试：

- 同步：初次/增量、分页、重复、离线队列、部分失败、状态冲突、协议切换、账号边界。
- 布局：五布局的正常/空态/错误态、选择与筛选、阅读状态一致性。
- AI：分片、取消、缓存、断流、错误传播、切换文章、译文清洗与渲染。
- 回归：将已确认缺陷关联 ISSUE/REQ 并放入合适的单元、集成或 E2E 层；不重复复制同一测试。
- 真实应用：先验证 Windows/Tauri 的驱动能力，再建立少量关键 E2E；浏览器 UI 工具只能证明其实际覆盖的边界。
- 架构：在目标边界被接受后，增加可执行的依赖/循环检查；设计合理性由独立审查补充。
