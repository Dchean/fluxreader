# 产品与治理边界

记录日期：2026-09-12。本文的“用户已确认”来自本次项目治理会话；源码事实另见 ARCHITECTURE 和 FEATURES。

## 产品目标

FluxReader 是现有的桌面 RSS 客户端。用户要求保留五种布局、通过 Google Reader / Fever 协议同步 FreshRSS / Miniflux 的核心能力，以及 AI 摘要和翻译。

本轮优化目标：代码可维护、架构边界明确、自动测试与回归测试可信、变更可追踪、需求可验收，并具有明确的回滚方式。性能数值、覆盖率阈值和具体架构方案尚未确定。

DEC-003 的用户原话：“先只允许考古与文档整理，建立测试基线前再确认。”

DEC-008 的用户原话：“调整一下，除了opt004其他的opt都要保留，调整会被影响的文档”。OPT 编号保留以便追踪；上述九项已经是必须保留的产品范围，不能继续标成可选。随后用户明确：“保留，但是功能调整为只同步订阅源客户端设置的数据”，记录为 DEC-009。所有 OPT 项均已确定保留，OPT-004 需要按收敛后的数据范围设计。用户进一步确认：“同步地址、模型等非敏感配置，不同步 API Key 和密码”。

DEC-004 仅免除旧数据兼容要求，不授予删除实际数据的权限。DEC-002 不自动授予当前考古阶段编码或运行应用测试的权限。

| DEC-013 | 解除批次任务数与单任务时间上限（2026-09-13 用户指令"解除项目数量和时间限制，直接跑完整个优化重构流程"）：管理 agent 自主跑完优化重构全部批次；CI 通过的 verified 候选可自主合并；发布仍需单独确认；真实服务/真实账号、新依赖等高风险边界不变 |

DEC-010 来自用户要求“agent负责项目管理，Claude负责代码编写”，并只偶尔审批高风险问题。低风险技术方案与 Note 的日常审查由管理 agent 承担；高风险和授权自身仍由用户决定。

DEC-011 的明确回复为“每任务最多 3 轮修复、90 分钟；每批最多 3 个任务”和“不需要设置费用上限”。未把费用上限为空解释成缺授权，也不把它解释成可扩大其他权限。

DEC-012 来自用户指令“后面统一调整调用 claude 的时候思考强度从 High 调整为 Max”。CLI 经 `--help` 核实支持 `--effort <level>`（low/medium/high/xhigh/max）；派发契约见 [CLAUDE-WORKER](CLAUDE-WORKER.md) 参数方案。

当前操作规则见 [HANDOFF](HANDOFF.md) 与 [EXECUTION-POLICY](../tasks/EXECUTION-POLICY.json)。这次交接准备没有执行新的编码批次。

## 已解决的范围问题

Q-SCOPE-001 已由 DEC-008 / DEC-009 解决：OPT-001～010 均保留，OPT-004 只同步订阅源与客户端设置。文章内容、媒体文件、已读/收藏状态和 AI 生成结果不属于这两类同步数据；Google Reader / Fever 的核心文章与阅读状态同步不受这一限制影响。

Q-CONFIG-SYNC-001 已解决：OPT-004 可同步服务地址、模型等非敏感配置，不同步 API Key、密码等敏感凭据。后续由具体任务明确字段清单，不能直接序列化整份 settings 或 ai_config。

Q-AUTOMATION-001 已由 DEC-011 解决；新管理 agent 按批准上限运行，不能自行追加预算。
