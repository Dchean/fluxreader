## 一次交接的顺序

### 1. 旧设备保存现场

由当前管理 agent 执行，不要求用户逐项手工整理：

1. 停止派发新工作。让属于当前任务的 Claude 和验证命令在剩余预算内结束；需要中断时保存输出并记录中断，不将部分结果写为 PASS。不要按复制来的 PID 终止其他进程。
2. 确认这份工作区只有一个写入者。导出开始后保持源文件不变；导出后旧设备不再继续修改该候选，直到交接取消或明确交还。
3. 核对完整 Git 差异，包括未跟踪文件、删除和重命名。当前未提交的 docs、tasks、AGENTS、CLAUDE、Note 和源码都是交付内容，不能只复制一个 Git 提交。
4. 为本次移交保存一份时间真实、路径相对的交接记录，建议位置 `tasks/handoffs/HANDOFF-<唯一标识>.json`。这是快照说明和索引，不是第二套任务状态权威。
5. 制作筛选后的交接目录或 ZIP，并生成逐文件 SHA-256 清单。复制完成后重新核对源文件和导出文件；有差异则先确认来源，不能交付一份混合时间点的快照。

进行中的任务若必须停下，可用项目已有的 `blocked` 状态说明 `handoff` 原因，保存中断前状态和恢复动作；不要为交接引入与 `status` 冲突的第二套 ready/verified 标记。已完成的任务保留真实状态，不能为了恢复再降回 ready。

交接记录至少说明：

| 内容 | 应保存什么 |
| --- | --- |
| 身份和事实源 | 项目、handoff_id、原 task_id/batch_id，以及 PROJECT、EXECUTION-POLICY 和任务文件的相对路径 |
| 源码与快照 | 实际 Git HEAD/分支或无 Git 的事实、当前工作区文件清单、补丁/快照摘要、哪些是既存未提交改动 |
| 进度与下一步 | 停在实现、验证、审查还是等待批准；完成及未完成动作；下一条允许执行的动作 |
| 运行记录 | 同一任务的全部尝试、Claude 结构化输出、可信命令、真实退出码、审查及证据路径 |
| 原预算 | 首次开始时间、原截止时间、已用修复轮和批次任务数；有争议的统计必须注明，不能猜填 |
| 写入者交接 | 源设备上的任务进程是否已结束、源工作区是否停止写入、待目标设备确认接管 |
| 环境 | Windows、Node/npm、Rust、构建工具及 CLI 版本；只存必要的非敏感信息 |
| 未决事项 | 具体阻塞、历史批准缺口、待确认的高风险事项、合并和发布状态 |
| 携带与排除 | 包内文件摘要、脱敏证据对应关系、未携带产物及原因 |

运行中的进程、CLI session、PID 和旧机权限批准不能直接迁到新设备。恢复的是任务与已保存产物，不是原来那个进程。

### 2. 只复制需要携带的内容

推荐复制管理 agent 制作的交接副本；原工作区留在旧机，不要剪切搬走。当前缓存中已确认存在认证令牌，因此不要直接全选压缩整个目录。

| 内容 | 处理方式 |
| --- | --- |
| src、src-tauri 的源码/配置/测试、tools、.github、锁文件及根配置 | 携带当前实际内容，包括已确认的未提交变更；排除其中的生成目录 |
| docs、tasks、AGENTS.md、CLAUDE.md、README.md | 携带，包含本轮全部报告和交接记录 |
| .agents/notes、项目所需 .agents/skills | 携带；保证隐藏目录没有在复制时遗漏 |
| workflow-kit | 如需参考则携带完整工具包；它不是已接入本项目的状态控制器 |
| .cache/baseline、.cache/runs、.cache/reviews 中必要证据 | 由管理 agent 逐项选择并检查/脱敏，只带被任务和审查引用的输入快照、日志、结果、哈希；不整目录复制 |
| .git 与历史 | 优先用管理 agent 核实并试恢复的 Git bundle 携带所需历史，配合完整工作区快照；若复制普通 .git 目录，须先确认它是独立仓库且不含需排除的本机配置。worktree 的 .git 指针文件不能直接搬用 |
| node_modules、dist、dist-test、src-tauri/target、生成 schemas、临时测试数据库 | 排除，在新设备按锁文件重建。若某个安装包是验收证据，单独列明是否携带及其哈希 |
| .env、API Key、密码、令牌、私钥、真实应用数据库、用户目录的 CLI 配置/登录信息 | 排除。新设备在相应工具中自行登录或按实际批准配置 |
| 本机 run-settings.json、probe-settings.json、复制了 env 的脚本或日志 | 不直接携带；只保留经过检查的非敏感信息或脱敏副本 |

仅凭 `.gitignore` 不足以决定安全的移交范围；路径允许清单也不能代替内容检查。原始日志含敏感信息时保留受控原件，移交脱敏副本，记录对应关系与脱敏副本哈希，不声称二者字节相同。

尽量在交接副本中保留证据原有的项目相对路径。若从 `.cache/` 迁到专门的证据目录，在交接记录中列出“原引用 → 包内相对路径”；不要改写历史报告里的源码版本、结果或运行时间。

只带源码、不带 Git 历史也可供阅读和继续准备任务，但必须记录为 snapshot-only，不能声称新目录已有旧 HEAD。准备提交或合并前，由管理 agent 在获准范围内恢复并验证真正的 Git 基准。不要把 Git bundle 或补丁直接覆盖到另一个有未提交修改的工作区。

### 3. 新 Windows 设备先验收交接包

1. 放入一个新的独立目录，例如任意盘符下的工作目录；目录可以与旧机不同。先查哈希和文件清单，确认最新源码、未提交文档、任务与证据齐全。
2. 在管理 agent 中打开这个项目根目录，使用 [MANAGER-RESUME](prompts/MANAGER-RESUME.md)。不要调用首次初始化流程。
3. 自动发现当前根目录、Git、Node/npm、Rust/Cargo、Windows 构建工具和 Claude CLI；不照抄旧机用户名、盘符或 claude.exe 绝对路径。旧报告中的绝对路径只用于识别历史来源。
4. 需要准备依赖时，沿用 package-lock.json 与 Cargo.lock，不顺带升级。新机缺少系统工具或登录时记录具体缺口，由用户在对应工具中配置；不要求用户把令牌粘贴进对话或文档。
5. 根据新机实际能力核对 Claude 参数、权限限制、已有模型选择和认证方式。缺少受限能力时不能静默删参数；原机批准的宿主权限不自动成为新机批准。
6. 创建新机的环境/恢复记录。旧机 PASS 作为历史证据保留；新机未运行的检查为 NOT_RUN。当前补充验证需遵守预算，BATCH-001 已满额时先准备范围和命令，不直接开始新的执行批次。
7. 在有剩余或新批准预算后，运行本任务要求的必要检查。Windows 平台相同并不保证依赖、SDK、路径或网络相同，不能把旧安装包或测试结果直接冒充新机验证。
8. 核对源机已停止写入后确认接管；仍沿用原任务身份和候选，不回退重做已有实现。

对于没有变化的独立部分，可以按哈希和原环境记录复用历史证据；需要证明“新环境也能构建/运行”的检查必须在新机真实执行。现有无浏览器前端回归不能代替真实桌面 UI 验收。

### 4. 处理中途转移与预算

现有策略是 **90 分钟墙钟时间/任务**，包含诊断、重放、验证、审查和等待。换设备、复制文件、换 agent 都不会自动暂停或重置截止时间。

例如原任务截止时间为 15:30，新设备在 16:00 才接管，就应保留原任务和产物，记录预算已耗尽，并请求用户追加；不能从 16:00 重新获得 90 分钟。若以后希望只计算实际工作时间，需要用户明确变更预算策略，本指南没有作此变更。

同样，已启动过的任务仍占用原批次额度；取消、换名、搬迁或重开对话都不能释放名额。本次 BATCH-001 已满额，下一批仍需用户确认。

## 与 workflow-kit 的关系

`workflow-kit/project-workflow/` 是通用流程包，其说明可复用，但其 STATE/POLICY 模板与本项目已有结构不同。FluxReader 目前的权限源仍是 `tasks/EXECUTION-POLICY.json`，已接受决定仍见 PRODUCT 的 DEC 表。

不要对当前仓库直接运行工具包 init、复制模板覆盖 PROJECT/任务，也不要为了让通用 check 通过而改写旧任务身份、预算和验证状态。若要正式接入其校验、看板或执行适配器，先提出明确迁移任务与验证方案。该工具包自己的测试成绩不等于 FluxReader 或新设备已经通过验证。

## 用户只需怎样操作

交接前，让旧管理 agent 按本文保存现场、制作并检查交接副本；将副本复制到新设备；在新设备项目根目录给管理 agent 发送：

> 请读取 docs/prompts/MANAGER-RESUME.md，并按其中接续 FluxReader。沿用现有任务、需求、权限和预算；先核对交接快照及所有相关运行证据。需要批次追加、高风险决定、合并或发布时，准备具体方案后再提交给我。

管理 agent 应先报告“恢复到哪个任务/阶段、证据是否齐全、剩余预算、下一允许动作”。只有真正缺少事实或授权时再询问用户，不能每换一台电脑就从产品定义重新开始。
