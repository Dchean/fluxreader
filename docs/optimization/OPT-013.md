# OPT-013：AI 完成状态与缓存恢复

Status: coding
覆盖F15。前置OPT002/011/008B；008B的内容实体与修订契约稳定后再派发缓存改造，避免两名执行者同时修改正文所有权。

## 设计与接口

SSE解析明确记录finish_reason与[DONE]/合法完成信号，stop自然结束才是完成产物；length/content_filter/协议EOF/网络中断/取消分型。不完整返回明确错误/完成结构，前端保留可见partial但标记未完成，提供重试/继续/清除入口，不写可复用完整缓存。无论SSE尾换行与TCP chunk如何切分都一致。

摘要与翻译共用完成语义，不能只修翻译。缓存键应至少考虑源内容修订与模型/提示词变化，或配置变化后明确失效策略；不能因已缓存任意非空就阻止重试。超长翻译按合理段落分块（保留HTML结构，不按字节切断标签），中途失败不把部分缓存当整篇，重试可以从已完成安全片段继续；服务端不支持继续时允许整篇重新生成但告知。

## 剩余范围定版依据（2026-10-12，尚未派发）

主控查阅真实入口确认：commands/ai.rs 当前只凭非空旧产物命中缓存，模型配置与提示词分两次读取，生成后按 article_id 无条件提交；前端 slices/ai.ts 也按非空产物短路，并存在 Done 后异步回读。013A只保证单次流与提交成功语义，不证明缓存适用于新的内容/配置或请求。

1. **输入与缓存身份**：一次读取有效模型/endpoint/提示词和正文输入快照；缓存签名覆盖实际发送的标题、正文修订、产物类型、模型与有效提示词、分段策略版本。凭据不得出现在公开签名、日志或IPC元数据中。旧无签名产物保留数据但不得冒充已验证缓存；其可见性与重新生成入口须明确。配置变更后前端非空短路也必须失效，不能只修后端缓存判定。
2. **提交与生命周期**：网络生成不持有DB锁；提交时复核内容身份/修订与清除代次。全文替换、远端正文更新、条目删除、共享内容分叉、用户清缓存后，旧请求不能写回或发Done冒充当前成功。前端delta/Done/安全回读按请求代次守卫，过时回包不得覆盖较新成功结果。按实际受影响键协调并发，不给全应用AI加无关串行锁。
3. **分段与恢复**：翻译以可重组的HTML结构/文本节点为边界，不截断UTF-8、实体或标签；超长单节点也需有界拆分。保留链接、列表、表格与嵌套结构，最终产物仍净化。完成片段独立记录且绑定同一输入签名，重启后可恢复；只有全部片段完成才形成完整产物。失败片段不追加重复文本，配置/正文变更不混用旧片段。摘要长输入同样要有明确策略，不静默截掉后半篇；超预算明确失败，不能假称完整。
4. **真实消费者**：Reader及卡片入口可区分生成中、部分完成、失败、完整、已过期，提供实际接线的重试/继续/清除。部分结果始终按安全显示规则处理，不能刷新后被当完整缓存；清除必须影响后台恢复记录而非只清前端文字。进度事件如需扩展要同步类型/组件/测试，不保留无人消费的字段。

补充确定性验收：严格loopback SSE观察长HTML实际发送的多段输入与顺序；第二段失败→重启→只重发未完成段；模型/提示词/正文变化后不复用旧片段；请求在途全文更新/清缓存→旧提交被拒且无Done；前后两次安全回读逆序→新结果不被覆盖；分类/源自动触发与手动入口并发不重复计费请求；全部完成/截断/过滤/取消/持久化故障均保持013A语义。真实付费API仍不在本卡测试边界内。

## 主控定版（2026-10-15，派发版）

现状核对（主控读源码）：`commands/ai.rs` 只凭 `ai_summary`/`translated_content` 非空短路，缓存签名不存在；`load_ai_config` 与 `load_prompts` 分两次读配置；`commit_*_cache` 已带 `AiCommitToken`（ai_epoch + content_id + revision）前提校验，但未记录生成时使用的输入/模型/提示词；`store/slices/ai.ts` 前端也按非空产物短路，译文回读无请求代次守卫；`ai.rs` 无分段能力，超长正文一次性送 `stream_chat`。013A 已完成严格 SSE 完成语义，父卡范围不变。

本条为 013A 之后的父卡实现定版，四项交付按顺序推进，前两项为一个提交边界，后两项各为一个提交边界：

1. **输入与缓存身份**（013-B1）
   - 新增 AI 产物缓存签名：`sha256(产物类型 ‖ 模型 ‖ base_url ‖ 有效 system 提示词 ‖ 标题 ‖ 正文修订(content_id,revision) ‖ 输入正文哈希 ‖ 分段策略版本)`；`api_key` 不得进入签名、日志或 IPC 元数据。
   - `ai_config` 与提示词在**同一把 DB 锁内一次性读取**成快照，生成与提交使用同一快照，不允许再出现模型配置与提示词分两次读的窗口。
   - 缓存命中判定改为「产物非空 **且** 签名匹配」；旧无签名产物不冒充已验证缓存：保留数据、参与 UI 显示，但带明确「未标记版本」状态并可被重新生成覆盖。
   - 签名与产物写入必须与产物同一次 UPDATE（同事务）；签名写入失败整体失败，不许出现「新产物 + 旧签名」或「新签名 + 旧产物」。
2. **提交与生命周期**（013-B1 同批）
   - `AiCommitToken` 扩展为包含签名所需输入前提，提交时在单条 UPDATE 的 WHERE 内复核签名前提（内容修订/清除代次/输入身份），迟到产物不得写回。
   - 前端新增请求代次（请求发起时自增的每条目序号）：`delta`/`Done`/安全回读按代次守卫，过时回包不得覆盖较新成功结果；前端非空短路同样必须验签名，配置/提示词/正文变化后旧产物不得短路。
   - 并发策略按条目键协调：同一 `(article_id, 产物类型)` 至多一个在途请求；不同条目/不同产物互不阻塞，不给全应用 AI 加无关串行锁；自动触发与手动入口复用同一在途请求而不重复计费。
   - 清除必须同时使签名失效，不得只清前端文字。
3. **分段与恢复**（013-B2，独立提交）
   - 翻译按可重组的 HTML 结构/文本节点边界分块：不截断 UTF-8、HTML 实体或标签；链接、列表、表格与嵌套结构在最终产物中保留；超长单节点有界拆分（如按文本节点递归切分并保持标签边界）。
   - 摘要长输入要有明确策略：超预算时显式失败或分段摘要后合并，不得静默截掉后半篇或假称完整。
   - 每个完成片段独立持久化并绑定同一签名，重启后可恢复；只有全部片段完成才形成完整产物；失败片段重试不追加重复文本；配置/正文变化后旧片段不复用。
   - 服务端不支持继续时允许整篇重新生成，但必须在 UI 明确告知用户。
4. **真实消费者**（013-B3，独立提交）
   - Reader 与卡片入口区分「生成中 / 部分完成 / 失败 / 完整 / 已过期（签名不匹配）」；重试 / 继续 / 清除三个入口真实接线，清除影响后台恢复记录（片段持久化）而非只清前端状态。
   - 部分结果始终按安全显示规则处理（沿用 `rawTranslatedIds` 纯文本渲染口径），刷新后不得被当成完整缓存；进度事件若需扩展必须同步 Rust 类型、前端类型、组件与测试，不留无人消费字段。

### 013-B3 主控定版（2026-10-15，派发版）

权威需求见上一条第 4 款。B2 已把后端状态与恢复原语落齐（`ai_cache_check` 返回
`translationSegments{total,completed,discarded}`、片段持久化、签名隔离、全段齐备
才提交、`aiIncomplete` 显式失败、`rawTranslatedIds` 纯文本预览口径），B3 只做
「真实消费者」：把这些原语变成 Reader/卡片可见、可操作、刷新后仍正确的状态。

**交付 1：状态模型（前端单点真值）**

- 每个 `(article_id, 产物类型)` 计算五态之一：`generating` / `partial` / `failed`
  / `complete` / `stale`，规则以实际数据判定，不得再用「产物非空即完整」：
  - `generating`：该条目该产物有在途请求（现有 `inflight` 登记）。
  - `complete`：产物非空且签名与当前输入签名匹配（沿用 B1 命中语义）。
  - `stale`：产物非空但签名不匹配或缺失（旧无签名产物）。
  - `partial`：无完整产物，但当前签名下 `0 < completed < total`（B2 片段）。
  - `failed`：无完整产物、无可用已完成片段，且存在明确失败分型/最近错误。
- 状态派发必须与既有 `ensureAiProduct`、`rawTranslatedIds`、`inflight` 在同一
  切片内，杜绝 Reader 与卡片各算一套；不得在组件内复制判定逻辑。

**交付 2：三入口真实接线**

- 重试：对 `failed` 发起一次全新生成；不得被「旧产物非空」短路。
- 继续：对 `partial` 复用已完成片段、只发缺失段（B2 已支持的恢复语义）；入口
  必须真实调用后端，不得只改前端文案。
- 清除：调用后端清除命令，同时删除该条目该产物在**所有签名**下的持久化片段
  （后台恢复记录），再清前端状态；不得只清前端文字而留下可靠重启续译的片段。
  清除后该条目回到「无产物/未生成」，不得显示 `partial`。

**交付 3：部分态安全显示与刷新一致性**

- `partial`/`generating` 的可见文本一律走 `rawTranslatedIds` 纯文本渲染；刷新
  或重新进入阅读器后，`partial` 仍显示为未完成（不得被当成完整缓存），`stale`
  显示为「已过期」并给出重新生成入口。
- 安全回读与代次守卫沿用 B1，不得因新状态机回退过时回包保护。

**交付 4：事件与类型同步**

- 若新增/扩展进度事件，Rust 类型、`src/lib/api.ts` 类型、切片、组件、前端与
  组件回归必须一次同步，不留无人消费字段；能复用 `ai_cache_check` 现有响应则
  不新增事件面。

**B3 强制反例（先红后绿，真实执行并保存证据）**

1. 五态判定表：同一组夹具数据在切片层得到 `generating/partial/failed/complete/
   stale` 唯一且互斥的结论；不存在「产物非空=complete」的回退路径。
2. `partial` 刷新重启后仍为 `partial`，可见文本按纯文本渲染，且不被 `complete`
   短路命中；B2 已完成段数在重启后不减少。
3. 继续入口：第二段失败后触发「继续」，只重发缺失段（断言实际发送段数/序号），
   已完成段不重发、结果不重复。
4. 清除入口：清除后全签名片段为空、整篇产物为空、状态回未生成；再「继续」不得
   复用任何旧片段（断言零恢复）。
5. `stale`：签名不匹配的旧产物显示为已过期，重新生成后签名与产物同时更新；
   不得在重新生成前被当完整缓存短路。
6. 既有回归不退化：B1 代次守卫/在途复用、B2 分段恢复、013A 分型（length/
   content_filter/取消/干净 EOF）全部保持绿。
