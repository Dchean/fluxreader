# OPT-022：手动同步完成态与远端写回确认

Status: verified-ci
审计覆盖：P1（同步状态不收敛）
前置：v0.18.1 实机复现（2026-10-20）
通用约束与验收流程：[路线](README.md)

## 交付目标

手动同步必须明确区分“远端写回已确认”和“整轮同步仍在拉取/刷新”，并且在所有
成功、失败、异常、超时和组件生命周期变化下收敛到确定的终态；不得出现远端已读
已经成功、客户端却长期停留在“同步中”的不可解释状态。

本卡先以真实源码和可重复前端夹具确认状态机，不对同步协议或 outbox 语义做
无证据重写。

## 已核实事实

- `src/store/slices/sync.ts` 的 `triggerManualSync` 在开始时写入
  `syncStatus='syncing'`，只有整条 feeds→states→refreshAllFeeds→reload 链
  最后成功才写 `synced`；任一步抛错才写 `error`。
- `states_phase` 的远端推送段在 `src-tauri/src/sync/phases.rs` 先执行，
  随后还要 `pull_entries`；远端已读确认并不等于手动同步完成。
- 当前 `syncStatus` 是进程内 UI 状态，不持久化；强制退出后不能从它推断同步
  任务仍在继续。
- 现有实机反馈：远端已读已成功，本地仍显示同步中；随后强退并重启，启动失败由
  OPT-021 的空集计数问题独立承接。

## 非目标

- 不把同步状态改造成持久化任务表，不引入新的后台任务框架。
- 不改变 Google Reader/Fever 的协议动作、队列幂等或失败重试语义。
- 不把“远端已经写回”误报成“整轮拉取已完成”。
- 不用固定延时定时器假装所有网络操作已经结束。
- 不处理 OPT-021 的 SQL 空值；两卡可独立验收。

## 实施要求

1. 先复现“远端写回成功但 UI 仍为 syncing”的最短路径，区分是：
   - `states` 推送已完成、`pull_entries` 仍在进行；
   - `refreshAllFeeds` 在等待网络/抓取；
   - `reloadFromBackend` 失败；
   - 某个 Promise 未返回。
2. 为手动同步建立单一、可测试的状态推进点；任何非等待路径都必须收敛到
   `synced` 或 `error`，并保留阶段/错误摘要。
3. 如果整轮同步确实仍在执行，UI 应显示可理解的阶段状态，而不是笼统的永久
   “同步中”；不得把“远端 outbox 已清空”直接伪装为“全部同步完成”。
4. 防重复点击：并发或重入调用不得让较早请求覆盖较新的终态；组件卸载/重新挂载
   不得留下无法恢复的全局忙锁。
5. 至少覆盖：
   - 远端 push 很快、pull 很慢；
   - push 成功、refresh/reload 失败；
   - 请求 reject；
   - 重入/重复点击；
   - 切换到其他页面后返回同步设置页；
   - 终态后 `syncStatus` 不再保持 `syncing`。

- `syncStatus` 的生产写入统一通过 activity owner/generation 协议；手动同步、添加
  订阅、保存后同步和 GitHub 断开均受同一协议保护，旧终态不得覆盖新终态。
