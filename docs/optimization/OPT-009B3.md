# OPT-009B3：订阅写回能力声明、持久回执与确认文案

Status: verified-ci
## 目标

在 OPT-009 B1/B2 已落地的类型化订阅 outbox 之上，把**远端能力边界**与**持久写回状态**如实暴露到 IPC 与 UI：用户能区分「本地已保存并等待远端」「远端已确认」「该协议不支持远端写回」，而不是只看一次性 toast。同时订正与 B2 实际语义不符的确认文案（删除源现在会产生持久退订意图）。

本卡只做**呈现与能力声明**，不重做 B1/B2 的执行器与队列语义。

## 现状证据（主控已核对，实施前必须自行复读）

- `src-tauri/src/db/outbox.rs:598-625`：`SubscriptionOutboxStats{pending, failed, local_only, last_error}` 与 `subscription_outbox_stats` **已存在**，但没有任何 `#[tauri::command]` 暴露；B1 的注释写着「UI 呈现由阶段 B2 接线」，实际未接。
- `src-tauri/src/sync/credentials.rs:123-128`：`Backend::supports_subscription_write()` 只在执行器内部用（`sync/subscriptions.rs:352`），没有公开的协议能力矩阵。
- `src-tauri/src/commands/folders.rs:934-951`：删除源已持久入队退订意图并即时尝试写回，返回值仍是 `AppResult<()>`；`update_feed:971-1019` 同理。
- `src/components/settings/FeedsTab.tsx:82`：确认弹窗仍写「同步服务端不受影响」——与 B2 落地的持久退订语义**直接矛盾**，属本卡必须订正的事实错误文案。
- `src/lib/syncPill.ts` 与 `SyncTab.tsx` 只展示 `sync_queue`（文章状态）四态；订阅 outbox 的 pending/failed/local_only **在 UI 完全不可见**。

## 必须交付

1. **协议能力矩阵（后端单一事实源）**：新增只读 IPC（建议 `subscription_capabilities`），返回结构化能力，至少区分每个动作（新增/编辑标题、移动分类、退订、分类改名、分类级删除、空分类远端表达）在 GReader / Fever 下的 `Supported` / `LocalOnly` / `Unsupported`。不得用「无操作 Ok」或字符串自由文本冒充结构化类型；枚举的 serde 名称即前后端契约，前端类型必须与之逐字一致。
2. **持久回执查询**：暴露订阅 outbox 状态给前端。至少包含 pending（含失败子集 `attempts>0`）、`local_only`、最近错误摘要，以及**当前账号限定**——异账号暂停的队项不得混入当前账号的计数（B2 已建立 account_key 语义；若 `subscription_outbox_stats` 现在是全库口径，必须收窄或在 IPC 层按当前账号过滤，并补测试说明选择）。不得暴露 token、密码、密文或完整 URL 中的凭据参数。
3. **事件驱动更新**：订阅 outbox 状态变化（入队、确认出队、失败累计、local_only 标记）必须推送到前端，使 UI 不依赖用户手动刷新设置页。复用现有 `sync-queue-changed` 模式（见 `src-tauri/src/sync/push.rs:262-282`、`src/App.tsx:150-165`）；若新增独立事件，需说明为何不能复用，并保证未配置同步时不发噪声事件。
4. **UI 持久展示与如实文案**：在设置页同步摘要卡（`src/components/settings/SyncTab.tsx`，`syncStateSummary` 在 `src/lib/syncPill.ts`）展示订阅写回状态：
   - 有待推/失败项 → 明确「订阅写回：等待 N 项 / 部分失败 M 项 + 最近错误」；
   - 有 `local_only` 项 → 明确该协议不支持远端写回、仅本地生效（不得写成成功，也不得隐藏）；
   - 无待办 → 不新增噪音行（保持既有「无队列不制造噪音」口径）。
   Fever 连接下必须能看出「编辑/新增/退订为仅本地」而不出现「已同步」错觉。
5. **确认弹窗事实订正**：`FeedsTab.tsx` 删除源与删除分类文案必须反映真实语义——本地条目删除 + **持久退订意图（可在离线/重启后重试）**；分类删除要说明其成员逐源退订与空分类的本地-only 边界（`record_folder_rename` 注释：空分类无成员时可验证的远端表达不存在）。不得继续写「同步服务端不受影响」。文案必须与后端能力矩阵同源或逐字对齐，不允许两处各写一套说法。
6. **限制清单（用户可见的能力边界）**：把 B2 已登记但尚无任何 UI 呈现的限制落到界面上或其后端返回中（择一，说明理由），至少包含：分类级改名/删除无分类级端点、用逐成员 `a=`/`r=` 表达；空分类改名不宣称远端已改；400 容忍把「目标不存在」近似为退订已满足（远端可能残留孤儿，直到 pull 确认回收）；非幂等 quick_add 服务端下删除+快速重加可能有界重复订阅；分类级命令不立即推送、等待下一轮同步（`rename_folder`/`delete_folder` 不调用 `try_push_subscription_outbox`）。
