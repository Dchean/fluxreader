# OPT-017：搜索、媒体与缓存性能

Status: verified-ci
覆盖：FTS零消费写放大、画廊非虚拟化、正文缓存/同步锁等待、封面后台覆盖与toast恢复入口。前置OPT007/008/016。

## 观测先于结构替换

在隔离合成库测20k/50k篇真实正文：列表/详情/search/feed_counts和同步写批次，分列DB等待/执行、JS堆、WebView RSS、媒体解码和DOM节点。不能以只载首页22卡证明深度滚动无界缓存安全。测量只访问假服务器/临时DB，不向真实账号同步；未执行的指标写未测。

## 必须消除的确定性成本与行为问题

- articles_fts当前无MATCH消费者；当前read/star已不触发FTS（v14限定内容列），不得基于相反前提实施优化。需评估的是内容写入继续维护无消费索引的成本。比较“删除FTS及触发器”和“仅正文更新维护+实际trigram/分词搜索”的收益/兼容性，按中文/英文搜索行为和数据规模决定；追加迁移，旧库不损失实际文章。
- gallery全量items.map长期滚动DOM累积，采用有可验证窗口上限的瀑布流虚拟化（现有tanstack-virtual或分行模型），保持图片比例、焦点、键盘/灯箱/返回位置与加载更多。若规模测量证实当前范围可接受也需明确边界与上限，不能无证据写无需优化。
- toast上限不能悄悄挤掉唯一重试入口：统一错误中心或重试项合并/持久可达，不能通过无限toast堆积解决。
- 封面补全不应仅source=direct导致服务端文章永不补；有预算/并发/超时/失败缓存，应用退出不残留任务；忽略DB失败要返回明确日志/可观测结果。
- numericId重复实现与零消费API/事件清理必须先搜实际消费者并锁行为，不删暂时未调用但有public契约。

## OPT-008B后的测量接点（2026-10-12）

017A旧基线不含本轮条目独立/显示去重及读闭包，不能直接拿它与新实现作优化前后对照。待008B完整落地后，在同一构建与固定种子语料上建立当前生产API基线，再对实际优化作对照；保留017A历史数值，不覆盖或拼成同构建曲线。

- 除列表/搜索外，测实际前端消费的组合计数快照（当前008B WIP为counts_snapshot）、读闭包写入与回执大小。数据覆盖无重复、多源少量重复、高重复组、同feed不同remoteID；去重开/关、布局/分类范围、深页和中英文无结果/唯一词/常用词分别观测。查询代表选择、同文读传播与独立收藏不可为了速度改变。
- 单DB锁内组合计数保证一致性，也可能扩大持锁时间；记录执行耗时与实际锁等待，不能把IPC总时长直接叫锁等待。优先优化无用扫描/关联子查询/索引，再按证据决定是否改连接模型。
- 画廊现有gallery-masonry-grid仍单独走非虚拟列表，需从真实渲染分支验证；useVirtualizer存在不代表画廊已虚拟化。实际滚动、图片尺寸变化、灯箱关闭恢复、键盘焦点与加载下一页都纳入固定场景，jsdom不能证明真实布局性能。
- 重试入口持久可达与有界内存同时验收；将回调无限存入另一数组不算解决toast容量问题。封面候选读失败/写失败不得压成空集合或0后把任务标为已处理，必须有可诊断且有界的恢复行为。

本节只确定后续验收接点，未执行新基线、未宣称性能改善；实现边界在008B稳定后按实际模块进一步收窄。
