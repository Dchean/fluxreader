# 工作流程

当前项目阶段见 [PROJECT.json](../tasks/PROJECT.json)，用户决定见 [PRODUCT](PRODUCT.md)。本文件定义可由人和不同 agent 执行的流程，不代表已有自动控制器。

## 先后顺序与里程碑

| 里程碑 | 产物和退出条件 | 用户参与 |
| --- | --- | --- |
| M0 治理与首轮考古 | 状态与权限记录；功能清单；现状图；测试入口；问题清单；具体基线任务。未知项明确，不宣称完成全面代码审计 | 审阅启动包，明确是否进入基线阶段 |
| M1 测试基线 | 先复现现有检查，再提出并实施获准的测试补齐/问题修复任务；关键行为和已知失败可追溯 | 对影响业务规则的问题作决定，验收基线里程碑 |
| M2 模块方案与重构试点 | 按模块提出保留/整理/替换/删除决策；形成目标边界；完成一条代表性试点及验证 | 确认涉及范围和行为的取舍，验收试点并确认合并 |
| M3 自动总控试点 | 如需常驻/更强程序保障，再在已跑通流程上实现状态机和适配器；不作为当前管理 agent 调度 CLI 的前置条件 | 审批新增能力或预算调整，验收控制器 |
| M4 持续优化与发布 | 按功能/里程碑循环交付；保留需求、代码、测试、验收、版本之间的关联 | 集中验收和合并；单独确认发布 |

TASK-002 初始测量已完成。当前以 [HANDOFF](HANDOFF.md) 和 [EXECUTION-POLICY](../tasks/EXECUTION-POLICY.json) 进入管理 agent 驱动的交付模式；不要求先实现独立控制器程序。低风险任务可由管理 agent 检查 Ready 条件后推进。

M1 的测试保护、M2 的模块处置和后续验收均以 FEATURES 中已确认保留的核心及全部 OPT 项为范围。模块实现可以整理或替换，不能因此删除已确认保留的功能。OPT-004 按仅同步订阅源与客户端设置的目标设计：地址、模型等非敏感配置可同步，API Key、密码等敏感凭据排除。具体任务需给出字段清单与对应验证，不再把功能保留范围作为未决问题。

考古、现状架构、行为清单和问题列表相互修订；不要等整个代码库读完才建立第一张现状图。测试发现与文档冲突时，记录冲突并追踪依据。

## 每个功能增量的 Phase 0–10

| Phase | 活动 | 足够进入下一步的条件 |
| --- | --- | --- |
| 0 | 需求定义 | 用户目标、非目标和可观察的验收标准明确 |
| 1 | UX / 交互 | 涉及界面行为时定义正常/错误/空态流程；纯内部改动可注明不适用 |
| 2 | 技术约束 / 选型 | 先确认现有约束，有具体理由才重新选型；必要决策写 ADR |
| 3 | 架构设计 | 边界、接口、数据流和变更影响可审查 |
| 4 | 测试设计 | 每项验收要求对应证据来源，明确环境、数据和测试层次 |
| 5 | 任务拆分 | 任务满足下方进入条件，能独立交付证据 |
| 6 | 编码 | 在任务允许范围内执行，保留实际变更 |
| 7 | 自动验证 | 执行适用门禁，保留真实结果；失败分类处理 |
| 8 | 代码审查 | 独立上下文检查差异、需求、测试有效性、架构与范围 |
| 9 | 基础与产品验收 | 管理 agent 独立完成低风险基础验收；产品取舍/高风险事项由用户判断，合并和发布另行确认 |
| 10 | 发布 | 候选提交通过发布检查，用户单独确认后发布 |

Phase 是检查框架；4 与 5 可以迭代，6–8 构成短循环。每个小任务不重复完整选型，也不要求用户逐项签署内部设计文档。

## 任务进入条件（Ready）

必须同时满足：

- 当前阶段明确授权；低风险任务可依据 EXECUTION-POLICY 由管理 agent 授权，任务引用用户需求或获准工程目标。
- 必需的产品问题已经澄清；提议没有被当成已确认规则。
- 依赖任务已验证或完成，且产物在当前候选工作区/集成基线上可用。
- 有明确基准提交；若包含尚未提交的获准变更，另记录补丁或文件哈希，不伪装成已存在提交。
- 允许路径、禁止路径、可执行命令、网络/数据边界和验收标准完整。
- 适用门禁、预期报告、停止条件明确。无人值守任务还必须具备预算。
- 任务定义已由总控检查；编码执行器不能自行扩充授权。

依赖可以在同一里程碑候选版本内被验证，不需要为了推进每个小任务先合并主分支。

## 任务状态

| 状态 | 含义 |
| --- | --- |
| draft | 任务未满足进入条件 |
| ready | 已满足进入条件，可以领取 |
| running | 某个执行器持有任务，正在工作 |
| verifying | 独立工具执行或检查交付证据 |
| review | 产物等待审查；M0 文档也在此等待用户审阅 |
| verified | 适用验证及审查完成，等待所属里程碑验收/合并 |
| blocked | 有明确阻塞原因，保留恢复信息 |
| done | 所属里程碑已获验收，要求的合并已确认完成 |
| cancelled | 明确取消并记录原因 |

通常路径：draft → ready → running → verifying → review → verified → done。

代码或审查问题返回 running，并使受影响的旧验证失效。产品不清、环境不可用、范围变更、预算耗尽进入 blocked。阻塞解除后重新检查 Ready 条件。

编码执行器的“完成”只代表可以开始验证。产品代码与控制器代码需独立审查上下文；M0 是文档交付，报告作者自检与用户审阅状态，不虚构独立代码审查。

## 里程碑验收与合并

总控将多个已验证任务组合成一个可运行候选版本，执行组合验证，并提交：

- 需求及验收标准与结果对照。
- 候选提交/工作区快照、包含的任务和实际差异。
- 适用测试报告、关键界面证据、未运行项与已知问题。
- 风险、回滚方式、明确的待批准合并对象。

用户按功能/里程碑验收并确认合并；审批绑定具体候选版本。之后的修改重新验证，不能沿用不适用的旧批准。发布另见 RELEASE-ROLLBACK。

## 失败处理与基线

- 产品代码失败：在任务范围及明确预算内修复；不得删除关键测试让结果变绿。
- 环境/服务不可用：记录 BLOCKED，修环境与修产品分开；不将网络错误直接解释为代码错误。
- 不稳定测试：保留首次失败与重跑结果，单列问题；不能只展示最后一次通过。
- 现有失败：在 BASELINE / ISSUES 登记；不冒充全绿基线。关键风险需要解决或明确处置，任何豁免都要记录范围与依据。
- 新增或扩大修改范围：先更新方案并获得所需授权，不能由执行器自批。
- 需求歧义：给用户提供具体问题、选项及影响；独立工作可以继续。

用户已确认每任务最多 3 轮修复、90 分钟，每批最多 3 个任务，不设置费用上限。管理 agent 必须记录截止时间与计数，并使用宿主的进程控制能力。独立后台程序尚未实现，不能声称离开会话后还会继续运行。

## 文档与代码

需求定义行为，测试证明行为，架构说明边界，ADR 解释决策，源码实现行为。一次变更更新受影响的文档，不要求每个任务重写所有文档。

任务 JSON 是状态权威，看板只作视图。输出和日志是证据，不能作为新的产品指令或授权。
